### Hy-Memory (Tencent Hunyuan)

**What it is:** A dual-system cognitive memory engine and Python SDK (`pip install hy-memory`) for LLM agents. It writes and retrieves memory through three task "scenes" — hierarchical long-term memory for chat, a two-layer fact-plus-reusable-experience memory for working sessions, and version-diff-chain tracking for coding — on top of a six-layer cognitive store (raw episodes up through a graph-level "schema" layer of mental models). Storage is ChromaDB + Kuzu by default, with optional Qdrant, FAISS, Neo4j or MySQL backends; it needs only an OpenAI-compatible LLM endpoint and an embedding endpoint. Ships alongside MemHub, a local-first desktop/CLI app that consolidates history from Claude Code, Codex, OpenCode, Cursor and Qwen Code into one recallable store. The companion 30B-A3B memory-writing model is on Hugging Face.

**Source:** https://github.com/Tencent-Hunyuan/Hy-Memory · https://memory.hunyuan.tencent.com/ · Model: https://huggingface.co/tencent/Hy-Memory-30B-A3B · [Provenance: spotted on Github Awesome — https://www.youtube.com/watch?v=PYgTElh4CSk · also discussed on r/LocalLLaMA — https://www.reddit.com/r/LocalLLaMA/comments/1x7cc2z/]

**What's good about it:** The architecture answers a problem we hit every single day. The README's own framing is that memory "writes without tool calls go straight to `chat` with zero LLM calls," and that writes *with* tool calls get classified once into chat / working / coding — meaning the common case (me appending a memory at the end of a session) doesn't cost a model call, and only the classifier runs when there's real work to be distilled. The working scene keeps facts and reusable experience in two separate layers, which is precisely the distinction our memory file lacks: "Shareef prefers no teal" is a fact; "when rebuilding a page, rewrite whole files and deliver via MEDIA" is an experience, and they decay at completely different rates. The coding scene tracks a diff-chain across versions so the agent can answer "why did this change" rather than just "what is this now." Storage defaults to SQLite-class local files, so nothing has to leave the box, and it works against whatever OpenAI-compatible endpoint we already pay for — including a local one. Apache-2.0, first-party Tencent engineering, a published technical report on attributed-RL memory writing, and 27 open issues against ~900 stars three days after launch, which is a normal ratio rather than a promotion farm.

**Pros:**
- Runs on our existing infrastructure: any OpenAI-compatible LLM plus an embedding endpoint; ChromaDB + Kuzu by default, no managed service required.
- Three scenes with different write disciplines — chat memory is hierarchical and cheap, working memory separates facts from reusable procedure, coding memory keeps a version diff chain.
- Automatic scene routing with a documented zero-LLM-call fast path for plain chat writes, which keeps the cost of remembering something trivial at essentially zero.
- Optional backends we already understand (Postgres-family via MySQL cache layer, Neo4j, Qdrant, FAISS) if we outgrow the defaults.
- Per-call embedding endpoint override, including a context-manager form for concurrency-safe endpoint switching — useful if we want one memory store for the VPS and one for the desktop.
- Apache-2.0 with a real company behind it; the companion memory-writing model is downloadable, so we can later do extraction locally instead of paying per write.
- MemHub is genuinely useful on its own for the desktop: one recallable store across the coding agents Shareef already touches.

**Cons:**
- ChromaDB + Kuzu as defaults are two more stateful stores to back up and keep coherent; neither is Postgres, which is what our other systems use.
- The memory-write quality argument leans on the 30B model in the technical report. Running extraction through a hosted chat model instead means the RL-tuned writing behaviour isn't what we actually get.
- It is three days old at this commit and Tencent's release cadence for these repos is fast — v2.0.3 today does not guarantee the API in a month.
- The README documents routing and backends thoroughly but the deployment story for "one store, several agents, one of them a cron job" is not spelled out.
- License file and badge agree (Apache-2.0) — but the 30B model on Hugging Face carries its own terms; check before ever serving it locally.
- Memory poisoning is the real risk with any agent-writable store: if a cron job writes a bad lesson, it's recalled forever. There's no built-in review/approval step mentioned.

**Should we...**
- ✅ **Adopt it** — integrate into our stack (strongly recommended)

**Impact on our stack:** High — **Hermes / the agent's long-term memory**. Concretely: move the prose memory file to a structured store the agent can query — facts about Shareef, the department and the stack in the fact layer; procedures ("deploy = stop, rm, up, not restart"; "never @montefiore.org from the VPS") in the experience layer; and per-project coding chains for the Unified Platform, the interview portal and the brief pipeline. That turns "what do we already know about X" from a 6,000-character reread into a scoped retrieval, and it gives the memory a place to grow that isn't the prompt budget.

**Why:** Of everything scanned today, this is the only item that changes something we already do badly. Our memory is a flat markdown file capped at 6,000 characters, and we are at 96% of it — which means the system's accumulated knowledge about this operation has been forced into a fixed box, and the pruning pressure has started deleting things that mattered. Hy-Memory's whole premise is that memory should be layered, typed by scene, written through an extraction step rather than by appending, and retrieved by relevance rather than read in full. The adoption path is honest: run the SDK against the endpoint we already use, point it at SQLite-backed defaults, seed it with the current memory file decomposed into facts and procedures, and run it in shadow alongside the markdown file for two weeks so we can compare what it recalls against what we'd have written. If it recalls better, the markdown file becomes a summary index into the store. The reason it earns adopt rather than watch is that it costs us no new vendor, no cloud account and no credentials on a datacenter IP — it is a Python package against an endpoint we already trust — and the feature it replaces is our most obviously constrained one. The cautions are real: keep a review step on writes from cron, back up the Chroma and Kuzu directories like we back up Postgres, and don't let the 30B model anywhere near the VPS.

### gitai

**What it is:** An open-source, MIT-licensed reimplementation of the source-control design Anthropic described for its internal "Scion" system — Git for fleets of coding agents. Server-centric: clients stay online and fetch only the objects they need, history questions (blame, path history, ancestry, code search) are answered and memoized server-side, changes land through compare-and-swap instead of a merge queue, every change is a changeset in a write-ahead log in SQLite or PostgreSQL with packs in object storage, and agents are first-class users with per-agent tokens, an RPC allowlist and branch policies.

**Source:** https://github.com/feder-cr/git-ai · [Provenance: spotted on Github Awesome — https://www.youtube.com/watch?v=PYgTElh4CSk]

**What's good about it:** It is the rare "rethink X for agents" project that names its own limits on the front page. The `LIMITATIONS.md` opens with "what Graft is not": not a hosting product, no web UI, no issues, no merge-request review, no CI, and — importantly — "not a security boundary by itself," because the access policy is local configuration and whoever can edit the config can re-point permissions. It also states outright that it is not a Scion implementation and doesn't reproduce Anthropic's internals, which is the honest version of the claim most projects would inflate. Beneath the candour is real engineering: per-agent tokens because the policy decides on the *token's* agent name rather than the acting user the client claims; `graft-verify` that tests the tip, bisects a failure and reverts the culprit change; sparse clones that materialize only the paths asked for; and a landing benchmark of 250 simultaneously-edited changes resolving every conflict. Version 0.2.0, unit + end-to-end + multi-node + crash + fuzz tests, with a `shadow` mode that lets you mirror existing repositories before switching to `authoritative` — a migration path rather than a hard cutover.

**Pros:**
- Designed for the actual failure mode of parallel agents on one branch: 250 concurrent changes landing through compare-and-swap instead of a merge queue.
- Honest, detailed documentation of what it does not do, including a security page — which is the first thing I look for in anything that touches source control.
- MIT, one Go build server + CLI, SQLite by default (Postgres when we need it), objects in file/S3/GCS/Azure storage.
- Shadow-mode migration means we could mirror a repo, compare, and only then make it authoritative — reversible by design.
- Per-agent identity with an RPC allowlist is the shape of control we want when several agents share a workspace.
- Vendor-neutral by construction: the server never calls a language model.

**Cons:**
- It solves a problem we don't have. We have manual deploys, a couple of repos and a handful of agent sessions — not hundreds of agents racing on one branch.
- No web UI, no issues, no review workflow, no CI: adopting it means either keeping GitHub/Gitea alongside it or losing those surfaces entirely.
- It is a fork/reimplementation lineage that carries GitLab Inc. copyright in the LICENSE alongside the author's — MIT for everything outside an optional `ee/` directory, but "which parts are which" is exactly the kind of thing to read before depending on it.
- Everything it replaces is load-bearing for the team's collaboration; the migration cost lands on people, not machines.
- 0.2.0 with "interfaces may still change before 1.0," so a deploy pipeline built on `graft` CLI commands today may need rewriting.
- Known gaps exist in the storage core (e.g. pack garbage collection) and are documented as gaps, not features.

**Should we...**
- 👀 **Watch it** — keep an eye on it, not ready yet but promising

**Impact on our stack:** Low — none of our systems improve measurably today. The only plausible future use is if the Unified Platform and interview portal repos end up with many concurrent agent branches, which we are nowhere near.

**Why:** gitai is the most technically credible item in the scan and the least relevant to us, and the gap between those two facts is why the verdict is watch rather than adopt. The problem it solves — server-side history, sparse fetch, compare-and-swap landing, per-agent tokens — becomes real at a scale we genuinely do not operate at: our repos are deployed by hand and our parallelism is a couple of sessions, not a fleet. Adopting it would mean running a second source-control server, losing the GitHub surfaces the team actually uses for review, and accepting a 0.x CLI in the deploy path, all to solve contention we don't experience. What is worth taking from it now is the shape of the idea, not the binary: per-agent tokens with an allowlist, and branch policies that say what each agent may do, are patterns we should carry into whatever we build to let agents touch deployed repos. Revisit if we ever have several agents landing changes on the same branches in a day — which is a plausible consequence of running more cron agents, but not today's problem.

### Harness² (google-research/harness2)

**What it is:** A Google Research framework for "recursive agent harnessing" — automatically improving the scaffold around a frozen model rather than the model itself. Two nested loops: task-level recursion runs a Propose–Probe–Compose step that edits the harness for the current task and picks the best variant from behavioural contrasts (no ground-truth feedback needed), while harnessing-level recursion records adopted harnesses and evidence-supported lessons into a persistent "improvement harness" that guides future tasks. It exposes eight editable harness components (system prompt, guardrails, memory, tool guidance, subagents, skills, scripts, plugins) and ships with JobBench, LAB and WorkBuddy-Bench, OpenCode/Codex executors, and parallel or sequential recursion.

**Source:** https://github.com/google-research/harness2 · Paper: https://arxiv.org/abs/2610.14224 · Site: https://harness2.github.io · [Provenance: GitHub search + HN — https://news.ycombinator.com/item?id=50146503 · also named in the Github Awesome rundown]

**What's good about it:** The framing is the useful part, and it's stated in one sentence: "a harness is the system around a model that enables it to act as an agent — prompts, tools, memory, skills, orchestration." That is a precise name for what our cron jobs actually are. Every scheduled job we run is a hand-tuned harness around a frozen model, and we have never systematically varied one — we tune by feel, one prompt at a time, with no record of which variant produced which outcome. The paper's contribution is methodological: hold the model fixed, vary only the scaffold, and attribute score changes to the scaffold. The eight-component decomposition is also a ready-made audit checklist for any agent we already run: what is the system prompt, what are the guardrails, what memory does it get, what tools, which subagents, which skills, which scripts, which plugins. A local demo runs both recursion modes with deterministic editors and requires no model credentials, so the mechanism is inspectable without spending anything.

**Pros:**
- Names and decomposes the thing we already build by hand, into eight components we can audit one at a time.
- Contrarian-but-correct default: most gains attributed to "better agent" work come from the harness, not the model — this framework measures that properly.
- No-ground-truth Propose–Probe–Compose means it can refine a harness on tasks where we have no labels, which is most of our operational work.
- Persistent improvement harness with evidence-backed lessons is a real alternative to prompt tuning by intuition.
- Google Research with an arXiv report, Apache-2.0, and a runnable local demo that costs nothing.
- Parallel and sequential recursion both supported, so it can be run cheaply (one extra probe) or thoroughly.

**Cons:**
- Model-backed benchmarks need Vertex AI, a GCP project, `gcloud auth application-default` and Node 20+; WorkBuddy-Bench needs Docker. That is a new cloud dependency we do not have.
- Executors are OpenCode and Codex — not Hermes. Adapting it to our runtime means writing an executor, which is real work before any benefit appears.
- README explicitly notes executor network access is unrestricted and Codex runs with its sandbox config — not something to point at production credentials.
- Repo has no description on GitHub, which for a research release usually means "paper artifact," not "thing to depend on."
- Benchmark gains are reported on professional-task benchmarks (WorkBuddy, JobBench, LAB), not on the operational, tool-heavy work our cron jobs do.
- A few days old with a research release cadence: no meaningful track record of the improvement loop holding up outside the paper.

**Should we...**
- 👀 **Watch it** — keep an eye on it, not ready yet but promising

**Impact on our stack:** Medium — **Hermes cron**. The concrete change is an audit: for each scheduled job, write down its eight components and its allowed write scope, then run one deliberate variant and measure. That is not adopting the framework; it's adopting the paper's discipline.

**Why:** The value here is a method we can start using today without installing anything, and a framework we should probably never install. The method: our daily brief, the vault filer, the watchdogs and the deploy jobs are all harnesses around a frozen model, and we have never once held one constant and varied a second to see which mattered — we change the prompt when an agent misbehaves, and file the result as "better." Harness²' eight components give that work a checklist, and its insistence on fixing the model first is the discipline that makes any comparison meaningful. The framework itself is a research artifact: Vertex AI credentials, gcloud login, Node, Docker per benchmark, and executors we don't run. The right move is to take the decomposition, spend an hour writing down what each of our cron jobs actually has in each of the eight slots and what it can read and write, and treat the framework as a reference for how to run controlled variants once we've done that. If a Hermes executor ever appears, or if the improvement-harness idea shows up as a small library rather than a benchmark suite, this becomes adoptable — but not before.

### Murmur (local meeting notetaker)

**What it is:** A local, bot-free meeting notetaker for Windows 10/11. It records the microphone and the computer's audio (WASAPI loopback) as separate tracks, runs voice-activity detection, echo cancellation, Whisper/Parakeet recognition and speaker separation on the local GPU, then writes notes, decisions and action items using whichever AI provider you configured — sending only text, and only for summaries. A FastAPI/uvicorn backend on 127.0.0.1:8765 streams the live transcript over a WebSocket; import of existing mp3/m4a/wav/mp4 files and TXT/SRT/Markdown export are supported.

**Source:** https://github.com/muradiodev/murmur-notetaker-copilot · [Provenance: GitHub search — new AI-agent repos, created 2026-10-17]

**What's good about it:** It solves the right half of the problem correctly for our situation. Recording Zoom, Teams or a phone call through a bot that joins the meeting is a non-starter in a hospital — it announces itself, it needs calendar access, and it puts a third party in the room. Murmur records the desktop's own audio instead, which means nothing joins and nothing is announced. The architecture is honest about the trust boundary: recognition, diarization, VAD and echo cancellation run locally, and "only text goes to the AI provider you pick, and only for summaries" — so a recording of a residency meeting never leaves the machine, and only the redactable summary text is sent. It also does the small things that make it usable: click-a-word to seek, playback at 1.5×/2×, screen-share capture placed at the right second, and export to SRT and Markdown, which is the format our briefs and vault already speak. MIT licensed.

**Pros:**
- No bot joins the call — it captures system audio locally, which is the only acceptable model for a clinical or academic meeting.
- Local ASR/diarization/VAD; only summary text is sent, so raw audio stays on the machine.
- Import an existing recording and get a transcript plus action items — useful for the 28 faculty interview clips if a transcript is ever needed.
- Markdown export lands directly in the shape our briefs and vault use.
- MIT, Python 3.12, FastAPI backend on localhost — inspectable and modifiable.
- Built-in summary step turns a transcript into decisions and action items, which is the part people actually reread.

**Cons:**
- Windows-only (WASAPI loopback for system audio), and it wants an NVIDIA GPU for the CUDA models — so it lives on Shareef's desktop and nowhere else. It cannot run on the VPS or the Mac.
- It needs an API key for one of Anthropic, OpenAI or NVIDIA just to summarize; there is no documented "point it at a local vLLM" path in the README.
- Always-on audio capture is exactly the kind of background process that drains a laptop and gets the user to switch it off — nothing in the README addresses battery, idle pause, or a time cap.
- Created 2026-10-17, two days old, small star count, one author; no evidence of use on long meetings yet.
- Diarization tells voices apart but does not verify who they are — in a room of residents with similar accents that matters.
- Recording patient-adjacent conversations raises HIPAA questions that no README can resolve; the safe use is internal academic and administrative meetings only.

**Should we...**
- 👀 **Watch it** — keep an eye on it, not ready yet but promising

**Impact on our stack:** Medium — **voice / knowledge capture**, on the desktop only. Concretely: Grand Rounds, residency committee and M&M meetings could produce minutes and action items without a person typing, and the Markdown export would feed the vault. It won't touch cron, the Unified Platform or the CRM.

**Why:** The capability — a private, locally-transcribed record of what was actually said in a meeting — is worth having, and this is the first notetaker in recent memory that gets the trust boundary right: no bot in the room, no audio off the machine, only summary text to a provider we choose. What keeps it at watch is placement and maturity. It only runs on Windows with an NVIDIA GPU, so the adoption is a single-user desktop install, not a system change; it's two days old with one author; and continuous capture is a battery and privacy cost that nobody has yet measured over a three-hour meeting. The plan if we pursue it: install on the desktop, run it on one internal Grand Rounds with the AI summary disabled (transcription only, fully offline), check the transcript quality and battery behaviour, and only then decide whether the summary step is worth pointing at a provider — for internal academic meetings only, never in a patient encounter. If it holds up, the transcript goes through the same copy-desk and filing discipline everything else does.

### earshot

**What it is:** "Ears for coding agents" — a CPU-only local tool that turns sound into something an agent can reason about: describing what a file sounds like in words, matching a recording against a described sound, finding the best moment inside a long recording, transcribing a whole film's audio second by second, generating a scorecard against launch films, and synthesizing its own sound effects in code (a 201-effect code bank that renders by id with no models and no network). Runs as a CLI, a Python API, and an MCP server.

**Source:** https://github.com/Leonxlnx/earshot · [Provenance: Github Awesome — https://www.youtube.com/watch?v=PYgTElh4CSk · also top of GitHub's new-repo list for AI agents, 2026-10-15]

**What's good about it:** The underlying observation is sharp and true: agents can now write the code that renders a film or a game, and they still cannot hear what they made — they can't tell a premium key press from a cheap one, or notice that a hit lands 80 ms after the cut. Turning sound into labelled evidence with confidence scores (the `z` values in its output) is a genuinely new capability class, and doing it CPU-only with an MCP server means an agent could check its own audio output without any special hardware. The engineering discipline shows in the small decisions: the launch film's sounds were all made in code, the evaluation data isn't redistributed (only derived numbers), and the license section separates MIT for code from the models' own licences (CLAP Apache-2.0, AST BSD-3-Clause) rather than glossing over it.

**Pros:**
- Real capability gap closed: audio evidence an agent can reason over, not just audio files.
- CPU-only, local, MCP server included — no GPU, no cloud, no accounts.
- Explicit licence separation between the MIT code and the models' own terms.
- The no-model effect bank (`earshot sfx`/`kit`) renders sounds by id in seconds with no network.
- Honest about evaluation limits: licensed reference recordings aren't in the repo, so the benchmark's fancy scorecards need refs you bring yourself.

**Cons:**
- The domain is launch films, product demos and game sound. We produce none of those — our audio is phone calls, meetings and maybe voice memos, none of which this is built to judge.
- First model call loads torch + CLAP + AST weights, roughly 20–40 s on CPU, which is a poor fit for a cron job that needs to answer in seconds.
- Bring-your-own reference set: the "how well does this fit the brief" feature only works with a local registry of licensed recordings, so the headline capability is out of the box only partially.
- Launched 2026-10-15, 0.3.x, effectively one author; the evaluation story is a research demo, not a track record.
- For any capture use we'd have to feed it recordings, and our recordings are the sensitive kind.

**Should we...**
- ❌ **Skip it** — not relevant, redundant, low quality, or not useful for us

**Impact on our stack:** Low — no system improves. The only conceivable hook is voice-memo quality checking for the Telegram voice replies, and a 20–40 s CPU model load per call is worse than listening to the memo.

**Why:** This is a well-built tool aimed at a problem we don't have. Its entire vocabulary — transient, attack, brightness, launch-film scorecard, whoosh, hit, click — is the vocabulary of sound design, and our audio output is text-to-speech voice memos and our audio input is meetings. The one plausible overlap, checking TTS quality, is actively a bad fit: it needs models loaded and 20–40 seconds of CPU before it answers, which is more expensive than the thing being checked. Nothing here is wrong; it's just aimed elsewhere. Skipping it frees the attention for the memory layer, which is where today's real gain is.

### tkmd

**What it is:** A single-binary Rust CLI (plus a stdio MCP server) that stores every task as a plain Markdown card with YAML frontmatter, schedules them with Critical Path Method and Design Structure Matrix maths (critical path, buffers, circular deadlock detection), and — the interesting part — makes an agent pass an automated shell verification gate (`eval`) and submit work for human sign-off (`pending-close`) before a task can transition to done. Local-only: zero network requests, POSIX file locking, optional Obsidian Kanban board sync.

**Source:** https://github.com/ktreharrison/tkmd · [Provenance: HN — https://news.ycombinator.com/item?id=50146130]

**What's good about it:** The core rule is exactly the control we keep wanting: an agent cannot mark its own work finished. It has to run the check and then hand it to a human, which is the difference between "the agent says it's done" and "the check passes and someone signed off." Storing tasks as Markdown cards with frontmatter means they diff, they live in the repo, and they're readable without the tool. The scheduling maths (CPM critical path, DSM dependency loops) is real rather than decorative, and the offline/no-network posture is the right default for a task store that may end up holding internal work descriptions.

**Pros:**
- The verification gate and sign-off step are the right shape for agent task governance.
- Plain Markdown cards, human-greppable, Git-friendly, readable without the tool installed.
- Real scheduling algorithms — critical path and deadlock detection rather than a flat list.
- Zero network, single binary, file locking — no daemon, no cloud, no accounts.
- One-command resume of the exact agent session attached to a task is a genuinely nice touch.

**Cons:**
- One day old (created and pushed 2026-10-18), seven stars, one author, no community, NOASSERTION licence — this is the textbook "watch at best, no matter how many stars" case.
- It replaces nothing we already have cleanly; our tasks live in the cron jobs themselves and in conversation, and adding a task store means a new ritual the team won't adopt.
- Rust binary moving fast at 0.0.x — the card format and CLI will churn.
- The CPM/DSM scheduling is overkill for the handful of parallel tasks we actually track.
- Obsidian + CLI dual mode is a nice feature but doubles the surface area for a first-week project.

**Should we...**
- ❌ **Skip it** — not relevant, redundant, low quality, or not useful for us

**Impact on our stack:** Low — no system changes. The idea of a verification gate belongs in our cron jobs, but as a five-line wrapper around each job's own check, not as a dependency.

**Why:** The idea is worth keeping and the artifact is not. "Agents may not mark their own work done until a check passes and a human signs off" is a rule we should enforce — but we can enforce it in the cron scripts that already exist, by making each job run its own verification and report pass/fail rather than asserting success. Adding a one-day-old Rust binary with an unresolved licence, an unproven card format and a task board nobody asked for, in order to get a gate we can write ourselves, is the wrong trade. Skip it, and write the gate.

### agent-bridge

**What it is:** A single Go binary that exposes an OpenAI-compatible API (`/v1/chat/completions`, `/v1/models`) and satisfies every request by running a coding-agent CLI in headless mode — Claude Code (`claude -p --output-format stream-json`), the OpenAI Codex CLI, or the Kimi Code CLI — with tool calling, MCP servers, sessions, streaming and per-agent models passed through.

**Source:** https://github.com/R3n3r0/agent-bridge · [Provenance: HN — https://news.ycombinator.com/item?id=50140329]

**What's good about it:** It's a clean, focused piece of engineering: one Go binary, standard library only at runtime, Linux/macOS/Windows, and a genuinely useful idea — if any OpenAI-speaking framework can talk to a headless coding agent, then tools built for chat completions (LangChain, CrewAI, the OpenAI SDKs) can drive a coding agent with no adapter code. It states plainly that it's independent, runs the official `claude` binary without modifying it, and "never accesses its credentials."

**Pros:**
- Single binary, no runtime dependencies, all three major platforms.
- Works with unmodified OpenAI SDKs — only `base_url`, `api_key` and `model` change.
- Supports function calling, MCP servers, sessions and streaming pass-through.
- Backend-agnostic: Claude Code, Codex, or Kimi Code behind the same API.
- Clear statement of independence and of what it does with credentials.

**Cons:**
- It wraps CLIs we don't run. Hermes is its own harness with its own provider layer — inserting a CLI-in-a-subprocess behind an HTTP chat endpoint adds a moving part and removes observability.
- The pattern it enables — automating a subscription-authenticated coding agent from a server — is precisely the shape of thing that got us in trouble with a vendor account before, and it is not the model to repeat from a datacenter IP.
- Two-day-old-ish repo with an unclear maintainer footprint; it runs an official binary whose output format can change at any time.
- Function calling through a text CLI's JSON stream is lossy by nature, whatever the README claims.
- No stated licence in the sources I could verify quickly, which is a blocker before any dependency.

**Should we...**
- ❌ **Skip it** — not relevant, redundant, low quality, or not useful for us

**Impact on our stack:** Low — Hermes already has a provider layer; nothing about our agent stack needs an OpenAI-shaped facade in front of a coding CLI.

**Why:** The problem agent-bridge solves — letting OpenAI-shaped frameworks talk to Claude Code — is a problem we've deliberately avoided having. Our stack talks to model providers through Hermes' own provider configuration; there is no CrewAI or LangChain orchestrator that needs a chat-completions endpoint pointed at a coding CLI, and introducing one would put a subprocess and a JSON stream between us and the thing that's actually working. More importantly, the core trick is using a subscription-login CLI programmatically, which is the operational shape that has burned us before; whatever else is true, we do not want to make that easier to do from a server. Skip it.

## Overall Assessment

Today's brief is honest about a narrow day: one item that should change how we work, one framework whose method is worth stealing without the software, and a local tool that would be good on the right machine.

**If we do nothing else, do these, in this order:**

1. **Pilot Hy-Memory as the agent's memory layer.** Seed it from the current memory file split into facts and procedures, run it against the same endpoints we already use, and keep the markdown file as a summary index for two weeks. This is the only item today that removes a real ceiling — we are at 96% of a 6,000-character file that is supposed to hold everything the system has learned about this operation.
2. **Run the Harness² audit — the checklist, not the framework.** For each cron job, write down its eight components and its actual read/write scope, then change exactly one thing and measure. It costs an hour and will almost certainly find a job whose write scope is wider than its job description.
3. **Trial Murmur on the desktop for one internal meeting, transcription only.** If it produces a usable transcript without wrecking battery or needing a bot in the room, it becomes the way Grand Rounds and committee meetings get minutes — with the AI summary step considered separately and internally only.
