### measured-type — Bringhurst with numbers attached, tested in a browser, and an evidence table that admits when it lost
**Link:** https://github.com/PetriLahdelma/measured-type (author Petri Lahdelma; created **29 October**, pushed **2 November**, 17 stars, 1 fork; text CC BY-NC 4.0, scripts MIT; on HN via the `typography` feed today)
**Type:** Tool
**What it is:** An agent skill (a `SKILL.md` plus dependency-free scripts) for web typography that does two things almost no typography prompt does. First, it **numbers Bringhurst's rules so a review can cite them** — `§2.1.2` comfortable measure, `§2.2.1` leading suits face and measure, `§2.3.1–2` mark paragraphs one way, `§2.1.3` ragged unless justification is ear — and then translates each into CSS that ships today: `max-inline-size: 34em`, unitless `line-height`, `p + p { text-indent: 1em; margin-block-start: 0 }`. Second, it **classifies the text before styling it** — reading text, display text, and interface/data text get different rule sets, with interface text getting tabular lining figures, end-aligned numbers, positive tracking on uppercase labels, and recoverable truncation — and it says explicitly to scope reading-text rules to a prose container so they don't leak into buttons. The scripts measure what can actually be measured: line length counted per line rather than trusting `ch`, growth under 200% zoom, contrast in both colour schemes, and font coverage. It ships a bundled Chromium, and when there is no browser it **estimates and says which claims it could not check**. It pairs with the same author's Stylelint plugin Rhythmguard, and the two are documented meeting only at the type scale.
**What's good about it:** The `## Evidence` table is the most honest artefact I have read in this entire run of briefs. It reports eleven experiments with run counts, model names, dates and p-values, and it repeatedly reports **the skill losing**. On line length: "with a browser, a model without the skill measures and fixes the same faults" — 24/24 both ways. On fluid heroes under zoom, a **one-sentence hint beat the skill** (1.63× growth against 1.50×, p < 0.0001), mostly by cheating on the requested desktop size. On the held-out set the score was 34/34 against 33/34, and the author's own summary is "**no measurable difference**." The conclusion drawn is the correct one and almost nobody draws it: the guidance is not the value, **the measuring tools are** — the bundled Chromium is what moves the number. Second, the `type-scale.js --fit` episode is a small masterclass in tool design: before `--fit` existed, 14 of 20 runs met the zoom bar by silently giving up the 72px desktop size the brief asked for; after it, 20/20 met both, because the tool prints the two-slope answer instead of hoping the model does the ratio math. That is "make the constraint executable rather than descriptive," and it is the single most reusable idea in the repo. Third, the rule content is genuinely competent and specific: **a 66-character measure is not 66ch in Verdana** (it sets about 81), and counting lines rather than units is exactly the correction a working typographer makes.
**Pros:**
- Every rule carries a citation (§ numbers) and a measured check, so a review comment can say *why* rather than *"feels cramped"* — that is the difference between taste and an argument, and it's what our review process lacks.
- The zoom-under-200% analysis is a real accessibility finding, not a style opinion: `clamp()` heroes written the obvious way **grow only 1.58×** when rem doubles and the viewport halves, and WCAG 1.4.4 has no ratio of its own, so nobody catches it.
- The text-type classification prevents the most common AI typesetting error — applying book rules (indents, measures) to buttons — which is exactly what generated UI gets wrong.
- Independence is verifiable: commits, run files and graders are committed, cases were frozen before the held-out runs, and the author reports incidents.
- It is tiny and portable (Markdown + stdlib scripts), so it can be read as a document by a human reviewer with no installation at all.
**Cons:**
- **17 stars and one author, four days old.** This is a research notebook, not a tool with users. Nothing here has survived a team, a legacy codebase, or a non-Tailwind dialect.
- **The licence is unsettled in exactly the way that matters**: the text adapts `webtypography.net` under **CC BY-NC 4.0**, and the README states plainly that "whether paid client work may use it is not settled." For a hospital marketing department producing commercial-adjacent material, non-commercial text is a real question, not a pedantic one.
- It only tests **Claude** models. Every eval number in the table is Opus/Sonnet 5.5; our pipeline is not that, and the triggering results (78/78 loads with Opus, 44/48 with Sonnet) may not transfer at all.
- The measured gains are **narrow and honestly small** — line length and one zoom case. It has nothing to say about hierarchy, contrast of *meaning*, or whether the page is any good.
- Requires `npm install` and a Chromium download for the measuring half, which contradicts its "small skill" register.

**Should we...**
- ✅ **Adopt it**
**Why:** Adopt the **two checks, not the skill**. The value that survives its own evidence table is measurement, and two of those measurements are immediately worth running on our surfaces. First, **count characters, don't trust `ch`** — a 66-character measure in a wide face is 81 characters in reality, and this is the cheapest single typographic fix available to any page we publish, including the residency landing pages and the Sub-I long-form copy. Second, **check what happens at 200% zoom**, because a `clamp()` hero that grows 1.58× is a hero that fails the one accessibility test nobody visually reviews — and our platform's display sizes are set by hand, which is exactly the pattern that produces this. Third, adopt the **`§`-numbering habit** for review: when someone says the paragraph text is "too wide," cite `§2.1.2` and a character count and the conversation ends with a fix instead of a preference. Where it fits: **Chapter Player** body copy and reading surfaces, and any marketing page with long prose. Where it does **not** fit: the **Unified Platform's dense UI**, where the skill's own advice (tabular figures, tracked uppercase labels, recoverable truncation) is already the system's behaviour, and where the NC licence on adapted text should be resolved by counsel before any of it is copied into our repo. The honest reason this is Adopt rather than Watch is that the *checks* cost nothing and are correct; the reason to be careful is that the *author* is four days into a project that admits most of its claims are indistinguishable from a one-sentence hint.

### designspec — the design system as a spec agents must read and CI must enforce, with a proposal gate for changing it
**Link:** https://github.com/Eronred/designspec (npm `designspec-kit`; MIT; created **31 October**, pushed **2 November**, 10 stars, 1 fork; source of the HN `AI design` feed lead today)
**Type:** Tool
**What it is:** A CLI that reads your existing design system **out of your code** into a `design/` folder — `tokens.json` in W3C DTCG format with theme modes, per-component contracts extracted from `cva()` / `tailwind-variants` / union props (variants, defaults, and a `controls` list of what each variant owns), a `rules.md` in plain language, and a baseline of violations that existed at adoption — then makes AI agents *read it* (`AGENTS.md` section, two skills, an MCP server wired into `.mcp.json`) and makes CI *enforce it*. The rule set is the interesting part because it targets the drift that lint rules miss: `no-hardcoded-color` (`bg-[#e5484d]`, `fill="#000"`, `StyleSheet.create`), `no-palette-color` (`bg-red-500`), `prefer-ds-component` (native `<button>` when the system has a `<Button>`), **`no-unknown-variant`** (`<Button variant="ghost2">`), and **`no-variant-override`** (`<Button className="h-12">` — overriding the height a size variant controls). Every finding carries a **corrective suggestion**, not just a complaint: *"Closest token: text-foreground"*, *"Allowed: default, destructive, outline, ghost, link. Need a new one? Run `designspec propose`."* And that last sentence is the real architecture: changes to the system itself go through **explore → propose → apply → verify → archive**, where the proposal declares what should change in front matter and `verify` checks the code did exactly that and nothing else. It reports against **changed lines only** by default, so adoption doesn't require fixing a legacy file first.
**What's good about it:** It attacks the failure I would name first if asked what actually rots a hand-built dark React UI, and it is *not* hardcoded hex. It is **variant inflation** — one panel needs slightly tighter padding, so somebody writes `className="px-3 py-2"`, and eighteen months later there are 147 looks for one component. This tool names that precisely: `controls` declares which CSS properties each variant owns, so an override is detectable as a *category* of error rather than a style preference, and `fix` rewrites the safe cases into real variants. Second, `explore` is the most design-director-shaped command in the repo: it opens with a **"design system adoption score — how much of the UI uses its components and color tokens"** and then shows you where code works around the system, with an example that could have come from our platform: `<Panel className="px-3 py-2">` written **100+ times**, which became `padding="compact"`. That is the correct output of a design-system audit — a *missing token*, not a list of sins. Third, the proposal gate is the one thing almost every other tool in this run lacks: it governs change to the system itself, so the answer to "AI invented `ghost2`" is a documented, reviewable `propose`, not a ban. Fourth, the print template is right: findings land as PR annotations, a maintained PR comment and a job summary, with **no server and no API key**.
**Pros:**
- Extracts the spec from code rather than asking anyone to write it by hand — which matters enormously for a React + Vite app nobody has fully documented, and `sync` keeps it honest.
- `--diff <base>` + `baseline.json` is the only adoption path that works on a live product: **it only ever reports on lines that changed**, so day one is not a 700-error wall.
- The corrective suggestions turn a lint failure into a fix instruction an agent can execute, which is the difference between a checker and a coworker.
- Fails the build for a UI change made without a proposal (`require-proposal`) and for code and spec disagreeing (`spec-drift`) — governance, not just linting.
- Real stack coverage for us: React, Next.js, **Vite**, Vue, Svelte; CSS variables including `.dark` and `[data-*]` theme modes; Tailwind v3 **and v4**; tokens from CSS vars, DTCG, Tokens Studio JSON or a Tailwind config.
**Cons:**
- **Ten stars, two days old, one author**, and the stack table is a claim about breadth that a two-day-old project cannot have verified across all of those. Treat "supports Vite + CSS variables" as untested until we run it.
- The whole model is **component-library shaped**. `cva()`, `variant` unions, shadcn/ui — our accent, type scale and spacing may not be declared the way it expects to read them, and the extraction could come back thin or wrong on the first run.
- It classifies values, not quality. A codebase that passes every rule is a codebase that is *consistent*; `no-variant-override` cannot tell a needed new variant from a lazy one, which is precisely why the proposal process exists and precisely why it depends on a human reading it.
- The proposal workflow is another ceremony for a small team. `explore → propose → apply → verify → archive` is five commands to add a `compact` padding variant, and in a department of our size the overhead may exceed the drift it prevents.
- Node/npm/yarn build-time tooling that assumes a CI culture; if the platform is deployed by hand, the enforcement half does nothing.

**Should we...**
- ✅ **Adopt it**
**Why:** Adopt `explore` and the message format, before adopting the gate. Run `npx designspec-kit explore` **read-only** against a copy of the Unified Platform and look at two numbers: the adoption score, and the list of repeated overrides. Those two lines are the most valuable diagnosis available of a UI I already suspect is drifting in exactly this way — buttons and panels overridden per-page instead of extended once — and it costs thirty seconds and changes nothing. Then adopt the *principle* regardless of the tool: **a repeated override is a missing token, and the fix is a system change, not a page change.** Where it fits: the **Unified Platform**, squarely, and the Chapter Player if it shares tokens. Where it does not fit: marketing and print, which live outside component contracts. The caution is specific and serious — this is a two-day-old tool by one author whose central claim is breadth across many stacks, and the worst possible outcome is porting the platform to a new spec format on a Monday because a README promised Vite support. Read-only this week; wire the gate only after `explore` proves it can actually read our tokens. That is why the verdict is Adopt: not because the tool is proven, but because the *diagnosis* is correct and cheap and the enforcement can wait until it earns the right.

### Affinity for iPad — the whole production suite, free for individuals, in one `.af` file
**Link:** https://affinity.studio/blog/affinity-update-ipad-2026 · App Store: https://apps.apple.com/us/app/affinity-by-canva/id6751323445 · coverage: https://9to5mac.com/2026/11/02/affinity-for-ipad-all-in-one-design-app-now-available-free-for-individuals · https://on.theverge.com/1024283/canva-affinity-for-ipad-design-app-availability (launched **2 November 2026**)
**Type:** Idea
**What it is:** Canva's single-app Affinity — vector, photo, page layout and sketching in one `.af` file, formerly three separate Serif apps — arrives on iPad with the same feature set as the Mac version, built for touch and Apple Pencil (pressure, tilt, **barrel roll, squeeze, hover** on the Pro). New iPad-first behaviour: **Sketch Studio** for freehand work and sketch-to-vector, a Mask Tool, and **Sketch to Shapes**, which converts rough pencil strokes into clean geometric shapes (the "rotate the canvas forty times to get one line right" problem, addressed in software). Real-time non-destructive editing at up to 120fps with nothing exported or converted between disciplines; a project goes sketch → vector → composite → print-ready without leaving the tablet. **Completely free for individuals** (a free Canva account required); **the AI tools are the paid add-on** — Canva Pro at $18/month, or the business Affinity licence at $250/year — and AppleInsider's hands-on states plainly there is no other catch. Desktop Affinity has passed **seven million sign-ups** since going free a year ago.
**What's good about it:** Read past the product launch and the actual news is a **pricing structure that inverts the industry's default**. Every other vendor this year has put AI in the base tier and charged for craft. Canva has put craft in the base tier, free, for individuals, and put the *AI* behind the subscription. For a department that has to make Sub-I packets, fellowship announcements, print collateral and social creative on a public-hospital budget, that is the difference between a template farm and a real production tool: the good version of Affinity costs nothing, and the thing we are actively trying not to rely on is the thing that costs $18. Second, the **single-file, single-app model** is a genuine workflow decision rather than a bundling exercise — the failure mode of print collateral in a small department is a file that has been through five apps and lost its type, and `.af` removes that class of failure. Third, **Sketch to Shapes** is the only feature here aimed at craft rather than throughput: it shortens the distance between a pencil sketch and a vector, which is exactly the step where hand-drawn ideas die in under-resourced teams. Fourth, the seven million sign-ups are the only adoption figure in this brief that means anything, because they are users, not downloads of a free trial.
**Pros:**
- Free for individuals with no functional crippling — vector, photo and layout all usable, offline, at full speed — which makes it the only genuinely professional-grade stack reachable at zero budget.
- The AI being the *paid* tier means the anti-slop position costs us nothing to hold: we can run the whole craft pipeline without a template library anywhere near it.
- One `.af` file across sketch, vector, photo and layout ends the export/convert/re-import chain that quietly destroys typography in print handoffs.
- Pencil Pro's barrel roll and squeeze are used for real controls (canvas rotation, tool switching) rather than as gestures that trigger a toolbar; the product-design head's line — "made by people who've done exactly that" — is specific enough to be a claim rather than a slogan.
**Cons:**
- **It is still an Apple-only, subscription-adjacent ecosystem.** Free for individuals; a *department* is not an individual, and the business licence is $250/year per seat — the free tier is an acquisition funnel, not a policy, and it can change (Canva already caught criticism for making Affinity free once).
- **iPad-only hardware requirement** (iPadOS 18, 7th-gen iPad or later) means this is a second device, not a workstation; nobody is laying out a 40-page packet on a 11-inch screen, so it complements a desktop rather than replacing it.
- The launch coverage is uniformly press-release shaped — AppleInsider's "initial testing" is a few hours, and no reviewer has used the iPad build for a print job. Large-file performance on a base-model iPad is unverified.
- Zero AI-design intelligence here. Yesteryear's Vectorizer-grade "AI" inside Affinity is a paid add-on of unspecified quality, and this brief has no reason to trust it.
- It does not solve the actual constraint on our creative output, which is art direction and a voice — the cheapest version of that problem costs nothing and this product doesn't touch it.

**Should we...**
- ✅ **Adopt it**
**Why:** Adopt the **cost structure as a strategic fact**, and the app as a practical one. Strategically, this is the clearest available answer to the question every department eventually asks — "can we do professional print and social work without an Adobe seat and without Canva templates?" Affinity free-for-individuals means yes, with the same file running the whole pipeline; and because the AI is the paid tier, choosing to work this way is choosing *craft over generation* at no financial cost. That is a better internal argument than any anti-slop essay, because it is a spreadsheet and not an opinion. Practically, the honest fit for Shareef's surfaces: **Sub-I welcome materials, fellowship announcements, conference collateral and graduation print** — anything destined for a page rather than a screen — with Sketch Studio/Sketch to Shapes being the feature that could actually raise the ceiling, because the gap between a rough idea for a mark and a usable vector is where those projects stall. Where it does **not** fit: the **Unified Platform** and the **Chapter Player**, which are code surfaces and have nothing to gain from a tablet raster/vector app; and social creative that lives in a template pipeline would be *downgraded* by moving it here if the alternative is a real system. The caution to state plainly: $250/year business seats mean this is free for Shareef as a person and not free for the department, iPadOS 18 excludes older hardware, and the free tier is a funnel that has already been repriced once.

### Nubank by Koto — keep the logo, refine the purple, add proprietary type, and *remove* rules
**Link:** https://lbbonline.com/news/nubank-partners-with-koto-on-brand-refresh-as-it-expands-internationally · studio case: https://koto.com/projects/nubank · Nubank's own account: https://blog.nubank.com.br/brand-refresh-como-renovamos-a-identidade-visual-do-nubank (work launched 10 September in Miami; the design-press coverage is **2 November 2026**, Design Week / LBB)
**Type:** Idea
**What it is:** Koto's refresh of Latin America's largest digital bank as it enters the US with Nu Global — spanning identity, tone of voice and digital, and built on one stated idea, "effortless banking, designed to delight." The method is the opposite of a rebrand: the **logo and wordmark were kept** because they carried equity, and everything else was rebuilt around them. The signature **purple was refined** inside a wider palette with new secondary, illustration and sub-brand palettes; the brand got its **first proprietary typefaces, Nu Sans Display and Nu Sans Text**, so type can move between bold expression and functional clarity; a small set of ingredients stretches across markets, products and channels with **motion carrying the same logic** from brand moments into illustrations and app interactions; and Koto built Nubank's first global photography library — **50+ photos and films** of families, travellers, students, fans and professionals, made to work across both marketing and product. It has to hold five different registers at once — pop/accessible Nubank, sophisticated Ultravioleta, Nu U18, Nu Empresas — while each stays "unmistakably Nu."
**What's good about it:** The quoted rationale is the most useful sentence in the whole item and it is the opposite of what institutional brands usually do: *"The temptation with a brand at this scale is to add. More rules, more assets, more complexity. We did the opposite. We kept the things that carried real equity, then built a system around evolutions of the type, colour, motion, photography and illustration, all pull in the same direction."* That is a design director describing **subtraction as the deliverable** — a refresh that ended with fewer rules and more range, rather than more brand police. Second, the sequencing is disciplined and transferable: **preserve the recognisable mark, then invest the differentiation into the two cheapest permanent assets** — a proprietary type family (two cuts, display and text, so expression and legibility have different tools) and a photography library with a point of view. That is exactly the White & Case move from 1 November arrived at independently, from a Q2 bank rather than a law firm, and the convergence is the signal. Third, the **multi-register problem** is the one every department actually has: a residency announcement, a fellowship deadline, a research paper and a graduation event are four registers, and Koto's answer is a small shared ingredient set rather than four sub-brands. Fourth, "the rules stay simple, so the brand can grow without becoming more complicated" is the correct definition of a scalable system — growth absorbed by *range* in fixed elements, not by adding rules.
**Pros:**
- A **refinement** rather than a rejection of the equity asset — for an institution with a navy and a wordmark it cannot change, this is the realistic model, and the one the press keeps ignoring in favour of the rebrand-from-scratch story.
- Two type cuts instead of one, split by *job* (display for expression, text for clarity) — the correct and rarely-taken typographic decision, and cheap to specify even without commissioning a family.
- A motion logic that carries from brand moments down into app interaction is systems thinking expressed where clients can see it, not in a guidelines PDF nobody opens.
- The photography library is a **rule**, not a mood board: 50+ assets built to a defined purpose across marketing *and* product, which is the authored-library pattern we keep arriving at from three different directions this week.
- It is a genuinely dated, named, third-party-verified case (Koto's own site, Nubank's own blog, LBB), not a studio boast picked up uncritically by a hungry press.
**Cons:**
- **The proprietary typefaces are unavailable to us** and are the centrepiece of the work; "commission a family" is a multi-month, five-figure programme with a foundry, and there is no small version of it that isn't just picking a better retail face.
- The register is a **consumer fintech at 135 million customers** — pop, delightful, high-energy. A hospital department that adopts "designed to delight" as its north star will sound like it is selling a credit card, which is a worse failure than looking generic.
- Everything is described by the agencies that did it; no independent craft critique of Nubank's execution at small sizes, in dark mode, or in the app's dense product UI has been published. Koto's own line, "each can flex… but everything still feels ownable," is unverified from outside.
- **The one asset that would be most useful — the reduced rule set — is not published.** They said they removed rules; they showed a headline. Nobody outside Koto can see what the system actually permits now, which limits how much of this transfers.
- Coverage arrived as a cluster of near-identical agency rewrites (Design Week, LBB, FF News) — the same press release in four fonts, which is a mild slop signal in the *reporting*, not the work.

**Should we...**
- ✅ **Adopt it**
**Why:** Adopt the **subtraction brief** as the frame for any Montefiore Urology refresh, and adopt the two-asset move as the budget request. The frame is one sentence Shareef can use in a meeting: *keep what carries equity, invest the rest into type and photography, and end with fewer rules than you started with.* Applied here it produces an actual sequence — the navy `#003da5` and the department wordmark stay (they carry equity and the platform is built on them); the differentiation goes into **one dedicated display face and one photographic rule for the 28 faculty interview clips and the clinical rooms we already have**; and the sub-registers (fellowship, residency, research, graduation) come from **colour and type weight within the system**, not from four new lockups. That last point is the direct answer to the thing that actually threatens our material's coherence — every programme inventing its own look because there was no cheap way to distinguish them. On the platforms: the **Unified Platform already makes this decision correctly** (single accent, one type family, surface steps instead of decoration) and is the internal proof that the method works; the Chapter Player's light theme is the second. Where it must not be copied: the *tone*. "Designed to delight" is fintech; ours is a hospital. The technique is subtraction and asset placement — not the mood.

### Canva Brush — an editing model that reads your layers and writes code, instead of repainting the picture
**Link:** https://www.fastcompany.com/91633207/could-canva-brush-new-ai-feature-end-graphic-design-slop (30 October 2026) · mechanism detail: https://thenewstack.io/canva-brush-design-editing · Canva's launch post: https://www.canva.com/newsroom/news/canva-brush/ · launch thread: https://x.com/canva/status/2115885750013321704 (launched **29 October 2026**, Pro only)
**Type:** Tool
**What it is:** Canva's **vision-language model for design editing**, from its 160-person Canva Research lab, launched a week after its image generator Craft. The claim that matters is mechanical, not aesthetic: Brush **does not paint pixels.** It reads a design's content, structure and layers, then **writes and runs small pieces of code to change specific elements and inspects the rendered result to guide the next step** — an agentic loop over the design's own structure. So restyling a deck or fixing one line of text doesn't cascade through everything else, and the output stays **fully editable** (text, imagery, colour, layout) rather than flattened. It runs up to **69% faster** than Canva's previous design agent at **46% less cost per task**, and Canva says brand-kit support and attachment referencing are in progress. It arrived into a genuinely loud conversation: a 2.2M-view promo, and a viral (paid-partnership) post arguing Canva of all companies was "spearheading the crusade against graphic design slop," set against a creator's footage of a state fair covered in AI-generated posters, menus and banners.
**What's good about it:** The diagnosis is exactly right and it is the one that separates a useful tool from a generator. The real defect in AI image editing is not that it draws badly — it's that **one requested change silently rewrites the things you asked to keep**, which is why nobody art-directs with these tools; you can only re-roll. "It needs to understand what a designer wants to change, how the design is structured, and importantly, **what needs to stay exactly as it is**" is a correct problem statement, and tracking interdependent decisions against real layers is the correct architecture for it. Second, **code-as-the-edit-mechanism** is the honest technical choice: it means the operation is inspectable and reversible and the artefact stays an editable document, which is the difference between editing a design and editing an image of a design. Third, **post-training on real design processes and RL against what Canva's own designers call good design** is the current best-practice recipe for vertical taste, and the outside analysis puts it well: "frontier models know the internet; Canva knows what hundreds of millions of people actually do with a slide deck." Fourth, coming from Canva specifically is meaningful — it is the tool that produced most of the slop, which means its model is trained on the richest available record of what people actually make.
**Pros:**
- Correct target: **editing, not generation.** Generation is commoditised; making a change without collateral damage is the actual bottleneck in every deck and social pipeline we run.
- Structural, layer-aware edits that stay fully editable — this is the property that would let a Canva-adjacent tool enter a real review loop instead of producing a picture to be remade.
- The agentic write-code-then-inspect loop is verifiable architecture, not a vibe; it is the same "measure, then correct" pattern the typography tools in this brief are built on.
- Canva's distribution means the tool meets the people who actually make the slop where they already work, which is a more effective anti-slop intervention than any skill file.

**Cons:**
- **The performance numbers are Canva's own** and unverified outside the launch blog: 69% faster and 46% cheaper are throughput metrics — the same "speed at the wrong standard" pattern this brief has flagged for two weeks, and not one published blind comparison on quality.
- **Brand kits don't work yet.** The capability our residency materials would actually need — reading our palette, type and components — is explicitly a future feature, so today the tool's taste is Canva's taste, and Canva's taste is the template default we are trying to escape.
- **Pro-only, and the slop conversation is partly marketing.** The loudest praise in the coverage comes from a paid partnership post, and the item's headline ("could it end design slop?") is a question the source frames and does not answer.
- An editing model that is very good at *polishing* an existing design still assumes the design is worth polishing — it doesn't address the art direction that makes a piece generic in the first place.
- Canva's ecosystem gravity is total: adopting it means the department's creative lives in a platform whose business is templates, whatever this model does.

**Should we...**
- 👀 **Watch it**
**Why:** Watch, and take the standard, not the tool. The standard is a single question to apply to every AI editing surface we touch: **does a change stay where it was asked to stay?** If a tool cannot guarantee that, it is a re-roller, and re-rolling is the behaviour that guarantees fourteen unrelated-looking posts. Where it could land, if brand kits ship: **residency announcement variants and Sub-I decks**, where the actual work is "same design, new date/name/photo" and the current failure is that every regeneration drifts. Where it must not go: the **Unified Platform** (a code surface with a real design system — Brush would be a fifth layer of drift, not a fix) and any print collateral that has to go to a sign shop. Why it is not Adopt: the one capability that would justify it for us is unshipped, the metrics are vendor-reported throughput, and the enthusiasm is partly a paid partnership. Watch for two specific things — brand-kit reading going live, and any independent test where a designer asks for one change and gets exactly one change.

### @designertom — build a throwaway control panel per project, from the sketch and the design system
**Link:** https://x.com/designertom/status/2114877969311334605 (**published 2026-10-27**, verified from the page's own `og:published_time`; 42 likes, 17 replies)
**Type:** Workflow
**What it is:** A practitioner thread (Tommy Geoco) reporting a workflow he says he now runs "across every surface area of work from film studio to design to SaaS," credited to @hewarsaber: take **the sketch and the team's design system** to an AI coding agent and ask for a **control panel built for that one project**. Motion and texture are brought in "through the agent," every small detail is tuned there, and then **a link is deployed for the client to review**. The tools are then handed to the agent to manage and evolve. The framing sentence is the actual idea: *"The best tool on a design project is sometimes one you build for that project and throw away."*
**What's good about it:** This is the only X find in two days that proposes a **workflow** rather than a prompt, and the workflow solves a real problem in art direction: timing and easing and texture are the parameters nobody can specify in a brief and nobody can review in a static comp, so they get decided in a general-purpose motion tool by whoever is holding it. Building a *project-specific* control panel means the parameters are named in the project's own language ("title card hold," "panel stagger"), the client can move them in a browser without a licence or a file, and the tuning loop happens in front of the person with the taste rather than in a handoff. Second, **"built from the design system"** is what keeps this from being chaos — the panel is generated inside existing tokens and components, so the exploration is constrained, which is precisely the discipline the rest of this brief keeps arguing for. Third, **throwaway** is the underrated part: a one-project tool carries no maintenance debt, and it sidesteps the standard failure where a bespoke internal tool becomes a thing you must keep alive instead of the work.
**Pros:**
- Names the real bottleneck in motion and texture work: the parameters, not the pixels. A slider named for the project's intent is a better brief than a sentence.
- Client review as a **deployed link** rather than a rendered file removes the round trip that swallows most of an approval cycle.
- Constrained by the design system, so it's exploration inside a system — the one shape of AI-assisted design this brief consistently endorses.
- Born from an actual practitioner's daily practice across film/design/SaaS, with the origin process credited to a named colleague, rather than a thread selling a course.
**Cons:**
- **Thinly evidenced, and it is a tweet.** No artefact, no before/after, no screenshot of one of these panels, no client reaction, no failure case. 42 likes is a conversation, not a track record.
- "Then I hand these tools to my agents to manage and evolve" is exactly the sentence that produces **unmaintained scaffolding** — the throwaway tool acquires a life, grows, and becomes the shadow design system nobody audits.
- Requires a level of agent fluency and a design system documented well enough for a coding agent to build against; our platform's tokens are not in that state today, which makes it a goal, not a move.
- Nothing here addresses whether the output is any *good* — a tuned control panel on a bad art direction is a faster bad result.
- The register is Silicon Valley craft-influencer; the underlying idea is genuinely useful but the thread dresses a small technique as a movement, which is itself a slop tell.

**Should we...**
- 👀 **Watch it**
**Why:** Watch, and run one cheap test this month rather than adopting it as a method. The test: on the next residency or Sub-I motion piece, before touching a general-purpose motion tool, spend an hour having an agent generate a single-page panel with **four named sliders — hold, stagger, easing strength, grain** — built from our tokens, deployed at a link, and used by the person making the call to tune the feel. If that hour produces a decision faster than the usual two rounds of "can it be slower?", the workflow is real and worth institutionalising; if it produces a tenth thing to maintain, the thread was a tweet. Where it fits: **Chapter Player motion**, social creative transitions, and any Sub-I or recruitment piece where the client review is the bottleneck. Where it does not: the **Unified Platform** in production — generating one-off control panels against a live dark React app is precisely the shade of shadow tooling that makes design systems rot. Why not Adopt: there is no artefact behind the claim, and the half of the thread that says "hand the tools to the agents" points at the failure mode instead of away from it.

## Overall Assessment
