### Postiz

**What it is:** An open-source, self-hosted social media scheduler — calendar, cross-posting, repeated posts, RSS auto-post, analytics — with a public API, a CLI and an MCP endpoint so an agent can queue posts instead of someone opening six tabs.

**Source:** https://github.com/gitroomhq/postiz-app · https://postiz.com  ·  Provenance: spotted on The Next New Thing — https://www.youtube.com/watch?v=rPNKWE4GrWA

**What's good about it:** It is the boring, load-bearing part of a content program: one calendar, every channel, a queue that survives the week you are on service. 41,331 stars, 70 contributors on the first page, commits today, and a real compliance posture — hosted uses official platform OAuth flows, does not scrape, does not proxy tokens. The agentic surfaces are the interesting part for us: Postiz exposes a public API, a CLI and an MCP server that points at *your own* instance, so Hermes can schedule a week of faculty-clip posts as one tool call rather than me hand-building API calls per platform.

**Pros:**
- Self-hosted edition is feature-complete against Cloud — the project explicitly does not gate features by license.
- Every channel in one queue: X, Instagram, LinkedIn, YouTube, TikTok, Threads, Bluesky, Mastodon, with a calendar and per-channel delays.
- MCP + CLI + public API means our agents can be the scheduling interface; no dashboard clicking required.
- RSS auto-post and "plugs" would let a faculty-quote feed publish itself.
- Runs in Docker against Postgres and Redis — the same shape as everything else we host.

**Cons:**
- Self-hosting means **you create your own developer app on each platform and get it approved** — the README says Meta, YouTube and TikTok can take weeks. That is the real cost, not the server.
- AGPL-3.0: fine to run internally, a real constraint if we ever expose it as a service to other departments.
- It is a heavy stack (Postgres + Redis + storage + worker) for what is, today, one person posting a few times a week.
- OAuth tokens for @MontefioreUrology would sit on the datacenter VPS — hosting the account-connection layer on a datacenter IP is exactly what gets institutional accounts reviewed or limited.

**Should we...**
- ✅ **Adopt it** — integrate into our stack (strongly recommended)
- 👀 **Watch it** — keep an eye on it, not ready yet but promising
- ❌ **Skip it** — not relevant, redundant, low quality, or not useful for us

**Impact on our stack:** High — social media program. It would replace ad-hoc per-platform posting with one scheduled queue the agent can write to, and give us a content calendar we can actually look at.

**Why:** This is the missing piece in the social program, and it is missing in a way we feel every week: we can generate copy and clips, but publishing is still manual and per-platform. Postiz closes that loop, and its MCP/CLI surface means Hermes stays the interface. The reason it is a watch rather than an adopt is the part nobody advertises: the self-hosted route requires us to register and get approval for a developer app on each network, which is a multi-week path with Meta and TikTok, and it puts the department's account tokens on a datacenter box. The clean first move is a 7-day Postiz Cloud trial with one channel — Instagram only — to test whether the scheduling model fits how we actually work, and only build the self-hosted path if the calendar earns it.

### OpenFilm

**What it is:** An open-source AI video agent: a coding agent writes each shot as an animated web page (`film.html`, one `frame(t)` function per shot), and a local browser editor called Studio lets you move, trim, crop and restyle anything it made — then render.

**Source:** https://github.com/openfilm/openfilm · https://openfilm.dev  ·  Provenance: spotted on Hyperautomation Labs — https://www.youtube.com/watch?v=jVePN-m7Fzk

**What's good about it:** It solves the part of AI video that is actually broken — the moment after generation, when every change means re-prompting from scratch. Here each shot is a web page, so a shot can be edited like a slide or re-generated like code, and the same artifact is both machine-editable and human-editable. 5,727 stars, 29 contributors, MIT, and an install that matches our skill model: `npx skills add openfilm/openfilm`. Node 22.2+, ffmpeg, one headless Chromium download — all of which our VPS already carries for other work.

**Pros:**
- Real editor with a timeline, not a prompt box: place, crop, restyle, trim, cut.
- Your agent already knows how to write HTML/CSS/three.js — the authoring model needs no new training for it.
- No account needed to make, edit or render; the bundled music/sfx/stickers are free to use.
- Bring-your-own keys for ElevenLabs, OpenAI, Google, OpenRouter, fal — we already hold most of those.
- MIT license, 29 contributors, and the launch video was made with the tool itself.

**Cons:**
- Five weeks old (created 2026-10-04). Promising, not proven over a semester of use.
- Web-page-as-video is a real constraint for footage-first content: it is much better at motion graphics, titles and explainers than at cutting an interview.
- Needs Node 22.2+, ffmpeg and ~100 MB of Chromium; first render on a CPU-only VPS will be slow.
- Generated voice/music means sending faculty-adjacent content to third-party model providers — a consent question, not a technical one.

**Should we...**
- ✅ **Adopt it** — integrate into our stack (strongly recommended)
- 👀 **Watch it** — keep an eye on it, not ready yet but promising
- ❌ **Skip it** — not relevant, redundant, low quality, or not useful for us

**Impact on our stack:** High — social media program, plus agentic-os. It gives the agent a video pipeline it can actually finish: titles, quote cards, animated stat plates and 20-second explainers built from the 28 faculty interview clips we already hold.

**Why:** We have 28 faculty clips and no repeatable way to turn a good 40-second answer into a branded vertical video — today that is either me in an editor or a subscription tool with a watermark. OpenFilm's model is a better fit for how we work than a hosted video AI: the film is a file in the repo, the agent writes it, and any change is an edit rather than a re-roll. It stays a watch because it is five weeks old and its strength is motion graphics, not interview cutting — so the honest trial is one clip, one branded title sequence, one 15-second vertical cut, on the desktop, before it touches the publishing queue.

### Gemini 4 Carbon (now generally available to paying developers)

**What it is:** Google's frontier model, released to cyber defenders on Oct 28 and opened on Nov 10 to every paying developer and enterprise through the Gemini API — at the same introductory price as Argon, $2 per million input tokens and $10 per million output.

**Source:** https://blog.google/innovation-and-ai/models-and-research/gemini-models/gemini-4-carbon-now-available/  ·  Provenance: spotted on Paul J Lipsky — https://www.youtube.com/watch?v=YTA_DsiYwAc · previously covered in the vault on 2026-10-29 when it was defenders-only; **new: real API access for paying developers, published pricing, and the `/swarm` multi-agent mode in Antigravity.**

**What's good about it:** The claim that matters is not "smartest" — it is **cost per finished task**. Google reports #1 on CursorBench 4.0, Perplexity's WANDR and Zapier's AutomationBench at more than 2× lower cost per task than the next best external model, and #2 on the new Multimodal Knowledge Agent benchmark at more than 6× lower cost per task. That is the profile we want for the long, verification-heavy jobs we hand to agents: CE audits, multi-file migrations in the Unified Platform, and anything that has to read dense documents with charts and tables and produce a spreadsheet or a deck at the end.

**Pros:**
- $2 / $10 per million tokens — Argon-level pricing for a stronger model, no premium tier to negotiate.
- Explicitly tuned for long-horizon agentic work and extended verification loops, which is what our CE pipeline actually does.
- 1M-token context suits whole-repo audits and dense document sets.
- Available today through AI Studio's API with an existing Google key — no new vendor, no procurement.
- `/swarm` in Antigravity pairs Carbon as planner with cheaper models as workers — a pattern we could mirror in Hermes subagents.

**Cons:**
- Consumer access is still gated (AI Ultra, rolling out), and the vendor benchmarks are Google's own framing with partner quotes — treat "2× cheaper per task" as a direction, not a measurement.
- It "uses more tokens than Argon to explore thoroughly," so the cost win depends entirely on task shape; on short prompts it will lose to a cheap model.
- Two weeks of production history. Nobody has yet run a semester of work through it.
- Adding a second frontier vendor to the stack means another key, another bill, another data-handling review — the last thing a healthcare deployment needs casually.

**Should we...**
- ✅ **Adopt it** — integrate into our stack (strongly recommended)
- 👀 **Watch it** — keep an eye on it, not ready yet but promising
- ❌ **Skip it** — not relevant, redundant, low quality, or not useful for us

**Impact on our stack:** Medium — Hermes model routing and the CE pipeline. It is a candidate second route for the deep, expensive jobs (ce:full audits, architecture reviews, dense-document analysis) while the cheap daily driver stays where it is.

**Why:** We already route Hermes on a cheap model for volume and pay for depth only when a task needs it, and Carbon slots directly into that second lane — Argon pricing for a model that is specifically built to grind through verification loops. The honest caution is that today's evidence is a launch-day benchmark suite written by the vendor, and a model that "uses more tokens to think" can quietly cost more on the short tasks that make up most of our traffic. Nothing here justifies switching the daily driver; the test is to point one ce:full-style audit at Carbon, compare the report and the invoice against the current model, and let the numbers decide.

### Arcjet

**What it is:** A runtime security layer for AI agents and LLM apps — it sits at the action boundary (before a tool call executes), checks for prompt injection, sensitive data, PII/PHI and policy violations, and returns a typed decision: allow, block, redact, or hold for review, with every decision written to an audit log.

**Source:** https://arcjet.com · https://github.com/arcjet/arcjet-js  ·  Provenance: spotted on ManuAGI — https://www.youtube.com/watch?v=9loeQNkfQ_8

**What's good about it:** It protects the right seam. Most agent security watches the door — who is asking — while the actual damage happens at step three, when a clean-looking session reads a record and then sends it somewhere. Arcjet judges the *sequence*: the same request that is fine alone trips the rule when it follows a PII read. It ships SDKs for Python (FastAPI, Flask), Node/Express/Next, Go, plus integrations for the common agent frameworks, and the sensitive checks run in-process so the data being checked does not have to leave our environment. OPA/Rego policy, SIEM streaming, and an audit trail that answers "what did the agent do on whose behalf" are exactly the questions a hospital compliance office asks after the fact.

**Pros:**
- Enforces at the tool-call boundary, not in the prompt — the only place enforcement actually holds.
- PII/PHI detection, redaction, prompt-injection detection, and budget control in one policy engine.
- In-process sensitive checks plus zero-data-retention options; self-hostable storage for the audit trail.
- Python SDK means it can wrap our FastAPI services without a rewrite.
- Real trust posture: SOC 2, published trust center, a security console and SIEM export.

**Cons:**
- **$299/month** for the Startup tier, plus $50 per million agent requests — a real line item before it has blocked a single bad call.
- No Hermes integration: our cron jobs and the agent runtime itself are not covered, only the application endpoints we explicitly wrap.
- A BAA for PHI would need to be negotiated; the free tier's one-hour log retention is useless for a compliance record.
- Adding a vendor inside the request path adds a failure mode — if the guard is down, requests either fail closed or silently pass.

**Should we...**
- ✅ **Adopt it** — integrate into our stack (strongly recommended)
- 👀 **Watch it** — keep an eye on it, not ready yet but promising
- ❌ **Skip it** — not relevant, redundant, low quality, or not useful for us

**Impact on our stack:** Medium — Unified Platform. It would put a policy gate in front of the endpoints that expose schedule, call-out and CRM data, and give us an audit answer for "which agent touched which record" without building that ourselves.

**Why:** The Unified Platform now has agents reading a CRM and a Postgres database that contain resident and patient-adjacent records, and the only guardrail is that we wrote the code carefully. Arcjet is the first product I have seen that prices that problem as an engineering control rather than a dashboard: a decision before execution, an audit after. But the honest verdict is watch, not adopt, for two reasons a vendor page will not tell you — the entry price is $299/month and the free tier keeps logs for one hour, which is not a compliance record, and a BAA for PHI is a negotiation, not a checkbox. The right first step is a free-tier pilot wrapped around one *non-PHI* endpoint — the public schedule — to see whether the false-positive rate is tolerable before anyone talks about PHI.

### STE80 Humanizer

**What it is:** An agent skill that removes AI writing tells and then rewrites what is left 80% of the way to ASD-STE100, the controlled English used in aircraft maintenance manuals — short sentences, one idea each, active voice, the actor named.

**Source:** https://github.com/Dodaios/ste80-humanizer · https://skills.sh/Dodaios/ste80-humanizer  ·  Provenance: spotted via GitHub trending (created 2026-11-09) — https://www.youtube.com/watch?v=jVePN-m7Fzk channel feed

**What's good about it:** It does two passes where most humanizers do one. Pass one strips the 26 tells from Wikipedia's "Signs of AI writing" — the "Great question!", the em-dash rider, the "-ing" clause that hides who did what. Pass two is the interesting one: it rebuilds each sentence under STE100 discipline, so the text stops sounding like a chatbot *and* stops being unreadable, which is the failure mode of every synonym-swapping humanizer. The worked before/after in the README is genuinely instructive — the "after" is shorter, plainer and names the actor every time. MIT, a validation CI badge, and the method is documented against ASD-STE100 Issue 9 rather than invented.

**Pros:**
- Two independent passes: vocabulary tells, then sentence architecture — the second is what actually kills the AI smell.
- The "80%" setting is the right call: 100% STE is stiff and wrong for patient-facing and marketing prose.
- Ships as a `SKILL.md` — a plain file we can read, adapt and version, no runtime dependency.
- MIT licensed, documented against a real standard, with a CI validation badge.
- Directly applicable to the copy desk's existing QA gate rather than a parallel process.

**Cons:**
- One author, created 2026-11-09, 348 stars — this is a two-day-old repo and star counts on new repos are usually promotion, not proof.
- It overlaps `impeccable`, which we already run: pass one is largely the same job.
- STE100 was written for maintenance manuals. Applied carelessly it flattens warmth out of donor and patient-facing copy.
- README includes a note that a widely-shared fact check found errors in the STE dictionary panel it illustrates — the author is honest, but the surrounding material is still new.

**Should we...**
- ✅ **Adopt it** — integrate into our stack (strongly recommended)
- 👀 **Watch it** — keep an eye on it, not ready yet but promising
- ❌ **Skip it** — not relevant, redundant, low quality, or not useful for us

**Impact on our stack:** Medium — the copy desk. Pass two is a concrete, testable rule we can add to the QA gate without adopting anyone's tooling.

**Why:** The copy desk's rule is already "one person, in the room, concrete beats clever," and the most common way copy fails that test is the disease this skill treats: sentences that carry three ideas, hide the actor and stack hedges. The second pass is the piece we do not have — `impeccable` catches the vocabulary, but nothing in our gate currently forces the sentence rebuild. Given the repo is two days old with a single author, the correct action is not to install it as a dependency; it is to read `SKILL.md`, take the two-pass structure, and write our own version into the copy-desk gate where it can be held to our brand rules. That is adoption of the method, not of the repo, and it costs an afternoon.

**Why:** This is the biggest product news of the day and it is genuinely good for the kind of work that currently happens in a Word doc and a half-filled Excel file — an accreditation self-study, a recruitment season plan, a QI project timeline. But it is a generic office suite pointed at healthcare data, and the risk profile is the mirror image of its convenience: the same continuity that makes it useful is the reason a roster must never be pasted into it. ### MCP1 (by Appwrite)

**What it is:** A hosted gateway that puts every MCP server behind one URL per team — humans authenticate once, admins decide which tools each group may call, and every call, sign-in and change lands in an audit log. Launched on Product Hunt today with a 273-server catalog.

**Source:** https://mcp1.com · Provenance: spotted on ManuAGI — https://www.youtube.com/watch?v=9loeQNkfQ_8

**What's good about it:** The design decisions are the right ones for teams: server tokens stay sealed in the gateway instead of spread across laptops, tool *search* replaces front-loading hundreds of tool schemas into context, and destructive tools can require an admin. It is built by Appwrite, so there is a real company behind it, with SOC 2, GDPR, HIPAA and CCPA claims, AES-256-GCM token storage and an audit export.

**Pros:**
- One URL per group with per-tool permissions — genuinely better than copying tokens onto every machine.
- Tool search keeps context small when a workspace has hundreds of tools.
- Audit log of every call with client, actor, latency and decision.
- Free tier is usable for one person; 273 servers in the catalog; keys for CI with expiry.
- Destructive-tool guardrails and read-only group access are the right defaults.

**Cons:**
- **Hosted in Frankfurt, EU** — the gateway sees tool names and arguments, and workspace data plus audit logs live on their infrastructure.
- HIPAA BAA is Enterprise-only at **$29/member/month**; Team is $12.
- Our MCP servers include a Postgres connection to patient-facing tables and a filesystem server — routing either through a third party is not a review we would pass.
- It solves a collaboration problem (many humans, many laptops, one org) that we do not have: one operator, one VPS, servers already configured in Hermes.

**Should we...**
- ✅ **Adopt it** — integrate into our stack (strongly recommended)
- 👀 **Watch it** — keep an eye on it, not ready yet but promising
- ❌ **Skip it** — not relevant, redundant, low quality, or not useful for us

**Impact on our stack:** Low — Hermes already speaks MCP natively and its server list lives in one config file on one machine.

**Why:** MCP1 is a well-built answer to a problem we do not presently have: token sprawl across a team of developers. Our MCP servers run inside the Hermes container, the config is a single file I control, and the traffic is neither distributed nor shared. Worse, the traffic that matters — Postgres and filesystem — carries data that must not traverse a Frankfurt-hosted proxy, and the compliance path that would make that acceptable starts at $29 per member per month with a BAA. Worth knowing it exists if the department ever grows to several agent operators; skip today.

### ProtoMap (by HoundDog.ai)

**What it is:** A context engine for gRPC and Protobuf codebases: it scans source, builds a graph of services, methods, messages and call sites, and serves that graph to coding agents over MCP so they stop grepping to rediscover the same structure.

**Source:** https://hounddog.ai/protomap/ · https://github.com/hounddogai/protomap  ·  Provenance: spotted on ManuAGI — https://www.youtube.com/watch?v=9loeQNkfQ_8

**What's good about it:** The demo task is the one every agent struggles with: "find every place that calls `PaymentService/CreatePayment`, including indirect calls." Done by grep it is 30 steps of probing, dead ends and string-splitting heuristics; done through the graph it is a handful of tool calls with file:line answers. It is self-hosted (Docker + Postgres), runs on a laptop with no GPU, derives context deterministically from code instead of a hand-maintained instruction file that goes stale, and supports ten languages plus monorepos.

**Pros:**
- Deterministic code graph rather than a memory file that rots.
- `protomap scan` builds it in seconds and updates on merge to main.
- MCP server so Claude Code, Codex and Antigravity can query it directly.
- Self-hosted with PostgreSQL; no source leaves the environment in that mode.
- Service-catalog output is useful to humans too, not just agents.

**Cons:**
- Built for **gRPC and Protobuf**, with other protocols "coming soon". Our stack is FastAPI/Express over Postgres — there is no `.proto` file in the building.
- The headline numbers (13× fewer tokens, 7.7× faster, 6.4× lower cost) come from a vendor-run benchmark on a synthetic 5M-LOC codebase.
- Self-hosted trial requires Docker Compose 2.23.1+, 4 GB RAM and 20 GB disk — on a VPS already running the platform, the CRM and Supabase.
- It is a second code-intelligence system to keep running, for a codebase small enough that our agent can read most of it directly.

**Should we...**
- ✅ **Adopt it** — integrate into our stack (strongly recommended)
- 👀 **Watch it** — keep an eye on it, not ready yet but promising
- ❌ **Skip it** — not relevant, redundant, low quality, or not useful for us

**Impact on our stack:** Low — it would improve agent navigation in large gRPC monorepos; we have neither the protocol nor the scale.

**Why:** This is the best-executed tool in today's batch and it is still wrong for us. ProtoMap's entire value comes from Protobuf being a machine-readable contract — the graph it builds is the thing our REST routes and SQL schema do not have. Adopting it would mean paying for a Docker service, a Postgres database and a scan pipeline to answer questions our agent already answers by reading the routes file. If the Unified Platform ever grows gRPC services, this is the first thing to revisit; until then, skip.

### Cicada

**What it is:** A desktop app for Mac, Windows, Linux and Android that puts live bilingual subtitles on any call or stream, writes structured meeting notes as it listens, and can speak a translated voice into the meeting when you hold a talk key.

**Source:** https://github.com/wquguru/cicada · https://cicada.indaloop.app  ·  Provenance: spotted on Hyperautomation Labs — https://www.youtube.com/watch?v=jVePN-m7Fzk

**What's good about it:** The engineering choices are thoughtful: it captures system audio directly instead of sending a bot into the meeting, so nobody sees a participant appear; on Apple silicon all speech recognition runs on device, so audio never leaves the machine; and it separates speakers with a local voiceprint model. Exports go to Markdown, Word or SRT, and it can reprocess an existing recording file.

**Pros:**
- No meeting bot — listens to system audio, invisible to other participants.
- On-device recognition on Apple silicon; no key needed for basic subtitles and records.
- Speaker separation, clickable transcript-to-audio, and SRT/Word/Markdown export.
- Works on existing recordings, not just live calls.

**Cons:**
- It is a **desktop GUI application**. There is no server mode, no headless CLI, no API — nothing Hermes can call.
- On Windows, Linux and Android, speech recognition is cloud-based and needs a Ling/OpenRouter-style key; on the Linux desktop the notes window is visible while screen sharing.
- Created 2026-11-01, ten days old, six contributors. Swift, and not notarized on macOS.
- Real-time note quality is exactly where new transcription apps overpromise.

**Should we...**
- ✅ **Adopt it** — integrate into our stack (strongly recommended)
- 👀 **Watch it** — keep an eye on it, not ready yet but promising
- ❌ **Skip it** — not relevant, redundant, low quality, or not useful for us

**Impact on our stack:** Low — our transcription runs server-side; a desktop subtitle bar does not plug into it.

**Why:** The interesting version of this product for us would be a headless service that ingests a Grand Rounds recording and returns a speaker-attributed transcript with notes — and that is precisely what Cicada is not. It is a well-built consumer app that lives on one person's laptop, needs a cloud speech key everywhere except Apple silicon, and cannot be driven by an agent. We already own the server-side transcription path and the M4B pipeline; adding a desktop app would create a second, unmanaged place where meeting audio lives. Skip.

## Overall assessment

If we do nothing else, do these, in this order:

**1) Postiz — start the 7-day Cloud trial on Instagram only.** It would give the social program the one thing it lacks: a scheduled, auditable publish queue that an agent can write to, instead of manual posting per platform. Keep it to one channel until the calendar proves it earns the self-hosted build.

**2) OpenFilm — build one branded vertical cut from one faculty clip, on the desktop.** It would turn the 28 clips we already own into a repeatable video pipeline where the agent writes the film and a human edits it, at zero subscription cost.

**3) Gemini 4 Carbon — run one real audit through it and compare the invoice.** It would give us a priced second lane for deep, verification-heavy work, decided by measurement rather than by a launch-day benchmark.

Arcjet is the one to revisit when the Unified Platform next touches PHI — the guardrail problem is real, it is just a $299/month plus BAA conversation rather than a today action. Everything else today is either redundant with what we run or aimed at a stack we do not have.
