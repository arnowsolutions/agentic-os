### Shirudo

**What it is:** An open-source eBPF security runtime from OpenAI and Cisco. An agent observes a running Linux system, generates a targeted "shield" — a small eBPF program attached to a specific kernel or network operation — tests it against the exploit and against real traffic, and once an operator approves it, loads it without restarting the service. Shields are cryptographically signed and verified before they load, and a TPM records what was loaded or removed.

**Source:** https://github.com/shirudo-dev/shirudo · docs https://docs.shirudo.dev · announcement https://openai.com/index/introducing-shirudo/ · Provenance: Google News RSS (`open source AI tool`) + Hacker News front page — https://news.ycombinator.com/item?id=50619630

**What's good about it:** The reference demo is the pitch: a Codex-generated shield added an input check to Java's Base64 decoder and attached it to a *running* Elasticsearch process; the Java4Shell exploit was rejected while the service kept serving. That is the exact window a hospital service is most exposed in — between the advisory and the maintenance window, which for us is measured in weeks. The trust model is unusually good for something agent-generated: the shield is signed, the eBPF verifier checks it against the kernel's safety rules, and the TPM keeps a verifiable record of loads and removals, so an attacker with root cannot quietly remove a protection. It is BSD-2-Clause, written in C, 19 MB, 1,129★ and 94 forks, with a Linux Plumbers Conference walkthrough behind it. The project existed before the announcement (created 2026-10-13), so it is six weeks of work, not a one-day press release.

**Pros:**
- Live protection without a restart — the only mitigation I have seen that fits a service we cannot take down during clinic hours.
- Signed shields plus the eBPF verifier plus TPM attestation give a control that survives a compromised root account, which is precisely the failure mode the Nov 22–23 items described.
- Agents do the legwork (investigate, write the shield, replay the traffic), humans approve the load. That split is the one we already use for cron approvals.
- The shield is scoped to one vulnerable operation, so blocking it does not require taking the service offline — the problem every WAF rule gets wrong on stateful APIs.
- BSD-2-Clause, C, documented, with a public place to contribute shields per CVE.

**Cons:**
- **The deployment requirement is the blocker.** As the HN thread's first substantive comment puts it, this wants a measured-boot setup — TPM2, unified kernel image, verified boot — or its self-defence story does not hold. Our Hostinger VPS has no TPM and no measured boot, so the "verify before it runs even if the attacker is root" property is unobtainable there.
- 62 open issues on a six-week-old project; it is a reference implementation with a blog post, not a supported product.
- Loading eBPF programs is a *host* change. On the VPS that means every container, including the Hermes gateway and the database — a bad place to experiment.
- It defends exploit paths. Our actual exposures this month were an unauthenticated upload, prompt injection through skills, and credentials in the wrong place. None of those are kernel-behaviour problems, and Shirudo would not have caught any of them.
- Generating shields at machine speed assumes the OpenAI cyber model (GPT-6 Cyber / Codex), i.e. an OpenAI credential and code egress from the host being defended.

**Should we...**
- 👀 **Watch it** — read the shield model, and file the hardware requirement as the blocker it is.

**Impact on our stack:** Medium-High — the VPS kernel and every service behind Traefik (public schedule, Unified Platform API, Postgres). The concrete change, if the hardware existed: a signed shield for the next critical CVE in nginx, Traefik or Postgres deployed in minutes instead of waiting for a maintenance window, with a TPM receipt proving it was loaded.

**Why:** This is the strongest security idea of the week and it is deliberately not an adopt, because the part that makes it trustworthy is the part we cannot do. Measured boot is not a configuration flag; it is a chain from firmware through the bootloader to the kernel image, and a VPS with no TPM has no root of trust to anchor it. Without that, Shirudo degrades into "root can load eBPF that root could unload" — still useful, but not the guarantee in the press release, and not something to run on the host that runs everything else. What I want from it now is the design: the shield model (one vulnerable operation, tested against both exploit and legitimate traffic, signed, attested) is the correct template for our next emergency, even if we implement it as a WAF rule and a deploy gate rather than eBPF. Revisit the moment a TPM-capable host or a bare-metal box enters the picture; at that point this is the first thing to install.

### gridlines

**What it is:** An MIT-licensed agent skill for alignment passes. It ships a `SKILL.md` procedure, a `probe.js` that runs inside a page to measure the ink edges of every text run, icon and control, draws the guide lines, and reports every item that misses its line with the delta in pixels, and an `audit.mjs` that does the same headlessly in Chromium and saves an annotated 2x capture plus a JSON report.

**Source:** https://github.com/pritamux/gridlines · install `npx skills add pritamux/gridlines` · Provenance: GitHub new-repo scan (created 2026-11-21, 232★, 9 forks, MIT, 3 open issues, 1.9 MB)

**What's good about it:** It measures ink, not boxes — a text run's glyph bounds, an icon's drawn shape rather than its viewBox, and the box itself only when a control has a fill, full border or shadow. Per container it emits six lines (lead, label, box, icon-column centre, trailing, trailing centre) and then one `MISS` row per stray item: which edge, how far off, which line it should be on. The example report in the README is four misses in a sidebar with 2–3px deltas, which is exactly the class of error the eye reports as "not premium" and cannot name. The process is written down and ordered: read the project's design policy first and do not re-derive its values, test with real data because empty states hide the misaligned rows, measure at 1440 and 390, open every overlay the page owns (menus, popovers, dialogs, the command palette), confirm each miss by eye because the probe groups rows by centre and can mis-assign one, then fix. The rules come from Karri Saarinen's redraw of the Linear sidebar and Apple's HIG layout chapter — a named standard, not taste.

**Pros:**
- It converts a taste verdict into a measurement with a number attached, which is the missing half of our redesign gate.
- One readable JS file; MIT; no service, no key, no telemetry, nothing to keep running.
- The headless path works on the static previews we already publish — a `file://` URL is enough, no server.
- The browser it needs is already on this box (Playwright 1.60 with chromium-1223 cached), so the headless audit is one `npm i --prefix` away, not a download.
- Measures 390px as well as desktop, which is where the schedule and call-out surfaces actually break.
- Produces an artifact — JSON plus annotated capture — that can be attached to a Decision Studio verdict instead of a paragraph of adjectives.

**Cons:**
- Three days old, one author, nine forks, three open issues. By this brief's own rule that is a watch regardless of the 232 stars, and the star curve looks like a trending-page artifact.
- It owns horizontal edges and row centring only. Spacing rhythm, type scale, density, colour and hierarchy — most of what Shareef actually rejects — are outside its scope, and the skill says so.
- Step 1 assumes a written design policy with edge values in it. Ours lives in memory and screenshots, so the first run needs that policy written down or the probe measures against nothing.
- The probe's row grouping is heuristic; it will produce false misses on tables and nested lists, and the skill's own advice is to confirm every miss by eye — which puts a human back in the loop on a 40-item report.
- The install path (`npx skills add`) targets Claude Code's skills layout; dropping it into `~/.hermes/skills` is a manual copy (the same adapter question as skillshare and Designer Skills).

**Should we...**
- 👀 **Watch it** — and run it by hand on one redesign surface today, from the browser console, before deciding whether it becomes a house skill.

**Impact on our stack:** Medium-High — the redesign previews and every Unified Platform page. The concrete change: an alignment pass that produces a written report (container, edge, delta) before a preview goes to Decision Studio, so a rejection comes back as named failures instead of "still not good" and a reset.

**Why:** The most expensive loop in our design work is the one where a surface gets rejected and I micro-tune colour instead of resetting to the principle. Half of that loop is a missing procedure: nobody ever wrote down what "aligned" means for our pages, so every review starts from taste. This skill is the first thing I have seen that makes the procedure executable — draw the lines, list the misses, fix the padding — and it does it with a standard (Linear's sidebar rules, Apple's HIG) that we can defend to a reviewer. The reason it is a watch is honest and narrow: it is three days old and one person wrote it. The pilot costs nothing and answers the real question — whether our surfaces fail on edges badly enough to justify making this a gate. Run it on `arnow-redesign-v8.html` from the console, read the report, and if the misses are real, copy the two files into `~/.hermes/skills/design/` and rewrite the design-policy step against our tokens.

### MROffice

**What it is:** The open-source editors behind MR Office, a commercial AI office suite: documents, spreadsheets, presentations, PDF and code in the browser, published as React packages (`mroffice-docs`, `mroffice-sheets`, `mroffice-slides`, `mroffice-pdf`, `mroffice-core`) under AGPL-3.0, plus a hosted embed service and an MCP server (`npx -y mroffice-mcp` or `https://mcp.mroffice.ai/mcp`) that lets Claude, ChatGPT, Cursor, Codex or any MCP client create, open, edit, render and export documents.

**Source:** https://github.com/XinaTian/MROffice · https://mroffice.ai/en/developers · MCP guide https://mroffice.ai/en/developers/mcp · Provenance: spotted on Github Awesome — https://www.youtube.com/watch?v=RuhuvsofJg8 (GitHub Trending Today #61)

**What's good about it:** The MCP surface is the most complete I have seen for Office files: `create_document`, `open_document`, `update_document`, `get_document`, `render_page`, `export_document` to docx, xlsx, pptx, pdf, md, html or csv — and the conflict rule is right, an update made on top of edits the agent has not seen is refused rather than lost. The editors are real: a paged word processor with headers, footers, comments and equations; a spreadsheet with a formula engine, conditional formatting, charts and sparklines; slides with speaker notes. Co-editing, a signed session token minted server-side, and saves returned to your server in a signed callback are all in the free embed tier. Fourteen days old, 3,444★, 388 forks, zero open issues, CI configured.

**Pros:**
- The MCP tool set is exactly the shape our reimbursement and schedule work needs: agent writes cells, renders the page to check it, exports xlsx.
- Server-minted session tokens and signed save callbacks are a sane integration model for the Unified Platform — no shared secret in the browser.
- The formula engine runs free in the hosted embed's free plan, so calculation is not a paid add-on.
- React packages mean the editor is a component, not an iframe we cannot style.
- It is the third entrant in two days to the "embed a spreadsheet" question, which means the question now has a market and a price.

**Cons:**
- **The README contradicts itself, and the fine print matters.** The headline is "edits real Word, Excel and PowerPoint files with you"; the self-hosting section says the open-source editors "open their own formats, CSV, HTML, Markdown and PDF; Word, Excel and PowerPoint files come with the hosted embed above." So the repository gives us `.mrdoc` / `.mrsheet` / `.mrslides` — proprietary formats — and the xlsx path we actually need exists only as their hosted service.
- 3,444 stars on **26 commits by one contributor in fourteen days**. That is the promotion pattern this brief is supposed to distrust, whatever the product's real quality.
- AGPL-3.0 with a NOTICE attribution requirement; a network-modified version obliges us to publish its source. A commercial licence is available by email — which tells you the licence is the product.
- The free embed tier is 100 sessions a month on our own domains, two apps. That is a trial, and the paid tier ($29–$149/month) sends department files to a vendor with no HIPAA story, no BAA, and a two-week-old public history.
- 163 MB repository; embedding it means owning a new editing surface with its own auth, save semantics and failure modes — the same objection as Univer, with a worse data path.

**Should we...**
- 👀 **Watch it** — hold the xlsx decision until the file filters are self-hostable, and do not route department files to the hosted tier.

**Impact on our stack:** High *if* usable — Unified Platform, specifically the reimbursement workbook and the schedule. The concrete change would be an agent that writes rows, renders the sheet to verify them, and exports xlsx without a human opening Excel.

**Why:** This is the second day in a row that the xlsx-in/xlsx-out gap has produced a candidate, and the two candidates fail in the same place: the file format we need is the commercial layer. That is now a pattern worth naming — every vendor keeps the Office filter closed because it is the moat, and the open-source editor is the loss leader. For us the consequence is a decision, not a repo: we are not sending reimbursement rows or schedule data to a two-week-old vendor, and we are not adopting a private format that locks the department's files to one product. The MCP idea is the part worth keeping — an agent that can read back the page it just wrote is a better verification loop than a generated file we hope renders. Watch the repository for a self-hosted xlsx import/export; until then, the answer to "can we stop generating files and start editing them" is still no, and it is cheaper to say so now than after an integration.

### Claude Ship

**What it is:** Anthropic's set of three agents for the code after the commit: Code Review (generally available since October), PR Steward (beta) which fixes failing CI, merge conflicts and review feedback and comments what it changed and how to roll it back, and Claude Approvals (beta) which reads an approval policy written as a file in the repository and decides whether a pull request still needs a human. Rolling out to Claude Team and Enterprise plans for GitHub repositories.

**Source:** https://code.claude.com/docs/en/claude-ship · announcement https://claude.com/resources/articles/introducing-claude-ship · Provenance: Google News RSS (`AI agent`) — TechCrunch, 2026-11-23 — https://techcrunch.com/2026/11/23/anthropic-launches-claude-ship-letting-ai-agents-review-fix-and-approve-code-changes/

**What's good about it:** The interesting part is not the code review — that shipped in October — it is that the approval decision becomes a **policy file in the repo**, written in natural language, composable with Code Review findings and classifiers, and revocable. Anthropic's own advice is to run it observe-only first, start with one repository, and set monthly spend limits, which is the correct rollout for a gate that can merge code. PR Steward's post-push comment on what changed and how to undo it is the audit trail most agent tooling forgets. It is also a clear statement of where the bottleneck moved: the slow part of a deploy is no longer writing the change, it is waiting for a human to say yes to a small one.

**Pros:**
- Policy-as-a-file is the right primitive: reviewable in a diff, versioned with the code, and independent of who is on call.
- Observe-only mode, per-repo scope and spend caps make a cautious pilot possible without a new process.
- PR Steward's rollback note per push is exactly what our deploys lack today — a written record of what changed between container recreates.
- It runs on GitHub, where our repos already are.
- It separates the two decisions that get conflated: "is this correct" (Code Review) and "may this ship" (Approvals).

**Cons:**
- Requires Claude Team or Enterprise. We do not have either, and adding a seat tier to approve PRs is a purchase, not a `pip install`.
- It assumes a PR-based deploy. Our Unified Platform flow is build → `docker stop/rm/up` on the VPS; there is no merge event to gate, so nothing would fire.
- An agent approving an agent's code is a governance question in a hospital, not a productivity feature. The policy file makes it auditable, not automatically acceptable.
- Beta for the two interesting agents; the approval agent cannot merge, only approve, so a human still clicks.
- It is one vendor's model judging one vendor's output, with Anthropic's own incentive in the loop.

**Should we...**
- 👀 **Watch it** — steal the policy file now; adopt the product only if we move deploys to PRs.

**Impact on our stack:** Medium — the Unified Platform and interview-portal repos. The concrete change, if adopted: a written approval policy in the repo, observe-only, so every deploy has a review record and routine changes stop queueing behind a human.

**Why:** The valuable idea here is free and does not need Anthropic: write the approval policy as a file in the repository, in plain language, and make a change's right to ship depend on recorded evidence rather than on who is awake. We can do that today with a `DEPLOY_POLICY.md` and a pre-deploy checklist, and it would already fix the failure we actually have — deploys that happen from a shell with no record of what changed. The product is a watch for two concrete reasons: it needs a plan tier we do not buy, and it fires on pull requests, which our deploy path does not use. If the Unified Platform ever moves to PR-based deploys — and after yesterday's Codex Security item it probably should — Claude Ship becomes the cheapest way to gate them, with the caveat that a hospital needs the policy to name what a human must always see.

### fast-anything

**What it is:** A CLI (npm `@el4cteo/fast-anything`, or `cargo install fast-anything`) that profiles a running Python, Node, Ruby, Java, Go, PHP, C/C++, C# or R app, ranks functions by time × how portable they are, has your coding agent port only the hot ones to Rust, records up to 500 real calls, replays every one against the Rust build to prove the output matches, then swaps it in through a single marked block that can be removed byte for byte.

**Source:** https://github.com/EL4CTEO/fast-anything · Provenance: GitHub new-repo scan (created 2026-11-21, 3,396★, 228 forks, MIT, 9 contributors, 87 commits, 30 open issues)

**What's good about it:** The method is the right one and the tooling is unusually disciplined about proof. `scan` measures before anything changes; `port` writes a one-function Rust crate plus a `TASK.md` for the agent; `verify` release-builds and replays every recorded call, which is equivalence evidence rather than a vibe; `enable`/`disable` is a reversible swap, not a rewrite; `bench` interleaves runs so the comparison is fair. Nine contributors and 87 commits in three days is a real project, not a star farm, and there is a CI workflow and published packages on both npm and crates.io.

**Pros:**
- Proof-before-swap: recorded real calls replayed against the port is the only honest way to claim "same behaviour, faster".
- Reversibility is designed in — one marked block, removed byte for byte, so a bad port is a one-command rollback.
- It targets the 5% that is actually slow instead of the rewrite-everything instinct that costs months.
- MIT, published packages, CI, multiple maintainers.
- The generated `TASK.md` makes the agent's job narrow and reviewable, which is the right use of an agent in a performance change.

**Cons:**
- It assumes a Rust toolchain in the environment. Our container is rebuilt from a layer on `docker recreate`, so a toolchain added for one port disappears — the same trap as the `/app/venv` pip installs.
- "Same results on recorded calls" is equivalence on the inputs seen, not a proof; the 501st input is untested.
- We do not have a performance problem. The public schedule page and the Unified API are small, and the last slow thing was a bad query, not a hot loop.
- Three days old, 30 open issues, and the headline is a trend-driven framing ("don't rewrite it in Rust") more than a measured claim.
- Porting a function to Rust adds a build step to a deploy path that is currently a `docker compose` recreate — more moving parts for a gain nobody has asked for.

**Should we...**
- 👀 **Watch it** — keep it for the day a cron or an endpoint actually times out, not before.

**Impact on our stack:** Low-Medium — the public-schedule service and reimbursement CSV handling would be the plausible targets. The concrete change, if a hot function ever shows up in a profile: one function ported and verified instead of a service rewrite.

**Why:** The instinct this tool corrects is real and we are not immune to it — the temptation to solve a slow endpoint by rewriting the service. Profiling first, porting one function, proving equivalence on recorded calls, and keeping the rollback is the disciplined version of that work, and it is the first tool in this brief that treats performance as an evidence problem. But a watch is the honest verdict because the precondition is missing: nothing in our stack is currently slow enough to justify a Rust toolchain in a container that loses installed layers on recreate. The thing to keep is the pattern — record real calls, replay them, prove the swap — which applies just as well to a Python rewrite of a slow query, at zero cost.

### PromptShield

**What it is:** A single-page, client-side tool that redacts API keys, personal and financial identifiers and network details from text before it goes to a model — 30 built-in detectors, live redaction as you type, a reversible session map (`[EMAIL_1]` ↔ the original), one-click restore of the model's reply, and (in the paid Pro tier) batch redaction of CSV, JSON, logs and code with a shared mapping exported as a ZIP.

**Source:** https://hxu129.github.io/scholarcraft-tools/promptshield/index.html · Provenance: Hacker News — "Show HN: PromptShield – Local reversible secret/PII redactor for LLM prompts" (2026-11-23)

**What's good about it:** The problem is exactly ours: every prompt that leaves this box for a model provider is an egress event, and a department that handles patient and faculty data should have a redaction step before it, not after. The design is right in one important respect — the mapping is reversible and local, so the model can reason about `[PATIENT_1]` consistently across a long prompt instead of seeing a different placeholder each time, and the answer can be restored losslessly. It also warns, in the UI, not to upload the restore map — which is the correct instinct about where the real secret lives.

**Pros:**
- Covers the categories that matter: API keys, personal identifiers, financial identifiers, IPs and connection strings.
- Reversible placeholders preserve the model's ability to reason about the same entity consistently.
- Runs entirely in the browser with no network call, which is the right architecture for a redactor.
- The batch mode (Pro) shares one mapping across files, which is the right model for a folder of logs.

**Cons:**
- **It is a web page, not a library.** There is no CLI, no SDK, no MCP server and no repository to audit — a cron cannot call it, and a pipeline cannot import it. The only way to use it is a human pasting text into a browser tab.
- Batch work, custom regex and rule profiles are behind a paid activation (ECDSA offline licence, sold through Gumroad and a Chinese marketplace), so the part a pipeline would need is the part that costs money.
- No licence, no source, no tests visible — for a tool whose entire job is to be trusted with secrets, that is disqualifying on its own.
- The restore map is the most sensitive artifact in the flow, and it lives in browser memory with an export button. One wrong drag into a chat window and the redaction was decorative.
- The interface is Chinese-first; the English is partial.

**Should we...**
- ❌ **Skip it** — keep the idea, not the artifact.

**Impact on our stack:** Low as delivered. The concept maps to a real gap (PHI-adjacent text in prompts), but the change belongs in our own code path — a redaction step in the cron and mail scripts — not in a page someone remembers to open.

**Why:** The honest reading is that this is a demo of a good idea, shipped as a UI. Our problem is not "a human wants to paste a prompt safely"; it is "twenty crons send text to a model provider every day and nobody checks what is in it." A browser page cannot sit in that path, and paying for the batch tier would buy us a manual workflow we would not use. What is worth taking is the spec: a small local redactor with a session-scoped reversible map, run inside the Python script before the API call, with the map never leaving the process. That is an afternoon of work against a known list of patterns, and it would be ours to audit — which is the only version of this a hospital should accept.

### songe

**What it is:** An Apache-2.0 Python training engine that turns idle compute into a fine-tuning loop for a local model — distillation and LoRA training from the coding-agent sessions already running on the machine, built around MLX.

**Source:** https://github.com/sous-labs/songe · Provenance: spotted on Github Awesome — https://www.youtube.com/watch?v=RuhuvsofJg8 (GitHub Trending Today #61)

**What's good about it:** The premise is clever: every agent session is a training example nobody is using, and the machine is idle most of the night. It ranks at 358★ with 49 forks and 20 open issues in four days, and the positioning — "a training engine for your local model, using your idle compute" — is the most concrete answer to "how would we ever improve a model on our own data" that has appeared in this brief.

**Pros:**
- Turns existing agent transcripts into training signal instead of throwing them away.
- Apache-2.0, Python, 1.7 MB, active (pushed today).
- Distillation and LoRA in one loop, so a small model can inherit behaviour from a large one.
- Cheap by design — it uses idle time rather than rented GPUs.

**Cons:**
- The topics and implementation are MLX, which is Apple Silicon. Our VPS is CPU-only Linux; there is no supported path here.
- We do not run a local model. Hermes runs on DeepSeek via API, so there is nothing on this box to fine-tune.
- Four days old, one organisation, 20 open issues, no published results on whether the distilled model is actually usable.
- Training on agent transcripts is training on our prompts — which include the same PHI-adjacent text we just said should be redacted.
- Even if it worked, replacing a frontier API model with a distilled local one is a research project with a quality cliff, not a stack improvement.

**Should we...**
- ❌ **Skip it** — no accelerator, no local model, no gain.

**Impact on our stack:** Low — nothing we run today gets better. If a Mac Studio or a GPU host ever lands and we want a small local model for redaction or classification, this is the loop to revisit.

**Why:** The idea is better than the tool's fit. Idle compute plus agent transcripts is a genuinely smart source of training data, and it is the kind of thing that would matter if we were trying to run a small local model for a narrow job — PHI detection, say, or triage of call-out messages. But we are not: we rent a frontier model, the box has no GPU, and the framework is Apple-only. Adopting it would mean buying hardware to train a model to replace a service that works. Skip, and keep the one-line idea in the vault so that if the hardware picture changes, the question is already framed.

## Overall assessment
