## 1. REA — Reverse Engineer Anything (morluto/rea)

**What it is:** An MCP server plus CLI that lets a coding agent investigate a closed-source application and explain how one of its features actually works — from JavaScript/Electron down to native binaries — with the evidence attached. It drives tools we already know (Ghidra, Hopper, IDA, jadx, apktool, tshark, binwalk, asar) through plain-language agent commands.

**Source:** https://github.com/morluto/rea · https://rea.tools · npm: `rea-agents`  ·  Provenance: spotted on The Next New Thing — https://www.youtube.com/watch?v=BctbCJP9lKU

**What's good about it:** The part worth respecting is not the demo reel of cloned apps — it is the evidence discipline. Every finding comes back with the code, references and *unknowns* behind it, so the agent can say "I could not determine this" instead of inventing a plausible answer. It covers an unusually wide surface for one tool: desktop installs, native binaries, Go/Rust binaries (reads embedded build metadata with no toolchain needed), .NET assemblies (pure static), Flutter APKs, Godot PCKs, IL2CPP metadata, SQLite databases, saved HAR/SAZ network captures, and recorded process behaviour. Static JavaScript and .NET analysis need no native analysis engine at all, which makes the low-risk half of it usable on a plain Linux box.

**Pros:**
- Mature by our standards: 6 months old (created 2026-04-14), TypeScript, MIT, multiple weekly committers including several outside the original author, pushed today, proper docs tree and versioned npm releases.
- Evidence-first output model — designed to produce traceable findings, not confident guesses. That is the correct shape for an agent tool.
- The static JavaScript/Electron path works with nothing but Node and npm; no Ghidra license dance to get value out of it.
- `npx rea-agents setup` wires itself into Claude Code, Codex, Cursor and Gemini CLI with backups of existing config — low blast radius to try.

**Cons:**
- **The whole point is inspecting software we do not own, and stripping paid features out of it.** The video's own chapter list includes "Premium Features: see REA recreate functionality that was hidden behind TickTick's paid plan." For a department that runs other people's clinical and scheduling systems, that is a policy line, not a curiosity.
- Deep native analysis needs Hopper (paid, macOS-first), Ghidra or IDA installed and licensed on the host. That is a real setup cost and another thing to keep patched.
- 1,300 open issues and the README itself warns that lookalike repos and copied READMEs exist — the supply chain needs care; only the official npm package or the repo above is safe.
- Node 22.19+/24.11+ requirement, and on Linux it needs a procps-compatible `ps` for the Ghidra/JADX launches — small, but it is a dependency that bites in containers.

**Should we...**
- 👀 **Watch it**

**Impact on our stack:** Medium-High — but only on a narrow, legitimate use: understanding our *own* long-running systems (the Unified Platform, the sick-call line, the interview portal) where we have partial or missing source, and where a stale build behaves differently from the repo. It does not touch Hermes cron, CRM or the email path at all.

**Why:** Read the README rather than the video and REA is a well-engineered, appropriately boring tool with real maintainers — but the headline use case in the coverage is cloning other people's apps and unlocking other people's paid tiers, and we are a hospital department, not a YouTube channel. The defensible use for us is "explain why our own production build does something the repo says it shouldn't," which is genuinely valuable — we have had two occasions this year where the deployed artifact and the source disagreed. But that use does not need to happen this week, and adopting a decompiler stack on the VPS before we have a specific bug to point it at would be buying a hammer. Watch: when we next hit a "the container is running something the repo doesn't contain" problem, install it then, static-JS path only, on the VPS, pointed at our own build output.

## 2. leanrea — the 8 KB skill that replaces REA's MCP layer

**What it is:** A single 8 KB `SKILL.md` that teaches an agent which recon command to run for each target type instead of wrapping those tools in an MCP server. The agent calls `asar`, `otool`, `nm`, `go version -m`, `jadx`, `apktool`, Ghidra, `tshark`, `binwalk`, `sqlite3` directly.

**Source:** https://github.com/aicodeking/leanrea  ·  Provenance: found via GitHub search while resolving the REA video (same subject matter, one day newer)

**What's good about it:** It attacks the real cost of MCP tool-heavy setups: context. Its benchmark claims REA adds 207 tool definitions — 3.35 MB of schema, roughly 400k tokens of overhead in agents that load every tool up front, against 34.5k for the skill. If those numbers hold, that is the difference between an agent that can afford to do careful work and one that has spent its budget describing its own tools. The README also does something rare: it publishes its caveats — 3 reps per cell, one model, one machine, Ghidra never installed, and an honest note that the plain model already does well and the skill's gain over *no skill* is only ~19% faster.

**Pros:**
- Zero install surface: no MCP server, no Node runtime, no npm supply chain — one markdown file we can read end to end before it goes near a machine.
- Directly relevant to how our Hermes agents are wired: fewer tool schemas means more of the context window spent on the actual task.
- Route-by-file-and-magic-bytes-first instructions match how a careful human would work, and it warns to "work on a copy" before touching binaries.
- Its published install path uses the skills CLI, i.e. it is already shaped for exactly the kind of agent skill bundles we maintain.

**Cons:**
- Three days old (created 2026-10-17), effectively one author, and the entire benchmark is self-graded against hand-made answer keys — a claim, not a measurement we ran.
- The benchmark shows REA still *scored* higher (75/75 vs 74/75), so the token saving comes with an accuracy tradeoff the README is honest about.
- The whole value depends on the agent being allowed to run arbitrary shell recon commands — that is a wider permission surface than a scoped MCP server, and our cron environment blocks several things already.
- It is a competitor to the very thing it benchmarks, so the framing of the comparison is not neutral.

**Should we...**
- 👀 **Watch it**

**Impact on our stack:** Medium — agentic-os / Hermes skill library. If the context-overhead claim survives our own testing, it is a template for how we should be writing our own skills: instructions and command recipes instead of tool schemas.

**Why:** The idea is better than the artifact: our skills should be instruction files that tell the agent which command to run, not MCP servers that hand it 207 tool schemas. But "18 days old" was our floor and this is 3 days old with a single author and a self-graded benchmark, so it cannot be an adopt no matter how clean the README is. Keep it on the watch list and check back in two weeks for commits from anyone other than the author; if it survives, the more valuable move is copying its *shape* into our own skills rather than installing it.

## 3. cache-tax (karanb192) — keep the Claude Code prompt cache warm, and show what a cold send costs

**What it is:** A Claude Code plugin that tracks when your prompt cache has gone cold, tells you what the first message after the gap would cost, and offers `/keepwarm 90m` to hold the cache warm while you step away.

**Source:** https://github.com/karanb192/cache-tax  ·  Provenance: spotted on Hyperautomation Labs — https://www.youtube.com/watch?v=ucs0s1_3BIs

**What's good about it:** This one names a cost that usually goes unnoticed. A cold cache means the next message re-reads the entire conversation context at full input price; on a long session that is a silent multiplier on spend, and it is exactly the failure mode of *automated* runs that fire intermittently. The plugin is narrow, does one thing, prints a number before you commit, and the keep-warm interval is opt-in rather than automatic. MIT licensed, created 2026-09-18, actively pushed yesterday, and the README-tested version requirement (Claude Code 2.1.287+) matches what we run.

**Pros:**
- Narrows an invisible cost to a single visible number instead of a surprise on the bill.
- MIT, 217 stars, 34 forks, pushed 2026-10-19 — a month of real use, not a weekend project.
- The keep-warm is explicit (`/keepwarm 90m`) rather than a background daemon, so there is no standing drain when we forget it.
- Its install is a standard plugin marketplace add, so it validates cleanly with `claude plugin validate` before any hook runs.

**Cons:**
- Keep-warm pings are themselves billable usage — the video says so plainly. On a light day it could cost more than it saves, so it needs judgement, not blind installation.
- It only models prompt-cache cost, not the rest of a session's spend; reading it as a budget tool would be wrong.
- Plugin hooks run with our full permissions and are not sandboxed, so a supply-chain compromise here sits inside the agent's own account.
- Requires Claude Code 2.1.287+; older installs fail with a cryptic `Unrecognized key: "options"` error.

**Should we...**
- ✅ **Adopt it**

**Impact on our stack:** Medium — cost control on every Claude Code / agentic-os session we run. The concrete change: we finally see the cost of *resuming* an old session versus starting fresh, which is the decision we make wrong most often.

**Why:** Of everything found today this is the only item that fixes a problem we can point at, with a small, auditable, MIT-licensed tool that prints before it spends. Our sessions are bursty — a cron fires, a long gap, then a human resumes — which is precisely the pattern that eats a cold-cache penalty on every return. Adopt narrowly: install on the desktop dev session first, not on the VPS, and never turn keep-warm on by default. If after two weeks the printed cold-send cost is trivial for how we work, uninstall it and we have lost nothing but an evening.

## 4. claude-reflect (BayramAnnakov) — turns your corrections into saved rules

**What it is:** A Claude Code plugin that watches for corrections and positive feedback in short prompts and writes them into `CLAUDE.md` / `AGENTS.md` as durable rules, so the agent stops repeating the mistake. One small Haiku call per short prompt.

**Source:** https://github.com/BayramAnnakov/claude-reflect  ·  Provenance: spotted on Hyperautomation Labs — https://www.youtube.com/watch?v=ucs0s1_3BIs

**What's good about it:** The concept maps almost exactly onto how our memory actually gets built — Shareef says "no, do it this way," and that correction should outlive the session. Doing that automatically, with the smallest possible model, is the right shape: the expensive model does the work, a cheap model does the bookkeeping. It is MIT, created 2026-01-03, ~1,800 stars, 166 forks and pushed 2026-10-03, so it is not a fly-by-night repo.

**Pros:**
- Highest-leverage idea in today's batch: every correction becomes a permanent rule instead of being re-learned next week.
- Uses Haiku for the extraction, so the cost per correction is small and predictable.
- Writes to plain `CLAUDE.md` / `AGENTS.md` — human-readable, version-controllable, and ours to edit or throw away.
- 9 months of history and a real fork count, which is the strongest maturity signal of any plugin in this brief.

**Cons:**
- 1,834 stars against only 10 open issues suggests more starring than filing — it is popular, but not heavily exercised in production by its users.
- Auto-writing rules into project instruction files risks the thing most likely to poison an agent: a bad rule it then follows confidently forever. Needs a review step.
- A component that silently decides which sentences are "corrections" is a classifier with no obvious throttle — false positives accumulate as noise in a file that shapes every future session.
- Designed for Claude Code's plugin system specifically; our Hermes memory layer does not share that file, so the benefit is confined to Claude Code work and not portable to the rest of the stack.

**Should we...**
- 👀 **Watch it**

**Impact on our stack:** High if it works, but not today — it would improve agentic-os code sessions by ending the repeat-mistake loop. Our Hermes memory is a different mechanism and would need a parallel bridge.

**Why:** This is the item that would change the most if it works, which is exactly why it should not be installed on trust. The failure mode is asymmetric: a good rule saves seconds, a bad rule silently distorts every future session in that project, and we have already been bitten by stale instructions outliving their context. Watch it, and when we do try it, run it on a scratch project with the write step made explicit — review the proposed rule before it lands in the file — rather than letting it append unattended.

## 5. claude-code-filetree (data-goblin) — see where in the tree Claude is working

**What it is:** A Claude Code mod that adds an IDE-style file tree to the right sidebar, colour-coding files as read (purple), written (orange) and committed (green), with an interactive tree you can navigate.

**Source:** https://github.com/data-goblin/claude-code-filetree  ·  Provenance: spotted on Hyperautomation Labs — https://www.youtube.com/watch?v=ucs0s1_3BIs

**What's good about it:** It makes the agent's blast radius legible while it works. Watching which files light up as an agent runs is the fastest way to notice it has wandered into the wrong directory — a real risk we carry, given how much of our stack lives in one workspace. The install is a two-line plugin marketplace add, MIT licensed, and it is being pushed daily.

**Pros:**
- Spatial feedback on what an agent is touching, which is faster to read than a scrolling tool-call log.
- The read/written/committed colour distinction answers the question we actually ask during a run: "has it saved anything yet?"
- MIT, actively maintained (pushed 2026-10-20), and its own repo doubles as the plugin marketplace so there is one less dependency.

**Cons:**
- Purely cosmetic for us — it changes nothing about what the agent does, only what we see.
- The terminal view needs `/tui fullscreen` and a 110+ column window; it does not load in WSL sessions of the Desktop app. Real constraints, and we use a mixed environment.
- 18 days old, 244 stars, single-author, version 0.2.x — this is early software by our standard.
- Another plugin running with our full, unsandboxed permissions for a visibility-only benefit.

**Should we...**
- 👀 **Watch it**

**Impact on our stack:** Low — developer experience on desktop Claude Code sessions only. It does not touch Hermes cron, the Unified Platform, CRM or email.

**Why:** A nice-looking tool with a real but small benefit, and today the cost/benefit does not clear our bar: it runs with full permissions, needs a specific terminal configuration, and the thing it improves is our comfort rather than our output. The failure we care about — an agent editing the wrong file — is not prevented by a colour, it is prevented by the review step we already do. Watch it; if it adds a warning when the agent writes outside its expected paths, that changes the calculation and we should revisit.

## 6. Claude Code Projects — coordinator plus parallel cloud threads

**What it is:** A redesign of Projects in Claude Code where one project conversation acts as a coordinator, splitting work into parallel cloud threads that each run as a full Claude Code session on its own branch and copy of the repo, then report back — keeping going after you close your laptop.

**Source:** https://www.marktechpost.com/2026/09/17/anthropic-launches-claude-code-projects-in-beta-parallel-cloud-sessions-that-keep-running-after-you-close-your-laptop/ · https://www.ssdnodes.com/learn/claude-code-projects-threads-and-usage-limits  ·  Provenance: spotted on Hyperautomation Labs — https://www.youtube.com/watch?v=F5vwBo5wToM

**What's good about it:** Genuinely the right architecture for a certain class of work — five independent fixes, five threads, each isolated on its own branch, with merge conflicts surfacing as ordinary PR conflicts. The detail worth crediting: in the demo run it *stopped and asked* for the refund policy rather than inventing one, and warned that wiring a button to checkout would charge people instantly. A cloud agent that declines to guess is better than one that guesses fast.

**Pros:**
- Branch-per-thread isolation means parallel work cannot stomp on itself; conflicts appear as normal PR conflicts rather than silent corruption.
- Threads survive you closing the laptop, which is the actual complaint it answers.
- Asking-instead-of-inventing on policy questions is the correct default for anything touching money or clinical rules.
- Per-project control over model and effort for coordinator and workers separately — the setting that decides whether it is affordable.

**Cons:**
- **It is not new this week.** Anthropic's launch post is 17 September 2026; the video is a test drive of an already-shipped beta, not the release.
- Public beta on Pro and Max only. **Not available on Team or Enterprise** — an organisational account cannot use it, which rules us out as a department.
- Not in the terminal CLI, the VS Code extension or the JetBrains plugin. Not on Bedrock, Google Cloud or Microsoft Foundry. A code project needs the repo on github.com with the Claude GitHub App installed — no GitLab, no Bitbucket.
- Defaults to Opus everywhere at high effort, so a few threads drain a five-hour window fast; docs describe preferences, not hard caps, with only 200 new threads/day actually enforced.

**Should we...**
- ❌ **Skip it**

**Impact on our stack:** Low — no system of ours changes. Our repos, our accounts and our workflow (VPS deploy, container rebuild, Telegram reports) have no place in it today.

**Why:** The capability is real and the design is sound, but it is a month-old Pro/Max beta with no terminal CLI, no Team/Enterprise tier and a hard dependency on GitHub.com repos — three separate things that each individually disqualify it for how we work. Grading it as an item, it is not something we can install or adopt today, so it belongs in the skip pile with a note to re-check if it reaches Team plans and the CLI. The transferable lesson is the one we can use for free: an agent should stop and ask when the correct behaviour is a policy it cannot see, and that is a rule our own prompts should encode.

## Overall assessment

Today's scan was thin on genuinely adoptable, mature tooling, and the honest read is that only one item is worth acting on. If we do nothing else, do these, in this order:

1. **Adopt cache-tax on the desktop Claude Code session** — it makes the cold-cache cost of resuming old sessions visible and lets us stop paying it by accident; smallest change, most immediate saving.
2. **Re-check leanrea in two weeks for a second committer** — if the 8 KB-skill-instead-of-207-MCP-tools pattern holds up, we copy the pattern into our own Hermes skills and cut context overhead across the stack.
3. **Park REA on the watch list until we have a specific "the deployed build doesn't match the repo" bug** — then install it static-JavaScript-only against our own artifacts, never against software we do not own.

The pattern worth noticing across today's items: the useful tools are all about the *harness* — cache warmth, correction capture, permission visibility — not the models. That matches where our own remaining wins are.
