### AWS Strands Harness

**What it is:** AWS's newly open-sourced, general-purpose AI agent harness — a preconfigured agent built on top of the Strands Agents SDK, bundling file/shell/web tools, context management, memory, persistent sessions, prompt caching, and agent-to-agent delegation out of the box. Runs locally or on any cloud, with model access switching to Anthropic, OpenAI, Google, or local Ollama in one line.

**What's good about it:** The interesting claim is not the feature list — it's the benchmark. AWS averaged across six benchmarks (ALFWorld, ContextBench, GAIA, WebShop, τ³-bench, Terminal-Bench 2.1) and measured *cost per task*, finding Strands Harness came out 45% cheaper than Claude Code and Codex at broadly comparable accuracy. On Terminal-Bench 2.1 with Fable 5, it cost $56.29 versus $248.05 for Claude Code across 89 trials (77% cheaper) and scored *higher* (69.7 vs 61.8). AWS attributes this to context-management defaults: it truncates oversized tool outputs, compacts context past a threshold, and recovers inside the loop on context overflow. That's exactly the unglamorous engineering every team rebuilds by hand, shipped as defaults.

**Pros:**
- Only out-of-the-box AWS dependency is Bedrock for the model call, and that's a one-line override — Anthropic, OpenAI, Google, and local Ollama all work, with context/sessions/tools/delegation identical regardless of provider.
- Genuinely open source, not a lead-gen wrapper: the agent loop, tools, context management, session handling, and delegation all run on your machine by default. AgentCore is optional hosting, not a requirement.
- CLI lets you configure an agent interactively and `/export` it as Python or TypeScript — so prototyping doesn't fork into a rewrite.
- Ships an Agent Skill that teaches *other* coding agents how to configure Strands Harness and generate deployment configs for AWS, GCP, Azure, Cloudflare, and Modal.
- Same team built AgentCore Harness, so improvements flow both directions between the OSS project and the managed product — the OSS side isn't a maintenance dead end.
- Provider-agnostic enough to survive a model swap, which matters given how fast our model landscape is moving.

**Cons:**
- The 45% figure is AWS's own benchmark, measured against competitors' products on AWS's chosen tasks. The real number is 28% once DeepSeek Harness is folded in — and DeepSeek Harness beat Strands Harness on cost outright (~14% cheaper), just at a lower accuracy. Marketing leads with the flattering framing.
- It's a *general-purpose* agent, not a coding assistant. If our primary need is code, the comparison set isn't obviously the right one.
- Referenced models in the examples (claude-opus-5, gpt-5.6-sol, Fable 5) are moving targets; benchmark significance decays fast.
- Deep integration with Bedrock remains the path of least resistance, which is a soft lock-in even if the code says otherwise.
- One more harness to learn, version, and patch — and we already have Hermes doing this job.

**Should we...**
- ✅ **Adopt it** — integrate into our stack (strongly recommended)

**Why:** The real value here isn't the agent — we have Hermes — it's the *context-management defaults* and the honest cost accounting behind them. The Terminal-Bench numbers show that harness design, not model choice, was responsible for a 77% cost difference on identical tasks. That's a claim we can test cheaply: stand Strands Harness up in a container, point it at a real recurring task we already run (a scheduled scan, a repo audit, a report build), and compare token cost and output quality against our current path. If context compaction is the lever AWS says it is, we should be stealing that pattern into our own agent loop regardless of whether we adopt the harness itself. Adopt in the narrow sense: pilot it as a reference implementation and a cost benchmark, not as a replacement for our stack.

### Jev / "System One" Decision Models (TypeSafe AI)

**What it is:** TypeSafe AI's Jev is the first shipped example of what they call a "System One model" — a non-generative model that answers *choice* questions by returning a confidence score plus a probability distribution over a provided set of options, rather than emitting free text.

**What's good about it:** This is a genuinely different shape of model, and the framing is the interesting part. Standard LLM output is text you then have to parse, constrain, and validate. Jev's output *is* structured by construction — a distribution over options you supplied. For any workflow that reduces to "pick one of these N things," that eliminates an entire category of prompt engineering and post-hoc validation. Simon Willison's writeup is measured but positive on the mechanism, and the ecosystem has already moved: an open-weight recreation effort (OpenJev) and a JevBench benchmark for comparing "Jev-class decision models" both appeared within days. Reported performance claims are striking — 75x faster at roughly 1/170th the cost for judgment-style tasks — though those come from vendor-adjacent coverage and should be treated as provisional.

**Pros:**
- Structured output is the native output, not a constraint bolted on. No JSON-schema pleading, no malformed-response retry loops.
- The probability distribution is the deliverable, so you get calibrated uncertainty *for free* — which is exactly what you want for triage, routing, and ranking decisions.
- 75x faster / ~1/170th cost on judgment tasks, if it holds, makes previously-uneconomical per-item scoring (score every email, every lead, every call-out reason) actually affordable at our volume.
- The concrete use cases reported from week one are unglamorous and real: email triage, slop detection, browser agents, lead scoring.
- Recreations and a benchmark already exist, which means it won't stay a single-vendor black box forever.

**Cons:**
- Bias is the serious problem, and Willison says so bluntly: a floating-point score can conceal all manner of unseen bias, and experimentally picking that apart is hard. He explicitly hopes nobody uses it to rank job applicants. For a healthcare department, that's not an abstract concern.
- Black boxes are back in fashion — we'd be trusting a number we can't explain to a compliance reviewer.
- The API requires a TypeSafe key; it's not a drop-in local model.
- The most quotable performance numbers come from vendor-adjacent sources, not independent replication.
- Also documented: it fails on some evaluations (a poker eval is cited), so it's not universally applicable.
- Model *category* is one week old. Interface, pricing, and longevity are all unsettled.

**Should we...**
- 👀 **Watch it** — keep an eye on it, not ready yet but promising

**Why:** The category is real and it maps onto a genuine gap in our stack. Our agent work is full of "pick one" decisions — routing a message to the right topic, triaging a call-out reason, classifying an incoming request — and today we handle those by asking a generative model to emit text we then parse. Jev's shape is the correct shape for that job, and the cost profile would let us score everything instead of sampling. But two things hold it back from adoption: the bias question is unresolved and, in a healthcare context, unresolved bias in a scoring model is a hard stop until someone can explain the number to a compliance officer; and a one-week-old model category with vendor-sourced benchmarks is exactly the kind of thing that looks different in six weeks. Watch it, read OpenJev and JevBench, and revisit when there's independent evaluation — or when someone wires it into a system we already trust.

Source: https://simonwillison.net/2026/Sep/21/jev/ · https://typesafe.ai/blog/introducing-system-one-models-and-jev

### Claude Code AGENTS.md support

**What it is:** Anthropic added native support for OpenAI's AGENTS.md instruction-file format to Claude Code. Starting in version 2.1.277, if there is no CLAUDE.md in a folder, Claude Code will look for and use AGENTS.md instead.

**What's good about it:** This is a small change with disproportionate operational payoff, and it's a rare case of a vendor adopting a competitor's open standard instead of defending its own. AGENTS.md is governed by the Agentic AI Foundation (a Linux Foundation initiative), so this is a genuine convergence on a shared spec rather than a proprietary format winning by default. The immediate effect: teams running more than one coding agent stop maintaining parallel, drifting instruction files. You write your project conventions once.

**Pros:**
- Ends the duplicate-instruction-file problem for anyone running Claude Code alongside Codex or another AGENTS.md-native agent.
- Adopting a Linux Foundation–governed open spec rather than a vendor format — the instruction layer becomes portable rather than owned.
- Forrester's framing is the right one for us: a common instruction format becomes a practical *control point* for coding conventions, security requirements, architectural guardrails, and compliance policies. One file to audit, not three.
- Precedence rule is conservative and predictable: CLAUDE.md wins if present, AGENTS.md is the fallback.
- Behavior is configurable via `/config` — you can read AGENTS.md, CLAUDE.md, or both.
- Upgrade is a version bump, not a migration.

**Cons:**
- The precedence rule cuts both ways: if a project has both files, AGENTS.md is silently ignored, which is a footgun in a mixed repo.
- "Fork it in a small project" is the honest ceiling — for large or enterprise codebases, the AGENTS.md/CLAUDE.md split adds a resolution step to debug.
- Standard is young and still governed by a foundation initiative rather than a mature spec.
- Doesn't help at all if you only run Claude Code — pure overhead in that case.

**Should we...**
- ✅ **Adopt it** — integrate into our stack (strongly recommended)

**Why:** This is the cheapest high-value item in today's brief. Hermes works from skills; Claude Code and Codex work from markdown instruction files. Where we maintain project conventions for agents, having one governed, portable format beats per-tool copies that drift out of sync — and the compliance control-point argument is the one that matters for us. The concrete action is small: where we currently keep CLAUDE.md files, mirror the content to AGENTS.md (or consolidate), then verify the resolution order behaves as expected with a test agent run. Adopt it, and adopt the convention of AGENTS.md-as-source-of-truth with CLAUDE.md as the tool-specific overlay only where we genuinely need Claude-only behavior.

Source: https://www.infoworld.com/article/4224410/claude-code-now-also-accepts-instructions-in-openais-agents-md-format.html · https://agents.md/

### Shai-Hulud: AI coding assistant session hijack (~100 repositories)

**What it is:** An attacker hijacked an active AI coding assistant session and used it to propagate the "Shai-Hulud" supply-chain worm across approximately 100 repositories — reported by The Hacker News on 2026-09-16, alongside a separate weekly recap noting an AI agent RCE vector and a 0-click RCE flaw in AI coding agents reported by The Register.

**What's good about it:** Not a tool, and "good" is the wrong word — this is a security reality check, and it's the single most actionable item today. AI coding agents hold live credentials, shell access, and write access to repositories, and they run inside a loop that accepts instructions from files, tool outputs, and web content. That's a privilege profile no traditional tool has. Shai-Hulud is the first supply-chain worm to propagate *through* that profile at scale, and it did so via session hijacking rather than a code vulnerability — meaning the mitigation is operational, not a patch.

**Pros:**
- Concrete, current, and directly applicable: we run AI coding agents against real repositories daily.
- The attack vector is now documented, so the defensive playbook is knowable rather than hypothetical.
- Highlights a class of risk — agents with repo write access — that doesn't show up in conventional dependency scanning.
- Reinforces the containerization argument: agents running sandboxed with scoped, short-lived credentials materially reduce blast radius.
- Encourages an audit we should do anyway: which agent sessions have write access to which repos, and how long do those sessions live?

**Cons:**
- Reporting is aggregated from weekly recaps, so the technical detail is thin — no CVE, no full timeline, no confirmed attribution to a specific agent product.
- "~100 repositories" is an approximation; the true scope is unclear.
- Prompt-injection-style attacks through agent tool outputs are largely unsolved at the framework level, so there's no clean vendor patch to apply.
- Easy to read as alarmist and move on, which is exactly the wrong response.
- Mitigations (sandboxing, credential scoping, session rotation) cost real engineering effort and slow agents down.

**Should we...**
- ✅ **Adopt it** — integrate into our stack (strongly recommended)

**Why:** It's not a tool to install — it's a set of controls to implement, and the blast radius is high enough to justify the work now. Concretely on our side: audit every AI coding agent session for unnecessary write access, make credentials scoped and short-lived rather than long-lived tokens, run agents in containers rather than on hosts with broad repo access, and treat agent-readable content (tool outputs, fetched pages, repo files) as untrusted input rather than instructions. The reason this gets an Adopt verdict despite being a threat rather than a product is that unlike everything else in today's brief, the cost of ignoring it isn't a missed opportunity — it's a compromised repository, and one of those we can't roll back cleanly.

## Overall Assessment

Today's scan has one dominant theme and three things worth doing about it: **harness design, not model choice, is where the leverage is.** AWS measured a 77% cost difference on Terminal-Bench 2.1 between two harnesses running the same model; Alibaba measured a 4.7x precision difference on code review between two harnesses running the same model; and OpenAI and AWS both shipped products whose core feature is context management. Three independent sources, one conclusion. The concrete action is not to adopt any of their harnesses — it's to audit our own context handling: do we compact proactively before overflow, or do we degrade? If Strands Harness's documented defaults are better than ours, implement the pattern directly. That's the highest-return work available today, and it requires no new dependency.

Two items get a straight Adopt. **Claude Code's AGENTS.md support** is a version bump and a file consolidation that removes duplicated instruction files across our agents — a direct win with a compliance-friendly side effect, since one governed instruction file is one file to audit. **The Shai-Hulud session-hijack story** isn't a tool, but it's the highest-stakes item in the brief: AI coding agents carry live credentials and repo write access, and a worm just propagated through exactly that profile across ~100 repositories. Audit session write access, scope and shorten credential lifetimes, and sandbox the agents. Unlike the missed opportunities elsewhere, this failure mode doesn't roll back cleanly.

Everything else is Watch, and for consistent reasons. **Jev** is a genuinely new model shape that maps onto real gaps in our agent work — but unresolved bias in a scoring model is a hard stop in a healthcare context, and a one-week-old category with vendor-sourced benchmarks deserves patience. **ZCode** is technically strong with explosive adoption, but it shipped with silent data uploads and only opened after being caught, which tells us enough about its defaults. **Z.ai's** 6,000 stars in 48 hours is simultaneously the best argument for watching it and the best argument against trusting it yet. **kerpopule/hermes-jev-skills** is the one I'd actually assign reading time today — it's built for our exact runtime and solves problems we have, so read the compaction and skill-selection logic now, implement the good parts natively, and skip the TypeSafe dependency until Jev matures.

Nothing in today's scan justifies disrupting our current stack. The work is: harden the agent sessions, consolidate the instruction files, and go read three harnesses' context-management strategies and steal the best one.
