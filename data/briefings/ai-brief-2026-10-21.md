## 1. OpenCode 2.0 (anomalyco/opencode)

**What it is:** An open-source terminal/desktop/IDE coding agent from Anomaly, rebuilt in 2.0 (shipped Oct 12) around a single background service that every client connects to. `opencode serve` runs a headless HTTP server with an OpenAPI spec; `opencode run "…"` does one-shot non-interactive runs; `@opencode-ai/sdk` is a type-safe JS/TS client for driving it from code.

**Source:** https://github.com/anomalyco/opencode · https://opencode.ai · changelog https://opencode.ai/changelog · Provenance: spotted on Hyperautomation Labs (Product Hunt Week 42 roundup) — https://www.youtube.com/watch?v=sZQpKHL58tk

**What's good about it:** The 2.0 rebuild is exactly the shape we already use for Hermes: one long-lived local service, many clients. `opencode serve` gives us a documented HTTP API (`/session`, `/message`, `/command`, `/file`, `/event` streams) with an OpenAPI spec — the same interface for a cron job, a Telegram handler and a browser. `opencode run` gives us the boring one-shot version for scripted jobs. The permission system is granular and real: each action resolves to `allow` / `ask` / `deny`, rules can be scoped to paths and bash command patterns, and `--auto` approves only what isn't explicitly denied — that is the gate we actually need before letting anything `git push` on our behalf. It also reads LSPs, so a TS/React session in the Unified Platform gets type errors the way an editor would.

**Pros:**
- **Provider-agnostic with logins we already pay for.** 75+ providers via Models.dev, plus "log in with GitHub for Copilot" and "log in with OpenAI for ChatGPT Plus/Pro". Our Claude Max / Copilot subscriptions become usable by the agent without metering every call as API spend.
- MIT licensed, 219,426 stars, 29,290 forks, 950 contributors, pushed continuously (latest changelog entry v2.1.2, Oct 21) — this is not a star-farmed newcomer.
- A real permission model: `"ask"` by default, `"deny"` enforced even under `--auto`, per-agent rule sets, and a read-only `plan` agent that denies edits and asks before bash. We can give the brief-writing agent a plan agent and keep the deploy agent on a short leash.
- Built-in worktree tools (v2.0.27): an agent can create an isolated worktree, move its session into it, and remove it with normal edit approval — so experimental work never touches a working tree.
- Session export/import and `/share` links, so an agent's run can be audited after the fact instead of trusted.
- Desktop app as a `.deb`/`.rpm`/AppImage means it runs on the VPS headless and on the Windows box if we ever want it there.

**Cons:**
- 3,806 open issues. A rebuild this fast (v2.0.27 on Oct 12 → v2.1.2 on Oct 21) means the plugin API changed under everyone, and anything we build on 2.0's extension points will chase churn for a few more weeks.
- The 1.x → 2.0 migration is not clean: community reports of customisations not carrying over. If we adopt, we adopt fresh on 2.x and port nothing.
- Auth is per-provider logins on the host. Anthropic/OpenAI subscription sessions on a datacenter IP is the exact pattern we already burned ourselves on — **this runs on the VPS only with API keys it can rotate, or on the desktop with the subscription logins. Never both.**
- `opencode serve` binds `127.0.0.1:4096` by default and is protected only by optional HTTP basic auth (`OPENCODE_SERVER_PASSWORD`). Exposing it needs Traefik + the same hygiene as any of our internal services.
- Free-model tiering is now a product surface (`OPENCODE_DISABLE_FREE_MODELS`, free-limit dialogs), i.e. the product is moving toward a paid hosted plan; the free local path may lag.

**Should we...**
- ✅ **Adopt it**

**Impact on our stack:** High — **Hermes cron + agentic-os.** Concretely: our `ce:build` / `ce:full` jobs currently hand-write code with the agent's own file tools. With `opencode serve` on 127.0.0.1 behind basic auth, a cron job can POST a session, stream `/event` for progress, and have the *coding* done by an agent with a permission file that denies `git push`, denies writes outside `/var/www/<project>/`, and asks on `docker`. Same job, one less class of "the agent deleted something interesting."

**Why:** We have run almost every cron job in this stack as *content* work — briefs, emails, audits, reports — and kept the code work manual, because a scheduler that can run an agent and an agent that can rewrite production files were never safely separable. OpenCode 2.0 separates them: the scheduler stays Hermes, the coding agent becomes a headless service with a documented API and a deny-first permission layer, and the model bill comes off our subscriptions instead of per-token API calls. The reason this is an adopt and not a watch is that it clears every bar a new repo cannot: a repo running since April 2025 with 950 contributors, MIT, daily releases, and a permission design we can read and tighten ourselves. The first concrete step is not a migration — it is installing it on the VPS, running `opencode serve` on localhost with a password and a deny-list that mirrors what our cron wrappers already refuse, and using it for a single non-production job (a weekly dependency/upgrade audit of the Unified Platform) for two weeks before trusting it with anything that ships.

## 2. Harness (autonomous-ai/openharness)

**What it is:** An open-source (MIT) "command centre" for coding agents — Claude Code, Codex, Cursor, OpenCode, Devin, Amp, Copilot and Hermes among 14 supported engines — that shows every agent on every machine side by side, each in its own tmux pane, with an end-to-end-encrypted relay between machines so no box has to open a port.

**Source:** https://github.com/autonomous-ai/openharness · https://www.autonomous.ai/harness · Provenance: spotted on Hyperautomation Labs (Product Hunt Week 42) — https://www.youtube.com/watch?v=sZQpKHL58tk

**What's good about it:** It names our exact topology. Its README headline is "Claude Code at work. Codex at home. **Hermes in the cloud.** One command center" — and it ships a Hermes engine entry among its 49 store harnesses. Under the hood it does the one thing we hand-rolled with Tailscale plus a SOCKS5 proxy: one daemon per machine dials *out*, so no machine accepts an inbound port, and remote terminals stream bytes peer-to-peer rather than pixels. The design decisions are the ones we would make: never wrap the agent (read transcripts, use the vendor hooks), one git worktree per harness, real tmux underneath so scrollback and keys work, and a keystroke-driven UI (⌘P to jump to any harness on any machine).

**Pros:**
- Solves our desktop↔VPS agent split without the SOCKS5/proxy dance: `harness remote-password set` + `harness start`, and the app links the machine by password. Our tailnet stays, but the agent path stops depending on it.
- ChaCha20-Poly1305 + X25519 session keys + pinned Ed25519 identities, with the relay forwarding ciphertext it cannot read — a credible answer to "does an agent we drive from a laptop leak departmental data to a broker's fast path?"
- Open source all the way down: app, CLI, daemon, relay and device in one MIT repo; 1,331★, 119 forks, real merge traffic from multiple authors (PRs #1494–#1497 today).
- The `harness` skill lets one agent start, wait for and read another — that is cross-agent orchestration we currently do by hand between cron jobs.
- Measured, published performance work (release fixture, 16 terminals, p50/p95 for UI and echo) rather than a vibe claim.

**Cons:**
- **The primary client is a Flutter desktop app for macOS/Linux.** The Windows box is our actual desktop; running the command centre means running it on the VPS with a display or living in the `hn` terminal UI, which throws away the thing that makes it good.
- The relay and the phone-home "sign in" path are infrastructure *we* do not operate. End-to-end encryption or not, agent keystrokes for a hospital department traversing a third party's relay is a policy question with a boring answer for now: only over the direct WebRTC path on our own tailnet.
- 50 open issues, 2 watchers, and a product company (Autonomous sells a $149/$299 "Harness" desk device) shipping the free app — the roadmap's centre of gravity is the hardware, not the self-hosted CLI.
- It adds a second scheduler-shaped thing next to Hermes. Two ways to start an agent is one too many unless it clearly wins on a specific job.
- Building from source needs Xcode and Flutter **3.47+ / Dart 3.13+**, so we cannot fork it on the VPS if we want to change anything.

**Should we...**
- 👀 **Watch it**

**Impact on our stack:** Medium — **Hermes cron, agentic-os, and the desktop↔VPS workflow.** If it earns a place, it replaces the `ssh desktop` + SOCKS5 path for *agent* work specifically, and gives one screen where the interview-portal agent, the brief agent and a Unified Platform agent can be watched and answered at once.

**Why:** This is the most on-target tool in today's batch — it is literally built to sit between a laptop and a cloud box where Hermes runs. But "on target" is not "usable on our hardware today": the good part is a desktop GUI on Linux/macOS, our desktop is Windows, and our only always-on Linux host is the VPS — which would mean either a virtual display or the terminal-only `hn` mode that does less than what we already have. Watch it for two things: whether the mobile/iOS-Android work that landed today (PR #1497) grows into a usable remote *watch-and-answer* client — which is what we'd actually want from a phone at 6 a.m. — and whether anyone reports running the desktop app on Windows via WSLg. If either lands, this becomes a strong adopt in place of our hand-rolled proxy path. Until then it is a nicer dashboard for a problem we have already solved adequately.

## 3. gitai (feder-cr/git-ai)

**What it is:** A Go re-implementation of the version-control design Anthropic described in "Redesigning source control" — server-centric, always-online clients, compare-and-swap landing instead of a merge queue, server-side history and blame, changeset log, and automatic conflict resolution where a model's proposal only lands if a configured `verify.command` passes on the exact tree.

**Source:** https://github.com/feder-cr/git-ai · Anthropic's original design write-up: https://www.anthropic.com/engineering/redesigning-source-control · Provenance: GitHub new-repo scan (1,044★ in six days)

**What's good about it:** The ideas are worth reading even if the software is not. The land-with-verification loop — a merge that only lands when a named check passes on the tree that would actually land, otherwise the agent gets the conflict package back — is a pattern we could copy into our own deploy scripts this week with plain `git` and a pre-receive hook. Making agents first-class users with per-agent tokens and an RPC allowlist is also the right shape for our cron agents. And the README is unusually honest: it documents limitations in `LIMITATIONS.md` and ships the design documents (PLAN.md through PLAN8.md) alongside the code.

**Pros:**
- The verify-before-land design is directly transferable; reading `RESOLVE.md` and `VERIFY.md` is worth more to us than running the server.
- Server-side derived data (blame, path history, ancestry, code search computed once per commit and memoized) is the correct instinct for a repo that agents query far more often than humans do.
- Real benchmark and fuzzing write-ups in-tree rather than a GIF.
- Stateless server nodes over SQLite/Postgres + object storage is a sane, boring operational model.

**Cons:**
- **The licence contradicts itself.** The README says "MIT licensed"; the LICENSE file is the **GNU Affero GPL v3** (with a GitLab-derived MIT carve-out for `ee/`). AGPL on a server product means modifications we serve must be published — and the "MIT" claim in the README is wrong. That is the single biggest red flag in today's batch.
- Six days old (created 2026-10-15), a single author, and commit history that is mostly merge commits of design plans — the artifact is a well-documented *experiment*, not a maintained system.
- Build needs Go 1.26, a C toolchain, Meson and Ninja because it compiles a bundled Git. It cannot be evaluated casually.
- It solves a problem we do not have: Scion exists because Anthropic reached ~30,000 merges a day. We run four repos and one human pushing.
- Independent "implementation of a publicly described design" is the highest-risk kind of software to trust with source of truth: the spec it copies is prose, not a conformance suite.

**Should we...**
- ❌ **Skip it**

**Impact on our stack:** Low — agentic-os source control, and only as a *pattern*, not a component.

**Why:** Skip the software, steal one idea. There is no world this week in which the department's source of truth moves off GitHub onto a six-day-old single-author AGPL server that compiles its own Git — and the licence mismatch alone disqualifies it, because the one thing we cannot afford in a version-control layer is ambiguity about what we are allowed to do with it. What we *should* take is the land-only-if-verified loop: an agent's change lands only when the deploy check passes on the exact tree being landed, otherwise the agent receives the failure and the diff and must try again. That is five lines in a pre-receive hook plus the verification step our cron jobs already run, and it closes a real hole — agents that "finish" work that does not build. Filed so it is not re-suggested; if Anthropic ever open-sources Scion itself, that is a different conversation.

## 4. Inbox Zero (elie222/inbox-zero)

**What it is:** An open-source (LICENSE file: AGPL-3.0) AI email assistant and email client for Gmail and Outlook. The assistant part runs in the background on your account: sorts and labels, pre-drafts replies in your tone, plain-English rules, "Reply Zero" tracking for emails awaiting a response, bulk unsubscribe/archive, cold-email blocking, meeting briefs, and — relevant to us — Slack and Telegram integration. Self-hostable via `npx @inbox-zero/cli setup` (Docker + Node 24) or with `pnpm local:start`, and the hosted plans run $18–$42/user/month.

**Source:** https://github.com/elie222/inbox-zero · https://www.getinboxzero.com · Provenance: spotted on Hyperautomation Labs (Product Hunt Week 42, ranked 9th) — https://www.youtube.com/watch?v=sZQpKHL58tk

**What's good about it:** Of the ten Product Hunt launches, this is the one whose *feature list* maps onto a job we do badly. The department inbox gets residency applications, attendee correspondence, vendor mail and journal alerts in one pile, and the "Reply Zero" idea — a queue of what needs a reply and what is awaiting one from someone else — is the piece Hermes does not give us, because our email path sends but does not track. The rules engine is plain English, so a program coordinator could write "label anything mentioning interview scheduling and draft a reply in my voice" without touching code. It also speaks Telegram, which is already where our notifications live.

**Pros:**
- 12,721★, 1,612 forks, repo active since July 2023, pushed today, 141 open issues with real triage — mature by any measure we use.
- Self-hosting is a documented first-class path (`@inbox-zero/cli`, Docker images on ghcr.io tagged per commit and per release), so the mailbox never has to sit in a third party.
- The free email *client* and the paid AI are separable — we can take the client without the model bill.
- Reply tracking + meeting briefs + smart attachment filing are three things a residency program director actually needs and currently does by hand.
- Telegram integration means no new surface for us to teach anyone.

**Cons:**
- **AGPL-3.0.** Every other item in our stack that we deploy is MIT or Apache. AGPL on a service we host for staff is an organisational decision, not a weekend install.
- **The scopes are the blocker.** Running the assistant means granting it live mailbox access (Gmail/Outlook OAuth with broad read/modify/send rights) for a *montefiore.org*-adjacent workflow. That is the same class of risk as the O365 device-code incident in July: a third-party-shaped app holding live credentials, now self-hosted on our own box.
- Signing in to a real Gmail/Outlook account from the VPS puts a live session on a datacenter IP. That rules out the VPS and points to the desktop.
- Next.js + Prisma + Redis + Postgres + Node 24 is a fifth stack for us to patch, next to Hermes, the Unified Platform, the interview portal and the schedule app.
- Hosted pricing is per-user per-month, and the free tier keeps the AI features behind the paid gate — "free and open source" in the launch list is really "open source, hosted plans start at $18."

**Should we...**
- 👀 **Watch it**

**Impact on our stack:** Medium — **email/Outlook path.** The concrete change, if it ever clears policy: a reply-tracking and triage layer in front of the department inbox, with Telegram as the control surface — which is the one piece our current `smtp_send.py` + `google_workspace.py` pair deliberately does not cover.

**Why:** The honest read is that this is the right product for our problem with the wrong licence and the wrong credential model for a hospital department. We already made one policy call in this area — we chose "data inline in the inbox" over "link behind a login" — and the same caution applies here, only more so, because this thing wants to read and write mail rather than just deliver it. The right next step costs nothing: run it locally against the *development* emulators (`pnpm local:start` ships mail-provider, billing and LLM emulators and needs no OAuth or API keys) to see whether Reply Zero and the rules engine would actually save the coordinators' time. If the workflow is a clear win, the sane deployment is the desktop app or the hosted plan on a department account with a scoped integration — not a self-hosted instance on the VPS holding live mailbox credentials. Watching, not adopting, and explicitly not on the VPS.

## 5. EmbeddingGemma 2 (google/embeddinggemma-2)

**What it is:** Google's second-generation EmbeddingGemma — a 744M-parameter, Apache-2.0 multimodal embedding model on Hugging Face (created 2026-09-14, last updated 2026-10-06) that maps text, images, audio and video into one shared vector space, with a GGUF build from Unsloth for local inference.

**Source:** https://huggingface.co/google/embeddinggemma-2 · https://huggingface.co/unsloth/embeddinggemma-2-GGUF · Provenance: spotted on Hyperautomation Labs (Product Hunt Week 42, "one search across text, photos, audio and video") — https://www.youtube.com/watch?v=sZQpKHL58tk

**What's good about it:** We have 28 faculty interview clips, an accumulating vault of 1,576 items, and several sets of recorded sessions — and no way to search any of it except by remembering what we wrote down. A single embedding model that covers the transcript text *and* the frames solves the hard half of "find the clip where the chair says X": audio and video go into the same space as the words, so a query in prose can retrieve a moment, not just a file. Apache-2.0 on 744M parameters means it runs on our own hardware with no per-token bill, and the Unsloth GGUF variant means CPU inference is viable through the same llama.cpp path we already have in the container for other models. It also supersedes the 300M EmbeddingGemma we would otherwise reach for, at a 2.5x size bump — an acceptable trade for multimodal.

**Pros:**
- Truly permissive for a hospital: Apache-2.0, unlike its predecessor's Gemma licence — that is a real change, not a formality.
- Multimodal in one space: text, image, audio and video tokens share an index, so evidence retrieval for the copy desk and the interview archive becomes one pipeline instead of three.
- 172,474 downloads and 2,784 likes since Sept 14, and `endpoints_compatible` — it is being used, not just announced.
- Fits where we already run things: features-extraction pipeline, transformers-compatible, safetensors, plus a GGUF quantisation.
- A genuine improvement over text-only search in the one place it matters to us: proving what is actually in a clip or a deck.

**Cons:**
- **Mind the date.** Last modified 2026-10-06, three weeks before this brief; it is the model *and* the Product Hunt coverage of it that are in-window. Google's model card is the place the specs live, and I am not going to invent a dimension count I did not read.
- 744M parameters on BF16 is ~1.5 GB before any index — fine for embed-once, wrong for embedding 28 videos' worth of frames on the CPU-only container we run. Ingestion belongs on the desktop or a GPU box.
- A shared vector space trades precision for breadth: it will beat text-only on "find the clip about the angry patient" and lose to a good text embedder on exact-name lookups (faculty names, drug names, MRN-adjacent strings). Hybrid retrieval is mandatory, not optional.
- Embedding text and video from *patient-adjacent* material means an index of those vectors sitting on disk — a data-governance question before it is an engineering one.
- The Product Hunt framing ("one search across text, photos, audio and video") oversells a model as an application; there is no UI here, only vectors, and the search layer is ours to build.

**Should we...**
- 👀 **Watch it**

**Impact on our stack:** Medium — **agentic-os (vault search) and the copy desk.** The concrete change: every interview clip and every brief gets a multimodal embedding at ingest, so the vault stops being a list you grep and becomes something you can ask "which clip shows the chair explaining the call-out policy?" — with a timestamp as the answer.

**Why:** The strategic value is high — it is the missing half of our media archive, and it is the first embedding model permissive enough (Apache-2.0) that we could actually ship a department index without a licence conversation. But the value is entirely in the *pipeline*, and the pipeline does not exist yet: we would need an ingest step that extracts audio, samples frames, embeds, and stores vectors next to the existing vault records, plus a hybrid retriever so exact names still work. That is a week of work on the desktop, not a cron job, and it presumes the ingest hardware is not the CPU-only container. The specific trigger to revisit: the next time we cut interview clips for social, because that workflow already produces the audio and frame extracts this needs — build the index as a by-product then, rather than as its own project. Watch, and do not let it near anything clinical.

## Overall assessment

If we do nothing else, do these, in this order:

1. **OpenCode 2.0 — install it on the VPS as a localhost-only service with a deny-first permission file, and give it one real but non-shipping job** (the weekly Unified Platform dependency and build audit). This is the only item today that changes what our scheduler is allowed to *do*: from writing content about the stack to safely maintaining it.
2. **Inbox Zero — run it against the local emulators, no credentials, and judge the Reply Zero queue.** Cost: an hour and a Docker compose. If the queue works for the department inbox as well as it looks, that is the first real answer to "what needs a reply" we have had.
3. **EmbeddingGemma 2 — fold it into the next interview-clip cutting session instead of building a search project.** The ingest work is already happening there; the index is a by-product, and it is the difference between owning 28 clips and being able to find the one you need.

**Deliberately not in the top three:** Harness is the best-matched tool and the worst-matched hardware — watch it until a Windows or mobile client exists. gitai is filed as rejected: right idea, wrong licence, six days old.
