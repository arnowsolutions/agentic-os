### ClawVet

**What it is:** An npm CLI (v0.18.0, MIT) that statically scans AI agent skills — `SKILL.md` plus every script it references — for prompt injection, credential theft, remote code execution, typosquatting and permission-changing updates. Seven passes: six run offline and free (frontmatter parsing, regex rules, Tree-sitter AST taint analysis for Python/JS/TS/shell, metadata hygiene, dependency checks, typosquat distance), with an optional LLM judge and OSV.dev lookup. It also does the thing nothing else in our stack does: a **rug-pull diff** that records what a skill was allowed to do and re-prompts when an update adds a secret read, persistence, or a new outbound host.

**Source:** https://github.com/MohibShaikh/clawvet · Playground: https://clawvet.vercel.app/ ·  · Provenance: Show HN — https://news.ycombinator.com/item?id=50587571 (posted 2026-11-21 09:40 UTC)

**What's good about it:** I installed it rather than reading the README: `npm install clawvet` pulled 6 packages with no conflicts, and `clawvet audit --dir /home/hermeswebui/.hermes/skills --summary` finished in **4.2 seconds** with real numbers — 86 bundles scanned, **1,555 findings**, grades A 33 / B 7 / C 1, and 58 items at high risk. Specific hits that are worth a human look regardless of whether they are malicious: the `runpod` skill reads `~/.ssh`, `~/.aws`/`~/.gnupg` and writes `~/.ssh/authorized_keys`; `vps-service-deployment` writes shell startup files; `reimbursement-workflow` produced 43 findings; `premium-product-stack` produced 86. Some of that is documented deploy choreography, not an attack — but nobody has ever had an inventory of what our 670 skills can actually *do*, and this produced one in four seconds. A single-skill `scan` on `admin/workday-contingent-worker-onboarding` took **0.17s** and returned grade A with one HIGH finding, so the per-skill path is fast enough to sit in front of an install.

**Pros:**
- Fully offline by default — no API key, no account, no Docker, no network. That means it can run on the VPS (datacenter IP) without tripping anything.
- The rug-pull diff is aimed at the exact attack class we are exposed to: a skill that is clean when we review it and adds a credential read or persistence hook in a later update. It stores approved installs in `~/.local/state/clawvet/installed` and names each new permission on update.
- Tree-sitter taint tracking proves credential→network flows in Python, JS/TS and shell instead of keyword-matching, which is why it can grade distinct risk rather than noise.
- 4 seconds for the whole tree and 0.17s for one skill — cheap enough to wrap around every install and run monthly.
- MIT, npm provenance attestations (`npm view clawvet dist.attestations`), a GitHub Action that posts a Permissions Diff on PRs, a pre-commit hook, and SARIF output for code scanning.
- It publishes its benchmark instead of claiming one: SkillTrustBench v1.1 held-out 556 cases, 0.833 accuracy / 0.770 macro F1 with the LLM judge, and 95.2% of code-injection rug-pulls caught at a 5.1% false-prompt rate on benign updates.

**Cons:**
- **One contributor.** A security tool with a bus factor of one should not become the only gate between us and a malicious skill.
- **Bulk audit undercounts our layout badly:** `audit --dir` found **86 items against our 670 `SKILL.md` files** — it treats a top-level directory as a skill, and our skills are nested one level deeper (`skills/<category>/<skill>/SKILL.md`). The per-skill `scan <path>` works fine; the summary does not, so any repo-wide number from it today is ~13% of the library.
- **45 of the 86 items came back "could not be fully inspected"** — coverage gaps concentrate on markdown-heavy skills, which is most of ours.
- **False positives on prose.** It flagged a HIGH "Docker socket/exec access" in a `references/*.md` that merely *mentions* `docker exec`, and the same skill still graded A — the score and the findings disagree, which is confusing in triage.
- The install-time gate integration is written for OpenClaw's `security.installPolicy`; there is no Hermes adapter, so gating our own installs means writing the wrapper ourselves.
- No Hermes harness profile (NVIDIA SkillEvaluator has one), so spec/frontmatter checks are generic.

**Should we...**
- ✅ **Adopt it** — narrowly, as a pre-install scanner plus a monthly sweep. Concretely: a `skill-vet <path>` wrapper around `clawvet scan <path> --format json --fail-on high` that runs before any third-party skill is installed, and a monthly per-skill pass over the top-level bundles (script the loop; do not trust `audit --dir` until the nesting is understood). Not as the only gate, and not as a repo-wide CI gate until the 87% undercount is fixed.

**Impact on our stack:** High — the Hermes skill library, which is 670 files of instructions and scripts that run with our shell, our keys and our Telegram bridge. The concrete change is that a third-party skill gets a permission manifest before it runs, and a skill we already trust gets diffed on update instead of trusted forever.

**Why:** This week produced a real example of the thing ClawVet scans for — an npm package that installed Hermes Agent and pointed it at an attacker's Telegram bot — and it arrived the day after we adopted SkillEvaluator, which answers "is this skill well built" but not "what can this skill do to us". ClawVet answers the second question offline, in seconds, with no credentials, which is the only kind of security tool we can actually run on this VPS. The verdict is adopt-but-narrow rather than a full gate because the tool is one maintainer old, misses most of our library in bulk mode, and contradicts itself on at least one finding — all of which are survivable for a pre-install advisory scan and not survivable for an unattended block. The payoff is not a cleaner report; it is knowing which of the 58 high-risk bundles should never have had the permissions they have.

### @leadstack/crm-connect — the npm package that turned Hermes Agent into a backdoor

**What it is:** A threat report on a malicious npm package, `@leadstack/crm-connect`, published by the account `zmaticoo` in nine versions on Nov 16, 2026. Its `postinstall` script installed Hermes Agent, fetched an `.env` and a `SOUL.md` (standing instructions) from `72[.]62[.]1[.]108`, connected the agent to a Telegram bot the attacker controls, and registered it as a systemd service renamed "LeadStack Lead Routing Daemon". When `npm install` ran as root, the agent ran as root. Later versions dropped the agent entirely and just ran a downloaded binary with the installer's full environment.

**Source:** https://safedep.io/blog/malicious-npm-leadstack-crm-connect-hermes-agent-backdoor ·  · Provenance: Hacker News — "NPM package installed Hermes Agent as root and tasked it over Telegram" (safedep.io, Nov 19–20). Not from a tracked channel.

**What's good about it:** It is a precise description of our own architecture used as a payload. Everything that makes Hermes useful — a `SOUL.md` of standing instructions, a `.env` full of keys, shell/file/browser tools, a Telegram bridge, systemd persistence, cron — is a turnkey implant if someone else supplies the instructions. The report also notes a September ThreatDown botnet that spreads through exposed Docker APIs and runs Hermes Agent as an implant, which makes this two independent campaigns using the same product as the payload rather than a one-off. The indicators are specific enough to check in a minute: `leadstack-routing.service`, `leadstack-ingest-worker.service`, `~/.leadstack/`, `~/.config/leadstack/`, `~/.local/share/leadstack/bin/`, `72[.]62[.]1[.]108`, `zmaticco[.]dev`.

**Pros:**
- Concrete, greppable IoCs rather than generic "supply chain risk" advice.
- Documents a Hermes-specific attack shape — install-time persona fetch (`SOUL.md` + `.env` from C2) — that no generic npm advisory would describe.
- I ran the check on this host: no `leadstack` in any `package.json`/lockfile under `/workspace`, no matching systemd units, no `~/.leadstack` or `~/.config/leadstack`. Clean, verified, not assumed.
- It points at the actual perimeter: the Docker API and root `npm install`, not the model.
- The timeline (nine versions in six hours, SafeDep flagging five minutes after the last release) shows how short the window between publish and payload is.

**Cons:**
- It is a threat report, not a tool — there is nothing to install, and the only real mitigation is policy we have to keep.
- The publisher account is still active per SafeDep, and three packages it released on Nov 18 contain no code of their own and pull a dependency from the attacker's server — the campaign did not end with this package being removed.
- The root systemd variant is the worst case, but version 1.0.18 falls back to a user service and enables linger, so "don't run as root" is necessary and not sufficient.
- The boring mitigations (no root `npm install`, `--ignore-scripts` for unknown packages, pinned versions, reviewing `postinstall`) are exactly the ones that get skipped under time pressure.
- It only covers npm; our Python path (`pip install` from arbitrary repos) has the same shape and got no equivalent study.

**Should we...**
- 👀 **Watch it** — as a standing threat class, not a one-day story. The two things to do now cost nothing: never `npm install` as root on the VPS, and use `--ignore-scripts` for anything that is not a known package. Add both unit names and `~/.leadstack` to the server-sweep checklist.

**Impact on our stack:** High — the VPS, the Hermes container, and every `npm install` we run. The concrete change is an install policy, not a dependency: unknown package → no root, no lifecycle scripts, read the `postinstall` first.

**Why:** This is the first time a threat report has described our exact stack as the payload rather than as a bystander: the attacker did not exploit Hermes, they *deployed* it, with their instructions and their Telegram bot, which is the same mechanism we use every day on purpose. That makes it more useful than any generic supply-chain advisory, and it pairs directly with ClawVet — ClawVet checks skills before they run, this checks the packages that would install an agent beside them. I verified this host is clean rather than assuming it, so the value today is not remediation; it is that the policy change is now grounded in a real incident with real indicators instead of a hypothetical.

### Chrome DevTools MCP (chrome-devtools-mcp)

**What it is:** Google's official MCP server and CLI that gives a coding agent a live Chrome browser: performance traces with actionable insights, network request inspection, console messages with source-mapped stack traces, screenshots, and script evaluation. 58,599 stars, Apache-2.0, TypeScript, last pushed Nov 20, 2026. Ships seven agent skills (browser control, CLI/scripting, accessibility, cookies, LCP optimization, memory leaks, troubleshooting).

**Source:** https://github.com/ChromeDevTools/chrome-devtools-mcp ·  · Provenance: spotted on The Next New Thing — https://www.youtube.com/watch?v=9oPorHRKsoY (chapter 10:46)

**What's good about it:** It closes the loop we currently fake. Every Unified Platform deploy gets verified by `curl` plus "does the HTML contain this string", which cannot see a React error boundary, a blank page from a stale anon key, or the doubled `/public-schedule` prefix that has broken the public schedule more than once — all three are visible only in the console and the network log. Because the package ships a CLI (`chrome-devtools navigate_page 1 --url …`, `take_screenshot 1 --filePath …`, `stop`), we do not need MCP wiring to use it: a post-deploy script can load the page, fail on any console error, and save a screenshot into the run log. The seven bundled skills are the same ones Claude Code and Gemini CLI install, so the instructions are already written.

**Pros:**
- CLI mode works from a terminal or a cron wrapper without any MCP client — that is the difference between "nice for interactive coding" and "usable in our pipeline".
- Console messages carry source-mapped stack traces, which is the specific blindness `curl` has.
- Real DevTools performance traces and LCP, plus `--slim` for a reduced tool surface when we only need navigation and screenshots.
- Google-maintained, Apache-2.0, weekly pushes, ~139 open issues on 58.6k stars — the healthiest ratio in this brief.
- Can attach to an already-running Chrome (`--browserUrl`) or take an explicit `--executablePath`, so it does not have to own the browser lifecycle.

**Cons:**
- Requires **Google Chrome stable**; the README says other Chromium builds are unsupported. Our container has Playwright's `chromium-1223`, which is exactly the unsupported case.
- **Telemetry is on by default** (tool invocation stats), and performance tools send trace URLs to Google's CrUX API. Two separate opt-outs (`--no-usage-statistics`, `--no-performance-crux`) have to be set explicitly — for a healthcare-adjacent environment that is configuration we must not leave to defaults.
- By design it exposes the entire browser instance — cookies, sessions, page data — to whatever is driving it. The README warns about this itself.
- The bundled skills must be re-copied on every version bump or the agent is taught tools that changed.
- It gives the agent eyes, not a test suite: unless it is wired into deploy checks, the value is zero.

**Should we...**
- 👀 **Watch it** — pilot the CLI on the desktop where real Chrome already exists, pointed at the Unified Platform staging URL, with both telemetry flags off. If it reliably catches the console errors our curl checks miss, install the server on the VPS later with Chrome baked into a layer that survives `docker recreate`.

**Impact on our stack:** Medium — the Unified Platform and the redesign-preview workflow. The concrete change is a post-deploy verification script that loads the page headless, fails on console error, and writes a screenshot to the run log instead of asserting on a string match.

**Why:** Our web work is the part of the stack where "it deployed" and "it works" are furthest apart, and the reason is that the agent has never been able to see the page it just published — it greps HTML and hopes. Chrome DevTools MCP is the most credible fix available (Google-maintained, official DevTools internals, a CLI we can call from cron), but it is a year old rather than new, it needs Chrome that our container does not have, and its telemetry defaults are wrong for our environment until we turn them off. That is a watch with a specific pilot, not an adopt: the cost of being wrong here is either a broken verification step that silently passes, or usage data leaving a system that sits next to clinical workflows.

### Kaggle Notebooks — free dual-GPU sessions

**What it is:** Kaggle's hosted notebook environment, used in the video as a free 32 GB VRAM server: two NVIDIA Tesla T4s at 16 GB each, no credit card, a one-time phone verification, a weekly GPU quota (Kaggle's docs say 30 hours), and Ollama installed inside the notebook. The demo runs Nous Research's Arete-27B Q4_K_M (17.2 GB) across both cards at 12.8 tokens/sec — a model no single 16 GB card can hold.

**Source:** https://www.kaggle.com/docs/efficient-gpu-usage ·  · Provenance: spotted on Hyperautomation Labs — https://www.youtube.com/watch?v=Uw5lbb9uJOk

**What's good about it:** Free aggregate VRAM is the difference between "we cannot test that" and "we can". The use case for us is not chat: it is `faster-whisper` large-v3 for the audiobook pipeline (an 8-hour book on CPU is hours of wall clock; on two T4s it is tens of minutes) and embedding passes for vault search. The video's numbers are concrete and reproducible — 155s download for a 17.2 GB model, 12.8 tok/s at Q4_K_M, 10,043 + 8,709 MiB split across the two cards — which is more than most "free GPU" claims come with.

**Pros:**
- No cost and no credit card; 30 GPU-hours a week is enough for recurring batch jobs if they are scripted rather than interactive.
- Two T4s hold a 27B Q4 model that does not fit on one consumer card, so it can test models we would otherwise only read about.
- The Kaggle API lets a notebook be pushed and run without opening an interactive session — the docs explicitly recommend this for efficiency.
- Public, reproducible benchmark numbers in the source video, including the install timing and memory split.

**Cons:**
- **The claims do not fully match Kaggle's own docs:** the GPU documentation still describes Tesla P100s and a **60-minute** idle timeout, while the video says dual T4s and 20 minutes. The docs win — verify the actual hardware and timeout in-account before planning around either number.
- It is Google's computer. No PHI, no patient data, no client files, no credentials. Audiobooks are personal material, which is already at the edge of what belongs there.
- Phone verification and an account are required, and GPU availability is demand-dependent.
- Interactive sessions burn quota while idle; without an API-driven workflow the free hours evaporate.
- A notebook is not a production environment — anything that works there has to be ported and re-validated.

**Should we...**
- 👀 **Watch it** — keep as the escape hatch for GPU work we cannot do on CPU. The one concrete pilot worth doing: a Kaggle notebook, pushed via the API, that transcribes one book with `faster-whisper` and returns text — measured against our current CPU time before anything is moved.

**Impact on our stack:** Medium — the audiobook/M4B pipeline and any local-model evaluation. The concrete change would be transcription wall-clock dropping from hours to tens of minutes for a full book, at the cost of a manual upload step.

**Why:** We keep hitting the same wall — the work that would benefit most from a GPU (transcription, embeddings) is exactly the work that runs on a CPU-only VPS, and buying or renting hardware for occasional jobs is a bad trade. Kaggle's free quota is a real way to test whether the GPU path is worth building, and the video even does the unglamorous work of timing it. But it lives on someone else's machine with a login and a phone gate, its documented hardware contradicts the video, and nothing sensitive can go near it — so it is a watch with one bounded experiment, not an infrastructure decision.

### replit/amuse

**What it is:** A self-hosted personal AI agent from Replit — research, a live browser, reminders and small apps, with approval prompts before actions, running on your own machine with an OpenAI key. 115 stars, Apache-2.0, created Nov 19, 2026.

**Source:** https://github.com/replit/amuse ·  · Provenance: GitHub Search API (`ai agent created:>2026-11-14`, sorted by stars)

**What's good about it:** Approval-gated actions are the right default and Replit is a real org with a real security posture, so this is not a random repo. The feature set — browser, reminders, small apps — is a coherent product rather than a framework demo.

**Pros:**
- Backed by Replit rather than an anonymous account; Apache-2.0.
- Approval-before-action is a better default than most agent shells ship with.
- Small, legible scope: one process, an OpenAI key, local files.

**Cons:**
- Two days old, 115 stars, a single push, no release, no visible test suite — by our own rule that is watch at best, and here it does not even clear that bar.
- It is a strictly narrower Hermes: no cron, no skills library, no Telegram or voice, no MCP breadth, no multi-provider routing. Everything it does, we already run.
- Tied to an OpenAI key; no provider abstraction documented, and we run DeepSeek/Nous.
- A second self-hosted agent on the same machines means a second thing reading our files and keys, for zero new capability.

**Should we...**
- ❌ **Skip it** — it duplicates the agent we already operate, at two days old, with no capability we lack.

**Impact on our stack:** Low — nothing it offers is missing here, and running it would add an attack surface without adding a function.

**Why:** The test for a new agent shell in this stack is "what can it do that Hermes cannot", and the honest answer is nothing: Amuse's browser, reminders and approvals are features we have had for months with more behind them. Filing it as a skip matters mostly so it does not resurface as a "promising new agent" in three weeks when the star count is higher and the commit count is still one — young, single-push repos are exactly where star promotion hides.

## Overall assessment

If we do nothing else, do these, in this order:

**1) ClawVet as a pre-install scan.** It is the only item today that I could install and run against our real system inside ten minutes, and it produced numbers we have never had: 1,555 findings across 86 skill bundles, 58 of them high-risk, including skills that write `~/.ssh/authorized_keys`. Wrap `clawvet scan <path> --format json --fail-on high` in a `skill-vet` script and run it before anything third-party is installed. Cost: a script and a minute per skill.

**2) The install policy from the SafeDep report.** No root `npm install`, `--ignore-scripts` for unknown packages, and the two `leadstack` unit names plus `~/.leadstack` added to the server sweep. This is the difference between auditing the things that run beside Hermes and discovering that something installed Hermes for us. This host is clean today — verified, not assumed.

**3) The Chrome DevTools MCP pilot on the desktop.** One script that loads a Unified Platform page through the CLI with telemetry off, fails on console error, and saves a screenshot. If it catches the class of breakage our `curl` checks miss — stale keys, doubled URL prefixes, error boundaries — it becomes the deploy check; if not, we have spent an hour.

The common thread: today's haul is about the *perimeter of the agent*, not its intelligence. The best model release of the week does nothing for us if a skill we installed in March can write to `authorized_keys`, or if a package we `npm install` hands someone a Telegram-controlled root shell. ClawVet, the SafeDep incident and the browser-control server all point the same way — make the agent's inputs visible before they execute.
