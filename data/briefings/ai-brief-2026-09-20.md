### TypeSafe AI — "Jev"

**What it is:** A new transformer-based model from TypeSafe AI (founded by Diogo Almeida, the OpenAI researcher who helped build ChatGPT and invent RLHF) that is deliberately *not* an LLM — it outputs calibrated probabilities ("calibrated decisions") instead of text. Released this week.

**What's good about it:** The design bet is that most automation doesn't need fluent language — it needs a reliable yes/no/score. By fixing the output space up front, the model structurally cannot hallucinate. It's also radically cheaper: output tokens are free, input tokens are metered by the billion rather than the million. Vercel reported that swapping OpenAI's Luna for Jev on a command-safety classifier produced results 5–18× faster with greater accuracy; another developer found Gemini was slightly more accurate on email classification but 10–20× more expensive.

**Pros:**
- Can't hallucinate — outputs are constrained to pre-defined decision categories, so failure mode is "low confidence," not "confidently wrong."
- Real probability scores — rare among classifiers, and exactly what you need to gate automated actions with a confidence threshold.
- Dramatically cheaper at scale — billion-token input metering makes high-volume classification/routing economically viable.
- Strong augmenting role — can act as a cheap oversight layer over LLM agents (tracing, jailbreak detection, routing) without the cost of running a second LLM.
- Credible founders — Almeida's RLHF pedigree plus a synthetic-data lab gives the approach real technical backing.

**Cons:**
- Closed API, no self-hosting — nothing about the a la carte deployment we need for anything touching PHI or internal resident data.
- Opaque architecture — outside observers suspect it's built on top of an open-weight LLM; TypeSafe won't say.
- Single-purpose by design — it is not a substitute for an LLM; it's a component, so it adds a second vendor and integration surface.
- Very early — API couldn't keep up with launch-day demand, a sign of operational immaturity.
- Delegates the calibration problem to you — a 50% probability still requires a human-defined threshold; no free lunch.

**Should we...**
- 👀 **Watch it** — keep an eye on it, not ready yet but promising

**Why:** Jev is the most intellectually interesting thing in this scan, and the general pattern — small, cheap, non-generative decision models bolted onto LLM pipelines to do classification, routing, and oversight — is almost certainly where the stack is heading. The practical fit for us is real: command-safety classification, agent-trace monitoring, and model routing are all jobs sitting in our Hermes/CE pipelines where a 10–20× cost reduction matters. But it's a closed API with an undisclosed architecture, and anything we'd route through it currently touches internal data subject to the same constraints that stopped us from moving healthcare data into third-party tooling. Watch until it has a self-hosted or enterprise option, and revisit when Almeida ships the next modality.

### Plugin4Shell — zero-click RCE across AI coding agents

**What it is:** A zero-click remote code execution vulnerability (dubbed "Plugin4Shell" by researchers at AIR) affecting Claude Code, OpenAI Codex, GitHub Copilot, and Gemini CLI. It bypasses the SHA-pinning mechanism that plugin marketplaces use to lock agent plugins to a reviewed, immutable commit.

**What's good about it:** Nothing — but the *disclosure* is exemplary and the fix situation is the real story. The vulnerability is a plugin SHA-pinning bypass: the agent asks git to check out the pinned commit but never verifies the checkout actually landed there. An attacker who controls a plugin's repo can make the checkout resolve to malicious code while the pin still appears honored. Because Claude Code and Codex auto-update installed plugins by default, the swap reaches already-installed plugins with **no user action at all** — the classic zero-click. Anthropic patched it in Claude Code 2.1.179 and OpenAI in Codex 0.146.0. Microsoft has shipped no Copilot fix; Google deprecated Gemini CLI entirely rather than patch, leaving every existing install exposed indefinitely.

**Pros:**
- (Of the mitigation landscape) Anthropic and OpenAI patched fast and published versions — a clean update path exists for the two most-used agents.
- The disclosure gives a precise, actionable remediation: verify agent version, then re-pin or remove third-party plugins.
- It exposes a *class* of architectural blind spot — the same trust-boundary failure has now hit this cluster of agents twice in 2026, so it's a fixable pattern rather than a one-off.
- GitHub applied naming restrictions on version/tag names resembling commit SHAs, partially mitigating its own marketplace.
- It's a forcing function for plugin/skill provenance hygiene, which we have not formally audited.

**Cons:**
- Two of four vendors left users exposed — Copilot unpatched, Gemini CLI permanently vulnerable by deprecation.
- "Deprecated" ≠ "fixed": every Gemini CLI install stays exploitable with no update path ever.
- Marketplace-side mitigation is insufficient by the researchers' own account — plugins can be hosted on Bitbucket etc., so only the agent itself can close the gap.
- Scope is broad: exposure is not limited to careless users — anyone with a reviewed, pinned, trusted plugin installed was reachable.
- Related research (SkillJacking) found 925 hijacked skills already in active use reaching 134,000 agents — the takeover half of the chain is proven at scale.

**Should we...**
- ✅ **Adopt it** — meaning: patch immediately and audit our plugin/skill surface

**Why:** This is the most operationally urgent item today because it maps directly onto how our own stack works. Our Hermes deployment runs third-party skills and pluggable integrations, and the CE pipelines and agentic-OS layer execute agent tooling against our repos and internal data — exactly the reach Plugin4Shell grants an attacker ("the same reach into a company's systems and data as the employee running the agent"). Three concrete actions: (1) confirm no agent we run is a Gemini CLI install, since those are permanently unfixable; (2) update Claude Code to ≥2.1.179 and Codex to ≥0.146.0 wherever they're invoked; (3) if anything in the stack uses Copilot as a coding agent, treat its marketplace plugins as untrusted until Microsoft patches. Then do a one-time inventory of every pinned plugin/skill across our agent surfaces so we know what a future disclosure would implicate. The reusable lesson: a pinned SHA is not a security boundary unless the agent verifies the checkout.

### PrismML — Ternary Bonsai 2 27B

**What it is:** A 27B-parameter reasoning model compressed to **~5.9 GB** (down from ~54 GB FP16) using "ternary" weights — instead of full-precision numbers, each weight is just +1, −1, or 0. It's a compressed copy of the open Qwen3.8 27B model, released to Hugging Face as GGUF. Backed by a $22.25M seed from Khosla Ventures and Caltech.

**What's good about it:** Retains 98% of the original model's benchmark performance while shrinking ~9×. The headline claim — "full 27B-class reasoning on a standard laptop or a single GPU" — is the kind of capability shift that changes where inference can physically run. For anyone doing local/offline work, this collapses the hardware requirement from "a real GPU" to "a decent laptop."

**Pros:**
- Order-of-magnitude memory reduction (~54 GB → ~5.9 GB) with only ~2% benchmark loss — an unusually good compression ratio.
- Built on open weights (Qwen3.8 27B), so the lineage is inspectable and the license tail is known.
- Runs on consumer hardware — laptop or single GPU — which makes genuinely offline, air-gapped inference feasible.
- Real backing and a named research team, not a weekend quantization script.
- GGUF format means it plugs into the existing llama.cpp ecosystem tooling rather than a bespoke runtime.

**Cons:**
- Requires PrismML's own llama.cpp build — not drop-in with stock tooling, which adds a maintenance branch.
- Heavy quantization at 27B class historically degrades instruction-following and long-context coherence in ways aggregate benchmarks hide; the 98% figure is benchmark-level, not task-level for our workflows.
- Ternary formats are young — tooling, fine-tuning, and merge support lag behind standard GGUF quants.
- CPU-only inference on a laptop will be slow; "fits" and "is usable interactively" are different claims.
- Needs a genuine evaluation against our actual tasks before any of this matters.

**Should we...**
- 👀 **Watch it** — keep an eye on it, not ready yet but promising

**Why:** This matters to us specifically because of the PHI constraint that governs everything: a model that runs entirely on local hardware with no third-party API in the loop is the only architecture that could ever let us put a capable model near resident data, call-out records, or CRM content. That's a real strategic door. But it's not open yet — the custom llama.cpp requirement, the young format, and the gap between "98% on benchmarks" and "good enough on our actual tasks" all say wait. The right next step is cheap and worth doing when time allows: pull the GGUF on the desktop node, run it against three or four representative internal tasks, and see whether a 5.9 GB model clears our bar. If it does, this becomes the first credible local-model option for the healthcare-adjacent side of the stack.

### Meta "Muse" personal AI agent

**What it is:** Meta's personal AI agent launched September 8, 2026 — a task-executing agent (not a Q&A assistant) that connects to a user's email, calendar, payments, health, shopping, and smart home, then works through multi-step goals semi-autonomously. Available in the US via a dedicated app, muse.ai, and WhatsApp; free tier plus $20/$100 monthly tiers.

**What's good about it:** It's the first mainstream consumer agent that actually *acts* rather than answers — opening browsers, filling forms, and negotiating on the user's behalf with minimal supervision. The breadth of app integration (six categories, including payments and health) is ahead of what OpenAI or Google have shipped to consumers at this scale, and it signals where the whole category is going.

**Pros:**
- Genuinely agentic — plans and executes multi-step real-world tasks rather than returning text.
- Unusually broad integration surface for a v1 consumer product (email, calendar, payments, health, shopping, smart home).
- Distribution advantage — WhatsApp reach means this will be many people's first real agent, which shapes user expectations for all of ours.
- Cheap entry tier, so adoption data will accumulate fast.
- Useful competitive signal: what Meta ships to consumers is a preview of what enterprise tooling will look like in 12–18 months.

**Cons:**
- Not our stack — it's a consumer household agent, not something we'd deploy for department ops.
- Serious privacy posture questions — an agent with payments, health, and email access is the single richest target surface imaginable, and Meta's track record is not reassuring.
- Health-data involvement is a red line for us by policy; any agent that ingests health context is disqualified regardless of convenience.
- Annotation/trust concerns — WSJ is already reporting a "trust problem." A consumer agent that acts on your behalf needs a much higher reliability bar than one that suggests.
- Closed ecosystem with no self-hosting path.

**Should we...**
- ❌ **Skip it** — not relevant, redundant, low quality, or not useful for us

**Why:** Muse is worth *knowing about* and nothing more. It's a consumer product aimed at households — scheduling, shopping, form-filling — and we have no consumer surface that would use it. More pointedly, the categorical strike against it is that it's an agent built to access health and payment data through a third-party consumer platform; the entire reason we've kept our email and data flows inside our own infrastructure is that we don't put resident data through systems like this, and nothing about Muse changes that calculus. Its real value to us is as a category signal: when Meta ships agentic task execution to mainstream consumers, expect the enterprise tools we *do* use to add the same surface, and expect the security and privacy questions Plugin4Shell raises to arrive with them.

### Microsoft Agent Framework 1.0 / GitHub Copilot plugin ecosystem

**What it is:** Microsoft's production-ready agent SDK (1.0) unifying Semantic Kernel and AutoGen into one open-source library for .NET and Python (`pip install agent-framework`), alongside VS Code 1.137's scheduled-agent and spoken-interaction features. Considered here mainly because Microsoft/GitHub Copilot is one of the two agents left unpatched for Plugin4Shell.

**What's good about it:** The 1.0 milestone is real — a single SDK superseding two overlapping frameworks removes a genuine source of confusion, and the C#/Python parity is useful for Microsoft-shop enterprises. VS Code's move toward scheduled agent work mirrors what we already run in Hermes.

**Pros:**
- Consolidates Semantic Kernel + AutoGen into one maintained SDK — less fragmentation than the Microsoft ecosystem had in 2025.
- First-class .NET and Python support with a consistent API surface.
- Backed by a large vendor with a long support horizon.
- VS Code 1.137's scheduled agent work aligns with our own cron-driven automation patterns.

**Cons:**
- Vendor lock-in — the quickstart path routes directly through Azure Foundry (`az login`, project endpoints), so "open source" comes with a cloud gravity well.
- GitHub Copilot, the adjacent Microsoft product, has no Plugin4Shell patch — that's a live security liability in the same product family.
- We have no Microsoft/.NET stack; adopting it would mean adding an entire runtime for no gain over what we run.
- The unification is a consolidation, not a capability leap — nothing here we can't already do.
- Enterprise agent frameworks solve organizational-scale problems we don't have.

**Should we...**
- ❌ **Skip it** — not relevant, redundant, low quality, or not useful for us

**Why:** There's no case for bringing a Microsoft agent SDK into a Hermes-based stack — we'd be trading a working system for a new runtime, a new auth model, and a cloud dependency, in exchange for functionality we already have. The one thing worth extracting from this item isn't the framework at all: it's that the Copilot plugin-share-a-security-hole situation is a reminder to check whether anything anywhere in our tooling chain runs GitHub Copilot as a coding agent. If it does, its marketplace plugins should be treated as untrusted until Microsoft ships a fix.

### kitze/skillbox

**What it is:** A self-hosted, versioned skills library for AI agents — MCP-based, with scoped clients and optional Jev recommendations. TypeScript, MIT licensed, 206 stars, created 2026-09-17 and actively pushed through 09-19.

**What's good about it:** It addresses a problem we hit constantly: skills for agents are currently just files in a directory with no versioning, no scoping, and no distribution story. skillbox gives skills a versioned home, scoped client access (so a skill exposed to one agent isn't automatically exposed to all), and an MCP interface so any MCP-capable agent can consume the library. The self-hosted posture is the important part — it means skills live on our infrastructure, not a vendor's.

**Pros:**
- Self-hosted — no third-party service in the path, which matters given everything else in our stack.
- Versioning for skills is genuinely missing from most agent tooling; this treats skills as artifacts worth versioning.
- Scoped clients — least-privilege skill exposure is the right security model and directly relevant post-Plugin4Shell.
- MCP-native, so it composes with the protocol we already lean on.
- MIT licensed and actively maintained (pushed within the last 24 hours).
- Very new, so the architecture hasn't accumulated legacy decisions yet.

**Cons:**
- Immature — four days old at scan time; no track record, no production users.
- Single-author project with no organizational backing behind it.
- One dependency on Jev/TypeSafe for the optional recommendation path, adding a closed-API vendor into a self-hosted tool.
- Overlaps with how we already manage Hermes skills — adopting means a migration, not an addition.
- Skills-as-artifacts versioning also raises the provenance question: once skills are versioned and shared, you inherit the supply-chain exposure Plugin4Shell demonstrated.

**Should we...**
- 👀 **Watch it** — keep an eye on it, not ready yet but promising

**Why:** This is the closest thing in today's scan to a problem we actually have. Our Hermes skills have grown into a real library — anti-slop gates, the tailscale skill, monster-prompter, copy-desk — and we manage them as loose files with no versioning and no scoping, which is exactly the gap skillbox targets. The self-hosted, MIT-licensed, MCP-native design is the right shape for us, and scoped clients are precisely the mitigation that would have blunted Plugin4Shell's blast radius. But it's four days old with one author; putting our skill library inside it today would be replacing a known-imperfect system with an unknown-fragile one. Watch it for a month or two — if it accumulates contributors and a release or two, it's worth a real evaluation against our current skills layout.

### indada/repopilot

**What it is:** Verification-driven AI software iteration built on the OpenAI Codex SDK. Self-hosted agents turn goals, GitHub Issues, and PR feedback into tested, reviewable changes, with bounded execution and human control over merging and deployment. TypeScript, MIT, 152 stars, created 2026-09-18, pushed today (2026-09-20).

**What's good about it:** The design constraints are the selling point, and they're the right ones: *bounded execution* (the agent has a defined stop condition rather than running until it decides it's done) and *human control over merging and deploying* (the agent proposes, a person approves). "Verification-driven" means changes have to pass tests before they surface as reviewable. This is the architecture that separates an agent you can safely point at a real repo from one you can't.

**Pros:**
- Human-in-the-loop by construction — agents cannot merge or deploy on their own authority.
- Bounded execution limits the blast radius of a runaway or misaligned agent.
- Verification-gated — tested changes only; the agent's output is a PR, not a fait accompli.
- Self-hosted, so no third party sees the repo contents.
- MIT licensed, TypeScript, actively developed (pushed the same day as this scan).
- Consumes GitHub Issues and PR feedback, so it fits an existing review workflow rather than inventing a new one.

**Cons:**
- Built on the OpenAI Codex SDK — inherits that dependency and its update cadence.
- Two days old, 152 stars, no production track record whatsoever.
- "Self-hosted agents" that run against your repo are exactly the trust surface Plugin4Shell just demonstrated is hard to secure; it would need a real security review before touching anything of ours.
- Verification-driven only works if the repo has meaningful tests — on an untested codebase it degrades to a confident diff generator.
- Adds a second agentic coding system alongside the one we already run.

**Should we...**
- 👀 **Watch it** — keep an eye on it, not ready yet but promising

**Why:** The interesting thing about repopilot isn't the code, it's the pattern: bounded execution plus mandatory human approval on merge is the correct shape for agentic coding, and it's worth internalizing regardless of whether we adopt this particular implementation. There's a plausible future where an agent does routine work against our own repos — the arnow-solutions site, the unified platform, the interview portal — and when that happens, the constraints repopilot encodes are the ones we'd want. But it's two days old, it's coupled to the Codex SDK, and pointing a brand-new self-hosted agent at a production repo is precisely the move Plugin4Shell argues against. Watch the architecture mature; borrow the design principles now.

### Matthew0822/ToolReplay

**What it is:** A dependency-free Python CLI for auditing AI agent tool-call transcripts — hash-chain sealing, deterministic replay, and scope-overreach checks. MIT, 180 stars, created 2026-09-14.

**What's good about it:** This is governance infrastructure for agents, which almost nobody is building. Hash-chain sealing means each tool call is cryptographically linked to the previous one, so a transcript can be tamper-evident rather than merely logged. Deterministic replay means you can re-run a recorded session to reproduce what an agent did and why. Scope-overreach checks flag when an agent used a tool or reached for data beyond what its task justified. For anything making consequential decisions, that's the difference between an audit trail and a log file.

**Pros:**
- Hash-chain sealing makes transcripts tamper-evident — a real audit primitive, not just logging.
- Deterministic replay lets you reproduce an agent session exactly, which is what you actually need when something goes wrong at 2am.
- Scope-overreach detection proactively flags an agent exceeding its mandate rather than requiring you to notice after the fact.
- Dependency-free Python CLI — trivially installable, no supply-chain surface of its own.
- MIT licensed and small enough to read end to end before trusting it.

**Cons:**
- Static since creation (2026-09-14, no pushes since) — possibly abandoned or a one-shot release.
- Single-author, no organizational backing.
- Recording and replaying agent tool calls means the transcripts themselves become sensitive data requiring their own handling policy — a governance tool that creates a governance problem.
- Replay fidelity depends on tools being deterministic; anything hitting a live external service won't reproduce exactly.
- Tool-call auditing is only as good as the coverage — an agent that bypasses the instrumentation isn't captured.

**Should we...**
- 👀 **Watch it** — keep an eye on it, not ready yet but promising

**Why:** This is the item whose *category* matters most even if the tool itself doesn't last. Our agents run scheduled, unattended jobs that touch production systems — cron-driven watchdogs, CE pipelines, vault writes, email sends — and right now the record of what an agent did is a text log. When something goes wrong, or when someone asks why a given action was taken, "grep the log" is not an answer with a chain of custody. ToolReplay is an early attempt at the thing that fixes that, and its three primitives are the right three. But it hasn't been touched in six days and has one author, so this is a pattern to watch and eventually build on, not a tool to install. The concrete forward-looking note: any future agent we give write access to production should be emitting sealed, replayable transcripts.

### misbahsy/anti-ai-slop

**What it is:** An agent skill with multiple gates that check for and remove AI slop. Works with Codex, Claude Code, or any AI tool that supports skills. MIT, Python, 71 stars, created 2026-09-14.

**What's good about it:** It's a direct implementation of a discipline we already enforce by hand. The skill runs a series of gates against generated output — the same multi-pass QA posture that Copy Desk uses — but packaged as a reusable, agent-native artifact rather than a set of rules a human has to remember to apply. The "works with any tool that supports skills" portability is the useful part: the same gate stack can run in Codex, Claude Code, or Hermes.

**Pros:**
- Multi-gate rather than single-check — catches slop through successive passes, which is how the problem actually gets solved.
- Portable across agent tools, so one gate definition serves every agent we run.
- Agent-native: encoded as a skill, so it fires automatically rather than depending on the human to remember the checklist.
- Directly applicable to two things we do constantly — generated code and generated copy.
- MIT, Python, readable, no dependencies worth worrying about.
- Low adoption cost: it's a skill, so trying it is cheap and reversible.

**Cons:**
- Static since the day it was created (2026-09-14, no pushes since) — likely a one-shot release.
- 71 stars, single author, no maintenance signal.
- Slop detection is fuzzy by nature; gate definitions will drift from what actually reads as slop over time without stewardship.
- A generic anti-slop skill won't know our brand voices or our per-surface standards (Copy Desk rules, unified-redesign conventions) — it can only enforce the generic layer.
- Risk of false positives that strip legitimate stylistic choices.

**Should we...**
- ✅ **Adopt it** — integrate into our stack (as an evaluation against our existing Copy Desk / CE QA gates)

**Why:** We already run a version of this discipline, which makes this the cheapest useful thing in today's scan: the question isn't whether anti-slop gates are worth having (they demonstrably are — we built our own), it's whether an external, portable, agent-native implementation is better than the ad-hoc one embedded in our prompts. The right move is a contained experiment, not a replacement: run it alongside the existing Copy Desk QA gate and the CE pipeline review on a real piece of output — a landing page rewrite, a brief — and compare what each catches. If the generic skill catches things our house gates miss, fold those gates in. Either way we learn something concrete about our own QA coverage, and the downside is bounded because a skill is trivially removable. One clear caveat: it enforces generic slop standards, not our brand voices — it layers underneath the per-brand rules, never replaces them.

## OVERALL ASSESSMENT

Overall Assessment: Today's dominant signal is security, not capability. Plugin4Shell is the item that actually demands action — a zero-click RCE across the four most-used coding agents, with two vendors still unpatched, and a threat model (malicious plugins reaching agents holding production credentials) that maps onto how our own stack is built. Concretely: verify no Gemini CLI install exists in our tooling, update Claude Code and Codex wherever they run, treat Copilot marketplace plugins as untrusted until Microsoft patches, and do a one-time inventory of every pinned plugin and skill across our agent surfaces. On capability, TypeSafe's Jev is the most interesting thing released this week — a cheap, non-hallucinating decision model that would slot naturally into classification, routing, and agent-oversight jobs — but it's a closed API, so it sits on the watch list until it can run outside a third-party service. PrismML's ternary 27B is quietly the most strategically relevant item for our constraints: 27B-class reasoning in 5.9 GB means a capable model could eventually run entirely locally, which is the only architecture that ever gets near resident data — worth a real evaluation on the desktop node when time allows. Of the three GitHub tools, only anti-ai-slop justifies immediate (and cheap, reversible) adoption as an experiment against our existing QA gates; skillbox and ToolReplay are worth watching specifically because they're precursors of infrastructure we'll need — versioned, scoped skill distribution, and tamper-evident agent audit trails. Microsoft's Agent Framework and Meta's Muse are both skips, for different reasons: one is a lock-in we have no use for, the other a consumer product whose health-and-payments data access disqualifies it categorically. No item today warrants an architectural change; one warrants a patch, and several warrant a calendar reminder.
