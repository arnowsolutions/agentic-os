### 1. shoulder — see what your agents are actually doing, live, without any account

**What it is:** A single-binary Go TUI (MIT, v0.3.0 released today) that follows Claude Code, Codex, Gemini CLI, opencode and omp through a project and shows, per agent: the file it is reading or editing right now, an inline diff against your last commit, the shell commands it ran and their output, an activity log with history stepping, and a context-window fill bar. It works by *reading the session logs those agents already write to disk* — `~/.claude/projects/`, `~/.codex/sessions/`, `~/.gemini/tmp/`, `~/.local/share/opencode/opencode.db`, `~/.omp/agent/sessions/`. No configuration, no plugin, no network.

**Source:** https://github.com/bjarneo/shoulder · site: https://bjarneo.github.io/shoulder/ · Provenance: GitHub Search API scan (created Oct 27, pushed today) — not seen in any of the eight tracked channels.

**What's good about it:** The design decision that makes it adoptable is the data source. It reads what is already on disk, which means **zero credentials and zero network** — the README states plainly that it "only reads. It does not send input to an agent, it does not change files, and it does not connect to the network. It opens the opencode database read-only." That is the inverse of every other agent-dashboard tool that wants an OAuth login. It also has a `status` subcommand that prints one line for a status bar, which is the shape a watchdog wants; and the "while you were away" line (`A1 claude edited 3 files · A2 codex asks you`) is the summary you actually want when you return to a terminal after lunch.

I installed and ran it rather than trusting the README: `go install github.com/bjarneo/shoulder@latest` → **shoulder v0.3.0** (`gopath/bin/shoulder`, 17 MB, go1.26 toolchain per `go.mod`), `--help` prints the documented flag set, and `shoulder status /workspace` **exited 0 with one blank line** — correct and honest, because there are no Claude Code or Codex sessions on this host, so there is nothing to report. The TUI itself exits with `bubbletea: error opening TTY` in this cron context, which is expected: it is a full-screen terminal app. The repo also has a real test file (`status_test.go`, `go test ./...`) and a `flake.nix`.

**Pros:**
- **No credentials, no network, no config.** It reads session logs that agents write anyway. That single property is what makes it safe to run inside the same trust boundary as Hermes, where a browser-login tool would not be.
- **Diff against HEAD, per agent.** Two agents editing the same project show as two live cursors with separate diffs — the thing you cannot get from `git diff` after the fact, and the exact gap that made the September comment-deletion incident invisible.
- **Real engineering signals:** one author, but 3 releases in 2 days with a changelog, tests, CI workflow, checksums on release artifacts, Nix flake, and *eight* stars-to-forks ratio evidence in neither direction — 60 stars / 4 forks / 1 watcher, which reads like a genuine small tool rather than promoted.
- **Shell-edit detection.** It catches files changed by `sed -i` or a script an agent ran, not just edits through the edit tool — this is the half of "what did the agent change" that hides.
- **Steppable history** (`,` / `.`) that rewinds the activity log, plus an editor hand-off (`e` → `nvim`, VS Code, Cursor).
- **`status` mode** for a status bar — the only piece that survives a non-interactive environment.

**Cons:**
- **It only knows about the four other agents, not Hermes.** Our daily briefs, watchdogs and vault jobs are Hermes cron scripts; they write no Claude Code session log, so shoulder would show an empty screen for the work we actually care about most. What it can see today is only whatever Claude Code / Codex sessions happen to run on the machine.
- **It is a terminal UI that needs a TTY.** Verified here: it refuses to start without `/dev/tty`. So the interactive half lives on the desktop, not in a VPS cron job.
- **Three days old, one author, no issues yet.** The engineering is real but the project has no track record; a breaking change next week costs us nothing because it is a read-only observer, which is why adopt is safe here — but do not build anything on top of its output format.
- **Approval state is an estimate** for Claude Code, Codex, opencode and omp (its own Limits section says so), so "agent asks you" is an inference from log shape, not a fact.
- **opencode 1.x is unsupported** — only 2.x, and the DB is opened read-only.

**Should we...**
- ✅ **Adopt it**

**Impact on our stack:** Medium-High — agent observability on the desktop and any machine running coding agents. Concrete change: when a coding agent is working in `/workspace/unified` or `agentic-os`, shoulder is the second window that shows the file and diff live, so a wrong edit is caught while it happens rather than in a post-mortem.

**Why:** Our entire failure history this year is the same shape — an agent said it did something, and we found out later from its effects. The vault-401 we worked around silently, the email skip in September, the comment file that went missing: every one of those would have been visible in a live view of *which file the agent had open and what it had just changed*. shoulder is a small, honest, zero-credential version of that view, and — rare in this category — it installs, builds and runs cleanly in two minutes on the very machine we would run it on. The adoption is deliberately narrow: install the binary on the desktop (`go install` or the linux-amd64 tarball) and run it in a side terminal whenever a coding agent is touching Unified or agentic-os. Do not wire it into cron and do not depend on its output format; it is a window, not a service. If it proves useful in a week, the next step is a small wrapper that polls `shoulder status` and appends one line per agent session to the daily brief's provenance — that is the piece of its data that survives without a TTY.

### 2. cvENGINE — which of this week's exploited CVEs are actually live on our domains

**What it is:** A GPL-3.0 self-hosted Django 5.2 + PostgreSQL 18 application (a fork of the reNgine 2.x attack-surface scanner) that discovers and maps your internet-facing assets — subdomains, IPs, ports, products, versions, TLS, technologies — then matches them against the live `cve.now` feed and the major exploitation sources, rates each CVE **fire / smoke / ice**, and runs safe read-only checks to reproduce what it can. AI triages findings, but fixed rules stop the model from waving away hard evidence, and every check records exactly what it ran. It also ships a REST API and MCP tools so an agent can query the asset graph.

**Source:** https://github.com/hevnsnt/CVEngine · docs: https://github.com/hevnsnt/CVEngine/tree/master/docs · Provenance: GitHub Search API scan (`topic:ai` created since Oct 21, 450 stars) — not from any tracked channel.

**What's good about it:** It answers a question our stack currently cannot answer at all. We run several public services — `unified.srv…hstgr.cloud`, `schedule.srv…`, `interview.srv…`, `vault.srv…`, `qgenda.srv…` (redirect), plus the Hermes gateway — and nobody knows, on any given morning, whether a service in that list is running a version with a CVE that is being exploited this week. cvENGINE turns that into one screen: assets, versions, and the CVEs that actually match, ranked by whether they are being exploited in the wild. The three-signal loop (surface discovery + vulnerability matching + exploit feed, in one continuous pass) is the right architecture, and the fixed-rule guardrail around the AI triage is the correct way to stop an LLM from dismissing a real finding.

The signal quality is also unusual for a repo this new: **450 stars, 16 forks, 2 releases, GPL-3.0 declared in both the sidebar and the badge**, an explicit list of what it is built *on* (reNgine 2.x, GPL-3.0, with third-party attribution in `THIRD-PARTY.md`), and 287 commits by a single author. That is a serious piece of software from one person rather than a star-farmed demo. It runs as its own Docker Compose stack with an `install.sh`, so it does not touch Hermes or the Unified stack.

**Cons:**
- **One author, five days old, zero external contributors.** 16 forks with no PRs merged is exactly the profile the honesty rule says to distrust — the difference here is that it is a *fork of a mature GPL project* (reNgine), so most of the code has years of history behind it, and the license is unambiguous.
- **GPL-3.0.** Fine for our own internal self-hosted use; it does mean we cannot lift code from it into the closed parts of the Unified Platform.
- **It scans the public internet from wherever it runs.** On a VPS this is the visible-scanning behaviour that can get an IP on abuse lists if pointed at anything outside our own domains. Must be scoped to our own hostnames and nothing else.
- **Resource-hungry stack:** PostgreSQL 18 + Django + nginx + the scan engine, on a VPS that already runs Supabase self-hosted, Hermes and several containers. Disk and RAM are the real constraint, not the app.
- **Python 3.14 + Postgres 18** are both very new targets; the compose file pins them, so it will work, but we already know how a container-layer install disappears on `docker recreate` (memory: `/app/venv` is a layer, not a volume). This one is volume-based by design, but the lesson is to check before trusting persistence.
- **The `cve.now` feed is its own dependency.** If that service goes dark the "which CVEs are live" half loses its ranking.

**Should we...**
- ✅ **Adopt it**

**Impact on our stack:** High — external attack-surface visibility for Unified, schedule, interview, vault and the Hermes gateway. Concrete change: one weekly cron pass that reads cvENGINE's API for hostnames we own and appends "new fire-rated CVE on <host>: <CVE>" to the existing health-watchdog notification path.

**Why:** We run five public hostnames off one VPS and we have never had a version inventory of any of them. The July Montefiore IT incident showed what happens when we discover our own exposure late — that time it was an agent's login, next time it could be a service version, and we would learn about it from a third party. cvENGINE is the only thing in today's scan that changes that, and it does it without a cloud account, without an API key, and without touching the Hermes runtime — its own Docker stack, its own database, read-only checks against our own domains. The adoption should be staged: deploy it on the VPS with the compose file, point it at *only* the `srv1738752.hstgr.cloud` hostnames, let discovery finish once, and read the first report before wiring anything to the API. If the fire/smoke/ice ranking on our own inventory is noise, drop it; if it names even one outdated service we did not know we were running, it is the best value of the day. Budget the disk first — the scan engine's stack is the largest thing we would add this month.

### 3. agentloop — the agent loop, in Go, with the guardrails we keep rebuilding

**What it is:** An MIT Go library (Go 1.21+) that implements the whole tool-calling loop — prompt the model, dispatch the tool calls it asks for, append results, repeat until a final answer — plus the things around it: per-run tool budgets, inference ceilings, duplicate-call loop detection, stream watchdogs, hooks at every step, on-demand skill folders with progressive disclosure, and a complete trace (every tool execution with output and duration, full transcript, token/cost usage). It sits on the author's `llmhub` for provider access (OpenAI, Anthropic, Gemini, Ollama, xAI, OpenRouter, Z.AI), compiles to a single static binary with `CGO_ENABLED=0`, and runs in about 7 MB of RAM.

**Source:** https://github.com/smhanov/agentloop · pkg: https://pkg.go.dev/github.com/smhanov/agentloop · Provenance: GitHub Search API scan (`llm tool` created since Oct 23) — not from any tracked channel.

**What's good about it:** The engineering discipline is the best of anything in today's scan and it is verifiable. I installed Go 1.24.5 in this container, `go get`'d the module, wrote a program that imports it, and it linked and ran: `agentloop.Hooks` comes back as a ten-slot struct (`OnStart, BeforeGenerate, RebuildContext, AfterGenerate, BeforeToolCall, AfterToolCall, OnDelta, OnDone, OnError`), and `agentloop.ToolResult` returns `{Name, ID, Args, Output, Err, Duration}`. Then I ran the repo's own suite inside the module cache: **the core package passes in 0.2s** (`ok github.com/smhanov/agentloop 0.213s`), as do `examples/ask` and `search`. The test names read like a specification of every agent-loop bug we have ever hit: `TestAskBudgetForcesFinalNotice`, `TestAskDupCallWarningThenStop`, `TestAskCtxCancelMidTool`, `TestAskMaxStepsExhausted`, `TestAskStreamWatchdogStale`, `TestAskUsageSummation`.

Two policy tests are unusual and worth naming: an **exported-API budget** test that fails when the public surface grows past a fixed ceiling, and a **repo hygiene** test that fails if the repository stops being domain-neutral. A library that tests itself for scope creep is a library that will still compile in a year.

**Pros:**
- **Bounded by default.** Tool-call budgets, inference ceilings, duplicate-call detection, stream watchdogs and `context.Context` — the loop "can never spin forever". Our cron jobs currently rely on `timeout` and hope.
- **One dependency** (`llmhub`), static binary, 7 MB RAM, no Python/Node sidecar. That is the opposite of the pip-in-a-container-layer traps we have been burned by twice.
- **Skills with progressive disclosure** through a jailed read tool — the same architectural idea as the Hermes skill system, but written as library primitives.
- **Trace comes back with the answer** rather than being something you add later. Every `Ask` returns full tool output and durations, which is the exact artifact our brief's provenance rule keeps asking for.
- **Honest about pre-v1:** semantic versioning statement in the README, stable module path, and a caveat about minor-version breakage while pre-v1.
- **Verified, not claimed:** core suite green here, in this container, offline.

**Cons:**
- **One failing test in the repo as shipped.** `TestLocalEnvironmentTimeoutKillsProcessGroup` in the `bash` preset fails here: *"process group … still has live members after the timeout kill"* — the sandboxed shell does not reliably kill an entire process group on timeout in this container. That is a real bug in the piece we would care about most (running shell commands safely), not a flake.
- **One author, four days old, 0 watchers, pre-v1.** The code quality is high but there is no community standing behind it; the correct posture is watch.
- **It is a library for writing an agent, and we already have one.** Hermes owns our loop, tools, skills and cron. Nothing in agentloop can be bolted onto Hermes today — the value is only if we deliberately write a *new* small agent (a health-check prober, a vault verifier) as a native Go binary.
- **Requires Go on the machine.** No Go toolchain existed here; I installed it in `/tmp` for the test. Any real use means either a Go build step on the VPS or shipping binaries.
- **Skills and search presets need extra services** (a skill folder layout we do not share; `serper.dev` for the search preset; an LLM provider key for anything real).

**Should we...**
- 👀 **Watch it**

**Impact on our stack:** Medium — a possible native replacement for one or two long-lived cron scripts (health watchdog, vault verifier) if we ever want them to be single binaries with bounded loops instead of Python scripts under `timeout`.

**Why:** Today's install test was worth doing because it separates the two Go projects in this brief: shoulder built and ran clean, agentloop built and ran clean *with one real failure in its sandboxed-shell preset*. The library's architecture is a better match to our failure modes than most of what we look at — bounded runs, hooks for approval gates, traces returned rather than logged — but the honest comparison is against Hermes itself, which already provides the loop, the skills and the scheduler. Writing a new agent in Go to replace a 60-line Python watchdog is not obviously an improvement, and adopting a four-day-old pre-v1 library with a failing isolation test as the base for anything we depend on would be exactly the mistake the verdict rules were written to prevent. So: revisit in a month, when there are external contributors and the process-group fix has landed. If the watchdog idea survives until then, port the vault verifier first — it is the smallest job with the clearest definition of "done".

### 4. grim-prompter — threat modelling as an agent skill, with citations required

**What it is:** An MIT skill (prompts plus a runbook, no runtime) that points a coding agent — Claude Code, Codex, or anything that reads `AGENTS.md` — at a repository and walks it through a structured threat-model review: 36 architecture workflows and 29 method/analysis prompts (STRIDE, LINDDUN, PASTA, CAPEC and friends), producing `SYSTEM_UNDER_REVIEW.md` (scope, evidence, assumptions, gaps), `report.md` (findings, mitigations, verification plans) and JSON artifacts for later change reviews. The runbook requires **read-only inspection with file-and-line citations**, and builds/tests/installs/network access need explicit authorization.

**Source:** https://github.com/jmanico/grim-prompter · runbook: https://github.com/jmanico/grim-prompter/blob/main/runbook.md · Provenance: GitHub Search API scan (created Oct 28, 95 stars) — not from any tracked channel.

**What's good about it:** It is the only new thing today shaped like our actual work inside Hermes: a **skill folder** with markdown prompts, installed by symlinking into `~/.claude/skills` or adding a section to `AGENTS.md` — the same shape as the skills we already run. There is no server, no daemon, no account. The author is Jim Manico (a well-known application-security educator), which is a real name behind a real method rather than an anonymous star-farmed repo — and the content is written by someone who has actually done the reviews.

The design detail that matters for us: it reviews MCP servers and agent tools by mapping each tool to its backend credentials and effective permissions, and explicitly records unknown grants as gaps. Plus a change-review mode (`/threat-model change main...feature` against a saved JSON baseline) which is what you want for "we just deployed a new route to Unified — what did that open?"

**Pros:**
- Non-invasive by construction: markdown prompts only, and the runbook forbids builds, installs and network access without authorization.
- Evidence-traced output with file-and-line citations, and an explicit instruction that the agent "should not invent ratings or approvals".
- Both a quick mode and a six-stage deep mode with stage handoffs and change reviews against a baseline.
- Works with any agent that reads `AGENTS.md` — so it drops into Hermes' skill system without a Claude Code dependency.
- Credential-boundary review is purpose-built for MCP/agent tools, i.e. exactly what our Unified Platform's agent-facing endpoints are.

**Cons:**
- **One day old, one author, 9 forks, 0 issues, no licence file ambiguity but also no track record** — 95 stars in 24 hours is a promotion curve, not adoption.
- **Never run against our stack.** The prompts are drafts by the author's own admission ("These prompts are drafts… a threat model does not certify that a system is secure"), and the quality of the output depends entirely on which model executes them — a weak model will produce a plausible-looking threat model that cites nothing real.
- **Running it already needs an agent with repo read access**, so on any repo holding Montefiore configuration (Gmail OAuth client, Supabase service-role key, CRM connection strings) the review itself is the exposure — the output must be kept out of version control, which the README says but cannot enforce.
- **The value is concentrated in the deep mode**, which is a long multi-stage run against a real repository — hours of model time per repo, not a lunch-break task.

**Should we...**
- 👀 **Watch it**

**Impact on our stack:** Medium — a security review of the Unified Platform's agent-facing endpoints and the Hermes skills that hold credentials, done once, offline, with citations.

**Why:** The right question for grim-prompter is not "is it good" but "what could we safely point it at". Our repos contain real credentials and healthcare data paths, and this skill asks an agent to read the code and write a report about how it could be attacked — useful, but not something to run on Monday because it trended. The skill shape is a genuine fit (a folder of markdown, `AGENTS.md`-compatible, no runtime), the author is credible, and the credential-boundary analysis is aimed at exactly the MCP surface we are building. But it is a one-day-old prompt library whose output quality is untested here, and the first real use has to be on a repo we can talk about and clean up afterwards. Concretely: clone it, read the runbook and the `reference/tool-credential-boundaries.md` page, and let one deep run loose on a scratch clone of Unifed's agent routes with no `.env` present — not on the live tree. If the citations hold up, it becomes a quarterly check; if the report is citation-free prose, it goes in the bin.

### 5. OmniRoute — one endpoint for 350 providers, and a headline number its own docs contradict

**What it is:** A large MIT self-hosted gateway (TypeScript, ~82k stars, 12k forks, created February 2026, now under the `cheaper-inference` org after a transfer from `diegosouzapw`) that puts ~350 providers behind one OpenAI-compatible endpoint at `localhost:20128/v1`, with 19 routing strategies, quota-aware auto-fallback across four tiers (subscription → API key → cheap → free), context "compression" engines, a built-in MCP server, an A2A server, memory, guardrails and a dashboard. It is positioned as "never hit a usage limit" for Claude Code, Codex, Cursor, Cline and 30-odd other clients.

**Source:** https://github.com/cheaper-inference/OmniRoute · site: https://omniroute.online · Provenance: spotted on Hyperautomation Labs — https://www.youtube.com/watch?v=5nawzIeuNJY (the video's "run Claude Code for free" walkthrough) and https://www.youtube.com/watch?v=v5Dv0cFuJ0w

**What's good about it:** As an engineering artifact it is substantial and current: 282 releases, a release branch, a CI-gated docs count, a self-hosted Docker image, and a genuinely useful idea — when a provider is rate-limited, transparently move to the next healthy one instead of stopping. The routing transparency (`X-OmniRoute-Decision` header naming strategy, provider and latency for every response) is better instrumentation than most paid gateways offer, and the free-tier accounting is unusual for trying to be honest at all.

**Pros:**
- One config line replaces per-client provider setup for a dozen CLIs.
- Circuit breakers, credential encryption, semantic cache and a decisions header that tells you *who actually answered* — the question the source video itself spends a chapter on.
- Docker-deployable and OpenAI-compatible, so it is technically easy to stand up.
- Actively maintained (pushed today, 282 releases).

**Cons:**
- **The headline contradicts its own reference doc.** The README marketing says "~1.53B / 1.62B free tokens per month"; `docs/reference/FREE_TIERS.md` (v3.8.50) says the honest headline is **~1.62B "documented recurring grant" but that "actual usable capacity can be lower, including zero on a fresh installation with no eligible route"**, that figures "move both ways", that one provider was reclassified from 150M recurring to a 10M one-time credit, and that **12–15 providers are marked `tos: avoid`** because their terms forbid this use. The README's number is a marketing artifact; the doc wins.
- **The free-Claude path is exactly what got us flagged in July.** The zero-cost tiers work by borrowing a *subscription OAuth session* (Claude Code Pro, Gemini CLI, GitHub Copilot) or a *web cookie* (35 providers listed as "Web cookie": ChatGPT, Claude Web, Gemini Web, Grok Web). Connecting those on a datacenter IP is the same pattern as the Montefiore IT incident — real account credentials on a VPS.
- **AGPL/GPL-adjacent provenance risk in its own history:** the README credits a fork chain (9router → CLIProxyAPI) and notes that a provider was excluded "while its GPL-derived provenance/licensing remains on HOLD" — a project that self-reports licensing uncertainty about a shipped provider is not a dependency to build on.
- **Absurd surface area for our need.** 110 MCP tools, 33 scopes, A2A, memory, guardrails, gamification with leaderboards, Obsidian integration, a Telegram bot bridge. We need none of it.
- **The `omniroute.online` site and the GitHub README disagree on every number** (290 vs 352 vs 375 providers; 18 vs 19 vs 20 strategies), which is the clearest sign the marketing is generated faster than the product is counted.

**Should we...**
- ❌ **Skip it**

**Impact on our stack:** Low — the only durable idea worth keeping is quota-aware fallback between *paid* providers.

### 6. RAD Debugger — Epic's open-source native debugger

**What it is:** Epic Games' MIT-licensed native, user-mode, multi-process graphical debugger for x64 applications on Windows and (early) Linux, in alpha, with its own debug-info format (RDI), a fast linker (RAD Linker) for huge PE/COFF binaries, and 30 releases since January 2024. Written in C.

**Source:** https://github.com/EpicGames/raddebugger · Provenance: spotted on The Next New Thing — https://www.youtube.com/shorts/mzLkzIF1Te8

**What's good about it:** Real, mature, MIT, 8.6k stars, pushed today, and an actual Epic Games project rather than a wrapper — 30 releases over two years is a track record. The RAD Linker's 50% faster link times on multi-gigabyte debug info is a genuine engineering result. For anyone shipping native C/C++ games, this is the correct tool.

**Pros:**
- MIT licensed, Epic-backed, two years of releases.
- Purpose-built for huge binaries where PDBs overflow 32-bit tables.
- Its own RDI format converts from PDB/DWARF, so it is not tied to MSVC.
- Actively developed (pushed today).

**Cons:**
- **It debugs native C/C++ x64 binaries.** Our stack is Python, TypeScript/React, PostgreSQL, Docker — there is nothing for it to attach to.

**Should we...**
- ❌ **Skip it**

**Impact on our stack:** Low — no native code in Unified, agentic-os, Hermes or the voice/email pipelines.

**Why:** This is good software aimed at a world we do not live in. Our bugs are Python tracebacks, React state, bad SQL and cron scripts that silently exit — none of which a native x64 debugger can see. The occasional macOS-only or Windows-only helper we run is not worth standing up an alpha debugger for. Filed only so the feed does not suggest it again.

### 9. farol — merge-risk scoring for the pull request someone has to approve

**What it is:** An MIT CLI and GitHub Action (Node 22+, TypeScript/Go/Python support) that runs *after* an AI code review and tells the approver how risky a merge is: a 0–100 score and a verdict (fast track / quick review / careful review) built from reach (what the changed code touches, with call chains), diff coverage, security findings, contract breaks and dependency changes — plus the riskiest files first with untested lines marked. It works from static analysis, never executes your code, never sends it anywhere, and never blocks a merge.

**Source:** https://github.com/winnin/farol · site: https://winnin.github.io/farol/ · Provenance: Hacker News Show HN (Oct 25)

**What's good about it:** The framing is the best sentence in any README I read today: "Agents write the code and agents review it. The last call is still a person's: approve the merge or not. That approval is the scarce part, and spread evenly over every pull request it turns into a skim." Review effort following change risk is exactly right, and doing it with static analysis instead of a model means the same PR always gets the same answer.

**Pros:**
- Deterministic (compiler-derived reachability, not a model guess).
- Local-first: no account, no hosted service, runs in CI or on your machine.
- Shadow mode never blocks a merge — safe to turn on anywhere.
- Works on TS/React, Go and Python, which covers most of our repos.

**Cons:**
- **Effectively unadopted.** 3 stars on the page, one contributor (`erich-oliveira-winnin`, 23 commits), one week old, last push Oct 26 — against a reported 160 stars, i.e. the star number does not match observed interest.
- **We do not have a PR-review bottleneck.** Unified changes are deployed by me and reviewed by Shareef at the browser level, not through PR gates.
- The reach analysis is strongest for route-based webapps and weakest exactly where our risk lives (Python cron scripts, SQL migrations).
- The Action comments on every PR, which is noise if nobody is reading PRs.

**Should we...**
- ❌ **Skip it**

**Impact on our stack:** Low — no PR workflow to attach it to.

**Why:** The principle is right and I would copy it: review effort should follow risk, not be spread evenly. But we do not run a merge-approval process, so a tool whose entire value is making that approval smarter has nothing to make smarter here. If Unified ever moves to a PR-gated deploy, farol is a ten-minute add and worth revisiting then. Filed as rejected so it does not come back tomorrow with a different headline.
