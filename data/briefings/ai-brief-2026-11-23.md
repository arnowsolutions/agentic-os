### agentic-attack-detections

**What it is:** An MIT-licensed repository of detection rules, hunting queries and indicators for agentic attack frameworks — the tools that hand an intrusion to an AI agent. Eleven frameworks are covered by folder (ARTEX, Cairn, PentAGI, HexStrike, CyberStrikeAI, Strix, Hermes Agent, Agent Zero, RedAmon, Xalgorix, Pentest Swarm AI), in KQL for Sentinel/Defender XDR, Sigma, Suricata, Zeek, YARA, STIX 2.1 and WAF rules for Cloudflare/AWS/Azure, plus one CSV of 572 sourced indicators.

**Source:** https://github.com/ThreatDefence/agentic-attack-detections · Hermes folder: https://github.com/ThreatDefence/agentic-attack-detections/tree/main/frameworks/hermes · Provenance: GitHub new-repo scan (created 2026-11-20, 481★, MIT, 5 open issues), direct follow-up to yesterday's MONAI Label / Cairn item.

**What's good about it:** There is a folder named after the software this brief runs on. `frameworks/hermes` reviews Hermes Agent at commit `7c34e2db` and documents what changes when it is used as an attack console: approvals off (`hermes --yolo`, `HERMES_YOLO_MODE`, `approvals.mode: off`), the bundled godmode skill installed to `~/.hermes/skills/security/godmode/`, `~/.hermes/SOUL.md` replaced with a "Red Team Operator" or GH0ST persona, loot written to `/root/.hermes/loot/`, control over the Telegram gateway, and exposed consoles on the WebUI (8878, `Server: HermesWebUI`) and dashboard (9119). It reports 75 indicators, 4 KQL hunts, 2 scheduled analytics rules, 3 Sigma rules, 7 Suricata rules and 4 YARA rules for that one framework, and cites the four campaigns that used it: Unit 42's knaithe/KnYuan actor against 460+ targets, Hunt.io on Thailand's Ministry of Finance, Gambit on retail card theft, ThreatDown on the Carbonato Docker botnet.

**Pros:**
- It names our harness with a pinned commit and file-level references, so the checks are concrete rather than generic.
- I ran the obvious ones against this box: `approvals.cron_mode: deny` (no `mode: off`), no godmode skill in `~/.hermes/skills`, no `prefill.json`, no `loot/`, and nothing listening on 8878 or 9119. Clean on every check but one.
- The one exception is real: `/app/hermes-agent-src/optional-skills/security/godmode` exists inside the image. The payload is present, one `install` away, on a box that runs unattended crons.
- YARA rules were tested against the Hermes source plus seven other agent codebases, and the repo has a validating CI workflow.
- MIT, 572 indicators in one CSV, STIX 2.1 export, and a one-minute Suricata test with a sample pcap so the rules can be proven before they are trusted.

**Cons:**
- Status is explicitly *Experimental* — "tested for syntax and conversion", with instructions to baseline before alerting. That is honest, and it means none of this is turnkey.
- Three days old, one publisher, 5 open issues. The IOCs are the durable part; the rules are a first draft.
- It is built for Sentinel, Defender, Suricata and Zeek. We run none of those. The usable pieces for us are the YARA files, the indicator CSV and the checklist — not the platform integration.
- The Hermes rules describe a laptop or a bare server with a home folder. We run in a container with a mounted `/workspace`, so path-based rules need translation.
- No medical or PHI-specific detections; the compromise of a department agent would look like data access, not like a Kali toolchain.

**Should we...**
- ✅ **Adopt it** — not as a SIEM deployment, as a one-hour self-audit plus a YARA pass on the image.

**Impact on our stack:** High — Hermes itself, which is the thing every cron, the gateway and the vault all run through. The concrete change: convert the six checks above into a script that runs at container start and alerts on drift (approvals mode, godmode skill present, SOUL.md hash changed, new listeners, a `loot/` directory), and run the Hermes YARA rules against `/app` after each rebuild. That is the first monitoring we would have on our own agent's tamper surface.

**Why:** Every previous security item in this brief was about something we expose to the internet. This one is about the thing doing the exposing. Hermes is a great target precisely because it is legitimate: it has a terminal tool, a skills system it can write itself, persistent memory, a persona file and a Telegram gateway, and every one of those is a control surface if approvals are off or the persona is replaced. Attackers are not exploiting a bug; they are using the features. We cannot patch that away, but we can detect the six-state change that turns our assistant into their console — and we can do it in an hour with files that already exist. The godmode directory sitting in the image is the part I would not leave unaddressed: an attacker does not need to bring a payload, only to install the one we shipped.

### skillshare

**What it is:** A single Go binary (plus a desktop app) that keeps one source directory — `~/.config/skillshare/skills/`, `/agents/`, `/extras/` — and syncs it into every AI coding tool by symlink or copy. It handles skills, custom agents, rules/commands, MCP connections and hooks, has a built-in security audit that runs on install and update, a web dashboard (`skillshare ui`), project-scoped skills committed with a repo, and install straight from any Git host.

**Source:** https://github.com/runkids/skillshare · docs https://skillshare.runkids.cc · Provenance: spotted on Hyperautomation Labs — https://www.youtube.com/watch?v=czifor5lk8I (item 8)

**What's good about it:** It solves the problem we have been solving with ad-hoc copies. One source directory becomes the truth, and every harness gets a symlink — Claude Code, Codex, Pi, OpenCode, OpenClaw, Copilot, VS Code, Antigravity — with `--mode copy` as the escape hatch when symlinks break. `skillshare sync --all` pushes skills, agents, extras, MCP and hooks together, and `skillshare sync mcp --dry-run` previews config changes before applying them, which is the only reason I would consider letting a tool edit live MCP config on this box. The audit step ("scan before skills reach your agent") is the feature I did not expect from a sync tool, and it is the one that matters for us, because half our skills came from repos reviewed in this brief.

**Pros:**
- No runtime dependency — one Go binary, no Node/npm, which is exactly the class of tool that survives a `docker recreate`.
- Git-versioned source and a documented "team onboarding" recipe: a shared `.skillshare/` in a repo, one install command, everyone's harness configured. That maps onto our split between the ops repo and the design surfaces.
- `audit` runs on install and update, so a compromised skill repo is caught at the door rather than after a cron uses it.
- `sync mcp --dry-run` makes MCP changes reviewable — this is the difference between a useful tool and a tool that breaks a working stack at 3am.
- Actively maintained: v0.30.11, pushed today, 3,299★ and 387 forks since January, MIT.

**Cons:**
- **Hermes is not a target.** The supported list is Claude Code, Codex, Pi, OpenCode, OpenClaw, Copilot, VS Code, Antigravity. Our skills live in `~/.hermes/skills`, so either we wait for a target, keep a symlink farm by hand, or invert the model and make the Hermes directory the source.
- The formats are not identical: a Claude Code plugin carries a marketplace manifest and commands; a Hermes skill is a `SKILL.md` with different frontmatter. A sync tool moves files, it does not translate semantics.
- It wants to own `~/.config/skillshare` and rewrite per-tool config for MCP and hooks. On a production box that is a blast-radius decision, not a convenience.
- 145 MB repo and a desktop app that assumes a human in front of it; the CLI is the part we would use.
- The audit is pattern-based, so it catches known-bad skill content, not a skill that is merely wrong for us.

**Should we...**
- 👀 **Watch it** — pilot on a copy of the skills tree, not the live one.

**Impact on our stack:** High — Hermes skills, and every other harness we touch. 662 skills exist in one tool's directory; the moment we run the same task in Claude Code or Codex, the knowledge forks. A canonical directory with symlinks would make "the skill" a single object again, with an audit log of what entered it.

**Why:** The expensive failure is not a missing skill, it is two copies of a skill that disagree — the one I edited in Hermes and the one Claude Code still has from March. skillshare is the first tool I have seen that treats skills, agents, MCP and hooks as one portable unit with an audit gate, and it does it in a static binary, which means it will not evaporate on the next container rebuild. The reason it is a watch rather than an adopt is narrow and technical: no Hermes target. The pilot is cheap — point a `--mode copy` target at a scratch directory, sync a dozen skills, and see whether the copy model breaks any of the frontmatter Hermes depends on. If it holds, we invert the source and make `~/.hermes/skills` the master; if it does not, we have learned why in an afternoon.

### Univer

**What it is:** An Office SDK for embedding spreadsheet, document, presentation, table, canvas and PDF capability inside your own product, in three parts: a Web SDK (content models, editing, rendering, formula engine, Facade APIs, headless processing without an editor), a Server SDK (real-time collaboration, edit history, Office file import/export), and an AI SDK that connects Office content to agents.

**Source:** https://github.com/dream-num/univer · docs https://docs.univer.ai · Provenance: spotted on Hyperautomation Labs — https://www.youtube.com/watch?v=czifor5lk8I (item 6)

**What's good about it:** The architecture is the right one for us. The Facade API is an application-facing interface to workbooks, worksheets and ranges, with events — so a React page can render a sheet and our FastAPI backend can populate it, recalculate it and read the result without a file round-trip. Headless mode reuses the same content models and formula engine with no editor mounted, which is what a cron needs: take the reimbursement workbook, write the rows, recompute, export. The plugin/preset composition means we can mount Sheets only and skip Docs and Slides. It is four years old, Apache-2.0, TypeScript, 31.4k stars and 2,847 forks — old enough to have survived its own rewrite, which is more than most things in this brief.

**Pros:**
- Facade API plus headless mode covers both audiences: a human editing a schedule in the browser and a job filling the same sheet at 6am.
- Formula and calculation engines are in the open-source core, so the numbers are the library's job, not ours.
- Plugin composition lets us ship Sheets alone — no Docs/Slides surface to secure or maintain.
- Apache-2.0 core, TypeScript, mature project with a documented headless guide for Node.
- Replaces a real gap: today the Unified Platform generates files and the editing happens in Excel, outside the system.

**Cons:**
- **The README contradicts the video's framing.** This repo is the Web SDK's core; "Commercial Web SDK plugins, Server SDK, and commercial AI SDK extensions are distributed and licensed separately" — and Office file import/export lives in the Server SDK. So the free tier renders and calculates; reading and writing the `.xlsx` files we already produce is the paid path.
- 180 MB repository, 207 open issues, and an editor integration into React is a months-scale project, not a sprint.
- Docs quality lags the surface area; the headless path is documented but thin compared to the browser path.
- Two commercial boundaries inside one product (plugins and server) means our cost model depends on a vendor's tiering that can change.
- It is a UI framework: adopting it means owning a new editing surface in the Unified Platform, with its own auth, save semantics and failure modes.

**Should we...**
- 👀 **Watch it** — scope one read-only surface before committing to the SDK.

**Impact on our stack:** High — Unified Platform, and specifically the reimbursement workbook and the schedule. The concrete change would be an in-browser sheet with our data already in it, instead of a generated file the user downloads, edits and re-uploads.

**Why:** The reimbursement flow is the highest-friction corner of our stack because it crosses a file boundary: we compute rows, emit a workbook, and then lose all visibility into what happens to it. Univer is the only mature open-source option that would let the same sheet be edited in the browser and computed by a job. But the honest reading of its README is that the part we need most — xlsx in and out — is the commercial tier, which means the pilot has to answer a pricing question before it answers an engineering one. Start with a read-only viewer of an existing reimbursement sheet using the Apache-2.0 core and see whether the file import path can be done in the browser; if it can, the editing surface follows. If it cannot, this is a paid product and should be evaluated as a purchase, not a repo.

### Codex Security

**What it is:** OpenAI's security CLI (`cs`) with a TypeScript SDK and a GitHub Action. It scans repositories, paths or Git diffs, validates candidate findings, generates patches and verifies existing fixes, drafts `SECURITY.md` and saves threat models, imports third-party scanner output, and exports SARIF/JSON/CSV or pushes findings to Linear, Jira and GitHub.

**Source:** https://github.com/openai/codex-security · npm https://www.npmjs.com/package/@openai/codex-security · Provenance: spotted on Hyperautomation Labs — https://www.youtube.com/watch?v=czifor5lk8I (item 10)

**What's good about it:** The workflow is investigation, not grep. A Standard scan maps the app, a Deep scan repeats it and returns deduplicated findings, and between them sits validation and patch generation with a follow-up "verify this fix" step — the part every scanner skips. `cs scan . --diff origin/main` scopes a scan to what a deploy changed, which is the shape a pre-deploy gate needs, and `--max-time` puts a budget on the investigation instead of letting it run. Findings carry source evidence and exclusions, owner suggestions from Git history, and a severity rubric you supply rather than one imposed. Output is portable: SARIF, JSON, CSV.

**Pros:**
- Validation and patch generation turn findings into fixes; a scanner that only reports is a scanner we ignore after week two.
- Diff-scoped scans (`--diff origin/main`) fit our deploy flow exactly — one command between build and restart.
- GitHub Action and SDK mean the same engine works interactively and in CI.
- Generates and then consumes `SECURITY.md`, so our own threat model becomes the scanner's context instead of being reinvented.
- Runs on Node 22.13+ — our container has 22.22.3, so no runtime fight.

**Cons:**
- It needs `cs login` against a ChatGPT account, or `OPENAI_API_KEY`/`CODEX_API_KEY` in the environment. We run Hermes on DeepSeek and do not provision an OpenAI key on this box — that is a credential decision, not a `pip install`.
- Some cybersecurity requests and protected findings require "Trusted Access for Cyber" / Daybreak access, so coverage depends on the account tier.
- It sends source code to OpenAI. Our repos are internal department systems; that is an egress decision somebody has to make explicitly.
- 227 open issues on a four-month-old repo, and it is one vendor's model judging one vendor's output.
- Cost is metered by investigation time; a `--mode deep` run on a large repo is a budget event, not a free command.

**Should we...**
- 👀 **Watch it** — run it once on a throwaway clone when an OpenAI key exists for it.

**Impact on our stack:** Medium-High — the public-schedule service and the Unified Platform API, both of which take untrusted input and were written fast. The concrete change: a diff-scoped scan in the deploy path, so a change that introduces an unauthenticated upload or a traversal is caught before the container is recreated.

**Why:** Yesterday's item was an agent finding a path-traversal in a medical imaging app and getting root in eleven minutes. The defensive answer is not a policy, it is a scanner that runs on every diff and can write the patch. Codex Security is the most complete version of that I have seen: it validates before it reports, which is the difference between a tool the team uses and a tool the team mutes. The blocker is entirely ours — it wants an OpenAI credential and sends code out. Both are acceptable for the public-schedule repo if we decide they are, and neither is acceptable by default on a hospital-adjacent box. Treat it as a procurement question with a one-command pilot, not a repo to install quietly.

### Designer Skills

**What it is:** A collection of 273 agent skills and 76 commands across 33 plugins, in five collections — design practice (research, systems, UX strategy, UI, interaction, prototyping and testing, design ops, visual critique), AI product design, UX program management, design leadership, and inclusive design. Distributed as a Claude Code plugin marketplace and as Gemini CLI extensions; the content is Markdown.

**Source:** https://github.com/Owl-Listener/designer-skills · index https://github.com/Owl-Listener/designer-skills/blob/main/INDEX.md · Provenance: spotted on Hyperautomation Labs — https://www.youtube.com/watch?v=czifor5lk8I (item 11)

**What's good about it:** It includes a visual-critique skill, which is the thing our design reviews keep failing at — not because the reviews are unserious, but because there is no written procedure for looking at a page and naming what is wrong at the experience level. The collection is organized by situation in `INDEX.md`, with the pairs most often confused for each other called out, and a `start-here` router that names the stage you are at and the one command to run. The inclusive-design collection is the part with regulatory teeth: cognitive accessibility, inclusive interaction, accessible content, accessibility decisions — the vocabulary a hospital site needs and that we have been improvising. It is MIT, Markdown, 3,472★, and it has been live since March.

**Pros:**
- Plain Markdown skills — readable in one sitting, forkable, and portable into Hermes with no adapter for the content itself.
- A written critique procedure is exactly what our redesign adoption gate lacks; today the verdict is taste, unrecorded.
- The inclusive-design collection maps to accessibility requirements we will be audited against, not just judged on.
- Situation-based index and a router command mean a non-designer can find the right skill without reading 273 of them.
- MIT, 452 forks, only 10 open issues — maintained, and small enough to audit.

**Cons:**
- Packaged for Claude Code's plugin marketplace and Gemini CLI extensions. Hermes is not a target, so this is the same adapter question as skillshare, in a different costume.
- 273 skills is far more surface than we can keep current; the value is in 5–10 of them, and the rest is someone else's workflow with someone else's opinions.
- Design skills are opinions encoded as procedure. Applied literally to a Montefiore surface, they will produce generic product-design advice — the exact failure mode Shareef rejects as "not premium".
- It is a design-practice corpus, not a Montefiore one: no brand, no accessibility standard specific to a hospital, no residency context.
- The commands assume a Claude Code slash-command surface we do not have.

**Should we...**
- 👀 **Watch it** — copy three skills in, not thirty.

**Impact on our stack:** Medium-High — the redesign previews, Decision Studio verdicts, and every surface the copy-desk writes into. The concrete change: a written visual-critique pass that produces a record of what was checked, so "not good" becomes a set of named failures instead of a reset.

**Why:** The most expensive loop in our design work is the one where Shareef says "still not good" and I micro-tune colors instead of resetting to the principle. That is a missing procedure, and this pack has one — a critique skill that walks a surface and names what fails. The reason not to adopt the pack wholesale is that its opinions are generic and our bar is specific: brand voice, hospital accessibility, and a scrapbook-not-collage principle that no external skill knows. The right move is to read the visual-critique and accessibility-decision skills, rewrite them against our own standard, and add them to Hermes as house skills. That is an hour of editing and it keeps the authorship where the taste lives.

### QMD

**What it is:** A local search engine for markdown — notes, transcripts, documentation, knowledge bases — combining BM25 full-text search, vector semantic search and LLM re-ranking, all on-device via `node-llama-cpp` with GGUF models. Collections group folders, a context tree attaches descriptions to documents, and an MCP server (stdio or HTTP daemon) exposes `query`, `get`, `multi_get`, `status` and `metadata` to agents.

**Source:** https://github.com/tobi/qmd · Provenance: spotted on Hyperautomation Labs — https://www.youtube.com/watch?v=czifor5lk8I (item 9)

**What's good about it:** The context tree is the idea worth stealing even if we never install it. Each collection and sub-document can carry a description that is returned *with* every hit, so an agent choosing between two results gets "this is the reimbursement policy" alongside the matching lines, instead of a bare snippet and a guess. Search is routed by query type — `lex` to BM25, `vec` and `hyde` to the vector index — then fused with reciprocal rank fusion and reranked, which is the modern recipe done in the right order. `--json` and `--files --min-score` output is designed for agent consumption rather than human reading. It is MIT, 31.4k★, 1,978 forks, and it indexes markdown, not a proprietary store.

**Pros:**
- Generates context for search results, which is exactly what our vault results lack — 1,980 items with titles and one-line summaries.
- BM25 works with no model at all, so a keyword index is available on our hardware even if the semantic half is not.
- MCP server with an HTTP daemon mode: one long-lived process instead of model loading on every call.
- Fully local, no cloud, no embedding bill — appropriate for briefings that discuss internal systems.
- Designed for exactly our corpus shape: markdown files in folders.

**Cons:**
- Semantic search and reranking need GGUF models via `node-llama-cpp`. On a CPU-only VPS, `qmd query` will be slow enough that a cron would time out; only `qmd search` is realistic here.
- 269 open issues and a Node runtime — this box is Node 22 and the tool's dependency tree is not trivial.
- We already have a vault with search. A second index over the same content is duplicate infrastructure unless it indexes things the vault cannot see (skills, briefings on disk, session transcripts).
- No documented incremental or hook-driven indexing story for cron use; `qmd embed` is a deliberate full pass.
- It indexes text only — no PDFs or docx without conversion, which is most of what a hospital department actually has.

**Should we...**
- 👀 **Watch it** — try BM25-only over the briefings folder on the desktop.

**Impact on our stack:** Medium — the briefings archive, the skills tree, and the vault's blind spots. The concrete change: "what did we say about X in September" answered from the files rather than from memory or a repeated web search.

**Why:** Our institutional memory is now 1,980 vault items and a few dozen markdown briefings, and the only way to read it is the vault's own search, which searches what was filed, not what was written. QMD's context tree would let a cron ask "have we already covered this repo" and get an answer with the surrounding reasoning attached — which is precisely the dedupe step this job performs by hand every morning. The blocker is hardware, not design: CPU-only means the semantic half is a batch job at best. Worth a desktop experiment with `qmd collection add` on the briefings directory and BM25 only. If keyword search over 60 files is faster and better than grep, that alone justifies a small index; if it needs the model to be useful, it waits for a GPU.

### Claude BugHunter

**What it is:** A Claude Code skill bundle for bug hunting and external red-team work: 82 skills, 15 slash commands, and 681 disclosed-report patterns curated across 24 core vulnerability classes, plus enterprise identity and infrastructure coverage.

**Source:** https://github.com/elementalsouls/Claude-BugHunter · Provenance: spotted on Hyperautomation Labs — https://www.youtube.com/watch?v=czifor5lk8I (item 1, the "fastest riser")

**What's good about it:** The corpus is real work: 681 patterns drawn from disclosed reports, organized by vulnerability class, with slash commands to drive a hunt. For a security team doing external engagements, a curated set of "here is how this class actually breaks" is worth more than another scanner. It is MIT, actively pushed, 18,698★ and 2,037 forks.

**Pros:**
- 681 real disclosed-report patterns is a genuine corpus, not generated filler.
- MIT and Python — no vendor, no account, no telemetry.
- The command structure makes a hunt repeatable across engagements.
- Actively maintained since May 2026.

**Cons:**
- It is offensive tooling. Installing a red-team skill bundle into an agent that has a terminal tool on a box holding department credentials is an unforced liability, and the skills system is exactly the surface yesterday's item warned about.
- Our need is defensive: we do not run bug bounties, we run a residency program's platform.
- The star count is a trend artifact — 11,269 stars in seven days on a six-month-old repo with a single owner, which is the promotion pattern this brief is supposed to distrust.
- Nothing in it addresses the vulnerability class we actually have: unauthenticated endpoints in our own FastAPI services.
- Skills that write exploits are skills that can be run by mistake by a cron with approvals denied but a bad prompt.

**Should we...**
- ❌ **Skip it** — not our job, and the wrong tool to have installed.

**Impact on our stack:** Low — no system improves. If anything, the risk surface grows.

**Why:** The honest test for offensive tooling is whether you are paid to attack or paid to defend. We defend. Yesterday's MONAI item described what happens when an agent gets root on a medical app — the useful response is a scanner and a checklist, not a bounty bundle. There is also a structural reason to refuse: the attack pattern in the Hermes detection rules is "install offensive skills, turn approvals off, point it at a target." Adding 82 offensive skills to the box that already has the terminal tool moves us closer to that shape for no gain. Skip, and spend the attention on Codex Security and the self-audit instead.

### Mailflare

**What it is:** A self-hosted alternative to Google Workspace — custom-domain mailboxes, calendar, booking links, Drive, and built-in AI agents with MCP — running on Cloudflare Workers or a single Docker container, with D1/Postgres/MySQL/SQLite storage and sending through Cloudflare Email, Resend or Amazon SES.

**Source:** https://github.com/hieunc229/mailflare · Provenance: spotted on Hyperautomation Labs — https://www.youtube.com/watch?v=czifor5lk8I (item 5)

**What's good about it:** It is a real product, not a demo: inbox, domains, mailboxes, calendar with invitations and time zones, public booking links, Drive, routing rules that store/forward/reject, admin with users and API keys, audit logs and backups, and import from IMAP, Gmail Takeout, `.eml` and `.mbox`. 34 languages. Storage is portable across D1, Postgres, MySQL, libSQL and SQLite, and receiving is free through Cloudflare Email Routing.

**Pros:**
- Genuinely complete surface — mail plus calendar plus booking plus drive, with admin and audit logs.
- Portable database layer; it does not lock our data into one provider.
- MCP endpoint so an agent can search mail and draft replies.
- Free receiving, and sending on Resend's 3,000/month tier.
- Active: 7,473★, 1,321 forks, pushed two days ago.

**Cons:**
- **Setup requires a Cloudflare API token with Email Sending:Edit, DNS Settings:Edit and Zone Settings:Edit across all accounts and all zones.** That token is the keys to every domain we own — a far larger grant than a mail server should need.
- It is a mailbox host, not a bridge: it cannot touch `@montefiore.org`, so it would create a second identity for a department that already has one.
- AGPL-3.0 — a network-use copyleft that reaches anything we expose alongside it.
- Deliverability is now a vendor question (Resend/SES reputation), and a new SES account starts in the sandbox.
- Five months old, and it would hold department correspondence on a stack with no HIPAA story.

**Should we...**
- ❌ **Skip it** — wrong layer, wrong risk, wrong domain.

**Impact on our stack:** Low — nothing we run gets better. Our outbound mail already works through Google Workspace SMTP, and the failure mode we have (a stale key) is not a hosting problem.

**Why:** The appeal of this repo is that it looks like a way to stop paying for Workspace. We are not paying for Workspace in a way this fixes, and we are not free to move `@montefiore.org` anywhere. What we would actually be doing is standing up a second mail domain with a Cloudflare token that can rewrite DNS for all of them, to solve a problem we do not have. The one idea worth keeping is the MCP endpoint for mail search — but the Gmail API already does that for the accounts we use, under a scope we have already reviewed. Skip.

### GPUWorks

**What it is:** A ~40 MB Go control plane for a heterogeneous GPU cluster: join bare-metal servers, cloud instances, private-cloud VMs, Kubernetes nodes or a Mac with one command, then pick a model and it estimates memory, chooses GPUs, launches vLLM/SGLang or a templated engine, and serves everything behind one OpenAI-compatible endpoint. It ships 1,235 launch specs for 392 models across NVIDIA, AMD, Ascend, PPU, Hygon and Apple Silicon.

**Source:** https://github.com/flitai-io/gpuworks · Provenance: spotted on Hyperautomation Labs — https://www.youtube.com/watch?v=JW9CM2jl1h4 (sponsored video; the measurements below are the host's, not the vendor's)

**What's good about it:** One endpoint across mixed accelerators is a real problem, and the verified model×accelerator catalog is the kind of thing that saves a week of flag-hunting — image, engine, flags and pinned weight revisions per GPU type. The control plane is 40 MB with the web UI included, and the Go binary has no Python dependency to rot. There are health checks, usage analytics, network tests and PD disaggregation in the UI.

**Pros:**
- 1,235 launch specs for 392 models removes the "which flags does this need on this card" tax.
- Heterogeneous by design — NVIDIA, AMD, Ascend, PPU, Hygon and Apple Silicon in one cluster.
- Single OpenAI-compatible endpoint in front of everything, which is the right abstraction.
- 40 MB Go binary with a web UI, Apache-2.0, active development.

**Cons:**
- **The sponsor video's own measurements refute the headline.** A MacBook Pro M4 Pro (16 GiB usable for models) plus a Mac mini M4 (11 GiB usable) do not pool: a model needing 17.5 GiB ran on neither. "One AI server from two Macs" is two servers with a shared control plane.
- We have no GPU. The VPS is CPU-only, which makes this a tool for hardware we do not own.
- 237 stars, created October 22, one month old, 26 open issues — and the coverage we saw came from a sponsored build, which is provenance, not a review.
- 87 MB repo for a 40 MB binary; the catalog and docs dominate.
- Running a multi-node MaaS platform adds a control plane we would have to secure for a capability nobody has asked for.

**Should we...**
- ❌ **Skip it** — revisit only if a GPU box is actually purchased.

**Impact on our stack:** Low — no system improves today. Local inference would matter for PHI-adjacent prompts, but we have no accelerator and no plan to buy one.

**Why:** The reason to read a sponsored video is to find the measurement inside it, and here the measurement is the finding: two Macs with 16 and 11 GB of usable model memory do not add up to 27, so a 17.5 GB model fits on neither. That is not a bug in GPUWorks — no scheduler can pool VRAM across machines — but it means the tool's headline use case is a cluster manager, not a bigger model. For us the question is moot at the hardware layer: there is no GPU on this box and no departmental budget line for one. If a GPU server does land, the catalog is worth remembering. Until then this is a skip, and the video's real value was the number, not the product.

## Overall assessment

If we do nothing else, do these, in this order: **1) Run the Hermes self-audit from agentic-attack-detections** — turn the six tamper checks into a start-time script and YARA the image, because the godmode skill payload is sitting in `/app` and every cron we run goes through that process; this is the only item where doing nothing leaves an existing exposure in place. **2) Pilot skillshare on a copy of the skills tree** — a source directory with symlinks and an audit gate is the fix for 662 skills that live in exactly one tool, and the same adapter question decides whether Designer Skills and every future skill pack are usable; one afternoon tells us which way to invert. **3) Decide the OpenAI credential question and run Codex Security once on the public-schedule repo** — a diff-scoped scanner that validates findings and writes patches would put a real gate between a bad change and a container recreate, and the only thing standing in the way is a procurement decision, not engineering.

The pattern across today's items is worth naming: the best tools are the ones that turn an invisible property into a recorded fact — a tamper surface, a skill's provenance, a validated finding, a written critique. The weakest are the ones that promise a bigger box out of hardware you already have.
