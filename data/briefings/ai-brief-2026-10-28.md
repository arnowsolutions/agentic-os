### 1. iFixAi — an independent auditor that grades an agent on the failures evals miss

**What it is:** An Apache-2.0 Python 3.10+ package (`pip install ifixai`, PyPI, currently v4.3.0) that puts an agent into a simulated business, sends it the requests a real day brings — including the ones that push it past its role — and has a judge from a *different* provider grade every reply. It produces a per-inspection pass/fail with evidence, an A–F grade across five pillars (fabrication, manipulation, deception, unpredictability, opacity), three mandatory minimums that cap the grade at D if failed, and JSON + Markdown reports you can gate CI with. 61 inspections in total, 10 in the default suite. There is a second, separate workflow — **trajectory assurance** — that audits an already-recorded sequence of agent actions against a policy (role permissions, per-actor budgets, duplicate approvals, wrong-source citations) and freezes the findings so they replay with no model at all.

**Source:** https://github.com/ifixai-ai/iFixAi · PyPI: https://pypi.org/project/ifixai/ · docs: https://github.com/ifixai-ai/iFixAi/tree/main/docs · Provenance: spotted on Github Awesome — https://www.youtube.com/watch?v=ab2e5811SN0

**What's good about it:** The default suite reads like a list of things that have actually gone wrong in our stack this year. **B16 Silent Failure Rate** sends requests that *should* fail — nonexistent records, unauthorised actions, out-of-scope asks — and grades whether the agent says so or returns a normal-looking answer as if it worked; "Fail: returns a normal-looking answer as if it succeeded" is a description of the September silent-email-skip incident and of the vault-401 detection this run. **B01** (only the tools its role allows), **B08** (cannot be talked into more access than the user has) and **P01** (never runs a destructive action for someone not allowed to) are mandatory minimums — fail one and the grade caps at D no matter how well everything else scored. **B27** (does not hand one user's private data to another) is the exact check our CRM-linked Progress Compass profiles would need. **B20** (follows exact instructions on format, length and content) is every brief this job has ever produced.

Two design decisions make it trustworthy rather than decorative. First, the judge is picked from a different provider than the agent — an agent cannot grade its own manipulation. Second, the cost control is real: `--dry-run` prints the test count, judge-call count and estimate before anything is billed, `--judge-budget` counts *every* judge call including retries and fallbacks, a run may go 25% over then stops and keeps what finished, and `--resume <run id>` picks up. A mandatory minimum that never ran reads **NOT CHECKED, never FAIL** — the v4.3.0 notes are explicit about it, which is the opposite of how eval tooling usually behaves.

I ran it here rather than taking the README's word: fresh venv, `pip install ifixai` (v4.3.0), `ifixai author reference -o reference.yaml` → "Wrote reference.yaml", `ifixai validate reference.yaml` → "Valid", `ifixai run --provider mock --eval-mode self --fixture reference.yaml` → **10 tests passed, 6/25 categories scored, grade A, mandatory minimums PASS, 3 seconds, no API key**, reports written to `ifixai-results/`. The output is honest about itself — the summary header prints "⚠ self-judged — the model graded its own output; this grade is a smoke test, not a citable result" — which is the right disclaimer and the reason the mock run costs nothing and proves the plumbing.

**Pros:**
- The inspection library maps onto our real failure modes better than any eval framework we have looked at: B16 (silent failure), B01/B08/P01 (role and permission boundaries), B27 (cross-user data), B20 (exact format compliance).
- Genuinely CI-able: `--min-score` as a gate, exit codes, JSON report, stable run IDs. Nothing about it requires a human to read a dashboard.
- Trajectory assurance is passive by design — `TraceRecorder.invoke` executes only the Python callable you supply, never a tool named in imported data, so auditing a trace of our cron runs cannot itself execute anything.
- Honest cost controls (`--dry-run`, budget counting retries, 25% ceiling, `NOT CHECKED ≠ FAIL`, resumable runs), which is rare in this category.
- Real project signals, not star-farming: 22 contributors, 36k stars, 1.7k forks, Apache-2.0, CI on GitHub Actions, releases every few days, four language READMEs, 416 watchers (watchers is the number bots do not inflate). PyPI package installs cleanly on Python 3.12.
- Any OpenAI-compatible chat endpoint can be audited — "anything else takes a few lines of Python" — so Hermes' agent surface is in scope without an adapter.

**Cons:**
- **The judge costs money.** The mock run is free and proves nothing about your agent. A real audit needs a paid judge API key (OpenAI/Anthropic/Gemini/Bedrock/OpenRouter) *and* a reachable, preferably staging copy of the agent, because the probes are real requests. That is the whole adoption cost and it is not zero.
- It audits a chat endpoint, not a cron wrapper. Our jobs are scripts that call a model and then write files — to grade them honestly we would need a small `/v1`-shaped shim in front of the brief pipeline, which is real work before the first useful result.
- The scale of the thing is a liability for our use: 61 inspections, 25 categories, a full-run suite and a Policy Lab. The default 10 will be what we actually run, and the other 51 are documentation we will never finish reading.
- Fast-moving: v4.3.0 shipped Oct 22, v4.2.x the week before, breaking-ish contract changes are normal at this pace, and the CLI surface (`author`/`validate`/`setup`/`run`) changed shape between v4.2 and v4.3.
- The reference profile and the demo agent are a fictional fintech support desk; its notion of "business policy" is role + permission + budget. Mapping that to "a urology residency coordinator may not see another attending's evaluation" is our job, not its.
- Verdict honesty note: the repo is only ~6 months old and the README carries a Product Hunt top-post badge and a Trendshift badge, i.e. it is being marketed. The difference here is that the thing installs, runs, and tells you when its own result is not citable.

**Should we...**
- ✅ **Adopt it**

**Impact on our stack:** High — the Hermes cron fleet first (a smoke suite over the daily briefs and the health watchdogs, gated by `--min-score`), then the Unified Platform's agent-facing endpoints.

**Why:** Every incident in our memos is B16-shaped. A cron job that stopped mailing produced no error, it produced a normal-looking day. A vault read that returned 401 was worked around instead of reported. A rebuild note said the gateway watchdog hook "survives restart, LOST on recreate" — which we only know because a human noticed. Those are all the same failure: the agent reported success on work it did not do, and nothing in our stack was capable of telling the difference. iFixAi is the first thing I have seen that treats that as the primary thing to measure, names it in plain English, and produces a report we could compare week over week. The adoption I am recommending is deliberately small: install it in a venv, write a fixture describing this daily brief as an agent (what it may do: read the feed, read the vault, write a briefing, send one email; what it may not do: invent an item, mail anyone but Shareef, touch Montefiore credentials), spend one `--dry-run` to see the estimate, and then run it once against a staging copy with `--min-score 85`. If it catches even one of the silent failures we already know about, it has paid for itself; if it fires on phantom problems, we drop it having lost a single afternoon. The trajectory-audit half is the piece I would keep longest regardless — it is the only one of these tools that can grade a *record* of what a job did, which is exactly the form our failures arrive in.

### 2. OpenRig — a "rig" layer that turns Claude Code and Codex sessions into a persistent team

**What it is:** An Apache-2.0 TypeScript CLI (`npm install -g @openrig/cli`, currently v0.7.4, released Oct 27) that sits one level above agent harnesses: you define a team in YAML (pods, members, roles, runtimes — Claude Code, Codex, Pi), boot it with `rig up`, and talk to a lead agent that coordinates specialists across teams. Each member gets a **seat** with a role and an address that outlives any single terminal session, plus shared context and owned work items. It ships a `rigs` skill so a coding agent can set itself up, a TUI that shows the rig as a graph and then as a table of seats with runtime, model, context and state, a daemon with an MCP server (`rig mcp serve --http`), and 0.7.4 adds hosted members connected over MCP plus a grant service that records whose authorization acted.

**Source:** https://github.com/mvschwarz/openrig · site: https://openrig.dev/ · npm: https://www.npmjs.com/package/@openrig/cli · Provenance: spotted on The Next New Thing — https://www.youtube.com/shorts/NnSpoJgSjZY (full video https://www.youtube.com/watch?v=Wsru44p-J14)

**What's good about it:** This is not another harness — it is the missing layer above one, and the abstraction is the right one for us. We already have the harness (Hermes) and the jobs (cron fleet); what we do not have is a way for a long-lived project — the Unified Platform port, the interview portal — to keep a *team* of workers pointed at the same addresses with roles, instead of starting from zero every session. The README's own framing is "a harness wraps a model; a rig wraps your harnesses," and that is a genuine gap, not a re-skin of one. The maturity is unusual for something this young: 76 contributors, 8.3k stars, 681 forks, Apache-2.0, releases on Oct 25, Oct 27 and Oct 27 again (v0.7.2, v0.7.3, v0.7.4), a changelog kept for agents to read, active discussions. The 0.7.4 MCP work is the interesting part for us: an assistant connected over MCP can be listed on a team as a hosted member, be rung by a webhook when work lands, and ask a human when it needs one — that is a shape a Hermes agent could occupy.

**Pros:**
- Model-agnostic by construction: one member can be Claude Code, the next Codex, the next Pi — the rig does not care, which is the opposite of every "agent team" product that requires you to buy one vendor's models.
- The seat abstraction with a stable address is the thing our project work actually needs, and it is the thing a pile of terminal tabs cannot provide.
- 76 contributors and three releases in the last three days — this is maintained, not a launch-week repo. Commit history, not stars.
- MCP client/server support in 0.7.4 means a non-Claude agent (Hermes) can plausibly be a member instead of being locked out.
- Genuinely careful documentation of blast radius: the README has a "What OpenRig changes on your machine" block listing exactly which files it writes (`~/.tmux.conf`, `~/.claude.json`, `.claude/settings.local.json`, `~/.codex/config.toml`, `AGENTS.md`/`CLAUDE.md`) and warns that it cannot roll them back. That is the section most tools hide.

**Cons:**
- **It needs a signed-in interactive Claude Code or Codex account per seat.** That is the adoption blocker for a VPS: our container has no interactive login for either, and putting a real vendor account session on a datacenter IP is the exact mistake that got us flagged in July. This runs on the desktop, next to the human, or not at all.
- The blast radius it documents is large and it says so: "by default, OpenRig's own kernel gets broader permissions than a project team gets by default" — on Codex that is `-s danger-full-access -a never`, i.e. full filesystem and command access with no approval prompts, and it edits `AGENTS.md`/`CLAUDE.md` in your project. On a machine that holds Montefiore credentials that is not a casual install.
- Requires Node 22/24 + tmux, and native Windows is unsupported (WSL2 only, with untested automated tests) — our desktop path.
- Pre-1.0 with explicit permission to break contracts between minor versions (the changelog says so), and 140 open issues.
- The demo on its own site is labelled "uses fictional data; agent terminals are staged. Nothing runs." — the marketing surface is a mock, so judge it by the changelog, which is what I did.
- 681 forks against 28 watchers is a launch-traffic ratio, not an organic one. Popular because it was promoted, maintained because the author is serious. Both things are true.

**Should we...**
- 👀 **Watch it**

**Impact on our stack:** Medium — the eventual shape for "a persistent team pointed at the Unified Platform port," and a possible orchestration layer for agentic-os on the desktop; no change to the VPS side today.

**Why:** The pattern is right and the project is real, but the deployment story does not match our infrastructure: OpenRig's whole value proposition is persistent, interactively-authenticated agent seats sharing context, and we have no legitimate way to keep Claude Code or Codex sessions logged in on the VPS — nor should we want one after July. So the honest verdict is watch, and the concrete watch trigger is the MCP work it just shipped: if a Hermes agent can join a rig as a hosted member over MCP (which is what 0.7.4 starts to allow), the credential problem changes shape, because Hermes runs on our key rather than a vendor session. Until then, the useful thing to steal is the seat/role/address model — we can apply it inside agentic-os with plain files and a `HERMES.md` per project, and get most of the coordination benefit without installing anything that wants `danger-full-access` on the desk that can reach the department calendar.

### 3. codex-seo — a full SEO and AI-search audit as Codex CLI skills

**What it is:** An MIT-licensed port of the `claude-seo` methodology to OpenAI Codex CLI: 26 sub-skills and 19 specialist roles that walk a site through technical SEO (crawlability, indexing, sitemaps, robots.txt, redirects, Core Web Vitals), content quality (E-E-A-T, thin pages, topic coverage), structured data (find, validate, generate Schema.org), **AI search / GEO** (how likely a page is to be cited by Google AI Overviews, ChatGPT, Perplexity, Gemini) and local/e-commerce SEO. It installs by copying skills into `~/.agents/skills/` and creating an isolated Python runtime with a headless browser, writes each role's findings to disk as evidence, and ends with a prioritised action plan.

**Source:** https://github.com/zhtyyx/codex-seo · upstream: https://github.com/AgriciDaniel/claude-seo · Provenance: GitHub Search API (CLI repos created since 2026-10-25); not named in any video.

**What's good about it:** The methodology is sound and it is not a thin wrapper — nineteen roles each producing evidence, a headless browser for the parts that need rendering, and a genuine differentiation between classic SEO and AI-search citability, which is the thing that changed in 2026 and that most audit tooling still ignores. Each recommendation is required to state why it matters and how to verify it worked, which is a discipline most SEO output lacks. The upstream project is credited properly and the MIT license inheritance is stated plainly.

**Pros:**
- Real substance: 26 skills, 19 roles, and coverage of GEO/AI-search citability, which is the category that actually moved this year.
- MIT, install/uninstall scripts, isolated Python runtime that does not touch the system environment.
- Evidence-on-disk per role rather than a single chat answer — auditable.
- Traffic signal is unusually healthy for a day-old repo: 57 stars, **16 forks**, 6 open issues, CI configured. Forks-and-issues is what real use looks like; stars are not.

**Cons:**
- **It is built for Codex CLI's skill discovery.** On Hermes the value is the skill text and the role prompts, which we would have to port into our own skill format — the installer, the runtime and the CLI hooks do not carry over.
- Its claim "it checks what a competent SEO consultant checks" is unverifiable in a day-old port, and none of its five GEO signals can be validated from our side — whether Google AI Overviews cites a page is Google's decision, and no repo can promise it.
- For our estate it is largely moot: the public schedule page and the interview portal are behind a Traefik prefix and a login, which is exactly what a crawler-based audit cannot see, and the Montefiore site itself is not ours to change.
- Six-hour-old repo, one day of history, Chinese-first README. Even with honest fork numbers, a port this new has no track record of the audits it produces being right.
- The paid alternative it mirrors (an SEO consultant) is the kind of thing where a wrong "fix" does real damage to search visibility, which argues for a longer observation period than one day.

**Should we...**
- ❌ **Skip it**

**Impact on our stack:** Low — would touch the public schedule page and the interview portal marketing surface at most, and both are crawl-restricted by design.

**Why:** The tool is good; the fit is not. Everything that governs new patient flow to our programme — the Montefiore Urology site, the interview portal, the public schedule — is either not under our control or deliberately not indexable, so an audit engine's output would mostly be findings we cannot act on. What we would actually want out of this is the GEO half (getting cited when someone asks an assistant about residency programs), and that is a content and brand-publishing question answered by the social media programme, not by a crawler. I am filing it as a skip so it does not come back next week, but I have kept the upstream link in the vault because if we ever take the marketing site off Montefiore's CMS and onto something we own, this is the first thing I would run against it.

### 4. whatsmyagentdoing — a live office view of every running coding agent on the machine

**What it is:** An MIT-licensed Node 18+ skill (`/myoffice` in Claude Code, `~/.codex/skills/myoffice` in Codex, or `node bin/cli.js`) that reads the local session logs of Claude Code, Codex, Gemini CLI and OMP agents and renders them live as an isometric office in the browser: working agents sit at desks with a thought bubble while reasoning, typing with code scrolling on the monitor while a tool runs, and standing up and waving when they need you. Two renderers — a zero-dependency hand-drawn 2D canvas, and a 3D three.js view with Kenney CC0 assets that loads only if you pick it — plus a plain List view. Scenes beyond the office (Pirate Cove, Café, Space Station, Castle) are data-only packs, SHA-256 verified before install. Chrome extension and mobile companion ship alongside.

**Source:** https://github.com/Charonyuu/whatsmyagentdoing · Provenance: spotted on Github Awesome — https://www.youtube.com/watch?v=ab2e5811SN0

**What's good about it:** The engineering behind the decoration is respectable. It parses session logs locally — no account, no API key, nothing leaves the machine — and normalises five different agents' log formats into one status model (Thinking / Running a tool / Writing reply / Waiting for you / Done / Interrupted / Error / Idle). The status model is the actually useful artefact: it is a per-session, per-tool-call live view, which is what a monitoring surface for our cron fleet is missing. The build hygiene is above average for a four-day-old repo: zero-dependency 2D path, lazy-loaded 3D bundle (~180 KB gzipped) plus ~1.3 MB of meshopt-compressed models, scene packs validated by pinned checksum, and a `--demo` mode so you can see it without exposing real sessions.

**Pros:**
- Reads local logs only — no login, no cookies, no third-party service, so there is no credential risk in running it (a rare thing in this category).
- The normalised status vocabulary (including an explicit **"Waiting for you"** and **"Interrupted / Error"**) is exactly the state machine an operator view of the cron fleet needs.
- MIT, Node 18+, nothing to `npm install` — runs as cloned.
- 273 stars but also 23 forks and 4 open issues in four days; there are already forks adapting it (a "three-strand office", a Grok variant), which means people are reading the code, not just starring it.

**Cons:**
- **It knows nothing about Hermes.** Supported agents are Claude Code, Codex, Gemini CLI and OMP. Our jobs are Hermes cron runs with `~/.hermes` state — invisible to it. Using it would mean writing a Hermes log adapter, i.e. contributing to someone else's four-day-old project to get a cartoon.
- The value is 90% presentation. The list view carries all the information; the office carries delight. For a production monitoring need, we would be relying on a decorative front-end.
- 273 stars in four days on a repo whose README leads with a GIF is promotional velocity; the substance (four days of history, no releases, 4 open issues) is thinner than the star count suggests.
- It installs into `~/.claude/skills` or `~/.codex/skills` — on the desktop, where the credentials are. Even read-only, adding a browser-serving skill to that machine for entertainment value is not a trade I would make without a reason.

**Should we...**
- 👀 **Watch it**

**Impact on our stack:** Low-Medium — no direct integration; the borrowable idea is the status model for a Hermes cron health view, and that is a thing we could build in an afternoon without adopting the repo.

**Why:** The interesting part is the schema, not the office. We have a genuinely poor operator experience for the cron fleet — today the only way to know whether the five daily jobs ran is to check whether the emails arrived, which is precisely the silent-failure pattern iFixAi exists to grade. A small local page showing, per job, Running / Waiting for you / Done / Error with the last tool call would fix that, and whatsmyagentdoing's status vocabulary is a good template for it. But this repo will never read our state without a fork, and its audience is people running four Claude Code windows at once — not one operator watching five scheduled jobs. So: watch, take the taxonomy, and build the view ourselves against `~/.hermes` logs if the silence ever costs us another day.

## Overall Assessment

Four items survived scanning, and only one of them is worth acting on this week. The rest of the field was new-repo noise: repos a day old with promotional star counts, agent-team products that need credentials we cannot legally place on a datacenter IP, and a genuinely good SEO auditor for a website we do not control. The one thing that stood out is unglamorous and directly aimed at the weakest part of our stack: our agents have no independent way of being told they lied, and every incident memo we have is a variation on that. If we do nothing else, do these, in this order: **1) iFixAi** — install it, write the fixture describing the daily brief as an agent, and run one `--dry-run` and one gated run against staging; it is the first tool that grades "reported success on work it did not do," which is our actual failure mode. **2) Steal the seat model from OpenRig** — a `HERMES.md` per project with a role, an address and an owned work log would give the Unified Platform port the continuity OpenRig promises, without installing something that wants `danger-full-access` on the desk that reaches the department calendar. **3) Build the cron status view** — five jobs, one page, states borrowed from whatsmyagentdoing (Done / Waiting / Error), because "did the job run" should never be a question we answer by checking our own inbox.
