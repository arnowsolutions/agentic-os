### hermes-official-plugins — specifically the memory-wiki plugin

**What it is:** Nous Research's single repo for every first-party Hermes plugin (Home Assistant, Spotify, Langfuse, Telegram Business, Memory Wiki, REA, X Chat, Blender, TouchDesigner, Snyk, Accent Picker). Memory Wiki is the one that matters today: a dashboard tab that derives a browsable session-history wiki from your local `state.db` and shows a read-only audit panel of exactly which `MEMORY.md` / `USER.md` entries the agent carries into every session.

**Source:** https://github.com/NousResearch/hermes-official-plugins · [Provenance: GitHub API new-repo scan — 306 stars, 30+ committers, 100+ commits since Oct 10]

**What's good about it:** This is the first time anyone can *see* our memory instead of trusting it. Our MEMORY.md is at 96% capacity (5,782/6,000 characters) and USER.md at 97% — at that fill level the file is one bad append away from silently dropping entries, and until now the only way to know what's actually in there was to read a file over SSH. Memory Wiki parses them the same way the memory tool does, so the panel and the agent agree. It also opens `state.db` strictly read-only through the public `hermes_state.SessionDB` API and makes zero LLM calls — no token cost, no writes, no prompt-cache disturbance. Editing stays with the `memory` tool where it belongs.

**Pros:**
- First-party and pinned to a reviewed catalog commit (`hermes plugins install hermes-memory-wiki --enable`) — reviewed by the same people who ship Hermes, tested nightly on Linux against current core
- Read-only by design: no LLM calls, no writes, no API keys, no network calls out — nothing to leak, nothing to break
- Directly solves a live problem: auditing a 96%-full MEMORY.md and 97%-full USER.md before an append starts evicting entries
- Subject pages and daily logs give us a searchable "what did we actually do on Oct 9" surface that currently doesn't exist anywhere except my chat scrollback
- Routes sit behind the dashboard's existing auth gate and respect `?profile=` scoping, so it works with the default profile without exposing anything new
- MIT, part of the official catalog (not a random community repo), so updates arrive via `hermes plugins update`

**Cons:**
- Requires Hermes Agent ≥ 0.21 (dashboard plugin SDK with `fetchJSON`) — needs a version check before install
- It is a dashboard tab only; it adds nothing to cron, Telegram, or the agent loop itself
- Session-history pages are derived from session titles and file paths, so a session titled "check this" produces a weak subject page
- Adding a manifest at runtime needs `/api/dashboard/plugins/rescan` and backend edits need a server restart — friction on a container that we've already learned loses boot hooks on `docker recreate`
- The umbrella repo is 11 days old with one directory per plugin; individual plugins carry the real history but the repo-level maturity is new

**Should we...**
- ✅ **Adopt it** — integrate into our stack (strongly recommended)

**Impact on our stack:** High — Hermes cron/agentic-os. Concretely: install memory-wiki, then use its Persistent Memory panel to prune MEMORY.md and USER.md — starting with the duplicate Cron/python-interpreter note and the redundant "Sick Call" entries — before the next append evicts something we need.

**Why:** Every other item in this brief is a tool we'd have to learn to trust; this one is built by the people who build the agent we run, it cannot write anything, and it answers a question we currently answer by squinting at a file over SSH. Our memory files are at 96% and 97% — that is not a hypothetical failure mode, it is one append away. The adoption is small (one install line, one restart, one version check), reversible (`hermes plugins remove memory-wiki`), and it makes every later memory decision visible rather than blind. Nothing else in today's scan comes close to that ratio of risk to value.

### Perplexity SPACE (Sandboxed Platform for Agentic Code Execution)

**What it is:** Perplexity's in-house agent sandbox, open-sourced Oct 16 under Apache 2.0. Every agent task gets its own Firecracker microVM; credentials and outbound network policy are controlled from *outside* the VM, and sandboxes outlive the request that created them. It's the platform that runs every task in Perplexity Computer, exposed as an HTTP API.

**Source:** https://github.com/perplexityai/SPACE · blog https://www.perplexity.ai/hub/blog/open-sourcing-space · [Provenance: Google News (MarkTechPost, Perplexity blog) + GitHub]

**What's good about it:** This is a production sandbox, not a weekend project — Perplexity replaced a commercial sandbox vendor with it in July and then red-teamed it: nine model configurations running as root inside the VM made 108 escape attempts and none reached the host. The design choices are the ones that actually matter for agents: the sandbox is treated as untrusted, credentials never enter it, egress is policy-controlled per profile, and state survives via pause/suspend plus base snapshots. It also ships an E2B-compatibility wrapper, so code written against the most common sandbox SDK works unmodified.

**Pros:**
- Real isolation boundary: microVM per task, host-managed credentials and egress — the strongest containment story of anything we've scanned this month
- Apache 2.0 with hosted docs, an OpenAPI spec, an operator CLI, warm pools and snapshots — production-shaped, not demo-shaped
- Rust implementation but HTTP + SSE API, so Python/MCP clients need no Rust dependency
- E2B compatibility wrapper lowers the cost of trying it against code we might write later
- Published adversarial test results rather than marketing claims
- Actively developed (pushed today, 99 forks, wired to an EKS reference deployment)

**Cons:**
- Needs KVM/Firecracker host privileges plus Kubernetes (Kind for local, EKS for real) — our VPS does not have nested virtualization to give it, so this is a *new dedicated host* decision, not an install
- 16 days old with 91 open issues; first public release, API fields still marked incubating
- Heavy for our actual threat model: hermeswebui already has root via the Docker socket, so a sandbox doesn't raise the ceiling for the agent that can `docker run` anything
- No HIPAA/BAA story and no stated answer for regulated data — which is the only place a sandbox would earn its keep for us
- Operational burden: templates, node pools, snapshots, versions — a second infrastructure product to run and patch

**Should we...**
- 👀 **Watch it** — keep an eye on it, not ready yet but promising

**Impact on our stack:** Medium now, High later — agentic-os. If we ever run untrusted agent-generated code against PHI-adjacent data, SPACE is the shape we want: one VM per job, no credentials inside it.

**Why:** The honest read is that this is the single most technically impressive thing in today's feed and also the wrong purchase for today. Our VPS cannot host Firecracker (no KVM), so adopting it means provisioning a dedicated sandbox host and running Kubernetes for it — a real infrastructure project in service of a threat we mostly don't have, because our agent is already trusted with the Docker socket. The version that would be worth that project is the one with a compliance posture: one microVM per resident-data job, credentials held outside, egress locked to Montefiore endpoints. Watch the repo for a plain Linux + KVM install path and any mention of regulated workloads; if that appears, this becomes an adopt.

### aindeev/agent-chrome-relay

**What it is:** A macOS background service + Chrome extension + Go CLI that lets an agent drive *your everyday Chrome*, with your real logins, in background tabs that never take focus. `chrome-relay do "<goal>"` runs a whole multi-step browser job in one command, replaying saved flows, filling known fields, and using a small decision model (TypeSafe Jev or Claude Haiku) only for the ambiguous clicks.

**Source:** https://github.com/aindeev/agent-chrome-relay · [Provenance: GitHub API new-repo scan (289 stars) + spotted on The Next New Thing — https://www.youtube.com/watch?v=0SDz3rjZBC4]

**What's good about it:** It attacks the real bottleneck. A relay command answers in ~15–20 ms, but agents take a median 2.8 seconds between actions because they're *thinking* — so `do` collapses a dozen model round-trips into one, and the README shows a 7-step order form completed in 2.5 s and 1.2 s on replay. The safety design is unusually careful: each agent sees only the tabs it opened, commands that could raise or focus the browser are swallowed, consequential buttons (delete, send, pay, deploy, authorize) require an explicit `--allow`, and "done" is only trusted when the `--until` condition actually holds. There's an audit trail of every action, and 1Password values are typed by the relay itself so the agent never sees them.

**Pros:**
- Solves the block-the-agent problem by using a browser that's *already* signed in, instead of pretending to be human from a datacenter IP
- Measured, published decision-accuracy table (Jev 91% live / 0.15 s per decision) rather than vibes
- Strong safety defaults: per-agent tab isolation, destructive-action gating, `--until` verification, 1Password integration the agent can't read
- Audit trail + saved flows per site make repeated jobs fast and inspectable
- MIT, active (pushed yesterday, 46 commits, multiple authors), with a real website and a skill file for Claude Code/Codex/Cursor

**Cons:**
- **macOS-only.** Needs a Mac, Chrome, Go 1.25+, a self-built and self-signed binary, a Chrome Web Store extension, and per-profile setup — unusable on the VPS
- By construction it puts *your* signed-in sessions in front of an agent — the exact risk profile we refuse to allow on a server, and one that deserves a throwaway browser profile even on a personal Mac
- The relay depends on an explicitly optional TypeSafe Jev key (or Claude Haiku through a Claude Code login) for the fast path; without either it degrades
- 7 days old, one primary author (3 contributors), 9 forks, 1 open issue — early even though it's well built
- Secure Enclave passkeys and 1Password features only work on a build with Xcode CLI tools and a signing identity

**Should we...**
- 👀 **Watch it** — keep an eye on it, not ready yet but promising

**Impact on our stack:** Low — no current system of ours benefits, because Hermes runs on a Linux VPS and nothing we automate depends on a signed-in desktop Chrome session.

**Why:** This is the most credible answer I've seen to "why does my agent get blocked," and it deserves to be on the radar for exactly one future case: a **desktop with a throwaway browser profile**, driving sites that require a human-authenticated session — never the VPS, never a real institutional account. It cannot be adopted where we'd need it today, and its own prerequisites (a Mac, a self-signed build, Chrome) rule out anything scripted from cron. Watch it for a Linux port; the `do`-loop design and the `--until` verification model are worth borrowing conceptually even if we never install it.

### daijro/camoufox

**What it is:** An open-source anti-detect browser — a Firefox fork with fingerprint spoofing baked in (canvas, WebGL, fonts, screen metrics, headers) — built specifically for web scraping and AI agents that get blocked.

**Source:** https://github.com/daijro/camoufox · [Provenance: spotted on The Next New Thing — https://www.youtube.com/watch?v=0SDz3rjZBC4]

**What's good about it:** It's the mature option in this category: 12.6k stars, 1,068 forks, MPL-2.0, in development since mid-2024, and pushed today. Rather than one patch at a time, Camoufox spoofs at the Firefox C++ implementation level, which is much harder for a site to detect than JS-level patching. Python API, plays fine with Playwright, and it's the pragmatic answer when a page refuses to render for a headless agent.

**Pros:**
- Two years of history, active daily commits, and a real fork community — not a promoted new repo
- Fingerprint spoofing at the engine level rather than injected JS, which is what actually passes modern detection
- MPL-2.0 — permissive enough for internal and commercial use
- Python-native, so it drops into any Playwright/Python automation we'd write

**Cons:**
- The README's own banner says "This project is under development. It may not be suitable for stable production use" — the author's words, not mine
- Its entire purpose is looking like a human from a datacenter IP; using it against accounts we actually care about (email, banking, healthcare portals) is how those accounts get flagged or locked, which is the exact failure our verdict rules exist to prevent
- Firefox fork = a patch cadence of its own; we'd be maintaining a second browser engine
- Sponsored by proxy vendors in the README; the incentive is scraping volume, not run stability

**Should we...**
- 👀 **Watch it** — keep an eye on it, not ready yet but promising

**Impact on our stack:** Low — nothing we run needs to defeat bot detection. If we ever do, it belongs on the desktop against throwaway accounts, not on the VPS.

**Why:** Camoufox is technically the strongest tool in this category, and that is exactly why it's dangerous to us: it makes it easy to point a browser at sites that have deliberately said "no automated clients" from a datacenter IP, and the accounts that pay for that are the real ones. Our access problems are about *being let in properly* (a signed-in session on a desktop), not about *looking human*. Watch it as the fallback if a public, non-account page ever refuses to render for an agent — and nothing more than that.

### outcrawlai/scout

**What it is:** An open-source browser agent from Outcrawl: you describe a task in plain words, it opens a Chromium browser, clicks and types until the job is done, and returns the answer plus a replay URL. Bring-your-own models (hands / brain / eyes / extract roles), or run it on Outcrawl's cloud with 1,000 free credits a month.

**Source:** https://github.com/outcrawlai/scout · [Provenance: GitHub API new-repo scan (914 stars, 28 forks, 6 days old)]

**What's good about it:** The model-role split is genuinely well designed — cheap fast model on the "hands" loop, optional stronger "brain" for planning, optional vision "eyes" for screenshot moments, optional "extract" for shaping output — and JSON Schema output means answers come back in a fixed shape. Local Playwright is a one-line switch, so it's not cloud-locked.

**Pros:**
- Clean separation of model roles, each with its own base URL and key, including fully local models
- JSON Schema output plus a replay URL per run — good for auditing what an agent actually did
- Apache-2.0, npm-installable, Node 22+

**Cons:**
- **It's a mirror**, by its own description: "Mirrored automatically from Outcrawl's own repository" — issues, PRs and commits don't live here, so we can't actually collaborate on it and history can be overwritten
- Six days old with zero commit attribution (all commits show no linked author) — the worst possible signal for a repo we'd depend on
- The best experience is on their paid cloud; the free tier is a hook
- We already have a browser tool in Hermes and Playwright available; this is a wrapper around the same thing with an extra vendor in the path
- No stated answer for sites that block automated browsers, which is the actual problem

**Should we...**
- ❌ **Skip it** — not relevant, redundant, low quality, or not useful for us

**Impact on our stack:** Low — nothing it does isn't already reachable through Hermes' own browser tool.

**Why:** Three disqualifiers at once: it's a read-only mirror of someone else's repo, it's six days old with no attributable commit history, and its core capability duplicates what our agent already has. Even if the product turns out good, we'd be adopting a vendor's cloud with a stale GitHub shell attached — the opposite of the self-contained tooling we run. Skip, and if Outcrawl's approach ever seems worth copying, read their docs rather than vendoring the mirror.

### genspark-ai/genoffice

**What it is:** A free, open-source AI Office suite — opens and saves native `.docx`, `.xlsx`, `.pptx` byte-preservingly, edits PDF/Markdown/HTML, with an AI panel beside every document. Ships a `genoffice` CLI and an agent skill so Claude Code/Codex can create, convert, read and edit Office files without a window.

**Source:** https://github.com/genspark-ai/genoffice · [Provenance: spotted on Hyperautomation Labs — https://www.youtube.com/watch?v=oZ9pO17PonU]

**What's good about it:** "Real formats, byte-preserving — only what you edit is rewritten" is the right engineering choice for anyone who has to hand a document back to a hospital that runs Word. Edits land as tracked changes with one-click rollback, PDF→Word/Excel and Markdown→Word conversions run on-device, and a local SQLite index gives full-text search across the files. It takes any OpenAI-compatible endpoint, including a local server, and the CLI/skill pairing is exactly the shape an agent needs.

**Pros:**
- Byte-preserving `.docx`/`.xlsx`/`.pptx` round-trip — the hard part, and the thing most OSS converters get wrong
- `genoffice` CLI + first-class skills for multiple coding agents, not just a GUI
- Apache 2.0, brings your own key or local model, with on-device conversion
- 9.9k stars, 1,256 forks, actively developed; Linux builds (deb/rpm/AppImage) exist

**Cons:**
- It is a **desktop Electron-class app first** (macOS/Windows/Linux GUI); headless CLI use is secondary and the docs don't spell out server/headless guarantees
- The demo video's own test had the local-model path time out after about a minute — bring a real hosted model or expect pain
- 2.5 months old, 76 open issues, and signing in with Genspark skips keys — a vendor account in the loop we'd rather avoid
- Our document work is already solved by python-docx/reportlab pipelines that run headless and predictably

**Should we...**
- 👀 **Watch it** — keep an eye on it, not ready yet but promising

**Impact on our stack:** Low — could eventually replace ad-hoc python-docx generation for documents that must return to Word intact (reimbursement packets, GME paperwork), but nothing today is broken.

**Why:** The byte-preserving round-trip is a real capability we don't have — when we generate a `.docx` for a Montefiore office, "Word opened it and the layout held" is not guaranteed by our current scripts. But this is a desktop application wearing a CLI, its own demo shows the local-model path stalling, and it's eight weeks old. If it grows a documented headless mode with a stable `genoffice` CLI contract, it becomes a legitimate swap for our document pipeline. Until then, watch.

### cjpais/Handy

**What it is:** A free, open-source, fully offline speech-to-text desktop app. Hold a shortcut, speak, release — Whisper (or CPU-friendly Parakeet V3) transcribes locally with Silero VAD and pastes the text into whatever field you're in. macOS, Windows, Linux.

**Source:** https://github.com/cjpais/Handy · [Provenance: spotted on Hyperautomation Labs — https://www.youtube.com/watch?v=oZ9pO17PonU]

**What's good about it:** 34k stars, MIT, active since early 2025, and genuinely local — no audio leaves the machine, models are selectable by size, and there's GPU acceleration when available. As a dictation tool it's the category leader among open-source options, with a Raycast integration and Homebrew/winget packages.

**Pros:**
- Fully offline transcription — the strongest privacy story for anyone dictating clinical-adjacent text
- Cross-platform with multiple model choices including a CPU-optimized one
- MIT, 34k stars, mature release history, third-party package manager coverage

**Cons:**
- It is a **keyboard-shortcut dictation app** — its entire value is pasting text into a focused field on a desktop. We run on a Linux VPS with no desktop and no cursor
- No CLI, no API, no server mode — nothing an agent or a cron job can call
- Requires microphone and accessibility permissions per machine
- Whisper local transcription on CPU is far slower than the hosted transcription we already use for the audiobook pipeline

**Should we...**
- ❌ **Skip it** — not relevant, redundant, low quality, or not useful for us

**Impact on our stack:** Low — there is no desktop to dictate into, and our voice/TTS work runs through the Hermes audio stack, not through keystroke injection.

**Why:** Good tool, wrong shape. Handy solves "I want to talk into my laptop instead of typing," and our stack has no laptop in the loop — the agent has a terminal, not a cursor in a text field. The one adjacent need we do have (local transcription) is already served by Whisper in the audiobook pipeline, running headless. Skip it; if Shareef ever wants offline dictation on the Windows desktop, this is the one to install — personally, not on the stack.

## Overall Assessment

Today's feed was heavy on genuinely impressive desktop software and thin on things that change how our system runs. The one item that clears the bar without argument is **Memory Wiki**, because it is first-party, write-free, and answers a question our memory files make urgent.

If we do nothing else, do these, in this order:

1) **Install `hermes-memory-wiki` and audit both memory files.** It changes us from "we hope the memory is right" to "we can see it" — and at 96% and 97% full, that visibility is the difference between pruning and silent eviction.
2) **Watch Perplexity SPACE for a plain Linux + KVM path.** A microVM per agent task with credentials held outside it is the containment model we'd want the day any of our agents touches regulated data; today the VPS can't host it, so it's a watch, not an install.
3) **Keep Chrome Relay as the desktop answer to getting blocked, not the server answer.** If a real signed-in session is ever needed, it runs on a desktop with a throwaway profile — written down now so nobody reaches for a flagged-account shortcut later.

Everything else in the feed — Scout, Handy, SolidCraft, Compositor, PureMac, and even the well-built Camoufox and GenOffice — is either a mirror, a desktop GUI, or a solution to a problem we don't have. No padding, no adoptions on star counts.
