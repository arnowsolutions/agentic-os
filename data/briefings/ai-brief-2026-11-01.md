### 1. TokenEconomizer — the three ways a coding agent burns money, made measurable

**What it is:** A Microsoft Research / UC Berkeley plugin for coding agents that leaves the model alone and cuts cost *across sessions in the same repository*. Three mechanisms: **micro-skills** (facts learned from finished sessions — "run tests with `python -m pytest` here", "this env var must be set" — injected at session start once three sessions confirm them, dropped when later sessions contradict them); **tool pruning** (a tool unused over 10 prompts across at least 2 sessions is written out of the agent's own settings file, restorable with one command); and a **loop guard** (when a turn keeps hitting the same failures, a judge model decides whether it is stuck and injects one redirect, then tells you to stop it). Apache-2.0, standard-library-only Python, state stays in `~/.tokeneconomizer`.

**Source:** https://github.com/microsoft/TokenEconomizer · paper: https://arxiv.org/abs/2610.22732 (submitted 15 Oct 2026, cs.CL) · project page: https://tokeneconomizer.github.io · Provenance: spotted on Github Awesome — https://www.youtube.com/watch?v=PeJqgL1NW0c (01:58)

**What's good about it — and I ran it.** This is not a README read:

- `git clone` → clean. Then, following the header, I created a venv and ran the suite: **`425 passed, 6 skipped in 14.99s`**, and the experiments suite separately **`393 passed, 4 skipped in 8.45s`**. That is 818 tests for a 19-day-old repo by ten contributors — the opposite of the star-promoted single-file skill repos that have dominated this feed.
- The CLI works against a real repo: `python -m tokeneconomizer.plugin.cli status` printed a proper status block for this clone, identified the repository by its git origin, and reported `microskills=off toolprune=auto loopguard=nudge`.
- The loop guard fired correctly. I loaded `SpiralState` and `is_stuck` from the cloned package and fed it a synthetic transcript modelled on our worst cron failure — 22 turns, edits to 3 files, the *same* assertion error each time. Result: `turns 44 churn 8 files 3 errout 22 stag 0.95 → IS_STUCK: True`. Then the control, a productive hard grind with a different failure each turn: `stag 0.0 → IS_STUCK: False`. It separates a doomed spiral from hard work, which is the whole ballgame for a detector that runs unattended.
- The paper's numbers are stated conservatively in the README and the README matches the abstract: 18.4–30.9% lower mean cost across five agent–model pairs, cheaper in **all 30** repository × combination cells, Pass@1 up in 4 of 5. The one cell where task success dropped is disclosed (Opus 4.8: −30.9% cost, **Pass@1 −1.0**).
- Cost accounting includes the plugin's own model calls ("its cost is included in its reports"), and it prices cached re-reads, which is where coding-agent bills actually go.
- Every action is reversible by design: contradicted facts drop, pruned tools come back, and the loop guard **never stops a turn itself** — it tells you to press Esc.

**Pros:**
- Real tests, real team, real paper: Apache-2.0, Microsoft-owned org, ten contributors, 66 commits in the last three weeks with active external PRs (Windows path handling, MCP side-calls, opencode console fixes).
- It needs **no API key of its own** and "never handles credentials" — it routes its judge/proposer calls through your existing agent login, which matters enormously for us (see the Montefiore rule).
- Tool pruning writes only its own entries into `.claude/settings.local.json`, keeps that file out of git via `.git/info/exclude`, and refuses to edit a file it cannot edit safely rather than half-writing it.
- The loop-guard heuristic is useful to us **outside** Claude Code: `SpiralState.update(tool, args, result)` folds a tool-call stream, and `is_stuck` is 15 lines of readable thresholds.
- Honest about failure modes: it publishes its "before" numbers in the lossless-memory sibling and here it publishes the one combination where success got worse.

**Cons:**
- **It cannot run in our Hermes stack as-is.** It is a plugin for Claude Code, Codex, Copilot CLI or Pi. There is no Hermes adapter, and the harness hooks it depends on (session-start context injection, deny-list writes, per-turn interception) do not exist in our agent. Adopting it means adopting it *on the desktop's Claude Code*, not in the VPS cron fleet.
- The README says "no API key of its own" but the plugin still spends model turns: the judge and the redirect writer are extra model calls on your plan. Micro-skills ships **off by default** because "how much it saves depends on the repository" — the 18–30% headline includes a mechanism the default install does not turn on.
- Version pinning is brutal: supported Claude Code is **2.1.300 to 2.1.310**. This box runs **2.1.202**, below the floor, so the plugin would refuse to work here today even if I completed the install. Every agent upgrade is a re-check.
- The loop guard in **headless** runs (which is how cron works) cannot stop anything: "In a headless run nobody may be watching, so a flagged turn runs until it ends or reaches the agent's own limits." The redirect needs an interactive Esc.
- Tool pruning is a no-op on Pi and on opencode, and on Copilot CLI it removes **whole MCP servers**, not individual tools — coarser than it sounds.

**Should we...**
- ✅ **Adopt it** — install it on the desktop's Claude Code for code work; lift the loop-guard heuristic into the cron watchdog.

**Impact on our stack:** High — two systems. (1) **Desktop coding agent:** micro-skills + tool pruning on the repos we work in repeatedly (Unified Platform, interview portal, arnow-solutions-site) cuts the recurring rediscovery cost on every session. (2) **Hermes cron:** the `SpiralState` / `is_stuck` pair is a drop-in heuristic for "this cron job has edited the same file six times and hit the same traceback six times — page Shareef instead of burning the rest of the budget." That is a concrete change to the watchdog layer, and it costs about forty lines.

**Why:** Our cost problem is not per-request pricing, it is per-repository repetition and unattended looping — the two things this plugin is built around, and the two things I could verify today. I ran the tests, ran the CLI, and proved the detector fires on a failure pattern we actually produce. What I could not do is install it into this box's Claude Code, because the local CLI is one minor version below its supported floor; that is a desktop task for Shareef, and it is a thirty-minute install, not a project. The cron half is the part worth doing this week: take the guard's decision function, feed it the tail of each cron run's tool calls, and let it post to Telegram when a job is spinning instead of letting it spend the remaining budget on the same error. Adopt the tool where it belongs, steal the algorithm where it does not fit.

### 2. Skills for Real Engineers — 27 procedures, of which we need three

**What it is:** Matt Pocock's `.agents` directory published as a Claude Code plugin (`mattpocock-skills`, marketplace `mattpocock`) and as a plain skills directory installable with `npx skills add mattpocock/skills`. Twenty-seven shipped skills plus twelve marked `in-progress`: an engineering chain (`to-spec` → `to-tickets` → `implement` → `tdd` → `code-review` → `pr`), design/domain skills (`codebase-design`, `domain-modeling`, `improve-codebase-architecture`, `prototype`), issue triage as a state machine (`triage`), and productivity skills (`handoff`, `grilling`, `teach`, `writing-for-agents`, `wait-what`). MIT.

**Source:** https://github.com/mattpocock/skills · site: https://www.aihero.dev/skills · Provenance: spotted on ManuAGI — https://www.youtube.com/watch?v=jbaJP2RSQCU (01:41)

**What's good about it — and I installed it.** I cloned the repo, added it as a marketplace (`claude plugin marketplace add ./` → "Successfully added marketplace: mattpocock"), and ran `claude plugin install mattpocock-skills@mattpocock` → **"✔ Successfully installed plugin: mattpocock-skills@mattpocock (scope: user)"**, landing `mattpocock-skills/1.3.2` at commit `4ae2317` in `~/.claude/plugins/cache/` with all 27 skill directories present. I then uninstalled it cleanly (`installed_plugins.json` back to `{"plugins": {}}`) so this box is not left with an experiment attached to it. Also worth recording: the README's headline install line `claude plugin install mattpocock-skills@claude-plugins-official` **fails** on a fresh CLI — "Plugin not found in marketplace" — because no marketplaces are configured until you add one. The marketplace route works.

What makes the library good is that the skills are *procedures with exit conditions*, not prompts. `to-tickets` explodes a spec into "tracer-bullet vertical slices, each declaring the tickets that block it". `code-review` runs two axes — Standards (does the code follow *this repo's* documented standards) and Spec (does it implement what the issue asked) — in parallel sub-agents so neither pollutes the other's context, and its own docs say **"the repo always overrides"** and the smell baseline is only labelled heuristics. `writing-for-agents` is a reference on how to write anything an agent consumes, which is directly applicable to our own skill authoring.

**Pros:**
- Mature and maintained: MIT, ~309k stars, 374 changelog lines, and the 1.3.2 release fixed real self-inflicted bugs (sub-agents fanning out into 50+ agents; `ask-matt` recommending steps from one-line summaries without reading the SKILL.md).
- `to-tickets` and `handoff` scratch our actual itch: turning a Shareef decision into an ordered work list, and compacting a long session into a document the next one can resume — the thing I do by hand every time a redesign verdict comes back.
- Small composable units by design ("refuse to own your process") — you can take three and leave twenty-four.
- The repo documents its own failures, including the code-review skill's known collision with Claude Code's built-in `/code-review` and the sub-agent fan-out bug.

**Cons:**
- **Context cost is the real price.** Every installed skill's frontmatter sits in the agent's context on every turn; 39 SKILL.md files total ~177 KB on disk and the top five alone are 12.5 KB, 12.4 KB and 10.9 KB. Installing all 27 is a known way to make a session slower and duller — the honest move is three.
- The most interesting skills are in `in-progress` and are not shipped in the plugin: `chief-of-staff`, `software-factory`, `claude-handoff`, `loop-me`.
- `code-review` collides with the harness's built-in of the same name; the README says the fix depends on install method and the sub-agent fan-out bug is **not shipped fixed** ("one report reached more than 50 agents"). Unattended use is exactly where that hurts.
- `claude-handoff` is hard-wired to `claude --bg`, so it is useless outside Claude Code — no Codex or Hermes path.
- Six days ago it was a 39-skill repo with a different install story; the README's headline command is already stale in the wild, which is a maintenance smell for a library publishing this fast.

**Should we...**
- ✅ **Adopt it** — but as three skills (`to-tickets`, `handoff`, `writing-for-agents`), copied into our own skill tree rather than installed as a 27-skill plugin.

**Impact on our stack:** High — **agentic-os** and the skill-authoring layer. `writing-for-agents` is a reference we would otherwise keep rewriting by hand for every new Hermes skill; `to-tickets` converts a Shareef decision (the redesign verdicts, the capstone emails) into an ordered, blocking-aware work list instead of a chat transcript; `handoff` is the missing piece for long background agents that die mid-job.

**Why:** The skills are the highest-quality agent procedures in this feed, and I confirmed they install. But installing the library whole is the mistake the same community made last week and then walked back ("I deleted most of my Claude skills last week; maxed out Claude with skills and got slow and incoherent"). Our skills run inside Hermes, not Claude Code, so the marketplace route does not even apply — what transfers is the *writing*: the two-axis review, the tracer-bullet ticket format, and the "how to write a document an agent consumes" reference. Copy those three, credit the source, and skip the other 24.

### 3. Lightpanda — a browser built for machines, and the bot wall it cannot pass

**What it is:** A headless browser written from scratch in Zig — not a Chromium fork, not WebKit — with no graphical rendering engine, V8 for JavaScript (15.5.35.13), a CDP server that Puppeteer and Playwright can connect to, and a built-in `fetch` subcommand that dumps a page as `markdown`, `html`, `pdf`, `png`, `structured_data` (JSON-LD/OpenGraph) or WPT results. 1.0 shipped Oct 2 (the 1.0.2 point release is Oct 23). AGPL-3.0.

**Source:** https://github.com/lightpanda-io/browser · https://lightpanda.io · Provenance: spotted on ManuAGI — https://www.youtube.com/watch?v=jbaJP2RSQCU (02:24)

**What's good about it — and I ran the binary.** I downloaded the 1.0.2 `x86_64-linux` release (76 MB), ran `version` → `1.0.2`, then bench-timed it against `curl` on pages we own:

- `https://www.montefiore.org/` — Lightpanda **0.95s**, 19,552 chars of markdown, exit 0. `curl` **0.17s** but 324,595 chars of raw HTML.
- `https://montefioreeinstein.org/education` — Lightpanda **0.61s**, 16,202 chars of markdown, exit 0.
- `https://www.reddit.com/r/LocalLLaMA/` — Lightpanda **0.12s**, 87,894 chars of *rendered text*; plain `curl` got **1,522 chars** of "you've been blocked". That is the case for a real JavaScript engine in one line.

It also handled pages where a headless session would normally get stuck: LinkedIn returned a sign-in form (836 chars, no data leak), X returned a login wall, MyChart returned its public landing page. Every one of those is the *right* failure for a scraper with no session — it does not carry credentials, so it cannot leak them.

**Pros:**
- Real markdown output out of the box (`--dump markdown`), plus `--dump structured_data` for JSON-LD/OpenGraph — that is the exact shape our cron scripts want and currently get by regexing HTML.
- Fast and tiny on paper and in fact: the README's benchmark (933 pages, AWS m5.large) is 123 MB peak vs 2 GB for headless Chrome, 5s vs 46s; my own single-page timings are sub-second.
- CDP-compatible, so existing Puppeteer/Playwright scripts point at `ws://127.0.0.1:9222` and keep working; Docker image available for amd64 and arm64.
- Ships `--obey-robots` and `--block-private-networks` (the 1.0.2 notes add CGNAT, multicast and NAT64 ranges to the block list), i.e. the polite defaults are built in rather than bolted on.

**Cons:**
- **It hits bot walls exactly like a headless browser, because it is one.** `moovitapp.com` returned `BotChallenge` in 0.1s (AWS WAF challenging `robots.txt` itself), and `reddit.com` under `--obey-robots` returned `RobotsBlocked`. Anything that matters on the modern web — search engines, ticketing, hospital portals, social caption sources — will challenge it. That is not a Lightpanda bug; it is the ceiling on the whole category, and it is why the honest verdict is watch.
- GitHub was the slow one: a `--wait-selector .issue` fetch of the TokenEconomizer issues page **timed out** after rendering the nav. GitHub issues are exactly the kind of page our automation reads.
- **AGPL-3.0.** The API sidebar and the `LICENSE` file agree (both AGPL-3.0), so there is no badge mismatch here — but AGPL on a browser we would run as a service inside the Unified Platform is a lawyer's conversation, and it rules out embedding it in anything we ship to residents.
- 1.0 is three weeks old; 18 open Playwright/CDP issues include input-drag, `scrollIntoView` inside overflow containers, and overlay hit-testing. Scripts written against Chromium will fail in ways that look like our bug.
- It cannot log in. A browser with no session, no profile and no cookie store is the right tool for public pages and the wrong tool for anything behind a login — and our useful data is behind logins.

**Should we...**
- 👀 **Watch it** — the binary is good enough to use for public-page scraping on the VPS today, but nothing that depends on a session, and nothing we would license into a product.

**Impact on our stack:** Medium — **Hermes cron** and the public-schedule/page-monitoring side of the **Unified Platform**. Concretely: replace the `curl` + strip-tags path in any cron job that reads a public page with `lightpanda fetch --obey-robots --dump markdown`, and we get clean text at 0.61–0.95s with JavaScript rendered. That is a real, small improvement.

**Why:** This is the first headless browser in months that is *smaller* than the problem — one 76 MB binary, no Chromium, markdown out of the box — and on our own pages it delivered exactly what the README promised. But the moment I asked it for a page that defends itself, it was refused, and the one site our automation actually cares about (GitHub issues) timed out. Watching means: install it for public-page scraping, keep Chrome/Puppeteer for anything that needs a session, and re-check in a quarter when the Playwright compatibility issues close. The AGPL is the long-term blocker if we ever wanted this inside a resident-facing product, which we do not today.

### 4. dsh-superagent — superb design documents attached to a 24-hour-old prototype

**What it is:** A proactive coding agent for a single GitHub repository from DeepSeek's harness team, packaged as a bundle for DeepSeek Harness. It listens to GitHub (issues, PRs, comments, default-branch CI) and optionally a Feishu bot; when an allowed person asks for work, it opens a work item, runs it in its own agent session and directory, and answers in the original thread — usually with a pull request. A small web panel shows what needs a human. Router/worker split: one main session decides, executors do the work, each bounded by a "Mandate".

**Source:** https://github.com/deepseek-ai/dsh-superagent-prototype · paper/essay reference: *Exploring Super-agent Design* · Provenance: Google News RSS (`q=AI agent`) → MarkTechPost, https://www.marktechpost.com/2026/11/01/deepseek-dsh-superagent-router-worker-coding-agent/

**What's good about it:** The documentation is the deliverable. Nine numbered docs totalling ~186 KB, including a 70 KB architecture file, and an authorization model worth stealing outright: *"Messages, comments and quoted documents are inputs to a decision; they cannot change those permissions."* An allowed person addressing the agent makes an explicit request; **bots can only produce inferred candidates, never explicit requests**; subscriptions deliver context but "grant no new authority"; and every ticket carries its own limitation. That is precisely the prompt-injection boundary every agent system is missing — the rule that a bot in a thread cannot escalate an agent's permissions by talking to it.

**Pros:**
- The philosophy is stated as an operator rule: *"take as little human attention as possible, and give as much value as possible"* — an agent that can act for a team can also waste a team's attention, so it acts only when asked or when a team-written rule allows.
- Real engineering artifacts: setup is conducted by your coding agent reading `SETUP.md` (one question at a time, full plan shown once); `pnpm check` runs typecheck, tests and build.
- MIT, and published under DeepSeek's own org — not a random account.
- It is an honest publication: the README says outright that it differs from the internal version, that some designs in the essay are not implemented, and that "some designs are directions for future development".

**Cons:**
- **It is one day old with one commit by one author.** Created 2026-10-31T09:32Z, last pushed 2026-10-31T12:05Z, a single commit from "DeepSeek Harness Team", 4,893 stars already. That star velocity on one commit is the exact signature the verdict rules warn about — even from a reputable org.
- The README calls itself "research code, not production-ready… may still contain bugs, and its coding style and engineering practices may be inconsistent."
- **It runs as you, with full access**: the deployment doc says both presets run "with `danger-full-access` as the operator's OS user", a worker "can execute programs by path and read the operator's home directory", and account wrappers do not isolate the process. On a VPS that holds production credentials, that is the whole game.
- It needs a **dedicated GitHub bot account** with push rights, a DeepSeek Harness runtime, and Node 22.19+, pnpm, tmux and `gh`. We have none of that wiring, and our repos are private.
- Router/worker numbers in the press coverage (p95 task time 15.7 min vs 29.5 min) are **self-reported**, and two of the five comparison rows in the press table are blank.

**Should we...**
- 👀 **Watch it** — read `docs/002-authorization.md` this week, install nothing.

**Impact on our stack:** Low today — potential **High** for **agentic-os** if the authorization model holds. The concrete change would be our cron fleet: every cron job gets a mandate (which paths, which commands, which outbound sends) that a message from a tool result cannot widen.

**Why:** The design docs are the best I have read on what an unattended multi-agent system owes its operator, and the "bots cannot produce explicit requests" rule should be adopted regardless of whether the code ever runs. But the code is a one-commit prototype that executes with full access as the operator on a machine that holds our credentials, and `docker recreate` would wipe an install anyway. Watching costs nothing; adopting a day-old `danger-full-access` agent costs the thing we cannot get back.

**Cons:**
- No artifact to install; nothing changes on our side today.
- Press coverage of the Pentagon incident varies in detail between outlets; treat the specifics as unverified.

**Should we...**
- ❌ **Skip it** — no installable artifact; filed only so today's brief has its context.

**Impact on our stack:** Low — context for a decision already made.

**Why:** These are the stories that explain why four of today's five verdicts are about *where* a thing runs rather than what it does. Filing them keeps the record honest: the industry's best new agent designs and its worst agent incident shipped in the same week, and the difference was permissions, not intelligence.
