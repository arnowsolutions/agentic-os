### 1. single-agent-loop-kit — Anthropic's migration kit for folding subagents into one agent loop

**What it is:** An Apache-2.0 "starter kit" published by Anthropic on Oct 15 alongside the Oct 22 article *Building agents: When to fold subagents into your main agent loop*. It ships a Claude Code skill that audits an existing multi-agent system and gives every subagent a verdict — **fold, merge, call as a tool, or keep** — plus three small Python scripts that do the measuring: `coupling_map.py` (from a trace export, which subagents carry the traffic and which always run together), `compare.py` (two eval runs side by side on task completion, latency, model calls, tokens, cost) and `chain_coverage.py` (checks your eval has a task for every subagent chain production actually uses). There is also `reference_loop/loop.py`, a ~readable single loop with parallel tool batches, on-demand skills, tool search, turn/cost budgets, a write gate and an optional verifier.

**Source:** https://github.com/anthropics/single-agent-loop-kit · article: https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop · Provenance: spotted on Hyperautomation Labs — https://www.youtube.com/watch?v=uparH_lHHyU (which cites the kit as the source of its "29% faster / 24% fewer model calls" numbers).

**What's good about it:** The kit's own claim is narrow and honest, and that is what makes it worth reading: *a single agent with skills frequently outperformed both the one-prompt-for-everything design and the subagent design on quality, often at lower cost and latency per task.* The part that actually matters to us is the failure story it tells. Anthropic folded one subagent into another on a sample support agent, latency dropped — and a process that used to pass broke, because the main agent now held the order-lookup tool and answered the delivery date itself instead of asking the shipping specialist. The break showed up in **one run out of two**. That is the exact class of silent regression our cron briefs are exposed to: a daily job that keeps producing a report, slightly worse, with no error. `compare.py`'s insistence on per-task flips rather than the average score is the discipline we currently lack.

**Pros:**
- The three scripts are framework-agnostic and read a trace export — they do not require us to be on Claude Code, and `KIT_MODEL=fake python3 evals/run_eval.py` gives a free, no-API-key plumbing check on the bundled example.
- `chain_coverage.py` encodes a rule we should already be following: every chain of agents that runs together in production needs a task in the eval, or a dropped handoff goes unnoticed.
- The skill stops at fixed checkpoints (after the audit, before any paid run with a token estimate, after baseline, after each change), which is the right shape for anything that spends money on our behalf.
- `reference_loop/loop.py` is genuinely readable and encodes the constraint set we care about: turn/cost budgets, a write gate on any writing tool, capped tool-call batches, and an answer withheld if the verifier rejects it twice.
- Apache-2.0, and the README states plainly what has *not* been run on a real model (the merge and upkeep steps, the finished single-loop version of the example, starting from a repo with no eval, and the kit on any system other than its own example).

**Cons:**
- **One commit, one author (`msegner-bot`), 225 stars.** Last commit Oct 21. "Reference implementation. Not maintained and not accepting contributions" — issues and PRs are not monitored. This is a document with code attached, not a dependency.
- It is written for Claude Code: the steps hand off to `/claude-api build-eval`, `/claude-api hillclimb`, `/skill-creator` and `/skill-doctor`. We run Hermes, so roughly half the workflow does not exist for us without substitution.
- The article's headline numbers (29% faster, 24% fewer model calls) come from Anthropic's recorded run on a mock support-desk system, not from any deployed system — and the kit's own README says its wording changed after the two recorded runs, with no session yet following the reworded steps.
- Adopting it means restructuring how our cron pipeline works, which is a real project with a real blast radius, on the strength of a two-week-old repo maintained by nobody.

**Should we...**
- 👀 **Watch it**

**Impact on our stack:** Medium-High — the `chain_coverage.py` + `compare.py` idea applies directly to the Hermes cron fleet (daily brief, weekly recap, health watchdogs): today a broken job looks identical to a working job until someone reads the output.

**Why:** Our cron fleet is quietly the closest thing we have to a multi-agent system — a fetch script hands structured context to a long prompt, which then decides what to file, what to email and what to skip, and every handoff is a summary. That is the "telephone game" Anthropic describes, and our own failures have been exactly of this kind: a provenance rule silently dropped, a write that never happened, a vault read that 401'd and was worked around instead of reported. The useful move is not to adopt a Claude Code skill we cannot run; it is to steal two habits from it this week — write ten golden tasks for this brief (a day where a video names a repo, a day where the vault is unreachable, a day where nothing is new) and, when anything changes in the pipeline, compare the *task-level* flips and not the average. Watch the kit for a Hermes-shaped port; in the meantime read `reference_loop/loop.py`, which is the part most likely to outlive the kit.

### 2. agents-contract — an `AGENTS.md` contract with a linter that keeps it honest

**What it is:** A template `AGENTS.md` (and a one-line `CLAUDE.md` that imports it) plus `scripts/agents_lint.py`, a zero-dependency Python 3.9+ linter that enforces five required sections — Project, Commands (with a mandatory test command), Conventions, Boundaries, Definition of Done — and errors on leftover placeholders, missing import targets, and **credential-shaped strings** (AWS, GitHub, OpenAI/Anthropic, Slack, Google, private keys). It also ships a SessionStart hook that runs lint + tests before an agent starts work, so the agent knows whether the tree was green before it touched anything.

**Source:** https://github.com/AntoGA/agents-contract · Provenance: GitHub Search API (repos created since 2026-10-19, AI-agent query); not named in any video this run.

**What's good about it:** The lint rules are the interesting part, not the template. E040 (no secret-shaped strings, including inside HTML comments) is a guardrail against the exact thing that went wrong in this very job — credential material reaching a place where it gets printed. W022 (`--check-commands`) verifies that commands named in the contract actually exist on `PATH`. W050 checks that paths in backticks exist in the repo. W101 warns above 32 KiB because Codex truncates instructions at that size. `--json` output and exit codes 0/1/2 make it CI-able in one line. The author also publishes an A/B benchmark with its own limitations stated: same task, 5 runs with and without the contract, agent steps down 32% (5.6 → 3.8) and median time down 29% (18.2s → 12.9s), with the honest caveat that a strong model already handled the toy repo and the only *quality* gain was on the rule that can't be inferred from code (writing to CHANGELOG).

**Pros:**
- Single-file, stdlib-only linter — the kind of thing that fits a cron wrapper or a pre-commit hook without adding a dependency tree.
- `--check-commands` and `--json` are the two flags that make it useful in automation rather than as advice.
- Explicitly vendor-neutral Markdown under git, with the `CLAUDE.md` → `@AGENTS.md` import pattern spelled out.
- 15 unit tests and a CI workflow that runs on Ubuntu, Windows and macOS — unusual rigor for a repo this new.

**Cons:**
- **Every document is in Russian.** The linter tolerates English headings, but the templates and the "How to read this honestly" benchmark section are not readable to anyone on our team who doesn't read Russian — that is a real adoption tax, not a nitpick.
- **One author (`Byerror`), created Oct 19, `pushed_at` still Oct 19.** No commits after day one, no issue activity. New-repo promotion smell until it shows maintenance.
- The A/B numbers are 5 runs on one toy repo with one model (Claude Code headless), and the author says so — they are not evidence of anything at our scale.
- The SessionStart hook is Claude Code-specific; on Hermes we'd wire the same command into our own run wrapper, which is more work than the README implies.
- Boundary section "Don'ts" is prose the linter can check for *presence*, not compliance — it does not enforce that the agent obeyed.

**Should we...**
- 👀 **Watch it**

**Impact on our stack:** Medium — a `HERMES.md`/`AGENTS.md` contract for the agentic-os workspace with a linter in the cron wrapper would catch placeholder and credential-shaped strings before they reach a report.

**Why:** We already run an informal version of this — memory entries, the "never do X" rules, the brand/Call-Out rename invariants — and we enforce all of it by hoping the model read the right section. A linter that fails loudly on a leftover `<...>`, a stale command, or an API-key-shaped string is cheap insurance for a system whose mistakes ship to a director's inbox. But I am not adopting a two-week-old, single-author, Russian-language repo as infrastructure today; the correct move is to read its rule list, copy the four checks that apply (sections present, no placeholders, commands exist, no secret shapes) into our own cron wrapper, and watch whether the author keeps committing. If it's still alive in a month with an English README, adopt it properly.

### 3. SPACE — Perplexity's sandbox platform for agent code execution

**What it is:** SPACE (Sandboxed Platform for Agentic Code Execution) is open source from Perplexity under Apache-2.0: a Rust service that hands out isolated **Firecracker microVMs** over an HTTP API. You create a sandbox from a template, open command sessions, stream output over a data-plane connection with a session-scoped token, then keep, pause, suspend or delete it. It includes warm pools (pre-booted sandboxes so creates skip cold boot), base snapshots, egress profiles, observability and an E2B-compatibility wrapper so the E2B Python SDK works against it.

**Source:** https://github.com/perplexityai/SPACE · guide: https://space.docs.perplexity.ai/guide/index.html · Provenance: spotted on ManuAGI — https://www.youtube.com/watch?v=zRl3UzA2G6A (listed as "SPACE").

**What's good about it:** This is the serious, maintained version of a thing we keep circling. 1,967 stars, created Oct 1, pushed today, **18 contributors from Perplexity** (`-pplx` handles), Apache-2.0 with a docs site that updates on merge. The API surface is the right shape for a cron fleet: asynchronous lifecycle with operation IDs to poll, a separate data-plane connection for command output, and pause/suspend semantics that mean a long-running job can be frozen instead of rebuilt. Warm pools and base snapshots are the two features that separate a usable agent sandbox from an academic one — cold-boot cost is what usually kills this pattern in practice.

**Pros:**
- Firecracker microVMs, not containers — a real security boundary between agent-generated code and the host, which is the entire point.
- Warm pools + base snapshots address the practical killer (boot latency) that most sandbox projects ignore.
- E2B-compatible wrapper means we are not locked into a bespoke API if we ever change our mind.
- 18 contributors, active pushes, hosted docs, and a reference EKS deployment applied on a schedule — this reads like infrastructure Perplexity actually runs, not a demo.
- The HTTP/SSE interface means our Python cron scripts can drive it without a Rust toolchain.

**Cons:**
- **It wants Kubernetes.** Installation is documented as a local Kind cluster with Tilt, and the architecture doc says it *can* run without Kubernetes but that is the unexplored path. We do not run a cluster; standing one up on the VPS to isolate cron jobs is a large, speculative infrastructure project.
- Firecracker needs KVM. Our VPS is a container host; whether `/dev/kvm` is exposed is an open question that decides this item's fate entirely.
- It solves a problem we have already solved more cheaply: our jobs run inside the Hermes container, which is not a hostile-code sandbox but is a real boundary, and `execute_code` is already blocked in cron mode. The remaining exposure is narrower than SPACE's target use case.
- New (Oct 1), 157 open issues, and "incubating" API operations (snapshots, checkpoint, rollback) that answer as if they don't exist unless your org enables them — the feature list is flatter than the README reads.
- No managed offering documented; running it means we own the cluster, the templates and the operations.

**Should we...**
- 👀 **Watch it**

**Impact on our stack:** Medium — it is the credible upgrade path if we ever need to run untrusted agent-generated code (client scrape workers, third-party repos from these briefs) on our own metal, beyond what the container gives us.

**Why:** Today our threat model is thin and mostly accidental: nothing in our pipelines runs genuinely hostile code, because we run our own scripts on our own data. SPACE becomes relevant the moment we want to *actually execute* something we found — clone a repo from one of these briefs and see if it works — without handing it our Postgres bridge or our `.vault.env`. That is a real future need; it is not today's. The blocker is concrete and checkable: Firecracker needs KVM and the documented install path needs a Kind cluster we don't have. So: watch, and if a genuine "run this unknown repo safely" need shows up, first test whether `/dev/kvm` is available on the VPS — that one command decides whether SPACE is a candidate or a dead end for us.

### 4. ContextCraft — fit a whole repository into a fixed token budget, on purpose

**What it is:** A Python CLI/SDK that packs a codebase for an LLM in a token budget instead of concatenating everything alphabetically. It parses 35 languages with Tree-sitter, resolves cross-file imports and scopes, ranks architectural centrality with Personalized PageRank + BM25F, then solves a multiple-choice knapsack across four AST fidelity tiers (FULL, SKEL, SIGS, TREE) to maximise signal inside the budget you set. On PyPI as `contextcraft-ai`; runnable via `uvx contextcraft-ai . --budget 8k --focus "..."`; emits Markdown or Claude-shaped XML; has an analysis-once/render-many snapshot API.

**Source:** https://github.com/khanhtq29vn/contextcraft · PyPI: https://pypi.org/project/contextcraft-ai/ · Provenance: GitHub Search API (LLM repos created since 2026-10-19); not named in any video this run.

**What's good about it:** The diagnosis is correct and specific: `repomix`, `gitingest` and `code2prompt` "blindly concatenate every file verbatim" and on real repos either blow the budget or, when truncated, drop most of the architecture. Nearly every time we have pointed an agent at one of our own codebases — the Unified Platform, the interview portal — we have either pasted too much and watched quality collapse in the middle, or pasted too little and watched it invent interfaces. The `--focus` flag biasing PageRank toward the task, plus a strict token budget, is the missing control.

**Pros:**
- `uvx contextcraft-ai . --budget 8k` is a one-liner with no install step — testable in a minute.
- The snapshot API (`analyze()` once, `render()` many times at different budgets/formats) means we can produce a 4k and a 32k view of the same repo without re-parsing.
- Token accounting is explicit (`cl100k_base` default, `o200k_base` for GPT/o3), which is the difference between "roughly fits" and "actually fits".
- CI, mypy-strict typing, ruff, a real PyPI release, and 5 contributors including a bot — more engineering discipline than most repos in this age bracket.
- The "URL swap trick" web playground can compress any public GitHub repo by path, which is useful for evaluating a brief item before cloning it.

**Cons:**
- **Six days old (created Oct 22), 54 stars, 5 contributors, 8 open issues.** No independent evidence that the knapsack ranking beats a good `--include` glob list.
- It reads **your whole repository** — including whatever `.env` and credentials files it finds. README mentions sanitisation, but shipping our Unified Platform source (with Supabase keys in env files) through a tool this young is a risk I would not take on the VPS.
- The value depends on the ranking heuristic matching what the model actually needs; a wrong rank silently hides the one file that mattered, and there is no "why wasn't this included" report mentioned.
- Python 3.10+ and a Tree-sitter dependency set — it will not drop cleanly into the cron interpreter without checking imports first (a failure mode we already know about).

**Should we...**
- 👀 **Watch it**

**Impact on our stack:** Medium — evaluated on the desktop against a sanitised copy of a Unified Platform module, it could cut the context we hand to Hermes for code work by a large factor, but it must never run against the live checkout.

**Why:** The problem is real and recurring: when we ask an agent to change something in the Unified Platform, we either hand it three files and hope, or hand it a merge-conflict-sized blob and watch reasoning degrade. ContextCraft is aimed exactly at that. But the risk profile says desktop, not VPS: point it at a copy of a repo with secrets stripped, run it at 8k and 16k, and diff what it chose against the files we know matter. If the selection is sane twice, it becomes a step in our code-review workflow. Until then it is a promising answer to a real question, from a repo too young to trust with our source tree.

### 5. Hy Memory / MemHub — Tencent's dual-system memory engine for agents

**What it is:** A Python SDK (`pip install hy-memory==2.0.4`) plus a local-first desktop/CLI product, MemHub, that unifies conversation history and coding traces from Claude Code, Cursor, Codex, OpenCode and Qwen Code into one governed local store. The engine is an 8-layer cognitive memory hierarchy for chat (raw dialogues → atomic facts → summaries → schemas → prospective intentions, with conflict reconciliation), a two-layer fact + reusable-experience memory for working tasks, and a version-evolution diff-chain for coding. There is a 30B-A3B MoE model on Hugging Face trained via attributed RL specifically for memory writing, with an EMNLP 2026 paper and an ICLR 2027 submission beside it.

**Source:** https://github.com/Tencent-Hunyuan/Hy-Memory · model: https://huggingface.co/tencent/Hy-Memory-30B-A3B · Provenance: spotted on ManuAGI — https://www.youtube.com/watch?v=hdc-Tvj6auM (listed as "Hy-Memory").

**What's good about it:** Of everything in this brief, this has the deepest research spine: an accepted EMNLP 2026 paper, an ICLR 2027 submission, a technical report for the memory-writing model, and a benchmark (CMB) built specifically for long-horizon coding memory. The productisation is real too — a signed macOS desktop app, a CLI on npm, FP8 and GGUF model releases, and a documented "any OpenAI-compatible endpoint" configuration path. 1,304 stars, 6 contributors, pushed today.

**Pros:**
- Conflict reconciliation is a first-class concept, not an afterthought — the exact thing our memory currently does by silently overwriting.
- The coding-memory mode's "version-evolution diff-chain" addresses a failure we have lived through: the agent forgets which revision of a thing it was working on and reverts intent.
- Works against any OpenAI-compatible LLM + embedding endpoint, so we are not forced onto Tencent's model.
- MemHub as a local-first aggregator across several coding agents is directly relevant — we run Hermes alongside Claude Code.
- Published benchmarks (CMB) mean the claims can be checked rather than taken on faith.

**Cons:**
- **It wants a second LLM and an embedding provider**, on top of the model Hermes already uses — a new API key, a new cost line, and new failure modes in every run that touches memory.
- It duplicates a capability Hermes already has (persistent memory across sessions), and running two memory systems is how you get contradictory facts with no authority between them.
- The LICENSE file returns `NOASSERTION` on GitHub while the README badge says Apache-2.0 — a licence mismatch is a real blocker for anything we'd ship internally, not a detail.
- 61 open issues on a repo two weeks old, and the heavy mode (`pro`/`ultra`) is where the interesting behaviour lives — `lite` "stores everything as raw memory", i.e. the dumb version.
- Wants ChromaDB/Kuzu by default, with Qdrant/FAISS/Neo4j extras — a datastore layer we'd have to own and back up.

**Should we...**
- 👀 **Watch it**

**Impact on our stack:** Medium — potentially a better memory substrate for Hermes, but it would have to displace, not supplement, the current memory system to be worth its cost.

**Why:** Our memory is a flat list of prose facts that grows until it hits a character ceiling, and the ceiling has already started costing us — this brief's own rules had to be re-derived because a memory entry pointed at a path that no longer exists. Hy Memory's hierarchical model with conflict reconciliation is the right medicine for that disease. But the medicine comes with a second model endpoint, a vector/graph datastore, and a licence question, and adopting it means deciding that Hermes' memory is replaceable. Watch for: the licence resolved to Apache-2.0 in the repo metadata, and a "no extra model required" mode. Then it becomes a real candidate rather than an interesting paper with a pip package.

### 6. RubricLoop — turn agent traces into executable rubrics and a reviewable report

**What it is:** A Python 0.1.0a2 tool (formerly AgentEval) that takes traces/message histories, applies YAML "executable rubrics" plus optional model judges through any OpenAI-compatible endpoint, and emits a standalone HTML report with JSON alongside it. Each criterion keeps its own outcome (pass / not applicable / fail / error) and the report counts them separately.

**Source:** https://github.com/kling01/RubricLoop · demo: https://kling01.github.io/RubricLoop/demo.html · Provenance: GitHub Search API (AI-agent repos created since 2026-10-19); not named in any video this run.

**What's good about it:** The report shape is genuinely good — trace, rule outcome and model judgment on the same page is what an evaluation review should look like, and it is the same "evidence next to decision" principle we use in the design-intel briefs. The offline demo needs no key (3 traces, 9 checks, 6 pass, 2 fail, 1 not applicable), so it is verifiable in two minutes.

**Pros:**
- Deterministic YAML rules for what can be stated precisely, model judges only for what can't — the correct split, and cheap to run.
- Standalone HTML report with no server, which fits our "send the evidence in the email" preference.
- Versioned criteria and evaluator versions, so a score change can be attributed.

**Cons:**
- **The rule `check` is a trusted Python expression executed locally and explicitly "not sandboxed",** and the README's mitigation is "review rule files before running them" — for a tool whose whole job is consuming files from elsewhere, that is a disqualifying default.
- **One author, created Oct 20, no commits since, 41 stars, pre-alpha version string** — the "promotion stars on a new repo" pattern we've been burned by.
- The CLI only handles trace-level runs; evaluator feedback, regression checks and the integrations are all roadmap.
- Its sibling repo and a second paper (arXiv 2610.26365) suggest a research pipeline shipping products faster than it can maintain them.

**Should we...**
- ❌ **Skip it**

**Impact on our stack:** Low — the idea (grade the brief's output against written criteria) is worth keeping; the implementation is not something we should execute on the VPS.

**Why:** I want the *concept* — a rubric for this brief that a different model can grade, with the trace attached — because our current quality control is "Shareef reads it and says this is wrong". But RubricLoop's implementation runs arbitrary Python from rule files in-process, ships pre-alpha from a single author with no commits since day one, and would put a second model endpoint into a pipeline that already has enough moving parts. Skip as software. The one thing worth stealing is the four-outcome model (pass / n/a / fail / error kept separate) — an eval that conflates "failed" with "couldn't run" is how we'd end up tuning against our own outages.
