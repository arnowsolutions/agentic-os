### safe-anything — erkamyaman/safe-anything

**What it is:** A single native binary (Rust) that scans a repository for the holes an AI agent leaves behind: SQL injection, XSS, `eval`, SSRF, path traversal and unsafe deserialization across nine languages and SQL; leaked keys and `.env` mistakes; Docker, GitHub Actions, Kubernetes, Terraform and nginx misconfiguration; every locked dependency checked against OSV.dev; and — the part that matters most to us — the agent setup itself: MCP servers, Claude Code / Codex / Cursor / Gemini / OpenCode settings, hooks and skills. 107 rules, each carrying a CWE id and an OWASP category. It ships as a CLI, a GitHub Action, an MCP server and a `SKILL.md`.

**Source:** https://github.com/erkamyaman/safe-anything  ·  https://www.npmjs.com/package/safe-anything (v1.1.0)  ·  Provenance: GitHub search (new repos, last 7 days, sorted by stars); 808★, 89 forks, 25 contributors, MIT, created November 22, pushed November 27.

**What's good about it:** It is the only tool today that treats the agent as part of the attack surface. Every other scanner looks at your application; this one also reads `.mcp.json`, the hooks file, the skills folder and the workflow YAML, and reports the exact things we have had to reason about by hand — a token in an MCP config, a `curl | sh` in a hook, a skill that reads `~/.ssh`, invisible Unicode in a rules file, unpinned MCP servers. The engineering is disciplined for a five-day-old project: one parallel walk using the `ignore` crate, one read per file, compiled regexes, **nothing executed**, and the only network call sends package names and versions to OSV.dev (with `--offline` to skip even that). The README publishes its own false positives — a run on Juice Shop found 67 issues in 0.03 s with two or three false positives, Flask produced two findings that are both false in practice, and the noisiest rule (`code.xss-inner-html`) is named as noisy rather than hidden. It also states the limit plainly: "it does not trace data through your program. A clean scan means none of these 107 problems were found, not that the code is safe."

**Pros:**
- Covers three surfaces in one pass — application code, secrets/config, and the agent scaffolding — which today are three separate manual reviews or nothing at all.
- Read-only by construction: no code execution, no upload, dependency checks are package names and versions only, `--offline` available, and findings are redacted.
- Fast enough to run on every commit in practice: 0.03–0.13 s on repos of 200–1,200 files, with a documented clean result on `express` (216 files, zero findings) to show it can stay quiet.
- Native binaries for macOS, Linux and Windows, published to both crates.io and npm, so it runs on the VPS, the Windows desktop, or as `npx safe-anything .` with no toolchain.
- MCP server mode with two tools (`scan`, `list_rules`) plus a bundled skill — small enough to mount in Hermes without the 20-tool context tax that made us cautious about pocket-design-mcp.
- A real CI story already: GitHub Action `@v1.1.0` with `fail-on: high`, a baseline file for existing findings, and SARIF output that lands in the Security tab.
- The rule set is sourced rather than invented — OWASP Top 10 and LLM Top 10, MASVS, CWE ids, OSV advisories — so a finding can be argued with.

**Cons:**
- **Five days old, 808 stars, 25 contributors in five days.** That is a launch, not a track record, and the contributor burst looks like a coordinated push. Nothing here has been reviewed by anyone outside the project.
- Pattern matching, not data-flow analysis — the README says so. On a React codebase the `innerHTML` rule will fire on template strings that are not attacker-reachable, and the fix is a judgement call, not a patch.
- The agent-config scanning is written for Claude Code, Codex, Cursor, Gemini and OpenCode paths. Hermes' own skill and MCP layout is not in that list, so our most interesting configs may simply be skipped — we would be trusting that "no findings" means "nothing found" rather than "nothing looked at".
- Dependency coverage leans npm/PyPI/Cargo; the code rules cover nine languages, but nothing in the README measures recall on TypeScript specifically, which is most of our code.
- It is a scanner, not a fixer: every finding is a ticket, and a first run on a year-old platform can produce a pile that no one triages. The baseline file helps, but it is on us to keep it honest.
- Sponsored by CodeRabbit and distributed with a large marketing surface (badges, a sponsor link, a terminal GIF). The tool may well be good; the presentation is selling.

**Should we...**
- ✅ **Adopt it** — run it, don't wire it into a gate yet: `npx safe-anything . --offline` on the Unified Platform repo and on `~/.hermes` this week, read every finding by hand, and only add the GitHub Action with a baseline once we know the noise level on our own code.

**Impact on our stack:** High — the Unified Platform and the Agentic OS at the same time. Concretely: one scan of `/var/www/unified` (React + Node) covers the code patterns and the secrets in `.env`-adjacent files; the same command pointed at `~/.hermes` covers the MCP configs, hooks and skills that decide what our agent is allowed to do. We have had a real credential incident this year (the Montefiore IT flag in July) and a key-rotation breakage in August — both were secret-handling failures that a scanner would have flagged in the file, not at the point of use.

**Why:** The two security stories of the week are both about agents leaking or reaching what they should not: The Register's November 24 piece described an agent, a browser and a macOS tool finding a financial firm's access key in under six minutes, and NordLayer reported on November 26 that a coding agent had been sending company secrets to an outside service for weeks. Neither is a story about a brilliant attacker; both are stories about nobody scanning the setup. We run an agent with a terminal, a browser and persistent credentials, and our review process is reading the diff — which catches intent, not a token in a config file. safe-anything is cheap, local and read-only, and its agent-config rules are aimed exactly at the files that no human reads twice. The verdict is adopt rather than watch because the risk of running it is close to zero and the risk of not running it is the one we have already been burned by; the caution is in the scope, not the tool — scan, read, then decide what to gate. Do not let it near CI until we have seen what it says about our own code, because a noisy gate gets disabled and then we are back to nothing.

### AutoClip — zhouxiaoka/autoclip

**What it is:** A local-first desktop and CLI tool that turns a long video into ready-to-post short clips: it finds the highlight moments, tracks the speaker and reframes to 9:16, burns in captions, generates covers and titles, and exports for Shorts, Reels, TikTok and YouTube. Transcription and rendering run on your own machine with Whisper or SenseVoice (or Ollama / LM Studio for the language work); cloud model keys are optional. It also ships an MCP server (`uvx autoclip-mcp`) and an agent skill (`npx skills add zhouxiaoka/autoclip`), so an agent can drive it.

**Source:** https://github.com/zhouxiaoka/autoclip  ·  https://github.com/zhouxiaoka/autoclip/releases/latest  ·  Provenance: spotted on ManuAGI — https://www.youtube.com/watch?v=njoBlawECkI  ·  17,325★, 2,430 forks, MIT, created July 2025, pushed November 26.

AutoClip's whole design is that loop — import, analyse, pick the moments, reframe, caption, export — and it does it locally, so a faculty interview does not get uploaded to a SaaS to be clipped. The measured benchmark in the README is the kind of number I can plan around: a 2 h 52 m interview produced 10 clips in 29.5 minutes with local Whisper, at a stated ¥0.20 of compute. The Windows build is the one that matters for us: an `x64-setup.exe` with Python and FFmpeg bundled, so there is no toolchain to assemble on Shareef's machine. v1.6 added live-replay sources (OBS, Twitch, YouTube, Kick, Discord) and one-click re-export of a finished clip to a different platform without re-rendering.

**Pros:**

- Windows 10/11 x64 installer with bundled Python and FFmpeg; Apple Silicon `.dmg` for the Mac; Docker/web option for a server.
- MCP server and an agent skill, so the clipping loop can be driven by Hermes rather than clicked through.
- MIT, 17k stars and 2.4k forks with active commits yesterday — this is a real project with a year of releases behind it, not a launch.

- Covers and titles are generated, and the export targets are the platforms we actually post to.

**Cons:**

- 47 open issues, and the desktop app is a Tauri/React shell around a FastAPI backend — a lot of surface for a render box.

**Should we...**

**Impact on our stack:** High — the content pipeline behind the social-media program. Concretely: three test clips replace the current manual cut-caption-export loop for the 28-clip library, with speaker tracking and captions done in one pass; if the pilot holds, the render step moves from "an afternoon per clip" to "a queue", and Hermes can drive it through the MCP server while the copy desk writes the hooks and captions that the tool should not.

**Why:** The content program's constraint has never been ideas or footage — it is that every clip costs a manual pass through a video editor, and 28 of them is a project nobody has time to start. ContentSkills (November 25) was the right shape but one commit old; AutoClip is the mature version of the same idea with a year of releases, 2.4k forks and a Windows installer that does not require assembling a Python environment. The verdict is adopt because the software already exists in the form we need and the cost of trying it is three clips; the honest caveats are the unsigned installer, which is an IT question on a managed laptop, and the v1.5.9 generation bug, which is why the pilot uses the previous build and why no delivery date should be promised until three clips come out clean. The part we keep is judgement: it picks moments and burns captions; the hook, the title and the brand voice stay with us.

### Piton — tony-stark2025/piton

**What it is:** A small Python CLI (two runtime dependencies: `pydantic`, `pyyaml`) that writes a lockfile for everything an agent loads before it runs — MCP server tool descriptions and schemas, Claude/Cursor hooks, rules and skill markdown — and fails a pull request when any of them changes. It also scans for agent-config RCE: `curl | sh` and reverse shells in `.claude/settings.json` hooks, `folderOpen` autorun in `.vscode/tasks.json`, malicious STDIO MCP commands, and hidden Unicode or prompt-injection text in `.cursor/rules` and `CLAUDE.md`.

**Source:** https://github.com/tony-stark2025/piton  ·  Provenance: Show HN, November 27 (hnrss.org/show feed) — the post is titled "Piton Lockfile and static supply-chain scanner for MCP/coding agent" and links the repo  ·  MIT, created September 3, 2026, 61 commits, one author, 0★.

**What's good about it:** The split-hash idea is the right refinement of "pin your dependencies". One hash covers the machine contract — tool name plus `inputSchema` structure — and is always blocking on drift; a second covers the prose — `description` and property descriptions — and is blocking only for third-party servers, warning-only for internal ones. That distinction is what makes a lockfile livable: a typo fix in an internal docstring does not break the build, while an upstream server silently rewriting its description to steer the agent does. Around that it has the rest of a real supply-chain gate: `piton wrap --enforce` proxies a local STDIO server and blocks a rug pull at runtime, `piton replay` computes a false-block rate against recorded traces and exports CEL or Cedar policies, and there is an Envoy `ext_proc` sidecar for production. The GitHub Action (v0.4.2) makes the CI half a five-line change.

**Pros:**
- Structural versus prose hashing is the correct design for MCP pinning, and it is argued rather than asserted in the README.
- Scans the config surfaces that actually grant code execution — agent hooks, tasks, rules, skill markdown — not just `package.json`.
- Detects homoglyph and zero-width/bidi poisoning in tool descriptions, which is the MCP attack that a human reviewer cannot see.
- Enforcement has two shapes: a runtime wrapper for local STDIO servers and policy export for a gateway we may already run.
- Tiny dependency footprint and a single-file install path (`uvx piton-cli scan --repo .`), so trying it costs nothing.
- The replay path is PII-preserving by design (emails tokenized, domains and numeric ceilings kept), which is the only way we would ever replay real agent traces.

**Cons:**
- **Zero stars, zero forks, one author, 61 commits since September.** No third party has run it; every claim about what it blocks is the author's own.
- It knows Claude Code, Cursor, Claude Desktop and OpenCode config paths — **not Hermes**. Our MCP servers and skills live in our own layout, so the scan would cover only part of what we load.
- The lockfile only protects what goes through it. We would have to adopt `piton wrap` as the way we launch MCP servers, which puts a Python proxy in the path of every tool call — a new failure point under the agent.
- The feature surface is enormous for one maintainer (lockfile, wrapper, replay, CEL/Cedar export, Envoy sidecar), and the maturity is uneven: the lockfile is plausible today, the production gateway story is not.
- Description-hash pinning will flag legitimate upstream documentation changes, and every flag is a human decision about whether the change was hostile or routine — the ongoing cost is attention, not compute.
- No published false-positive measurement on a real third-party server set, so we would be calibrating on our own two or three servers.

**Should we...**
- 👀 **Watch it** — run `piton scan --repo .` once inside `~/.hermes` (read-only, no pins written) to see whether its findings map to our layout at all, and revisit if a Hermes-aware path lands or a second contributor appears.

**Impact on our stack:** Medium — Hermes' MCP configs and the Agentic OS. Concretely: it would pin the tool descriptions of every MCP server we mount and fail a check when one changes, which is the mechanical half of the "approving a server means approving instructions" policy we said yesterday we needed to write.

**Why:** Yesterday's item was the MCP Skills extension, and the reason it mattered was that a server can now ship prose that steers the agent. Today's Hacker News has the live example: a thread reporting that Notion's official MCP server injects hidden upsell instructions into agent context. That is exactly the rug pull Piton exists to catch, and it arrived within 24 hours of us deciding the policy question — which is a strong argument that the policy needs a mechanism behind it, not just a paragraph. The verdict is watch for supply-chain reasons rather than conceptual ones: one author, zero users, no Hermes paths, and a wrapper that would sit in front of every tool call we make. The cheap move is the scan, because it costs nothing and tells us whether our config layout is even visible to it; the expensive move — putting a one-person proxy under our agent — waits for evidence.

### SlopSquatShield — agivanttechnologies/SlopSquatShield

**What it is:** A Node CLI and set of hooks that checks a package before `npm`, `pip` or `mvn` installs it. If the package does not exist it blocks; if it was published in the last 14 days, has fewer than 500 weekly downloads, is one or two letters from a popular name, or has no source repository link, it warns; two warnings on the same package become a block. It installs as a shell wrapper, an agent hook, a pre-commit check and an IDE extension.

**Source:** https://github.com/agivanttechnologies/SlopSquatShield  ·  Provenance: GitHub search (new repos, last 7 days, sorted by stars); 53★, 41 forks, Apache-2.0, created November 22, five commits, one author.

**What's good about it:** The failure it targets is specific and real: an agent invents a plausible package name, an attacker registers it, and the next agent that makes the same mistake installs their code. The threshold logic is published rather than hidden — no score, just six checks and a rule that two warnings block — and the thresholds are configurable. The wrapper model is the correct one for an agent that runs `npm install` in a terminal tool: the check happens at the point of installation, not in a report nobody reads. It is honest about what it is not: no malware scanning, no transitive dependency tree, and only npm, PyPI and Maven.

**Pros:**
- Blocks the specific class of mistake an LLM makes — a plausible but nonexistent dependency — before the install runs.
- Four enforcement points (shell wrapper, agent hook, pre-commit, IDE), so it does not depend on the agent cooperating.
- Published, adjustable thresholds with no hidden scoring.
- Apache-2.0 and a small install (`npm i -g slopsquatshield`, Node 22+).
- Privacy statement is clear: only package names leave the machine, to the public registries, and results are cached.
- `slopsquatshield doctor` and a clean `uninstall` that removes everything except the allowlist.

**Cons:**
- **Five commits, one author, and the last push was November 23** — it has not been touched since two days after it appeared, which is not a maintenance signal.
- 53 stars and 41 forks is a launch-shaped ratio, not an adoption signal; almost no one is running this.
- `init` writes a marked block into `.bashrc`/`.zshrc` and a hook into every agent config it finds — it edits the one file and the one config layer that must not break, on day four of its life.
- The wrapper covers only `npm`, `pip` and `mvn`: not `uv`, `pnpm`, `yarn`, `poetry` or Gradle, and our Python work often goes through `uv` and `pipx`.
- It sends our private package names to public registries (deps.dev, npm, PyPI, pypistats) unless they are in the allowlist — for a hospital, the name of an internal package is itself information.
- It does not check transitive dependencies, so a real package with a poisoned dependency passes.

**Should we...**
- 👀 **Watch it** — do not install the wrapper; if the idea proves out, the cheaper version for us is a hook that runs `slopsquatshield scan` on the manifest before an install job, not a `.bashrc` edit.

**Impact on our stack:** Medium — the agentic-os install path. Concretely: a cron job or an ad-hoc session that adds a Python or Node dependency would be checked against the registry before the install, which is the only place where a hallucinated package name becomes code execution on our box.

**Why:** This is a small tool aimed at a real hole in agent safety, and the hole is one we have: agents write `pip install` and `npm install` lines, and the failure mode is silent until the package runs. The reason it is watch rather than adopt is that the implementation is four days old, five commits deep, and wants to patch our shell profile and every agent config — a blast radius far larger than the value it delivers today. The idea, though, is worth keeping: a single pre-install check is a cheap addition to the install step, and the honest version for us is a scan invoked from the job, not a wrapper around the shell. If it is still maintained in a month and covers `uv`, it becomes easy to adopt.

### cookout — mattpocock/cookout

**What it is:** A self-hosted, Slack-style board where humans and agents share channels and threads. `npx @ai-hero/cookout serve` starts a web UI at `/` and an API under `/v1/`, backed by SQLite (or Postgres via `DATABASE_URL`); agents log in with the `cookout` CLI and can be given idle-expiring session tokens, webhooks and triggers so a message in a channel starts work.

**Source:** https://github.com/mattpocock/cookout  ·  Provenance: spotted on Github Awesome — https://www.youtube.com/watch?v=Z0xEtyaEg24  ·  339★, 26 forks, created November 22, three contributors (one of them `claude`), 22 open issues.

**What's good about it:** The premise — one place where agents and people talk in channels instead of a dozen separate chat integrations — is a real gap in multi-agent work, and the implementation choices are sane: SQLite by default so a restart loses nothing, Postgres when you need it, a single admin token, host-header validation that refuses foreign hosts with a 421, S3-compatible attachment storage, and agent tokens that expire when idle. It is also deployable in one command on Fly or Render, which means the operational story is not "run a cluster".

**Pros:**
- Agent-native identity and tokens, not a bot bolted onto a human chat app.
- SQLite-first with Postgres as an upgrade path — the right default for a small internal tool.
- Triggers and webhooks mean a channel message can start a job, which is the shape of an agent inbox.
- Deploy recipes for Fly and Render are documented down to the health check.
- Attachment storage on disk or S3, with the bucket kept private behind the same auth check.

**Cons:**
- **There is no license file.** GitHub reports no license, which means no permission to use, modify or deploy it internally — that alone disqualifies it until the author adds one.
- It duplicates Telegram, which already delivers every brief, alert and job result to Shareef's phone, with push. A board is a place messages go to be missed.
- Another always-on service with a database, a token, an asset store and a deploy pipeline to monitor on a box that is supposed to stay boring.
- Three contributors in five days, one of whom is `claude`, and 22 open issues already — this is an AI-written launch, not a maintained product.
- COOKOUT_MAX_IDLE_EXPIRY, S3 credentials and an admin token are three more secrets to rotate.
- No mobile story, so the "human in the loop" half would be checking a web board.

**Should we...**
- ❌ **Skip it** — no license, no mobile, and it solves a problem Telegram already solves for us.

**Impact on our stack:** Low — it would sit beside Telegram as a second delivery surface, adding a service, a database and a token to maintain while making it *less* likely that a job result is seen.

**Why:** The interesting part is the agent-inbox idea: an agent that watches a channel and acts on a message is closer to how a department actually hands over work than a cron schedule is. But that idea does not need this product, and this product cannot legally be used without a license anyway. Our delivery problem is solved — Telegram pushes to a phone — and the failure mode of a board is that it becomes a second inbox nobody opens. File it as rejected so it does not come back around; if a licensed, maintained version of the pattern appears, the idea is worth revisiting then.

### deslop-please — deterministic-machines/deslop-please

**What it is:** A Rust linter that enforces one idea from *A Philosophy of Software Design*: deep modules and narrow interfaces. It reports four classes of structural sloppiness — `module-cycle` (two modules that know each other), `tangle` (siblings that know each other through a third), `field-leak` (fields read and written from outside their type), and `shallow-module` (a module whose interface is nearly as wide as its implementation) — with a call-site map and an SVG before/after suggestion. It requires `rust-analyzer` and ships a `.deslop-please.allow` baselist plus an `AGENTS.md` snippet telling a coding agent to fix findings from first principles rather than silence them.

**Source:** https://github.com/deterministic-machines/deslop-please  ·  Provenance: spotted on Github Awesome — https://www.youtube.com/watch?v=Z0xEtyaEg24  ·  1,172★, 61 forks, MIT, six contributors, 63 commits, CI and tests, created November 22.

**What's good about it:** It is the rare linter with a thesis, and the thesis is the right one for a codebase that agents keep extending: the problem is not style, it is that shallow modules and field leaks make every future change harder, and an agent will happily add a fifth leak rather than fix the abstraction. The output is designed for a model to read — a tree of call sites and a diagram — and the README's `AGENTS.md` block explicitly tells the agent not to do mechanical moves to hide errors. The engineering is credible for five days old: six contributors, 63 commits, CI with a test badge, a crates.io release, and an allowlist so adoption on an existing codebase is possible.

**Pros:**
- Encodes an architectural principle rather than a formatting preference, with a diagram per violation.
- The `AGENTS.md` guidance turns a finding into an instruction an agent can act on correctly.
- An allowlist file makes incremental adoption possible on a legacy repo.
- Six contributors and CI on a five-day-old project — unusual discipline for a launch.
- MIT and a single `cargo install`, with `rust-analyzer` as the only prerequisite.

**Cons:**
- **It only lints Rust.** It requires `rust-analyzer` and parses Rust syntax; our codebase is TypeScript/React plus Python, so it cannot read a single file we own.
- The TypeScript ports that appeared this week (`cmd8/deslop-please-ts`, `sachaarbonel/deslop-please-ts`, `irvinebroque/deslop-please-ts`) have 0–2 stars and one author each, and are days old — adopting one would be adopting a fork of a five-day-old tool.
- Five days old itself: the rule semantics will move, and an allowlist written today may not survive.
- The four rules are structural only — no test coverage, no dependency direction beyond cycles, no performance.
- 1,172 stars in five days is a launch curve; the number reflects the thesis, not validation.

**Should we...**
- ❌ **Skip it** — wrong language for our stack; re-check only if a TypeScript port with real usage appears.

**Impact on our stack:** Low — nothing we own is written in Rust, so the tool cannot run on the Unified Platform, the Agentic OS or the Hermes skills.

**Why:** This is the best-argued tool in today's batch and it is still a skip, which is worth saying plainly. The problem it names is real for us — AI-written code accumulates shallow abstractions and field leaks, and our React codebase has grown fast — but the tool cannot see TypeScript. The tempting move would be to adopt one of the TypeScript ports and call it covered; that would be adopting a days-old single-author rewrite of a days-old tool on the strength of a Rust repo's star count. The honest sequence is to skip the Rust tool, note the ports, and revisit if one of them gains contributors and a release history — at which point the architectural linter becomes genuinely valuable for reviewing Hermes-written code.

### magpie — yetone/magpie

**What it is:** A local gateway (127.0.0.1:3425) that pools the LLM access you already pay for — API keys, and subscription accounts for Claude, ChatGPT, Copilot, GLM and Kimi — behind one endpoint that any agent can use, with routing groups that fail over when a quota runs out. It discovers subscriptions by reading Claude Code's and Codex's sign-in files and the macOS Keychain, can start each account's quota window on a schedule, and offers optional secret masking that swaps keys, emails and card numbers for placeholders before a request leaves the machine.

**Source:** https://github.com/yetone/magpie  ·  Provenance: spotted on ManuAGI — https://www.youtube.com/watch?v=njoBlawECkI  ·  MIT, Go, 42,350★, 3,890 forks, 5,317 open issues, created September 23, 2026.

**What's good about it:** Two ideas in it are strong. The first is the masking layer: it replaces secrets and personal data with placeholders in the prompt and restores them in the reply, so an agent that reads a `.env` into context does not send the value to the vendor — that is a genuine answer to the failure mode we saw in the NordLayer story this week, and it is off by default rather than forced. The second is honest product positioning: the README says outright that if you use one agent on its vendor's own plan, you do not need it. The routing engine is thought through — quota-aware selection, prompt-cache affinity so a conversation stays on the account that answered it, per-account proxies, OTLP export.

**Pros:**
- Prompt-side secret masking with rules for keys, tokens, emails, card and ID numbers, and an optional local model for names and addresses.
- Real failover logic: routing groups across models and accounts, with prompt-cache affinity to avoid paying twice for the same context.
- Usage and quota accounting per key and per account, with cost at list price.
- Supports local models alongside hosted ones, so an offline path exists.
- Cross-platform (macOS, Windows, Linux) and MIT.

**Cons:**
- **It works by reading your agents' sign-ins** — Claude Code and Codex credential files, and the macOS Keychain. That is exactly the class of tool that must not run on a datacenter IP with real accounts behind it.
- Multi-account failover and the "daily warm-up" that starts an account's five-hour window on a schedule are designed to stretch plan quotas; vendors treat that as abuse, and the accounts at risk are the ones we would be relying on.
- 5,317 open issues. Whatever the tool does well, its support surface is chaos.
- Our inference is a single paid API provider; we have no subscription pool to consolidate, so the core feature is irrelevant to us.
- Adds a gateway hop and a credential store in front of every model call — the one path that must not fail silently.
- The masking feature is coupled to the gateway; we cannot take it without taking the account pooling.

**Should we...**
- ❌ **Skip it** — the account-pooling half is unusable for us and the masking idea is worth copying, not installing.

**Impact on our stack:** Low — a gateway in front of Hermes would add a failure point and a credential store for a problem we do not have, since our inference is one API key with predictable behavior.

**Why:** The pitch — never hit a limit again by rotating subscription accounts — is the kind of offer that is only attractive if someone else's terms are paying for it, and the endpoint is a process that holds every credential we own. For a department that already had a platform-credential incident this year, a tool whose first-run behaviour is to read other apps' sign-ins is a non-starter on any shared machine, let alone a VPS. The one durable idea is prompt-side masking: a small pre-send filter in Hermes that replaces key-shaped strings and patient identifiers with placeholders would give us most of the benefit of this feature with none of the account plumbing. Skip the product, keep the idea.

## Overall assessment

If we do nothing else, do these, in this order: **1) Run `safe-anything` on the Unified Platform and on `~/.hermes`, and read every finding** — it costs one command and an hour, it covers the three surfaces we have never scanned together (code, secrets, agent config), and it is the only item today that addresses a failure we have already had rather than one we might have. **2) Install AutoClip on the Windows desktop and cut three faculty interviews** — the content program has 28 clips and no renderer, and three clips settle whether this becomes the pipeline or stays a demo; publish nothing from inside it, and write the hooks yourself. **3) Run one `piton scan` inside `~/.hermes`** — read-only, no lockfile written, just to learn whether our MCP and skill layout is visible to it; if it is, pin the servers we actually mount, because the Notion MCP story on Hacker News today is the exact attack that pinning catches.

The pattern in today's seven items is that the useful ones are about **what the agent is allowed to load and run**, not about what it can do. Three of the four real candidates — safe-anything, Piton, SlopSquatShield — are checks on the install-and-load path: the package name, the tool description, the hook, the `.env`. That is where the risk moved this year. The one capability item, AutoClip, is the opposite kind of thing: it makes something possible that currently costs an afternoon per clip. The three skips share a different flaw: each would add a second runtime next to one we already have — a second chat surface, a second agent methodology in the wrong language, a second gateway in front of the only path that must stay reliable.
