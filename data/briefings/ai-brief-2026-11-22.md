### Amazon / MONAI Label zero-day (Cairn agents)

**What it is:** Amazon Threat Intelligence documented a China-nexus operator running the open-source Cairn agent framework against East Asian university IPs. The agents mapped the API of MONAI Label — an open-source medical-image annotation tool — found a path-traversal bug in its file-upload function, wrote files to the server, and planted a Python reverse shell that ran on interpreter start, ending at a root shell.

**Source:** https://www.securityweek.com/amazon-china-linked-hackers-ai-agents-exploited-medical-software-zero-day/ · advisory https://github.com/Project-MONAI/MONAILabel/security/advisories/GHSA-qc22-rmgc-vg94 · AWS https://aws.amazon.com/blogs/security/chinese-nexus-actors-cairn-ai-agents-found-a-zero-day-on-their-own/ · Provenance: Google News RSS (`AI agent`)

**What's good about it:** It is the first well-documented case of agent-speed offense against medical software, with numbers instead of adjectives. Amazon says the agents went from mapping the application's API to arbitrary file write in about 11 minutes. One failed attempt logged 148 actions over 16 hours. The MONAI Label advisory rates the bug critical, affects 0.8.5 and earlier, and notes authentication is **off by default** — anyone who can reach the server can exploit it. A fix exists and ships in the next release.

**Pros:**
- Gives us an attack-speed benchmark: minutes, not the weeks a human pentester needs, which is faster than most SOC triage windows.
- The vulnerability class is boring and checkable — unauthenticated upload endpoint plus path traversal. We can grep our own services for it this week.
- Cairn is open source, so the capability is not reserved to a nation-state; the same playbook is available to anyone who reads this report.
- The advisory is specific about version range and the auth-off default, which makes an inventory check possible instead of a vibe check.

**Cons:**
- Vendor-sourced (Amazon) with only *moderate* confidence on attribution; treat the attribution as a claim, the technical timeline as the useful part.
- No CVE assigned at publication, so scanner coverage will lag.
- The fix was not yet released when the story ran — "upgrade" is not actionable until the next MONAI Label release lands.
- Details come from an unauthenticated Cairn instance the researchers found, which is lucky rather than representative.

**Should we...**
- ✅ **Adopt it** — treat the advisory as an action item, not news.

**Impact on our stack:** High — Unified Platform, public-schedule service, and any departmental imaging AI. We expose FastAPI services behind Traefik, several with file-upload or document paths, and our default posture is "add auth if we remembered." The concrete change: inventory any MONAI Label instance in the department (confirm ≤0.8.5 is not reachable from the network), audit our own upload handlers for traversal and auth-off defaults, and tighten agent credentials so a compromised cron can only write inside its own workspace.

**Why:** The takeaway is not "AI is dangerous." It is that an unauthenticated upload endpoint is now found and exploited in the time it takes to read this brief, and our services are one forgotten `Depends()` away from that shape. A hospital department running imaging AI is exactly the target profile here — the payload was a Python startup-file write, which is how a lot of our own tooling works. Doing the inventory is an hour of work; skipping it because the story is about universities in Asia is how the next one lands on us.

### skill-distill

**What it is:** A skill (SKILL.md + scripts + harness adapters) for Claude Code, Codex or omp that takes a session which went well and turns it into a skill a chosen open-weight model can reproduce. The teacher writes the skill, starts the student in tmux on a fresh copy of the starting state with the original prompt, compares output to the reference, fixes the skill at the first divergence, and repeats three trials per version until the student matches and a human accepts.

**Source:** https://github.com/sybil-solutions/skill-distill · Provenance: GitHub new-repo scan (created 2026-11-21, 422★ in a day, 36 forks)

**What's good about it:** It encodes the part everyone skips: verification. The repo ships `distill.py` for run bookkeeping (init, trial, status, wait, evidence, verdict, ledger, report, accept), `extract_session.py` to turn Claude Code/Codex/omp logs into a readable reference, `capture_web.py` to screenshot a web result, and adapters for omp, pi, Codex, Claude Code and opencode. The rules are unusually disciplined — the student gets the reference prompt verbatim and a clean state, the produced skill may not contain the finished output or a script that writes it, and global context files are turned off where the harness allows. Honest limits are documented.

**Pros:**
- The loop is model-agnostic: teacher = strong model, student = whatever cheap model you name (the README's own example is DeepSeek-V4.1-Flash).
- It produces evidence, not vibes — a ledger, three trials per version, side-by-side reference vs student, and a human accept gate.
- Everything runs locally; it makes no LLM calls of its own beyond the harnesses you point it at.
- The output is a plain SKILL.md, which is exactly the format our Hermes skills already use.

**Cons:**
- Two commits, one author (`0xSero`), one day old. This is a method published as a repo, not a maintained tool.
- The teacher has to be Claude Code or Codex. Hermes is not a supported teacher harness, so we would run the loop manually or wire an adapter ourselves.
- Needs tmux and a second agent harness installed alongside — real setup, not a `pip install`.
- A produced skill is scoped to one model *and* one harness; the moment we change the cron model, the skill needs re-distilling.
- No test suite in the repo; the only quality signal is the human accept step, which does not scale past a handful of skills.

**Should we...**
- 👀 **Watch it** — borrow the loop now, adopt the repo when it has a second author.

**Impact on our stack:** High — Hermes skills and every cron job that runs on deepseek-v4-flash. We carry ~662 skills and no evidence that the cheap model executes any of them the way the strong model did when the skill was written. This gives us a repeatable way to answer that for one skill at a time.

**Why:** The expensive failure in our stack is not a missing tool; it is a skill that works when I write it and quietly degrades when a weaker model runs it. Today the only feedback is "the brief looked bad." skill-distill's contribution is the three-trial, first-divergence loop, and that costs nothing to copy: pick the copy-desk or the brief pipeline, run the same prompt three times on deepseek-v4-flash against the reference output, fix the skill where it first goes wrong. If the repo survives a month with a second contributor, install it; until then, steal the method and keep our skills honest.

### Muru

**What it is:** A Rust `muructl` binary plus an in-process Python runtime that serves WSGI and ASGI applications. It has a routing edge, Python-aware process management, and a release model where each deploy is a directory started beside the running release, given traffic only when ready, and kept warm for rollback. Built by Graham Dumpleton, who wrote mod_wsgi twenty years ago.

**Source:** https://github.com/muruhq/muru · docs https://grahamdumpleton.me/posts/2026/11/a-first-look-at-muru/ · Provenance: HN (`newest?q=AI`) via Simon Willison's link blog, 2026-11-21

**What's good about it:** The release model is the differentiator. With gunicorn, a deploy is a HUP or USR2 and a deploy script you write yourself; with Muru, `muructl deploy` starts the new release beside the old one, moves traffic when it is ready, and keeps the previous release warm so rollback is a command. Canaries are judged on what the workers report about the requests they handle, without a service mesh. It imports the app once and forks workers, with an explicit fork-safety check at import so a database connection opened at import does not produce mystery failures later. The access log splits queue time from app time. It runs as a user daemon, under systemd, or in a container, and supports CPython 3.11+ including free-threaded builds.

**Pros:**
- Zero-downtime releases, blue/green and rollback are built in rather than assembled from signals and a shell script.
- Development mode uses the same process model as production, so a reload locally is a miniature release — including the failed-start case.
- Canary and scaling decisions come from worker-reported request data, not a separate metrics stack.
- A dashboard and per-request tracing ship with it; the author has published 17 design posts in three weeks, so the reasoning is inspectable.
- Apache-2.0, Linux and macOS, no Python dependencies in the control binary.

**Cons:**
- Alpha: `v0.1.0-alpha.34`, 28 stars, 183 open issues, one maintainer plus dependabot. No stable release.
- It adds a routing edge of its own in front of the app — stacked with Traefik that is two proxies and two places to debug.
- The container mode assumes releases-as-directories; our compose flow is rebuild-image-then-restart, so adopting it is a deployment redesign, not a swap.
- No Windows support, and CPython 3.11+ only — fine for us, but it narrows the fallback if a dependency pins an older runtime.

**Should we...**
- 👀 **Watch it** — pilot when it reaches beta, on one low-risk service.

**Impact on our stack:** High — Unified Platform deploys and anything else we serve with uvicorn behind Traefik. Our current deploy is stop/rm/up, which is exactly why watchdogs vanish and why rollback means rebuilding. Muru's release model would make a deploy reversible in one command.

**Why:** We lose time and confidence on every deploy because restart is the only primitive we have — the container comes up, the watchers are gone, and undoing a bad release means another build. Muru is the first project I have seen that treats "keep the old release warm" as the default rather than a load-balancer feature you assemble. It is too young and too opinionated about directories to put the Unified Platform on it today, but the public-schedule service or the interview portal is a good pilot: one process, low traffic, easy to revert. Watch for a beta tag; if beta lands, that is the week to try it.

### NeonClipping

**What it is:** A local web app that turns a YouTube/Twitch/Kick link or a local MP4 into captioned 9:16 clips. It is audio-first: download audio only, take word-timed captions from YouTube (or local Whisper as fallback), score loudness jumps and 2–4 kHz energy for candidate moments, let a local Ollama model write titles and hooks, then download only the chosen sections and render 1080x1920.

**Source:** https://github.com/iamajmeena/neonclipping · Provenance: GitHub new-repo scan (created 2026-11-19, 1,908★, 98 forks)

**What's good about it:** The engineering choices fit the job. Audio-only download means an 85-minute stream costs 79 MB before you decide anything, and the README's measured number — 85-minute stream clipped in 97 seconds — comes from never looking at the whole video. It only downloads the chosen sections. Captions cover 52 languages and Hinglish, five styles, with quiet-part awareness. There are 11 layouts including an automatic facecam finder, which matters for interview footage. Everything stays on the machine: no account, no upload, no credits. CI runs the unit tests on macOS, Ubuntu and Windows.

**Pros:**
- No upload and no account — the right property for faculty footage that should not sit on a vendor's server.
- Audio-first pipeline is genuinely fast and cheap; no GPU required to find the moments.
- Section-only download keeps disk and bandwidth sane for long source files.
- Local LLM (Ollama) is optional — without it, clips are still picked by the audio/motion score.
- Facecam finder and 11 layouts cover the two-person interview case better than a generic center-crop.

**Cons:**
- Four days old, one primary author, 21 open issues; the Mac installer is explicitly untested by the maintainer.
- Free transcription depends on YouTube's captions — our own interview files would fall back to local Whisper and a slower path.
- It is a local web app with no batch API; 28 clips means 28 manual passes unless we script it.
- Rendering wants an NVIDIA GPU; on our CPU-only VPS this is a desktop job, not a cron job.
- Cropping a two-person interview to 9:16 is a judgment call the audio score cannot make; every clip needs a human look before it goes anywhere public.

**Should we...**
- 👀 **Watch it** — try three clips on the desktop, not a batch.

**Impact on our stack:** Medium — the social-media program, not the clinical stack. It would replace the manual "open the interview, find the good 40 seconds, caption it, reformat" loop with a repeatable first pass.

**Why:** Shareef has 28 faculty interview clips and no repeatable way to turn them into vertical clips; every current option is either a cloud subscription that uploads the footage or a Docker stack that needs an API key. NeonClipping is the first local option whose method matches the material — audio-first, facecam-aware, captions included. The honest gate is quality, not features: run three interviews through it, look at the crops, and decide whether the output is good enough to represent the department. If it is, it becomes the front half of the social pipeline; if the crops are wrong on two-person shots, it stays a watch item.

### kvdiff

**What it is:** A zero-config local proxy that sits between an LLM client and the provider, captures the request, and pinpoints the exact UTF-8 byte where the prompt prefix diverges from the previous turn — then classifies the break: tool reorder, mutated tool schema, volatile system text, TTL expiry, model switch, or prefix under the provider's cache floor. It prices the wasted tokens and can optionally heal tool ordering.

**Source:** https://github.com/flipcyde101/kvdiff · Provenance: HN (`newest?q=LLM`), 2026-11-21

**What's good about it:** The break taxonomy is the useful part. `TOOL_REORDER` (an MCP server reconnecting and reshuffling schemas), `TOOL_MUTATED`, `VOLATILE_SYSTEM` (a timestamp that landed inside the cached prefix), `TTL_EXPIRED`, `MODEL_CHANGED`, `PREFIX_TOO_SHORT` — those are the real reasons cache hits collapse, and each has a different fix. It is local-only (127.0.0.1, SQLite at `~/.kvdiff`), zero telemetry, and the default mode forwards request bytes and auth headers unmodified; `--heal` is opt-in and only sorts tool definitions. It works across Anthropic, OpenAI, Gemini, llama.cpp and vLLM, and ships a demo with seeded sessions so you can see the waterfall before pointing it at real traffic.

**Pros:**
- Wire-level byte diff plus JSONPath mapping, which is more precise than reading post-hoc token logs.
- Zero-mutation default means it does not silently change what our agents send.
- Local SQLite, no cloud account, no telemetry — safe for prompts that contain internal context.
- Has `npm test`, `typecheck` and `build` scripts, which is more than most day-one repos.
- The cost line ("$0.38 wasted") turns an invisible problem into a number.

**Cons:**
- One day old, one star, one author, no issue history — the definition of unproven.
- Requires Node ≥ 24; the Hermes container here runs Node 22.22.3, so it does not even start without a runtime bump.
- DeepSeek is not in the documented provider list; it is OpenAI-compatible, but "should work" is not "tested".
- Needs a base-URL override in the client — for Hermes that is config surgery, and a long-lived proxy for short-lived cron jobs.
- Healing mutates the request; on a provider with implicit caching, a wrong sort could cost more than it saves.

**Should we...**
- 👀 **Watch it** — run the demo on the desktop, not in the cron path.

**Impact on our stack:** Medium — Hermes cron cost. Most of our token spend is the same large system prompt and skill catalog on every run; if a tool description reorders or a timestamp sits in the system message, we pay full price on every job and never see it in a bill.

**Why:** Prompt caching is the single largest lever on what our daily crons cost, and we currently have no visibility into whether we are getting it. kvdiff is the first tool that answers "which byte broke it" instead of "your cache hit rate was low." But it is one day old, needs a Node runtime we do not have, and its documented providers do not include the one we actually use. The right move is to run `npx @drod915/kvdiff --demo` on the desktop to see whether our request shape even matches its model, and revisit when it has a DeepSeek report or a second contributor.

### AG-UI

**What it is:** An open, event-based protocol (MIT) that standardizes how agents stream to user-facing applications: typed events for tokens, tool calls mid-response, shared state updates, human-in-the-loop pauses and subagents. Ships TypeScript and Python SDKs, a spec, and a dojo of examples.

**Source:** https://github.com/ag-ui-protocol/ag-ui · Provenance: spotted on ManuAGI — https://www.youtube.com/watch?v=RMbAluxCI24 (timestamp 07:03)

**What's good about it:** It replaces bespoke SSE wiring with one bi-directional event stream that any client can render, regardless of which framework built the agent. The same agent can drive a web app, mobile app, terminal or Slack. Human-approval and shared-state events are first-class rather than something you bolt on, and the SDKs mean a React front end does not have to invent its own event schema. At 21k stars with a published spec and examples, it is the closest thing to a standard in this space.

**Pros:**
- Typed events instead of hand-rolled SSE — tool calls, state and interrupts are part of the protocol.
- Frontend-agnostic; our React Unified Platform could consume it without adopting a specific agent framework.
- MIT, with TS and Python SDKs and a public spec to build against.
- Human-in-the-loop is modeled explicitly, which matches how we actually want agents to act on production systems.

**Cons:**
- No Hermes adapter, so the server side is ours to write and maintain.
- 605 open issues — a fast-moving protocol is a moving target for a small team.
- Adds a protocol layer between FastAPI and React for a feature we have not scoped; there is no agent surface in the UP today.
- The value only appears once we build an agent panel; until then it is architecture homework.

**Should we...**
- 👀 **Watch it** — the standard to build against if the feature gets scoped.

**Impact on our stack:** Medium-Low — Unified Platform. If we ever add "ask the platform" or approval-driven actions, this is the contract to use instead of inventing event names in a Saturday session.

**Why:** The Unified Platform is a React app over FastAPI with no live agent surface, and the temptation when we add one will be to invent a custom WebSocket event format that only our dashboard understands. AG-UI is the alternative: a published event model with SDKs, so a tool call, a token stream and an approval prompt look the same to any client. We should not build an adapter today — there is no feature asking for it — but when the request arrives ("let me ask the schedule a question"), the answer should be AG-UI rather than a bespoke stream.
