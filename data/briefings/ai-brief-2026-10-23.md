### 1. ai-memory — long-term memory server for coding agents (akitaonrails/ai-memory)

**What it is:** A single self-contained Rust binary that captures what an agent does (prompts, tool calls, session boundaries) through lifecycle hooks, consolidates it into a git-backed markdown wiki, and serves it back as a bounded "brief" plus full-text/entity/graph search to the *next* agent, in *any* harness, on *any* machine. The database is a derived index; the `.md` files are the source of truth. Three releases in the last 36 hours (v3.2.0 Oct 22 01:37, v3.2.1 Oct 22 18:59, v3.2.2 Oct 23 00:17 UTC).

**Source:** https://github.com/akitaonrails/ai-memory · https://aimemory.sh/ · Provenance: spotted on ManuAGI — https://www.youtube.com/watch?v=x50MJN6HVgs (08:14 mark) — and confirmed against its own release feed.

**What's good about it:** The README's support matrix lists **Hermes Agent as a first-party supported harness** alongside Claude Code, Codex, Cursor, Gemini CLI, OpenCode, Kimi, Copilot CLI and about twenty others — the acknowledgements section even credits Hermes for "the self-improvement loop." That is the first tool in weeks that assumes our exact split (an agent on the desktop, a long-running agent on a VPS) instead of assuming one laptop. The default path makes **zero LLM calls**: capture, FTS5 + entity retrieval, rule-based summaries, decay, dedup and contradiction-flagging all run with no API key, which matters because our cron jobs are already the biggest token spend we have. Memory ages without an LLM too — used pages decay slower, cold episodic notes compact to durable facts, near-duplicates collapse, and versions are kept (`restore-page`), so a bad consolidation is reversible. The published benchmark is end-to-end through the shipped capture pipeline: LongMemEval-S hit@5 **0.951 zero-LLM / 0.949 with local embeddings** on the 3.2.1 release run, with the harness in the repo. And the comparison doc is honest in a way that is rare — it explicitly says none of the published numbers in this field are like-for-like, and it lists "where we're behind" instead of hiding it.

**Pros:**
- A **Hermes-supported harness** in the support matrix means the cross-agent handoff we currently fake with files and memory notes becomes a typed protocol: an owner per handoff, claimed exactly once.
- Zero-LLM default for capture, retrieval and artifact summarisation — no new credentials, no per-token cost on the VPS, and the parts that need a model (LLM consolidation, vectors, the "dream" rewrite) are opt-in and off by default.
- Multimodal import already exists for the thing we actually have: the comparison doc and commit history show an importer for VTT/SRT subtitles — the 28 faculty interview clips are transcript files, not code.
- Runs as one binary on Linux with `install.sh` + `ai-memory setup`, Docker image published, checksum-verified release assets, per-project multi-user auth with an audit log — deployable on the VPS without new infrastructure.
- 4,577 commits, 168 contributors, 136 releases, daily security patches (a sanitizer fix for JSON secrets and Basic auth landed Oct 22); this is not a 2-week-old star-bomb.

**Cons:**
- Star counts are promotional everywhere now, and 12.9K★ is not a quality signal — the real signal here is the commit and release history, which I checked.
- Default local embeddings download an ~87 MB model from HuggingFace on first start (sha256-pinned, opt-out via `embedding_provider = "none"`); fine on the VPS, worth knowing before running it on the desktop over the Tailscale link.
- Server replication is *not* automatic: the VPS and the desktop are separate stores unless we add the `ai-memory-wikisync` companion (two-way, git-based, conflict-aware). That companion is where the real work of "one memory across both machines" lives.
- The comparison doc openly admits two aging features shipped but are **unproven and off by default** ("shipped, opt-in, unproven"). Do not expect them to improve recall.
- Hooks mean the memory captures tool output — including anything our cron jobs print. It sanitises at a typed privacy boundary and strips escape sequences, but for a healthcare-adjacent stack that boundary needs a read before it is pointed at the Unified Platform work, not after.

**Should we...**
- ✅ **Adopt it** — integrate into our stack (strongly recommended)

**Impact on our stack:** High — Hermes cron + Hermes desktop/VPS split + agentic-os. Concretely: one `ai-memory serve` on the VPS (Docker or the release binary), hooks installed for Hermes on both machines, and the `ai-memory-wikisync` companion pointed at a private git remote. The change it makes is that the "what did we already try and why did it fail" knowledge stops living in my memory budget and starts living in greppable pages that any agent picks up at session start.

**Why:** Our failure mode this month has not been bad tooling, it has been re-deriving solved problems — the same routing bug, the same Supabase key mismatch, the same "the PWA needs a hard refresh" — in a six-thousand-character memory file that is 96% full, while three large briefings a day add to a vault nothing reads back into context. ai-memory is the first tool I have seen that treats that as a memory-hierarchy problem rather than a prompt problem: files you own in git, a derived index you can rebuild, a bounded brief at session start, and search across everything when the brief isn't enough — with the rare property of already naming Hermes as a supported harness, so we do not have to write the adapter ourselves. The honest case against adopting today is that it is a server with hooks in every agent, and a wrong hook silently captures sensitive tool output; so adopt it, but sequence it: install on the VPS first with `embedding_provider = "none"`, point it at one project (agentic-os), read one week of captured pages before it goes near the Unified Platform or anything patient-adjacent. That is an adopt-sized change with a watch-sized blast radius, which is the version of this verdict I can defend.

### 2. OpenUI Lang — the open standard for generative UI (thesysdev/openui)

**What it is:** A compact, streaming-first language that a model writes so an interface renders while the answer is still streaming — `root = Stack([header, chart])`, one component per line, restricted to components you define and register, with typed props via Zod. The repo is MIT-licensed and ships renderers for React, Vue, Svelte, Angular, React Native and email, plus LangChain/LangGraph integration, a CLI, and a React Email library for generated emails. OpenUI 1.0 spec landed Oct 14; the repo pushed today.

**Source:** https://github.com/thesysdev/openui · https://openui.com/ · Provenance: spotted on The Next New Thing — https://www.youtube.com/watch?v=tqpOfHS5-VY (item 5 of 15).

**What's good about it:** The token economics are the interesting part, and they are measured rather than claimed: across seven UI scenarios, OpenUI Lang used **4,800 tokens against 10,180 for Vercel's json-render (-52.8%) and 9,948 for Thesys C1 (-51.7%)** — with the methodology and reproduction steps in `benchmarks/`. Half the tokens for a generated dashboard is not an aesthetic gain, it is a cost and latency gain on every request. The renderer targets are the other half: the same response renders through React, Vue, Svelte, React Native, email or a plain script tag, which means an agent's output is not tied to one front end. And the "controlled rendering" model — the model can only emit components you have registered, with props validated up front — is the correct answer to the problem that makes generated UI untrustworthy: the model cannot invent a widget that doesn't exist in your design system. `setup-agent` writes the instructions into `AGENTS.md`, so the agent in this repo learns the format without a manual.

**Pros:**
- Component-registry restrictions mean generated UI can only use **our** components with **our** design tokens — the exact thing that stops an agent-produced page from looking like a random Tailwind template.
- Streaming render: the user sees the dashboard assemble instead of waiting for a complete JSON payload — valuable for anything that reads four tables at once.
- ~52% fewer output tokens than the JSON-based alternatives, measured with tiktoken, with the harness published.
- MIT with 58 contributors, 82 releases, an actual 1.0 spec in `spec/` — a real standard attempt rather than a vendor demo. Thesys is the company behind it, so there is commercial gravity keeping it alive.
- React Email support: generated *emails* rendered by components is directly relevant to the brief you are reading right now.

**Cons:**
- It is a **front-end refactor**, not an install. Our Unified Platform is React already, so the React path is plausible, but every dashboard we care about (Reports, Command Center, Swaps) would need its component set registered and its data layer adapted. That is a project, not an afternoon.
- The format is another thing an agent must be taught; the failure mode of a new UI DSL is agents confidently emitting components we don't have. The registry catches it, but only if our registry is complete.
- The benchmark is the vendor's own, over seven scenarios, and it compares against two JSON formats it also controls the framing of. Treat -52% as directional.
- Nobody in healthcare ops has shipped this yet. There is no story here for permissions, audit trails, or resident-scoped data — those are ours to build on top.
- It solves the *rendering* half of agentic interfaces and none of the *authorization* half, which is the hard half for us.

**Should we...**
- 👀 **Watch it** — keep an eye on it, not ready yet but promising

**Impact on our stack:** High later — Unified Platform (Reports / Command Center dashboards) and the email system. The concrete change, if adopted, is that a dashboard stops being a hand-built page and becomes a registry of components plus a prompt: "show this week's block utilisation, per campus."

**Why:** The recurring complaint about our agent output is that it is either a paragraph of text or a screenshot of a page someone built by hand; there is no middle ground where an agent assembles a real, brand-correct view out of components we already own. OpenUI Lang is the most credible proposal I have seen for that middle ground, and its restrictions are the reason to trust it — a model that can only reference registered components cannot wander into a design that violates the navy-and-light system. But the honest reason this is a watch and not an adopt: it is a rewrite of how our dashboards are built, and we are already mid-flight on the redesign adoption gate with eighteen surfaces waiting on your verdicts. Adding a UI DSL to the stack before that gate closes would mean two half-finished front-end stories at once, and the second one would silently invalidate the previews you are reviewing. Watch it, and when the Reports/Command Center verdicts land, prototype OpenUI on the *one* surface you decide to rebuild — if it holds up there, it becomes the pattern for the rest.

### 3. wshobson/agents — multi-harness agentic plugin marketplace (wshobson/agents)

**What it is:** A plugin marketplace of agents and **185 skills** that generates native plugin trees for six harnesses — Claude Code, Codex, Cursor, OpenCode, GitHub Copilot, Google Antigravity and Pi — from one source. The skill count is the point: each skill is a `SKILL.md` with explicit boundaries, a numbered workflow, and (in the newest ones) an evidence discipline about what was actually inspected.

**Source:** https://github.com/wshobson/agents · Provenance: spotted on ManuAGI — https://www.youtube.com/watch?v=x50MJN6HVgs (12:02 mark).

**What's good about it:** The newest addition is exactly our problem, written by someone else: `content-marketing/social-evidence-research` — an eight-step method for researching public social discussion where **every report claim points to the inspected material behind it**, with an evidence record schema, ten acceptance examples, and explicit rules for what was *not* inspected and where access gaps exist. We have been hand-rolling that discipline into social posts and briefs for months; here it is as a reusable, reviewable artifact. The multi-harness generation is the second useful idea: write the skill once in a harness-neutral source, generate the `.claude-plugin`, `.cursor-plugin`, `.pi` trees from it by a `make generate HARNESS=<name>` step, with a "gardener" that reports stale artifacts. MIT, 41.6K★, 91 contributors, 620 commits.

**Pros:**
- 185 skills is a corpus worth reading even if we install none of it — the structure of a good skill (boundaries, numbered workflow, acceptance examples) is a template for the ones we write ourselves.
- The evidence-traceability skill is a direct fit for the social-media program and for these briefs: claims that point at what was inspected.
- Harness-neutral generation means one source of truth for skill text across Hermes-adjacent CLIs, instead of drift between a Claude-flavoured skill and an OpenCode-flavoured one.
- MIT, mature, one active maintainer with a sponsor link and a real contributor graph — not a star-bomb.

**Cons:**
- 185 skills is also the risk: our Hermes memory is at 96% of a 6,000-character budget, and skills whose descriptions all want to be loaded compete for the same context. Installing a marketplace is how a lean stack becomes a slow one.
- Effort is concentrated in the Claude Code path; the other harness targets are generated, and generated targets are where subtle breakage lives.
- No releases — no tags, no changelog, no version to pin. You track `main`.
- The skill quality is uneven by nature: some are method documents with acceptance examples, others are prompt collections. There is no tiering in the repo to tell you which is which.

**Should we...**
- 👀 **Watch it** — keep an eye on it, not ready yet but promising

**Impact on our stack:** Medium — Hermes skills (copy-desk, brief, redesign workflow) and the social-media program. The concrete change would be one or two skills lifted from it — the evidence-traceability one first — rather than the marketplace itself.

**Why:** The thing I keep rebuilding by hand is the review discipline inside our skills: what was inspected, what was skipped, and what a claim rests on. wshobson/agents has written that down as a reusable spec with acceptance examples, and it has done the harder structural work of separating the skill source from the harness it runs on — the same separation we are missing between Hermes skills and the Claude/OpenCode tooling that surrounds them. But adopting the marketplace wholesale is the wrong move for us: our memory budget is nearly full, and a marketplace is a subscription to someone else's taste and someone else's context cost. So: watch it, read two of the skills properly (the evidence one and one content-marketing skill), and if the structure holds, write our own version of the evidence skill in the Hermes format. If we ever run more than one harness against the same codebase, the generation approach becomes worth copying outright.

### 4. ai-job-search — job application framework built on Claude Code (ai-job-search-dev/ai-job-search)

**What it is:** A fork-and-own framework, built on Claude Code, that evaluates job postings against your CV, tailors the CV per posting, writes the cover letter and preps the interview. Ships as a workflow of prompts and scripts you run locally. 63.7K★, 19.7K forks, MIT, actively pushed.

**Source:** https://github.com/ai-job-search-dev/ai-job-search · Provenance: spotted on ManuAGI — https://www.youtube.com/watch?v=x50MJN6HVgs (01:04 mark).

**What's good about it:** The architecture is the part worth stealing: a per-listing evaluation step that scores fit *before* anything is generated, so the expensive writing only happens for postings that pass a filter — the same pattern our brief pipeline could use (evaluate the candidate, then spend tokens only on survivors). It is also a working example of a Claude-Code-native framework with enough users that the rough edges are known.

**Pros:**
- A clean, readable example of filter-then-generate, which is the pattern our own pipelines keep getting wrong by generating everything.
- MIT, fork-first by design (you own your copy and your data), 19.7K forks means the workflow has survived real use.
- Actively maintained — pushed Oct 21.

**Cons:**
- It solves a problem nobody in our stack has: no one is job-hunting with this.
- It is Claude-Code-specific and assumes a paid Claude plan; a port to Hermes would be a rewrite of the orchestration, not a config change.
- The 63.7K stars against a single-purpose personal workflow is a promotional ratio, not a quality signal.
- No tests in the repo worth relying on, and the "fork it and own it" model means the maintainer has no obligation to keep the workflow coherent.

**Should we...**
- ❌ **Skip it** — not relevant, redundant, low quality, or not useful for us

**Impact on our stack:** Low — none. The only thing transferable is a design pattern, and that is a paragraph in a note, not a dependency.

**Why:** Real, large, and competently built, which is why it gets a breakdown instead of being silently dropped — but there is no version of our day where this runs. Residency recruitment is a different problem from job application, our candidates are interviewed by humans with a defined process, and adopting a personal job-search framework would put a third-party prompt workflow between us and a compliance-sensitive process. Filed as judged so it is never suggested again; the filter-then-generate idea is noted where it belongs, in how we build briefs and audits.

### 5. Agent Compute Engine — a microVM per agent (Google Cloud)

**What it is:** The infrastructure Google built to run Gemini's agents, now being sold as a Google Cloud service: every agent gets its own hardware-isolated microVM (Titanium IPU + Cloud Hypervisor boundary), with copy-on-write memory sharing to run many agents per host, fast checkpoint/restore to pause an idle agent mid-loop and resume it, a Hyperdisk per microVM for a persistent workspace, and agent identity wired into cloud IAM so the same access model and audit trail apply to agent-issued calls. Preview "in the coming months." Announced Oct 22 at AGNTCon + MCPCon alongside a companion, Agent Substrate, for Kubernetes.

**Source:** https://cloud.google.com/blog/topics/ai-infrastructure/introducing-agent-compute-engine-and-expanded-agent-governance · Provenance: Google News RSS scan (Oct 22–23, multiple outlets: The New Stack, Techzine, IT Automation Week).

**What's good about it:** The design decisions are a rubric for anyone planning to isolate agents, and they are stated plainly: pause an agent while it waits on a human, resume from a snapshot rather than keeping a VM warm; share memory copy-on-write so density survives; give each agent its own identity so an agent's actions are attributable. That is the blueprint for a future where our cron agents do not all share one container and one set of credentials.

**Pros:**
- The clearest public articulation of the isolation properties an agent platform needs — isolation, identity, pause/resume, audit — which is directly useful as an internal design note.
- Pause/resume with checkpointing is a real economic argument for agent workloads that are mostly waiting on humans, which is exactly what our approval-gated workflows do.
- Companion Agent Substrate extends the same idea to Kubernetes with microVM *or* gVisor isolation — gVisor is something we could run ourselves today.

**Cons:**
- Preview "in the coming months," no API, no pricing, nothing to install or call this week.
- It looks like the control-plane equivalent of a vendor lock: agents, identity and audit all land inside Google Cloud's model.
- Nothing here runs on our hardware; the VPS has no nested virtualisation path, and gVisor on the existing Docker host is a separate experiment we would have to run ourselves.

**Should we...**
- 👀 **Watch it** — keep an eye on it, not ready yet but promising

**Impact on our stack:** Low today — Hermes cron and the VPS container model. The concrete change, if it ever lands for us, is per-job isolation with per-job identity, so a compromised brief run cannot read the CRM.

**Why:** We do not have an agent-isolation problem yet; we have one container, one user, and agents that are trusted by construction. But the trajectory is obvious — the briefs keep finding agent tooling that assumes it can run anything, and the day one of those runs unattended with a database credential is the day we need the properties Google just enumerated. Watch it as a design reference rather than a purchase: read the pause/resume and identity decisions, write them into our own architecture note, and run the cheap experiment now (gVisor on the Docker host) instead of waiting for a preview.

## Overall Assessment

If we do nothing else, do these, in this order:

1. **Install ai-memory on the VPS, scoped to agentic-os, zero-LLM mode on.** It is the only item today that changes how the whole stack works rather than adding a tool to it — it turns "what did we already try" from a nearly-full memory file into a greppable, git-backed wiki that Hermes itself already reports as a supported harness. One binary, no API key, one project to start.
2. **Add the `ai-memory-wikisync` companion once the VPS copy earns it.** That is the step that actually connects the desktop agent to the VPS agent; until it exists, we have two memories that look like one. One week of VPS capture first, then sync.
3. **Prototype OpenUI Lang on exactly one surface when the redesign gate closes.** The Reports or Command Center dashboard you choose to rebuild becomes the test: register our components, generate the layout, measure whether the agent's output respects the design system. If it does, it becomes the pattern for generated views everywhere; if it does not, we learned it on one page.

**The single sentence:** today's best find is a memory layer that already knows our agent exists, and the discipline it needs from us — start with one project, no embeddings, read the pages before trusting them — is the same discipline the last three briefs have been asking for.
