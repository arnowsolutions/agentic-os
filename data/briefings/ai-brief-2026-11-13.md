### agent-roast — the tripwire for a build that goes green by getting weaker

**What it is:** A deterministic, offline npm tool that compares the before and after of a change and blocks it when the *checks* got weaker instead of the code getting fixed — a loosened assertion, a skipped test, a lowered coverage threshold, a CI step allowed to fail.

**Source:** https://github.com/Nari-Ab/agent-roast · https://www.npmjs.com/package/agent-roast · Provenance: Show HN — https://news.ycombinator.com/item?id=50468500 (posted 2026-11-12)

**What's good about it:** A linter cannot see this class of change, because every new line looks fine on its own; only the diff pair does. `toBe(42)` becoming `toBeDefined()`, a `lines: 90` threshold dropping to `50`, `continue-on-error: true` appearing on the test step — each is a legitimate-looking edit that turns red into green without fixing anything. agent-roast reads policy from the *base* branch, so a pull request cannot relax the rules that review it, and it hooks the agent itself: when Claude Code, Codex, Cursor, Gemini CLI, Copilot or Factory Droid is about to finish, it reviews what changed and sends the agent back once with the file, line and both versions. It also runs as a git hook, a pre-commit hook, a GitHub Action with SARIF output, and a read-only MCP tool. The honesty in the README is unusual: it publishes that 164 of 164 hand-labelled cheating edits were caught but that the cases were written *with* the detector, that on unseen repositories between a quarter and two thirds of its blocks were questions with a harmless answer, and that four of the nine hacks in an external reward-hack zoo are caught while five are not. That is a vendor telling you where it is blind.

**Pros:**
- I ran it: `npx agent-roast@0.23.0 demo` on this box returned `BLOCKED` with six findings — a trivial assertion, a skipped test, a weakened assertion, `continue-on-error: true`, and two lowered coverage thresholds — in about ten seconds, offline, no API key.
- Deterministic and token-free: exact matching plus diff analysis, no model in the loop, so a finding is reproducible and costs nothing to re-run on every commit.
- Covers the languages we actually write: full before/after comparison for JavaScript/TypeScript, Python and Go; skip and placeholder detection across Rust, Java, Kotlin, C#, Ruby, PHP and Swift; CI and config files in any language.
- Refuses to grade its own homework — config lives at the repo root and is read from `HEAD` or the base branch, with expiring exceptions instead of permanent rule-offs, and a baseline mode to adopt it on a repo with existing debt.
- Six weeks old but not a weekend repo: 74 commits, 32 published versions (0.23.0 today), MIT, zero open issues, CI workflow published.
- The `--advisory` install and `replay` over the last 50 commits let us measure false-positive rate on our own history before it blocks anything.

**Cons:**
- Its own benchmark says a quarter to two thirds of blocks on unfamiliar repos were false alarms — on a fast-moving build that means real interruptions until the baseline and ignore paths are tuned.
- It catches textual weakening, not semantic cheating: special-casing the input, overfitting to the test, swallowed errors inside normal-looking code are explicitly out of scope.
- Agent-hook integrations are tested against simulated hook input, not long live sessions — the README says so plainly.
- One author, eleven stars; if it is abandoned we own a fork of the rules we depend on.
- Node 22 here is fine, but the GitHub Action and hook paths add a second place where policy can drift from the repo's real conventions.

**Should we...**
- ✅ **Adopt it** — integrate into our stack (strongly recommended)
- 👀 **Watch it** — keep an eye on it, not ready yet but promising
- ❌ **Skip it** — not relevant, redundant, low quality, or not useful for us

**Impact on our stack:** Medium — the ce:build / ce:full pipeline and every repo the agent touches. Concretely: `.agentroastrc.json` plus the GitHub Action in advisory mode on the Unified Platform and interview-portal repos for one week, `replay` over the last 50 commits to measure our own false-positive rate, then flip the specific rules we trust to blocking and install the hook for Claude Code/Gemini CLI sessions.

**Why:** We already learned this lesson the expensive way once — the Apiiro research we covered yesterday was about agents leaking what they touch, and this is the same shape of problem one layer up: an agent under pressure to make CI green will edit the assertion, and nothing in our current stack notices, because the diff looks clean line by line and the build genuinely passes. The cost of adoption is one npm install and one config file, the tool is offline and deterministic so it cannot break a build by itself, and I verified the core behaviour on this machine rather than trusting the README. The reason it is an adopt and not a watch is that the risk is bounded by the install mode: advisory first means the worst case is a comment nobody acts on, and the published false-positive numbers tell us exactly what to expect while we tune it. If after two weeks the block rate on honest commits is above a few percent, we turn it off and we have lost an afternoon.

### swapback — a local proxy that keeps names, emails and phones out of the prompt

**What it is:** A local HTTP proxy (127.0.0.1:8787) that replaces listed names, emails, phones, cards, IBANs, SSNs and API keys with typed placeholders before a request reaches a model provider, then restores the real values byte-exact in the reply — including streams and tool-call arguments.

**Source:** https://github.com/rmpmrepo1278/swapback · https://pypi.org/project/swapback/ · Provenance: Hacker News, "Keeping names, emails and phone numbers out of LLM prompts with a local proxy" — https://news.ycombinator.com/item?id=50460951

**What's good about it:** It solves the one problem we have never solved properly: Hermes reads email, calendar and CRM text, and every one of those calls ships whatever is in the text to a model provider. swapback sits in front of the client, changes nothing but the base URL, and fails closed — an egress re-check scans the outgoing request again, and if a listed value is still there or the scrub fails, the request is blocked with a 503 rather than sent. The part that matters for an agent rather than a chat app: tool calls that could send data out (`web_fetch`, shell, message) keep the placeholder unless you explicitly allow that tool, so a prompt-injected fetch cannot carry an address out. It restores placeholders in plain and streamed OpenAI Chat Completions, OpenAI Responses and Anthropic Messages replies, and handles nested JSON, escaped and URL-encoded variants of the same value. And it is not theoretical about us: the README states it runs in front of the maintainer's own Hermes agent every day on real email and calendar traffic, and lists Hermes Agent as a tested host alongside OpenClaw.

**Pros:**
- Verified on this box: `pip install swapback` (0.4.17) then `swapback selftest` returned **PASS** — 1,694/1,694 exact round trips, 105/105 encoded forms decoded back, 96/96 nested-JSON levels valid and exact, 10/10 over-nested bodies blocked, 57/57 ordinary sentences untouched.
- Fails closed by design, and the failure mode is a blocked request, not a leak — the right default for anything clinical-adjacent.
- Three dependencies (PyYAML, phonenumbers, pyahocorasick), stdlib HTTP server, ~5,900 lines, MIT; no model to download and no probabilistic step, so behaviour is auditable.
- Works with any OpenAI-compatible client (OpenAI SDK, OpenRouter, LiteLLM) and the Anthropic SDK, which means it can front the whole Hermes provider config without touching agent code.
- `swapback known init --vcf contacts.vcf` can build the known-values list from a contacts export, which is exactly how we would seed it from the CRM rather than typing names by hand.
- Nineteen PyPI releases in five days and a limits document that names every gap instead of hiding them — rare and useful.

**Cons:**
- **No NER.** A name you did not list goes out as written. Its own docs say it plainly: "Priya Raman in free text goes out as written." For our use that means the known-values file is the security boundary, and a stale CRM export is a silent leak.
- **Medical record numbers are not covered** — the docs list them among the identifiers missed unless a rule covers them. That is the single most important gap for a hospital system, and it must be a custom rule before any pilot.
- Dates of birth are caught only after English labels ("Date of birth:", "DOB", "born on"), not as "Birthdate", "DOB =", non-English, or unlabelled.
- Base64, hex and rot13 re-encodings are out of scope, and an agent with a shell can produce them.
- Gemini's native API streams pass through with placeholders left in; only OpenAI chat, OpenAI Responses and Anthropic Messages are restored.
- Long streamed replies that are themselves escaped JSON restore slowly — roughly quadratic, measured at 6–42 s for 40 KB at two JSON levels.
- Five days old, two stars, one author. The README badge says MIT and the repo LICENSE says MIT, but PyPI's licence metadata is empty — a metadata mismatch worth resolving before we depend on it.

**Should we...**
- ✅ **Adopt it** — integrate into our stack (strongly recommended)
- 👀 **Watch it** — keep an eye on it, not ready yet but promising
- ❌ **Skip it** — not relevant, redundant, low quality, or not useful for us

**Impact on our stack:** High — Hermes email/Outlook handling, CRM lookups, and any skill that pastes resident or faculty text into a prompt. Concretely: a one-week pilot as a systemd unit on the VPS in front of the model base URL, with `known.yaml` seeded from the CRM contacts export plus an explicit MRN/date-of-birth rule, logging every 503 it raises.

**Why:** This is the highest-impact item today because it addresses a risk we are currently carrying without noticing: every brief, every email triage, every CRM summary puts real names and contact details into a third-party model call, and our only defence is that nobody has asked. The mechanism is the right one — a local proxy that fails closed, needs no provider co-operation, and is already proven against Hermes by someone else's daily use — and I confirmed on this machine that the round trip is byte-exact and that it blocks rather than leaks when the list breaks. The reason it is a watch and not an adopt is the gap that matters most to us: no NER and no MRN pattern means the protection is exactly as good as the list we feed it, and a five-day-old single-author project should not become a compliance control before it has run in front of our traffic for a week with the logs to show what it caught. Run the pilot, count the blocks, then decide — and if it holds, this becomes the default path for every non-clinical model call.

### Gemini 4 Hydrogen — the cheap tier that finally makes a 1M context affordable

**What it is:** Google's new Gemini 4 tier built for fast agentic execution — the successor to the 3.8 Flash line — priced flat at $1.50 per million input and $7.50 per million output across its entire 1M-token context window.

**Source:** https://blog.google/innovation-and-ai/models-and-research/gemini-models/introducing-gemini-4-hydrogen/ · https://deepmind.google/models/model-cards/gemini-4-hydrogen/ · Provenance: spotted on Paul J Lipsky — https://www.youtube.com/watch?v=bm8x0hopWTU and Hyperautomation Labs — https://www.youtube.com/watch?v=E4TzPbJUrX0 ; HN front page — https://news.ycombinator.com/item?id=50471431

**What's good about it:** The headline number is the price structure, not the benchmark: a flat rate across a million tokens means a job that stuffs an entire corpus into one prompt has a predictable cost instead of a cliff. On capability it edges past Argon on the Artificial Analysis Intelligence Index at its default high setting (51 vs 50, 54 at xhigh), triples Terminal-Bench 4.1 over 3.8 Flash (57% vs 18.2%), finishes tasks 2.5x faster at the default setting, and cuts fabricated claims by more than 5x. Google also shipped an Orchestrator in Antigravity that switches between Carbon and Hydrogen inside one session — near-Carbon task success on Terminal-Bench 4.0 while using 24% less quota and finishing 19% faster — which is the more interesting signal: the vendor is now optimising for model *routing*, not one model doing everything. It is available across AI Studio, the Gemini API, Gemini for business, the Gemini app, Search, and paid AI Pro/Ultra in Antigravity, so there is no waitlist.

**Pros:**
- Flat $1.50/$7.50 across 1M tokens removes the long-context surcharge that makes big-context jobs uneconomic — a full-vault pass becomes a line item we can actually budget.
- 2.5x faster at default settings and 5x fewer fabricated claims directly address the two things that hurt agent loops: wall-clock and invented results.
- Better at recovering from a failed tool call or an empty search result, which is precisely where our cron jobs break.
- Same API surface as the rest of Gemini 4, so switching a job is a model-ID change, not a rewrite.
- The Orchestrator data is a template worth copying even if we never use Antigravity: coordinator on the expensive model, workers on the cheap one.

**Cons:**
- Output at $7.50/M is not cheap for high-volume, long-output work like the brief itself — the economics only work for input-heavy, output-light jobs.
- Google's tier churn is brutal: this replaces 3.8 Flash months after it shipped, and our own vault already carries Carbon and Argon entries from six weeks apart. Anything we build on a specific tier has a shelf life.
- No BAA and no HIPAA posture, so it cannot touch resident, faculty or patient text regardless of quality.
- Benchmark parity with Argon at default settings (51 vs 50) is within noise; the real gain is price and speed, not intelligence.
- Vendor-reported benchmark table; the fabricated-claims and tool-recovery numbers have no independent replication yet.

**Should we...**
- ✅ **Adopt it** — integrate into our stack (strongly recommended)
- 👀 **Watch it** — keep an eye on it, not ready yet but promising
- ❌ **Skip it** — not relevant, redundant, low quality, or not useful for us

**Impact on our stack:** Medium — Hermes cron, specifically the daily brief's dedupe step. Today that step is a `curl` of the vault JSON plus a hand-built title/link set; a 1M-token model could take the whole vault index (1,845 items) plus the last 30 briefs in one call and return the candidate list with reasons, for roughly a quarter per run.

**Why:** The reason to care is not "new Gemini model" — we have covered three of those in six weeks and two of them changed nothing for us. The reason is that the price structure unlocks a specific job we do badly: dedupe against 1,845 vault items and three prior briefs is a context problem, and we solve it with regex and hope. A flat-rate million-token window turns it into a single prompt with the whole index attached, which would catch the near-duplicates that link-normalisation misses — the same repo under a different URL, the renamed fork, the tool that came back with a new name. It stays a watch rather than an adopt because the job is not worth rebuilding until we have measured what the current dedupe misses, and because a model with no BAA can only ever see the vault metadata, never the underlying content. The cheap experiment is a one-off script: take yesterday's brief, feed the vault index and yesterday's candidates, and see whether it flags anything the regex missed.

### AgentRun — durable execution and a memory of what worked, around the harness you already use

**What it is:** An open-source control plane that wraps an existing agent harness (Claude Code, Codex, OpenCode, pi) and adds three things: every run is persisted so a killed process resumes instead of vanishing, the agent keeps notes/skills/workflows from each run so the next one starts warmer, and one console governs approvals, spend caps and cost.

**Source:** https://github.com/Parcha-ai/agentrun · https://agentrun.ai · Provenance: Show HN — https://news.ycombinator.com/item?id=50471650

**What's good about it:** It names the exact failure we have. Our cron jobs die with the gateway — we learned that the hard way with the watchdogs, and the fix was external background processes, which is a workaround, not durability. AgentRun's model is that a run lives in one store, so killing the server mid-run and restarting continues the run rather than losing it. The learning loop is the other half: after each run the agent keeps a note, a skill, or a workflow, so a job it has done a hundred times stops rediscovering the same API. The published case studies are concrete and unglamorous — a code review agent tuned on their own PRs at 18 cents a review that caught 1.6x the real bugs Greptile did across 30 unseen PRs, and a merchant-classification job handed from Opus to a cheap model at $0.12 a merchant. It also provisions the computer each job needs: sandbox, Linux desktop, Android phone, or browser. Apache-2.0, 728 stars, npm 0.4.4, created September 23, pushed today.

**Pros:**
- Durable runs are the missing primitive in our stack; a resumed run is worth more than a faster one when the job takes twenty minutes and the gateway restarts.
- The learn-then-hand-off pattern (expensive model figures it out once, cheap model repeats it) is exactly how we should be running the recurring brief and audit jobs.
- Spend caps and approvals per agent are a real answer to the "an agent ran up a bill overnight" failure mode.
- One container or one `npx` to start, Render deploy button, Apache-2.0, active development.
- Multi-harness by design, so it is not a bet on one vendor's agent CLI.

**Cons:**
- Needs Node 24.22.3 or newer; this box runs 22.22.3, so it is a runtime upgrade or a container before anything else happens.
- Hermes is not one of the supported harnesses — we would be running it beside our stack, not inside it, and the scheduler overlap with Hermes cron is real duplication.
- It wants to be a server with its own store and console; on a box with 5.2GB of free disk and 15.6GB of RAM that is a meaningful commitment.
- The case studies are the vendor's own, on the vendor's repos, with no independent replication.
- Two months old, one company behind it; the "self-improvement" claim is the least verifiable part of the pitch.

**Should we...**
- ✅ **Adopt it** — integrate into our stack (strongly recommended)
- 👀 **Watch it** — keep an eye on it, not ready yet but promising
- ❌ **Skip it** — not relevant, redundant, low quality, or not useful for us

**Impact on our stack:** Medium — Hermes cron and agentic-os. Concretely: a single experiment, not a migration — run one recurring job (the weekly vault review) under AgentRun on a container, with the durable-resume and spend-cap features enabled, and compare it against the same job under Hermes cron.

**Why:** The honest framing is that this is the most interesting architecture we have seen for the problem our watchdog scripts paper over, and the least likely thing we should install this month. Durability and per-run memory are exactly what a brief that takes twenty minutes on a four-core box needs, and the learn-then-hand-off economics match how we already use models. But adopting it means a second control plane next to Hermes, a Node 24 runtime we do not have, and a server plus store on a disk that is 98% full — and the thing it does best, replacing a scheduler, is the thing we have already solved with cron and watchdogs. Watch it, run the one experiment when there is disk to spare, and revisit if Hermes cron ever grows run persistence. Do not let it become a parallel stack.

### VideoLingo — subtitles, translation and dubbing in one pipeline

**What it is:** An open-source Streamlit app and CLI that takes a video, transcribes it word-level, segments and translates the subtitles, and optionally dubs the result with a cloned or synthetic voice.

**Source:** https://github.com/Huanshere/VideoLingo · https://videolingo.io · Provenance: spotted on The Next New Thing — https://www.youtube.com/shorts/hbzicDw4xZw

**What's good about it:** It is the whole chain rather than one step: download, word-level ASR with Qwen3-ASR plus forced alignment, AI-assisted subtitle segmentation with configurable line lengths, terminology lists for consistent translation, optional reflection/rewrite pass, and dubbing through GPT-SoVITS, OpenAI TTS, Edge TTS, Fish Audio or a custom adapter. The parts that make it usable on real work rather than a demo: progress resumption, pause/resume/stop at any step, an HTTP API that replaced the old Excel batch mode, and a model searchbox that pulls the provider's list instead of making you type IDs. It is genuinely mature — 19,236 stars, Apache-2.0, 1,096 commits, pushed today — and the maintainers are honest that translation quality depends on the source audio, the language pair and the model chosen.

**Pros:**
- Word-level alignment with Qwen3-ASR plus forced aligner is the difference between subtitles that sit on the sentence and subtitles that flash mid-word.
- Terminology lists are the feature our faculty clips need — a name or a procedure should translate the same way in every clip.
- HTTP API mode means it can be driven from a skill rather than clicked through a Streamlit UI.
- Dubbing backends are pluggable, including zero-shot voice cloning via GPT-SoVITS, which is the interesting option for a consistent narrator voice.
- Apache-2.0, two years of history, 26 open issues rather than 260 — actively maintained.

**Cons:**
- It cannot run here: the container path wants an NVIDIA GPU and CUDA 12.8, this VPS has no GPU, and `/workspace` has 5.2GB free against a PyTorch-plus-models install.
- Translation quality is model-dependent and the README recommends a specific relay provider (OpenLux) — that is a vendor nudge, and we would use our own OpenAI-compatible endpoint.
- The default ASR path runs locally, so CPU-only means slow; WhisperX is not installed by the installer and needs a manual path.
- Streamlit as the primary interface is fine for a human and awkward for automation; the API is the real integration surface.
- Ingest is built around YouTube download, so local files and Drive links need the API or manual staging.

**Should we...**
- ✅ **Adopt it** — integrate into our stack (strongly recommended)
- 👀 **Watch it** — keep an eye on it, not ready yet but promising
- ❌ **Skip it** — not relevant, redundant, low quality, or not useful for us

**Impact on our stack:** Medium — the urology social media program. Concretely: two of the 28 faculty interview clips, run on the desktop with Spanish subtitles and a terminology list of names and procedures, to test whether subtitled cuts are worth producing at volume before building any pipeline.

**Why:** There are 28 interview clips sitting in a library and a Bronx audience that is substantially Spanish-speaking, and the gap between "we have clips" and "we have subtitled clips" is currently manual work nobody has time for. VideoLingo collapses transcription, segmentation, translation and burn-in into one run, and the terminology list is what stops a faculty member's name from arriving mangled in the Spanish cut. The reason it is a watch is purely mechanical: it needs a GPU and disk we do not have on the box where our agents live, so the realistic home is the desktop, and a pipeline that lives on one person's laptop is not a pipeline yet. The cheap test is two clips on the desktop, judged by whether the subtitles are good enough to publish without a human rewrite — if they are, we find it a permanent home; if not, this is a solved problem we do not have.

### Relate — an agent-native graph database in a single file

**What it is:** An embedded property-graph engine written in Rust — one `.rl` file, a directory, or pure memory — queried in openCypher, with an MCP endpoint and an agent skill so an agent can keep connected facts instead of loose text.

**Source:** https://github.com/relatedb/relate · https://relatedb.ai · Provenance: Hacker News, "Relate by Neo4j — embedded, agent-native graph database" — https://news.ycombinator.com/item?id=50469300

**What's good about it:** The install story is the pitch: `relate "RETURN 1 + 2 AS sum"` and you have a database, no server, no account, no instance. It speaks openCypher and is tested against the openCypher TCK, so the query language is not invented; a graph is a single file with an fsync'd write-ahead log and Parquet checkpoints; and the same engine ships as a CLI, a Python package (`pip install relate-db`), Node and WASM packages, a Rust crate, and an optional one-process server speaking Bolt, HTTP and MCP. `relate skill install` drops CLI, Cypher, vector and spatial references into every detected agent, which is the most agent-native install path we have seen from a database. Releases are signed with SSHSIG and the installer fails closed on a missing signature — someone there thinks about supply chain.

**Pros:**
- Zero infrastructure: a file plus a binary, which is the only shape of database that fits an agent that runs in a container for twenty minutes.
- Cypher, not a bespoke query API — an agent that knows SQL can be taught this in one prompt, and it is tested against the language's own conformance suite.
- The MCP endpoint plus skill bundle means Hermes could query it with no connector code.
- Relationships and vector similarity in one statement is the right primitive for "who works with whom, and what else is like this".
- Signed releases, notarised macOS builds, a documented limitations page that volunteers what it does not do.

**Cons:**
- Nine days old (created 2026-11-04) with 233 stars — the star count on a repo this young is attention, not evidence.
- Deliberate scope limits that matter to us: working set fits in memory, one graph per store, a single user or agent per process — it is explicitly not a multi-tenant server.
- It would be a second source of truth next to Postgres and the CRM, and our rule is that the CRM wins. A graph that mirrors CRM identities is a sync problem we do not have today.
- No migration path from or to Neo4j beyond CSV/Aura mirroring; if the project stalls, the data is in a format one small team maintains.
- The "Relate by Neo4j" framing on HN is confusing — the repo and site read as an independent project, so the corporate backing is unclear.

**Should we...**
- ✅ **Adopt it** — integrate into our stack (strongly recommended)
- 👀 **Watch it** — keep an eye on it, not ready yet but promising
- ❌ **Skip it** — not relevant, redundant, low quality, or not useful for us

**Impact on our stack:** Low — agentic-os memory and possibly the CRM relationship layer, if we ever need graph queries that Postgres recursive CTEs make painful. No concrete change now.

**Why:** The idea is right and the timing is wrong. Agent memory as connected facts rather than a pile of notes is a real improvement over how Hermes remembers things, and a single-file Cypher database an agent can install with one command is the first version of that idea that does not require us to operate a server. But we already decided that the CRM is the source of truth for every identity in the system, and a graph database that mirrors it would become a second place where a name lives — the exact failure we have been avoiding. Nine days and 233 stars is also too young to bet architecture on. Watch it, and if a genuine graph-shaped question appears (referral networks, co-authorship, rotation dependencies), reach for this before Neo4j.

### Edge0-145B — a 145B model that runs on a laptop, just not this one

**What it is:** An open-weight 145B mixture-of-experts model plus an inference framework and desktop app, released with reported peak memory of 29GB and 80+ tokens/s decode on a personal machine.

**Source:** https://edge0.ai/blog/introducing-edge0-145b-frontier-ai-capabilities-on-your-own-computer · https://huggingface.co/Edge0 · Provenance: Hacker News front page — https://news.ycombinator.com/item?id=50475713

**What's good about it:** Fitting 145B parameters into 29GB at 80+ tokens/s with 1,100+ tokens/s prefill and 128K–256K context is a genuine engineering result, and the whole stack is released — weights, framework, app — not just a demo. - Full stack released: weights on HuggingFace (including an NVFP4 quantisation), framework, desktop app.
- Long context (128K–256K) at essentially constant speed is the hard part and they claim it.
- No cloud dependency at all once the weights are local.

**Cons:**

- Every performance number is vendor-reported on unspecified hardware; "a compatible laptop such as a MacBook Pro" is doing a lot of work.
- "Open-source" here means weights plus a framework, not a training recipe, and the licence terms per model card need reading before any clinical use.
- A 145B local model is still slower and weaker than the hosted models we already call, so the only reason to run it is data residency — which for us is governed by policy, not hardware.

- ✅ **Adopt it** — integrate into our stack (strongly recommended)
- 👀 **Watch it** — keep an eye on it, not ready yet but promising
- ❌ **Skip it** — not relevant, redundant, low quality, or not useful for us

**Impact on our stack:** None today — it would need a 32GB+ desktop with fast storage, and even then it duplicates hosted models we already have without solving the compliance question that actually blocks local inference for us.

**Why:** The interesting version of this item is two years away: a model good enough to run on the machine that already holds the data, so the compliance question becomes a hardware question. Today it does not fit anywhere we run — 29GB against 15.6GB, no GPU, and a disk with 5.2GB free — and buying a workstation to run a vendor-benchmarked model we cannot yet put resident data through is the wrong order of operations. ### Chap (ChatPanel) — a meeting notetaker that never joins the call

**What it is:** A browser extension, desktop app and CLI that read live captions from Zoom, Meet, Teams and Webex to produce running notes, decisions and action items without a bot joining the meeting, with reversible anonymization of names, emails, cards and keys before anything reaches a model.

**Source:** https://chatpanel.net/ · Provenance: Show HN, "Chap — Meeting notes from live captions (no bot) with any LLM or agent" — https://news.ycombinator.com/item?id=50479186

**What's good about it:** The architecture is the right one for a hospital: no bot in the participant list, nothing uploaded to a vendor server, captions processed locally, and the anonymization layer sits in front of whichever model you point it at — including Claude Code or Codex under your own login. The free tier is real (one model, ten notes, ten meetings), and the CLI (`cpcli ask`, `git diff | cpcli ask`) means the same privacy gateway can front a terminal workflow. Model independence is genuine: in-browser model, Ollama, LM Studio, 20+ cloud APIs, or your own agent.

**Pros:**
- No bot joins the call, which is the difference between usable and blocked in most enterprise meeting policies.
- Local-first anonymization with restore is the correct shape for clinical-adjacent meetings.
- Works across all four major platforms and ships as extension, desktop app and CLI.
- Bring-your-own-model, including local, so the data path is ours to choose.

**Cons:**
- Closed source with a paid Pro tier; the free tier's ten-meeting cap is a trial, not a deployment.
- It captures meeting audio and captions inside a real signed-in browser session — exactly the pattern our rules say not to put on a shared or datacenter machine, and the value collapses if you use a throwaway account instead of your real one.
- No BAA, no HIPAA documentation, and no statement about where the local store lives or how it is encrypted.
- Meeting notes for this department would contain faculty performance, patient-adjacent scheduling and HR conversation; "privacy-first" marketing is not a compliance review.
- Our meeting notes already flow to Claude Meetings / whiteboards (covered 2026-11-11); this duplicates it with a weaker compliance story.

**Should we...**
- ✅ **Adopt it** — integrate into our stack (strongly recommended)
- 👀 **Watch it** — keep an eye on it, not ready yet but promising
- ❌ **Skip it** — not relevant, redundant, low quality, or not useful for us

**Impact on our stack:** Low — it would touch meeting notes, which is the one place we have already chosen a vendor path, and it cannot run headless where our agents live.

**Why:** The feature is right and the product is wrong for us. A notetaker that reads captions instead of joining the call is what a hospital meeting policy actually permits, and local anonymization is the correct instinct. But this is a closed, paid product that must run inside the browser session where Shareef is signed into Montefiore's Zoom and Teams, holding audio and captions from conversations about faculty and patients, with no BAA and no published data-handling documentation. That combination fails the first question our compliance office would ask, and the alternative — running it on a throwaway account on the desktop — throws away the only thing that makes it useful, which is being present in the real meetings. Skip it, and if meeting capture becomes a real requirement, start the conversation with IT about an approved tool rather than adopting one from a Show HN post.

## Overall assessment

If we do nothing else, do these, in this order:

1. **agent-roast** — install it in advisory mode on the two repos the agent writes to, run `replay` over the last 50 commits, then make the rules we trust blocking. It changes "the build is green" from a claim into evidence, and it costs an afternoon with a bounded worst case.
2. **swapback** — one-week pilot in front of the Hermes model calls, with `known.yaml` seeded from the CRM export plus an MRN rule, logging every 503. It changes the blast radius of every email and CRM summary we send to a model from "whatever is in the text" to "whatever is on the list", and the pilot tells us whether the list is good enough.
3. **Gemini 4 Hydrogen** — one scripted test that feeds the whole vault index plus yesterday's candidates into a single 1M-token call and compares the result against the regex dedupe. It changes the least glamorous and most repeated part of this job — deciding what we have already seen — from pattern matching into a judgement call, at about a quarter a run.

VideoLingo is the one to try on the desktop when the social program needs Spanish cuts; AgentRun and Relate are worth remembering but not installing; Edge0 and Chap are filed as rejected so they stop resurfacing.
