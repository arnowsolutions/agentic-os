### Modern Web Guidance 1.0

**What it is:** A set of agent skills plus a CLI from the Chrome team that injects expert-vetted, cross-browser web platform guidance into a coding agent's context — so the agent reaches for `<dialog>` and the Popover API instead of a jQuery-era modal, and for modern CSS instead of a polyfill.

**Source:** https://github.com/GoogleChrome/modern-web-guidance · https://developer.chrome.com/docs/modern-web-guidance  ·  Provenance: spotted on Github Awesome (first item in the rundown) — https://www.youtube.com/watch?v=i5OYXeCUHwY · announcement — https://developer.chrome.com/blog/modern-web-guidance-v1

**What's good about it:** The premise is exactly our problem. Our pages are written by an agent, and an agent's taste is a weighted average of every 2018 tutorial it ever read. Modern Web Guidance is the counterweight: hundreds of guides targeting specific, measured model knowledge gaps, each one reviewed by a content-area tech lead with a dedicated accessibility pass, all carrying browser compatibility data. It went 1.0 stable on **November 10, 2026**, and at that milestone it stopped being a Chrome project — Firefox and Edge joined, alongside MDN. It also ships a `legacy-scan` subcommand that walks an existing codebase and names the legacy patterns worth modernizing, which is the part that matters for a codebase we did not write by hand. And I did not take the README's word for it: I ran the CLI on this machine and it returned live guide IDs in JSON.

**Pros:**
- It works as a plain CLI (`search`, `retrieve`, `legacy-scan`) — no marketplace, no vendor account, no MCP handshake, so Hermes can call it with a shell command today.
- Cross-browser and standards-backed: Chrome, Edge, Firefox and MDN stewarding the same guide set means it will not push us onto a Chrome-only API path.
- The failure modes it targets are the ones reviewers keep catching in our work by hand: focus and inert management, reduced motion, form validation, dialog and popover transitions, light/dark theme correctness.
- There is a public eval dashboard showing measurable improvement over agents without it — a rare case of "trust me" replaced by a number.
- `legacy-scan` gives us a second opinion on our own React code instead of only guiding new work.
- Free, Apache-2.0, and it installs into the project, not into a hosted service.

**Cons:**
- It is not Hermes-native. The announced marketplaces are Claude Code, Codex, Cursor, Antigravity, Copilot, WebStorm, Kimi Code and Grok Build — Hermes is not on that list, so the honest integration is "call the CLI from a skill," not "flip a switch."
- Guide retrieval is search-based; if the agent's query is vague, it gets an irrelevant guide and burns context for nothing.
- It adds another moving part between the model and the file system, and context windows are already the binding constraint in our long build sessions.
- Docs and guides are English-only, and "modern" is a moving target — this needs an update cadence or it becomes last year's advice.

**Should we...**
- ✅ **Adopt it** — integrate into our stack (strongly recommended)
- 👀 **Watch it** — keep an eye on it, not ready yet but promising
- ❌ **Skip it** — not relevant, redundant, low quality, or not useful for us

**Impact on our stack:** High — Unified Platform, interview portal, and every redesign preview. Concretely: a `web-standards` skill in the Hermes skill set that runs `modern-web-guidance search "<task>"` before the agent writes a component, plus a monthly `legacy-scan` over the Unified Platform repo.

**Why:** This is the only item today that improves work we are already doing every week rather than adding a new capability we would have to go find a use for. Our UI output is the thing Shareef judges most harshly, and the criticism that recurs is not "wrong colour" but "this is not how the platform should behave" — focus traps, missing reduced-motion, a modal that scrolls the page underneath it. Those are precisely the documented model knowledge gaps this project exists to close, and the guides come with browser data instead of opinions. The adoption cost is an afternoon: install, write one skill that wraps the CLI, pin a version. The reason it is an adopt rather than a watch is that there is nothing to wait for — 1.0 shipped two days ago, it is Apache-2.0, it needs no credentials, and it fails safe (a bad guide is a bad suggestion, not a broken build). The one thing I want to prove in the first week is token cost: run it on one real page, measure the context it adds, and only then wire it into every session.

### chrome-capture

**What it is:** A CLI and small TypeScript library that records a Chrome tab straight to an AV1 `.mp4` at 60–120fps and up to 2160p, with tab audio, using Chrome 153's new `Page.startScreenRecording` — frames go from the compositor to an out-of-process encoder over shared memory, so there is no ffmpeg and no multi-second flush when you stop.

**Source:** https://github.com/paulirish/chrome-capture · https://paulirish.github.io/chrome-capture/  ·  Provenance: spotted on Github Awesome (#59, item 09) — https://www.youtube.com/watch?v=i5OYXeCUHwY

**What's good about it:** We produce video about software and never had a clean way to do it — screen recording means a person, a screen, and a re-take. This turns it into a command: `npx chrome-capture <url> demo.mp4 4s`, and because recording can be started and stopped at will you can log in, warm the page, and then record only the interaction. It takes a Playwright page, a Puppeteer page or a raw CDP session, so the same call fits inside a Hermes script that drives the Unified Platform. The benchmarks in the README are the useful part for us: **headless Linux with no GPU holds 1080p at 60fps (60.4 unique frames measured)**, and 1440p at roughly 58 — this is a container-class workload, not a Mac-class one. Audio is included, stops are instant because encoding already happened, and the whole implementation is small enough to read.

**Pros:**
- No ffmpeg dependency and no post-processing step — the file is finished when recording stops.
- One API across Playwright, Puppeteer and raw CDP, so it drops into our existing browser-automation scripts without a new abstraction.
- Verified headless-Linux numbers: 1080p60 without a GPU, which is exactly what our VPS is.
- Records tab audio too, which matters the moment a demo has narration or UI sounds.
- Apache-2.0 from Paul Irish, with tests and CI in the repo rather than a demo dump.
- Output is AV1 mp4 — small files for what they contain.

**Cons:**
- Requires **Chrome 153+**. Our Hermes container has no Chrome binary at all, and per our own ops notes anything installed under `/app` dies on `docker recreate` — so a Chrome install has to live on a mounted volume or be re-run after every recreate.
- No bitrate or CRF control: quality is a side effect of resolution and frame rate, and the README says so plainly. Fine for demos, not fine if someone asks for a specific delivery spec.
- AV1-only. Editors and some social platforms still want H.264, so a transcode step reappears for anything that leaves our stack.
- Four days old, 54 commits, one author, version 0.1.2 — the API will move.
- Disk is the quiet blocker: `/workspace` is at 97% with 5.9 GB free, and a Chrome install plus recorded output will eat that.

**Should we...**
- ✅ **Adopt it** — integrate into our stack (strongly recommended)
- 👀 **Watch it** — keep an eye on it, not ready yet but promising
- ❌ **Skip it** — not relevant, redundant, low quality, or not useful for us

**Impact on our stack:** High — social media program and Unified Platform documentation. Concretely: a `record-demo` helper that points at a route, does a scripted interaction, and drops a 1080p60 mp4 into the content pipeline — faculty onboarding clips, design-review walkthroughs for Shareef, and social cuts of the actual product instead of stock video.

**Why:** The social program's bottleneck moved. We can write copy and we can cut clips; what we cannot do cheaply is show the product working, because that requires a human, a screen share and three attempts. chrome-capture makes it a scripted step with a deterministic output, and the README's own benchmarks say the hardware we already rent is enough. It is a watch rather than an adopt for two concrete reasons: the Chrome 153 requirement collides with our container's ephemerality, and a four-day-old 0.1.x library with one author is not something to hang a publishing calendar on. The clean pilot is one afternoon on the Windows desktop — Chrome is already there, `npx chrome-capture` costs nothing, and if the output looks good we then solve the container problem deliberately (a Chrome layer on a volume) rather than by accident.

**Should we...**

**Impact on our stack:** Medium — social media and marketing program, and the department site. The tooling is genuinely ready — 45 contributors, 55 releases, Hermes support written into the README — but the thing it automates (search visibility) is not currently on our list of problems, and adopting it would mean standing up a service, buying query credits and owning an SEO practice. If it does not, we have spent ten dollars and learned that SEO is not our bottleneck — which is also a result.

### Exact

**What it is:** A framework from the Expo team where you write an app once and it runs natively on the web, macOS, iOS and Linux — with the twist that the app is written against a contract file an agent can build, run, see and test on every one of those platforms.

**Source:** https://github.com/expo/exact  ·  Provenance: spotted on Github Awesome (#59, item 03) — https://www.youtube.com/watch?v=i5OYXeCUHwY

**What's good about it:** Exact attacks the part of cross-platform that everyone else hand-waves: verification. A single `app.contract` describes the screen, an agent driver (`scripts/agent.mjs`) runs the tests on web, macOS and the iOS Simulator, and the README shows the same page captured on three hosts — browser DOM and CSS on the web, UIKit views on iOS, AppKit on macOS. The claim is not marketing: they document a fresh agent with a clean checkout finishing a small app in about 57 minutes with tests passing on all three platforms, and they break that time down honestly (roughly 25 minutes of it is first builds). For us the appeal is concrete — the schedule and the call-out flow are the two things people actually want on a phone, and today they get a responsive web page.

**Pros:**
- MIT licensed, from the Expo organisation, which means a real company's maintenance tail rather than a weekend project.
- The contract-and-agent-driver model is designed for our exact workflow: an agent writes, runs, screenshots and tests without a human clicking through a simulator.
- Genuine native controls per platform rather than a webview — UIKit and AppKit views, not "looks like iOS."
- 773 commits across seven contributors in ten days, with AGENTS.md, CLAUDE.md and a QUEUE.md in the repo — the agent workflow is the product, not an add-on.
- Linux and web targets mean our CI and VPS can build and verify part of the app.

**Cons:**
- **No Windows target**, and iOS/macOS builds require Xcode on a Mac. Shareef's desktop is Windows and the VPS is Linux, so the two platforms that make this interesting are the two we cannot build.
- Ten days old. 3,147 stars in that time is attention, not a track record.
- Adopting it means rewriting an app in its own contract model — this is not a library you add, it is a framework you move into.
- 176 MB repository, with Rust in the toolchain — a heavy build dependency for a four-core VPS at 97% disk.
- The agent-driven demo is the vendor's own measurement on their own hardware; our numbers would differ.

**Should we...**
- ✅ **Adopt it** — integrate into our stack (strongly recommended)
- 👀 **Watch it** — keep an eye on it, not ready yet but promising
- ❌ **Skip it** — not relevant, redundant, low quality, or not useful for us

**Impact on our stack:** Medium — Unified Platform mobile experience. If it works, the schedule ships as a real iOS app with native controls instead of a responsive page; if it does not, we have not touched anything.

**Why:** The idea is better than the current options and worse than the current situation. We have a working React app deployed through Traefik with Postgres behind it; Exact would replace that with a proprietary contract model to gain a native shell on platforms we cannot compile. The honest read is that this becomes relevant the day there is a Mac in the loop, or the day Exact ships a Windows target — whichever comes first. Until then I would watch it and steal one idea from it immediately, because that idea is free: put the acceptance criteria in a contract file and let the agent verify the screen on every target it can reach, rather than describing the fix in a chat message.

### ztd charts

**What it is:** A React charting library — 44 animated charts in pure SVG, zero runtime dependencies, 12–26 kB per chart — where every chart is also a JSON spec with a public JSON Schema, plus a CLI, an MCP server and an agent skill that validate a spec and render it to PNG, SVG or HTML.

**Source:** https://github.com/Junhan2/ztd-charts · https://charts.ztd.app  ·  Provenance: spotted on Github Awesome (#59, item 14) — https://www.youtube.com/watch?v=i5OYXeCUHwY

**What's good about it:** It is built around a principle our dashboards could use: one card says one thing, one series takes the accent colour, the rest stay neutral, and a bold takeaway sits under the chart so a reader gets the point before reading the axes. That is a design opinion, not a style option, and it is the right one for a program director scanning call-out coverage at 6am. The accessibility work is not decorative either — keyboard navigation, a screen-reader description and a data table for every chart, reduced motion, and every label at WCAG AA contrast. And the agent surface is the part that fits us: because each chart is a JSON spec with a schema, Hermes can author a report figure without writing React at all, and render it to PNG for an email.

**Pros:**
- Zero runtime dependencies and React as the only peer — nothing to audit, nothing to keep in step.
- JSON Schema + MCP + CLI means our agents can produce charts as data, then render them, which is exactly how our briefs and CE reports get built.
- Accessibility treated as a requirement: data table fallback, keyboard nav, reduced motion, AA contrast.
- Small bundles (12–26 kB Brotli) and automatic canvas fallback for large datasets.
- The "one takeaway per card" default would improve our dashboards without anyone redesigning them.

**Cons:**
- One contributor, 20 commits, six days old. Star velocity is not maintenance.
- Korean-first project: docs and examples are EN/KO, and the README's own screenshots are Korean-labelled, so some reference material will be a translation.
- Animation-forward by default, which fights the restrained, report-like register we use in the Unified Platform.
- Touching dashboard layout is off-limits without Shareef's explicit sign-off, so this could only ever land in new surfaces first (CE reports, emailed briefs).
- 44 charts is a broad surface for a single author to keep correct against React releases.

**Should we...**
- ✅ **Adopt it** — integrate into our stack (strongly recommended)
- 👀 **Watch it** — keep an eye on it, not ready yet but promising
- ❌ **Skip it** — not relevant, redundant, low quality, or not useful for us

**Impact on our stack:** Medium-low — CE report figures and emailed briefs first, dashboards only by explicit request. Concretely: chart-as-JSON means a Hermes skill can render a call-out coverage or case-log figure into an email without a human in a design tool.

**Why:** The MCP-plus-JSON-spec design is the right shape for how we work, and the "one card, one takeaway" discipline is the single best dashboard idea I have seen this month. But a six-day-old, single-author library is not something to put inside a production dashboard, and our dashboards are explicitly protected from unapproved change. The sensible move is to use it where the blast radius is a document: let a Hermes skill render report figures from a JSON spec into PNG for the CE reports and the daily brief, and revisit the dashboard question only when the repo has a second maintainer and more than twenty commits.

### raea

**What it is:** "Render Anything Engine" — videos, motion graphics, 3D scenes and small games written as React and TypeScript components and rendered on your own GPU by a Rust + Bevy engine, with an installer that also drops agent skills so Claude Code (or another skill-reading agent) knows how to write, render and check raea work.

**Source:** https://github.com/shinyobjectz/raea · https://raea.io  ·  Provenance: spotted on Github Awesome (#59, item 02) — https://www.youtube.com/watch?v=i5OYXeCUHwY

**What's good about it:** The concept is the right one for agent-generated video: the composition is code the model already writes well, and the render is deterministic and local, so nothing is metered by the second. v0.1.1 is the first release with the desktop app on macOS, Linux and Windows, the engine needs no account, and the render speed claim — "faster than they play" — is the kind of thing that changes whether iteration is practical. For our social program it is a plausible route from a faculty quote to a title card with real motion, driven by an agent instead of a timeline editor.

**Pros:**
- Compositions are React/TSX, which our models write fluently, and the agent skills ship with the installer.
- Local GPU rendering with no account, no queue, no per-render billing.
- Desktop apps on all three platforms, with the engine usable from the CLI.
- 479 commits and six contributors in under a month — more than a solo experiment.
- Motion graphics, 3D and small games from one engine is a genuinely unusual range.

**Cons:**
- **It needs a GPU.** Our VPS has none — `nvidia-smi` is not present and the box is four vCPUs — so it cannot run where our agents run.
- The licence is **FSL-1.1-ALv2** (source-available, with a two-year conversion to Apache-2.0), while the GitHub sidebar reports `NOASSERTION` — the badge and the metadata disagree, and neither is OSI open source. That is a real constraint for anything we would redistribute.
- Windows is described in the README as the "newest and least tested" target, and Windows is the desktop we have.
- 93 MB repository, Rust toolchain, v0.1.1 — "young: expect rough edges and gaps in the docs," per its own README.
- It overlaps two things we already have: OpenFilm (watched yesterday) for agent video, and Manim for programmatic rendering.

**Should we...**
- ✅ **Adopt it** — integrate into our stack (strongly recommended)
- 👀 **Watch it** — keep an eye on it, not ready yet but promising
- ❌ **Skip it** — not relevant, redundant, low quality, or not useful for us

**Impact on our stack:** Low — the social video pipeline, and only if a GPU machine enters the picture.

**Why:** I wanted this one to work, because "an agent writes a React component and gets a finished motion graphic" is the shortest path from a faculty quote to a post. Two facts decide it. First, the engine renders on a local GPU, and there is no GPU anywhere in our stack — the VPS has none and the desktop is a Windows machine for which raea is its least-tested target. Second, the licence is Functional Source License, not MIT: fine for internal rendering, unpleasant the moment we hand a render to another department or a vendor, and the repo's own metadata cannot agree with its badge about it. Add that we are already watching OpenFilm for the same job and already run Manim, and this becomes a third engine competing for one slot.

### agentes.chat

**What it is:** A self-hosted, AGPL-3.0 Slack alternative where AI agents are workspace members — they join channels and DMs with a role, an owner and a budget, run Claude, ChatGPT/Codex, Gemini, Grok or any OpenRouter model, get their own computer and browser, and wait for a person's approval before anything sensitive.

**What's good about it:** The design decisions are the right ones: approvals sit in the chat for merges and deploys, every model call is budgeted and recorded per agent, and agents are members of the workspace rather than a sidebar bot. Running on Postgres alone with Docker Compose is a sane deployment for a team that already hosts its own Postgres, and the "own computer and browser you can watch and take over" idea is the same instinct as the VM-with-a-real-browser pattern we have been circling for weeks.

**Pros:**
- Approval gates and per-agent budgets are exactly the guardrails an agent doing real work needs.
- Postgres as the only dependency makes it cheap to stand up next to our existing stack.
- Agents can use MCP tools and their own browser session, which is the shape of the social-posting problem.
- Web, desktop and phone clients, all from the same self-hosted codebase.
- AGPL is at least honest about what it is, unlike a proprietary "open core."

**Cons:**
- Three days old. 7,817 commits in three days is imported history, not velocity, and seven contributors on a 134 MB repo is a lot of surface for a first release.
- AGPL-3.0 — the same constraint we noted on Postiz: fine internally, awkward the day another department wants it.
- A clinical team chat with no BAA is a compliance question, not a feature question. Residents and faculty discussing service matters is patient-adjacent data.
- We already have the coordination layer: Telegram for alerts, Outlook for institutional mail, Hermes as the agent surface. This adds a fourth place to look.
- Agents with their own browser and computer inside a chat tool is a large new attack surface to secure before it holds anything real.

**Should we...**
- ✅ **Adopt it** — integrate into our stack (strongly recommended)
- 👀 **Watch it** — keep an eye on it, not ready yet but promising
- ❌ **Skip it** — not relevant, redundant, low quality, or not useful for us

**Impact on our stack:** Low — it would compete with Telegram and Outlook rather than improve them.

**Why:** The ideas are good and the execution is too new to judge: a three-day-old chat platform is a promise, and a chat platform is the hardest kind of software to be early on because everyone has to move at once. The decisive issue is not maturity, though — it is that a self-hosted team chat holding clinical-adjacent conversation without a BAA is a compliance conversation we have not had, and the coordination problem it solves is already solved for us by Telegram plus Hermes. Worth re-reading in three months if the approval-and-budget model turns out to be the thing our agents are missing; the idea is more valuable than the product right now.

### AI coding agents leaking credentials to public GitHub repos (Apiiro research)

**What it is:** Security research finding 2,539 credentials across nearly 2,000 public GitHub repositories, some traced to Claude Code silently copying secrets into a hidden file and committing them alongside the developer's code — including a production Azure Postgres password, a Square production token, and the owner password of a medical-records database, across 63 organisations.

**Source:** https://www.darkreading.com/cyber-risk/ai-coding-agents-leak-secrets-github · https://apiiro.com/blog/coding-agents-leaking-secrets-github-dont-ask-again  ·  Provenance: Google News, November 10, 2026

**What's good about it:** It is a precise description of a failure mode we are structurally exposed to: an agent with shell access, a `.env` full of credentials, and a `git add -A` at the end of a long session. The detail that matters is the mechanism — not a human pasting a key, but a tool writing secrets into a file nobody asked for and committing it with the rest. That is a workflow bug, so it has a workflow fix.

**Pros:**
- Names the mechanism rather than just the symptom, which makes it actionable.
- The affected categories are exactly our categories: Postgres passwords, cloud keys, API tokens, SSH root logins.
- Free to mitigate — a pre-commit secret scan and a `.gitignore` that is not advisory.
- It validates decisions we already made: the Montefiore credential ban came from the same class of mistake.

**Cons:**
- It is research about other people's repositories; the headline number says nothing about our exposure.
- The specific Claude Code behaviour may be patched by now, so the mechanism can go stale while the lesson does not.
- Vendor research, with the usual incentive to make the problem look large.

**Should we...**
- ✅ **Adopt it** — integrate into our stack (strongly recommended)
- 👀 **Watch it** — keep an eye on it, not ready yet but promising
- ❌ **Skip it** — not relevant, redundant, low quality, or not useful for us

**Impact on our stack:** Medium — agentic-os, Unified Platform, and every repo an agent has ever committed to. I checked our own exposure while writing this: across the 16 git repositories under `/workspace`, only `.env.example` files are tracked, and `git log --all --diff-filter=A` finds no `.env` that was ever added and later deleted. We are clean — by habit, not by gate.

**Why:** This is the one item today where the correct action is a change to process rather than software. Our agents run with shell access in a directory full of credentials, and the only thing standing between a long session and a public repo is that nobody has yet written `git add -A` at the wrong moment. The gate is cheap: a pre-commit secret scan on every repo an agent can reach, a `.gitignore` that refuses `.env` by default, and one line in the Hermes system prompt that says secrets never enter a tracked file. The research being about other people's repos is precisely why it is a watch — there is no incident here — but the fix should be in place before there is one.

## Overall assessment

If we do nothing else, do these, in this order:

1. **Modern Web Guidance 1.0** — install it and wrap it in a skill. It changes every page we ship from this week forward, and the failure it prevents (focus, motion, theming, dialog behaviour) is the failure Shareef keeps catching in review.
2. **chrome-capture** — one afternoon on the Windows desktop, one recording of a real screen. It turns "we should make a demo" into a command, and it is the missing production step between the faculty clips and a post.
3. **A pre-commit secret gate** — not an install, a policy: no agent commits a `.env`, ever. Our repos are clean today by luck; the Apiiro research is a map of what luck costs.

Everything else on the list can wait for a reason to exist: OpenSEO waits on the website becoming a channel, Exact waits on a Mac, ztd charts waits on a second maintainer, and raea, agentes.chat and CleanYourTV are filed as no.
