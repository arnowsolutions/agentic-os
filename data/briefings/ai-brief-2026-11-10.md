# AI & Hermes Brief — November 10, 2026

**The one question:** which of today's tools, repos and platforms is best for *our* system to make a major improvement?

**Short answer: nothing here is an adopt — and the most useful find is a measuring instrument, not a tool.** **flawless-ui-ux** is an Agent Skill plus a CLI that loads a running page in Playwright, records what it measured, and after a change reports which findings persisted, which are new, and which disappeared. That is exactly the missing half of our redesign process: we have eighteen surfaces waiting on verdicts and no repeatable way to check contrast, overflow, broken images or JavaScript errors across them. **Graphicle** is the runner-up: a single Rust binary that builds a code graph and project memory for coding agents over MCP, with a LoRA-free memory benchmark that ties Hindsight at a twelfth of the model calls.

The rest of the day is guardrails: **agent-email-guard** (loop detection and a kill switch in front of any SMTP send), **ovnfs** (copy-on-write checkouts so an agent never edits our real folder) and **office-engine** (DOCX/XLSX/PPTX opened in the browser, no server). Two of the three cannot run where our agents run, and the third is one day old.

### flawless-ui-ux — a design gate that leaves a record of what it checked

**What it is:** An Agent Skill plus a Node CLI for building, refining and reviewing interfaces. The skill carries the design guidance; the CLI does the measuring: it loads a running dev server in Playwright, records axe contrast and accessible-name results, computed font sizes and horizontal overflow at two viewports, visible broken images and uncaught JavaScript errors, then repeats the run after a change and separates **persistent**, **new** and **no-longer-observed** findings.

**Source:** https://github.com/smokeeaasd/flawless-ui-ux · MIT · 206★, created Nov 3, last push Nov 6, 0 open issues, ~705 KB repo · npm: `flawless-ui-ux` · Provenance: GitHub trending #58 — https://www.youtube.com/watch?v=zHZPb7wdQuk

**What's good about it:** The comparison run is the real idea, and it is the part everyone else skips. `inspect --url http://localhost:5173 --output ../app-before` saves a baseline `run.json` and screenshots; `verify ../app-before/run.json` after the fix re-runs the saved scope and tells you what actually changed rather than what you hoped changed. Exit codes are useful in a pipeline: 0 for complete coverage with no confirmed errors, 1 for confirmed errors, 2 for incomplete coverage — so "we didn't look" can never pass as "it's clean." The honesty is unusual for this genre: the README states plainly that these samples do not establish full WCAG conformance, complete keyboard journeys, business-flow correctness or visual quality, and that small text and repetition need a human. It never edits files, never starts servers, never downloads a browser and never submits a form.

**Pros:**
- **A before/after diff of design defects**, not a fresh opinion each time — the only way to prove a redesign fixed something instead of moving it.
- **Measured evidence we can put next to a verdict**: contrast pairs, overflow at 1440×900 and 390×844, broken images, uncaught JS errors, repeated phrases.
- **Exit codes separate "clean" from "didn't finish"**, which is the failure mode of every screenshot-based review.
- **Read-only by construction** — inspection does not touch the repo, so it is safe on a production branch.
- **Works against a live URL**, so it can review the `unified-*-redesign-vN.html` previews where they actually run.
- **The design guidance is separated from the measurement**, so a host that ignores the skill can still use the CLI, and vice versa.
- **MIT, no account, no telemetry, npm-installable**; the installer backs up and preserves existing files.

**Cons:**
- **Five days old, one author, zero open issues** — no issue tracker means no evidence anyone else has hit the edge cases yet.
- **Hermes is not one of the twelve supported hosts.** It writes into Claude Code, Codex, Cursor, VS Code, Kiro, Devin, Grok Build and similar directories; we would have to copy the skill into `~/.hermes/skills` by hand and skip the installer.
- **Needs Node 22.12+ and a Playwright 1.64.1 Chromium download** on whatever machine runs it — that is a second browser stack beside `browser_exec`.
- **Judgement is thin where our reviews actually differ**: it flags repeated phrases and arrow cues for "contextual review," but taste, hierarchy and whether a page feels premium are still a human call.
- **The measured set is narrow by design** (axe-selected rules, sampled widths, selected source files), so a clean run is not a design approval.
- **No CI recipe for our kind of artifact** — the previews are static HTML behind Traefik, so someone has to point it at each surface.
- **The npm package name is generic enough that typosquatting is a live risk**; install from the repo, not from search.

**Should we...**
- ✅ **Adopt it** — integrate into our stack (strongly recommended)
- 👀 **Watch it** — keep an eye on it, not ready yet but promising  ← **our call**
- ❌ **Skip it** — not relevant, redundant, low quality, or not useful for us

**Impact on our stack:** **Medium–High — Unified Platform design gate.** Concretely: install the CLI on the desktop or in a scratch container, point `inspect` at three of the eighteen `unified-*-redesign-vN.html` surfaces with a saved baseline, and see whether its findings match the things Shareef actually rejects. If they track, it becomes the evidence step before a Decision Studio verdict; if they don't, we learned that in an afternoon.

**Why:** Our redesign process has a verdict mechanism and a preview mechanism, but no instrument: every review is a fresh pair of eyes on a fresh screenshot, and nothing measures whether the thing we changed introduced a contrast failure at 390px or a broken image. flawless-ui-ux is the first tool in this genre that persists its own findings and reports the difference, which is precisely what a nineteen-surface review needs and what stops "looks better" from standing in for "is better." It is not an adopt today for three specific reasons: it is five days old with an empty issue tracker, it has never met Hermes, and its cheap checks are the ones we least often miss — the value is in the diff, not the rules. A three-surface trial answers that in an afternoon and costs nothing but a Chromium download, which is why this is a watch with a test attached rather than a bookmark.

### Graphicle — give the coding agent the repo's map and its own history

**What it is:** One Rust program that indexes a repository into a code graph (files, functions, classes, calls, imports — parsed with tree-sitter, no model), remembers project docs, reviewed decisions and past agent sessions, and serves both to any MCP client as cited excerpts within a token budget. One SQLite file, no server, no account, no API key for the graph and memory paths.

**Source:** https://github.com/Graphicle-AI/graphicle · Apache-2.0 · 548★, 42 forks, created Oct 14, pushed Nov 9, 7 open issues, Rust · Provenance: GitHub trending #58 — https://www.youtube.com/watch?v=zHZPb7wdQuk · also on Hacker News as a Meta hackathon project

**What's good about it:** The engineering is real and the claims are labelled. It is a Rust port of Graphify's code-graph engine (credited, Apache-2.0), and the published numbers are specific: on 13 codebases it took 3.4–23.9× less time than Graphify 0.9.100 in 34 of 39 measurements, and it loses the other five honestly (updates where Graphify now stops early). On agent memory it scored 87.7 on LoCoMo-10, level with Hindsight 0.10.2 (87.3) and above Mem0 OSS 2.2.1 (81.9), while making about 12 model calls per conversation against 160 and 332. Memories an agent proposes wait for human approval, memories are anchored to the code symbols they describe so they go stale when that code changes, and deletions produce a hash-chained receipt. `graphicle setup` backs up every file it edits and `graphicle disconnect` undoes all of it.

**Pros:**
- **Code graph, memory, MCP server and web app in one install** — one binary, one SQLite file, no Docker, no database server, no Python.
- **Cited answers**: every excerpt names the file and the lines, so a wrong answer is checkable rather than plausible.
- **Honest benchmarks** — the README prints the five measurements where the older tool won, and says outright that it tied grep on finding code and does not claim token savings.
- **Memory tied to symbols**, which is the right staleness rule for a codebase that changes weekly.
- **Approval queue for agent-proposed memories** and a deletion receipt — governance we would otherwise write ourselves.
- **Local by default**: loopback binding, no telemetry, `.env` and credential files skipped during sync.
- **Real release cadence** — 0.1.x with a changelog, 42 forks, and a documented migration path from Graphify.

**Cons:**
- **Its own agent tests undercut the pitch**: on 100 SWE-bench Verified issues it tied plain Claude Code (95/100 files found for both), used 16% more tokens, and "the agent never called Graphicle's tools" in one test. Better retrieval did not become better work.
- **Session capture covers Claude Code, Codex and Muse Code only** — the exact gap the Tinker skill had. Our sessions are Hermes, so the "remembers past sessions" promise is empty for us until someone writes a converter.
- **26 days old, one company, self-reported benchmarks** run partly during Meta's hackathon; nobody independent has reproduced them.
- **Release binaries are not signed with a trusted certificate**, and the Windows build uses a test certificate Windows does not trust.
- **Full extracts send documents and images to a configured model** — on a repo holding clinical documents that is a PHI path we would have to gate before running `graph extract` without `--code-only`.
- **Peak memory is heavy on big repos** (3.0 GB on a Kubernetes extract), which is a real constraint in our container.
- **Graphify's tool names** (`query_graph`, `get_neighbors`) mean any existing prompt written for Graphify silently changes meaning.

**Should we...**
- ✅ **Adopt it** — integrate into our stack (strongly recommended)
- 👀 **Watch it** — keep an eye on it, not ready yet but promising  ← **our call**
- ❌ **Skip it** — not relevant, redundant, low quality, or not useful for us

**Impact on our stack:** **Medium — Unified Platform + agentic-os.** Concretely: `graphicle setup` on a clone of the Unified Platform repo, `--code-only` so nothing leaves the box, then point one agent session at it and compare what it retrieves against `search_files` on the same question. The parts worth stealing regardless of the verdict are the symbol-anchored memory and the approval queue.

**Why:** Our agents work in a large React + Supabase codebase where the expensive failure is not typing — it is a plausible edit in the wrong file. A code graph with cited excerpts is the right context for that, and Graphicle is the first one small enough to live in one binary next to the repo instead of a database server beside it. What keeps it a watch is the evidence in its own README: retrieval tied grep, the agent did not call the tools in their test, tokens went up, and session capture does not see Hermes at all. Those are not disqualifying — they are exactly what a two-hour trial on our own repo would settle, and they are why we do not adopt a 26-day-old memory layer on the strength of a benchmark table.

### agent-email-guard — the seatbelt for an agent that can send mail

**What it is:** A small library, in Node, Python, PHP and Go, that wraps any mail transport (nodemailer, SES, Resend, Postmark, plain SMTP) and returns one of three decisions per send — `allow`, `hold_for_approval` or `refuse` — with a stable reason token, a human sentence and the numbers behind it. It refuses the fourth near-identical message to the same inbox in an hour, refuses a send to an inbox holding a third of a 20-send window, enforces hourly/daily budgets and a sliding per-minute ceiling, holds mail to flagged or new recipients for a person, and has a kill switch that never resumes on a timer.

**Source:** https://github.com/agentisend/agent-email-guard · MIT · created Nov 9, 5★, TypeScript (+ Python, PHP, Go packages), one spec with shared conformance vectors · Provenance: Hacker News "Show HN: Agent-email-guard — agent tried to send 400 receipts, stopped at 5" — https://news.ycombinator.com/item?id=50432613

**What's good about it:** It targets the failure that actually happens, and names it in the README: a retry loop sends one message 4,000 times; a loop rewrites each message but keeps mailing the same two inboxes. Both are caught by defaults, not configuration. The decision object is designed for a human: `loop_repetition_detected`, a sentence explaining that three near-identical emails went to the same address within 60 minutes, and evidence with the similarity score and window. Four implementations passing one set of conformance vectors means a Python cron job and a Node service can share the same budget through Redis or Postgres.

**Pros:**
- **Loop detection is on by default** — the specific bug that produces four hundred emails needs no configuration at all.
- **Recipient-collapse detection**: catches the loop that rewrites the body but keeps hitting one inbox, which similarity checks alone miss.
- **Decisions are explainable** — stable reason tokens plus a sentence a person can act on, so a refusal is not a mystery.
- **Kill switch with no timer** — the only correct design for "stop everything now."
- **One policy file across four languages**, with a `check` CLI that exits 0/2/3 so a shell script can gate a send.
- **Wraps the transport we already use** — plain SMTP is listed, which is what `smtp_send.py` speaks.
- **Small enough to read in full** before trusting it, which is the right size for a guard.

**Cons:**
- **One day old and five stars.** This is a launch, not a proven library; the behaviour under a real loop has not been observed by anyone but its author.
- **It runs inside the agent's process** — the README says so itself: "code the agent controls can remove it." That makes it a seatbelt the passenger can unbuckle, not a boundary.
- **The real enforcement is the vendor's hosted product.** AgentiSend is where limits cannot be raised by the agent, so the OSS library doubles as a funnel into a paid API that would see our email metadata.
- **Budgets are per key, in UTC calendar periods** — a daily cap resets at 00:00 UTC, which is 19:00 or 20:00 Eastern, not when our day ends.
- **In-memory store means two processes keep two budgets**; you need Redis or Postgres for the cron fleet, i.e. another moving part.
- **No Outlook/Graph path** — it wraps SMTP sends, so anything that goes through Microsoft Graph is outside it.
- **Not a Hermes plugin or skill**; using it means editing `smtp_send.py` to call it, and re-editing it on every container recreate.

**Should we...**
- ✅ **Adopt it** — integrate into our stack (strongly recommended)
- 👀 **Watch it** — keep an eye on it, not ready yet but promising  ← **our call**
- ❌ **Skip it** — not relevant, redundant, low quality, or not useful for us

**Impact on our stack:** **Medium — email/cron.** Concretely: implement the same two rules in `smtp_send.py` ourselves — refuse a sixth send to the same recipient within an hour, refuse when the recipient count collapses inside a burst — plus a `--dry-run` that prints the decision without sending. That is about thirty lines, has no new dependency, and closes the one failure mode where a bad cron run reaches Shareef's inbox four hundred times.

**Why:** Our email path is a Python script with no rate limit, no duplicate check and no kill switch, invoked by cron jobs that can loop; the only thing standing between a retry bug and a mail-bomb is that it has not happened yet. This library is the right shape of fix and its defaults are the right defaults, which is why the pattern is worth copying today. It is not an adopt because the code is a day old, the guard is removable by the agent it guards, and the version that actually enforces anything is the vendor's paid API. Copy the two rules into our sender, and revisit the library if it survives a month with real issues and a second contributor.

### ovnfs — an agent's checkout that never touches the real folder

**What it is:** A Go daemon that serves isolated, copy-on-write views of any folder — git repository or not — as a mount (NFSv3 on macOS, FUSE on Linux, SMB or WinFsp on Windows). The agent works inside the checkout; you review with `ovnfs diff` and merge with a three-way `ovnfs apply`. Checkouts can be snapshotted, forked and attached to another machine, where content arrives on first read.

**Source:** https://github.com/stencil-hq/ovnfs · MIT · 213★, 10 forks, created Nov 5, pushed Nov 9, 4 open issues, Go · Provenance: GitHub trending #58 — https://www.youtube.com/watch?v=zHZPb7wdQuk

**What's good about it:** The classification model is more thoughtful than "copy the directory": `source` paths are captured and are all that `diff` and `apply` see; `cache` and `local` paths (build outputs, ignored files, secrets) show the live folder until the checkout writes them, and `apply` never carries them back; `hidden` paths are absent entirely. In a git repo the checkout gets a private git directory, so the agent can commit freely and you bring the commits back with `apply --branch` or fetch them from its remote. `ovnfs run -- make test` gives a disposable checkout for one command. `ovnfs prune . --idle 7d` cleans up after itself.

**Pros:**
- **No copy cost.** Opening a folder does not duplicate it — that is what makes per-task checkouts practical on a repo we edit daily.
- **Three-way apply** with a real diff, so merging an agent's work is a review, not a leap of faith.
- **`ovnfs run` is the killer verb**: run a test or a migration in a throwaway view of the repo and have nothing to clean up.
- **Remote checkouts**: the same checkout can be attached to the desktop over ssh, installing ovnfs there if needed — useful for the VPS/desktop split we already run.
- **No root**, and no kernel extension except WinFsp on Windows.
- **Honest scope**: `ovnfs grep` addresses the daemon directly instead of traversing the mount.
- **MIT and a real CLI** with shell completion, `--dry-run` on prune, and an agent skill in the repo.

**Cons:**
- **It needs a mount, and our container cannot provide one.** This box has no `/dev/fuse` and `CapEff: 0000000000000000`, so FUSE inside the Hermes container is not available today; on the desktop it means installing WinFsp.
- **"ovnfs isolates files, not processes: it is not a sandbox"** — the limitations doc says absolute paths and symlinks can still reach the host, so it is a safety net for edits, not for an untrusted agent.
- **Best-effort view, not a snapshot** — a file rewritten while the agent reads it can show either version.
- **Five days old, four open issues, one organization**, and the git implementation is its own, not git's — `%(prefix)/` paths and some system config are explicitly unsupported.
- **Remote checkouts cannot be attached onward** and losing the source machine's objects can make tracked files unreadable.
- **NFSv3 cannot push cache invalidations**, so a stale view can persist up to 60 seconds — harmless for edits, confusing during a review.
- **Another daemon to run and supervise** on a box where we already own a gateway and two watchdogs.

**Should we...**
- ✅ **Adopt it** — integrate into our stack (strongly recommended)
- 👀 **Watch it** — keep an eye on it, not ready yet but promising  ← **our call**
- ❌ **Skip it** — not relevant, redundant, low quality, or not useful for us

**Impact on our stack:** **Medium — agentic-os / Unified Platform.** Concretely: a trial on the desktop, where WinFsp or a Linux box gives it a mount, with one task — an agent edits a copy of the Unified Platform repo, we review `ovnfs diff`, `ovnfs apply` the parts we want. On the VPS the honest answer is no: no FUSE, no mount.

**Why:** The most expensive mistake our agents can make is not a bad edit, it is a bad edit in the working tree of a live repository — which is exactly what happens today when a coding task runs in `/workspace`. ovnfs is the first tool here that makes "work in a copy, merge deliberately" cheaper than working in place, because the copy costs nothing until the agent writes. The blocker is environmental and concrete: our container has no `/dev/fuse` and no capabilities, so this cannot run where our cron agents run; it would be a desktop-side habit for coding sessions, which is where the risky edits happen anyway. Watch it, run one trial on the desktop, and do not try to force it into the container.

### Claude Fable 5.2 — the frontier gets cheaper and further away

- ✅ **Adopt it** — integrate into our stack (strongly recommended)
- 👀 **Watch it** — keep an eye on it, not ready yet but promising  ← **our call**
- ❌ **Skip it** — not relevant, redundant, low quality, or not useful for us

**Impact on our stack:** **Low–Medium — model routing in Hermes.** Concretely: nothing this week. The one use case worth pricing is a single hard, one-shot task — a tricky migration plan or a gnarly CORS/RLS bug in the Unified Platform — where 220 s of thinking is acceptable and $5 is not a problem. Not the cron fleet, not the copy desk.

**Why:** This is the best model in the world by independent measure and it got cheaper, which is worth knowing and worth a paragraph — but the brief's question is what makes our system better now, and a model that takes four minutes to start answering, burns 275M tokens on an eval suite and costs $26 a task is the wrong instrument for a fleet of 05:30 cron jobs and a copy desk that iterates in minutes. The honest read of Anthropic's own guidance is that Opus 5.5 is the daily driver and Fable is for the hardest open-ended work; our hardest open-ended work is coding on a repo we can also point a cheaper model at with the code graph above. ### office-engine — Office files in the browser, with no server

**What it is:** A zero-dependency TypeScript library (`@p10node/office-engine`) that views and edits DOCX, XLSX and PPTX — plus legacy DOC/XLS/PPT, RTF, OpenDocument, CSV, Markdown and Mermaid/PlantUML/Graphviz diagrams — entirely in a Web Worker, streaming large files as they scroll and saving back to the original format. One-line React embed (`<DocViewer src={file} editable onSave={...} />`) or a web component.

**Source:** https://github.com/p10node/office-engine · MIT · npm `@p10node/office-engine` · 115★, 4 forks, created Nov 2, pushed Nov 10, 0 open issues · Provenance: GitHub trending #58 — https://www.youtube.com/watch?v=zHZPb7wdQuk

**What's good about it:** The performance claims are specific and testable: a 55 GB CSV (500M rows × 10 columns) opens in about 4.5 minutes in Chrome with the tab under 1 GB, 300k-row XLSX in about 2 seconds, and there is no row limit because rows are read from the file as they scroll. Zero runtime dependencies, parsing and formulas and ZIP all in the worker, nothing leaves the browser. Real-time collaboration is built in, and `onSave` hands back a Blob in the original format — which matters, because "download as PDF" is where most browser viewers stop.

**Pros:**
- **No server and no conversion step** — the file the program actually uses stays the file.
- **Streaming that survives real files**: 55 GB CSV and 305-slide decks in the demo, not just toy samples.
- **Saves back to DOCX/XLSX/PPTX**, so an edit round-trip does not require Office on the machine.
- **React 18 peer only**, CSS auto-injected, one component; a `<office-viewer>` web component for the standalone HTML surfaces.
- **Real-time collaboration included**, which is unusual at this size.
- **MIT with a live demo and heavy-file samples** we can test in ten minutes.

**Cons:**
- **Eight days old, one organization, zero open issues** — an empty tracker is not a clean bill of health at this age, it is no signal at all.
- **The 55 GB claim is unverified by us** and irrelevant to our files; the load that matters is a few hundred pages, where any viewer works.
- **Editing fidelity is the hard part of this problem** and the README does not publish a fidelity or round-trip test suite — an edited DOCX that loses numbering is worse than no editor.
- **Bundle weight**: a worker-based Office engine is not a small addition to a page the user already waits on.
- **No server-side rendering**, so nothing here helps generate a PDF; it only displays and edits.

### cc-remote — Claude Code's brain on a server, its hands on your laptop

**What it is:** An ACP agent that runs Claude Code on a server reachable over ssh while every tool call — Read, Write, Edit, Bash, Glob, Grep and your local MCP servers — executes on your own machine. The model, the login and the subscription stay on the server; the code, shell, toolchain and editor stay with you.

**What's good about it:** The split is a clean idea: it is `claude-agent-acp` with one change — the `claude` binary it starts runs on the server — so sessions, permission prompts, modes, model selection, forks and diffs behave exactly as they do in the original adapter. - 👀 **Watch it** — keep an eye on it, not ready yet but promising

**Why:** The architecture is interesting and, on a laptop that must not hold a subscription token, defensible — but for us it solves a problem we do not have, in a tool we do not run, under a licence that grants nothing. ## Overall assessment

Today's real theme is instrumentation and guardrails rather than capability: the tools worth attention are the ones that measure or contain what an agent does, and none of them is ready to be wired into a deploy gate. That is not a thin day — it is the shape of the stack's next problem. We have eighteen redesign surfaces waiting on judgement, a cron fleet that can email in a loop, and agents editing live repositories; three of today's finds address exactly those, and all three are a week old.

**If we do nothing else, do these, in this order:**

1. **Run flawless-ui-ux read-only against three of the eighteen redesign previews** — save a baseline, make no code changes, and compare its findings with Shareef's own rejections. What it changes: it gives the redesign verdicts a measured second opinion on contrast, overflow and runtime errors, and tells us in an afternoon whether an automated design gate is worth building at all.
2. **Put loop and duplicate protection into `smtp_send.py`** — refuse a sixth send to the same recipient inside an hour and refuse when the recipient count collapses in a burst, with a `--dry-run` that prints the decision. What it changes: it removes the one failure mode where a bad cron run mails Shareef's inbox hundreds of times, and it needs no new dependency.
3. **Trial Graphicle with `--code-only` on a clone of the Unified Platform** — one session, one question, compared against `search_files` on the same question. What it changes: if cited code context beats grep for our repo, every coding task gets cheaper and less likely to edit the wrong file; if it does not, we stop wondering.

Everything else is a watch with a reason: ovnfs is the right isolation model on a machine that can mount it, office-engine is the right viewer for files we do not yet display, Fable 5.2 is the right model for a hard task we do not have this week, and Jane Street's skills, mini-harness and cc-remote are all real work aimed at somebody else's stack.
