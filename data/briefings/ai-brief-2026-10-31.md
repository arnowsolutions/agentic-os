### 1. Project Quarry — rules that run over an agent's transcript, compiled and checkable

**What it is:** A Python framework from Cisco's AI Defense group for detecting threats and behaviour patterns **in agent conversations**. You write `.rule` files in a small declarative DSL over `user_messages`, `tool_calls`, `tool_results` and event order; Quarry parses and validates each rule at load time and compiles it to a symbolic finite-state automaton, then runs that compiled program over a transcript. It ships a CLI (`quarry scan`), sync and async Python APIs (`QuarryGuard`, `DSLScanner`), and an MCP/agent plugin for Claude Code, Codex and other MCP hosts exposing five read-only tools. Apache-2.0.

**Source:** https://github.com/cisco-ai-defense/project-quarry · plugin docs: https://raw.githubusercontent.com/cisco-ai-defense/project-quarry/main/docs/PLUGIN.md · Provenance: GitHub Search (new repos, `ai agent`) and Google News — *"Cisco Open Sources Quarry to Catch AI Agent Attacks Hidden in Harmless Steps"* (SecurityWeek, Oct 30).

**What's good about it — and I ran it:** This is not a README read. I cloned the repo, ran `uv sync --frozen` (clean, exit 0), then wrote **our own rule** and four hand-built transcripts:

```
rule "Unapproved outbound send"
metadata:
    severity = "high"
strings:
    $blocked = ["@montefiore.org", "smtp.gmail.com", "graph.microsoft.com"]
condition:
    any call in tool_calls where
        call.arguments.* contains_any $blocked
```

- Shipped examples: `benign.json` → **0 matches, exit 0**; `tool_calls.json` → **2 matches, exit 1** (the `rm -rf` example).
- Our rule against a transcript where the agent runs `smtp_send.py --to sfrasier@montefiore.org` → **1 match, exit 1**, naming the file and the rule.
- Our rule against a transcript where the agent lists a workspace → **0 matches, exit 0**.
- Our rule against the same email *under a different tool name* → **0 matches**. That is the honest boundary: the rule sees argument values, not tool names, so name-based rules are the one thing that has to be rewritten if Hermes ever renames a tool.

It compiled a rule I wrote in ninety seconds, it exited non-zero when it found something, and it printed which rule fired. That is the whole proposition, and it held.

**Pros:**
- **Fails closed at load time.** Rules that do not compile fail when the scanner loads, not silently at scan time. I confirmed this: an early draft using `any t in $blocked` was rejected outright with `could not be compiled to a DFA artifact` and exit 2. A guard you can trust to complain is worth more than one that quietly passes.
- **It audits the transcript, not the outcome.** Our cron jobs all "succeed" — the failure mode we cannot see is a job that did something *extra*: an email to the wrong address, a `rm -rf` in a scratch dir, a `psql` write against the wrong database. Quarry's rules are over tool calls and their arguments, which is exactly the layer where those live.
- **Symbolic compilation, not an LLM.** Deterministic, fast, no token cost, no model in the trust path, and rules you can read and diff in a code review.
- **Runs on the transcripts Hermes already writes.** No login, no cookies, no cloud, no API key. `uv sync` + a YAML config pointing at a rules directory; the CLI reads a JSON file of `{"messages": [...]}`.
- **Real backing, not a promotion profile.** Published by `cisco-ai-defense`, 22 commits across 4 contributors with `deadbits` as primary, pytest suite in-tree, Apache-2.0, and an independent press write-up the day it went public.
- **The MCP plugin is the lightest possible integration route** — five read-only tools, no scanning of anything you did not hand it.

**Cons:**
- **Alpha, and the DSL is explicitly promised to break.** The README says the syntax "may change before v1.0.0 in ways that require updates to existing rules". Version is 0.1.0. Rules we write this month may need rewriting before v1.
- **It does not know your tool names.** My own test proved it: the same email sent from a tool called `exec` instead of `terminal` produced no match. Any rule keyed on a tool *name* is fragile; rules keyed on argument content are not. That has to shape how we write them.
- **The semantic half is stubbed.** Four of the fourteen example rules use "deterministic keyword stubs via an explicit config opt-in" and the README itself says the stubs "are for examples and tests, not production decisions". Without wiring a model adapter, Quarry is a very good regex-and-structure engine, not a judge.
- **Nothing schedules it.** There is no daemon, no watch mode, no retention. Feeding it our cron transcripts is a cron job of our own — which is fine, but it is work, not a switch.
- **Wrong shape for a healthcare decision on its own.** It is a *detector*, not an approver. It can tell us a transcript crossed a line; it cannot decide whether the line mattered. It has to run beside a human-readable log, not instead of one.

**Should we...**
- ✅ **Adopt it** — as the audit layer on our top three cron jobs (this brief, the call-out line, any job with SMTP or Postgres in it).

**Impact on our stack:** High — **Hermes cron**. Concrete change: a nightly job serialises yesterday's cron transcripts (already on disk), runs `quarry scan` with a small rules directory (outbound email to anything outside our allowlist, writes to the production Postgres, `rm -rf`/`git reset --hard`, `.env` reads), and appends a one-line summary to the vault review: *"N transcripts scanned, M matches"*. Today the only proof a cron job behaved is that nothing visibly broke.

**Why:** Every item in the last month's briefs that touched agent safety died on the same rock — it needed a session, a login, or a cloud account, or it wanted to be the thing making the decisions. Quarry asks for none of that. It is a compiler and a file reader, which means it can run from a cron job on the same VPS as the jobs it is auditing, on data that never leaves the box. I did not take the README's word for it: I installed it, wrote a rule in the shape of our actual July incident (an email to `@montefiore.org` from this server), and watched it fire on the offending transcript and stay silent on the clean one. The caveat my own test produced is the important one — it matches on argument content, so our rules should be written about *what gets sent and where*, not *which tool did it*. The adoption is therefore narrow and cheap: one rules directory, one wrapper script, one line in the nightly review. If the DSL churns before v1.0, we lose an hour of rule rewriting, not a system.

### 2. Kensaku — find the thing by what was in it, locally, and let an agent search the same index

**What it is:** A MIT-licensed Rust/Tauri desktop launcher (plus a `kensaku-cli` binary) that indexes filenames, full text inside PDF/DOCX/EPUB and code, text inside screenshots and images via OCR, and meaning via local embeddings — all on-device. It exposes the same index to AI agents over a **local, read-only MCP server**. Published Linux `AppImage`/`.deb`/`.rpm`, macOS `.dmg`, Windows `.exe` on its releases page; v1.0.11 landed Oct 30.

**Source:** https://github.com/yjid/kensaku · releases: https://github.com/yjid/kensaku/releases · Provenance: spotted on Github Awesome — https://www.youtube.com/watch?v=S8g5nwZN9as (GitHub Trending Weekly #56, 05:45) and GitHub Search (`ocr`, created since Oct 20).

**What's good about it:** The claim is the interesting part, and unlike most of this week's repos it is a claim about *our* problem. The Unified Platform, the agentic-os tree and 60 days of briefings are a corpus nobody can search by memory ("the PDF about X", "the screenshot with the error"). Kensaku indexes it locally and — the piece that matters — exposes that index **over MCP to agents**, which means Hermes could ask "which file discusses the GME cap" and get a citation instead of a grep. The 100k-filename-in-a-millisecond claim and the 12 MB memory figure are from the project's own benchmark table and should be read as claims; the deliverable, though, is visible: real release artifacts for all three platforms, 100+ commits across 5 contributors including an automated release bot, and a CI badge that points at a workflow that exists.

**Pros:**
- **Nothing leaves the machine.** Local index, local OCR, local embeddings — no cloud call in the read path, which for a department holding resident documents is the difference between "could use" and "won't use".
- **MCP is a first-class feature, not an afterthought.** Read-only, local, no token — that is the shape our stack can actually consume, and it is the same shape as the MCP servers we already have.
- **It does the three searches we do by hand** (filename, content, screenshot text) in one box, and returns the highlighted match rather than a list of paths.
- **Twelve releases and a CLI binary published separately** — the CLI is what a cron job would call; the GUI is a bonus.
- **Honest comparison table.** The README puts itself beside Everything, Listary and PowerToys Run and marks what each *cannot* do rather than claiming to beat them everywhere.

**Cons:**
- **The shipped product is a desktop app.** The release assets are `AppImage/.deb/.rpm/.dmg/.exe`. There is no headless server build advertised, no Docker image, no systemd story. Whatever runs on the VPS would be the CLI against an index that has to be built somewhere — and the "somewhere" our documents actually sit is Shareef's machine and this container, not the same disk.
- **Rust Tauri application, twenty-odd directories, a week old.** `src-tauri/` plus `src/` plus `cli/` plus `tools/` — this is a large surface for a young project, and the "100,000 files in a millisecond" number depends on a warm cache nobody has quantified for a cold index of our tree.
- **OCR quality is unmeasured for our documents.** No benchmark table for scanned schedules, faxed notes or phone photos of paperwork — the exact inputs a residency office cares about.
- **Index maintenance is the hidden cost.** Incremental pickup is claimed; there is no published story for what happens when a folder is moved or a drive is unplugged, which historically is where every launcher index rots.
- **It is one author plus a bot** (74 of the last 100 commits from `yjid`, 15 from one collaborator, 8 from the release bot). Not disqualifying — a launcher is one person's job — but it means the roadmap is one person's attention.

**Should we...**
- 👀 **Watch it** — do not put it on the VPS. If we want it now, it runs on the **desktop** against Shareef's own files.

**Impact on our stack:** Medium — **agentic-os / briefings corpus and the document archive**. Concrete change: an MCP tool that answers "which of our files mentions this" with a path and a highlighted snippet, instead of a `grep -r` that misses PDFs and screenshots entirely. It also overlaps the OCR question in item 3: both are about turning documents we own into text an agent can read.

**Why:** The reason this is watch and not adopt is a hardware fact, not a quality judgment: the thing that ships is a GUI for a laptop, and the place the index would have to live to serve a cron job is a container with no display and no copy of the documents. The README's headline is a *local* search over a *personal* machine, and our personal machine is the one on the other end of the Tailscale link. So the honest verdict is: if it is useful, it is useful on the desktop, indexing the folders Shareef actually opens. What would move it to adopt is a headless mode or a documented way to build the index once and mount it read-only where a cron job can reach it. Until then it is the right idea at the wrong address.

### 3. MiniCPM-OCR — a 1.3B document parser that fits in 2 GB of GGUF

**What it is:** An open Apache-2.0 family of document-parsing models from OpenBMB. **MiniCPM-OCR 1.0** (1.3B) turns documents and PDFs into text/tables/formulas/charts/structured JSON, holds SOTA on Real5-OmniDocBench (93.68), OmniDocBench v1.6, Wild-OmniDocBench and olmOCR-Bench, and claims 1.49× the throughput of PaddleOCR-VL-1.6. A second model, **MiniCPM-OCR Jev**, audits OCR output *region by region*, flagging which parts need a human look. Ships day-one support for vLLM, SGLang, llama.cpp and **Ollama**, plus a pip SDK and a `SKILL.md`.

**Source:** https://github.com/OpenBMB/MiniCPM-OCR · weights: https://huggingface.co/openbmb/MiniCPM-OCR-1.0 · Provenance: GitHub Search (`ocr`, created since Oct 20 — 703★ in 4 days) and GitHub Search (`created:>2026-10-24 stars:>80`).

**What's good about it:** The deployment numbers, not the benchmark numbers. The Ollama path is documented end-to-end: `MiniCPM-OCR-1_0-Q8_0.gguf` at **0.81 GB**, an F16 vision projector at **0.90 GB**, a DSpark speculative-decoding draft model at **0.33 GB** — roughly 2 GB total, service on `127.0.0.1:18499`, and it needs Ollama 0.40.12 or later. Compare with OXR, this week's other parser (item 7): 24 GB of NVIDIA GPU. The second half is **Jev**, which is the part that actually maps onto a hospital: it does not just parse, it *scores its own regions* and tells you where to look. That is the difference between a tool that produces confident-looking text about a document and a tool that says "cells 4–7 of this table are unreliable, check them".

**Pros:**
- **Apache-2.0 with no revenue cap, no attribution clause, no competing-service restriction.** For a health system this is the whole ballgame — see item 7 for what the alternative costs.
- **Fits hardware we can actually get.** ~2 GB of GGUF is the first document-parsing model in months that a CPU-only box can run at all, and the first that a laptop runs comfortably.
- **Four inference frameworks from day one**, including llama.cpp and Ollama — so one model file and a well-known serving API, not a bespoke build.
- **Jev is a genuinely new idea** in this category: region-level confidence over *another* parser's output, which means it can audit OXR or PaddleOCR output without being the parser itself.
- **OpenBMB has a track record.** This is the MiniCPM family, not a first release from an unknown org; the model card, the tutorial and the benchmark reproduction guide ship in the same repo.
- **It ships a `SKILL.md`**, which is the shape our own skills take.

**Cons:**
- **Every benchmark in the README is the authors' own.** "Reproduction guide" is honest but still author-run; the radar chart even notes some values "remain to be confirmed". Treat SOTA as a claim to check on *our* documents before it decides anything.
- **Chinese-first documentation and a Chinese-market demo endpoint.** English docs exist and are good, but a chunk of the linked reference material is Simplified Chinese only, and the free API demo runs on `platform.modelbest.cn`.
- **1.3B is small.** It wins on throughput and fits in RAM; it will lose on dense or unusual tables to a model five times its size — which is precisely the document type (a reimbursement form, a schedule grid) we care about.
- **CPU throughput is unbounded in the docs.** "1.2 pages/s" is quoted on GPU-class hardware. On this VPS, expect seconds per page, not pages per second — that is fine for a nightly batch and not fine for a live workflow.
- **Four days old, one release, 43 forks vs 703 stars.** Apache-2.0 and OpenBMB's backing help, but there is no independent test of the Ollama path yet.

**Should we...**
- 👀 **Watch it** — and install it on the **desktop** first, against our own worst documents, rather than promising the VPS can run it.

**Impact on our stack:** High if it works — **agentic-os / reimbursement and call-out paperwork**, and the document side of the briefings. Concrete change: the reimbursement tip sheet and any scanned GME paperwork become machine-readable text a cron job can check, instead of an image nobody can query.

**Why:** The OCR gap is real and it has been quietly blocking things: the resident reimbursement flow, the call-out paperwork, the scanned stuff that lives in email attachments — none of it is queryable, and every OCR release this month either needed a 24 GB GPU (OXR) or was a vendor API. MiniCPM-OCR is the first one whose own documentation describes a ~2 GB Ollama deployment and a CPU path. That still is not an adopt, for two reasons I cannot paper over: our VPS has no GPU and would be slow enough that this is a nightly job at best, and the accuracy numbers are the authors' own on the authors' benchmarks. So the verdict is watch with a specific next step attached — run the Q8 GGUF through Ollama on the desktop against five real documents from the reimbursement folder and time it. If it reads a scanned GME form and a schedule grid correctly, the follow-up is a nightly job that OCRs new attachments into text. If it garbles the tables, the answer was Jev auditing a bigger parser, and we skip the model and keep the idea.

### 4. Kimi K3.1 Pro — a 3-trillion-class model, a million-token window, and weights that do not exist yet

**What it is:** Moonshot's upgraded tier of its open-weight Kimi K3 line: a 3T-parameter-class model with a **1M-token context**, live now in Kimi's apps and API, scoring **65.7% on Terminal-Bench 4.0**. Moonshot says the full weights will be published **by November 4, 2026**. The company also frames the release around deliberately *reduced* offensive-cyber capability relative to the previous version.

**Source:** https://www.kimi.ai/blog/kimi-k3-1-pro · coverage: https://thenextweb.com/news/moonshot-kimi-k3-1-pro-open-weight-cyber · Provenance: spotted on Matt Wolfe — https://www.youtube.com/watch?v=eDiQNFa-zYg and Paul J Lipsky — https://www.youtube.com/watch?v=lXLmgsNP3MY; confirmed via Google News RSS.

**What's good about it:** The 1M context is the property that matters for us. Our brief jobs read six days of markdown, a vault dump, multiple RSS feeds and a pile of READMEs in one turn — that is a long-context problem more than a reasoning problem, and a model that holds a million tokens without shattering is directly applicable to it. Terminal-Bench 4.0 at 65.7% is a coding-agent number, not a writing number, but it is in the same band as the closed models we pay for. And the *reduced* cyber capability is a genuinely interesting editorial choice: a frontier lab choosing to ship a less offensive model is a signal about what "open weights" is going to look like in 2027.

**Pros:**
- **1M-token context** at frontier-adjacent quality, which is the one spec our house brief workload genuinely needs.
- **Open weights promised on a date** (Nov 4), not "coming soon" — testable, and a promise that can be checked rather than trusted.
- **Available today via API**, so we can measure quality on our own prompts before any machine is bought or rented.
- **Cheaper long-context summarisation** is the realistic use: put a month of briefings in one call instead of six.

**Cons:**
- **The weights do not exist yet.** Everything the README-equivalent describes about local operation is a promise with a date. A brief that grades an unshipped artifact is guessing.
- **A 3T-class model is not runnable by us at any quantization.** Even a 1-bit build is hundreds of gigabytes. Open weights will change nothing about what we can host.
- **Chinese provider, US export politics.** The news of the last week includes US curbs being lifted on Anthropic's Fable/Mythos models — the regulatory weather around Chinese frontier models is not settled, and a healthcare department putting resident-adjacent text through it is a compliance question, not a latency question.
- **The headline is a coding benchmark** on a benchmark that has been revised repeatedly this year; 65.7% tells us little about writing a brief or reading a schedule.
- **"Cut its hacking skills" is a claim by the company about its own model**, and the released version still solved 81% of whatever test that is. Unverified in either direction.

**Should we...**
- 👀 **Watch it** — specifically, re-check on **November 5** when the weights are supposed to be out.

**Impact on our stack:** Medium — **Hermes cron / the brief job** only, as an API swap candidate behind an A/B test. Concrete change: one trial run comparing this model against the one we already pay for on a week of briefings, judged by whether it still gets the dedupe and verdict discipline right.

**Why:** This is a big release and it is a *news* release for us, not a stack release. The 1M context is the only property that maps onto a job we run, and the honest test for it is cheap — one week of briefings through a second endpoint, scored against the model we already use. What keeps it at watch rather than adopt is that the weights date is five days away and the runnable-in-our-stack answer is "never, at any quantization". Add the compliance question — this is text about residents and a faculty schedule going to a Chinese provider's API — and the correct disposition is: do not migrate, do measure, and revisit only if the measurement is lopsided enough to justify the conversation.

### 5. Floorplan — the map of the Unified Platform nobody has drawn

**What it is:** A MIT-licensed, zero-dependency Node plugin for **Claude Code and Codex** that scans a codebase (one repo or several), has the agent name every part, file and endpoint in plain English, matches each frontend web request to the server endpoint that answers it — **across repos** — and writes an explorable `floorplan/index.html` map. Includes zoom levels, "ask the map" questions, a **health check** (passwords in code, endpoints callable without signing in, unused files, files too big to edit), a "recent work" diff view, and export as a single HTML file. Never committed to git; the scan and its local server stay on your machine.

**Source:** https://github.com/haydenschmitty/floorplan · live demo: https://haydenschmitty.github.io/floorplan-demo/ · Provenance: spotted on Github Awesome — https://www.youtube.com/watch?v=S8g5nwZN9as (GitHub Trending Weekly #56, 03:39) and GitHub Search (`created:>2026-10-24 stars:>80`).

**What's good about it:** Two specifics, not the pitch. First, **cross-repo request→endpoint matching**: the Unified Platform is a React frontend, a Node/Express server, and a separate public-schedule app behind Traefik — exactly the "frontend and backend in different repos" case the README says to open the parent folder for. Second, the **health check** is a security review of the thing we deploy: secrets in code, endpoints anyone can call without signing in, and a one-click fix prompt for each. Every redesign cycle we do has a manual step that is, in effect, "remember what connects to what" — and the audit finding we keep re-learning (the schedule page's relative-fetch double-prefix bug behind Traefik) is exactly a request→endpoint mismatch a map would have shown.

**Pros:**
- **Zero dependencies, no hooks, no MCP server, no downloads** — and there is a dedicated `docs/is-it-safe.md` that enumerates every program it runs and how to verify the installed copy. That level of paranoia is the right signal for something we would point at a repo holding Montefiore config.
- **Plain English by default** ("Takes card payments at checkout", not "Stripe API wrapper") with a developer-view switch — the right default for a non-programmer reading the map.
- **Cross-repo endpoint matching plus route-framework support for the stacks we actually use**: Express, Next.js, FastAPI, Flask, Django, React Router, TanStack.
- **Static HTML output, exports as one file.** That is the deliverable format our briefs already use, and it can be opened by anyone without installing anything.
- **It re-reads only what changed** and reloads an open map — so "update the floorplan" after a deploy is a cheap operation, not a rescan.

**Cons:**
- **It is a plugin for Claude Code or Codex, not for Hermes.** The install is `claude plugin marketplace add` or `codex plugin marketplace add`. Our agent is Hermes; there is no documented way to run it from here, and the "ask the map" box runs on the Claude/Codex sign-in.
- **Driven by an agent's sign-in, which is the exact credential pattern we banned in July.** The map itself is local, but generating it means pointing a logged-in coding agent at the repo. That is a *desktop* operation, not a VPS one.
- **Nine days old, one primary author** (70 of 76 commits), version 0.4.4, and it advertises a "Floorplan Cloud" in its privacy section — the commercial direction is already visible.
- **The map is only as good as the agent's naming.** A wrong "part" name is worse than no name, because it looks authoritative.
- **Health-check findings need triage, not trust.** "Endpoint anyone can call without signing in" will fire on genuinely public pages (the public schedule) and on false positives alike.

**Should we...**
- 👀 **Watch it** — run it **on the desktop**, once, against the Unified Platform tree, and judge the map.

**Impact on our stack:** Medium — **Unified Platform**. Concrete change: a single HTML map of frontend → API → Postgres, with the Traefik prefix games made visible, that we attach to the next redesign review instead of rebuilding the mental model each time.

**Why:** The case for this is not "it is cool" — it is that the last three redesign rejections and the schedule-page breakage all came from someone (me) holding the connection graph in their head and getting it wrong. A tool that derives the graph from imports and requests, and shows it as something Shareef can click, removes a recurring class of error. The case against is specific and not fixable by us: it is an agent-plugin for two harnesses we do not run, and generating the map means a signed-in coding agent pointed at our repo, which on this VPS is the July incident again. So the verdict is watch with an exact action: on the desktop, install it in Claude Code, point it at the Unified Platform folder, export the HTML, and read it. If the map is right about the Traefik prefix and the Supabase auth path, we have a tool; if it is hand-wavy about which server answers which request, we learned that for the cost of one afternoon.

### 6. Kero — a terminal built for driving several coding agents at once

**What it is:** A MIT-licensed cross-platform (macOS/Windows/Linux) native terminal app aimed at coding agents. Sessions run in a small daemon (`kerod`) so they survive closing the window; each pane reports working/waiting/idle/error/exited; a `kero` CLI lets *agents* start sessions, split panes, type into them, wait on them and read their screens; remote hosts (Linux, Mac, Windows, WSL) appear in the same sidebar over SSH or Tailscale. Terminals render on libghostty.

**Source:** https://github.com/egoist/kero · Provenance: spotted on Github Awesome — https://www.youtube.com/watch?v=S8g5nwZN9as (GitHub Trending Weekly #56, 00:11).

**What's good about it:** The session daemon plus the agent-drivable CLI is a genuinely coherent design, and the "remote hosts over SSH or Tailscale" line describes a topology we already have — the desktop and this VPS are on a Tailscale link. The status-per-pane idea (which agent needs you, which is done) is the same problem our cron notifications solve badly. It is also real software: 1.3k stars, 100 commits in the recent window, 11 contributors, MIT, shipping binaries on three platforms, with sustained daily pushes.

**Pros:**
- **Sessions outlive the window** — a `kerod` daemon means quitting the app does not kill a running agent or its scrollback.
- **A CLI agents can drive** — start, split, type, wait, read the screen — which is the missing piece in most "agent terminal" products.
- **Remote hosts over SSH/Tailscale** map onto our actual desktop↔VPS topology.
- **libghostty rendering** means Ghostty themes and config work unchanged, which is a real quality bar.
- **Cross-platform with released binaries**, not a build-from-source-only project.

**Cons:**
- **It is a GUI for a human at a laptop.** The entire value is a sidebar and a status dot. Our operations run headless: cron jobs on a VPS, no display, and Shareef on Windows through the WebUI — not a person babysitting six panes of Claude Code.
- **It solves a problem we do not have.** We do not run "many concurrent coding agents I need to watch"; we run scheduled jobs that report by Telegram and email.
- **A daemon we would have to own.** `kerod` running sessions on the VPS is another long-lived process to supervise, and our watchdog budget is already a documented mess.
- **Two prior-art projects named in its own README** (Rex, Herdr) — which is honest, and also means the category is crowded and the moat is taste.
- **Installing the server build on the VPS means a `curl | sh` installer** from a GitHub release — the exact pattern we should not run unexamined on a box holding Montefiore config.

**Should we...**
- ❌ **Skip it** — the GUI is the product, and we have no GUI in the loop.

**Impact on our stack:** Low — nothing we run is a watched terminal session.

**Why:** This is a good product for a different person. The design is thoughtful and the remote-host feature is aimed straight at our topology, but the thing being improved is *human attention on many simultaneous agent panes*, and that is not a resource we are short of — our agents are unattended, scheduled, and report asynchronously. Adopting it would add a daemon to supervise and an installer to audit in exchange for a sidebar nobody is sitting in front of. Worth remembering if Shareef ever moves to live interactive agent work on the desktop; not worth a slot on this VPS.

### 7. TStack — the merge queue as agent skills, for a team that merges PRs

**What it is:** A MIT-licensed collection of nine agent skills for the pull-request lifecycle, installable by copying into `~/.claude/skills/` or `~/.codex/skills/`: `full-send` (take a change to a merged PR unattended), `full-stop` (same, stop before merge), `council` (review from three providers, loop until they agree), `sol-loop`, `file-pr`, `takeover`, `babysit-pr`, `modernize`, `leaving-pr-comments`.

**Source:** https://github.com/t3dotgg/tstack · Provenance: GitHub Search (`created:>2026-10-24 stars:>80`, 2.4k★ in four days).

**What's good about it:** The skills are narrow, named by the sentence you say, and they compose (`full-send` calls `sol-loop`, `file-pr`, `babysit-pr`). The "make them yours" section is the right instruction — put per-machine settings in `CLAUDE.md`/`AGENTS.md` so skill updates do not clobber your config — and that pattern is directly transferable to how we write Hermes skills. `council` is the closest thing to the multi-model review we do by hand when I want a second opinion on a rewrite.

**Pros:**
- **Explicit, sentence-shaped triggers** — the user says "full send", not "please orchestrate the PR pipeline".
- **Composition is documented** — each skill lists which others it needs, so partial adoption is safe.
- **The personal-settings-in-`AGENTS.md` pattern** is worth stealing regardless of the repo.
- **MIT, 2.5k stars, quick to read** — nine short skill files, no runtime.

**Cons:**
- **It assumes a GitHub PR queue and `gh` auth.** Our deployments are `docker` commands and `scp` to `/var/www`, documented in memory — there is no PR to babysit.
- **`council` and `sol-loop` need models on other providers**, which on the reference implementation means T3 Code's `delegate_task`. Without that, the most interesting skill does not run.
- **Four days old and mostly one author's personal workflow.** 158 forks in four days is attention, not validation.
- **PR-hardening is the wrong safety model for us.** "Merge it and babysit CI" is a workflow where a human reviews the diff afterwards; our risk is a cron job acting without anyone looking at all.

**Should we...**
- ❌ **Skip it** — no PR queue, and the parts that would transfer are two sentences of a pattern, not the repo.

**Impact on our stack:** Low — no PR workflow to improve.

**Why:** The skills are well written and the composition is clean, which makes this a slightly annoying skip. But every one of them ends at "merge the pull request", and we do not merge pull requests — we deploy with `docker` and copy a `dist/` folder. The one transferable idea, keeping machine-specific settings in `AGENTS.md` so skill updates survive, we can apply in an afternoon without installing anything. If the department ever moves to GitHub-flow with review, this becomes the first place to look.

### 8. OXR — SOTA document parsing under a licence that is not open enough for a hospital

**What it is:** A 1.3B document-parsing model from SoMark that converts PDFs and page images into Markdown/JSON with layout coordinates, covering 13 element types. It claims #1 on olmOCR-Bench, OmniDocBench and DocParsingBench, makes layout analysis independently pluggable, and offers a free demo API. Hosted weights on Hugging Face/ModelScope; local operation needs **24 GB of GPU memory minimum, 48 GB recommended** with CUDA 13.

**Source:** https://github.com/SoMarkAI/OXR · licence: https://github.com/SoMarkAI/OXR/blob/main/LICENSE · Provenance: spotted on Github Awesome — https://www.youtube.com/watch?v=S8g5nwZN9as (GitHub Trending Weekly #56, 01:33).

**What's good about it:** The pluggable layout analyser is the right architectural call — layout rules differ by domain (a GME form is not a newspaper) and every other parser welds layout to recognition. The 13 element types include the awkward ones we would need: tables as HTML/Markdown with bounding boxes, handwriting, and stamps.

**Pros:**
- **Layout analysis is replaceable** without touching recognition or reading order — a real differentiator.
- **Benchmark leader across three popular parsing suites**, with a reproduction guide.
- **Bounding-box coordinates on every element**, which is what makes an OCR result auditable.
- **A free API to test against** before committing to anything.

**Cons:**
- **The licence is not Apache-2.0 despite the badge.** The `LICENSE` file describes "Apache License 2.0, subject to additional terms": commercial use is permitted **only** below **$2M total funding or $2M annual revenue**, requires prominent "SoMark OXR" attribution in any online service, and **forbids offering a hosted parsing API that competes with SoMark's**. GitHub and the README both report `NOASSERTION`, which is the correct read and an honest flag — but the badge language still gets quoted as "open source".
- **24 GB of GPU to run it locally, 48 GB recommended.** No machine in our stack qualifies.
- **"SOTA" is self-reported** on three benchmarks in one week, by the company selling the hosted version.
- **Fourteen commits, two authors, 21 open issues** for a 2.7k-star repo — the community is watching, not building.
- **The free API queues your documents** through a third party and the README says explicitly not to use it in production — so for us the *only* usable path is a licence we should not accept and hardware we do not have.

**Should we...**
- ❌ **Skip it** — MiniCPM-OCR (item 3) does the same job as a real Apache-2.0 model in 2 GB of GGUF.

**Impact on our stack:** Low — licence and hardware both disqualify it.

**Why:** OXR is the better-engineered parser on paper and the worse choice for us on two counts we cannot engineer around. The licence is the decisive one: a revenue threshold plus a compulsory attribution clause plus a non-compete on hosted APIs is a procurement conversation for a health system, not a `pip install`, and it is written by the same team whose paid product it protects. The hardware is the second: 24 GB of GPU puts it out of reach of every machine we control, while MiniCPM-OCR claims the same document-parsing job from ~2 GB of GGUF under real Apache-2.0. Where OXR *is* still useful is as a measuring stick — its free API is a way to check whether MiniCPM-OCR's output on our documents is actually good, and that is a legitimate, non-committal use of a deceptively-licensed model.

## Overall assessment

If we do nothing else, do these, in this order:

1. **Project Quarry, as a nightly audit over our cron transcripts.** It is the only item this month that answers a question we currently cannot answer — *did the unattended jobs do anything they were not supposed to do* — and I ran it here with a rule written in the shape of our July incident: it fired on the offending transcript and stayed silent on the clean one, from a `uv sync` in this container. The cost is one rules directory, one wrapper script, and a line in the nightly review; the DSL will churn before v1.0 but the rules are small enough that churn is an hour, not a project.

2. **MiniCPM-OCR on the desktop, against five real documents from the reimbursement folder.** Document parsing is the oldest unaddressed gap in this stack — call-out paperwork and reimbursement forms are images to every job we run — and this is the first release in weeks that fits in ~2 GB of GGUF under a licence we can actually accept. The test is an afternoon: Q8 through Ollama, time it, check the tables. If it works, a nightly job turns new attachments into text; if it fails, the answer was Jev auditing a bigger parser, and we have lost an afternoon to knowing that.

3. **Floorplan, exported once from the desktop against the Unified Platform.** It is not an adoption — it is a diagnostic we keep doing by hand and getting wrong. The last three schedule/dashboard incidents were all request→endpoint mismatches behind Traefik, which is exactly the edge this tool draws. One afternoon, one exported HTML, and either we gain a map we keep current or we learn the map is hand-wavy and stop treating codebase diagrams as a tooling problem.

The rest are correctly parked: Kensaku's index lives on the wrong machine, Kimi K3.1 Pro is a long-context API trial at best and its weights do not exist yet, and Kero, TStack and OXR are good software pointed at people and problems that are not ours.
