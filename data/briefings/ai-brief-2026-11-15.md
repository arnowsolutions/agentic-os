### shorts-kit

**What it is:** A 10-skill agent pack plus a Remotion component library that takes a topic all the way to a finished vertical short — facts first, script, TTS, scenes, render, cover, caption — and stops before upload. It also ships `sk-promo` for 16:9 product and launch films, a 160+ recipe shot library, and 20 named storytelling flows.

**Source:** https://github.com/howznguyen/shorts-kit · Provenance: spotted on Github Awesome — https://www.youtube.com/watch?v=vnq7Gq2ZxzY (chapter 13:00)

**What's good about it:** This is the only thing in today's scan that maps directly onto a program we are already building. Shareef has 28 faculty interview clips and wants a content creation flow with automated posting — shorts-kit is the production half of exactly that, minus the posting (it deliberately never posts). What makes it more than a template pack is the **fact ledger** (`docs/facts/`): no sentence enters a script until its claim has a verified record, and a linter enforces it. For clinical content that is the difference between usable and unusable — a residency program cannot publish an unverified claim about a procedure. The `SOUL.md` rulebook tags every rule `[measured]`, `[default]`, `[craft]` or `[hard]`, so the voice can be re-authored per channel without breaking the mechanics. And `bun run ingest` + `bun run cut` takes his own recorded voice through Whisper, proposes filler/retake cuts, and drives the video from that audio instead of TTS — which means the faculty's actual voices can carry the clips.

**Pros:**
- 1,004 files, 537 under `src/` — a real Remotion codebase, not a docs shell: word-timed captions, kinetic type, safe-zone overlay, music bed, camera moves, and a maps/globe module (Natural Earth coastlines, borders, routes that draw on).
- Bring-your-own-voice path (`ingest` → Whisper → cut) is the only way a 28-clip faculty library becomes shorts without sounding synthesised.
- Fact ledger + linter is a governance mechanism we would otherwise have to write ourselves, and it generalises past video.
- `bun run dev gallery` browses every shared graphic, so a non-programmer can pick a look instead of describing one.
- MIT, no account, no service dependency — it renders locally.

**Cons:**
- One contributor, eleven days old, no test suite visible. Every rule in it is one person's experience of one channel; the README is honest that topics far from that niche flopped.
- Rendering is Remotion behind headless Chrome on 4 CPU cores with no GPU. A 60-second short will be slow, and `/workspace` is at 93% (15 GB free) — Chrome's shell plus `node_modules` eats into that.
- The defaults are tuned to a Vietnamese knowledge channel; `SOUL.md` has to be rewritten for "Elite Humanism" and for clinical accuracy before the first real render.
- "Never posts anything" means the posting half of our flow stays unbuilt — this solves production, not distribution.

**Should we...**
- 👀 **Watch it** — but pilot it this week on two clips. It is too young to adopt wholesale and too relevant to leave sitting.

**Impact on our stack:** High — agentic-os content pipeline. Concretely: a `content/` workspace inside agentic-os that takes a faculty clip, transcribes it, and emits a 9:16 cut with captions and a cover, with the fact ledger as the gate before anything renders.

**Why:** Because the social media program has a stated shape — interview clips in, finished posts out — and every piece of it we have built so far is either distribution plumbing or a design skill. shorts-kit is the missing production layer, and it comes with the one thing we cannot invent cheaply: a pass/fail gate on claims. The honest caveat is maturity, not fit: one author, eleven days, tuned to someone else's channel. So the right move is a two-clip trial with our own `SOUL.md`, run on the VPS where bun 1.3.14 and node 22 already exist, and judge it on the third clip. If the renders hold up and the fact linter survives clinical content, it earns a permanent place and the posting side stays our problem to solve separately.

### sand3d

**What it is:** A Python library for writing 3D objects as short programs — profiles, solids, edits, frames, joints and assemblies — over Blender's `bpy`. A model writes a part in a few hundred tokens; a person can read it. Exports GLB, URDF, USD, IFC, OBJ, STL.

**Source:** https://github.com/Sandflow-ai/sand3d · Docs: https://sand3d.sandflow.ai/ · Provenance: spotted on Github Awesome — https://www.youtube.com/watch?v=vnq7Gq2ZxzY (chapter 1:59)

**What's good about it:** The design problem it solves is the one that makes LLM-authored 3D useless: coordinates. sand3d addresses parts, edges and faces **by name**, never by hand-computed position, and the whole API fits in ~3,600 tokens — so a model can hold the entire vocabulary in context and still produce something deterministic ("the same program builds the same mesh, bit for bit"). The token comparison is measured part by part on a published page: 2–6× fewer tokens than Blender Python, CadQuery or FeatureScript for the same part. Real joints — `s3d.joint("door_hinge", door, hinge, axis="-Z", range=(0, 143))` — are what separate it from a mesh generator: a washer with a door that opens and a drum that spins is a 38-line program. For a residency program, anatomy cutaways and equipment explainers suddenly become something an agent can build and a human can audit line by line.

**Pros:**
- Apache-2.0, CI running bpy 5.2, 7 contributors, 14 open issues in twelve days — unusually healthy for a repo this young, and Sandflow is a company with public datasets and an explorer space on Hugging Face.
- Named access plus deterministic output means a render we approved can be reproduced exactly, which matters when a graphic goes on a public department account.
- One-call export to GLB/USD/STL/URDF covers both a still render and an interactive web asset for the Unified Platform.
- The API being ~3,600 tokens means it can live in a skill file rather than a retrieval step.

**Cons:**
- **Hard blocker on our box:** `bpy` has no wheel for Python 3.12, and the container's `python3` is 3.12.14. The README asks for 3.13 (bpy 5.2) or 3.11 (bpy 4.5). Adopting means a separate 3.13 interpreter and a ~1 GB Blender module — and `/app/venv` is a container layer, not a volume, so it evaporates on `docker recreate`.
- 15 GB free on `/workspace`. Blender plus a render cache is a meaningful bite of that.
- Twelve days old. The API is stable today; nothing guarantees it stays stable across a bpy upgrade.
- No GPU. Blender on CPU renders fine for stills, slowly for anything animated.

**Should we...**
- 👀 **Watch it** — and test it on the desktop first, where Python 3.13 and Blender are one installer away, before touching the VPS.

**Impact on our stack:** Medium — agentic-os design/content, and indirectly the Manim rendering path. A named-part 3D pipeline would let us produce anatomy and equipment visuals for education posts that are auditable rather than plausible-looking.

**Why:** We already render Manim in the container and accept that it is CPU-only and slow; sand3d is the 3D sibling of that capability, and its token efficiency plus named-part addressing is a genuine advance over writing Blender Python by hand. But the Python version requirement is not a detail — it is the whole question of where this runs. On the VPS it needs a 3.13 sidecar that survives `docker recreate` and ~1 GB of disk we do not really have; on the Windows desktop it is a normal install. The sensible sequence is one anatomy still built on the desktop from a short program, judged on whether it is good enough to publish, and only then a decision about where it lives permanently. Until that still exists, this is a watch.

### gpucanvas

**What it is:** A WebGPU infinite canvas that puts thousands of *live* DOM and React nodes on one surface — pan, zoom, click, type — with an editor, WGSL shader effects, pixel diffs, snapshot filmstrips, and an "agent view" that exposes what is on the canvas as a short JSON tree plus an image of any region.

**Source:** https://github.com/berkantay/gpucanvas · Demo: https://berkantay.github.io/gpucanvas/ · Provenance: spotted on Github Awesome — https://www.youtube.com/watch?v=vnq7Gq2ZxzY (chapter 14:49)

**What's good about it:** The interesting part is not the rendering, it is the **agent view**: an agent can read a structured description of what is on screen, point at a specific node with a mark, and drop a comment pin — all against live components, not screenshots. That is precisely the missing piece in our redesign review gate, where 18 surfaces sit in Decision Studio and the feedback loop is currently "Shareef looks at a preview and writes a note". Pixel diffs between versions and a filmstrip of a node's history would make the redesign-compare flow reviewable rather than impressionistic. The 5,000-screen benchmark (plain DOM vs canvas, frame rate measured live on both sides) is a credible demonstration, and it degrades honestly: without WebGPU it is just a page.

**Pros:**
- Marks — arrows between elements, comment pins, live agent cursors that follow the camera — turn a review into an annotated artifact instead of a paragraph of prose.
- Snapshots and pixel diffs give us a machine-checkable answer to "did the redesign actually change this component".
- Real DOM under the canvas means clicks, typing and React state still work; it is not a screenshot tool pretending to be interactive.
- MIT, and the demo is self-serve in a browser, so it can be evaluated in ten minutes.

**Cons:**
- Three days old, one contributor, one open issue. Nothing about it has been exercised at our scale, and the README's headline benchmark is recorded on a MacBook Pro.
- Requires Chrome 157 or later with WebGPU — which no phone browser in a clinic reliably has, so it cannot be the primary review surface for anyone but us.
- It is a rendering layer, not a product. Hosting it means owning a React app that mounts our components inside it.
- A second rendering path for the same UI is a maintenance liability as long as the platform itself is still being ported.

**Should we...**
- 👀 **Watch it** — steal the *idea* of an agent-readable canvas view for the review gate before adopting the library.

**Impact on our stack:** Medium — Unified Platform design-review workflow (Decision Studio / redesign-compare). Not a user-facing change; a change to how review evidence is captured and compared.

**Why:** Our adoption gate currently depends on Shareef opening a preview URL and forming a judgement in prose, and the decisions live in localStorage. gpucanvas suggests a better shape: an agent that can read the live surface, mark the exact element under discussion, and store a pixel diff against the previous version — reviewable evidence rather than adjectives. That is worth building toward. But it is three days old with one author, it needs a browser most of our users do not have, and mounting the Unified Platform's components inside someone else's canvas while that platform is mid-port is how a redesign grows a second head. Watch the repo, and if a review round in December would benefit, prototype the agent-view JSON on one surface rather than the whole canvas.

### Yogurt

**What it is:** A free, open-source alternative to Granola: a desktop app that records your mic and system audio, transcribes locally with whisper.cpp, summarises with a local open-weight model through llama.cpp, and exposes the notes to an assistant over a local MCP server. No bot joins the call.

**Source:** https://github.com/FrigadeHQ/yogurt · Site: https://yogurt.so · Provenance: spotted on Github Awesome — https://www.youtube.com/watch?v=vnq7Gq2ZxzY (chapter 2:25)

**What's good about it:** Everything stays on the machine — audio, transcripts and the model itself — which is the only architecture worth considering for anything said in a residency program's meetings. It ships a Linux x86_64 AppImage as well as Mac and Windows builds, so it is not a Mac-only toy. The local MCP server is the detail that makes it structurally interesting to us: an assistant that can read and search your meeting notes without those notes leaving the laptop. And it is not a weekend project — seven contributors, MIT, seventeen open issues, pushed today, from a company (Frigade) that ships product.

**Pros:**
- Local whisper.cpp + llama.cpp with no account required; after a one-time 5–14 GB model download it works offline.
- Speaker attribution from Zoom/Teams/Meet (Mac only for now) and 99-language multi-language mode.
- Answers cite the meeting they came from, and everything exports to Markdown.
- Local MCP server means Hermes could query it — no bespoke export step.

**Cons:**
- It captures a microphone and system audio. The VPS has neither, and it never will; this can only run on Shareef's own machine.
- The useful model is a 5–14 GB download. On a 15 GB-free disk, that is not a casual install.
- Speaker naming and calendar integration are Mac-only, and the machine in question is Windows.
- Meeting capture in a healthcare setting is a policy question before it is a technical one — consent, retention, and whether recorded PHI may exist in a local app at all.

**Should we...**
- 👀 **Watch it** — with a note to run it on the desktop under a test account, not the VPS.

**Impact on our stack:** Medium — a personal note layer for Shareef's meetings that Hermes could read via MCP, with no cloud dependency. Adjacent to the voice agent, not a replacement for it.

**Why:** The architecture is right and the packaging is real: MIT, cross-platform, local models, MCP out. But nothing about it can run where our stack runs — it needs a microphone, and the value is in the room with the person, not on a server. That makes this a desktop install decision, not a platform one, and the sequencing matters: a local note store that Hermes can query would be genuinely useful for the residency work, but recording department meetings crosses a policy line that has to be settled first, in writing, before an app is installed. Watch it, and if it survives a policy check, install it on the Windows machine and wire the MCP server into Hermes there.

### Haru-4B

**What it is:** An open pretrained full-duplex spoken dialogue model — it listens and speaks simultaneously, taking one audio frame and emitting one frame of its own audio plus text every 133 ms. Inference code in PyTorch, MLX (Apple), and as a vLLM-Omni plugin, with weights on Hugging Face.

**Source:** https://github.com/higurashi-ai/Haru · Weights: https://huggingface.co/higurashi-ai/Haru-4B · Provenance: spotted on Github Awesome — https://www.youtube.com/watch?v=vnq7Gq2ZxzY (chapter 6:30)

**What's good about it:** Full duplex at 7.5 Hz is the difference between a voice agent and a walkie-talkie. The user's audio frame, the model's last text token and its last speech latent are summed into a single position of the language model, so listening and speaking never block each other — no separate audio transformer, no discrete audio tokens, one MLP head producing a 64-dimensional audio latent in a single sampling step. Character comes from a text card, voice from a 3-second-to-3-minute reference clip. Nine languages. That is a compact, well-documented design, and the inclusion of a vLLM plugin means it is meant to be served, not just demoed.

**Pros:**
- True simultaneity — barge-in without a VAD turn-taking hack, which is where our current voice path is weakest.
- Voice cloning from a short reference clip makes a consistent brand voice possible without a hosted TTS vendor.
- Apache-2.0 with weights published, and three separate inference paths including an MLX build for a Mac.
- The architecture write-up is specific enough to audit (frame rate, latent size, codec, prompt structure).

**Cons:**
- "With an NVIDIA GPU (about 12 GB of memory)" — we have no GPU on the VPS, and 12 GB of VRAM is not a rounding error.
- Two days old, two contributors, two open issues. No evidence yet of stability across a long conversation.
- The README is explicit that you must only clone voices you have the right to use — for a public-facing department voice, that is a licensing conversation, not a config flag.
- Latency claims assume wired mic and headphones; Bluetooth adds 100 ms or more, which is the whole budget.

**Should we...**
- 👀 **Watch it** — it cannot run on our hardware today, and voice cloning needs a rights decision before it needs an install.

**Impact on our stack:** Medium — the voice agent (Kimberly, `/opt/arnow-voice`). A full-duplex model would replace the turn-taking logic in the current pipeline with a model that handles overlap natively.

**Why:** Our voice agent's weak point is not the model's knowledge, it is the rhythm — the pause where it decides the human has finished. Haru-4B attacks that at the architecture level rather than with a better VAD, and it does so under Apache-2.0 with weights out. But it needs a 12 GB NVIDIA card, and the VPS has none; running it would mean renting a GPU instance purely for voice, which is a real monthly cost against a benefit we have not measured. The right move is to watch it, and if voice becomes a priority, benchmark it on rented GPU time against the current pipeline on the same five calls before committing to hardware. The voice-cloning capability can wait until there is a documented right to the voice being cloned.

### pine (pmndrs/pine)

**What it is:** A CLI agent harness from the poimandres collective — agents that subscribe to event sources (file watchers, webhooks, commands, endpoints) and react, with chat, coding, memory, sub-agent orchestration and a terminal UI with tabs, images and drag-and-drop.

**Source:** https://github.com/pmndrs/pine · Provenance: spotted on Github Awesome — https://www.youtube.com/watch?v=vnq7Gq2ZxzY (chapter 5:34)

**What's good about it:** The event-source model is the interesting idea: an event source is just a `*.ts` service with a schema, and you tell the agent what you want in words ("watch ~/documents/scans, for every new file: extract summaries"), which it wires up through administrative tool calls rather than a config file. That is a cleaner mental model than cron expressions plus a shell script. The BM25 self-discovery manual tool — letting the agent look up its own API on demand instead of carrying docs in context — is a good pattern. And it is macOS/Linux with a real CLI, not a chat window.

**Pros:**
- Event sources as first-class, schema-bearing services is a better abstraction than what our watchdogs hand-roll.
- Agents configure themselves through tool calls, never touching user config.
- Parallel sub-agents, `/goal` persistence, plan mode, diffs and undo are all present.
- MIT, from a collective with a long track record (react-three-fiber, drei, zustand).

**Cons:**
- **It is a second harness.** Hermes already owns cron, watchdogs, skills, memory and tool policy on this box; running pine alongside means two agents with overlapping jobs and two places to look when something fires twice.
- Three days old, one contributor — no matter how good the pedigree, nothing here has a track record.
- Computer use is macOS-only, and Windows support is explicitly unfinished.
- The event-source idea is portable; the harness is not. We can take the pattern without taking the dependency.

**Should we...**
- ❌ **Skip it** — the abstraction is worth borrowing, the binary is not.

**Impact on our stack:** Low — no system improves by adding a parallel harness. The concrete takeaway is a pattern, not an install: an event source as a declared, schema-bearing file rather than a script plus a crontab line.

**Why:** We have spent months making one agent stack reliable on this box: watchdogs installed as external background processes because cron-scheduled ones die with the gateway, skills as the unit of procedure, memory as the record. Every one of those decisions was about there being exactly one place where agency lives. A second harness — three days old, one author, unfinished on Windows, with its own memory and its own tool policy — fragments that for no capability we lack. What is genuinely better in pine is the shape of an event source: named, typed, discoverable, and something an agent can create on request. That is worth writing down as a pattern for how our watchdog installers and cron jobs should be declared. Watch for the abstraction, skip the product.

### ARTEX — FBI FLASH-20261113-001

**What it is:** An open-source, LLM-driven autonomous penetration-testing framework that chains reconnaissance through data exfiltration at machine speed. The FBI issued a flash alert on 2026-11-13 warning that criminal and nation-state actors are using it against government and critical sectors, healthcare among them.

**Source:** https://therecord.media/artex-ai-tool-fbi-flash-alert · Primary: https://www.ic3.gov/CSA/2026/261113.pdf · Provenance: Google News RSS (`AI agent` query, 2026-11-13/14)

**What's good about it:** As intel rather than as a tool: the advisory quantifies what "agents change the threat model" means in practice. Intrusions reaching privileged access in under three hours, multiple targets in parallel, minimal operator expertise required. Censys counted over 1,600 publicly exposed Artex console instances. The named target sectors include **healthcare**, and Amazon's parallel study describes a self-sustaining loop where stolen API keys pay for the inference that hunts more keys. That is a direct description of the environment any autonomous agent stack now lives in — including ours.

**Pros:**
- Concrete, dated, primary-source advisory (IC3 FLASH-20261113-001 with IOCs) rather than a vendor blog.
- Names healthcare as a target sector, which makes it a departmental concern rather than a generic infosec headline.
- The 1,600 exposed console figure is a useful reminder that agent frameworks are being deployed with default-open interfaces.
- Provides IOCs and a CSV, so it can be checked against logs rather than merely read.

**Cons:**
- Not actionable against Hermes specifically — our exposure surface is our own services, not Artex consoles.
- The framework itself was pulled from GitHub by its author in October and lives on through forks, so there is no clean upstream to block.
- Sector-level warnings are easy to file and forget; without a concrete checklist they change nothing.
- The economics described (stolen keys funding further inference) primarily threaten LLM API credentials, which we do hold.

**Should we...**
- 👀 **Watch it** — and do the one concrete thing it implies: confirm no agent-facing endpoint of ours answers without auth from a datacenter IP.

**Impact on our stack:** Medium — agentic-os and the Unified Platform's public surfaces. The specific change: a short access review of every service that an agent or the public internet can reach, plus rotation discipline for model API keys.

**Why:** We run autonomous agents with shell access, a public schedule page, an interview portal, a voice service and a CRM, and the vault has carried four separate agent-security stories this year. This advisory is the first one to name healthcare explicitly and to put a number on the speed — under three hours from targeting to privileged access. None of that requires new software; it requires checking that the things we already exposed are authenticated. The one thing to verify this week is that no agent-facing endpoint answers unauthenticated from a datacenter IP, and that model API keys are rotated on a schedule rather than on incident. That is a thirty-minute job that would be embarrassing to skip.

## Overall assessment

If we do nothing else, do these, in this order:

1. **Pilot shorts-kit on two faculty clips** — it is the only item today that advances the social media program from "we have 28 clips" to "we have a repeatable production line with a fact gate", and the fact ledger alone is worth the trial.
2. **Test sand3d on the desktop, not the VPS** — one anatomy still, built from a short program, to find out whether auditable 3D is good enough to publish; the Python 3.12 blocker makes the VPS the wrong place to answer that question.
3. **Do the thirty-minute access review the ARTEX advisory implies** — confirm nothing agent-facing answers unauthenticated from a datacenter IP, and put model API key rotation on a schedule.

Nothing today earned an unconditional adopt, and that is the honest reading: the strongest items are all under two weeks old, several have a single author, and two of them cannot run on our hardware at all. What they share is a direction — agents producing verifiable artifacts rather than plausible ones — and each pilot above is a cheap way to test that direction against work we actually have to ship.
