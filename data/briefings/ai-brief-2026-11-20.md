### NVIDIA SkillEvaluator

**What it is:** A Python CLI and agent skill that evaluates other agent skills: 500+ static quality/security rules in Tier 1 (schema, PII, license, Unicode, script linting, plus SkillSpector, Gitleaks and Bandit scanners), harness-compatibility checks per agent, semantic overlap detection, and optional live agent evaluation that measures whether a skill actually improves task results. Version 1.0.1 was published to PyPI on Nov 18, 2026.

**Source:** https://github.com/NVIDIA/SkillEvaluator · Docs: https://docs.nvidia.com/skills/skillevaluator/  ·  Provenance: spotted on ManuAGI — https://www.youtube.com/watch?v=QCEEjQMYR1M (chapter 5:13)

**What's good about it:** I ran it rather than reading about it. `skillevaluator harness-check` walked `/home/hermeswebui/.hermes/skills` and reported **662 skills and 107,872 characters of descriptions** — that last number is the standing context tax we pay on every skill listing, and we have never been able to measure it before. `quality-check` on `or-schedule-briefing-parser` returned 88.0/100 (grade B) with a single MEDIUM finding: `metadata.author` missing from the spec — the kind of small, fixable defect that accumulates silently across 662 folders. Most important, its harness matrix has a **`hermes` profile and it returns "loads"** for our loader, which means it was built with our format in mind, not retrofitted. The keyless tier needs no API key, no GPU, no Docker.

**Pros:**
- Free Tier 1 runs with no LLM key: `validate --tiers 1` gives quality, schema, security and PII checks in one pass, so it can gate every skill install at zero marginal cost.
- The `hermes` harness profile means description-length limits and front-matter requirements are checked against our actual loader instead of a generic one.
- Semantic overlap detection is directly aimed at our known problem: duplicated skills (`impeccable` vs multiple design-skill forks, three separate `craft` entries in the vault) that compete for the same routing slots.
- NVIDIA-backed, Apache-2.0, on PyPI with a real 1.0 release (0.6 → 1.0.1 across October–November), a published arXiv paper (2608.20614) and CI templates for GitHub/GitLab.
- Installs as an agent skill itself (`npx skills add NVIDIA/SkillEvaluator`), so the quality question can be asked inside the session: "is my skill any good?"
- Tier 3 can compare runs with and without a skill, which is the only honest way to know whether a skill earns its context.

**Cons:**
- Installing into the shared interpreter pulled `click>=8.3.3`, which fought the pins in our existing stack (browser-use wants `click==8.3.1`, composio wants `rich<14`). I restored `click 8.5.1` / `rich 14.3.1` afterwards and the CLI still runs — but the correct install is an isolated venv, not `pip --user`.
- Tier 3 live evaluation needs an NVIDIA Build key and real agent runs; that is time and tokens per skill, not a free scan.
- It assumes the agentskills.io spec. Hermes skills with non-standard front matter get flagged as missing fields, so the first full run will produce noise that has to be triaged once.
- The harness matrix reports "not found" for every other agent's directory (claude-code, codex, copilot-cli, opencode) unless skills are installed there too — real output looked like "5 of 6 not loaded" for a skill that is perfectly fine.
- 57 open issues and roughly five months of history; it scores and reports, it does not fix anything for you.
- One more thing to keep current: the rule set will need updating as agentskills.io evolves.

**Should we...**
- ✅ **Adopt it** — as the audit gate for the skill library, not as a runtime dependency. Concretely: isolated venv at `~/.hermes/venvs/skillevaluator`, a monthly `validate --tiers 1` sweep over all 662 skills, `harness-check` on anything new before it is installed, and one pass to trim the description budget.

**Impact on our stack:** High — the Hermes skill library and every cron job that loads it. A 107,872-character description catalog is context spent before any work begins; cutting the bottom quartile of duplicate or verbose skills is a recurring saving, and a quality floor stops the slow drift into 662 unevenly-maintained folders.

**Why:** Our skills are the operating system of this whole stack — cron briefs, deploy recipes, brand voice, vault filing — and until today we had no instrument for them. Every other item in this brief is a tool that might help one workflow; this is the first thing that measures the layer all the workflows run on, and it already produced a number worth acting on before I finished the first command. It is also the only item today that I could install and verify end to end inside our actual environment, which is the difference between a promising repo and an adoptable one. The risk is low and reversible (a venv and a report), the finding is immediate, and the ongoing cost is one monthly command.

### DataCat (replit/datacat)

**What it is:** A self-hosted observability platform — metrics, logs, distributed traces, dashboards, host maps and alerts — running as one process that serves the API, web UI and installer, storing telemetry in PostgreSQL (or ClickHouse) and accepting OpenTelemetry and Datadog-compatible agent traffic. Includes an OTel-Collector-based host agent plus Node.js and Python instrumentation libraries.

**Source:** https://github.com/replit/datacat  ·  Provenance: spotted on Github Awesome — https://www.youtube.com/watch?v=uZHMYykJMAw (chapter 1:27); created 2026-11-17 per the GitHub API

**What's good about it:** It is aimed exactly at the failure mode we actually suffer, which is silence rather than downtime. This prompt now carries three separate PROOF RULEs because one cron run skipped its email without saying so; the watchdogs exist because a container restart can quietly take a background process with it. DataCat gives cron wrappers somewhere to write a run trace, a duration and a success flag, and gives us a dashboard and webhook alert when a job that should have run at 06:00 did not. Because intake is OTLP/HTTP, instrumentation is a few lines in a Python wrapper, not a rewrite. `GET /api/v1/intake/stats` reports stored-versus-dropped per intake path, which is the anti-silence guarantee we have been hand-rolling.

**Pros:**
- Single-process deployment with docker compose; stores in the PostgreSQL we already run, so no new database engine to operate.
- Native OTLP/HTTP for traces, metrics and logs plus Datadog-intake compatibility — no vendor SDK lock-in at the instrumentation layer.
- Webhook and Slack alerting on metric, log and trace monitors means a failed brief can page instead of disappearing.
- Local email/password accounts and single-use invites; no hosted account required, no external service in the data path.
- Apache-2.0, multiple Replit engineers committing daily (three distinct authors in the first three days), and a real self-hosting doc rather than a README stub.

**Cons:**
- Three days old, 433 stars, six pull requests — there is no operating history, no release notes and no evidence of anyone running it at scale.
- No email alerting; webhook or Slack only, so we would need a relay script to get a Telegram or inbox ping.
- It is inert until every job is instrumented — the value is proportional to work we have not done yet, and there is no auto-discovery of cron schedules.
- Another Postgres-backed service with its own auth on the VPS: RAM, disk, backup scope and one more public surface to keep patched.
- Retention, HA and upgrade paths are undocumented at this age.
- Node 22.15+ and pnpm 10.11 required for source builds; the compose path is easier but pins us to their packaging.

**Should we...**
- 👀 **Watch it** — the right shape for our biggest operational hole, but a three-day-old project should not become the system that tells us whether production is healthy. Revisit at the first tagged release or ~30 days of commit history; in the meantime, wrap cron jobs in a heartbeat file so the data is ready when we install something.

**Impact on our stack:** High — Hermes cron and the Unified Platform. Traces per job plus a monitor on the daily brief would convert "did it run?" from an inference into a fact, and the same instance would cover UP route latency and container health.

**Why:** The honest ranking here is "best idea, wrong week." We have lost real work to silent failures — the proof rules in this prompt are scar tissue — and DataCat is the first self-hosted thing I have seen that addresses it without asking us to adopt a SaaS or re-instrument in a proprietary SDK. But at three days old it is a bet on a stranger's weekend, and the whole point of an observability system is that it is more reliable than the thing it watches. Watch it, keep the heartbeat instrumentation cheap in the meantime, and adopt at the first stable release. The instrumentation work is not wasted either way, because OTLP is OTLP.

### Obscura

**What it is:** A headless browser engine written in Rust for AI agents and scraping: runs real JavaScript via V8, speaks the Chrome DevTools Protocol, and is positioned as a drop-in replacement for headless Chrome with Puppeteer and Playwright. Native rendering means screenshots, live screencasts and PDF export without a Chromium download.

**Source:** https://github.com/h4ckf0r0day/obscura · Site: https://obscura.sh · Provenance: spotted on Github Awesome — https://www.youtube.com/watch?v=uZHMYykJMAw (chapter 1:51)

**What's good about it:** Playwright plus Chromium is the single heaviest dependency we carry for scraping, and it is the usual suspect when a container runs out of memory mid-job. Obscura claims 30 MB resident against 200 MB+, a ~70 MiB binary against 300 MB, and 85 ms page loads against ~500 ms, all while staying CDP-compatible — which matters more than the numbers, because CDP-compatible means existing Playwright code can point at it without a rewrite. Cloudflare has already built a product on this idea: their Kitesurf agent-first browser started by porting Obscura to Workers, which is an unusually strong external validation for a project this size. It also ships on GitHub with Apache-2.0 and 112 contributors, so it is not a single-author artifact.

**Pros:**
- CDP + Puppeteer/Playwright compatibility means a pilot can be one environment variable, not a code migration.
- Memory and startup profile are the difference between a browser step fitting in a small container and OOM-killing the job.
- Native PDF export and screenshots map directly onto our brief generation and design-preview workflows.
- Apache-2.0 core with an explicit "no feature gating, ever" commitment, and daily commits (three fix commits on Nov 20 alone).
- Real-world validation through Cloudflare's Kitesurf prototype, plus 36.6K stars and 2.9K forks.

**Cons:**
- Every performance number in that table is the vendor's own; there is no third-party benchmark, and "85 ms page load" is not a number that survives contact with a real site.
- A native rendering engine is not Chrome. Edge-case CSS, exotic JS and anything that sniffs the engine will diverge, so scrapers tuned against Chrome behaviour can break in ways that are hard to diagnose.
- "Anti-detect built-in" does not change the fact that our scraping runs from a datacenter IP; the sites that block us will still block us.
- 269 open issues against a project with a small core team, and an "Obscura Cloud" upsell on the roadmap — the no-gating promise is a promise, not a license term.
- Reviewing it properly means running our five most fragile scrapers against both engines, which is half a day of work.

**Should we...**
- 👀 **Watch it** — with a concrete pilot: point one non-critical scraper at Obscura and compare output against Playwright. Adopt only after two weeks of identical results and a measured memory drop in the container.

**Impact on our stack:** Medium — Hermes scraping/automation and the container's memory budget. A drop-in swap would let the same VPS run browser work without the Chromium tax, and would make browser steps viable inside more cron jobs.

**Why:** This is the rare "drop-in replacement" claim that is architecturally plausible, because CDP is a real contract and Playwright already speaks it. That is why it is worth attention and why it is still not an adopt today: the cost of being wrong is a scraper that silently returns different HTML, and the cost of waiting is nothing. Run it beside Playwright on one job, measure memory before and after, and let the diff decide. If it holds, it pays for itself in container headroom on every browser job we run.

### Arcane (getarcaneapp/arcane)

**What it is:** A modern Docker management platform written in Go — containers, stacks, images, networks and volumes, with live logs, a web console, git-based stack updates and multi-environment agents — as a self-hosted web UI over the Docker socket.

**Source:** https://github.com/getarcaneapp/arcane · Docs: https://getarcane.app  ·  Provenance: spotted on ManuAGI — https://www.youtube.com/watch?v=QCEEjQMYR1M (chapter 4:44)

**What's good about it:** The riskiest work we do on the VPS is Docker surgery at the command line — stop, rm, up, watch what the container says as it comes back, and remember that `recreate` (not `restart`) is what wipes the watchdogs. A UI that shows compose stacks, live logs and a console in one place makes that work reviewable instead of improvised, and the stack view is a much better mental model of "which containers belong to the Unified Platform" than a `docker ps` wall. It is BSD-3, written in Go, backed by 10.1K stars and active daily development.

**Pros:**
- Stacks view maps onto our existing compose files, so the deploy loop becomes observable rather than remembered.
- Live logs and a container console in the browser remove a class of "SSH in, grep, guess" incidents.
- Git-based stack updates and multi-environment agents fit how we already deploy (pull, rebuild, restart).
- BSD-3-Clause, 576 forks, active maintainers, and a Snyk vulnerability badge in the README rather than silence.

**Cons:**
- `main` is Arcane v3, a breaking rewrite; the last stable line lives on `release/2.x.x`. Adopting now means tracking a migration mid-flight.
- It exposes the Docker socket through a web app. On a public VPS that is the highest-privilege surface we could add, and it needs its own auth, TLS and network policy.
- It duplicates Portainer/dockge functionality we may already have, so the win is UI taste, not capability.
- It does not fix the actual problem behind our watchdog pain — a container recreate losing `/app` state is a volume question, which no UI answers.
- Version churn plus a feature-request migration to Discussions signals a project still settling its process.

**Should we...**
- 👀 **Watch it** — revisit once v3 has a tagged stable release. If it lands, deploy it behind Traefik with auth on an internal-only route, never on a public hostname.

**Impact on our stack:** Medium — VPS Docker operations and deploy reliability. Concretely, it would shorten the container stop/rm/up loop and make stack state legible during an incident.

**Why:** Most of our production incidents are Docker-shaped, and a good UI genuinely shortens the diagnostic loop. But this specific UI is mid-rewrite and would sit on top of the Docker socket, which is the one credential on that box that can do anything. The benefit is convenience; the cost of a mistake is the whole host. Watch it until v3 stabilises, then put it behind Traefik with auth on a route only we can reach, and treat it as a convenience layer — not as the thing that keeps production honest.

### Mimvox

**What it is:** A desktop application, written in Rust, that clones your voice from existing recordings or a short guided read, then speaks any typed text in that voice across roughly 60 languages and dubs video into your voice — with training and synthesis running entirely on your own machine.

**Source:** https://github.com/tarpetos/mimvox  ·  Provenance: spotted on Github Awesome — https://www.youtube.com/watch?v=uZHMYykJMAw (chapter 8:50)

**What's good about it:** The audiobook pipeline is the one place where voice consistency has real value for us: a single narrator voice across chapters, generated locally, with no upload of source audio. Mimvox is explicitly built for that case — its demo is a setup flow, training, an audiobook and dubbing — and it runs on Linux with CUDA or ROCm, which means the desktop GPU can do the work while the VPS stays out of it. Cross-platform builds (Windows, Linux, Apple Silicon) and a local-only architecture are the right defaults for anything touching a person's voice.

**Pros:**
- Fully local: recordings, models and generated audio never leave the machine — the only acceptable architecture for a cloned voice.
- GPU-accelerated on NVIDIA, AMD (ROCm) and Apple Silicon, with CPU fallback for portability.
- Audiobook and dubbing workflows are first-class, not demo afterthoughts.
- Cross-platform desktop builds for all three families we might use.

**Cons:**
- **PolyForm Noncommercial 1.0.0, and the OmniVoice weights it speaks with are non-commercial too.** That is a hard block on any department or business use — this is a personal-audiobooks-only tool.
- The README's own warning: "Early version: expect bugs… features may not work, may work badly."
- Training on CPU takes several hours; without a supported GPU it is not practical, and the VPS has none.
- Desktop GUI only — no headless mode or CLI, so it cannot be wired into a cron or server pipeline.
- A single-author hobby project with 146 stars and one open issue; no track record to lean on.

**Should we...**
- 👀 **Watch it** — the license, not the maturity, is the blocker. Useful for personal audiobook listening today; unusable for anything Shareef publishes or sends.

**Impact on our stack:** Low–Medium — voice/audio. It would improve the M4B audiobook experience and voice-memo output with a consistent cloned narrator, but it cannot run on the VPS and cannot be used for work content under its license.

**Why:** The technical fit is real — local, GPU-capable, audiobook-first — and the audiobook player exists precisely because that workflow matters to him. But a non-commercial license on both the app and the voice model disqualifies it for departmental content, and a desktop-only GUI means it can never be part of an automated pipeline. So the honest verdict is watch: it is worth knowing about, worth trying for personal listening, and worth re-checking if the license ever changes. Licence changes do happen, and this is the one item today where a single file edit would turn a watch into an adopt.

### PaperOrchestra (google-research/paper-orchestra)

**What it is:** A multi-agent research-paper framework from Google Cloud AI Research that takes unconstrained pre-writing material — ideas, experimental logs — and produces submission-ready LaTeX: outline generation, literature synthesis, section writing, content refinement and generated plots, orchestrated as a team of specialised agents.

**Source:** https://github.com/google-research/paper-orchestra  ·  Provenance: spotted on ManuAGI — https://www.youtube.com/watch?v=QCEEjQMYR1M (chapter 6:57)

**What's good about it:** The pipeline shape mirrors what actually goes wrong in academic writing under time pressure: the literature review is thin, the sections do not agree with each other, and the figures come last and badly. PaperOrchestra forces an outline, builds a prioritised literature synthesis, writes sections against it, refines for coherence, and generates plots — which is precisely the sequence a fellow with three weeks and a full service would skip. For a residency program, the highest-value use is not the finished manuscript but the coherent draft that makes the first revision possible, plus a literature pass that would otherwise be a week of tab-hopping.

**Pros:**
- Google Cloud AI Research authorship and an Apache-2.0 license; this is a research artifact, not a startup landing page.
- Explicit multi-agent decomposition (outline → literature → sections → refinement → plots) that is inspectable and can be run stage by stage.
- Produces LaTeX against target conference templates, which removes the formatting tax at the end.
- Literature search is built in rather than bolted on, so citations come from a retrieval step rather than the model's memory.

**Cons:**
- Requires a Conda env on Python 3.11 and Vertex AI / Gemini credentials; it is a research codebase, not a packaged tool.
- It generates manuscripts. Journal and institutional authorship rules require disclosure and human accountability, so using its output as submitted text is an integrity risk, not just a quality risk.
- Nothing in it checks generated claims against the underlying data — the very failure mode that retracts papers.
- It is built for ML research papers; a clinical QI manuscript or an IRB narrative is off-distribution for its templates and literature heuristics.
- 50 open issues, last push Nov 15, and no release tags — a lab artifact with lab-artifact maintenance.

**Should we...**
- 👀 **Watch it** — and if used, use it for the literature and outline stages only, with every generated sentence treated as a claim to verify.

**Impact on our stack:** Medium — research support for the residency program, not operations. It would shorten the distance from "we have data" to "we have a structured draft", which is the step that most often stalls a QI project.

**Why:** A program director's research bottleneck is rarely prose; it is the literature pass and the structural spine, and those are exactly the two stages this framework does well. But the same pipeline that produces a polished manuscript will happily produce a confident, unsourced one, and in a clinical department that is a career problem rather than a style problem. So: watch, then use the outline and literature stages as an assistant with a human reading every citation, and never as an author. If a future release adds claim-level provenance checks, this moves up sharply.

### SignuDoc

**What it is:** An MIT-licensed open-source e-signature application: upload a PDF, place fields, send signing links, and keep the sealed signed copy with an audit certificate. The primary deployment path is one click to Vercel, with Neon for data and Resend for email; a self-hosting guide also exists.

**Source:** https://github.com/NYLLON-SOFTWARE/SignuDoc  ·  Provenance: spotted on The Next New Thing — https://www.youtube.com/watch?v=RweiB44H1n0 (chapter 3:09)

**What's good about it:** It is a genuinely competent DocuSign substitute for a small organisation, with the two features that actually matter — a sealed copy and an audit certificate — and a deployment story simple enough that the README offers a "copy this to your LLM" path. At roughly 250 documents a month on free tiers it is $0 against DocuSign's per-seat pricing, and the code is MIT.

**Pros:**
- MIT license, real audit certificate, sealed document retention.
- Deploy-to-Vercel path with Resend and Neon wired in; also a documented self-hosting route.
- 2.5K stars, active commits, and an explicit "not affiliated with DocuSign" disclaimer rather than trademark games.

**Cons:**
- The happy path is Vercel + Neon + Resend: a third-party host and two third-party services in the path of signed documents — for a hospital department, that is a compliance question, not a convenience.
- Signed documents here are HR, legal and consent artifacts with retention obligations; the tool does not give us the records-governance story those artifacts require.
- Montefiore already has institutional e-signature; adding a second signing authority creates exactly the ambiguity auditors dislike.
- Self-hosting moves the problem rather than solving it: we would own key management, retention and legal hold for signature records.
- No integration with the systems where these documents actually live.

**Should we...**
- ❌ **Skip it** — not because it is weak software, but because signatures are a records-governance problem we already have a governed answer for.

**Impact on our stack:** Low / none. It would add a second, ungoverned signing authority beside the institutional one, and take on retention liability for legal documents.

**Why:** The temptation is obvious — it is free, it is MIT, and it does the thing DocuSign charges for. But the cost of an e-signature system is not the software license; it is the obligation to keep sealed documents retrievable for years, prove who signed what, and defend the audit trail. Standing that up on free Vercel and Neon tiers, administered by us, inside a hospital, is a liability we would be creating to save a line item that the institution already pays. Skip, and if a departmental form ever needs signatures, route it through the existing institutional process.

## Skipped at intake

Also named today and dropped without grading, because none of them can be installed, called, or adopted in a way that changes our stack: **trnrt** (Trainium-only inference engine — we have no Trainium), **tamserve** (multi-camera SAM3 tracking — no cameras, and clinical video would be a HIPAA question first), **zigzag** (macOS browser), **openwren** (desktop mail client — cannot reach Montefiore's O365 tenant), **rust-anything** (behaviour-checked Rust migration — no rewrite on the roadmap), **inference-optimisation-skill** (local LLM serving — we call hosted APIs), **Claude-BugHunter** (red-team skill bundle — not our domain), **rakazo / OpenMausBot / raea / ECC / mattpocock-skills** (already judged in the vault on 2026-10-11 through 2026-11-14), **ArtCraft / craft-launcher** (already adopted 2026-10-09; today's video covers the same 17-app suite), and **Gemini Spark's texting/emailing agent** (consumer Google accounts, partly covered by the existing Spark entry).

## Overall assessment

If we do nothing else, do these, in this order:

1. **Run SkillEvaluator across the whole skill library and fix what it finds.** A monthly `validate --tiers 1` sweep plus `harness-check` on every new skill. What it changes: 662 skills stop being an unmeasured liability, and the 107,872-character description catalog — context we pay for on every turn — starts shrinking.
2. **Instrument the cron jobs with a heartbeat now, and adopt DataCat at its first stable release.** What it changes: "did the brief run?" becomes a fact on a dashboard with an alert, instead of a PROOF RULE in a prompt hoping the job remembered to say so.
3. **Pilot Obscura on one fragile scraper, side by side with Playwright.** What it changes: if it holds, the container stops carrying Chromium for browser work, and browser steps become cheap enough to put inside more jobs.

Everything else today is a watch: worth knowing, not worth installing this week.
