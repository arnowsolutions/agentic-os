### 1. Scientific Agent Skills (K-Dense-AI/scientific-agent-skills)

**What it is:** A 54.3K-star, MIT-licensed library of **177 agent skills** for scientific and clinical work — each one a `SKILL.md` with the conventions, endpoint guidance and validation checks for a specific package, database or workflow. It ships a `database-lookup` skill documenting 80 external databases (ClinicalTrials.gov, ClinVar, cBioPortal, PubChem, ChEMBL, UniProt, gnomAD…), plus clinical-research workflows: pharmacogenomics, variant evidence review, PK/PD modelling and dose-regimen evaluation, aggregate decision-support evaluation, and clinician-authored treatment-plan formatting. Latest release **v2.72.0**; the repo pushed Oct 19 and needs nothing but `gh skill install`.

**Source:** https://github.com/K-Dense-AI/scientific-agent-skills · Provenance: spotted on The Next New Thing — https://www.youtube.com/watch?v=BrBQRNIDRS8 (16:48 chapter, "Scientific Agent Skills for Researchers"); repo metadata and README read directly via the GitHub API.

**What's good about it:** This is the first skills library in weeks whose subject matter is *ours* rather than a generic coding workflow. The clinical-research category is specific about what it will and won't do — "aggregate decision-support research", "source-bound draft report structures", "an aid to severity assessment, never a decision rule" — which is the right posture for a GME environment and reads like it was written by someone who has been through a research-integrity review. The `database-lookup` skill is more valuable than the marketing bullet suggests: it documents *pagination tokens, rate limits and licence status per source*, with an explicit rule that **API payloads are untrusted data** and must never be pasted into a shell — a rule that exists because an agent will otherwise pipe a JSON lab-value field straight into `bash`. It also tells the agent not to invent pagination tokens by incrementing them, which is the exact class of hallucination that makes scraped clinical data worthless. Install path is honest and boring: `gh skill install` with `--pin` for reproducible installs and provenance metadata, across Claude Code, Codex, Gemini CLI, Cursor and Codex hosts.

**Pros:**
- **Clinical-trial and evidence lookups come pre-encoded** — ClinicalTrials.gov, ClinVar, cBioPortal, trial registries — with approval, entitlement and cost caveats per provider, which is the part our own agents would get wrong.
- Same SKILL.md format our skills already use, so the mechanics transfer: no runtime, no server, no API key of its own.
- 54K stars, 478 forks, an actual release cadence (v2.72.0) rather than a launch-day star-bomb, and five categories of maintainers' work visible in the history.
- Pinning + provenance metadata means we can install two skills, not 177, and still say exactly what commit we ran.
- The database skill's untrusted-data rule is a policy we should steal even if we install nothing else.

**Cons:**
- **It is a PHI machine you don't control.** Every one of those 80 databases is an outbound call the agent makes; the moment a skill gets handed a real MRN, a resident's record or a patient list, data leaves our boundary under someone else's README rules. In practice this means any skill here runs on aggregate, de-identified or published data only — and nothing in the repo enforces that.
- Scope mismatch: it is built for *AI scientists*, not department operations. Residency scheduling, reimbursement reporting and resident evaluation — the things our stack actually does — get nothing from it.
- 177 skills is roughly 170 more than anyone needs; the failure mode is context bloat and an agent confidently invoking a chemoinformatics skill on a scheduling question.
- Deliberately does *not* bundle the docx/pdf/pptx/xlsx document skills (vendored from `anthropics/skills`, now removed for licence reasons), so "make me a slides deck from this clinical trial" needs a second install and a licence read.
- Some of the framing ("used by 250,000+ scientists worldwide", "#1 Agent Skills library") is marketing the repo cannot substantiate; the README's own feature list is the only metric worth trusting.

**Should we...**
- 👀 **Watch it** — keep an eye on it, not ready yet but promising

**Impact on our stack:** Medium-High *later* — Hermes skills + agentic-os. The concrete change: a research subagent that can answer "pull me every trial for X indication, 2024 onward, with phase and enrollment" with correct pagination, provenance links and a no-PHI rule, instead of handing me a plausible-looking list with invented NCT numbers.

**Why:** The honest reason this is a watch and not an adopt is that our bottleneck is not research throughput — it is that we have no PHI boundary for an agent making 80-100 external calls, and installing a library whose entire value is those calls before that boundary exists is how a healthcare-adjacent AI program ends up in an incident review. But the watch is a real watch, not a file-and-forget: the two things worth stealing now are cheap. First, the `database-lookup` skill's untrusted-payload rule belongs in our Hermes system prompt today, because it applies to every RSS fetch, GitHub API call and news scrape our cron jobs already do. Second, the clinical-research skill set is the correct shape for the one genuinely research-shaped thing we run — the Grand Rounds / faculty interview content pipeline needs literature context, and a pinned subset (three skills, aggregate data only) is a defensible pilot once we can state the boundary in one sentence. That is what would move it from watch to adopt: not a new release, but us writing the PHI rule first.

### 2. OSS Verify (theorem-labs/oss-verify)

**What it is:** Theorem Labs' enrollment pipeline for **formal verification of open-source software**: you add a `projects/<name>/` directory (a `project.yaml`, a `Dockerfile`, a `build.sh`) via pull request, their builder compiles your fuzz targets twice and pins the SHA-256 of each binary, and they emit **machine-checked Rocq proofs** stating that no input up to 64 MiB makes that compiled binary crash, hang, or fail an ASan check. Free for qualifying OSI-licensed projects; findings are disclosed privately to a named contact. The repo is Apache-2.0 and carries an explicit attribution to Anthropic's OSS Scanner, which it rewrites from "scanning" to "proving". Shipped Oct 22 alongside Anthropic's research post; 55★, 3 contributors (Jason Gross among them), 8 forks, still pushing today.

**Source:** https://github.com/theorem-labs/oss-verify · https://theorem.dev/oss-verify/ · published proofs: https://github.com/theorem-labs/oss-verify-proofs · Provenance: spotted on Hyperautomation Labs — https://www.youtube.com/watch?v=RxGLRbkCjeU (which also dates the Anthropic post to Oct 22); README, FAQ and org listings read directly.

**What's good about it:** The claim is genuinely different from fuzzing and the site says so precisely: a fuzzer covers the inputs someone thought of, a proof covers the whole square — and crucially, **the theorem is about the compiled RISC-V assembly, not the source translation**, which is the stronger guarantee that most formal-verification pitches quietly skip. The output is checked by the Rocq kernel, so the trust question reduces to "do you trust Rocq", not "do you trust Theorem's model". The process is deliberately modeled on OSS-Fuzz, which thousands of maintainers already know: same shape of files, same `build.sh` contract, and if the project is already in OSS-Fuzz you start from those files. They publish the proofs, they let you `disabled: true` to pause or delete the directory to leave, and they are unusually explicit about the limits — findings and patches are **AI-generated and not guaranteed to be human-reviewed**, there is no disclosure deadline, and dependencies' bugs go to the dependency maintainers.

**Pros:**
- A proof of "no input crashes this" is the only artifact in this whole brief that removes a class of bug instead of finding instances of it — and it is free for qualifying OSS.
- Enrollment is a pull request against a public repo, which means the whole thing is auditable and reversible by design.
- The `AGENTS.md` path means a coding agent can do the enrollment work — including porting the build to static riscv64 — which is normally the expensive part.
- Published proofs and a per-project `patch_style.md` mean the output can be shaped to what a maintainer actually wants.
- Three contributors since Oct 22 is thin, but one of them is a well-known proof-engineering name and the repo is a rewrite of an Anthropic codebase rather than a weekend hack.

**Cons:**
- **We are not eligible in the way that matters.** Eligibility requires a core maintainer of an established OSI-licensed project to enroll. Big Reef's internal apps are neither public nor OSS-Fuzz-shaped, and neither is Hermes.
- 55★ and three days old; the pipeline is a *process*, and the actual prover is theirs. "Free" here means "free while they choose to run it", with no SLA — proofs "can take multiple days".
- Only useful for C-family binaries with fuzz targets today; nothing in Python/TypeScript — i.e. nothing in the Unified Platform or our cron scripts.
- The generated patches are AI-written and explicitly unreviewed, so any bug report they send needs the same scrutiny as any other model output.
- The strong `tools/check` warning — it builds the project's Dockerfile **with network access** — is a real supply-chain hazard for anyone who runs it on a repo they don't fully trust.

**Should we...**
- 👀 **Watch it** — keep an eye on it, not ready yet but promising

**Impact on our stack:** Low-Medium — no system of ours is a C fuzz target, so nothing changes today. The transferable idea is the posture: "prove the property, don't sample the inputs". If it ever supports Python/TypeScript or a self-hosted prover lands, the natural first target is the cron pipeline's parsers, which is exactly where three of this month's silent failures lived.

**Why:** I put this in because the headline is the strongest technical claim in a week of product-launch noise, and because the honest verdict is instructive: the thing is genuinely good and genuinely not for us. Our failures this month were not memory-safety bugs — they were a stale deploy hook, a rotated API key and a parser that silently returned nothing — and not one of those is provable by a Rocq theorem about a compiled binary. Enrolling anything would also mean publishing a project we don't publish, or spending maintainer time we don't have on a repo that isn't ours. So: watch, and take the *idea*, which is that "10 million tests passed" is not evidence and a machine-checked claim about every input is. If Theorem later offers the pipeline to private codebases (they invite "not open source? talk to us" on the site, which is a lead worth following when someone has a week to spend), the first thing to point it at is the cron parsers — but that is a future brief, not this one.

### 3. Cursor Plugins (cursor/plugins)

**What it is:** Cursor's official plugin marketplace repository — 100+ standalone plugin directories, each with a `.cursor-plugin/plugin.json` manifest plus `skills/` (SKILL.md with frontmatter), `rules/` (.mdc), and `mcp.json` server definitions. Two halves: a **dev-workflow** set (`pstack`, `dyl-stack`, `thermos`, `ralph-loop`, `cli-for-agent`, `agent-compatibility`, `continual-learning`, `cursor-team-kit`, `advisor`, `orchestrate`, `pr-review-canvas`, `docs-canvas`, `create-plugin`, `teaching`, `grok-voice`) and an **integrations** set of ~90 third-party MCP connectors (Gmail, Google Drive/Calendar/Docs/Sheets/Slides, GitHub, Playwright, Tailscale, Zoom, Teams, SharePoint, Power BI, Salesforce, Notion-adjacent tools…). 13.8K★, MIT per the README, 1,367 forks, pushed today.

**Source:** https://github.com/cursor/plugins · Provenance: spotted on The Next New Thing — https://www.youtube.com/watch?v=BrBQRNIDRS8 (23:32 chapter, "Cursor Plugins and P-Stack Skills"); README read in full via the GitHub API.

**What's good about it:** `cli-for-agent` is the single most directly useful artifact here for us: it is a written pattern set for designing CLIs that *agents* can drive reliably — flags, help-with-examples, pipelines, error shape, idempotency, dry-run. Every wrapper script in `~/.hermes/scripts/` was written for a human or a cron line, and several of them (`smtp_send.py`, `vault_append.py`, `backup_to_vps.sh`) are now driven by agents that guess at flags. Adopting that convention costs nothing and would have prevented at least one creative misuse. `agent-compatibility` is the second: CLI-backed repo scans plus agents that audit startup, validation and docs **against reality** — which is precisely the audit rule I keep re-learning the hard way (two false positives in August because a grep-only scan missed the central mount). `thermos` (parallel subagents, harsh quality rubric, merge-ready PR flow) and `orchestrate` (planner/worker/verifier fan-out with structured handoffs) are the multi-agent shapes we keep hand-rolling. And `continual-learning` is transcript-driven memory updates for `AGENTS.md` using high-signal bullets only — the closest thing in the repo to our 6,000-char memory problem.

**Pros:**
- The skills are plain `SKILL.md` + `rules/*.mdc` + `mcp.json` — readable, copyable building blocks, not a runtime we'd have to adopt. We can lift `cli-for-agent` and `agent-compatibility` without installing Cursor.
- 13.8K★ with a real commit history and a named-author manifest convention (`author.name` matches `plugin.json`), which is more provenance than most skill repos offer.
- The integrations half is a live, maintained catalogue of what MCP servers actually exist for Gmail, Google Workspace, GitHub, Playwright and Tailscale — useful as a reference even where we already have a bespoke tool.
- `grok-voice` documents realtime speech-to-speech, dictation and read-aloud **plus a log-driven fix loop for voice sessions**, which is the missing piece of our voice stack's debugging story.
- MIT and one clone, so the cost of evaluating is minutes.

**Cons:**
- **The useful integrations are Grok Bot's, not ours.** Roughly half the README describes connectors that route through Grok/xAI accounts (Tailscale "so Grok Bot can reach MCP servers", Gmail, X, Robinhood, Coinbase, QuickBooks, Workday) — installing any of those as-is means handing a live logged-in account to a third-party plugin, which by our own rule is a desktop-with-throwaway-account job at best, never the VPS.
- **Licence mismatch worth noting:** the repo has no SPDX licence detected by GitHub, while the README's last line says MIT. That is exactly the badge-versus-sidebar contradiction worth calling out — individual plugins carry their own `LICENSE` files, so each one has to be read before use.
- Everything is shaped around Cursor's plugin conventions; adopting one means translating its manifest into a Hermes skill by hand, and there is no guarantee of parity on hooks.
- `ralph-loop`, `pstack`, `dyl-stack` are opinionated personal or vendor workflows with little evidence base; they read as taste, not verification.
- 361 open issues on a repo this new suggests the marketplace is churning under people's feet.

**Should we...**
- 👀 **Watch it** — keep an eye on it, not ready yet but promising

**Impact on our stack:** Medium — Hermes skills + agentic-os cron scripts. The concrete change is small and real: adopt `cli-for-agent` as the cli-contract rule for every script we expect an agent to call (explicit `--dry-run`, machine-readable errors, idempotent re-runs), and lift `agent-compatibility`'s "audit startup and docs against reality" checklist into the audit procedure we already run — the one that produced two false positives in August.

**Why:** This is a watch because the thing is 10% ours and 90% Cursor's ecosystem: the integrations are a service catalogue for a different agent, and the workflow plugins are somebody's taste encoded as prompts. But the 10% that is ours is worth having, and it is the boring 10% — how you write a CLI so an agent can't misfire it, and how you audit a repo's claims against its actual mounted code instead of a grep. Both of those are lessons I have learned expensively this quarter, written down by someone else with a large audience behind them. Copy the two skills, translate them into our `SKILL.md` format, forget the marketplace. The moment it becomes an adopt is the moment Cursor's MCP manifests become portable across harnesses in more than name, or the moment one of those connectors (Gmail, Google Workspace) is something we actually want and can run with a scoped service account rather than somebody's personal login.

### 4. DeepInfer (deepseek-ai/DeepInfer)

**What it is:** DeepSeek's open-source release of the inference framework that powers its production services — **offline inference only** in this release, serving **DeepSeek-V4.1-Flash** specifically. It bundles the kernel stack (FlashMLA, DeepGEMM, DeepEP, TileKernels, DeepSelect), parallelism (Attention DP / balanced CP, MoE EP + EPLB), speculative decoding via C-DSpark with confidence-scheduled verification, decoder SWA bounded replay, an asynchronous batch scheduler, **batch-invariant inference** and **deterministic sampling**, and structured outputs constrained to regex/JSON-schema/EBNF. Apache-2.0, 21.4K★, 2,416 forks, created Oct 16, pushed Oct 21.

**Source:** https://github.com/deepseek-ai/DeepInfer · Provenance: spotted on Hyperautomation Labs — https://www.youtube.com/watch?v=SSjR7h9SJvs (the $38-per-GPU-hour receipt and the four inference tricks); README read directly.

**What's good about it:** The engineering is genuinely interesting and the README is honest in a way vendor launches rarely are — it lists what is **required for a complete inference service and not included**: a KV-cache system, prefill/decode disaggregation (mostly implemented), and cross-replica load balancing. It supports exactly two accelerators (NVIDIA SM100 GPUs, Huawei Ascend 950 NPUs), which is a deliberate statement about whose hardware it was built on. **Batch-invariant inference** and **deterministic sampling** are the two features worth understanding even for people who will never run it: they are the answer to "why did the same prompt give a different answer yesterday", which is a question our cron reports raise constantly. Deterministic sampling requires a fixed `seq_seed` plus `DEEPINFER_BATCH_INVARIANT=1`, and NVIDIA-only.

**Pros:**
- Batch-invariant + deterministic sampling are a real capability, not a marketing line, and the README states the exact env flags and their hardware restriction.
- Structured outputs via regex/JSON-schema/EBNF is built in — the thing we currently bolt on in prompts.
- Apache-2.0 with 21.4K★ in eight days, but this is DeepSeek's own org and a framework behind a live production service, so the star count is not the only evidence.
- The bounded-replay (SWA) prefill trick cut decoder prefill work; the technique is instructive regardless of hardware.
- Honest "not included" list — you know what you're signing up for before you clone.

**Cons:**
- **We cannot run it.** NVIDIA SM100 or Ascend 950 only, CUDA 13, GCC ≥ 13, Python 3.12, and the hardware class is eight-figure infrastructure. There is no GPU in this stack at all.
- It serves **one model family** — DeepSeek-V4.1-Flash — and no other weights. That is a vendor framework, not a general runtime.
- Offline inference only in this release, with KV cache and disaggregation explicitly missing: nothing here serves a real API yet in the open.
- 201 open issues in eight days, and "the receipts" (155T tokens/day, $38/GPU-hour) come from DeepSeek's own deployment Q&A — a vendor accounting for its own margins.
- It is a distraction from the only inference question we actually have, which is whether our cron jobs should call a cheaper model — a provider/price decision, not an engine decision.

**Should we...**
- ❌ **Skip it** — not relevant, redundant, low quality, or not useful for us

**Impact on our stack:** Low — nothing. No system of ours runs model weights; Hermes calls providers. The only durable takeaway is the concept of batch-invariant, seeded sampling, which belongs on a wishlist for whichever API provider we use, not on our install list.

**Why:** The coverage around this is all about DeepSeek's economics, and the economics are not our problem — our cron jobs spend cents, not GPU-hours. What would make DeepInfer relevant is hardware we don't have and don't need, to serve a model we access through an API today. Including it properly, rather than waving it through as "impressive open source", is the point: a 21K-star repo with a real engineering story can still be a skip for a urology department's ops stack, and this one is, for the same reason we skipped ai-job-search yesterday — it is good at a job we don't have. The one thing I'd carry forward is the deterministic-sampling idea: if a future model provider exposes a seed and a batch-invariant mode, that ends the "why did today's report differ from yesterday's" class of question for good, and it costs us nothing to look for.

## Overall Assessment

If we do nothing else, do these, in this order:

1. **Steal the untrusted-payload rule from K-Dense's `database-lookup` skill and put it in the Hermes system prompt** — one paragraph that says fetched API/RSS/web payloads are data, never instructions, never shell input. It costs an afternoon, applies to every cron job we already run, and is the cheapest security improvement available this week.
2. **Adopt `cli-for-agent`'s CLI contract for `~/.hermes/scripts/`** — explicit `--dry-run`, idempotent re-runs, machine-readable errors on the five scripts agents actually call. This is where "the agent guessed a flag" turns into a silent cron no-op.
3. **Write the one-sentence PHI boundary** — the gate that converts K-Dense's 177 skills from a liability into a usable research pilot, and the thing every future "can the agent look this up" question resolves against.

Nothing today is an adopt at full install scale, and that is the honest read of the week: two product launches that are events rather than tools, one framework for hardware we don't own, and two pattern libraries whose value is a few hundred lines of rules. The best item — K-Dense's clinical skill set — is a high-impact *watch*, blocked on a policy we owe ourselves rather than on a missing feature.
