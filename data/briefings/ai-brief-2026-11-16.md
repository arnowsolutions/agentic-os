### NVIDIA SkillSpector

**What it is:** NVIDIA's security scanner for AI agent skills. It reads a skill — repo, URL, zip, directory or a single `SKILL.md` — and reports a 0–100 risk score against 71 vulnerability patterns in 17 categories, as terminal output, JSON, Markdown or SARIF. Runs as a CLI, a Docker image, or an MCP tool that an agent can call on its own sessions.

**Source:** https://github.com/NVIDIA/SkillSpector · Docs: https://docs.nvidia.com/skills/scanning-agent-skills · Provenance: spotted on Hyperautomation Labs — https://www.youtube.com/watch?v=HnPw30Fxqb8 (repo #1, chapter 0:52)

**What's good about it:** We install skills from strangers. A brief names a repo, an `npx` installer writes into `~/.hermes/skills`, and from that moment the skill's instructions run with our shell, our SMTP credentials, our CRM token and our calendar. Nothing in our pipeline asks whether the skill is hostile. SkillSpector's own research number is the argument: across a 31,132-skill dataset, 26.1% contained vulnerabilities and 5.2% showed likely malicious intent. The coverage set is the one that matters for us — prompt injection, data exfiltration, excessive agency, system-prompt leakage, memory poisoning, MCP tool poisoning and MCP rug-pull, supply chain, YARA signatures, AST analysis, taint tracking — plus live CVE lookups against OSV.dev with an offline fallback. Two details make it usable as a gate rather than a report generator: a **baseline/suppression** file so re-scans only surface *new* findings, and an `analysis_completeness` block that reports coverage percent and per-analyzer status, so a partial scan is visibly partial instead of quietly green.

**Verified today, not just read:** installed with `uv tool install` on the container's Python 3.12.14 in about two minutes, as uid 1000, no root, no API key. `skillspector scan ~/.hermes/skills/copy-desk --no-llm` returned `score 0 / LOW / SAFE`, 100% coverage, and correctly flagged three path references in our own SKILL.md that don't resolve to bundled files. A recursive run over `~/.hermes/skills/creative` (44 skills) returned scores spanning 0 to 100, including two at 100/CRITICAL.

**Pros:**
- Works fully offline with `--no-llm`: no API key, no account, no data leaving the box — which is the only mode we can use on clinical-adjacent skill text.
- Covers the attack classes that actually apply to us: a skill is a prompt with shell access, so prompt injection, exfiltration and excessive agency are the relevant categories, not CVE matching.
- Structured JSON plus SARIF plus baseline suppression means a pre-install gate is a five-line shell check, and a CI report is free.
- The completeness ledger distinguishes "scanned 3 of 3 components, 0 issues" from "scanned 1 of 3" — most scanners just print a clean bill of health either way.
- Apache-2.0, 26.3k stars, 100+ contributors, pushed today, v2.12.0; NVIDIA runs the same scanner behind its own skills catalog, so the pattern rules are exercised at volume.

**Cons:**
- **Static-only analysis flag-raises our own tree.** Two skills under `~/.hermes/skills/creative` scored 100/CRITICAL with no LLM pass. That is the false-positive class we must triage before this becomes a hard gate — a skill that legitimately instructs an agent to `curl` a URL and write a file looks like exfiltration to a pattern matcher.
- **It is slow on trees.** 44 skills took minutes; `~/.hermes/skills` holds 665 `SKILL.md` files, so a full sweep is an overnight job, not a cron-minute job. Also: point it at a bare directory without `--recursive` and it scans only the top level (it warned us, but the report still looked complete).
- Input detection is layout-based. A directory without a recognizable `SKILL.md` errors with "Cannot determine input type" rather than scanning the files in it — fine for skills, annoying for our `references/`-heavy layout.
- The semantic pass is the part that reads *intent*, and it needs a provider key and adapter config. Without it, a plainly-worded malicious skill has to trip a pattern to be caught.
- Findings describe the skill's text and bundled code, not what an MCP server it calls does at runtime — pair it with something that pins server versions.

**Should we...**
- ✅ **Adopt it** — as a pre-install gate and a weekly sweep, in static mode first.

**Impact on our stack:** High — agentic-os skill pipeline, and by extension every cron job that loads a skill. Concretely: no skill from a brief, a YouTube video or an `npx` installer lands in `~/.hermes/skills` until `skillspector scan <path> --no-llm --format json` has run and been read; a monthly SARIF sweep over the tree, with a baseline committed, reports only what changed.

**Why:** We have spent a year accumulating skills from exactly the sources this tool was built for — vault finds, brief picks, installers that write into our skills directory — and we have never once checked what one of them asks the agent to do before granting it our shell and our credentials. That is the largest unguarded surface in the stack, and it is unguarded for a mundane reason: nobody wants to read 100 SKILL.md files by hand. SkillSpector does the first pass for free, locally, in a mode that needs no key and phones home to nothing. The honest caveat is calibration, not capability: our own skills tripped it at CRITICAL, which tells us the thresholds need a suppression baseline built from our own benign instructions before it can block anything. So the sequence is: install it (already proven), scan the ten most recently added third-party skills, write down which findings are real, then turn it into a gate. The first real finding will pay for the afternoon.

### ffmpeg-skill

**What it is:** An Agent Skill that gives a coding agent a local video editor — 42 tools behind a machine-readable contract and an MCP server, covering probe, cut, join, silence removal, fit-to-duration and fit-to-aspect, captions and karaoke, overlays, HDR→SDR and LUTs, audio cleanup, sync with drift correction, multicam, loudness and delivery checks. Every tool is a typed script; every job ends with the output being re-probed and verified.

**Source:** https://github.com/kajisho5/ffmpeg-skill · Site: https://kajisho5.github.io/ffmpeg-skill/ · Provenance: spotted on Hyperautomation Labs — https://www.youtube.com/watch?v=HnPw30Fxqb8 (repo #5, chapter 5:58)

**What's good about it:** The content program has a bottleneck that is not creative: 28 faculty interview clips that need to become vertical, captioned, loudness-normalized assets, and the work is mechanical. This does precisely that work offline — `fit.py --aspect 9:16 --fit crop` for the reframe, `caption.py --animate pop --karaoke` for burned captions from a transcript, `silence.py --threshold -35` to cut dead air, `loudness.py -I -14 --tp -1` for platform-spec audio, then `check.py` to prove the file is what it claims. The design detail that makes it trustworthy is the verify loop: the README's own framing is that an agent that "knows FFmpeg" guesses frame rates and reports success without opening the result, so every operation is followed by a probe of the actual output and, when the picture changed, a contact sheet. Nothing goes through a shell — each operation is a typed script, and no filter graph is accepted from the caller, which removes the injection surface that makes "let the model write an ffmpeg command" dangerous.

**Pros:**
- MIT, 6.1k stars, 10 contributors, CI tested against FFmpeg 6.1 / 7.1 / 8 / 9 — the version matrix matters because we do not control the host's build.
- Python standard library only, no pip dependencies: it cannot rot when a package disappears, and it runs on the host's system Python.
- The MCP tool surface is **derived from the same argparse parser as the CLI**, and CI fails if they drift — the contract cannot lie about what a tool takes.
- Optional local ASR (whisper.cpp / parakeet) means transcripts are produced on our machine; the audio in those interviews never leaves the VPS.
- Typed JSON output from every tool means a pipeline can branch on measured values (duration, fps, loudness) instead of parsing prose.

**Cons:**
- **Not installable in the Hermes container.** There is no `ffmpeg` or `ffprobe` binary in it and we run as uid 1000 with no apt — this is a host-side install, over SSH, not a skill we can just drop into `~/.hermes/skills`. The VPS host does have ffmpeg 6.1.1 (a CI-tested version) and node 22, so the path exists; it just is not the container.
- Its installer targets `~/.claude/skills`, `~/.cursor/skills`, `~/.agents/skills`. Our layout needs `--dir`, or vendoring the tools into a skill of our own.
- It is an engine, not a director: it will not choose cut points, judge whether a clip is publishable, or write captions. That brain lives in a separate repo of the same author's ecosystem.
- 42 tools is more surface than we will use, and the routing discipline lives in its `SKILL.md` — an agent that ignores the routing will call the wrong tool and get a technically-correct, useless file.

**Should we...**
- ✅ **Adopt it** — on the VPS host, as the mechanical half of the clip pipeline.

**Impact on our stack:** High — agentic-os content pipeline. Concretely: a host-side `ffmpeg-skill` checkout that Hermes calls over SSH, taking `faculty-clip.mp4` → 9:16 with burned captions and -14 LUFS audio, with `check.py` gating each output before it is queued for review.

**Why:** Everything else in the content program is taste — brand voice, titles, layouts — and taste is the part we can direct. Cutting, reframing, captioning and normalizing is the part that silently eats the hours, and it is exactly the sort of work an agent should be doing with tools that verify themselves. What separates this from the pile of "FFmpeg for agents" wrappers is that it refuses to trust its own output: probe first, measure after, look at a contact sheet when the picture changed. For a department account where a badly cropped faculty face is a real embarrassment, that verification is the feature. The constraint is honest and small — it needs a real ffmpeg, which lives on the host and not in the container — and the fix is a checkout on the host invoked over SSH, not a rewrite. Start with three clips from the 28 and judge whether the burned captions and the 9:16 crop are good enough to publish without a human re-cut.

### Plannotator (Inbox)

**What it is:** A local, browser-based review surface for agent output. It annotates plans, specs, Markdown, rendered HTML and diffs, and sends the annotations back to the agent as its next turn. The new **Inbox** is a decision queue: agents leave questions, files and guided reviews; you answer with a click; the answer returns to the session that asked without holding that session open. Any non-plugin agent reaches the Inbox over MCP with `plannotator inbox mcp`.

**Source:** https://github.com/backnotprop/plannotator · Site: https://plannotator.ai/ · Provenance: spotted on Hyperautomation Labs — https://www.youtube.com/watch?v=HnPw30Fxqb8 (repo #6, chapter 8:13)

**What's good about it:** Our review loop is the most load-bearing process we have, and it is currently held together with a live URL and a promise: Hermes builds an HTML report, deploys it, Shareef reads it later, and comes back with a decision in chat. The Inbox is that same loop with structure — the question is a card with the options as buttons, the artifacts attach, and the decision lands in the session that asked. The README explicitly lists **Hermes** among the personal assistants the Inbox supports over MCP, which is the first time a review tool has named our harness rather than requiring a plugin. Two smaller fits: `/plannotator-annotate report.html --render-html` renders an HTML artifact as-is instead of converting it (our CE reports are HTML), and `plannotator archive` keeps past plan decisions browsable, which is what the redesign gate has been doing in localStorage.

**Pros:**
- MCP is the integration, so nothing needs to be installed inside Hermes — we would register the inbox as a tool, not patch the runtime.
- HTML annotation renders our report format as-is; annotation pins and comments become an artifact instead of a paragraph of feedback.
- Code review covers local diffs and GitHub/GitLab PRs — directly useful for the Unified Platform React port.
- 12.2k stars, Apache-2.0, 100+ contributors, commits today; the tool has been through real use, unlike most of what crosses this desk.
- Decisions are archived rather than lost in a chat scroll, which is the difference between a review and a vibe.

**Cons:**
- **It is a desktop app with a browser window.** On the VPS that means exposing another port behind Traefik with auth; on Shareef's desktop it means the review flow lives somewhere other than where the artifacts are produced. Either way it is a new always-on service on a box that already runs a gateway, watchdogs, a voice agent and two Supabase stacks.
- It overlaps **Decision Studio** (`/redesign-compare.html`, `up-decisions-v1`), which already holds 18 surfaces' verdicts. Adopting this means retiring that, not running both.
- Install is a `curl | bash` installer that rewrites agent hook configs; on our infrastructure that is a policy decision, not a convenience.
- The Inbox's value depends on Shareef having it open — an agent that queues a decision nobody sees has added latency, not removed it.

**Should we...**
- 👀 **Watch it** — and pilot the Inbox as the CE decision queue on one audit before deciding anything about Decision Studio.

**Impact on our stack:** Medium — agentic-os review loop and the CE pipeline. Concretely: `ce:full` finishes, writes `decisions.json` to the inbox, and Shareef answers approve/changes from his phone instead of replying in chat; Hermes picks the answer up on its next turn.

**Why:** We have a review process that works because Shareef is disciplined about coming back with a decision, and it would work better if the decision were a click on the artifact rather than a paragraph typed later from memory. That is exactly what the Inbox is, and it is the first such tool to support Hermes without a plugin. But the reason this is a watch and not an adopt is placement: the artifacts are produced on the VPS and the human is at a desktop, so either we expose a review surface on the public internet or we move the review off the machine that makes the work. Neither is hard, and neither should be decided in a brief. The cheap experiment is one CE audit routed through the Inbox on the desktop, judged on whether the decision actually came back faster — and only then a conversation about whether Decision Studio survives.

### billion-context

**What it is:** A context-compression plugin for long agent sessions. Installed from npm, it wraps the harness (its support list includes hermes) and manages history hierarchically — compressing older turns into a maintained structure instead of truncating them — claiming roughly 5× fewer tokens and a 96–99% prefix-cache hit rate. Ships with a paper and a third-party benchmark folder.

**Source:** https://github.com/ranxianglei/billion-context · Paper: in-repo `paper/` · Provenance: spotted on Hyperautomation Labs — https://www.youtube.com/watch?v=HnPw30Fxqb8 (repo #8, chapter 10:30)

**What's good about it:** Context is our most expensive and least visible resource. A CE audit, a redesign port and a cron brief all burn it, and Hermes' own compaction is a blunt truncate-and-summarize. What makes this worth an hour of attention is that it is the rare compression claim with a method behind it: a 4.5-month production study (174k model calls, 18.76B input tokens, zero window violations on 204.8k-token models) plus a 1,500-item cross-benchmark evaluation against three RAG baselines on LongMemEval-S, ContextBench and MemoryAgentBench, where it reports #1 on ContextBench at −58.3% cost versus full context and +16.6% over the best RAG arm on LongMemEval-S. It is also explicit about cache health — a healthy session keeps a 96–99% prefix-cache hit rate and compression itself costs ≤2% — which is the metric that actually decides whether a compression layer saves money or loses it.

**Pros:**
- Published methodology, an in-repo benchmark suite, and a paper that is itself MIT-licensed — we can read the claims instead of trusting a chart.
- Hermes is a named supported harness, which is rare and means someone has looked at our session format.
- Compression that preserves the prefix cache is the only kind that reduces spend; naive summarization destroys the cache and costs more.
- 7.6k stars, active daily, MIT in the LICENSE file.

**Cons:**
- **GitHub reports the license as NOASSERTION** while the LICENSE file reads MIT. A metadata mismatch is not a legal problem, but it is a five-minute read before we vendor anything.
- **1,155 open issues** against 7.6k stars. That ratio says rough edges — and a compression bug in this system is silent, not loud.
- It is lossy by design: the model sees a maintained summary of the thread rather than the thread. In residency ops that is how "the CMO's office at 11:15, not the Moses campus" becomes "the CMO's office at 11:00" in an email to 40 people.
- It works by wrapping the harness — a layer between Hermes and the model provider, not a skill we install and forget. That is an architectural change with a blast radius of every job.

**Should we...**
- 👀 **Watch it** — and test the idea rather than the plugin: measure what a long CE session actually costs us before buying a compressor.

**Impact on our stack:** Medium — Hermes cron and any long session. Concretely: if the numbers hold, the monthly cost of briefs and audits falls materially, and long redesign sessions stop losing the first hour of context.

**Why:** Cost is the one dimension of this stack we have never measured properly, and a 5× reduction with a preserved prefix cache would be the single largest operating-cost change available to us. But the failure mode is exactly the one this system cannot tolerate: a compressed history that quietly drops a constraint — a name, a date, an exclusion — produces work that looks right and is wrong. The README's own benchmark story is about coding agents, where a lost detail costs a retry, not a mis-sent email. So the order is: instrument what a CE audit actually spends, run one audit with the plugin and one without on the same task, and diff the outputs for dropped facts. If nothing drops, the cost case is obvious. Until that diff exists, this stays a watch.

### TrustGraph

**What it is:** Policy-as-code for what an agent's output may contain and where it may go. One YAML file declares sources, the groups who may read them, which agents may use them, and which actions may receive the result; the library tracks provenance through every handoff and answers **allow**, **needs approval** or **deny** with a reason. Decisions are deterministic — there is no model in the decision path.

**Source:** https://github.com/skishore23/trustgraph · Provenance: Hacker News, "TrustGraph – ACLs that follow the data through your AI agents" — https://news.ycombinator.com/newest (Show HN, 2026-11-16)

**What's good about it:** It names the hole in every agent permission model we have. Our access controls decide what Hermes may *read*. Nothing decides where what it derived may *go*. Hermes reads the CRM and a resident's email, then writes a Telegram message, a public schedule page and an outbound email — and no layer in that chain asks whether the second is allowed to carry the first. The illustrative failure in the README is the exact shape of our risk: an agent reads a private source, then publishes something built from it to a public destination, and every individual step was permitted. The rule it implements is small and auditable — readers(output) is the intersection of readers of every input, deny by default, and approval can only add a requirement, never widen the audience.

**Pros:**
- Deterministic allow/needs-approval/deny: no LLM in the decision path, which is the only kind of guardrail worth trusting.
- The policy file is short enough for a non-programmer to read and challenge — a residency program director can audit it, which matters more than elegance.
- Deny-by-default plus approval-as-additional-requirement is the correct security posture and it is stated, not implied.
- Models the multi-agent handoff case (agent → agent), which our cron chains actually are.

**Cons:**
- **Two days old, one contributor, zero stars, no releases or visible tests.** This is a Show HN launch, not a product, and the README's own verification page is the only evidence it works.
- It assumes writes route through the library. Our writes go through Python scripts, MCP tools, `smtplib` and shell — every path would need wrapping before a single policy had teeth.
- Rust binary plus a policy engine is another service on a box that is already dense, for a capability we could approximate with a 30-line audience check inside our own senders.
- No documented integration with Hermes, MCP, IMAP or SMTP; we would be the first to try, and clinical data is a bad place to be a first user.

**Should we...**
- 👀 **Watch it** — and steal the model now, not the code.

**Impact on our stack:** Medium — CRM, email/Outlook and the public schedule. Concretely: a small `phi_audience` table in our senders that refuses to mail a body derived from CRM contacts to a non-staff audience, with the intersection rule as the spec.

**Why:** Every agent-security story in the vault this year has been about something getting in — prompt injection, credential theft, a hijacked session. This is the first one about something getting *out*, and it happens to describe our exact topology: a private source, a public destination, and a chain of individually-permitted steps in between. We are not going to run a two-day-old Rust policy engine in front of PHI, and we are not going to hand-wrap every write path in the stack. But the rule itself — an output may only go where every one of its inputs could go — is worth implementing now, in the three places we actually send mail and Telegram messages, because it is cheap, it is testable, and it turns a policy conversation into twenty lines of Python.

### Tencent LoopForge

**What it is:** A self-hosted workspace where coding agents deliver software through SOPs — ordered nodes of agent steps, deterministic scripts and human approval gates, each run in its own Docker sandbox, with retry, pause and rerun-from-any-node. Ten coding-agent CLIs can act as executors; the platform adds roles, checkpoints, artifacts and cost reports around them.

**Source:** https://github.com/Tencent/LoopForge · Provenance: spotted on Hyperautomation Labs — https://www.youtube.com/watch?v=HnPw30Fxqb8 (bonus repo, chapter 12:49)

**What's good about it:** The model is right, and it is the model our CE pipeline has been improvising: a fixed sequence of stages, a script where determinism beats a model, and a human gate where a decision belongs, with the ability to send work back to a chosen step rather than starting over. "Script" nodes that run a build or a lint with no AI in them are the part most agent frameworks get wrong, and the resumability — rerun from node 4 after fixing node 3 — is exactly what our cron retries lack.

**Pros:**
- SOPs are declarative and versionable, so a review process becomes an artifact instead of a convention.
- Node-level logs, artifacts and cost reporting per run.
- Tencent-backed, 2.1k stars, 16 contributors, active today, MIT text in the LICENSE file.
- Separates planning, implementation, review and testing into distinct roles with their own prompts and tools.

**Cons:**
- **It asks for the Docker socket.** The README is explicit: socket access grants control of the host daemon and the default install is "for trusted teams, not untrusted multi-tenant isolation." On a VPS that runs Traefik, two Supabase stacks, the Unified Platform, a voice agent and the Hermes container, that is root-equivalent access for a new service.
- No Docker CLI inside our container and uid 1000 — the whole install happens on the host, on production.
- It is a software-delivery product: repos, PRs, merges, branch modes. We are not a team shipping PRs; the things we want gated are audits, redesigns and monthly reports.
- The GitHub API reports the license as NOASSERTION because Tencent's LICENSE adds a third-party carve-out preamble — MIT in substance, but a mismatch worth noting.

**Should we...**
- ❌ **Skip it** — take the SOP/gate pattern, leave the platform.

**Impact on our stack:** Low — the orchestration need it addresses is already covered by Hermes cron plus skills, and the deployment cost lands on a host we cannot hand the Docker socket.

**Why:** Four months ago this would have been an adopt, because our pipeline had no notion of stages or gates. It has one now — the CE flow is build, publish, review, decide, apply, and the decide step is Shareef's — and the gap LoopForge would fill is a UI over a sequence we already encode in prompts. Against that modest benefit sits a serious cost: a compose stack with host Docker socket access, on the same box as everything else, administered by a single operator who is not a programmer. The transferable idea is small and free — make the script steps deterministic, make the human gate explicit, and let a run resume at a node instead of restarting — and we should write that into the CE pipeline ourselves rather than inherit a team product to get it.

## Overall assessment

If we do nothing else, do these, in this order:

1. **Gate the skill pipeline with SkillSpector** — one command that already works in the container, applied to the ten most recent third-party skills, then to every install. It closes the largest unguarded surface we have: skills that execute with our credentials and have never been read by anything but us.
2. **Install ffmpeg-skill on the VPS host and run three faculty clips through it** — reframe to 9:16, burn captions, normalize loudness, verify with `check.py`. It converts 28 clips from "a library we have" into a production line with measured output, and it is the only item today that advances the social media program.
3. **Pilot the Plannotator Inbox as the CE decision queue on one audit** — it is the first review tool that supports Hermes over MCP, and it would turn "Shareef reads it later and replies" into a decision that is recorded against the artifact.
