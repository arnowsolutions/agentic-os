### `skills` — the CLI that makes Hermes a first-class citizen of the agent-skills ecosystem

**What it is:** An MIT CLI (`npx skills`) from Vercel Labs that installs agent skills — folders of a `SKILL.md` plus supporting files — from any GitHub repo into whichever agent harness you run, with per-skill selection, a lockfile, and **78 supported agents including Hermes**.

**Source:** https://github.com/vercel-labs/skills · https://skills.sh · agent-target table: https://github.com/vercel-labs/skills/blob/main/docs/agents.md  ·  Provenance: surfaced via the install instructions in addyosmani/agent-skills, which The Next New Thing covered today — https://www.youtube.com/watch?v=pnZh5PAF3VE

**What's good about it:** The agents table has a row for us: `Hermes Agent | hermes-agent | .hermes/skills/ | ~/.hermes/skills/`. That is not a hopeful guess on my part — I ran it on this box and it printed `hermes-agent  Agent detected — installing non-interactively`, cloned the repo, found all 25 skills, and then installed the two I asked for into `./.hermes/skills/<name>/SKILL.md` with correct YAML frontmatter (`name`, `description`) and nothing else. It also wrote a `skills-lock.json` with a `computedHash` per skill, so what we install is pinned and verifiable rather than "whatever main was that afternoon". Per-skill selection matters more than it sounds: our own experience with mattpocock's set was that installing all 27 was known context bloat and we ended up copying three by hand — this makes the copy step a flag instead of a manual job. And it is not new-and-shiny-in-a-bad-way: 39.3k stars, MIT, created January, pushed two days ago, Node ≥22.20 required and this box runs 22.22.3.

**Pros:**
- Verified end to end on this machine: detection, clone, skill listing, install, and a valid `SKILL.md` that Hermes can load — not a README claim.
- `--skill` selects individual skills and `-a hermes-agent` targets us explicitly, so we install the two we want instead of a 25-skill context bomb.
- `skills-lock.json` records source, path and a content hash per skill — an install we can audit and re-pin, which is rare in this ecosystem.
- Works from any repo, not just a curated marketplace, so our own skills could be published and re-installed the same way across the VPS and the desktop.
- The `--list` mode prints the full catalogue with descriptions before anything is written, so the review step is cheap.

**Cons:**
- **The global path is wrong on this box.** It resolves `~/.hermes/skills/`, and `$HOME` here is `/home/hermeswebui/.hermes/home`, so `-g` would write to `/home/hermeswebui/.hermes/home/.hermes/skills` — a near-empty stub holding one skill — not the live `/home/hermeswebui/.hermes/skills` with 126. Install per-project, or pass the path deliberately; never `-g` blind.
- Skills run with full agent permissions, and the tool says so in its own closing line ("Review skills before use"). Anything installed from a random repo is arbitrary instructions in our context — this needs the same gate we apply to code.
- It is a Vercel Labs product and a `.sh` registry with its own incentives (it is a discovery surface as much as an installer) — the star counts on the repos it surfaces are partly a function of being listed there.
- Node-only, so it does not exist inside the Hermes container as a runtime dependency; it is a build-time tool for a checkout, nothing more.
- No uninstall-in-one-command story that I could verify, so a skill tree that grows this way will need pruning by hand.

**Should we...**
- ✅ **Adopt it** — integrate into our stack (strongly recommended)
- 👀 **Watch it** — keep an eye on it, not ready yet but promising
- ❌ **Skip it** — not relevant, redundant, low quality, or not useful for us

**Impact on our stack:** High — the Hermes skill system, which is the mechanism by which every other capability in this stack actually changes behaviour. Concretely: a `skills-install` helper next to our existing skill tooling that runs `npx skills add <repo> --skill <name> -a hermes-agent` in a scratch directory, diffs the resulting `SKILL.md` against nothing (a human reads it once), then copies it into `/home/hermeswebui/.hermes/skills/<name>/` and records the hash in the repo. That is the whole integration, and it turns "we should write a skill for that" into "somebody already wrote it, review and install".

**Why:** Our skill library is the most valuable thing in this stack — 126 directories of hard-won operational knowledge, from Traefik provisioning to the Manim rebuild — and it grows one hand-written skill at a time, which means it grows at the speed of one person noticing a problem twice. There is now a whole ecosystem of these things, in the format we already use, and a CLI that knows our directory layout by name. The reason this is an adopt rather than a watch is that the risk is entirely in what we install, not in the installer: the tool writes files into a directory we control, pins them with hashes, and does nothing at runtime. The one real trap I found is the `$HOME` resolution, which is why the integration is "install into a scratch dir, read it, copy it in" rather than a global flag. Do this first, because items 2 and 3 depend on it and nothing else on today's list gets cheaper by waiting.

And the repo is real project-shaped: 88 contributors, 848 commits, a commit this morning, 117k stars, MIT, and its install path is the CLI from item 1.

**Pros:**

- There is real overlap with what we adopted yesterday: `constraint-driven-development` and agent-roast both police a weakened quality bar, from opposite ends (written contract vs. diff analysis). Running both is defensible, but it is two systems to keep in agreement.
- It is process for a codebase with a review culture; two of the nine commands (`/webperf`, `/code-simplify`) assume a web product with a build we can measure, which only half our repos are.
- Addy Osmani's name on it means the voice is opinionated and the defaults are his, not ours — every threshold has to be re-decided for a 4-vCPU box running cron jobs.

- ❌ **Skip it** — not relevant, redundant, low quality, or not useful for us

The discipline is in choosing six and in rewriting their thresholds to match this box, not in pulling all twenty-five and hoping.

### Perplexity Decider v1.3 / Decider Flash v1.3 — a classifier that can also find the names nobody listed

**What it is:** Two Apache-2.0 open-weight "decision" models — `pplx-decider-v1.3` on a Qwen3.8-27B base and `pplx-decider-flash-v1.3` distilled down to Qwen3.5-4B — that answer typed questions about a piece of text, an image or JSON: yes/no probability, one of up to 255 options, an ordered score, and a new `locate` type that returns verbatim spans with character offsets.

**Source:** https://huggingface.co/perplexity-ai/pplx-decider-flash-v1.3 · https://huggingface.co/perplexity-ai/pplx-decider-v1.3 · https://www.perplexity.ai/hub/blog/perplexity-decider  ·  Provenance: r/LocalLLaMA, "Perplexity releases Decider v1.3 (26B) and Decider Flash v1.3 (5B)" — https://reddit.com/r/LocalLLaMA/comments/1xv7fku/perplexity_releases_decider_v13_26b_and_decider/

**What's good about it:** `locate` is the thing. It takes a label ("person", "email address") or an instruction ("the person who signed the contract") and returns the spans it finds, with start and end offsets and a score, or an empty list. That is exactly the capability we named as swapback's fatal gap yesterday — *"Priya Raman in free text goes out as written"* — because a list-based scrubber can only remove names that are on the list. The model files show it is a real architectural addition, not a prompt: `locate-span/adapter.safetensors` plus `locate-span/head.safetensors` alongside the base weights. On 17 out-of-domain NER, PII and extractive-QA tasks Perplexity reports an average of 69.0 (27B) and 63.6 (Flash) against 43.3 for Liquid d1, 41.5 for Cloudflare Clairic and 33.6 for GLiNER large v2.5 — a comparison against the actual zero-shot span-extraction tools, not against a strawman. The rest of the schema is sensible too: outputs are probabilities over discrete answers, `output_tokens` is always 0, and questions are answered in separate sequences so adding a question cannot change another answer.

**Pros:**
- `locate` returns offsets, not prose — which means a redaction layer gets character ranges it can splice, not a paragraph it has to re-parse.
- Apache 2.0 on both sizes with the training base disclosed (Qwen3.8-27B, Qwen3.5-4B), so the licence question is settled before we build on it.
- A 4B Flash variant distilled from the 27B is the right shape for a pipeline component: fast, small, and close enough on the benchmark.
- One schema answers four question types, so the same call can classify a triage email *and* locate the identifiers in it.
- Five days old (created 2026-11-09) but from Perplexity with a published paper-style eval, not a weekend fork.

**Cons:**
- **It needs a CUDA GPU.** The model card says Python 3.12+ and a CUDA GPU with room for ~8.5 GiB of BF16 weights plus working memory. This VPS has no GPU, 4 vCPUs and 6.0 GB free on a 97%-full disk. Self-hosting is not possible here today.
- **The API path defeats the purpose.** Calling Decider over Perplexity's API or OpenRouter to find the PII means sending the unredacted text to a third party — the exact egress we are trying to stop. For this one job, remote inference is not a compromise, it is a contradiction.
- The Hugging Face repo is gated: the card states "The repository is private: authenticate with a Hugging Face token that has access to it." Access is an approval step, not a clone.
- Mixing `locate` and decision questions in one request costs separate forward passes, and `separate` mode means questions never see each other — so multi-step reasoning about the same document is on us.
- Five days of existence, benchmark numbers from the vendor, and no independent reproduction of the 69.0 figure yet.

**Should we...**
- ✅ **Adopt it** — integrate into our stack (strongly recommended)
- 👀 **Watch it** — keep an eye on it, not ready yet but promising
- ❌ **Skip it** — not relevant, redundant, low quality, or not useful for us

**Impact on our stack:** High in principle, blocked in practice — it is the missing NER layer in front of the swapback PII proxy we flagged yesterday, and the cheap classifier for email triage, but only if it runs locally. Concretely: on a machine with a CUDA card, `pplx-decider-flash-v1.3` behind a small local HTTP service that returns spans for `person`, `email`, `phone`, `MRN`, `DOB`; swapback consumes those spans as extra known values before its fail-closed check.

**Why:** Yesterday's brief concluded that swapback's protection is exactly as good as the list we feed it, and that a name in free text goes out as written. This model closes precisely that hole, and it closes it in the only shape that works for us — spans with offsets, produced locally, with no third party seeing the text. The honest verdict is watch and not adopt, because every deployment path available today is wrong: self-hosting needs a GPU we do not have, and the hosted API means shipping the unredacted email to Perplexity to find out what should not have been shipped. So the action is not an install, it is a test: when a GPU machine is available (the desktop, if it has a CUDA card), run Flash over 200 real emails from the triage corpus with `locate` labels for person, MRN and date of birth, and count what it finds that swapback's list missed. If it finds even one, this becomes a component; if it finds none, the list was always enough and we learned that for the price of an afternoon.

### AgentLeak — a leak detector for the channels nobody audits

**What it is:** An MIT Python SDK, CLI, MCP tool set and local web UI that analyse agent execution traces for sensitive data disclosed through the channels that never make it into the final answer — tool calls, tool outputs, shared memory, inter-agent messages, logs and generated files — with redacted reports and CI gates; the analysis runs locally with no LLM dependency.

**Source:** https://github.com/yagobski/agentleak · https://www.agentleak.org · research benchmark and paper: https://github.com/Privatris/AgentLeak  ·  Provenance: Show HN, "AgentLeak — open-source privacy testing for multi-agent LLM systems" — https://news.ycombinator.com/item?id=50476987

**What's good about it:** The research behind it names the failure we have been circling: across 1,000 scenarios and 4,979 validated traces over five models, inter-agent messages leaked sensitive data 68.8% of the time against 27.2% for final outputs, and output-only audits missed 41.7% of what was actually disclosed. Translated: auditing what an agent *said* to a human tells you less than half the story, because the leak happens between the agents and through the tools. That is our architecture exactly — Hermes calls tools, tools call models, cron jobs hand off to subagents, and nobody has ever looked at the intermediate channel. The tool itself is the practical half: `pip install agentleak`, `agentleak run --scenario healthcare_patient_summary` ships a synthetic healthcare demo with a clean final answer and dirty internals, and the analysis of your own traces needs no model. A CI gate plus a redacted report is the right output shape for something that runs on every build.

**Pros:**
- It measures the channel we do not look at, which is the one the paper says leaks most.
- Deterministic local trace analysis with no LLM in the loop — the finding is reproducible and costs nothing to re-run.
- The bundled healthcare scenario means the first run produces something recognisable to us instead of a toy.
- MIT with a Python SDK, CLI and MCP tools, so it can be driven from a skill rather than clicked through a web UI.
- A CI gate is exactly how a privacy check survives contact with a busy week.

**Cons:**
- Eleven stars and effectively one author, last pushed eight days ago — young, small, and unproven in a field where false confidence is expensive.
- The parent research repo admits its headline table is a "separate unreconciled repository summary" whose 5,694-trace basis has "not been reconciled" with the paper's 4,979 validated traces. A privacy tool with an unreconciled numbers page is not a compliance control yet.
- It needs traces in its own format; Hermes does not emit them, so step one is instrumentation we would have to write and keep.
- Detection is pattern and channel based — the same weakness as any rule-based scanner, and it will not know a patient name it has never seen unless a rule describes it.
- The licence on the research repo reads NOASSERTION while the tool repo is MIT; the two halves are governed differently and only one of them is the paper.

**Should we...**
- ✅ **Adopt it** — integrate into our stack (strongly recommended)
- 👀 **Watch it** — keep an eye on it, not ready yet but promising
- ❌ **Skip it** — not relevant, redundant, low quality, or not useful for us

**Impact on our stack:** Medium — the swapback pilot we scoped yesterday, and the email-triage path behind it. Concretely: instrument one Hermes cron job (the nightly email triage) to emit a trace in AgentLeak's shape, run the bundled healthcare scenario first to see what a report looks like, then run ours and count disclosures in tool inputs and logs rather than in the reply.

**Why:** Yesterday's conclusion was "run the pilot, count the blocks, then decide", and the weak point in that plan is the counting — swapback's own logs tell us what it blocked, not what got past it, and the research here says the interesting leaks are the ones that never reach the final answer. This is the cheapest way to get a before-and-after number on the channel that matters, and the bundled healthcare scenario is close enough to our data to be a useful rehearsal. It stays a watch because eleven stars and one author cannot be a compliance control, and because building trace instrumentation for a tool this young is real work that only pays off if the tool survives. Do the demo, look at the report, and only then decide whether instrumenting a cron job is worth a day.

### Langfuse AI Gateway — one Rust binary in front of every model call, reporting cost

**What it is:** A standalone Rust gateway that sits in front of provider APIs — `/openai/v1` for Responses, Chat Completions, **Decisions**, Embeddings and Models; `/anthropic/v1` for Messages — relays native JSON and SSE bytes without rewriting them, and uploads every finalized generation to a Langfuse project over OTLP.

**Source:** https://github.com/langfuse/langfuse/tree/main/ai-gateway  ·  https://langfuse.com  ·  Provenance: Show HN, "Langfuse AI Gateway, open source rust gateway to trace every LLM call" — https://news.ycombinator.com/item?id=50484682

**What's good about it:** It is a proxy that does not get in the way: the README is explicit that it relays native JSON or SSE without rewriting provider bytes, with one deliberate exception (a streamed Chat Completions request is asked for its usage), and that model listings and token counting are passed through and not billed as generations. That is the correct design for something sitting on the critical path of every request — a gateway that reformats payloads is a gateway that breaks tools. The capture layer is bounded and logs its own completeness at debug level, which is the kind of honesty that makes a tracing tool trustworthy. It ships as a Docker image (`langfuse/ai-gateway`), has tests, an `AGENTS.md`, a pinned toolchain (Rust 1.98.0) and Clippy in CI. And it is in the Langfuse repo itself — 37.4k stars, company-backed, with a real product behind it rather than a weekend proxy.

**Pros:**
- Native-byte relay means adding it in front of Hermes is a base-URL change, not an integration.
- Per-generation ingestion with token counts is the cost and latency visibility we have never had — we currently cannot say what a cron job costs.
- One gateway covers both provider formats we would use, and it already understands `/decisions` if we ever call that endpoint.
- Docker image plus tests and a pinned toolchain: this is deployable, not a prototype.
- OpenTelemetry ingestion means the data lands in a standard backend, not a bespoke dashboard.

**Cons:**
- **It is a component of Langfuse, not a standalone proxy.** It resolves a gateway key against a Langfuse Web service (`LANGFUSE_*` config, a service key, readiness returning 503 without it), so the "one Rust binary" framing hides a platform: Web, database, and the usual Langfuse stack behind it.
- The repo licence is NOASSERTION — Langfuse is open core with enterprise portions, so what is MIT and what is not needs reading before we depend on it.
- Self-hosting the backend on this box means Postgres plus ClickHouse plus Redis on a disk with 6.0 GB free — that is not a test, that is a project.
- Using Langfuse Cloud instead means every prompt and response we route through it becomes someone else's data, which for the email path is the same egress question as swapback.
- A gateway on the critical path of every model call is a new single point of failure, and we have no on-call.

**Should we...**
- ✅ **Adopt it** — integrate into our stack (strongly recommended)
- 👀 **Watch it** — keep an eye on it, not ready yet but promising
- ❌ **Skip it** — not relevant, redundant, low quality, or not useful for us

**Impact on our stack:** Medium — Hermes cron cost and latency accounting, and any future debugging of "why did that job take twenty minutes". Concretely: the honest version of this is a decision we have not made — self-host the stack (no disk) or use the cloud (data leaves). Until one of those changes, there is no change.

**Why:** We run somewhere between ten and twenty scheduled jobs a day and cannot answer the simplest operational question about them, which is what they cost and where the time goes. A byte-preserving proxy that reports every generation is the right shape of answer, and the fact that it ships in the Langfuse repo with tests and a Dockerfile makes it credible. It is a watch for a structural reason: it is not a proxy you can drop on a box by itself, it is the front door of a platform that wants Postgres and ClickHouse, and the cloud alternative sends our prompts to a third party — the same trade we spent all of yesterday trying to avoid. Keep it in view for the day we consolidate agent observability; do not put it on the critical path this month.

### rea-video — a shot-by-shot teardown of any video, written for an agent to rebuild

**What it is:** An Apache-2.0 CLI and agent skill that takes a video, measures and inspects it shot by shot, decides whether each shot was filmed, AI-generated or coded, and writes the whole breakdown to `VIDEO.md` — an open format an agent reads layer by layer — including how to remake it.

**Source:** https://github.com/JuneYaooo/rea-video · https://www.reavideo.ai · https://videomd.github.io/videomd/  ·  Provenance: bonus repository on The Next New Thing — https://www.youtube.com/watch?v=pnZh5PAF3VE

**What's good about it:** The method is more interesting than the output format. It gathers evidence rather than guessing: frame cadence, sensor noise, whether the whole image moves as one flat plane, AIGC tags in the metadata, then looks at hands, text and physics, then listens for BPM, key and whether the voice is sung or spoken. That is a real forensic checklist, and it is the kind of thing a person does by squinting and getting it wrong. The output is `VIDEO.md`, a layered format with a dedicated spec site, so the artefact is inspectable by any agent rather than locked in a vendor's UI. It needs only ffmpeg and Python 3.10+ to do the analysis; a video-capable model (Gemini or Doubao) is optional and only makes the live/AI/3D calls more accurate and adds a reverse-engineered prompt. The demo in the README is a fair illustration of the value: a phone-shot TikTok ad versus an AI remake, correctly identified as "all live footage, one set, two camera positions" against "all AI, 8 shots across 3 generations".

**Pros:**
- Evidence-based shot classification — cadence, noise, plane motion, metadata — is a method we could trust enough to use on a competitor's clip.
- `VIDEO.md` plus a published spec means the breakdown is a durable artefact our own skills can read, not a chat transcript.

**Cons:**
- Two weeks old (created 2026-10-29), one author, 156 MB repo, 8.2k stars on a repo that age — attention, not track record.
- The accurate version of the "is this AI or filmed" call and the reverse-engineered prompt need a video-capable model, which means an API key and a cost per clip.

- ❌ **Skip it** — not relevant, redundant, low quality, or not useful for us

**Impact on our stack:** Medium — the social media program. Concretely: run it on three of the 28 faculty clips and one department video we admire, and read the `VIDEO.md` for whether it tells us anything a person watching once would miss — shot rhythm, what makes a clip feel produced. ### OpenMausBot — a desktop app for bot contacts, which is a shape we already have

**What it is:** An Apache-2.0 Electron desktop application (macOS, Windows, Ubuntu) where each item in the sidebar is a real agent — Claude or Codex running locally — with its own personality, model, cloud computer and connected apps, presented as a contact list you chat with and approve.

**What's good about it:** The product thinking is right and it is the same thinking that has been circling us for weeks: bots as contacts rather than a chat window, each with its own computer and browser, with approval in the conversation before anything sensitive happens. - Apache-2.0 with a real release process and downloadable builds for all three desktop platforms.

**Cons:**

- 551 MB repo, 1,101 open issues, created in August, one principal author. That is a lot of surface area for a tool that duplicates what we have.
- Nothing about it is callable from a script; there is no API or headless mode described that our cron jobs could use.
- We already decided the coordination layer (Telegram for alerts, Outlook for mail, Hermes as the agent surface) — this is a fourth place to look.

**Impact on our stack:** None — it competes with the surface we already use rather than improving a system inside it.

**Why:** Filed so it stops coming back, because 22k stars will resurface it. The idea — agents as contacts with their own computer and a human approval step — is one we should keep stealing; Hermes plus Telegram plus its tool permissions already is that idea, headless, on the machine where the work actually lives. What OpenMausBot adds is a desktop window and a second identity store, at the cost of 551 MB, an Electron attack surface and a thousand open issues.
