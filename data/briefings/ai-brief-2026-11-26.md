### Modelpin — samarthputhraya/Modelpin

**What it is:** A CLI that answers one question before you switch models: did the app's behavior change? You describe scenarios (system prompt, user message, tools) or record traces, and it replays them several times on the baseline model and the candidate, then reports regressions — changed tool-call plans, new refusals, output-format drift — only when the difference is statistically significant, material, and reproduces on a fresh set of runs. It also ships `modelpin watch`, a deprecation registry transcribed from OpenAI, Anthropic and Google's own pages.

**Source:** https://github.com/samarthputhraya/Modelpin  ·  https://pypi.org/project/modelpin/  ·  Provenance: Show HN, November 26 — https://news.ycombinator.com/item?id=50644468

**What's good about it:** It targets the failure we actually have. A model swap does not usually break loudly; it changes which tool gets called second, or starts refusing a request the old model handled, and the final text still looks plausible. Modelpin scores those channels separately and re-runs a flagged scenario before failing a build, which is the difference between a signal and a coin flip. The statistical discipline is documented rather than asserted: every scenario runs multiple times on both models, a change must be significant, large enough to matter and reproducible, and the README publishes both its false-alarm measurement (0 alarms in 972 same-model checks across six Gemini models) and the caveats behind that number. The deprecation registry is the sleeper feature — each entry carries the vendor page it was read from and the date, so `modelpin watch` can tell you that a model ID in your config retires on a given day and name its successor. That is a five-second check we currently do by noticing a 404 in production.

**Pros:**
- Behavior-level comparison instead of text diffing: tool-call sequence changes, newly added refusals and format drift each get their own verdict, so an identical-looking answer that took a different path is caught.
- Built to stay quiet: a difference counts only when it is significant, material and reproduced on a second set of candidate runs — the documented direction of error is "miss a borderline change", not "cry wolf".
- Runs on your keys and your machine, with an offline demo (`modelpin init --demo`) that exercises the same diff and statistics without a network call; error output is scrubbed of key-shaped strings.
- The deprecation registry has a source URL and `fetched_at` date per entry, and `watch` exits non-zero inside a notice window or 90 days of a shutdown — scriptable in cron with `--json`.
- Daily releases this week (0.5.4 → 0.5.7), a CI badge, a GitHub Action and SARIF/JSON output, so a model bump can be gated like a dependency bump.
- Apache-2.0, Python 3.11+, `pipx install "modelpin[providers]"`, and a demo that runs in thirty seconds.

**Cons:**
- **DeepSeek is not a provider.** The table is openai, anthropic, google, groq, openrouter, together and cerebras, with no generic `base_url` setting — so the model we actually run cannot be the baseline or the candidate. `watch` would also report it as *unknown* (exit 3), because the registry only reads the three labs' own pages.
- Two stars, zero forks, one contributor (142 commits). The artifacts look professional, but no one outside the author has validated it in public, and a test harness that is wrong in the quiet direction is worse than none.
- It costs real tokens per run: the printed estimate for 8 scenarios × 5 runs is at least 40 paid calls plus up to 360 judge calls, and flagged scenarios are replayed before the build fails.
- It measures single requests with declared tools, not the Hermes agent loop — our skills, prompt assembly and retry logic are outside the scenario, so a green check does not mean a cron job still works.
- The judge is a model, and its sensitivity depends on which judge you configure; the calibration was done with an OpenAI judge and others are described as unmeasured.
- It measures change, not quality. A consistently worse model passes.

**Should we...**
- 👀 **Watch it** — run `modelpin watch` today (it needs no keys and no network), pilot one `check` against a Gemini model we already use, and revisit once DeepSeek can be a provider.

**Impact on our stack:** Medium — Hermes cron and model routing. Concretely: the next time a provider retires the model under a scheduled job, this is the thing that says "scenario `brief_format` now emits the verdict field in a different order" before the job silently degrades. Until DeepSeek is supported, the realistic use is a deprecation watch plus a guard on Gemini-based jobs.

**Why:** Our failure mode all year has been silent change: a job runs, exits zero, and delivers something subtly wrong, and we diagnose it by reading logs backwards. Changing models is the highest-frequency silent change we make — the stack has moved providers repeatedly, and each move was validated by eyeballing a couple of runs. Modelpin turns that into a repeatable check with a documented error direction, and it does it offline with our own keys, which is the only shape of testing we would accept anyway. The verdict is watch rather than adopt for two concrete reasons: it cannot test the model we actually run, and a two-star, single-author harness needs to prove its false-negative rate on our scenarios before we let it gate anything. What we should do now is cheap and useful regardless: run `watch` against the models named in our configs for retirement dates, because that half needs no keys and answers a question we have never systematically asked.

### Hush — OgnjenAdzic28/hush

**What it is:** A Rust computer-use layer that lets an agent see and drive desktop apps in the background. It reads a window as a short accessibility outline, sends a batch of steps (click, type, key, menu, scroll, drag, drag-and-drop), and returns only what changed. It ships as a CLI, an MCP server and an agent skill, works on macOS 15+ and on Linux through AT-SPI, and on Linux runs the apps an agent opens on a hidden X display it calls "the lane".

**Source:** https://github.com/OgnjenAdzic28/hush  ·  Provenance: Show HN, November 26 — https://news.ycombinator.com/item?id=50651523

**What's good about it:** The engineering is aimed at the two things that make computer use impractical: latency and theft of the user's screen. A read-click-type-read round is quoted at 178 ms against 653 ms for the next tool in its own comparison, and the token cost is 972 for the whole seven-tool surface versus 10,514 for agent-desktop. Refs survive re-renders and a repeat read of an unchanged window is 12 tokens, so a long session does not accumulate context. The background claim is structural rather than polite: events go only to the target app, and on Linux the lane is a separate hidden X server, so the pointer, clipboard and focus never move. It also ships the part most projects skip — desktop tests as plain text files that replay with no model, `hush save` to turn a successful run into one, and per-app `never` / `read` / `only` limits that are enforced before a command executes.

**Pros:**
- Fast enough to be usable interactively (178 ms round, 20–35 ms click settle measured on GitHub's Linux runners) and cheap in context (12-token repeat reads, 972-token tool list).
- True background operation: no focus stealing, no pointer movement, untouched clipboard, and a hidden display for agent-launched apps on Linux.
- Desktop tests without a model — a text format with `expect` lines, fresh session per file, first failure stops the run, outline and screenshot kept on failure.
- Per-app limits are a config file read on every command and every MCP session, so an edit applies immediately and a typo stops Hush rather than silently running unrestricted.
- Seven tools mapped to real actions, plus `timeline` for millisecond-scheduled key and pointer playback and `record` for demos with an agent cursor.
- MIT, 92 commits, an install script that also registers a skill in `~/.agents/skills`, and an MCP mode that drops into any stdio client.

**Cons:**
- **Windows is "next."** macOS 15+ and Linux only — and the desktop we actually run Hermes on is Windows, so today this cannot touch the machine Shareef works on.
- One contributor, 92 commits, 11 days public, 17 stars, one fork. The polish is real but there is no third-party use to point at.
- The comparison table is self-run, and its own footnote admits the other tools' tool lists were measured on a different date — treat the 178 ms as a claim, not a benchmark we can audit.
- Linux support is AT-SPI, which means apps with no accessibility tree (custom-drawn UIs, many games, Electron with accessibility off) are invisible — a real ceiling for "any desktop app".
- It drives apps, not browsers-as-products: for web portals, our existing HTTP and extraction tools are still the right path, and Hush would add a display stack to the VPS for no gain.
- The installer is `curl | sh`, and on Linux it wants `xvfb`, `at-spi2-core` and `ffmpeg` installed — a new runtime layer on a box that is supposed to stay boring.

**Should we...**
- 👀 **Watch it** — no action on Windows today; if a Linux workstation ever enters the stack, this is the first thing to try on it.

**Impact on our stack:** Medium — Hermes desktop capability, not cron. Concretely: on a Linux box it is the missing "operate a real application" layer beside our terminal and HTTP tools — a cron-spawned agent could drive LibreOffice or a file manager on a hidden display without touching anyone's session, with the `only` limits scoping it to the two apps it needs.

**Why:** Hush is the best-executed tool in today's batch and the one I would most like to adopt, which is exactly why the verdict has to be honest about where it runs. Our automation is HTTP, files and cron; there is no GUI application in the loop except the ones Shareef clicks himself on Windows, and Hush does not support Windows yet. Putting it on the VPS would mean carrying Xvfb and an accessibility bus to drive apps that do not exist there. The reason to keep watching rather than dismiss it is that the design solves real problems we would hit the moment we did have a desktop target: background operation, token-cheap observation, and tests that replay without a model. If the Windows port lands and the Windows desktop becomes a Hermes host with GUI tasks, this jumps to adopt on the strength of the limits file alone.

### Turbo Desktop — Tthanh2k6/turbo-desktop

**What it is:** A Windows 10/11 desktop-automation stack for agents, built on UI Automation rather than screenshot loops. The part we would use is `desktop-mcp`, a standalone stdio MCP server exposing nine tools: list windows, compact inspect with `onlyChanged` diffs, act, batch actions, launch, wait, window control, screenshot and system state. Around it sits an optional FastAPI hub with ECDSA-signed requests, TOTP sessions, approval prompts, hash-chained audit logs, and an Android app with an emergency STOP and Wake-on-LAN relay.

**Source:** https://github.com/Tthanh2k6/turbo-desktop  ·  Provenance: Show HN, November 26 — https://news.ycombinator.com/item?id=50653216

**What's good about it:** It treats desktop automation as a safety problem, not a speed problem. UIA patterns (`Invoke`, `Value`, `SelectionItem`, `Toggle`, `ExpandCollapse`, `Scroll`) are used before simulated input, so the pointer and focus usually stay where the owner left them; when real input is unavoidable it waits for five seconds of idle, lights an orange border on every monitor, and restores focus after. Password fields (`IsPassword`) are never read or typed, windows with secret-looking titles (`.env`, `credentials`, `.pem`, `.kdbx`, "password", "api key") are denied across inspect, act, screenshot and OCR, and screen-derived text is wrapped in `<<<SCREEN_CONTENT>>>` boundaries so window contents are marked as data rather than instructions. When a custom-drawn window has an empty UIA tree it falls back to WinRT OCR automatically. The README also lists what does not work — elevated windows, UAC prompts, the lock screen — which is the sign of someone who ran it.

**Pros:**
- Nine focused UIA tools with `onlyChanged` diffs, which is the token-efficient shape we want from a desktop server.
- A real security floor: per-action approvals, signed remote protocol, TOTP sessions, hash-chained JSONL audit logs, and a hardware-independent kill switch (Ctrl+Alt+Shift+K or the phone's STOP).
- Secret-window and password-field denial is enforced in every tool, not documented as advice.
- 384 tests claimed (237 desktop-mcp, 125 hub/relay, 22 Android) against isolated WinForms/WPF fixture apps, with `TURBO_DESKTOP_NO_INPUT=1` so a test run cannot move the mouse.
- A field report from November 20: 29/30 desktop tasks passed, with the single skip named (a UWP app inside a desktop isolation container).
- MIT, Python 3.12, and the MCP server runs standalone — we can ignore the hub and phone app entirely.

**Cons:**
- One day public, one contributor, one star, 53 commits (a squashed import of a private project). Every claim above is the author's own test run.
- Windows-only, and explicitly cannot drive elevated windows, UAC prompts or the lock screen — which is where the interesting Outlook and admin flows live.
- The full stack is a lot of surface (MCP server + FastAPI hub + Android client + Wake-on-LAN relay) for the one capability we would want.
- The hub's operational guide is in Vietnamese; the English README covers the architecture but not the runbook.
- Pointing an agent at Outlook or a clinical application on a Montefiore-managed laptop is an IT-policy question before it is a technical one — and our rule about not putting credentials on unapproved paths applies doubly to a desktop session.
- No Python packaging published (no PyPI); installation is `pip install -e .` from a clone, which means pinning a commit and maintaining it.

**Should we...**
- 👀 **Watch it** — the `desktop-mcp` half only, and only after the Windows desktop gets a task that the terminal genuinely cannot do.

**Impact on our stack:** Medium — Hermes desktop. Concretely: Hermes on the Windows machine could read and click applications that have no CLI (Excel dialogs, Word's save-as, a browser print dialog) with per-app scoping and an audit log, instead of asking Shareef to do it by hand.

**Why:** This is the Windows answer to Hush, and the reason it is watch rather than skip is that the Windows desktop is the one machine we control that has GUI applications on it. The reason it is watch rather than adopt is everything about its provenance: a single author, a repository that appeared today with a squashed history, and security claims (signed protocol, TOTP, audit chain) that no one outside the author has reviewed. The security design is the part that makes it interesting and the part that would need review before we ran it, because a tool that can click anything on a work laptop is a much bigger grant than a shell script. Park it, re-check in a month for stars, issues and a second contributor, and pilot the standalone server on a throwaway Windows VM first — never on the laptop that holds clinical mail.

### pocket-design-mcp — jasonmello/pocket-design-mcp

**What it is:** An MCP server that gives a coding agent a designer's toolbox: Iconify icons across ~280 sets, Google/Fontshare/Fontsource fonts, shadcn and React Bits components, OKLCH palettes with WCAG and APCA contrast, fluid type and spacing scales, layered shadows, easings, SVG optimization and SVG-to-React conversion, plus token export as CSS variables, Tailwind v4 `@theme` or DTCG JSON. No API keys required; Pixabay is optional for image search.

**Source:** https://github.com/jasonmello/pocket-design-mcp  ·  https://www.npmjs.com/package/pocket-design-mcp (v0.3.1, published November 21)  ·  Provenance: GitHub search (MCP servers, created last 7 days, sorted by stars); 25★, Apache-2.0.

**What's good about it:** It replaces taste-by-improvisation with numbers. `make_palette` returns a 50–950 OKLCH scale that contains the color you started from, with harmonies and contrast; `check_contrast` returns WCAG 2 ratio and APCA Lc with a suggested fix; `type_scale` returns `clamp()` values with line-height and tracking; `export_tokens` emits the same system in three formats. For an agent, that is the difference between "make it look premium" and "use step 700 for text on step 50, ratio 7.4:1". The four bundled prompts map cleanly onto our review loop — `design_review`, `build_section`, `brand_kit`, `unify_icons` — and `unify_icons` is exactly the cleanup our redesign previews need, where two pages can end up with three icon families.

**Pros:**
- Zero credentials and zero hosting: `npx -y pocket-design-mcp`, and the heavy lifting (`svg_to_react`, `optimize_svg`) is local.
- Deterministic outputs — contrast ratios, scales, tokens — which is what makes eighteen generated pages look like one product.
- `export_tokens` in three formats means the same palette can feed plain HTML previews and a Tailwind build without a second source of truth.
- ~20 tools with honest sources named per tool (Iconify, Google Fonts, shadcn, Openverse, Wikimedia), so we know what breaks if a catalog changes.
- Apache-2.0, TypeScript, and a `design_review` prompt that checks contrast, type scale, spacing rhythm, icon consistency and motion — the same axes Shareef reviews on.
- Small blast radius: it writes nothing outside the response, so a bad call costs a bad suggestion, not a broken file.

**Cons:**
- Five days old, seven commits, one human author plus dependabot, 25 stars, no tests in the tree.
- Every catalog lookup is a third-party dependency (Iconify, Google Fonts, Fontsource, shadcn); a shape change upstream breaks a tool with no error we control.
- No brand awareness: it will happily produce a generic indigo SaaS palette — Montefiore navy `#003da5` has to be pinned in the prompt or every generation drifts.
- Twenty tools is real context cost in every session where it is mounted; it should be a design-only mount, not a default.
- Image search without the optional Pixabay key is weak, and the README's "no API keys" glosses that over.
- Token export is only as good as the tokens we feed it; it does not know our existing design system, so `unify_icons` can pick a consistent set that is consistently wrong for the brand.

**Should we...**
- 👀 **Watch it** — mount it for design sessions this week, generate the token block once for the redesign previews, and see whether the output survives a side-by-side review.

**Impact on our stack:** Medium — the redesign-preview pipeline and any Unified Platform UI work. Concretely: one `export_tokens` call replaces the hand-written `:root` blocks that currently differ across `unified-*-redesign-vN.html`, and `check_contrast` gives us an accessibility gate we currently apply by eye.

**Why:** The redesign work has a consistency problem that is not a taste problem: eighteen pages generated over weeks drift in spacing, icon family and palette, and every drift is a round of review that has to be re-litigated. A token generator with contrast math removes the part of that which is mechanical, and the bundled `design_review` prompt matches the axes Shareef already critiques on. The verdict is watch for a mundane reason — five days and seven commits is not enough history to make it a dependency, and its catalogs are third-party services that can change under us. The cheap move is to run it ad hoc in a design session, export one token file, and judge the pages that come out; if the output holds, this becomes the token source for the previews and eventually the React port.

### Skills over MCP — official MCP extension (SEP-2640)

**What it is:** The Model Context Protocol published "Skills over MCP" as an official extension (SEP-2640, Final): an MCP server can expose `SKILL.md` workflow instructions and their supporting files through the existing Resources primitive, and a client can discover which skills a server offers and load the files only when needed. It is in public beta in Claude and Claude Code, shipped in VS Code 1.147+, and arrives alongside Tasks (long-running server work), Elicitation (a server pauses to ask the user) and File Uploads (files passed to a server without entering the context window).

**Source:** https://modelcontextprotocol.io/extensions/skills/overview  ·  https://github.com/modelcontextprotocol/ext-skills  ·  https://claude.com/resources/articles/skills-over-mcp-tasks-and-more  ·  Provenance: Google News (VentureBeat, November 25), Hacker News, and the official MCP docs.

**What's good about it:** It closes a split we live with every day: MCP gives an agent access, skills give it judgment, and today they come from different places with different trust models. Serving instructions from the server that owns the workflow means the tool and its usage documentation ship together — the same reason our `~/.hermes/skills` folder works. The security posture is also the right one: a skill served over MCP **cannot grant itself tool permissions or hooks** — those declarations are ignored, and the client decides what the skill is allowed to do. For a client like Hermes that already has a skills router, that is the correct default and worth matching deliberately rather than by accident.

**Pros:**
- One distribution channel for a tool and its instructions, which removes the "you installed the server but not the skill" failure mode.
- Skills are fetched through Resources on demand, so there is no context cost until the skill matches the task.
- The extension is Final, not a draft, with a working group and a published spec repository.
- Real implementations already exist — Claude/Claude Code public beta, VS Code 1.147 with its own approval controls — so the pattern is being tested in public.
- Tasks and Elicitation address what our cron jobs actually need: hand off long work, and ask a human before a destructive step.
- Permission and hook stripping keeps server-supplied prose from escalating itself, which is the failure we would worry about most.

**Cons:**
- Host support is still being implemented; the docs publish a client support matrix, and Hermes is not on it. Consuming remote skills would be our integration to write.
- It widens the trust boundary in a way that is easy to under-rate: connecting a server now means accepting prose that can steer the agent, and prose is a better injection vehicle than a tool schema.
- Our skill router keys off `name` and `description` in local files; mapping a remote catalog into that router, with precedence and conflict rules, is real design work.
- Everything in this wave is days old; the extension will move, and anything we build now is against a beta.
- We have no MCP servers of our own that would publish skills, so the near-term benefit is consumer-only — and we consume very few MCP servers.
- The Claude-side article is also a product announcement (Tasks, Elicitation, File Uploads GA on paid plans), so the "standard" and one vendor's implementation are easy to conflate.

**Should we...**
- 👀 **Watch it** — but the useful action is a policy line, not code: decide now whether a mounted MCP server may inject instructions at all, and write it down before the first one asks.

**Impact on our stack:** Medium — Hermes skills and MCP. Concretely: either Hermes' MCP client learns to read a server's skill catalog from Resources (with our local skills taking precedence), or we explicitly refuse server-supplied instructions — and that decision changes what "approved MCP server" means in every future integration.

**Why:** This is the most consequential standard change of the week for a system built on skills, and it cuts both ways. If our client can read remote skills, a single MCP mount can bring its own operating manual and our skills folder stops being the only source of procedure. If it cannot — or if we decide not to trust it — then every server that ships skills becomes a partially useful server, and we should know that before evaluating one on its tools alone. The reason to watch rather than build is that host support is still landing and the client matrix does not include us; writing against a beta to consume skills from servers we do not yet run would be work in search of a problem. The reason not to ignore it is the security half: "approving a server" quietly becoming "approving instructions" is exactly the kind of change that gets adopted by default, and a one-paragraph policy now is cheaper than an incident later.

### Inkling 2 Mini — Thinking Machines Lab

**What it is:** An open-weights model released November 20 under Apache-2.0: a 26.4B-parameter mixture-of-experts with 3.4B active, built as a looped transformer that runs its middle layers three times per token. Total footprint is about 20 GB at its native NVFP4/MXFP8 precision, which puts it on a 32 GB laptop or a single desktop GPU. It leads open-weights models under 100B on DeepSWE v1.1 (48.2% resolved) and Vals Index v2.2 (46.5%). *Previously covered: Inkling appeared in the vault three times in 2026 (the 975B model in July, Inkling Small in September) — this is a new release with a new architecture, not a re-run.*

**Source:** https://thinkingmachines.ai/news/inkling-2-mini/  ·  https://huggingface.co/thinkingmachines/Inkling-2-Mini  ·  Provenance: spotted on The Next New Thing — https://www.youtube.com/watch?v=Gtfxe_hFDs4 · vendor page verified November 26.

**What's good about it:** The looping is the interesting part, and it is argued on monitorability rather than benchmarks: running the middle layers repeatedly lets the model reason longer without writing its reasoning down, so the chain of thought stays short and legible — the variable-loop variant in the release went from a 16-second no-CoT time horizon at one pass to 37 seconds at three, while the CoT stayed readable. For a department that has to explain what an automated system did, a model whose reasoning is short by construction is a real property, not a spec-sheet line. Inference support landed on day one across SGLang, vLLM, Ollama, Unsloth, Dynamo and TokenSpeed, with RL fine-tuning on SkyRL, Miles and NVIDIA AutoModel, and the weights plus a research variable-loop variant are on Hugging Face.

**Pros:**
- Apache-2.0 weights, ~20 GB total, and a stated target of a 32 GB laptop or one consumer GPU — the smallest credible "runs on your own machine" footprint for its class.
- Strong agentic-coding numbers for sub-100B open weights (DeepSWE v1.1 48.2%), which is the benchmark that maps to what we would use it for.
- Short, legible chain of thought by design, with published experiments on how looping affects both performance and monitorability.
- Broad day-one inference support and native NVFP4/MXFP8 deployment, so it is not a research artifact that needs a custom stack.
- The vendor documents the limits of its own evaluation, and the Hugging Face post says plainly that more validation is needed.

**Cons:**
- Nothing in our stack can run it: the VPS is CPU-only, and the Windows desktop's GPU is unverified. Inference on CPU at 26B is not a plan.
- Six days old, with no independent evaluation beyond the vendor's charts and a Hugging Face post that asks for exactly that validation.
- Looped transformers are new enough that most serving stacks' optimizations were not built for them; expect rough edges in throughput and quantization.
- Apache-2.0 covers the weights, but a separate acceptable-use policy still constrains what it may be used for.
- It solves a problem we do not have: our models are API-hosted and cheap, and a local model would add weights, a runtime and a second inference path to maintain.
- The interesting security property (monitorable CoT) is the vendor's claim about its own model, and there is no third-party audit of the sabotage tests.

**Should we...**
- 👀 **Watch it** — worth remembering as the local fallback if a GPU box ever joins the stack; no action today.

**Impact on our stack:** Low — a candidate local model, nothing more. It would touch Hermes cron only if we ever wanted an offline path for jobs that cannot call an API, and that is not a constraint we have.

**Why:** This is the most interesting model release of the week and it still does not change anything we do, which is worth saying plainly. Our inference is hosted API calls; the VPS is CPU-only; the department's constraint is not model access but review throughput. Inkling 2 Mini matters as a marker: a 20 GB open-weights model that is genuinely good at agentic coding means the option of an offline, no-data-leaves-the-box path is getting real, and that is the shape of a solution if we ever need to run something on clinical text without an external API. Until then it is a bookmark, and the honest verdict is watch with low impact rather than a plan to download 20 GB onto a machine that cannot use it.

### Memora — lian84/memora

**What it is:** A self-hosted, file-first personal AI assistant built on the Pi agent kernel: persistent chats, a Markdown "Second Brain", human-reviewed memory, projects, artifacts, web research, Telegram, scheduled automations and MCP, with encrypted backups. v0.1.4, AGPL-3.0-only, Node 24, TypeScript.

**Source:** https://github.com/lian84/memora  ·  Provenance: Hacker News, November 26 — https://news.ycombinator.com/item?id=50653773

**What's good about it:** The design instincts are right — memory is Markdown files you can read, memory writes are reviewed by a human before they stick, and backups are encrypted rather than an afterthought. The README is unusually honest for a v0.1.x: it warns that restore, update and rollback validation are still in progress and that the service should not be exposed without TLS and a reverse proxy.

**Pros:**
- File-first memory with human review is a better default than a hidden vector store, and it is inspectable with `grep`.
- CI badge and a versioned release cadence (v0.1.4) on a seven-day-old repo — not a weekend dump.
- Telegram, automations and MCP are all present, so it is a complete assistant rather than a demo.
- Encrypted backups documented as a first-class feature.

**Cons:**
- It duplicates Hermes almost feature for feature — memory, skills/automations, Telegram, MCP, cron-style schedules — and does it on a different agent kernel (`pi`), so nothing we have transfers.
- Three stars, seven days, one author, and the maintainer's own warning that restore and update paths are unvalidated.
- AGPL-3.0-only, which is fine self-hosted but viral for anything derived.
- A second assistant means a second set of model keys, a second log, and a second place where a schedule can silently fail — the exact failure mode we have been fixing in Hermes.

**Should we...**
- ❌ **Skip it** — redundant runtime, earlier-stage than what we already run.

**Impact on our stack:** Low — it would sit beside Hermes and do a subset of what Hermes does, while adding another credential store and another scheduler to monitor.

**Why:** The one idea worth stealing is the memory review gate — a human approves what the assistant remembers about you — and that is a feature to add inside Hermes, not a reason to run a second assistant. Everything else is duplication: skills become automations, cron becomes schedules, MCP becomes a connector list, and Telegram is already wired. Adopting it would mean maintaining two agent runtimes on one box to get a memory UI we could write as a skill. File it as rejected so it does not come back around, and keep the review-gate idea.

### FreeLLM — jaredfreellm/FREELLM_INSTALL

**What it is:** A self-hosted gateway that stacks the free tiers of many LLM providers behind one OpenAI-compatible `/v1` endpoint, with model routing by speed and capability, failover on 429/5xx with per-key cooldowns, per-key request and token quota tracking, key rotation, fallback chains, encrypted key storage and a dashboard. The repository is an install page: the actual software is a ZIP attached to a GitHub release, protected by the password `FREELLM`.

**Source:** https://github.com/jaredfreellm/FREELLM_INSTALL  ·  Provenance: GitHub search (LLM repos, created last 7 days, sorted by stars); 252★, MIT badge.

**What's good about it:** The router design is the right shape for the problem it names: free tiers are individually useless and collectively annoying, and quota bookkeeping per `(provider, model, key)` is the part everyone gets wrong. Cooldowns on 429 with automatic failover to the next model in a chain, plus a transparent response header naming the provider that served the request, is a sane architecture. It also says out loud what most free-tier projects hide: no SLA, no frontier models, for experimentation only.

**Pros:**
- Correct architecture for free-tier juggling: live routing scores, per-key quota counters, failover, and profiles for different workloads.
- Drop-in OpenAI compatibility, so any client works by changing a base URL.
- Encrypted key storage at rest, with apps seeing only one unified token.
- Docker and Node deployment, including ARM boards; custom OpenAI-compatible endpoints supported.
- The README is explicit about the limits and the intended use.

**Cons:**
- **The code ships as a password-protected ZIP.** A process that holds every provider key would be the most sensitive thing on the box, and we cannot read what it does before running it. That is a supply-chain decision disguised as a download.
- Free-tier stacking violates or strains several providers' terms; the realistic outcome is keys getting banned, and the tool's whole value is the keys.
- We already judged this idea: `FreeLLMAPI` (a different repo) is in the vault from October 7 as an adopt, and production cron runs through our own provider configuration. A second gateway would add a failure point under the jobs that matter.
- 252 stars on a repository whose main artifact is a ZIP is a distribution pattern, not an adoption signal.
- No source history means no issue tracker worth reading, no way to audit the routing logic, and no patch path when a provider changes its API.
- "MIT" on an install page says nothing about the binary inside the archive.

**Should we...**
- ❌ **Skip it** — unauditable distribution of a key-holding service, for a problem we have already solved.

**Impact on our stack:** Low — a second LLM gateway in front of Hermes would add a hop, a key store and an unreadable dependency to the one path that must not fail silently.

**Why:** The README decides this one. A gateway that holds every provider credential and sits in front of every model call is exactly the process we would insist on reading end to end, and this one asks us to run an encrypted archive with a password published in the README. Even setting that aside, the value proposition is free tiers, and free tiers are the one thing our stack does not need: our inference is a single paid provider with predictable behavior, and the whole point of this week's better idea — Modelpin — is that model behavior is something to measure, not something to shuffle for cost. Skip, and if cost ever becomes the constraint, solve it with one provider's volume pricing rather than five providers' terms of service.

## Overall assessment

If we do nothing else, do these, in this order: **1) Run `modelpin watch` and pilot one `check`** — the `watch` half needs no keys and no network, and answers a question we have never systematically asked: which model IDs in our configs retire, when, and what replaces them; then write five scenarios for the cron jobs whose output shape matters and run a check against a Gemini model we already use, so we learn whether the harness is trustworthy before we need it. **2) Write the MCP-instructions policy** — one paragraph saying whether a mounted MCP server may deliver workflow instructions to Hermes, where they sit relative to our local skills, and who approves them; the Skills extension is Final and shipping in clients now, and this is the kind of default that gets set by whoever ships first. **3) Mount `pocket-design-mcp` for design sessions and export one token file** — it costs an `npx` line, and if the tokens hold up, the eighteen redesign previews stop drifting in palette, spacing and icon family, which is review time back every week.

The pattern in today's eight items is that the useful ones are *checks*, not capabilities. Modelpin is a check on model behavior; Skills over MCP is a check on what a server is allowed to say; pocket-design's contrast tool is a check on accessibility; even Hush's contribution is a test format that replays without a model. The two skips are both "run a second thing" — a second assistant runtime, a second LLM gateway — and neither would make anything we already do materially better. The one capability item, Turbo Desktop, is the most interesting risk of the day: the right idea for the Windows machine, from a source with one day of public history, which is precisely the profile that should sit in a watch list rather than on a work laptop.
