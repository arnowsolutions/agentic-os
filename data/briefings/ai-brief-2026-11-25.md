### ContentSkills — blotato/contentskills

**What it is:** A repo containing eleven agent skills (`brand-brief`, `viral-hooks`, `post-writer`, `post-grader`, `quality-check`, `repurpose`, `make-video`, `post-scheduler`, `content-coach`, `generate`, `setup`) plus a local Node and Python pipeline that cuts, transcribes, captions, themes, renders and storyboards short-form video. The README names Hermes explicitly in its supported-agent list alongside Claude Code, Codex, Cursor and Gemini CLI.

**Source:** https://github.com/blotato/contentskills  ·  Provenance: GitHub search (new repos, last 7 days, sorted by stars); v1.0.0 tagged November 23, pushed November 25.

**What's good about it:** It is not a video generator, it is a production line with a gate. The agent writes a script, builds a storyboard as a phone-sized preview page, and sends a link — nothing renders until a human presses "Make my video". After that, edits happen per scene, in parallel, each one reviewed on its own page. The pieces we actually need for the interview-clip library are all here: face finding and reframing to vertical, captioning from local transcription, a theme/effects library, and a quality-check skill that runs before a draft is called finished. Default voice and transcription are local, so the cost of a clip is compute rather than credits; kie.ai and ElevenLabs are opt-in paid paths.

**Pros:**
- Eleven skills in plain `SKILL.md` format with a setup skill that installs the rest — this drops into `~/.hermes/skills/` without an adapter, and Hermes is on the supported list.
- The storyboard approval gate matches how Shareef actually reviews content: look at it, approve or mark changes, then render. It does not fire 28 clips into the void.
- `post-writer` already encodes our copy rules (zero em dashes, no filler openers like "in today's world", banned words list, active voice, contractions) and `post-grader` scores the draft before `post-scheduler` will touch it. That is the copy desk's QA gate, written down as a skill.
- `post-scheduler` degrades gracefully: without a Blotato key it writes a copy-paste file instead of failing the run.
- The input shape is exactly ours — one raw take in, a cut vertical with captions and a hook out. The 28 faculty clips are 28 raw takes.
- 2,711 files, 849 JS/TS and 72 Python, a working dashboard on `localhost:4600`, scene-level undo, and a documented Windows/Linux install (`winget` or `apt` + Node 22 + `uv`).

**Cons:**
- Four days old, **one commit, one author**, no test suite and no CI workflow anywhere in the tree. The v1.0.0 tag is a first public import of an internal tool, not a release with a track record.
- AGPL-3.0-only. Fine while it runs inside our own box; viral the moment we ship anything derived from it, which matters if this ever touches client work.
- Publishing is not self-contained: real posting goes through Blotato (paid SaaS, MCP tools `blotato_create_post` / `blotato_list_accounts`). Without that account the pipeline stops at a text file.
- Heavy local dependencies (Node 22+, ffmpeg, Python via `uv`, a 50 MB effects library). Rendering long interview footage on our CPU-only VPS will be slow, so the realistic home for the renderer is the desktop.
- No evidence of anyone running it under Hermes — the shipped plugin manifests are `.claude-plugin` and `.grok-plugin`, so the Hermes path is "read the SKILL.md and hope", not a tested integration.

**Should we...**
- 👀 **Watch it** — pilot the skills half this week; hold the renderer until it survives three real clips.

**Impact on our stack:** High — the content pipeline behind the social-media program. Concretely: copy `brand-brief`, `post-writer`, `post-grader` and `quality-check` into `~/.hermes/skills/`, point `brand-brief` at the Montefiore voice doc, and use them to draft and grade captions for the 28 clips before the renderer is trusted. If the render survives a three-clip pilot on the desktop, it replaces the manual cut-caption-export loop entirely.

**Why:** The content program has a bottleneck that is not ideas, it is throughput: 28 raw interviews need 28 cuts, captions, hooks and captions again for three platforms, and every one of those steps is currently either manual or improvised per clip. ContentSkills is the first thing I have seen that treats that as a pipeline with an approval gate rather than a prompt, and the gate is the part that makes it usable by a department that has to review what goes out. The verdict is watch, not adopt, for a boring reason: one commit and no tests means we would be the first production user of someone's four-day-old import, and the failure mode (a half-rendered clip with burned-in wrong captions going to a faculty member's feed) is embarrassing in a way a bad README is not. Pilot it where failure is cheap — the skills half immediately, the renderer on three clips on the desktop — and if the output holds up, this becomes the spine of the content workflow instead of another tool in the folder.

### Google Workspace CLI (`gwscli`) + Workspace MCP servers

**What it is:** On November 24 Google made its Workspace MCP servers generally available for Gmail, Calendar, Drive, Docs, Sheets, Slides, Chat and Tasks, alongside `gwscli`, a unified command-line interface that exposes every Workspace API as structured JSON with schema discovery. The same announcement sets the policy: from **February 1, 2027** AI agents must access Workspace data through MCP rather than calling REST APIs directly, with direct-REST agents capped at Standard Tier quotas regardless of tier; billing and quota enforcement follow on April 1, 2027.

**Source:** https://developers.google.com/workspace/guides/workspace-cli  ·  https://workspaceupdates.googleblog.com/2026/11/mcp-servers-cli-standardized-usage-tiers-now-available.html  ·  Quotas and dates: https://developers.google.com/workspace/guides/quota-usage-tiers  ·  Provenance: Hacker News front page, November 25 ("Google mandates MCP for AI agents accessing Workspace and restricts direct API").

**What's good about it:** This replaces hand-rolled REST plumbing with a supported interface that is designed for agents. `gwscli` discovers its own command surface and JSON schemas at runtime, ships packaged agent skills, and documents headless auth, prompt-injection screening and human-in-the-loop confirmation as first-class concerns rather than blog-post advice. The MCP servers inherit each user's permissions, DLP rules and classification labels, so a mailbox rule we set in the admin console actually applies to what the agent can read. Standard Tier is free at 5,000 requests per day, per project, per product, with no billing account — enough for our volume by a wide margin.

**Pros:**
- One interface for Gmail, Calendar, Drive, Docs, Sheets, Slides, Tasks and Chat, with JSON output and `JSON Schema` introspection — a real alternative to maintaining our own `google_workspace.py` REST wrappers.
- Free Standard Tier (5,000 requests/day/project/product, no card), so the pilot costs nothing but setup time.
- The dates are published and generous: enforcement February 1, 2027, billing April 1, 2027. That is a runway, not an ambush.
- Google's own docs put security in the request path — scoped OAuth clients for agents, per-call permission checks, DLP, and confirmation required for sending mail or changing sharing.
- Packaged skills mean Hermes can be taught the CLI's conventions once and reuse them across Gmail, Drive and Calendar work.

**Cons:**
- We do not have a Workspace tenant. Our Google automation authenticates as a personal `@gmail.com` account, and the MCP mandate governs Workspace (business/education) access — so this is a convenience upgrade, not a compliance deadline we are behind on. Do not let the news headline panic us into a migration we do not need.
- Migration cost is real: a new Google Cloud project, a new OAuth client designated for agents, new least-privilege scopes, and re-consent. Every script that assumes the current token has to be re-tested.
- The docs are Workspace-first (Chat sending needs a Workspace account and a configured Chat app; People API needs its own enablement). Consumer Gmail is not the target audience, and some paths may simply not apply.
- Name collision: the 32k-star community `gws` (`npm i -g @googleworkspace/cli`) is **not** the official tool — its own README says so and points at `gwscli`. Installing the wrong one and thinking we are compliant is an easy, quiet mistake.
- MCP tools can cost more than one request each (some fan out to several API calls), so the 5,000/day cap arrives sooner than the number suggests on batch work.

**Should we...**
- 👀 **Watch it** — stand up a scratch Cloud project and pilot `gwscli` on a test calendar and mailbox; decide by January 2027 whether to fold it into `google_workspace.py`.

**Impact on our stack:** Medium — email/Outlook and Google automation. Concretely: a `gwscli calendar events list --params '{"timeMin":"..."}'`-style interface replaces bespoke REST code in `google_workspace.py`, and the same auth covers Drive and Sheets, which is where several report generators currently hand-roll requests. It would be High inside a Workspace tenant; we are not one.

**Why:** The honest read is that today's announcement matters more to organizations than to us: we run Google automation on a consumer account, we do not touch Montefiore's Workspace tenant (and must not — IT flagged exactly that pattern in July), and nothing we do today breaks on February 1, 2027. What the GA does give us is a supported, agent-shaped interface for the Gmail/Calendar/Drive work we already do, with JSON output and packaged skills, replacing code we maintain by hand and re-verify every time Google changes a response shape. The reason to watch rather than adopt is that adopting means a new Cloud project, a new OAuth client and re-consenting every job that touches Google — churn with no crisis forcing it this week. The right move is a bounded pilot: one scratch project, one test calendar, one mailbox, and a decision in January, well before the enforcement date makes the choice for us.

### Agent Debugger — woxlo1/agent-debugger

**What it is:** A local-first debugger for **failed** agent runs. You feed it a trace you already have (NDJSON or JSONL, or events posted to its local API), and it produces a "Cause Package": observed evidence with event IDs, rule-based cause candidates each carrying a falsifier, reproduction steps, and a hand-off pointing at where to look next in your real debugger. It runs entirely on the machine, with no account, no cloud and no external model.

**Source:** https://github.com/woxlo1/agent-debugger  ·  Provenance: Show HN, November 25 ("Show HN: Agent Debugger – local-first failure debugger for AI agents"); npm `agent-debugger-server` v1.0.2 published November 24.

**What's good about it:** It answers a narrower question than an observability platform, and that is the point. Langfuse and LangSmith tell you what happened; this tells you what to inspect next and how to prove the hypothesis wrong. Evidence and interpretation are kept in separate sections, a rule flag never silently becomes a root cause, and every hypothesis carries a falsifier. Redaction runs on ingest, stream, export and bundle creation, and the portable bundle carries a SHA-256 fingerprint — which means a failed run involving a patient name can leave the box without the name in it. The MCP server is stdio-only and opens no port, so Hermes can call it without exposing anything.

**Pros:**
- MIT, local, no external service. Nothing about a trace has to leave the box to be analyzed, which is the only version of this we can use for anything touching clinical text.
- Deterministic, rule-based analysis with explicit falsifiers — it cannot invent a root cause, and it says when it does not know.
- Comparison across two traces (metrics, evidence, hypotheses, usage, redaction findings), which is exactly the "what changed between the run that worked and the run that did not" question.
- The MCP server exposes analyze, compare, export, import and privacy-audit tools over stdio JSON-RPC, so Hermes can drive it directly instead of shelling out.
- An SDK on npm plus a plain JSONL pipe, so any language can emit events — including our Python cron wrappers.

**Cons:**
- It only understands its own `schemaVersion: 2` events. There is no OpenTelemetry, Langfuse, Phoenix or LangSmith importer, so today's Hermes cron runs are not ingestible without instrumentation we do not have.
- Two contributors, zero stars, three npm publishes, all on November 24. There is no third-party validation of any kind, and the CLI surface is a week old in the wild.
- Local store only: no cross-run view, so "this failed on Tuesday and again on Friday" means opening two bundles and comparing by hand.
- Rule-based hypotheses are generic (timeouts, tool errors, empty results). They will not know our domain rules — that `smtp_send.py` skipped because `.smtp.env` was missing, for instance.
- Its "Claude Code transcript" reader is off by default and needs a process switch plus an allowlist — a sign the authors know transcript access is the dangerous part, and a reminder that our equivalent path would need the same care.

**Should we...**
- 👀 **Watch it** — but the useful move is ours, not theirs: make the cron wrappers emit one NDJSON line per step so a debugger like this has something to read.

**Impact on our stack:** Medium — Hermes cron. Concretely: when a scheduled brief sends no email and exits zero, this is the shape of tool that turns "it said nothing" into "step 4 returned an empty list, here is the falsifier". The prerequisite is a five-line trace emitter in the cron wrappers.

**Why:** Our recurring failure mode is not a crash, it is silence — a job that runs, exits zero, and delivers nothing, which we then diagnose by reading logs backwards. Agent Debugger is aimed exactly at that gap and is built with the constraints we actually have: local, no accounts, redaction at every boundary, deterministic output. It fails the adoption test for one concrete reason: it needs our traces in its schema, and Hermes does not emit them. That makes the order of operations clear — emit structured events from the cron wrappers first, because that work is useful with or without this tool and is a prerequisite for any debugging story; then, once there is a week of real traces, try Agent Debugger on the ones that failed. Watching costs nothing and the instrumentation is worth doing regardless.

### OctoSift — Octosift/OctoSift

**What it is:** A self-hosted Reddit monitor built for lead research. It watches the subreddits you name, runs every new post through free filters and then a two-stage model screen (a cheap small-model pass across many posts, then a careful single-post check), and produces an inbox of scored leads with a plain-language reason, a suggested way to help, and a drafted reply you copy and post yourself.

**Source:** https://github.com/Octosift/OctoSift  ·  Provenance: GitHub search (self-hosted AI, created last 7 days); 100 commits in six days, AGPL-3.0.

**What's good about it:** The cost design is right. Free filters drop removed posts, bots, spam and stale threads before any model sees them; then a small model screens in batches and a stronger model judges only the survivors. You bring your own key, including a local Ollama or LM Studio endpoint, so spend is visible and capped by us rather than by a vendor. The output is a decision surface, not a firehose: every post gets a verdict, a score, and a reason you can disagree with. It also keeps a mentions tab and an evergreen tab for threads that rank in search, which is closer to "what are people asking about urology" than to lead-gen.

**Pros:**
- Human-in-the-loop by construction: it drafts, you post. No automated posting from a server, which is the only version of this we would ever run.
- Two-stage screening plus free pre-filters keeps token cost per lead low; BYO key means it can run against a local model for the cheap pass.
- SQLite, Docker, a dashboard, Slack/Discord webhook, keyboard-driven inbox — the operational shape of something we could run on the desktop without ceremony.
- 100 commits in six days with a written README, demo mode that needs no key or network, and 106 stars from a standing start.
- Genuinely useful for content research: the exact words patients and caregivers use when they ask about a urology problem, which is better input for hooks than anything we invent.

**Cons:**
- It reads Reddit through **a logged-in account's session cookie** (the browser sign-in flow, or a pasted cookie in Docker), falling back to public RSS that Reddit has already retired and says may stop at any time. That is precisely the credential pattern our rules forbid on the VPS: a real session on a datacenter IP gets accounts flagged.
- AGPL-3.0, one contributor, six days old, no third-party review, no tests visible in the README.
- Platform risk sits outside the code: Reddit's public data access is being retired through March 2027, so the reading path may degrade regardless of how good the tool is.
- The product's framing is lead generation — reply to convert. A clinical department using it for outreach would sound like a vendor in patient threads, which is the opposite of the voice we want.
- Bringing your own key means the posts you screen leave the box to whichever provider you choose; that needs to be an explicit decision, not a default.

**Should we...**
- 👀 **Watch it** — and if we try it, on the desktop with a throwaway account, never on the VPS.

**Impact on our stack:** Medium, and only for the marketing side — content research, not clinical operations. Concretely: a weekly scan of r/Urology, r/Prostatecancer and r/KidneyStones turned into a list of real questions in real words, feeding `viral-hooks` and the blog calendar. Nothing in Hermes, the Unified Platform or the CRM changes.

**Why:** The valuable half of OctoSift is the research loop — what people actually ask, scored and explained — and the half we cannot use is the account session it needs to read Reddit at all. That combination makes it a desktop tool with a throwaway account, not a VPS service, and it makes the verdict watch regardless of how good the code is. The lead-gen framing is a second reason to keep it at arm's length: our content voice is warm and authoritative, and a tool optimized to convert a thread into a DM would push it toward sales copy. If the marketing program needs a research feed, this is the most competent self-hosted option I found this week; if it needs a posting tool, this is not it.

### agent-sim — Developing-Gamer/agent-sim

**What it is:** iOS simulators for AI agents on ordinary Linux machines, with no Mac and no GPU. It layers an agent interface — read the screen, tap, type — on top of x86Sim, which is the project that runs Apple's iOS simulator runtime on Linux.

**Source:** https://github.com/Developing-Gamer/agent-sim  ·  Provenance: GitHub search (AI agent repos, created last 7 days); v0.1.0, 577 stars in four days.

**What's good about it:** The engineering is legitimately interesting. Running Apple's simulator runtime on x86 Linux without a Mac removes the single biggest cost of mobile QA, and the demo (an agent playing the dino game in Safari, another driving Settings) shows the screen-read-and-tap loop actually closing. If we ever ship a native iOS app, or need to test the Unified Platform at true iPhone viewports with real Safari behaviour, this is the cheapest path to it.

**Pros:**
- No Mac required, no GPU required — the hardware barrier that normally makes iOS testing a separate purchase disappears.
- The agent layer is the point: screenshots in, taps and keystrokes out, which is the interface a computer-use agent needs.
- Built on an existing runtime project rather than a reimplementation, so the hard part (Apple's simulator on Linux) is not being reinvented.
- Recorded at 60 fps in the demo, with release artifacts published — it is a working thing, not a video.

**Cons:**
- We have no iOS app and no iOS release path. The Unified Platform is React in a browser; iPhone-sized testing is a devtools viewport, not a simulator farm.
- Apple's runtime licensing on non-Apple hardware is a grey area, and a department tool built on it would be a compliance conversation nobody wants.
- Four days old, 577 stars, one release — the star curve looks like launch-day promotion more than adoption.
- Heavy: an iOS runtime image plus a VM layer on a box that also runs our agent, for a capability we would use approximately never.

**Should we...**
- ❌ **Skip it** — real engineering pointed at a problem we do not have.

**Impact on our stack:** Low — nothing we run today gets better. It becomes relevant only if a native iOS app for residents or faculty ever exists.

**Why:** This is the cleanest example today of a good tool that fails the fit test. Every property that makes it impressive — no Mac, no GPU, agent-driven screen control — solves a constraint we are not under, because our entire product surface is a browser page and our mobile story is a responsive layout. Adopting it would mean carrying an Apple runtime and a VM layer on the VPS to test a viewport we can already emulate in Chrome. File it as rejected so it does not come around again, and revisit only if a native app enters the roadmap.

### PiBot — w01fb0ss/PiBot

**What it is:** An open-source, local-first AI agent team for the desktop. Named bots work on your own computer — chat with one or put several in a group chat, and they plan, run commands, edit files, browse and use the computer, with risky steps waiting for approval. Apache-2.0, macOS/Windows/Linux plus an Android app, built on the `pi` agent kernel.

**Source:** https://github.com/w01fb0ss/PiBot  ·  Provenance: GitHub search (self-hosted AI, created last 7 days); 575 stars, 87 forks, 9 open issues.

**What's good about it:** The approval gate on risky steps and the multi-agent group chat are the two features most desktop agent projects get wrong, and PiBot ships both. Apache-2.0 is the most permissive licence in today's set, the Android app is unusual for this category, and building on an existing kernel rather than from scratch means the tool-calling layer is not bespoke.

**Pros:**
- Approval-before-action on risky operations, which is the right default for anything that can run shell commands on a personal machine.
- Group-chat orchestration with named bots is a genuinely different interaction model from a single assistant.
- Apache-2.0 with releases published, cross-platform including Android, and a website with documentation.
- Built on the `pi` kernel, so improvements upstream are inherited rather than reimplemented.

**Cons:**
- It duplicates Hermes. We already have skills, cron, MCP, a gateway and a voice agent; a second desktop runtime means a second place to configure model keys, permissions and logs.
- Desktop-first by design — it is not a server runtime, so it cannot host the cron jobs that do our actual work.
- Four days old with 575 stars and 87 forks, which is a promotion curve more than an adoption curve; 9 open issues already.
- Local command execution plus computer control is the highest-risk surface in this category, and there is no security review, no sandbox story and no third-party audit in the README.

**Should we...**
- ❌ **Skip it** — redundant runtime, wrong host, no security story.

**Impact on our stack:** Low — it would sit beside Hermes on the desktop and do a subset of what Hermes already does, while adding another set of credentials and permissions to manage.

**Why:** The interesting question PiBot raises is whether a named, multi-bot group chat is a better interface for the work Shareef hands off than a single agent with skills. It might be, but we cannot answer that by running a four-day-old project with local shell access and no sandbox on the same machine that holds our credentials. The duplication is the deciding factor: every capability listed here exists in Hermes today, on a runtime we control, with an audit trail we wrote. Skip it, and if the group-chat interaction model proves valuable, it is a UI idea to borrow inside Hermes rather than a second agent to install.

## Overall assessment

If we do nothing else, do these, in this order: **1) Pilot ContentSkills on three faculty clips** — copy `brand-brief`, `post-writer`, `post-grader` and `quality-check` into `~/.hermes/skills/` today (they are just SKILL.md files and cost nothing), then run the renderer on three of the 28 interviews on the desktop; if the cuts and captions hold up, it replaces the manual edit loop for the whole library, and if they do not, we have lost an afternoon and learned that a four-day-old pipeline is not ready. **2) Stand up a scratch Google Cloud project and test `gwscli`** against a throwaway calendar and mailbox, so the January decision about folding it into `google_workspace.py` is made on evidence rather than on a February 1, 2027 headline that does not actually bind our consumer-account automation. **3) Add NDJSON trace emission to the cron wrappers** — one line per step with a timestamp, tool name, exit code and result size — because that single change is what turns "the job said nothing" into a diagnosis, and it is the prerequisite for Agent Debugger or any other tool we might point at the problem later.
