### ZCode

**What it is:** Z.ai's (zai-org) open-source coding agent harness — desktop Electron app, browser workbench, and terminal CLI (`zcode`), all built around the same Agent runtime, MIT-or-Apache-licensed TypeScript monorepo. Released Sept 20, 2026, and it hit 6,449 stars in three days.

**What's good about it:** It's not just a CLI wrapper — the repo exposes the full stack: `packages/desktop` (Electron), `packages/web`, `packages/server` (HTTP/WS), `packages/ui` (shared React + Zustand), a `provider` abstraction layer, and `apps/zcode-cli` (TUI + agent runtime + tools). That means you can self-host the same agent runtime across three surfaces and swap providers locally via `ZCODE_BUILTIN_PROVIDER_CONFIG_FILE`. It also ships a documented remote workflow (SSH/WSL with SFTP asset upload) and a clean one-command CLI installer that drops a `zcode` binary into `~/.local/bin`.

**Pros:**
- Genuine tri-surface parity: TUI, Web, and Electron share one agent runtime and one server — so behavior matches wherever you run it.
- Local-first data with `ZCODE_DATA_BASE_DIR` and in-repo provider config, so credentials and session data stay on your machine.
- Token/auth model is explicit — `--token`/`--no-token`, `ZCODE_SERVER_AUTH_TOKEN`, and an access token auto-generated whenever it binds beyond loopback. Sensible default.
- Apache-2.0 + published third-party notice process (`third-party/README.md`), which matters for anything we'd touch at the hospital.
- Very fast community traction (6.4k stars / 1.9k forks in 3 days) signals it'll get maintained.

**Cons:**
- **Z.ai is the same vendor whose coding agent was caught uploading user data without consent** (reported Sept 21–22; Z.ai disabled the feature after the exposure). Shipping a vendor's agent harness into anything sensitive before that incident is fully understood is a real risk.
- Pinned to Node 24.14.0 / pnpm 10.33.2 exactly, and the README is primarily Chinese with a secondary English file — friction for a small team.
- The repo is huge (38,620 KB) and bundles a full Electron desktop app we would never use on a headless VPS.
- No releases page or signed artifacts evidenced; the DMG build is explicitly unsigned and requires `xattr -rd com.apple.quarantine`.
- Its own data-consent posture is exactly the thing that just burned the vendor — need to see a postmortem before trusting the runtime with repo access.

**Should we...**
- 👀 **Watch it** — keep an eye on it, not ready yet but promising

**Why:** The architecture is genuinely good and it's the kind of harness — provider-pluggable, self-hostable, local-first — that we'd want if we ever standardized on a non-Claude, non-Codex coding agent. But the timing is wrong. The same organization had a data-exfiltration defect in its *previous* coding agent disclosed this week, and ZCode's core feature set (broad filesystem + shell access, remote workspace sync) is precisely the attack surface involved. Watching costs nothing; adopting now means inheriting an unresolved vendor security question into an environment where we already carry HIPAA obligations. Revisit after Z.ai publishes a root-cause writeup and a few weeks of public usage.

### RepoPilot

**What it is:** A self-hosted, MIT-licensed agent controller that turns GitHub Issues and PRs into a bounded cycle of test generation → failure reproduction → code repair → *independent* verification, driven by the OpenAI Codex SDK but running the controller, test execution, and reports on your own machine.

**What's good about it:** The design principle is the good part: tests are **frozen before repair**, candidates must preserve test identities, and a *separate* Docker runner verifies before the controller can publish a branch. The controller never merges — maintainers keep that decision. It also accounts for its own model spend (`maxCalls`, `maxAttempts`, `maxTokens`) and fails closed on symlinks, submodules, binaries, and case collisions when reading a repo.

**Pros:**
- **Verification is architecturally separate from generation.** Codex proposes; a pinned Docker runner re-executes and rechecks policy. That's the single most important pattern in autonomous code change, and it's built in rather than bolted on.
- Bounded by construction: attempt limits, call/token budgets, task timeouts, process-tree cleanup, and a persistent cancel request checked every 250 ms.
- Reads repository rules from committed `.repopilot/policy.json` and nested `AGENTS.md`, with **verbatim rule and code citations** in its findings — auditable rather than vibes-based.
- Real test-runner breadth for v1.3.0: Node `node --test`, Vitest, pytest, Go test, and compatible JUnit XML.
- Portable standalone binaries for Linux/Windows/macOS, so no Node install needed to run it; MIT license; explicit SECURITY.md and stated limits (10,000 files / 16 MiB, public text repos, one controller serially).
- Honest documentation — it explicitly says unattended merging and deployment are *not* current capabilities, and that test execution is evidence, not tamper-proof attestation.

**Cons:**
- Public text-based repos only, one serial controller, no dashboard, no webhook server, no distributed queue, no fork-PR execution, no browser E2E. Its own docs list these as out of scope today.
- Hard dependency on the OpenAI Codex SDK and `OPENAI_API_KEY` — model calls go to OpenAI even though the controller is self-hosted. "Self-hosted" does not mean offline here.
- Docker with Linux containers is a hard requirement for test/agent execution, which adds a runtime dependency to any box we deploy it on.
- Early-stage: v1.3.0, no adoption claims made by the authors, and the watched repo surface is text-only repos under 16 MiB — much smaller than our Unified Platform tree.
- No Slack/Telegram notification surface out of the box; we'd be parsing `.repopilot-data` JSON ourselves.

**Should we...**
- ✅ **Adopt it** — integrate into our stack (strongly recommended)

**Why:** This is the closest thing we've seen to a packaged version of the guardrail pattern we keep rebuilding by hand — freeze the test, prove the failure reproduces on base, then let a candidate fix be validated by something that doesn't share the generator's context. Concretely: run it against one bounded, non-clinical repo (interview-unified is a good candidate — it has tests and PR flow already), scoped to `check` mode only with publishing disabled, and see whether its frozen-test discipline catches anything our current review misses. The Codex SDK dependency is acceptable because the controller, policy rules, and report artifacts all stay local, and the skill is how we'd eventually want to let an agent touch a repo at all: bounded, cited, and reversible.

### AnchorShell Relay

**What it is:** A self-hosted AI gateway — one Go binary (with a Vue/Nuxt dashboard compiled in) that sits between your app and 100+ model providers, exposing a single OpenAI-compatible API with queueing, request pacing, model groups, ordered fallbacks, guardrails, and cost/usage tracking.

**What's good about it:** It solves the specific problem our cron scripts keep hitting — a job wants a model, the provider returns 429, and the script does something dumb. Relay queues-first instead of instantly falling back to a weaker backup, so a preferred model stays in play within a wait budget rather than degrading silently. It ships as one compiled binary with SQLite built in: no separate database, no queue to operate.

**Pros:**
- Single-binary deployment with embedded SQLite and a built-in dashboard — meaningfully less infrastructure than the LiteLLM-style alternatives we'd otherwise stand up.
- Queue-first routing with pacing and cooldowns, which is exactly the failure mode that bites our scheduled jobs at 6am when everything fires at once.
- Provider credentials are stored once, AES-256-GCM encrypted in Relay, instead of being copied across every cron script and `.env` — a real secret-sprawl reduction.
- Per-provider limits (request/token/cost/concurrency) plus pre-dispatch and post-response guardrails, so we can block sensitive prompts at the gateway rather than trusting each caller.
- OpenAI-compatible API means existing scripts need only a base-URL and token change; a Playground mode generates the equivalent curl for any request.
- Optional local **Laya** classifier worker (`RELAY_LAYA_URL`) for tagging request intent/complexity without shipping prompts to a third party.

**Cons:**
- Community Edition is *source-available*, not open-source: free for personal/non-commercial and "qualifying small businesses," with other commercial use requiring a separate license. We'd need to check whether a hospital department qualifies before deploying.
- The best routing features (Smart Groups, Pro classification, per-user budgets, teams) are **hosted-only** — the self-hosted edition gets basic classification and static groups.
- The optional Laya worker pulls a pinned PyTorch model and wants Python 3.11–3.13 plus `uv`; skipping it means falling back to the built-in classifier.
- Brand new: launched on Product Hunt Sept 22, version 0.1.0, single vendor (AnchorShell), no independent security review.
- Go 1.26.4 + Node 22.19.0 exact pins for source builds, and the Go backend on port 11730 behind a separate dashboard port is slightly awkward for our Traefik setup.

**Should we...**
- ✅ **Adopt it** — integrate into our stack (strongly recommended)

**Why:** Every one of our scheduled scripts currently carries its own provider handling and its own copy of a key, and the failure mode when a provider rate-limits us is undefined behavior in a cron job that nobody is watching. Relay replaces that with one internal endpoint, one place keys live, one place limits are enforced, and a realtime view of what actually went out — which is also a compliance story, since post-response guardrails give us a chokepoint to inspect content before it leaves. The license question is the one blocker to resolve first: confirm the Community License covers an academic medical center department, and if it doesn't, the hosted tier is still cheaper than the engineering time we're currently spending on retry logic. Start by routing one non-clinical job (the AI brief itself is the obvious pilot) through it before touching anything that moves PHI.

### RondoFlow

**What it is:** A local-first, MIT-licensed platform for visually orchestrating teams of **real Claude Code CLI subprocesses** — you drag agents, skills, safety rules, resources, and MCP connections onto a React Flow canvas, connect them into a DAG, and watch the team execute live.

**What's good about it:** The agents are actual Claude Code CLI processes, not chat completions — so the nodes on the canvas read and write files, run commands, and use MCP tools and skills. On top of that it layers three AI helpers that reason *about* the run: a **Planner** (before — reviews the team/models/order), a **Director** (during — decides continue/redirect/conclude after each step), and an **Advisor** (after — compares result to objective and offers fixes). There's also a Facilitator-driven Team Discussion mode for multi-agent debate.

**Pros:**
- Genuinely executes rather than just wiring prompts — file I/O, shell, MCP, and skills all work because it's spawning the real CLI.
- Three-layer policy model (global → per-agent → per-session) where the *most restrictive wins* and risky commands require approval, plus budget limits to stop runaway cost.
- Workflow generation from a plain-English task description, producing a reviewable 2–5 agent DAG you can edit before it runs.
- Server-enforced RBAC (viewer/editor/admin) on both the REST API and the socket layer, with admin actions written to an audit log — invite-only, no open self-registration.
- Multi-provider in one workflow: Claude Code, OpenAI, and Perplexity agents can coexist.
- Clean Docker Compose story: five containers, browser at `localhost:3000`, no host Node required in Docker mode.

**Cons:**
- **Claude-Code-CLI-bound at the core.** Claude Code is the default and only provider with full tool/MCP/skill access; OpenAI and Perplexity agents are API-based sidekicks. That ties it to one vendor's CLI availability and licensing.
- v1.0.0, reached by forking an existing project (Orchestra), substantial divergence but no independent security review — and SECURITY.md itself warns to review the threat model before exposing it beyond localhost.
- Agents can execute code on your machine by design. A web-accessible canvas that spawns shell-capable subprocesses is a large attack surface for a departmental network.
- Requires Postgres plus five containers and Node 20+, versus Relay's single binary — heavier for what it does.
- Invite-only with admin bootstrapped via `RONDOFLOW_ADMIN_EMAIL`/`RONDOFLOW_ADMIN_PASSWORD` env vars, which is a clunky secrets path for us.
- The "describe it and it builds your team" flow is exactly the kind of feature that looks impressive in a demo and produces unpredictable agent topologies in production.

**Should we...**
- 👀 **Watch it** — keep an eye on it, not ready yet but promising

**Why:** The Planner/Director/Advisor triad is a real idea — evaluating a run mid-flight and deciding whether to continue, retry with sharper instructions, or conclude is precisely what our multi-step agent work lacks today, and the canvas makes an otherwise invisible control flow legible to a non-programmer. But two things hold it back for us: it's built on Claude Code CLI subprocesses, which is a single-vendor dependency we've deliberately avoided binding to, and it exposes shell-capable agents behind a web UI, which we cannot put on a departmental network without a serious isolation story. Worth re-evaluating once it supports a second first-class local provider, or if we stand it up on a throwaway box to study the Director pattern and reimplement just that piece inside our own skills.

### gwae

**What it is:** A daemon-free scrolling terminal multiplexer: run coding agents, shells, and TUIs side by side, and when you add panes past the screen edge the viewport **scrolls** instead of shrinking them. Inspired by niri's scrolling tiling, MIT-licensed, written in Rust.

**What's good about it:** It fixes a real ergonomic problem that tmux does not — tmux splits the same space, so four agents means four unreadable columns. gwae keeps pane width fixed (`1/4` default, `⌥+r` to cycle) and lets the strip scroll, snapping to column boundaries. Agent status is genuinely thoughtful: it reads standard **OSC 133** markers when available and falls back to an output-activity/idle-time heuristic, showing `»` working, `!` needs input, `✓` done, `✗` failed — and `⌥+g` jumps straight to the pane that needs you.

**Pros:**
- Solves a problem tmux structurally can't: readable panes beyond the screen edge, with no sliver columns.
- One process, no daemon, no socket — trivially installable (`brew install hongnoul/tap/gwae`, a curl install script, or `cargo install gwae`).
- OSC 133 status integration plus the `⌥+g` smart-jump means monitoring N agents doesn't require polling each one.
- `gwae run "claude"` / `gwae run "codex"` starts with an existing CLI agent, and it explicitly never claims `Ctrl+J/K` so agent harnesses keep their own chords.
- Forwarded and pane-clipped Kitty graphics, plus a `gwae doctor` config check.

**Cons:**
- **No detach/attach and no session persistence** — the docs are explicit that agent persistence means `claude --resume`, and a process does not survive a disconnected terminal. That's the single biggest thing tmux gives us for long-running work.
- No daemon means no way to reattach from a different machine or after an SSH drop; you'd lose the running process, not just the view.
- Windows support is explicitly experimental (ConPTY), and all chords assume Alt/Option as Meta, which surprises people until they reconfigure the terminal.
- Very new and single-maintainer; the agent status heuristic is documented as "not a guarantee that an agent needs input."
- Doesn't help headless at all — this is a local interactive tool only.

**Should we...**
- 👀 **Watch it** — keep an eye on it, not ready yet but promising

**Why:** Our agent work is dominated by unattended cron jobs on the VPS, where gwae offers nothing — but the desktop machine is a different story, and running several interactive agents side by side without shrinking them into unreadable strips is a genuine daily friction that tmux cannot fix. The blocker is the missing detach/attach: without it, a dropped Tailscale connection kills the session, which is exactly the situation our remote-access setup creates. Worth keeping on the list for the desktop box once it grows session persistence (or paired with tmux purely as a launcher), but not something to standardize on yet.

### typesafe-mcp / skillranker / Jev ecosystem

**What it is:** A cluster of small tools built on TypeSafe.ai's "Jev" model, positioned as fast-and-cheap "system one" primitives for agents: `typesafe-mcp` exposes Jev to any MCP client via a Go connector, `skillranker` is a Rust CLI that ranks agent skills for the next step using live session context, and `jevlang` is positioned as a policy engine for LLM decisions. Related community saw ~268 and ~114 stars respectively within days of creation.

**What's good about it:** The underlying thesis is sound and increasingly popular: not every decision an agent makes needs a frontier model, and a small fast classifier can decide routing, skill selection, or policy questions at a fraction of the cost. `skillranker` in particular has a real design detail — it includes **abstention**, i.e. it can decline to rank rather than guessing, plus structured JSON output and Claude Code hooks.

**Pros:**
- Correct architectural instinct: cheap classifier for the "which skill do I use next" decision instead of a full frontier-model hop.
- `skillranker` supports abstention and local feedback, and emits structured JSON — the right shape for hooking into an existing loop.
- MCP-native, so integration with MCP-capable agents is straightforward rather than a bespoke SDK.
- Interesting lineage — the same week produced a Register piece on Jev's primitives for coders, suggesting real technical substance behind the branding.

**Cons:**
- **All require a TypeSafe API key.** These are not local tools — they're clients for a hosted model, which means session context leaves the machine for a third-party commercial endpoint.
- Sending agent session context to an unknown vendor endpoint is a hard no for anything touching clinical or personnel data, and the tools are designed to consume exactly that.
- The ecosystem is noisy and self-referential: multiple repos created the same day by overlapping accounts, all citing the same model, with stars accruing fast enough to look promotional.
- `skillranker` is effectively a Rust wrapper whose core value lives in someone else's API — no fallback if the vendor changes terms or pricing.
- We already have local classifier options (including the optional local Laya worker in Relay) that don't introduce a vendor dependency or exfiltrate session context.

**Should we...**
- ❌ **Skip it** — not relevant, redundant, low quality, or not useful for us

**Why:** The *idea* — a cheap fast model for agent routing decisions — is right, and we should steal it. The *implementation* is wrong for us: every one of these tools is a thin client around a commercial hosted API that wants your live session context, which is precisely the data class we cannot send to an unvetted vendor endpoint. We also already have a strictly better version of this capability available locally through Relay's optional Laya worker, which classifies request intent on our own hardware with no API key and no egress. If we want skill-selection ranking, the honest move is a small local classifier wired into our own skill loader, informed by the abstention-and-structured-JSON pattern these tools got right.

### LFM2.5-2.6B

**What it is:** Liquid AI's 2.69B-parameter hybrid model, pre-trained on ~34T tokens, whose post-training ran **agentic reinforcement learning inside real agent harnesses** — so tool calling was learned where tool calling actually happens. It runs at 220 tok/s on an M5 Max CPU and fits in about **1.7GB at Q4** on a phone.

**What's good about it:** The training methodology is the interesting part and it's directly relevant to us: Liquid post-trained *inside* Harness, OpenClaw, and Pi — real agent scaffolds — rather than in a synthetic tool-use sandbox. The stated result is that it beats Qwen3.5-9B, a model more than three times its size, on ToolSandbox and instruction following. For a model that fits in 1.7GB, that's a real capability-to-footprint ratio.

**Pros:**
- Post-trained in real harnesses, which means its tool-calling behavior should transfer to harnesses like ours instead of needing heavy prompt scaffolding.
- Beats a 3x larger model (Qwen3.5-9B) on tool-use and instruction-following benchmarks per Liquid's reporting.
- Small enough to run entirely on-device — private by construction, no per-token cost, no network dependency.
- Runs at 220 tok/s on an M5 Max CPU, so it's usable without a GPU.
- Liquid's own model card **scopes it honestly** — explicitly says it's *not* for agentic coding or knowledge-heavy work, and that it's for private on-device agents. Self-limiting documentation is a good sign.

**Cons:**
- 2.7B parameters means real limits: Liquid itself rules out agentic coding and knowledge-heavy tasks, which is most of what our agents do.
- Only 1.7GB at Q4 — the Q4 quant is doing a lot of work in that size claim, and quality at 4-bit is lower than the headline numbers suggest.
- Benchmarks are vendor-reported on ToolSandbox and instruction following; no independent agentic eval published.
- Doesn't meaningfully help our VPS workloads, which are API-model-driven — the payoff is on-device only.
- Very new, and the "hybrid" architecture means tooling support (llama.cpp-style runtimes, quant pipelines) may lag behind standard transformers.

**Should we...**
- 👀 **Watch it** — keep an eye on it, not ready yet but promising

**Why:** The reason to watch this one specifically is that the Hermes Agent harness is named as one of the environments it was RL-trained inside — meaning its tool-calling is being shaped by our kind of loop, which should transfer better than a generic instruct model. The practical applications for us are narrow but real: a fully local classifier for the routing/skill-selection job we just declined to send to TypeSafe, or an offline path where a phone-native agent handles something without any egress. It cannot do our substantive work at 2.7B, and Liquid says so itself. Revisit when there's an independent agentic benchmark and when we have a concrete on-device use case that isn't better served by an API call.

### Qwen3.8-27B

**What it is:** Alibaba's Apache-2.0 27B dense model, released as the community darling of the week — scoring 52 on the Artificial Analysis Intelligence Index (level with GPT-5.6 Luna at max reasoning) and 51 on the Agentic index, while running at roughly 68 tokens/sec on a single RTX 4090.

**What's good about it:** The deployment profile is what stands out — ~40 tok/s on Macs via MLX and even ~11 tok/s in-browser on WebGPU kernels — which means a capability level comparable to a mid-frontier hosted model at zero marginal cost on hardware a small team already owns. r/LocalLLaMA dedicated a release-day megathread to it, and one observed characteristic is worth noting: it leans toward *running shell commands* to interact with the filesystem (file reads, partial reads, content search) rather than reasoning over pasted context.

**Pros:**
- Apache-2.0 with no usage restrictions — cleanest licensing tier for anything we'd deploy internally.
- 27B dense at roughly GPT-5.6 Luna level on the Intelligence Index, and 51 on the Agentic index — genuinely useful agentic capability, not just chat.
- Runs on a single 4090 at ~68 tok/s, and via MLX on Macs — no cluster needed.
- Its noted bias toward shell-tool use rather than context-stuffing is a *good* agentic trait; it means less token burn per task.
- Ships natively multimodal (text/image/video per the family), with a large native context window.

**Cons:**
- Benchmark scores are provider-independent (Artificial Analysis) but still a single aggregate index — no independent agentic eval on our kinds of tasks.
- 27B at practical quantizations needs real VRAM; the "runs on a 4090" claim assumes a 24GB card we'd have to dedicate.
- Serving it ourselves means owning uptime, batching, and upgrades — the operational burden we just decided to reduce by adopting a gateway.
- Version churn in the Qwen line is aggressive (3.5 and 3.8 both landing in recent weeks), so anything built on a specific 3.x will need migration attention.
- Community tooling around a brand-new release lags: llama.cpp builds and quant pipelines need to catch up.

**Should we...**
- 👀 **Watch it** — keep an eye on it, not ready yet but promising

**Why:** This is the first open-weight model this scan has surfaced where the capability-to-cost ratio actually changes a decision for us: at roughly Luna-level intelligence and Apache-2.0 licensing, a locally hosted 27B becomes a credible option for the middle tier of our work — drafting, summarization, classification, routine code edits — where we currently pay per token for frontier models on tasks that don't need them. The reason it's a watch and not an adopt is that we just decided to *reduce* infrastructure complexity by centralizing model routing, and adding a GPU-served local model in the same week cuts against that. The right sequence is Relay first, then register a local Qwen endpoint behind it as one more provider — at which point swapping traffic onto it becomes a config change rather than a project.

### Claude Opus 5.5 / Fable 5.1 / GPT-6 Astra (frontier pricing shift)

**What it is:** A compressed frontier release cycle — Anthropic shipped Opus 5.5 (announced Sept 22) and Fable 5.1 with **cache reads cut 75% to $0.25/M**, and OpenAI launched GPT-6 Astra with a 1.05M-token context window and a 1.9x-faster harness on Mind2Web. Input/output pricing sits at roughly $10/$50 per million on both sides, with a 1M-token context tier now standard.

**What's good about it:** The pricing movement matters more than the benchmark numbers for us. Cache reads at $0.25/M — down from $1/M — is a direct cut to the cost of any agent loop that re-reads a stable system prompt, skill library, or repo context on every turn, which is every loop we run. Astra's long-context numbers (100% MRCR at 256K–512K, 96.3% at 512K–1M) plus Codex's new ability to keep notes *across* context windows and ask the user a question mid-task without stopping work are both structural improvements to long-horizon agent reliability.

**Pros:**
- 75% cheaper cache reads is a real, immediate cost reduction for any agent doing repeated context reuse — our exact usage pattern.
- 1M-token context with near-perfect retrieval accuracy at 512K removes the need for aggressive compaction in long-horizon jobs.
- Codex's cross-context-window notes and non-blocking async questions directly address two failure modes we hit: losing state across compaction, and stalling on a question that other work doesn't depend on.
- Anthropic's 30-day data retention "Covered Model" designation with an optional zero-retention enterprise framework is a compliance-relevant option.
- Pricing is converging at the top ($10/$50 on both sides), which makes provider choice about capability and compliance rather than cost.

**Cons:**
- No migration action is available to us without a deliberate decision — swapping models touches every skill and script.
- Newer models mean new behavior: Anthropic's own prompting guide notes an "Opus 5 jargon style" (mannered prose) that has to be prompted away, which is a regression against our house voice until tuned.
- Real-time misalignment monitoring on every tool-using inference run (per OpenAI's framework) may complicate audit posture rather than simplify it.
- Benchmarks are vendor-reported; Artificial Analysis scored Astra at 61 on its Intelligence Index, *behind* Fable 5.1 — the headline numbers and the independent index disagree.
- The whole release cycle raised the evaluation tax: five frontier models in ten days means any routing layer we build needs re-benchmarking on a weekly cadence, not a quarterly one.

**Should we...**
- 👀 **Watch it** — keep an eye on it, not ready yet but promising

**Why:** Two things here are worth acting on eventually and neither is urgent today. First, the cache-read price cut is a straightforward win for our heaviest token consumers — if our agent loops re-read stable context per turn (they do), we should confirm we're getting the cached rate rather than the full input rate, which is a config check rather than a migration. Second, the 1M-context tier with reliable retrieval at 512K changes what's possible for the vault and briefing work: whole-document reasoning without the compaction dance that loses state. The reason to hold rather than move is that we're mid-flight on routing consolidation — picking a model this week just adds a variable to an environment that's about to change anyway. Land the gateway, then re-evaluate model selection as a routing decision made in one place.

## Overall Assessment

The through-line across everything real that surfaced today is control: RepoPilot bounds and independently verifies what an agent changes, Relay centralizes and constrains what models an agent can reach, and both are adoptable now. That is not a coincidence — the industry spent this week shipping control layers, and the incident reports (Z.ai's coding agent uploading user data without consent, a 0-click RCE class in AI coding agents, an attacker hijacking a coding assistant session across ~100 repos) explain why. The practical recommendation is to act on the two control layers and explicitly *not* to act on the shiny model releases: stand up AnchorShell Relay (after a five-minute license check) and route one non-clinical job — this brief — through it, then put RepoPilot in `check`-only mode against interview-unified with publishing disabled and measure whether its frozen-test discipline catches anything our review currently misses. Defer every model decision, including Qwen3.8-27B, until traffic flows through the gateway, at which point model selection stops being a migration and becomes a routing config. The one thing worth checking this week rather than later is whether our heaviest agent loops are actually receiving the cached-input rate now that cache reads dropped 75% — that is a cost question with a yes/no answer, and it's the only item on this list where doing nothing has a measurable price.
