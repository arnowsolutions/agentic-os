## 1. Lightpanda 1.0.3 — previously covered, new: the CDP browser path

**What it is:** A headless browser built for automation and AI agents, written in Zig, shipped as a single 77 MB Linux binary. It speaks the Chrome DevTools Protocol, so the tools that already drive Chrome can attach to it instead. Version 1.0.3 was published on November 5.

**Source:** https://github.com/lightpanda-io/browser · release: https://github.com/lightpanda-io/browser/releases/tag/1.0.3 · Provenance: GitHub trending (Nov 6); previously covered in the Nov 1 brief as a `fetch` tool.

**What's good about it:** It runs where Chrome cannot. Our Hermes container is Debian 13, user `hermeswebui`, uid 1000, no sudo. `agent-browser install` downloaded Chrome for Testing 157 and Chrome died immediately with `error while loading shared libraries: libglib-2.0.so.0` — the container has no GTK stack and we cannot apt-install one as a normal user. Lightpanda started a CDP server on the first attempt, as an unprivileged process, out of a home directory that survives `docker recreate`. It read the live public schedule correctly: title "Montefiore Urology — Call Schedule", plus the real controls (Contacts, Dark, Print, Calendar, Month roster, the month picker, the All/Moses/Weiler/Wakefield filters). It also executed the React Unified Platform: the accessibility snapshot came back with the actual landing-page headings — "Everything your residency runs on.", "Built for residency operations", Schedules, Reimbursements, Progress, Secure. That is JavaScript running, not a static fetch.

**Pros:**
- **No root, no system libraries, no Chrome.** One binary, one `chmod`, one `serve` command. This is the deciding property for our container, where every apt dependency is a fight we lose on recreate.
- **CDP-compatible**, so it works with agent-browser today and with Playwright's `connectOverCDP` tomorrow. We are not locked into one client.
- **Small and fast.** 77 MB on disk, starts in under a second, and exposes a server mode with connection limits (`max_connections=3832`, `max_browser_connections=16`) rather than one process per call.
- **Lives in the home volume.** Installed to `~/.local/bin`, it survives container restarts and recreates — the same lesson we learned the hard way with watchdogs and `/app`.
- 41,453 stars, 2,048 forks, active today, and 1.0.3 is a real release rather than a trending repo with a README.

**Cons:**
- **AGPL-3.0.** Fine for internal use, but if we ever ship a product that embeds it, the licence follows the service. That is a real constraint, not a formality.
- **No pixels.** It executes JavaScript and builds a DOM, but it does not paint the page. A screenshot of the call schedule came back 1920×1080 with 18 unique colours — white, greys, no palette. It cannot do design QA, contrast checks, or "does this look right".
- **Not Chrome.** Its user agent advertises Chrome 124; agent-browser warns that this is 33 versions behind and lists 1,100 CVEs it does not have the fixes for. Some sites will serve it degraded content, and heavy CSS/JS frameworks may render partially.
- **One static page and one landing page is not a test suite.** We have not clicked through a form, a login, or the schedule's month navigation. Fidelity claims beyond "reads the DOM" are unproven for our apps.
- **The November 1 bench already found its limits:** an AWS WAF BotChallenge on the first protected site, `RobotsBlocked` on Reddit, and a GitHub issues page that timed out. Public pages only, no logins — the same rule as before.
- **AGPL project, no commercial support path documented** on the repo for the open-source binary — we would be our own support.

**Should we…**

- ✅ **Adopt it** — install the binary in `~/.local/bin`, run it as the engine behind agent-browser ← *this one*
- 👀 **Watch it** — keep an eye on it, not ready yet
- ❌ **Skip it**

**Impact on our stack:** **High — Hermes cron and Unified Platform.** Every deploy of the public schedule or the Unified Platform is currently verified by `curl` and by me reading the HTML, which misses anything rendered client-side and misses broken buttons entirely. With Lightpanda, a cron job can open the page, assert the title and a handful of refs, click a control, and fail the job when the result is wrong. It also gives the design-review loop a way to read a page's actual structure during an audit instead of guessing from source.

**Why:** The value is not that Lightpanda is a better browser than Chrome — it is not. The value is that it is the only browser that will run in the place where our agents live. We have spent months working around that gap: `web_extract` for static pages, screenshots taken by hand on the desktop, deploys "verified" by a 200 status. A 77 MB binary in the home directory closes it, and the test above was not a demo — it read two of our own production URLs, one of them a React app, correctly. The honest limit is rendering: this is a DOM and content verifier, not a visual one, so we should adopt it for post-deploy assertions and click-through checks, and keep pixel-level design review where it belongs — on a real browser, on the desktop. Installing it costs nothing; Chrome's failure costs us the illusion that we could ever run Chrome here.

## 2. agent-browser 0.41.2

**What it is:** A native Rust CLI from Vercel Labs that gives an agent a browser it can drive one command at a time. `snapshot` returns the page as compact text with a ref such as `@e1` for each element; the agent acts on a ref, reads the page again, and repeats. The browser stays open between commands in a background daemon, so each step is one short shell call.

**Source:** https://github.com/vercel-labs/agent-browser · https://agent-browser.dev · npm `agent-browser@0.41.2`, published November 3 · Provenance: GitHub trending (Nov 6).

**What's good about it:** The interaction model fits a tool-calling agent instead of fighting it. There is no long-lived Python session to babysit: `open`, `snapshot -i`, `click @e1`, `get url`, `close` — each is a separate process that talks to a daemon, which is exactly how Hermes cron thinks. The snapshot is an accessibility tree with refs, not a screenshot, so it costs a few hundred tokens instead of an image. And it is honest about failure: a click on a hidden, disabled, off-screen or covered element fails rather than reporting success, which is the difference between a verification step that means something and one that always passes. `--cdp` lets it attach to any CDP endpoint, which is how we got it running on Lightpanda. Apache-2.0, 46,197 stars, 3,163 forks, released every few days.

**Pros:**
- **The snapshot format is built for models** — `button "Contacts" [ref=e1]` is directly actionable, and refs avoid brittle CSS selectors.
- **Session daemons** mean state persists across calls without a custom harness, and `--session` isolates parallel jobs.
- **Attach mode (`--cdp`, `--auto-connect`)** is what makes it usable on our VPS at all: bring your own engine.
- **Explicit failure semantics** — covered/disabled targets fail loudly. Our cron jobs need assertions, not reassurance.
- **Broad engine support** — Chrome, Lightpanda, Obscura, iOS Simulator, and cloud providers, so the same scripts can move to the desktop later.
- A published skill (`skills.sh/vercel-labs/agent-browser`) means Hermes could learn the command set rather than me re-documenting it.

**Cons:**
- **It declares Node ≥24 and we run 22.22.3.** npm printed `EBADENGINE` and it worked anyway, but that is an untested configuration that can break on any release. Either upgrade Node in the image or pin 0.41.2.
- **The default install does not work here.** `agent-browser install` pulls Chrome for Testing 157, which cannot start without `libglib-2.0.so.0`; there is no root to install the dependency stack. Without Lightpanda, this tool is inert on our box.
- **It is a CLI plus a daemon, not a library.** In cron we now own daemon lifecycle: start, idle timeout (one hour by default), and cleanup. That is one more thing that can leak across container recreates.
- **493 open issues** and a fast release cadence — the surface is still moving.
- **No visual verification on Lightpanda** — screenshots exist as a command but come back effectively unpainted, so this is DOM QA only.

**Should we…**

- ✅ **Adopt it** — with Lightpanda as the engine, for post-deploy checks ← *this one*
- 👀 **Watch it**
- ❌ **Skip it**

**Impact on our stack:** **High — Unified Platform and Hermes cron.** A wrapper script can now assert, after every deploy: the schedule page loads, the month grid renders, "Contacts" opens, the Unified Platform landing page shows its headings, and the sign-in link exists. That is a real smoke test for the two surfaces Shareef and the residents actually use, and it runs from the same cron runner that already watches the gateway.

**Why:** agent-browser and Lightpanda are one capability split across two repos, and neither is sufficient alone in our environment: agent-browser gives the agent a usable vocabulary, Lightpanda gives it a body that can stand up in a container with no root. Together they passed a live test on both of our public properties this morning. The reason to adopt rather than watch is that the risk here is low and measurable — it is a read-only client that opens pages, and if it breaks, we lose a check, not a system. The reason to scope it tightly is equally clear: Node 22 is below the declared floor, screenshots are useless on Lightpanda, and the daemon needs a watchdog like everything else we run. Install it, write one verification script against the public schedule, and let it prove itself for a week before it gates a deploy.

## 3. Craft Anything

**What it is:** An open-source, clean-room "rebuild engine" from the ArtCraft team, written in Rust. You point it at a website, app or game, say what you want, and it inspects the original with real tools, has a coding agent build a new project, checks the result against the original and refines it. It ships as a desktop app, a CLI (`craft-anything-cli rebuild https://example.com "Recreate this website"`) and an MCP server exposing 320 tools.

**Source:** https://github.com/storytold/craft-anything · https://getartcraft.com/apps/craft-anything · Provenance: spotted on **Hyperautomation Labs** — https://www.youtube.com/watch?v=_Etse2-mjqA

**What's good about it:** The similarity check is the part that matters. It does not just generate a page and call it done — it compares its build against the original page by page and reports how alike each one is, then iterates against that number. The video's own results (a feature rebuilt at 4,915/4,915 on its check list, a site at 91% alike) are the vendor's framing, but the mechanism is visible in the README, not just in a demo. The engineering behind it is not a weekend project: 48 contributors, 2,955 forks, 100+ commits in six days, a real CLI, an MCP server, and adapters for Claude Code, Codex and Copilot CLI. For our purposes the interesting use is not cloning someone else's site — it is rebuilding one of our own legacy pages from a screenshot or a live URL into a fresh React component and getting a scored diff instead of an opinion.

**Pros:**
- **A score, not a vibe.** Page-level similarity is precisely the feedback loop our redesign work lacks; "does it look like the mockup" currently depends on my eye.
- **CLI and MCP**, so it can run from an agent rather than only from a GUI.
- **Real inspection tools** — it studies the target with the same 320 tools it exposes, rather than guessing from one screenshot.
- **48 contributors and active daily pushes** — the star count is promotion, the contributor graph is not.
- **Runs on our own machines** and takes our own coding agent's sign-in; no ArtCraft account required for the build.

**Cons:**
- **Six days old and labelled early alpha** in its own README, with 306 open issues. The gap between "works in a demo" and "works on a React app with auth" is where alpha projects die.
- **It needs a signed-in coding agent** — Claude Code first, with your own `claude` login; Codex and Copilot adapters exist. Running that on a datacenter IP is the same account-risk conversation we had about X and Instagram, and it burns real tokens per rebuild.
- **Licence discrepancy:** the README badge says "MIT OR Apache-2.0", the GitHub repository metadata says Apache-2.0. Minor, but it is the kind of thing to settle before we depend on it.
- **Legal exposure on third-party targets.** A clean-room reverse-engineering tool pointed at someone else's site is a copyright and terms-of-service question. Pointed at our own, it is fine.
- **Desktop-first, Rust 1.97 to build from source** — a heavy install for a tool we would use occasionally.

**Should we…**

- ✅ **Adopt it**
- 👀 **Watch it** — pilot on one of our own pages when it leaves alpha ← *this one*
- ❌ **Skip it**

**Impact on our stack:** **Medium — Unified Platform redesign.** It could turn a redesign hand-off into a scored rebuild: take the approved mockup URL, rebuild it, get a similarity number, iterate. That would compress the loop between "here is a preview" and "here is the React port" — the exact step where our redesigns have drifted.

**Why:** This is the most substantial thing in today's feed and the closest to a problem we actually have — faithfully porting a design into code without losing features, which is the failure mode Shareef has called out more than once. But it is six days old, it is early alpha by its own label, and its workflow requires a coding agent with an account and a token budget. The sensible posture is to watch it for two or three weeks and then run one controlled test on a page we own, comparing its output against the current port. If it scores well and the code is clean, it becomes a real tool. If not, we have lost a test, not a quarter.

## 4. Beacon

**What it is:** An open-source, local-first memory layer for coding agents, written in Go. It captures session history from Claude Code, Cursor, Codex, OpenCode, Cline and 20+ other harnesses, turns workflows, corrections and debugging patterns into reusable knowledge, and exposes that knowledge back to agents through MCP or Agent Skills. It also keeps exact session traces — prompts, tool calls, commands, edits, approvals, tokens.

**Source:** https://github.com/asymptote-labs/agent-beacon · https://beacon.sh · Provenance: named in **The Next New Thing** — https://www.youtube.com/watch?v=-s4rbKbrO0w (link in the show notes: github.com/asymptote-labs/agent-beacon)

**What's good about it:** The premise is the one we keep rediscovering the hard way: a problem solved by one agent should not be learned from scratch by the next. Our own record proves it — the container-recreate lesson, the PWA service-worker lesson, the Vapi bridge tunnel lesson were each learned twice before they were written down. Beacon automates the writing down: it records the trace, extracts the pattern, and serves it back through MCP so any agent can retrieve it. The project is six months old, MIT, actively released (v1.3.56 on Nov 5), and local-first by design — durable JSONL on disk, an explicit destination, no harness lock-in.

**Pros:**
- **Exact session replay** — prompts, responses, tools, commands, edits, approvals, MCP activity and tokens in one trace. That is better evidence than any log we currently keep for a failed cron run.
- **Knowledge retrieval over MCP or Agent Skills**, which means Hermes could consume it as a tool without a custom integration.
- **Local mode keeps everything on the machine** — `beacon traces` is a terminal browser over local data, and nothing is sent anywhere.
- **Cross-harness** — if we ever run Claude Code or Codex alongside Hermes, the knowledge does not fragment.
- **Mature release cadence and MIT licence**, with an install path that does not require root (user-mode tarball).

**Cons:**
- **The default wizard pushes Beacon Cloud.** Signing in preselects a managed destination that forwards session history to Asymptote Labs. For a stack that touches patient-adjacent data, that default is disqualifying unless someone deliberately chooses Local, and defaults are what busy people accept.
- **It does not capture Hermes.** The supported harnesses are Claude Code, Cursor, Codex, OpenCode, Cline and similar. Hermes is not on the list, so the sessions we most want to learn from are exactly the ones it would miss.
- **Overlap with what we already have.** Hermes memory, the capability ledger and the skills library already do a version of this; adding a second memory store risks two half-truths.
- **`sudo apt install` for the .deb** — the same root problem as Chrome, with a user-mode workaround that is less documented.
- 23 open issues and a vendor dashboard attached to an "open-source" product; the business model is visible in the onboarding.

**Should we…**

- ✅ **Adopt it**
- 👀 **Watch it** — local mode only, and only if it can see Hermes sessions ← *this one*
- ❌ **Skip it**

**Impact on our stack:** **Medium — Hermes cron operations.** If Hermes traces could be fed in, the recurring failures (watchdogs lost on recreate, env-file ordering, double-prefixed API paths) would become retrievable knowledge instead of paragraphs in my memory file. As it stands, the value is limited to whatever else we run alongside it.

**Why:** The idea is right and the execution looks serious, but the fit is wrong in two specific ways: it cannot see Hermes sessions, and its default path sends data to a vendor cloud. Either one alone would make this a watch; together they make it a watch with a condition — try it in local mode on a scratch machine, see whether the MCP retrieval is good enough to justify a bridge into Hermes, and do not let the wizard's preselected cloud option anywhere near department data. The reason it still earns a breakdown rather than a skip is that "make agent knowledge compound" is the correct diagnosis of our most expensive recurring problem.

## 5. hermes-voice

**What it is:** A Home Assistant integration that lets you talk to a Hermes Agent profile out loud through Assist. A custom component (`custom_components/hermes_voice`) sends each conversational turn to a Hermes profile's API with a stable `X-Hermes-Session-Id`, streams the reply so speech starts early, cleans it for speech, and speaks a short fallback instead of error text. The repo also ships a Hermes skill that configures the whole thing, a guide for building a dedicated voice profile, and a reproducible pipeline that trained a "hey hermes" wake word. It is designed to run on an old Amazon Echo running `echo-dot-assist`.

**Source:** https://github.com/majorminorlabs/hermes-voice · Provenance: GitHub search API — voice-agent repos created since Oct 30; 309 stars, created Nov 5.

**What's good about it:** It integrates with Hermes the correct way, not by scraping a chat window. It uses the profile API (standalone `:8650/v1` or the multiplexed `:8642/p/<profile>/v1`), keeps history on the Hermes side via a session header, and streams partial output so the speaker starts before the model finishes. The speech-cleaning step — stripping markdown and tool noise before TTS — is the detail most voice integrations miss, and the "short fallback instead of error text" choice is what keeps a voice assistant from reading a stack trace into the kitchen. The inclusion of a trained wake-word model and a setup skill shows someone actually ran this end to end.

**Pros:**
- **Correct Hermes API usage** — session continuity, streaming, profile selection by URL. It could be a reference for our own voice work.
- **A Hermes skill ships with it**, so the agent can configure its own voice profile rather than us hand-editing SOUL.md.
- **Cheap hardware path** — a used Echo Dot instead of a new device.
- **Speech-specific handling** — cleaning, fallbacks and early streaming, which is where most of the perceived quality lives.
- MIT, small, readable (25 commits, two contributors), and it does not ask for credentials beyond the local API.

**Cons:**
- **One day old.** Created Nov 5, two contributors, four open issues. There is no track record at all.
- **It requires an Echo on custom firmware** (`echo-dot-assist` replaces the Alexa client while keeping Fire OS). That is a hardware project with a real chance of bricking a device, and it is not something to do to a department asset.
- **Voice quality is whatever Home Assistant's pipeline gives you** — Whisper for STT, Piper for TTS. Fine for a kitchen; not a phone line.
- **It is not a Vapi replacement.** No telephony, no inbound number, no barge-in, no call control. The open question from yesterday's OpenRing pilot is untouched by this.
- **Home Assistant becomes a dependency** — another service to run, back up and secure.

**Should we…**

- ✅ **Adopt it**
- 👀 **Watch it** — interesting for personal use, not for the department line ← *this one*
- ❌ **Skip it**

**Impact on our stack:** **Low — voice, and only on the personal side.** It would give Shareef a way to talk to a Hermes profile in a room without opening a laptop. It would not improve the Vapi bridge, the call-out line, or anything residents touch.

**Why:** This is a well-built little integration aimed at a hobbyist setup, and the honest read is that its value to us is as a reference implementation rather than a deployment. The Hermes session-header pattern and the speech-cleaning step are worth copying into our own voice work; the Echo firmware and Home Assistant dependency are not worth adopting for a department. Watch it, read the custom component when we next touch the Vapi bridge, and leave the hardware alone.

## 6. Scenario Agent Skills

**What it is:** A set of Agent Skills from Scenario that teach coding agents to produce images, video, audio, textures, skyboxes and 3D through the Scenario MCP server. The skills pick the right model for the job, price the render before spending, and carry character and brand consistency across generations; expert families also drive Blender, Maya, ZBrush, Unreal and Unity.

**Source:** https://github.com/scenario-labs/skills · https://skills.sh/scenario-labs/skills · https://mcp.scenario.com · Provenance: GitHub trending (Nov 6); MIT, 3,322 stars, pushed today.

**What's good about it:** Two things we actually need. First, **it prices before it spends** — the skill estimates the cost of a generation before firing it, which is the difference between a content pipeline and a surprise invoice. Second, **character and brand consistency** — the same face, the same palette, the same product across a set of images, which is exactly what a department's social feed needs and exactly what one-off prompts fail at. The MCP transport means Hermes could attach to it as a tool rather than us writing a new integration, and the skills are grouped by role (2D artist, producer, etc.) instead of dumped in one pile.

**Pros:**
- **Cost preview before generation** — rare, and directly addresses the "we burned $40 on bad images" problem.
- **Model routing** — the skill chooses among Scenario's models instead of us hard-coding one.
- **Consistency controls** for characters and brands across a campaign.
- **MCP + skills**, so it fits Hermes and Claude Code without a bespoke connector.
- MIT skills, active repo, real docs and an OSS scorecard badge.

**Cons:**
- **It is a vendor in the loop.** Scenario account, OAuth or API key, credits, and their model catalogue. Our image work currently goes through model-specific paths; this centralizes it on a paid platform.
- **The skills target coding agents** (Claude Code, Cursor, Codex, Copilot); installing them is an `npx skills add` away, but the workflow assumes an agent that can run shell commands.
- **No medical or health-content evidence** — brand consistency for a hospital is a different problem from brand consistency for a game studio, and clinical accuracy still needs a human.
- **Texture/3D/engine integrations are irrelevant to us** — most of the repo's surface is for game art.

**Should we…**

- ✅ **Adopt it**
- 👀 **Watch it** — trial for the social-content pipeline with a hard credit cap ← *this one*
- ❌ **Skip it**

**Impact on our stack:** **Medium — social media content pipeline.** A cost-previewed, consistency-preserving image path would make the faculty-interview and campaign work more predictable: same look across a series, known spend per render, and an MCP interface Hermes can call.

**Why:** The social program is real and the pain is real — images that do not match across a series, and spend that is invisible until the bill. Scenario's skills address both, and the MCP path means we would not be building another bespoke integration. But it is a paid platform with a vendor account, and our current image work already has a working path. Watch it, run one campaign through it with a credit cap, and compare the consistency and the cost against what we do today. If it wins on both, it earns a place; if it only wins on convenience, we keep what we have.

## 7. Claude certifications

**What it is:** Anthropic now runs four official Claude certification exams: Claude Certified Associate ($99), Claude Certified Developer ($125), Claude Certified Architect – Foundations ($125) and Claude Certified Architect – Professional ($175). The training for all four is free; the exams are proctored and cost between $99 and $175 per attempt, valid for 12 months.

**Pros:**

- **Fast** — under an hour per video, which is a real throughput advantage.

**Cons:**
- **It is a faceless-content factory.** The product's own marketing is "channels that run on one click per video" and "real channels, real money". That is the opposite of a clinical brand built on named faculty and real interviews.
- **No medical accuracy control.** The script is whatever you paste; the footage is generic stock. For anything a patient might act on, that is a liability, not a shortcut.
- **No source control or review workflow** — you get an MP4, not an editable project.
- **Subscription SaaS with opaque credit pricing** and no self-hosted option.
- **The output style is recognizable** — the same caption style, zoom punches and counters that every other faceless channel uses.

**Should we…**

- ✅ **Adopt it**
- 👀 **Watch it**
- ❌ **Skip it** — wrong tool for a clinical brand ← *this one*

**Impact on our stack:** **Low.** It would not touch the platform, the agents or the data. At best it is a content vendor we do not need.

**Why:** Shareef already has the raw material this tool is trying to fake: 28 real faculty interview clips, real names, real expertise. Turning those into stock-footage documentaries with synthetic narration would spend the department's credibility to save editing time. The honest use case for GoMotion is a faceless channel with no experts in it — which is precisely what we are not. Skip it; if video throughput becomes the bottleneck, the answer is a proper editor working from the faculty footage, not a one-click factory.
