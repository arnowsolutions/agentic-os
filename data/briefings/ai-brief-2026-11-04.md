## 1. OmniDiff

**What it is:** A content-aware diff tool written in Rust. Instead of treating every file as lines of text, it parses each side with tree-sitter and diffs the syntax tree, so a changed Python expression, a renamed PDF box, one redrawn glyph in a WOFF2 font, or one edited PNG region is reported as *that change* rather than as a whole replaced line or `Binary files differ`. It runs as a terminal TUI, as git's `difftool`/`GIT_EXTERNAL_DIFF`, in `--headless` batch mode, and with `--mode json`.

**Source:** https://github.com/ivankovic/omnidiff · showcase: https://ivankovic.github.io/omnidiff/showcase/ · release verified on the VPS: `v0.3.0`, published 2026-11-01 · Provenance: spotted on **Github Awesome** — https://www.youtube.com/watch?v=20tIkdPmhgQ *(same repo also appears in 71xuvjb80EU's trending list)*

**What's good about it:** It closes a real gap in our workflow. Every time Hermes edits a file for Shareef, the receipt is a unified diff — and a unified diff is where "did the agent change the one line it said it changed, or rewrite the block?" turns into manual reading. I verified the actual behaviour rather than trusting the README: with a naive `total()` refactored into `return sum(numbers)`, `--headless` printed `-` on the three removed lines and a single `~` on the changed `return` line, and `--mode json` emitted hunks with row/column ranges and an `update` operation for exactly that expression — automatable. It also reports *what kind of change* a non-text edit is (invisible / imperceptible / artifacts / edited / redrawn / replaced), which for a design-to-design comparison is the difference between "the PNG changed" and "the padding moved by 4 px".

**Pros:**
- Verified working on this VPS out of the box: prebuilt `x86_64-unknown-linux-gnu` and `musl` tarballs on every release, no runtime deps, 54 MB binary, `v0.3.0` shipped two days ago.
- Three machine-readable surfaces — `--headless` plain text, `--mode json` with a published JSON Schema, and a defined exit code (I confirmed exit 2 on bad arguments) — which means a cron job can *assert* what changed instead of a human eyeballing it.
- Content coverage that matters to us specifically: PDF page-by-page (the GME handbook, the reimbursement tip sheet), Office documents and EPUBs inside archives, fonts, images, and message catalogs.
- Python, TypeScript, Rust etc. diffs are AST-based, so refactors read as moves rather than as deletes-plus-inserts — exactly the noise that makes agent diffs unreviewable today.
- Real engineering, not promotion: 1,535 commits, a CI badge that resolves, a coverage endpoint measured from `research/data/coverage/`, a commit-per-day cadence since Oct 2025.
- Drops into git in one command (`omnidiff git configure`) so nothing about the existing workflow has to change.

**Cons:**
- **License ambiguity is real.** The GitHub sidebar reports `NOASSERTION` while the README badge says AGPL-3.0-only; the actual LICENSE file confirms AGPL-3.0-only, and `LICENSE-COMMERCIAL` (v1.0, dated 2026-09-24) sells monthly subscriptions to organisations that cannot accept source-disclosure obligations. AGPL on a self-hosted CLI that we never distribute is fine for us — but it is not MIT, and the two "readings" of the license badge are the kind of thing that gets found in an audit and has to be explained.
- **One contributor.** 1,535 commits, one login. There is a bus factor of one person in Switzerland, and AGPL + commercial dual-licensing means the commercial tier is the roadmap.
- It is a terminal TUI at heart. Over SSH without `-t` the interactive viewer won't open (the README says so); the batch modes are what we would actually use, and those are the less-exercised paths.
- Binary formats other than pictures, archives, fonts, cursors, PDFs and catalogs still degrade to `Binary file <path> differs` — verify against the specific file, not the table.
- 57% "fast" on PDFs and under ten judged PDF test cases: thin evidence behind the most impressive-looking claim.
- AGPL means if we ever embed it in a product we hand to another department, the source obligation travels with it. Fine for internal tooling; a trap for anything we ship.

**Should we…**
- ✅ **Adopt it** — integrate into our stack
- 👀 **Watch it** — keep an eye on it, not ready yet but promising ← *the honest label, given the license and one-person risk, but pilot it now*
- ❌ **Skip it**

**Impact on our stack:** High — **Hermes cron (agent receipts) and Unified Platform (design review).** Concretely: (a) wrap every agent file-write in a Headless/JSON OmniDiff so the Telegram receipt says "3 expressions changed in UnifiedPage.tsx" rather than dumping a 200-line unified diff; (b) diff `unified-*-redesign-vN.html` and screenshots version-to-version and let it tell us whether a change was *edited*, *redrawn* or merely *re-encoded*, which is the "did the redesign actually change the layout or just re-render it?" question we currently answer by squinting.

**Why:** The redesign loop and the agent-receipt loop share the same failure: a diff that is technically correct and practically unreadable. Shareef's standing instruction is that a "still not good" verdict means reset to the principle, not micro-tune — but we cannot tell whether a change *was* a micro-tune or a real move, because line diffs smear them together. OmniDiff answers that at the only place it can be answered cheaply: the file level, before anyone opens a browser. It qualifies as a pilot rather than an adopt for two concrete reasons — the AGPL/sidebar-license mismatch and a single-author bus factor — but neither is a reason to wait, because the risk of running it read-only is near zero: I installed it from a released tarball on this box and it produced correct output on the first try with no configuration. The move: add `omnidiff --headless` to the file-write receipt path in one Hermes workflow and to one redesign comparison, look at both outputs, and only then decide whether it becomes the default diff.

## 2. Looper

**What it is:** A Go daemon (`looperd`) plus CLI (`looper`) that registers local checkouts of GitHub or Forgejo repos, picks up issues by label and assignee, and runs four role agents in sequence — planner, reviewer, fixer, worker — each looping against its own success criterion until a PR is ready for human merge. It shells out to an already-installed agent CLI (`claude-code`, `codex`, `cursor-cli`, `opencode`, `grok-build`, `pi`, `omp`) using your own credentials, and isolates work in git worktrees.

**Source:** https://github.com/nexu-io/looper · Provenance: spotted on **ManuAGI** — https://www.youtube.com/watch?v=iSGafeh186o

**What's good about it:** The design decision that matters is that each role loops against a *stated exit condition* rather than a fixed step count — "planner loops until the spec PR is open and labeled", "fixer loops until every actionable review thread is resolved". That is testable, and it is the difference between an autonomous loop and an expensive one. It is deliberately local: a daemon on the machine, a thin CLI, `looper ps` / `looper logs` / `looper stop`, no hosted control plane, worktrees per run so two loops cannot fight over the same files. Vendor-pluggable by design, which means the model choice stays ours. MIT, Go, and it runs a real CI workflow with E2E tests including a live sandbox mode.

**Pros:**
- Success criteria per loop, written into the README as testable end-states — auditable autonomy rather than vibes.
- Local daemon with inspectable state and a stop button; worktree isolation limits blast radius to one branch.
- Bring-your-own agent CLI, so no new subscription and no new key to leak — it uses whatever is already authenticated on the box.
- `network.mode=off` exists as a documented mode for single-machine operation.
- Four months of history (created April 2026, pushed Oct 28), 403 commits from the primary author plus a handful of others, MIT.

**Cons:**
- Contribution history is lopsided — 403 commits from one author, 17 from the next. Effectively a one-maintainer project with a 47-issue backlog.
- It needs a live `gh` auth on the machine, and it *acts* on that account: creating issues, branches, PRs, labels and comments. On our VPS that means a real GitHub token with write scope sitting next to production code — the same class of risk that got us in trouble with the Montefiore login in July.
- The loop agents run with *your* credentials and no sandbox beyond a worktree. If a reviewer and fixer disagree forever, it will politely burn tokens until something stops it.
- Go binary + daemon + agent CLI + `gh` is a real install surface on a box that we currently keep deliberately thin.
- The pitch assumes a repo with a healthy issue/PR culture; our repos are push-to-main, so there is nothing for it to claim.

**Should we…**
- ✅ **Adopt it**
- 👀 **Watch it** — keep an eye on it, not ready yet but promising ← *this one*
- ❌ **Skip it**

**Impact on our stack:** Medium — **agentic-os / Hermes cron.** The concrete change would be converting "cron job notices a drift and pings Shareef" into "cron job files an issue, an agent plans and implements it in a worktree, and a reviewer loop argues until the PR is clean" for low-risk repos like the interview portal and the briefings tooling.

**Why:** The architecture is the right one for where we are heading — autonomous work with *stated* success criteria and a human merge gate — and it is the most honest implementation of that idea I have seen in a while, because it does not pretend the human is optional. What keeps it at watch is that adopting it today would mean putting a write-scoped GitHub token on the VPS and pointing a looping agent at repositories where a bad merge reaches a live student-facing portal. Our current operating mode is a human reads the diff and says go, and Looper's whole premise is that most of those reads are unnecessary — which is very likely true, and still not a safe first step on a system with no branching discipline. The right trial is a throwaway repo: register one sandbox repo, wire `claude-code` or `codex` as the vendor, and see whether the reviewer↔fixer ping-pong converges or spins. If it converges, the next candidate is the interview portal's non-production branch, with a token scoped to that single repo.

## 3. T3 Code

**What it is:** An MIT-licensed "agent harness control surface" (TypeScript/Electron) — a single server plus web app, desktop app, iOS and Android apps that drive whatever coding-agent CLIs are already authenticated on your machine: Claude Code, Codex, Cursor CLI, Grok Build, OpenCode, Google Antigravity, fx. You start `t3` on a computer, and the phone becomes a remote for agent sessions running there.

**Source:** https://github.com/pingdotgg/t3code · https://t3.codes · Provenance: spotted on **Github Awesome** — https://www.youtube.com/watch?v=20tIkdPmhgQ

**What's good about it:** It is a *control surface* rather than another agent, which is the only honest way to build this — it does not ask you to move your subscription or your keys, it drives the CLIs you already trust. 45,284 stars, 9,333 forks and a real release pipeline across winget, scoop, Homebrew, `.deb`, AUR and nixpkgs. The authors state plainly "we are very very early… expect bugs" and that they are mostly not accepting contributions, which is more candour than most trending repos manage. `t3 service install` keeps a background daemon, and there is a documented remote-access path plus MCP interop so other agents can attach.

**Pros:**
- Drives existing authenticated CLIs — no new key, no new subscription, no model lock-in.
- Genuinely cross-platform client set (iOS, Android, web, Electron) for a problem that is usually solved by SSH from a phone.
- MIT, huge contributor base, forkable by design — the README says so explicitly.
- Serious packaging: signed-ish distribution through every major package manager, dedicated `.deb`, nixpkgs entry.

**Cons:**
- The install path is `curl … | sh` or `npx t3@latest` — a remote-shell-install of a fast-moving pre-1.0 project, which is exactly the pattern we should not run on the VPS.
- It requires at least one *interactively authenticated* agent CLI on the host, which is the credential-on-a-datacenter-IP situation we already decided against for anything account-bound.
- 4,830 open issues on a project created nine months ago; the maintainer says big features are not being accepted. You are adopting a moving target you cannot steer.
- Our agent does not live on a workstation — Hermes runs on a headless VPS and talks to Shareef over Telegram. A phone remote for terminal agents on a Windows laptop does not solve a problem we currently have; the laptop is not where the work happens.

**Should we…**
- ✅ **Adopt it**
- 👀 **Watch it**
- ❌ **Skip it** ← *this one, for the VPS*

**Impact on our stack:** Low — it would sit on the desktop, not the server, and our desktop usage is upload-and-ask, not live terminal sessions.

**Why:** This is a well-built product aimed at a workflow we do not have. The value it promises — start an agent on my workstation, check on it from my phone — is already delivered for us by Hermes over Telegram, which runs on the machine where the work actually is and needs no session handoff. Adopting it would mean installing a `curl | sh` server plus a set of authenticated agent CLIs on a desktop and keeping a 4,830-issue pre-1.0 project in sync, for a capability we already have. If Shareef ever wants to drive long Claude Code sessions from his phone against a repo checked out on the Windows desktop, this becomes a reasonable install *on that desktop* — but it is a desktop tool, not a stack improvement, and it does not touch Hermes, Unified Platform, CRM, voice or email.

## 4. Sarvam Prism — *news*

**What it is:** An open-weights "System One" decision model built by Sarvam AI on the Sarvam 105B-10B base. Instead of generating prose, it picks among options and returns a calibrated confidence, scoring 71.8 average across three decision benchmarks at a 44 ms median response on a single B200 GPU — the highest score under 100 ms among 25 decision models they benchmarked. Released Nov 3 with open weights for enterprise fine-tuning on private data.

**Source:** https://www.sarvam.ai/blogs/sarvam-prism · Provenance: Google News RSS, 2026-11-04

**What's good about it:** The category is the interesting part. Most of our automations that would benefit from a model do not need prose — they need "approve / deny / escalate" plus a confidence number the system can act on. A model whose *errors stay inside its confidence bounds* and whose answer does not change when you reorder the options is a different kind of component than an LLM; it can be given a threshold and wired into a control flow. Open weights mean the decision logic could eventually run on our own hardware, which is the only version of this a healthcare department should consider.

**Pros:**
- Calibration is the headline and it is the right headline: a decision model is only automatable if its confidence is trustworthy.
- Order-invariance — same options in a different order, same answer — kills a whole class of bias bugs in approval flows.
- Open weights, small active parameter count (10B base), enterprise posture.
- Fast enough (44 ms) to sit in a request path rather than in a batch job.
- Transparent self-benchmarking, including the models it loses to.

**Cons:**
- Benchmarks are Sarvam's own, on their own three indices, with their own timing harness. The top-of-table claim is against models they chose to include.
- The strongest column in their own table is *Indian languages* (82.5) — a deliberate strength that is irrelevant to us.
- "Decision model" means it answers multiple-choice-style questions, not free-form clinical or administrative judgment. It will not adjudicate a scheduling conflict described in a paragraph of email.
- Open weights for training do not equal open weights for inference convenience; a B200 is not in our rack.
- Vendor-authored announcement in a very new category that a competitor (TypeSafe/Jev) defined a month ago — the benchmarks are young and moving.

**Should we…**
- ✅ **Adopt it**
- 👀 **Watch it** — keep an eye on it, not ready yet but promising ← *this one*
- ❌ **Skip it**

**Impact on our stack:** Low today, Medium if the class proves out — the plausible target is **Unified Platform** approvals (call-out swap requests, schedule-conflict triage) where a calibrated yes/no/escalate would replace a human read of a queue.

**Why:** The concept is a better fit for our administrative automations than a general LLM, and calibration plus order-invariance is exactly what would make an automated approval defensible if anyone ever asked how it decided. But the model is Indian-language-leaning by design, benchmarked mainly against itself, and tuned for a category that is three weeks old. Filing it as news-watch is the honest call: in six months, if two or three of these decision models are stable and one can run on a card we can rent, the question "should the call-out swap queue triage itself?" becomes answerable with a threshold instead of a guess. Until then there is nothing to install.

## 5. Hyperresearch

**What it is:** A hosted research agent that runs long deep-research passes (3–5 hours, 150–200 sources), checks every cited claim against its source before shipping the report, and keeps all sources in a searchable workspace vault. New this week: an "Answers" MCP server and API where an agent's lookup returns a short answer with word-for-word quotes, or `not_found` — never a guess. Started as an MIT repo, now a paid product with $5 of free credit.

**Source:** https://hyperresearch.ai · https://www.producthunt.com/products/hyperresearch · Provenance: spotted on **ManuAGI** — https://www.youtube.com/watch?v=iSGafeh186o

**What's good about it:** "`not_found` instead of a hallucination" is precisely the failure mode that has burned us in this brief — the standing rule against fabricated items exists because a research tool once confidently produced things that did not exist. A researched return type that includes the verbatim quote and the page's own age is the correct API shape for an agent that has to prove a claim. Durable sources matter too: a follow-up question should not re-crawl the web, and their answer to "does a citation resolve to what the run read or to the live page?" was "what the run read," which is the right answer for an audit trail. The maker's own ratio claim on 100 BrowseComp questions (89% vs Parallel 73%, Perplexity Sonar Pro 43%) is checkable in principle.

**Pros:**
- Evidence-first API contract: quotes, source age, and an explicit `not_found` — designed for agents, not for shoppers.
- Persistent source vault with semantic search, so research compounds instead of restarting.
- MCP server drops into any MCP client, which our stack already speaks.
- Honest provenance: it started as an MIT repo and they say so.
- Free $5 credit, no card — cheap to test on real questions.

**Cons:**
- Hosted and paid. Every question we ask leaves our network, and our questions are about a healthcare department.
- The maker's benchmarks are self-reported on a benchmark they say they lead; the comparison numbers came from their own harness.
- "Double-checked against its source" is a claim about their pipeline, not a guarantee we can inspect — the repo is MIT but the product is not the repo.
- 3–5 hour deep runs are priced for people with time; ours is a daily brief, not a quarterly report.
- The product is days old on Product Hunt, which is exactly when the pricing and reliability story is least proven.

**Should we…**
- ✅ **Adopt it**
- 👀 **Watch it** — keep an eye on it, not ready yet but promising ← *this one*
- ❌ **Skip it**

**Impact on our stack:** Medium — **Hermes cron** research jobs (this brief, news digests) could call an `ask` that returns quotes-or-nothing instead of me re-checking every claim by hand.

**Why:** The API contract is the best design idea of the day: an answer that carries its own receipts and says `not_found` when the receipts are missing is exactly what the "never fabricate an item" rule has been doing manually for months. What stops adoption is everything around the idea — it is hosted, it is paid, and the moment it is doing real work for us it is reading our prompts. For a department whose data posture rules out sending work behind a stranger's login, the right first test is a single low-stakes question with a publicly checkable answer, run through the free credit, to see whether `not_found` arrives when it should. If the contract holds, the interesting future is wiring it as an optional `ask` tool in the brief job with a hard rule that its output is a *lead*, never a filing. Until the vault index lets us dedupe, it changes nothing.

## 6. hop

**What it is:** A single Windows application (C#/.NET) that installs Linux alongside Windows without a USB stick: it verifies the machine, shrinks or finds free space, copies a verified ISO's files onto a small FAT32 partition on the internal disk, adds a one-time signed boot entry, and reboots straight into the distro's own installer.

**Source:** https://github.com/Arjun-Ingole/hop · Provenance: spotted on **Github Awesome** — https://www.youtube.com/watch?v=20tIkdPmhgQ

**What's good about it:** It is a genuinely clever reduction — a USB installer is just a FAT32 volume with an ISO on it, so make one on the internal disk and skip the stick. The release notes are unusually honest for a trending repo: 0.3.2 says out loud that physical PCs have had limited testing and to back up anything you cannot lose, and each entry names the specific bug it fixes (`$Mft::$BITMAP` blocking the shrink, "Ready when nothing was installed", a startup entry that could land first by accident). It verifies downloaded ISOs against published checksums, refuses to touch the disk until preflight checks pass, and requires typing `ERASE` for the destructive path.

**Pros:**
- A real problem — finding a USB stick is the actual blocker for a first Linux install.
- MIT, signed commits, a proper changelog, and preflight checks before any disk mutation.
- The Undo path is taken seriously: give the space back, list what could not be removed.
- Supports both a dual-boot and a full-replace path, with the full-replace list limited to systems actually observed working.

**Cons:**
- Created Oct 30 — four days old, one contributor, `v0.1.0`'s own release note says "Don't use this build… a bug here can stop the install after the disk has changed." That failure mode is the one that costs data.
- It repartitions a live Windows disk. SmartScreen flags it because it is not code-signed; it wants administrator rights; BitLocker must be fully off for some paths.
- 1,487 stars in four days with an empty README exception list — star velocity on a four-day-old single-author repo is promotion, not proof.
- Irrelevant where we would use it: our servers are Linux and our agents run in a container. This is a personal-laptop tool.

**Should we…**
- ✅ **Adopt it**
- 👀 **Watch it**
- ❌ **Skip it** ← *this one*

**Impact on our stack:** Low — nothing in Hermes, Unified Platform, CRM, voice or email touches this.

**Why:** It solves a laptop problem with the highest blast radius of anything in today's brief, and it has been in the world for four days. The only machine it would help is Shareef's Windows desktop, and the cost of being wrong is a repartitioned drive — while the benefit, if we ever want a Linux laptop, is one USB stick's worth of convenience that `rufus` already provides for free with ten years of scar tissue. Skip it, and revisit only if it is still being maintained in six months with physical-hardware testing described in the changelog.

## Overall assessment

If we do nothing else, do these, in this order:

**1) OmniDiff — pilot it on receipts and redesign comparisons.** It changes what an agent's "here is what I changed" message *is*: from something a human must re-read to something a cron job can assert, and it gives the redesign loop a factual answer to "did this change the layout or just re-render it?" Verified working on this VPS, one tarball, no configuration, batch and JSON modes for automation.

**2) Hyperresearch — one free-credit question with a checkable answer.** It changes how this brief grounds itself: from me hand-verifying every claim to an API that returns quotes or `not_found`, with the caveat that its output would be a lead and never a filing.

**3) Looper — a throwaway sandbox repo to see if the reviewer↔fixer loop converges.** It changes the shape of maintenance work from "cron notices drift and pings Shareef" to "cron files an issue and an agent ships a reviewed PR," but only if the loop demonstrably converges before we point it at anything live.
