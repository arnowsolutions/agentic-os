# AI & Hermes Brief — November 08, 2026

**The one question:** which of today's tools, repos and platforms is best for *our* system to make a major improvement?

**Short answer: OpenViking.** It is not a new repo — it is a 41.7k-star context database from ByteDance's Volcengine team with 100+ contributors — and that is exactly why it wins today. It ships a **first-class Hermes integration that is already bundled in the Hermes build we run** (`hermes memory --help` lists `openviking` as a bundled provider), it benchmarks Hermes memory at **33.38% → 82.86% on LoCoMo** with 34–91% fewer input tokens, and adopting it is one command, not a migration.

While verifying that, I found a live defect in our own stack: `hermes memory status` reports provider **mnemosyne**, plugin **NOT installed** — the plugin directory is a symlink to `/opt/hermes/.venv/...`, a path that does not exist in this container. So our external-memory slot has been pointing at nothing. The built-in MEMORY.md/USER.md still works (that is where 6,000 characters of standing notes live), but the layer that would give every cron run shared, searchable, retrievable context is inert. OpenViking fills that slot with something real.

### 1. OpenViking — the context database Hermes already has a slot for

**What it is:** A self-hosted "context database" for AI agents. Everything an agent knows — documents, memories, skills — is organised as a virtual filesystem under `viking://` that agents navigate with `ls`, `tree`, `read`, `write` and `grep`. Every directory carries a generated abstract (L0) and overview (L1), so an agent judges relevance from the summary before opening the full text (L2), and semantic search is scoped to a directory subtree rather than a flat vector pool.

**Source:** https://github.com/volcengine/OpenViking · docs: https://docs.openviking.ai · Hermes integration: https://docs.openviking.ai/en/agent-integrations/05-hermes · Provenance: Hacker News Show HN (`volcengine/OpenViking` — "We Build Shareable Context Layer for Agent Teams", Nov 8) — no tracked channel covered it.

**What's good about it:** The Hermes integration is not a community adapter, it is **shipped**: `hermes memory --help` on our box (v0.21.5) lists `openviking` among the bundled providers, and the documented path is three commands — `hermes plugins install openviking --enable`, `hermes memory setup openviking`, restart. Setup offers **Quick Local**, which installs a local server plus an embedding model and reuses our existing model for extraction — no separate vector database, no new API contract to babysit. The mechanism itself is the interesting part: sessions become files, memories are extracted as Markdown you can read, edit and merge, and every memory has a `viking://` URI and an **evidence link** you can audit in the memory graph. For a system whose failures are silent and only discovered weeks later, inspectability beats accuracy claims. The vendor's own numbers — LoCoMo 33.38% → 82.86% for Hermes, input tokens down 34.3–91.0%, latency down 58–66% — are exactly the two things that hurt us: a 6,000-character memory ceiling and long cron prompts rebuilt from scratch every run. Licensing is cleaner than it looks: the **Hermes plugin in `examples/hermes-plugin` is MIT**, only the server is AGPL-3.0 (fine for internal use — we never distribute it), and the repo is backed by three papers (VLDB 2026, ICDE, arXiv) rather than a landing page.

**Pros:**
- **Zero-integration adoption.** The provider is already in our Hermes build; this is a config change plus a local server, not a port. The fallback path is documented too: if a release drops the built-in provider, it tries to install the catalog plugin for existing profiles.
- **Directory-scoped retrieval instead of a flat index.** We have five distinct knowledge domains (residency operations, CRM, the Unified Platform, copy/brand, infra runbooks) that currently all collapse into one 6,000-character file. `viking://resources/<project>/` gives each its own searchable subtree with summaries above it.
- **The three-tier loading model directly attacks token cost.** L0 abstract → L1 overview → L2 full text is the same discipline as our skills index, but enforced by the store instead of by prompt discipline.
- **Sessions are durable and inspectable.** "Commit a session, get Markdown memories back" is the audit trail our cron jobs lack — today the only record of what a job concluded is a Telegram message.
- **Real engineering behind it:** 100 contributors, top committer at 327 commits, three peer-reviewed papers, a published benchmark harness with reproduction scripts in `./benchmark`.
- **Hermes is a listed partner project**, alongside deer-flow and NVIDIA cuVS — this integration will be maintained, not orphaned.
- **Commercial escape hatches exist** (managed SaaS on Volcengine, BYOC for self-managed) if we ever need support, and the OSS server needs no activation key.

**Cons:**
- **Self-hosting needs more than a text model.** The server requires a model provider with an **embedding model and a VLM** for ingestion; Quick Local installs a local embedding model, and the reference memory evaluation used Doubao 2.0 Pro + Doubao-embedding-vision. That is a new cost line and a new failure mode on a box that already runs Traefik, Postgres, the Unified Platform, the voice agent and two watchdogs.
- **It is another daemon.** Quick Local "keeps its server running after Hermes exits" — on this VPS that means a third process to watchdog, and our history says daemons that are not in the external watchdog installers die silently on `docker recreate`.
- **The headline benchmark is vendor-run.** LoCoMo and tau2-bench numbers come from OpenViking's own blog and its own harness, with Volcengine's models as the judge stack. Nobody independent has reproduced the Hermes 33% → 83% jump.
- **AGPL-3.0 on the server plus an unusual clause:** the licence forbids wholesale re-open-sourcing and requires written permission to translate the codebase into another language. Irrelevant for internal use, relevant if we ever want to fork or embed it in something shipped.
- **Feature surface is enormous** — VikingBot, Studio, desktop app, nine SDKs, LangChain adapters. The blast radius of a bad upgrade is proportional.
- **Memory is only as good as what gets committed.** The plugin commits at 20,000 pending tokens, at session end, or on session switch; a cron job that dies mid-run may commit nothing.

**Should we...**
- ✅ **Adopt it** — integrate into our stack (strongly recommended)  ← **our call**
- 👀 **Watch it** — keep an eye on it, not ready yet but promising
- ❌ **Skip it** — not relevant, redundant, low quality, or not useful for us

**Impact on our stack:** High — **Hermes cron + agentic-os**. Concretely: flip the memory provider from the broken `mnemosyne` slot to `openviking` with Quick Local, point `viking://resources/` at the four things every job re-derives from scratch (the copy-desk brand rules, the vault/briefing archive, the infra runbook set, the CRM crosswalk notes), and measure one week of cron runs for prompt size and repeated-question rate before touching anything else.

**Why:** Our agents are amnesiac by construction. Every cron run starts with a 6,000-character memory file and a system prompt, then rebuilds context from disk — the brief format itself exists because a job cannot remember what it learned yesterday. OpenViking is the one item in months that changes that at the layer where it matters, and it does so through a provider slot Hermes already has, with an MIT-licensed plugin and a documented Hermes path. The reason this is an adopt rather than a watch is that the risk is bounded and reversible: `hermes memory off` returns us to built-in-only memory, and the server touches its own directory. The reason to do it *this week* is the defect I found while checking — the provider is set to `mnemosyne`, whose plugin directory is a broken symlink to `/opt/hermes`, a path that does not exist in this container. We are paying for a memory provider slot that has been doing nothing. Either install OpenViking behind it or turn it off; leaving it broken is the only indefensible option.

### 2. cinecode — a film studio that renders from code, not footage

**What it is:** A repository of skills that lets a coding agent (Claude Code desktop/VS Code/terminal, or Cursor) write a film as code: a script, every frame built in three.js, sound designed, rendered in headless Chrome and encoded with ffmpeg into a finished MP4. It targets short films, long-form YouTube documentaries with acts and chapters, product/ad films, and 30–60 second vertical social explainers.

**Source:** https://github.com/sarpstar/cinecode · English README: https://github.com/sarpstar/cinecode/blob/main/README.en.md · Provenance: GitHub search API — new agent repos created since Nov 1, sorted by stars (1,193★, 221 forks, created Nov 3).

**What's good about it:** The output format is exactly the shape our social program needs — **9:16, 1:1 and 16:9 versions with safe areas** from one master, kinetic type built line by line, −14 LUFS mastering, and a credits file generated for the video description. Two design decisions show taste: the agent is instructed to collide the user's idea with something real from the world (a museum object, an old invention, a historical place) so it does not produce the first generic idea, and every proposal is compared against films you already made so it does not repeat itself. For long-form it claims researched scripts with a source for every claim about a real person or event, and open-archive photography and documents. It also does the thing most "AI video" tools skip: it shows you the first two scenes for approval before rendering the film.

**Pros:**
- **It is code, not a model** — deterministic re-renders, version control on the film, no per-second generation bill. Voice-over is optional and can use a free Gemini quota, ElevenLabs, or a local voice.
- **Correct aspect-ratio matrix out of the box** (9:16 / 1:1 / 16:9 with safe areas), which is the single most tedious part of publishing to Instagram and X from one asset.
- **Brand-safety mechanics that matter to us:** a "specificity test" that rejects a film which could belong to another brand, and a colour/font/logo intake from the advertiser.
- **MIT, tests badge, English/Chinese/Japanese READMEs** — a 5-day-old repo that already documents itself in four languages.

**Cons:**
- **Seven commits, three contributors, two of whom are literally `claude` and `cursoragent`,** and last push was Nov 3. Everything above is a claim in a README from a repo that has not been touched in five days.
- **It contradicts a standing brand rule.** Our campaign photography is real photos of real faculty; cinecode renders illustration, 3D, paper, ink, clay and pixel styles. It cannot produce a real attending in a real clinic.
- **Render cost lands on our VPS** — headless Chrome + three.js + ffmpeg is CPU-bound, and this box is already running Traefik, Postgres, the Unified Platform, a voice agent and the M4B player.
- **Turkish-first project**; the English README is a translation and some agent instructions may still assume Turkish voice options.
- **No medical/claims review path.** Health-adjacent video with generated narration and generated claims is precisely where a hallucinated statistic becomes a compliance problem.

**Should we...**
- ✅ **Adopt it**
- 👀 **Watch it**  ← **our call**
- ❌ **Skip it**

**Impact on our stack:** Medium — **social media content pipeline**. A concrete first use that does not touch patient content: the department's recurring *explainer* and *event-promo* videos (match day, research symposium, residency recruitment) in 9:16 with kinetic type, while photography stays real.

**Why:** Shareef's social program needs volume in vertical formats and this is the first repo I have seen that produces that volume from a git checkout rather than a per-second bill. But it is five days old, has never been updated, and its output style is the opposite of the "real photos of real faculty" rule that governs the campaign. Watching costs nothing; the trigger to adopt is a v0.2 with actual commit history and one rendered explainer we can compare against a human-made one. If it holds up, the first job is recruitment-season explainers, not anything with a patient or a clinical claim in it.

### 3. devvm — one VM per project, because an agent should not have your whole machine

**What it is:** A CLI that gives every project folder its own isolated VM built on Lima, with the toolchain the project's files imply (node, python, rust, go, dotnet), coding agents (Claude Code, Codex, opencode, pi) pre-wired with your settings, skills and MCP servers, and **network tiers that default to an allowlist**.

**Source:** https://github.com/devvmhq/devvm · docs: https://devvm.dev · Provenance: GitHub search API — new repos created since Nov 6, sorted by stars (381★, created Nov 6, 621 commits by the lead maintainer).

**What's good about it:** It treats agent isolation as the product rather than a side effect. The VM mounts only the project folder at the same path; `devvm --clone` goes further and gives the VM its own clone so **nothing in the VM can touch your working tree or `.git`**, and work arrives back only through `git fetch devvm` plus a reviewable diff. Network access defaults to an allowlist tier, and "your GitHub token and Claude Code token stay on your machine" is stated as a property of every tier. For anyone who has ever run `npm install` on a trending repo to see what it does, that is the missing seatbelt. It also gets the small things right: `devvm doctor` tells you what is missing, releases are signed with a minisign key, and the install-script verification procedure is documented.

**Pros:**
- **Per-project isolation with a reviewable return path** (`git fetch devvm`, `git log -p main..devvm/main`) — the cleanest agent-sandbox model I have read in months.
- **Network allowlist by default**, which is the control that would have limited the damage in most "agent did something surprising" stories.
- **Toolchain detection from project files** — no Dockerfile to write, no image to maintain; `cd` in and run `devvm`.
- **Real engineering:** 621 commits from the lead (w3cj), MIT, dependabot wired up, layered images (docker/nix/desktop) shared read-only across VMs.
- **Secrets stay on the host**, not inside the sandbox — the opposite of the usual container pattern.

**Cons:**
- **It is a workstation tool.** It needs Lima 2.2+ and, on Linux, QEMU with `/dev/kvm`; our Hermes runs in a container on a VPS where nested KVM is not a thing. It cannot protect the environment it would actually need to protect here.
- **Not tested on Intel Macs**, and macOS 13+ on Apple silicon only — if Shareef's desktop is either of those, that is a hard stop.
- **It solves a problem Docker already solves for us.** Our agents run *in* containers on the VPS; the risk they carry is not a dirty laptop, it is root on a shared host.
- **Another abstraction layer** over Lima to learn, with its own image store and upgrade path.
- **381 stars in two days** on a repo with 621 commits suggests an imported history, so star velocity tells us nothing about adoption.

**Should we...**
- ✅ **Adopt it**
- 👀 **Watch it**  ← **our call**
- ❌ **Skip it**

**Impact on our stack:** Medium — **agent execution safety, but only on the desktop**. It would not change the VPS; it would change how Shareef's own machine handles a repo he wants an agent to try.

**Why:** The idea is right and the implementation looks serious, but the deployment target is wrong for us today: we need agent isolation on the VPS, where devvm cannot run, and we already have containers there. The honest use case is narrow and real — when Shareef wants Claude Code or Codex to take a run at a repo on his laptop, `devvm --clone` gives him a VM with an allowlist and his credentials outside it. That is worth watching and worth a test on the desktop, not worth adopting as stack infrastructure. If KVM isolation ever comes to the VPS, this becomes an adopt; until then it is a good answer to a question we are not asking on the machine that matters.

### 4. good-door (elbab) — a secret manager written for agents that must not see secrets

**What it is:** A single-file CLI (`elbab`) that encrypts credentials with age, keeps each machine's key in the OS vault or chip (Keychain, Secure Enclave, TPM/systemd-creds, GNOME Keyring/KWallet, DPAPI), and gives agents a `run` path so a command gets the secret **in its environment while the agent never sees the value**. `show` and `csv query` mask output when it detects an agent shell (`CLAUDECODE`, `AI_AGENT`, `CODEX_*` set).

**Source:** https://github.com/dreamers-laboratory/good-door · Provenance: GitHub search API — new repos created since Nov 4, sorted by stars (198★, 42 forks, created Nov 4).

**What's good about it:** It names our exact failure mode in its first paragraph — "they read what you left in plaintext: `~/.aws/credentials`, an SSH key with no passphrase, a `.env` in an old backup, or a token in an agent's transcript." The migration story is the strongest part: `elbab import-env app .env && elbab encrypt .env` then `elbab run app -- npm start`, plus `ssh-protect`, `aws-protect`, `guard-seal` shims for `gcloud`/`az`, and `elbab scan ~/code` which reports **names, never values**. Recovery is deliberately boring: plain `age -d` plus `tar` recovers a file without elbab, so we are not locked in.

**Pros:**
- **The agent-safe primitive we do not have:** `elbab run <entry> -- <cmd>` puts the value in the environment of one process and never in a file or a transcript.
- **Agent detection is built in** — when the shell looks like an agent, `show` output is masked unless you explicitly ask for it.
- **Real migration commands** for the sprawl we actually have: `.env` files, SSH keys, cloud CLIs, whole directories.
- **Escape hatch by design** — plain age + tar recovery, no proprietary store, no server.
- **A threat model written down in "Limits"**, including the honest one: anything running as you can call elbab.

**Cons:**
- **Four commits, one author, four days old.** No tests run in CI by default (`gh workflow run test` is manual), no releases, no second contributor.
- **Its Linux backends do not exist in our container.** TPM/systemd-creds, GNOME Keyring and KWallet all assume a real Linux host; inside a Docker container the only workable option is `--identity-file`, which puts the age key on the same disk as the secrets — the threat it defends against is partially reintroduced.
- **The `.env` files it would protect are baked into container config** (`env_file` loads at start), so `elbab run` cannot wrap the gateway, the Unified Platform or the voice agent without changing how they are launched.
- **Scope creep risk:** it also wants to manage SSH keys, AWS, gcloud and shims, which is a lot of blast radius for a tool this young.
- **"Anything running as you can call elbab"** — with our agents running as the same user, an agent can call `show --dump`, so the masking is a speed bump, not a boundary.

**Should we...**
- ✅ **Adopt it**
- 👀 **Watch it**  ← **our call**
- ❌ **Skip it**

**Impact on our stack:** Medium — **Hermes cron secrets and email/Outlook credentials**, if it were host-native. In our container it would be Low.

**Why:** The problem is real: we have `.vault.env`, Supabase keys in two places that must match, Google OAuth tokens, SMTP credentials and a rotating set of API keys, and the failure mode (a token in a transcript) is exactly what this tool targets. But where it must run is where it cannot: our agents live in a container with no TPM, no keyring and no systemd-creds, so the only supported path is an identity file on the same disk. That is a marginal improvement over `.env` files, not the protection the README promises. Watch it, and if it grows an encrypted-file-with-passphrase backend plus a second contributor and tests, re-open the question — this is the right shape, four months too early.

### 5. DeepTutor — a personal tutor that keeps its own memory

**What it is:** A learning workspace (desktop app + web + CLI) from HKUDS that runs chat, quiz, research, visualize, solve, mastery-path and reading modes over your own materials, builds versioned knowledge libraries with LlamaIndex, PageIndex, GraphRAG or LightRAG, and exposes three layers of memory — L1 traces, L2 facts, L3 synthesis — that are visible and editable in a Memory Graph.

**Source:** https://github.com/HKUDS/DeepTutor · site: https://deeptutor.info · Provenance: spotted on **ManuAGI** — https://www.youtube.com/watch?v=yDQ69gYO4RM (timestamps `05:15 - DeepTutor`).

**What's good about it:** "Mastery Path" is the mode that matters for a residency program: it is the only item in months that models *learning progress* rather than answering questions. It grounds answers in documents **with source-linked citations**, supports learning beside video and audio, and can run persistent "Partners" (Claude Code, Codex, Grok CLI) with their own resources — the pattern of a study agent that keeps its own shelf of material. The memory model is the most interesting engineering: three layers, evidence links, and everything editable, which is the opposite of the black-box memory most tools ship.

**Pros:**
- **Genuinely large and maintained:** 56.6k stars, Apache-2.0, v1.7.0 on Oct 28, pre-built Docker images on GHCR, a published arXiv preprint, and a docs site.
- **Built-in citation discipline** — answers link to the source passage, which is the minimum bar for anything a resident would use for exam prep.
- **Versioned knowledge libraries** so the MKSAP/urology-reading corpus could be swapped per academic year instead of rebuilt.
- **Docker deployment exists**, so it could run beside our stack rather than on Shareef's laptop.
- **CLI and agent-native interface** — it can be driven by Hermes rather than only by a human.

**Cons:**
- **324 open issues** and a very broad surface (books, calendar, task board, practice, IM channels, subagents) — it is a product, not a component, and adopting it means adopting all of it.
- **Nothing here is built for clinical education.** No ACGME milestones, no case logs, no in-training exam mapping; a program director would be hand-mapping everything.
- **Heavy:** LlamaIndex/GraphRAG/LightRAG plus a memory graph plus partner agents means Postgres/vector storage, embedding compute and a UI to administer, on a box that is already at its limit.
- **Student data.** Resident study habits, weak areas and quiz history are personal data; running that through a self-hosted app is fine, but it needs a real access-control decision we have not made.
- **The 56k stars are a research-lab magnet effect** — HKUDS repos trend hard; star count is not evidence of fit for a urology department.

**Should we...**
- ✅ **Adopt it**
- 👀 **Watch it**  ← **our call**
- ❌ **Skip it**

**Impact on our stack:** Low–Medium — **resident education**, a system we do not run today (the Unified Platform covers schedule, call-outs, evals, reimbursement).

**Why:** This is a watch with a specific trigger: if the department ever wants a self-hosted study companion for the in-service exam, DeepTutor is the most credible starting point I have seen, and its citation discipline is the reason. But it is a product with its own UI and its own data model, and buying it means operating it — for a program of this size that is a project, not a config change. Nothing about it improves the systems that are failing today (memory, secrets, cron reliability, publishing), so it goes on the watch list with a clear condition: a small pilot with one year of urology reading material and no resident-identifiable data.

### 6. download-anything — one command to fetch and file almost any media

**What it is:** A Python CLI (`da`) plus an Agent Skill that takes a URL, a share token, a DOI, an ISBN or a package id and downloads the media **with its structured attachments** — subtitles, cover art, separate audio track, `citation.bib`, localized images, `.info.json`/`.md` metadata — then verifies integrity with `ffprobe`/`pypdf`/`Pillow` so an HTML error page is never mistaken for a successful download.

**Source:** https://github.com/nengong/download-anything · Provenance: GitHub search API — new repos created since Nov 4 (85★, created Nov 4, pushed Nov 8).

**What's good about it:** The design principle is the useful part: **verify the artifact, do not trust the exit code**. It checks both audio and video tracks and duration with `ffprobe`, checks document and archive structure, and fails loudly. It also strips the garbage off share text — emoji, promo prefixes, extraction codes — which is exactly what a Google Drive or YouTube link pasted from a phone looks like. Obsidian-ready Markdown output with localized images is a nice touch for the copy desk's research files.

**Pros:**
- **Integrity verification** (`ffprobe` two-track check, PDF/EPUB/ZIP structure) — the thing most downloaders skip and the reason "the transcript is empty" bugs happen.
- **Structured sidecar output** (`.srt`, `cover.jpg`, `audio.mp3`, `citation.bib`, metadata) ready to feed an agent or an Obsidian vault.
- **Ships as an Agent Skill** for Claude Code/Codex, so Hermes could drive it the same way.
- **MIT** — and worth noting: GitHub's sidebar reports no licence, but the `LICENSE` file is a plain MIT text. That is a detection failure, not a legal gap.

**Cons:**
- **Four days old, 85 stars, one author, Chinese-first documentation** — the English README is a translation and some CLI details are only in Chinese.
- **Most of its sources are Chinese platforms** (Bilibili, Douyin, Xiaohongshu, WeChat, 网易云) that we will never use; the Western coverage (YouTube, arXiv, Apple Podcasts) is the thin part.
- **Downloads from YouTube and similar violate platform terms** in ways that matter more for an institutional account than for an individual.
- **Overlaps with what we already do:** the audiobook pipeline already handles Drive links, and `yt-dlp` covers the video case in one line.

**Should we...**
- ✅ **Adopt it**
- 👀 **Watch it**  ← **our call**
- ❌ **Skip it**

**Impact on our stack:** Low — **the M4B audiobook pipeline and content research archiving**. It would replace a bespoke download step with a verified one.

**Why:** The verification idea is worth stealing even if we never install it: our pipeline failures tend to be "the file arrived but it was an HTML error page", which is exactly what `ffprobe`-based checks catch. But as a tool it is four days old, written for a Chinese media ecosystem, and duplicates `yt-dlp` plus our existing Drive handling. Watch it; if it stabilises and the English docs catch up, it is a clean replacement for the ad-hoc download step in the audiobook flow.

### 7. Bird — agents that can call, text and email you

**What it is:** Bird (formerly MessageBird) is an enterprise customer-communications platform — email, SMS and voice — that now exposes an **MCP endpoint (`mcp.bird.com`), a CLI and agent skills** so Claude, Cursor, ChatGPT or a custom agent can send email and SMS, verify domains, read inbox replies and place calls as a first-class tool call.

**Source:** https://bird.com/ai · docs: https://bird.com/docs/ai/set-up-your-agent · Provenance: spotted on **Matt Wolfe** — https://www.youtube.com/shorts/A5SfzBD6M3o ("Claude Code Just Called My Phone").

**What's good about it:** The pattern is genuinely useful and it is the same one we built for Kimberly: an agent that hits a decision it should not make alone **calls a human** instead of sitting in a terminal. Bird's version is one API for email + SMS + voice with deliverability tooling (domain verification, inbox reply reading) that we have had to assemble by hand from SMTP plus Twilio.

**Pros:**
- **One platform for three channels** with an official MCP server, so any agent gets `send email`, `send SMS`, `place call` as tools without custom glue.
- **Deliverability infrastructure** (domain verification, reply reading) that our plain-SMTP sender lacks.
- **Routing is inbound too** — messages can be routed *to* an agent, not just from it, which is how a real call-out line works.
- **Works with the agents we already run** (Claude Code, ChatGPT, Cursor, Codex).

**Cons:**
- **It is a third-party CPaaS in the path of clinical communication.** Email and SMS content would traverse a vendor we have no BAA with; our current SMTP path at least stays inside Montefiore-controlled mail.
- **No self-host, no free tier for what we would need** — a paid workspace, verified domains and provisioned numbers, i.e. a procurement decision, not a config change.
- **Redundant with what we run:** Kimberly already does outbound voice on Vapi with a dedicated number, and our email path is deliberately boring for compliance reasons.
- **Agent-initiated calls to humans are a policy problem before they are a technical one** — who may call whom, with what script, and what gets logged, is undefined for us.

**Should we...**
