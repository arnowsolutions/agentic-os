### Underlay's five files — how a studio put 490 screens through an agent without losing the file
**Link:** https://x.com/marcelkargul/status/2122430710053019994 · published **16 November 2026** · by Marcel Kargul (founder, Kargul Studio; 470 likes, 26 reposts, 33 replies) · the product: Underlay, an all-in-one workspace for agencies
**Type:** Workflow (a documented production method)

**What it is:** A first-person account of putting **490 screens** — 244 desktop frames, 246 mobile — of a real product through Claude Code running *inside Figma through the plugin API*, with designers owning every screen and a 24-page brief as the input. The honest framing is in the opening: they asked Claude to add a screen and **"it came back completely wrong. black fallback colours behind every token, icons with five different stroke weights, frames clipping content they shouldn't. not because Claude is bad at this, but because everything that makes our work feel right lived in our heads. Claude had no way to see it."** The fix was not a better prompt. It was five files.

**What's good about it:** The finding that makes this worth the whole brief: **"Figma stores a fallback colour when you bind a variable. Claude was writing black. it looked fine in screenshots, because screenshots resolve variables."** Their designers caught it only by opening the actual file — *"there are a lot of problems like this, don't you see them?"* — and that single sentence invalidates the review method almost everyone uses on AI-generated UI. Everything else follows from it. **File one:** a three-tier token system (foundations → 244 raw palette variables → theme with one brand colour on a 12-step scale → tokens named for *use*: `text/sub-600`, `bg/weak-50`, `state/error/base`), with one rule: the agent binds to tokens, never types a hex. **File two:** one markdown file as the agent's memory, one sentence per decision, reason and date attached, because sessions end and context compresses — *"the reason matters more than the rule. when Claude hits a case nobody wrote down, the reason is what it works from."* The examples are the good part: *"44px buttons: 18px icon, 8px gap. set after icon sizes drifted across mobile."* / *"sheet top edge: 54px or 102px. never in between. anything else cuts the iOS nav bar in half."* / *"light brand colours: if it can't hit 4.5:1 contrast against white, the button gets darker. a yellow brand still needs to be readable."* **File three:** six named blocks — list card, sheet, form sheet, dock, bottom bar, empty state — but only *after* designers had drawn real screens and noticed what kept being rebuilt. They deliberately built no component library upfront. Notably the bottom bar exists because a floating card was rejected by the designers as looking like *"a box inside a box."* **File four:** an audit script run after every batch, checking fallback colours against token values, raw hex, text styles on every text node, icon stroke weight against icon size, clip only on frames with effects, button size/radius/padding. **File five:** the compounding rule — every correction becomes a fix, a written rule with reason, an automated check if possible, and a retroactive pass over every screen already drawn. *"pull the gaps to 8px" → rule written. 59 buttons updated across all mobile pages. audit check added.*

**Pros:**
- **It names the failure mode of screenshot review and then closes it.** One audit pass caught **112 icon vectors with the wrong stroke weight**; another found **clip incorrectly set on 858 frames**. Neither is visible in a rendered image. This is the single most transferable technical fact in today's scan: if your review artifact is a screenshot, you are not reviewing the file.
- The rule file's format — one sentence, the reason, the date — is the cheapest high-leverage artifact in the entire brief, and it is the same idea `sui-motion` arrived at from motion and `craft` from states, now with a production number attached.
- Inference from real screens rather than a library designed in advance. Six blocks carried almost every mobile screen *because* the designers drew first and named later; a library built upfront would have produced twelve blocks that didn't fit.
- Retroactive application is the part everyone skips. The correction changes the existing screens, not just the next one — which is what makes the workflow compound instead of oscillating.
- The honest division of labour, stated without modesty: **"Claude handled the volume. it did not make a single design decision. taste, judgement, 'this doesn't feel right' — all our team."**

**Cons:**
- **No before/after images with the numbers attached.** 470 likes and a claim about 858 frames, from a founder promoting his own product and his own studio. The audit output is quoted, never shown; there is no repo, no script, no screenshot of the rule file.
- The sample is one team, one product, one design system, one model — and the author is selling agency services on the back of it. Treat the method as a hypothesis with a plausible mechanism, not a result.
- Everything depends on Figma's plugin API surface, which is the least stable integration in the stack. The 112-icon catch presupposes a naming and layer convention disciplined enough for a script to read; a messy file returns noise.
- Six blocks carrying "almost every mobile screen" is a description of a product with a narrow layout vocabulary. Transplant it to a schedule grid, a 40-field form and a role-gated dashboard and the block set has to be rebuilt, not copied.
- The 24-page brief is doing enormous unexamined work. Nothing in the post explains how those 24 pages were written, and that is where most of the design decisions actually live.

**Should we...**
- ✅ **Adopt it** — the five-file structure, starting this week.
**Why:** Shareef's platform is code, not Figma, which makes this *more* applicable rather than less — every one of the five files has a direct code-side equivalent, and one of them solves a problem we demonstrably have. The Unified Platform runs on a navy `#003da5` single-accent system with an Inter type scale and flat SVG icons; the exact drift Underlay describes (icon strokes at five weights, buttons at four radii, a spacing value invented because nothing fit) is what happens when six agents and three humans touch the same surface over a year. What to do, concretely: (1) write `design-system.md` in the reason-plus-date format, seeded from the rules we already hold in our heads — 44px controls, 18px icons, 8px gaps, one accent, contrast floors, and *why* each exists; (2) add an audit script that checks what a screenshot cannot — token bindings rather than literal hex, icon stroke weight against icon size, focus rings present, no clip on frames without effects; (3) run it after every batch of generated screens and resolve the output to zero before review. The single most valuable rule to steal is the contrast one, because it is a design decision expressed as a conditional: *if the brand colour can't hit 4.5:1 on white, the button gets darker — a yellow brand still needs to be readable.* That is how a brand system survives contact with an agent.

### Duoasa — "Be Yourself": the design-skill genre, reviewed by one of its own authors
**Link:** https://github.com/Duoasa/Duoasa-skill · README EN: https://github.com/Duoasa/Duoasa-skill/blob/main/README.en.md · created **14 November 2026**, pushed 15 November · MIT · **148 stars, 23 forks**
**Type:** Idea (a polemic with a skill attached as the punchline)

**What it is:** A repository titled **做自己 / BE YOURSELF** that opens: *"I distilled the essence of generations of design masters. Different styles, different eras. Somehow, the distillation left just one parameter. It is now open source. You have already read it in the title."* The body is an argument, not documentation: the last fortnight has produced a design-style skill roughly every day, each packaging colours, brushwork, materials and lighting into a preset — and somewhere between *"this preset is useful"* and *"install this and acquire my taste"* an enormous amount has been quietly skipped. The actual `SKILL.md` inside is a conversational partner prompt: take the user's existing draft and preferences and help them develop *that* direction.

**What's good about it:** It states the thing this brief has been circling for a week without saying plainly: **"AI is increasingly good at producing ten attractive images at once. What matters more is knowing why you choose one, or why you want none of them."** And then it puts its money where the argument is by naming what it thinks the real work is — infrastructure that leaves room, with four worked examples: Kubai's **Glasswork** (liquid glass as adjustable parameters and copyable CSS), Emil Kowalski's **Vaul** (drawer interaction solved, visual style left to you), Paco Coursey's **cmdk** (composable, unstyled command menu), Rauno Freiberg's **inspx** (inspect layout dimensions in place). The distinction it draws is the useful one: *"These tools carry their authors' experience, and often their taste. But they leave room for the person using them to keep designing: take them apart, change them, and make something the author never imagined."* The test is not whether a tool embodies taste — all good tools do — but whether it hands the next decision back.

**Pros:**
- It is a credential-free attack on credential-by-install-count, written by someone who built the thing he's attacking. The self-aware structure (a "distilled masters" repo whose answer is "there is no preset") is more persuasive than any listicle making the same point.
- The four exemplars are the correct canon and they share a property that is easy to name and hard to design for: each solves one hard problem completely and refuses to style the rest. That is a build specification for our own internal tools.
- It gives Shareef language for a real institutional argument. When someone asks why the department isn't just installing the design-skill-of-the-week, the answer is now a paragraph rather than a shrug: a preset can keep generating, someone still has to decide.
- 148 stars in three days on an essay with no product — evidence that the audience for this argument is larger than the audience for another preset.

**Cons:**
- **It is a well-written essay with a thin artifact.** The `SKILL.md` is a good conversational prompt and nothing more; the repo's value is entirely in the README. Judge it as an editorial position, not a tool.
- The absolutism is convenient for its author. Presets genuinely do help — a house style encoded once saves a hundred decisions — and the essay's framing ("half an hour to package a style") flattens the difference between a locked brand system and a Midjourney SREF dump.
- Chinese-first with an English README; the referenced DSH plugins (Blender, ComfyUI) are a different ecosystem from anything Shareef runs, which weakens the "here is what to do instead" half.
- It offers no method. It tells you taste cannot be installed and that infrastructure is the answer, then hands you a prompt — the gap between diagnosis and prescription is the whole distance.

**Should we...**
- ✅ **Adopt it** — the argument, as the standing answer to the genre.
**Why:** This brief has spent a week cataloguing design-skill packs, and the honest conclusion of that catalogue is the one Duoasa states: a preset reproduces an *effect*, and the effect is the cheapest part of the work. For Shareef specifically, the line that matters is the one about choosing: the department will increasingly be handed ten competent options for a Sub-I cover or a Grand Rounds poster, and the professional skill is not generating them — it is being able to say *this one, because it does X that the others don't, and here is why the other nine fail*. That is a reviewable judgment, it can be written down, and it is exactly what a design director is paid for. Practically: keep the four exemplars as a build standard for anything we commission or make internally — solve one problem completely, leave the styling to us — and use the essay's test on every tool in this brief, including the ones I am telling him to adopt. If a tool wants to decide what the page looks like, it is a template. If it hands the decision back with better information, it is infrastructure.

### Studio Kiln × Reset — Ester, a mascot with no face
**Link:** https://www.creativeboom.com/news/studio-kiln-builds-a-shape-shifting-character-for-weight-loss-app-reset/ · published **16 November 2026** · Creative Boom, by Tom May · work by **Studio Kiln** (Falmouth/London) for Reset, a weight-loss app first launched 2019
**Type:** Idea (a brand-character system worth studying)

**What it is:** A rebrand built around a single character: **Ester**, a body assembled from soft, rounded 3D blocks — a head-like shape with one circular eye, a small floating dot, two chunky legs — which in their resting arrangement spell the letter **R** for Reset. The blocks are never still: they revolve, tumble, shift and reassemble in response to what the app is doing, falling apart and rebuilding. **Ester has no face.** No smiles, no frowns, no cartoon expressions — the character communicates entirely through movement, cascading and shuffling to suggest uncertainty, encouragement or a small victory.

**What's good about it:** The refusal. Every digital product in 2026 is buying trust with a friendly human-like character, and the friendly human-like character has become the same three-quarter-smiling 3D blob in every category — which means the shortcut no longer produces trust, it produces the suspicion that nobody designed this. Studio Kiln's answer is to remove the one thing that carries all the genericness — the face — and put the expressive load on *motion*, which is far harder to fake and far more specific to the product's state. The studio's stated frame is *"how people feel rather than how they look,"* and the choice follows: an abstract form leaves room for a reader to project their own feeling, where a fixed smile tells them what to feel about a topic — body weight — that people would rather work out privately. Second good decision: the letterform. The blocks spell R at rest, so the character is entailed by the wordmark rather than applied beside it, which is the same derivation discipline Landor used on the Crystal Ski "Y" two days ago, arrived at independently in a different category, by a smaller studio, without a snowflake.

**Pros:**
- Character design by subtraction: remove the face, keep the geometry, make the *state* the expression. A system that can show loading, listening, encouraging and celebrating without a single new illustration is a system, not a set of drawings.
- Motion as the brand asset, not decoration. The tumbling has a job — signalling what the app is doing — which is the difference between animation with intent and animation because it was available.
- The mark does double duty: a mascot a user can follow and a letterform that reinforces the wordmark, with no extra asset to manage.
- It is a health-adjacent product that chose dignity over cheerfulness, which is the harder and better call, and it is directly relevant to a clinical audience that is allergic to being infantalised.

**Cons:**
- **The article is studio-supplied.** Every quote is press material; there are no performance numbers, no evidence Ester survives a paywall banner, an app-store icon or a 24px favicon, and no mention of what it cost to animate.
- The technique is expensive to do properly. Motion-led identity needs an animation system, state mapping and someone who owns its timing; a still-image pipeline like ours degrades it to "a pile of blocks" — the exact fate of every mascot system implemented by people who only ever see the logo sheet.
- Faceless abstraction has a failure mode nobody in the piece mentions: users read it as corporate avoidance. A character that refuses to have a face can feel like a brand that refuses to have an opinion.
- One case study, one studio, one category. It is a principle source, not a validated method.

**Should we...**
- ✅ **Adopt it** — the principle, applied to the residency programme's social system.
**Why:** The residency programme has 28 filmed faculty interviews, and the social output built from them has to look like a *programme* across a hundred posts rather than a hundred unrelated stills — which is a character-system problem, not a template problem. What Ester teaches is the shape of the system: pick one abstract, ownable form derived from something the programme actually is, let it move according to what is happening (a match day, a call-out, a graduation, a research result), and give it no face — because the residents' faces are the asset, and a drawn mascot competes with them. Concretely: the blocks-and-letterform trick is available to us in a way the snowflake was not — the Montefiore wordmark, the department name, the uroflow curve, the cystoscope's circular field all have real geometry to derive from. The bound to respect is the institution's own brand governance: this is a *motion system and a gesture language* for the department's channels, not a new logo. And the honest caveat: adopting this means committing to animation as a standing capability, not a one-off. A mascot that only exists in a static PNG is worse than no mascot.

### artboards — design UI as typed code, with a linter that fails on clipped text
**Link:** https://github.com/unixzii/artboards · site: https://artboards.cy4n.dev · npm: `artboards-design` (latest **0.0.1**, published 15 November 2026, no GitHub releases) · MIT · **21 stars, 0 forks** · created 15 November, pushed 16 November
**Type:** Tool

**What it is:** A harness-agnostic design tool where an artboard **is a JSX/TSX component**: `<Frame width={390} height={844} fill="#ffffff">` containing `Column`, `Row`, `Text` with flexbox/grid layout (Taffy) and Skia/CanvasKit rendering, so a CLI-produced PNG and the browser viewer render identically. The CLI does `lint` (type-checks, renders every artboard, reports layout problems such as overflow or clipped text, **exits 1 on error**), `render` (PNG at a scale), `inspect` (layer tree with position, size, **and source line**), `dev` (browser viewer with comments saved to `design.comments.json`), `build` (static review site), and `comments` (lists open comments with the source line of the layer, `--resolve <id>`). `useVariant` declares the states a reviewer can switch between — loading, empty, error, a step of a flow — and `onClick` makes a prototype that runs in the viewer's Play mode. Fonts bundled: Inter, Noto Sans SC, Fraunces, JetBrains Mono. The project's own website is designed in it.

**What's good about it:** The review loop is closed in a way no other tool this fortnight manages. A comment is attached to a layer, the layer knows its source line, the agent fixes that line, and `--resolve` closes the comment — so "the type is clipped here" becomes a one-line edit rather than a paragraph of description and a guess. And `lint` treats *clipped text and overflow* as errors that fail a build: the two defects that rendered-screenshot review is worst at catching, precisely because a screenshot of a clipped frame looks like a design decision. That is the same insight as Underlay's audit and it arrived independently, from a tool rather than a workflow. The other genuinely good call is refusing to be a design tool: no package.json, no tsconfig, no node_modules — one file and a CLI, which means an agent can write a design without a build system and a human can review it without installing anything.

**Pros:**
- **`lint` exits 1 on overflow and clipped text.** After a fortnight of "constraints as prose," a design tool whose first-class operation is a failing check is the right shape, and it is the only one of the four design-as-code tools scanned that ships it.
- Comments carry the source line of the layer they're on, and `--resolve` closes them. This is the review-in-place pattern (yesterday's Doop) implemented where it costs nothing: in a text file.
- `useVariant` makes states a first-class declaration rather than a second file — the same discipline `craft` enforces in prose, enforced here by the file format.
- `inspect` returns positions, sizes and source lines, optionally as JSON — an agent-readable structure rather than a screenshot it has to narrate, which is the primitive gpucanvas was reaching for.
- Zero project setup, MIT, and the author uses it to build his own site, which is the only portfolio evidence that counts.

**Cons:**
- **0.0.1, one publish, zero GitHub releases, 21 stars, two days old, one author.** The version number is the honest summary: this is a first cut, and the DSL will move under anyone who builds on it.
- A bespoke DSL is a new language for every agent to learn. It ships `artboards docs` for exactly that reason — but a UI written in a private JSX dialect is not a UI anyone else can maintain, and there is no export to React or HTML in the command list.
- It is a *drawing* system, not an app: nothing here produces production components, so a design made in artboards still has to be rebuilt in the platform's real React codebase. The value is review and iteration, not delivery.
- Node 24 or later, and CanvasKit is a heavy asm/WASM download — awkward on a locked-down hospital image, and the CLI silently requires the agent to be able to run it.
- Bundled fonts are four faces, no token system, no spacing scale, no brand layer. The tool is agnostic to the things our platform is most disciplined about.

**Should we...**
- 👀 **Watch it** — and copy the comment-to-source-line loop now.
**Why:** The idea worth taking is the one that costs nothing to implement and that Underlay's audit proves is needed: *a review comment should land on a line of code, not in a paragraph.* Our current review of generated screens is a human looking at a rendered page and describing what is wrong, which is the least precise possible channel and the one that lets "the type is clipped" become "looks fine to me" across three rounds. artboards is the first tool that makes the precise version the default — comment on the layer, resolve at the source line, lint refuses to let overflow through. It is a *watch* rather than an adopt for one blunt reason: 0.0.1 with a single publish is not something to put in front of a hospital platform, and the DSL would be ours to maintain forever if we built on it. Pilot it on one throwaway screen — the Sub-I application form is the right test, because its failure modes are clipped labels and overflowing name fields — and judge only one thing: whether the comment-to-line loop catches something our screenshot review missed.

### punchcutter — a type foundry that runs inside the agent
**Link:** https://github.com/byrishi/punchcutter · docs: https://byrishi.github.io/punchcutter/ · created **13 November 2026**, pushed 15 November · MIT · **11 stars, 1 fork** · by Rishi (byrishi)
**Type:** Tool

**What it is:** A skill/MCP server/CLI that takes a sentence, a photograph of your handwriting, or a picture whose mood you like, and returns a **font family**: nine stages — brief → drawing (every letter built from pen strokes, or traced from your writing) → spacing from the white space around each shape → kerning measured pair-by-pair in 2D and merged into classes → OpenType features (kerning, tabular figures, slashed zero, case forms) → **UFO masters and a designspace** → compile variable TTF, static TTF, OTF and WOFF2 → quality assurance on coverage, metrics, names and features → a release package with a one-file offline **Studio** app (type tester, weight slider, feature switches, glyph inspector). Six routes in, including "open base": reshape an OFL variable font (Roboto Flex, Noto, Inter, Fraunces, Recursive) and ship under OFL with the original credited. Six families are published in the gallery, each with a live Studio.

**What's good about it:** It treats the type-design process as the product rather than hiding it. *"Each stage reports what it did. Between drafts the AI looks at the proof, finds weak letters and fixes them, at least twice, before anything ships."* A proof-and-correct loop, with the proof as the input to the next draft, is how type is actually made — and it is the opposite of one-shot generation. The outputs are the real artifacts a foundry ships, not a TTF and a promise: UFO sources and a designspace mean the family is *editable* by a human in Glyphs or FontForge, which is the difference between a typeface and a generated image of one. Shipping the Studio app as one offline HTML file is a small, sharp piece of product thinking — every font arrives with its own tester, so judging it never requires a pipeline.

**Pros:**
- **Sources, not just binaries.** UFO masters plus a designspace plus compiled variable/static/OTF/WOFF2 is the actual deliverable of a type foundry, and it means a designer can take over.
- Handwriting → font is the only route here with a defensible claim to *ownership*: it derives from a real, irreproducible input rather than from a model's average of the category.
- The open-base route is legally and practically the honest one — reshape an OFL variable font, ship under OFL, credit the original. Very few generators are this clean about provenance.
- The stage reporting and the ≥2 proof revisions are documented process, and the gallery of six live families is more output evidence than most tools at any star count provide.

**Cons:**
- **"Demo writing is simulated."** The headline demo — the photograph-to-font route — is advertised with synthetic writing, and the README says so in small type. That is honest and also disqualifying as proof: the one route with a real claim to authorship is the one with no unedited example.
- 11 stars, one author, three days old, no foundry credentials. Type design is a decade-long apprenticeship; a nine-stage pipeline that reports its own QA is not evidence that the spacing is good.
- What is missing is exactly what separates a usable face from a font file: optical sizes, hinting and stem-weight interpolation at small sizes, language coverage beyond the base glyph set, and real-world proofing on screens. None of that appears in the docs.
- **The institutional answer is no.** Montefiore has brand typography, and a department cannot introduce a typeface into a health system's materials on its own authority. Any real use would have to be lettering — a display cut for a campaign or the Chapter Player — not a text face.

**Should we...**
- 👀 **Watch it** — and test the handwriting route on lettering only.
**Why:** For a design director, type is the highest-leverage lever and the one AI has been worst at, so a tool that produces *sources* rather than a picture is the right direction of travel. But the honest read of this repo today is that it is a very well-organized pipeline with an unproven output, tested on nobody, aimed at a problem we are not allowed to solve: the platform's typeface is decided by the institution. What it is genuinely good for is the narrow, real gap — a **display cut for a single campaign**: the residency programme's annual identity, a Grand Rounds series, the Chapter Player's wordmark. Those need a few characters with a specific voice, no optical sizes, no language coverage, and a human can take the UFO and finish it. Try route 2 on real handwriting from the department — a faculty member's, with permission — and judge it as lettering. If the result is a face we would actually put on a poster, the tool has earned a second look; if it is a font-shaped object, we learned that in an afternoon for free.

### nakis — the slop checklist, as a script that exits non-zero
**Link:** https://github.com/bboga7/skills (the `nakis/` skill) · live page: https://beratboga.me/nakis.html · write-up: https://beratboga.me/#/blog/nakis · created **15 November 2026** · MIT · **2 stars** · by Berat Boğa
**Type:** Tool / Technique

**What it is:** An agent skill for building pages that *"look and read hand-made instead of machine-generated"* — a Turkish word meaning hand embroidery, "every stitch placed on purpose, never printed from a stock pattern." The agent reads the brief, writes the copy first (with every factual claim required to point back to the brief), builds a palette from one seed colour with tinted neutrals and checked contrast, adds exactly one moment of motion that stops under `prefers-reduced-motion`, then audits the page with a local Python script. The script (`audit.py`, Python 3.8+, no dependencies) scores 0–100 and lists what to fix, with `--min-score 85` returning **exit code 1** below the threshold. It also ships `palette.py`, which builds a readable palette from one hex and checks contrast pairs.

**What's good about it:** Two things, and the second is the one that matters. First, the checklist itself is the most complete enumeration of the tells I have seen in executable form: on the copy side — stock phrases, inflated verbs, empty adjectives, mirror sentences, decorative emoji, **everything in threes**, title case, colon headings, question openers, question headings, dash overload, flat sentence rhythm, repeated lines and numbers, placeholders left on the page. On the visual side — violet-blue default gradients, gradient text, glass panels, identical large corner radius, shadows everywhere, centered everything, too many colours, fonts that are not bundled. On motion — missing reduced-motion support, infinite loops, `transition: all`, animated layout properties, drawn lines that cannot draw. Second, the author ran a blind test and reported the uncomfortable part: pages built **without** the skill invented **6–16 claims the brief never gave**, depending on round; pages built with it produced **0** in English and 2 small flagged inferences in Turkish. Then he published the result that hurts his own product: *"The score barely separated them: pages built without the skill already scored 84–95."*

**Pros:**
- **The invented-facts measurement is the most operationally important number in today's brief.** For a hospital, a generated page that invents a statistic, a fellowship match result or a faculty credential is not a design problem, it is a compliance incident. 6–16 fabrications per page is the real cost of unconstrained generation, and it is measured rather than asserted.
- The check list is portable and free: every item is a rule you can paste into a review checklist today, regardless of whether you install anything.
- Honest self-reporting that a competitor would have buried — reporting that the score doesn't discriminate, that the judge was a model, that the Turkish result came from a single round, and that the before page "was written to fail on purpose."
- Zero dependencies, local only, no keys, no network calls in the scripts — deployable inside a network that will not approve a SaaS tool, and auditable in ten minutes.

**Cons:**
- **2 stars, one author, and the evaluation is a model judging pages it can partly recognise.** A 0–100 score from regex over HTML is a spelling check for taste: it catches vocabulary, not judgment, and the author says so.
- The "before" example was *written to fail on purpose*, which makes the audit's discriminative power untested precisely where it would be most impressive — on a competent page with two or three tells.
- English and Turkish only, and several copy checks (mirror sentences, translation smell, `-mektedir` stacking) are Turkish-specific. Our copy is English and clinical; the pattern lists would need a pass.
- It optimises for a particular aesthetic outcome — linen tone, serif headline, one red thread — which is itself a look, and a look that is now recognisable as the anti-slop look.

**Should we...**
- 👀 **Watch it** — and lift the copy checks into our own review gate.
**Why:** The tool is small; the finding is large. Our surfaces are generated pages on a hospital's behalf, and the highest-severity failure of a generated page in that context is not an ugly gradient — it is an invented number. nakis is the only artifact in this scan that measured that and published the count, and the count is the argument for putting a claim-tracing rule into every prompt we run: *every factual assertion must point at a line of the brief, and anything not in the brief is omitted.* That rule is free, it costs one sentence, and it is worth more than the 84–95-scoring script. Take the check list as a pre-flight document for marketing pages — the "everything in threes" and "question heading" items in particular are live in our current social copy — and hold the tool at watch until it has been run against a page we already think is good. If it scores our best page badly, it is measuring a style; if it scores it clean, it is measuring slop.

### SalkarsaUI — 573 tokens of someone else's decisions
**Link:** https://github.com/salahudinalyb/SalkarsaUI · created **13 November 2026**, pushed 17 November · MIT · **17 stars, 2 forks** · by Salahudin Alyb
**Type:** Tool (design system)

**What it is:** A mobile-first web design system delivered as an installable whole: a Figma library with three pages ("0. SalkarsaUI Docs" with a doc frame per component, "1. Foundations", "2. Components"), **51 components** each mapped to a shadcn/ui equivalent, **959 icons** in Regular and Filled, **573 design tokens** across light and dark in W3C DTCG format, 21 text styles, 12 effect styles, 4 grid styles, a Tailwind v4 bridge, and an agent skill. The `DESIGN.md` is genuinely rigorous: semantic tokens only, never primitives; pair foreground and background tokens explicitly; every interactive element carries Default, Hover, Focus, Pressed and Disabled; touch targets at least 44px; "if nothing fits, ask instead of making one up."

**What's good about it:** The rule set is the best part and it is unusually disciplined for a kit at this age: nine core rules that read like a design systems lead wrote them, states specified for every interactive component rather than left to the implementer, and tokens defined by *role* (`--bg-brand-default`) with primitives quarantined underneath. The "ask instead of inventing a value" instruction is the single rule most design systems omit and the one that prevents drift. Shipping the Figma library, the DTCG JSON, the CSS variables and the agent instructions from one source is the correct architecture.

**Pros:**
- 573 recursively-named semantic tokens with descriptions, in light and dark, in an open standard format — substantial, competent work, and free.
- Every interactive component documents five states, and the `DESIGN.md` states the 44px touch floor and the contrast pairing rules explicitly.
- The agent layer is thorough: `SKILL.md`, `AGENTS.md`, `CLAUDE.md`, a Cursor rule file, Copilot instructions and `llms.txt`.
- The Figma library and the code tokens are maintained together, which is the thing most systems get wrong.

**Cons:**
- **It is 573 decisions we did not make.** Our platform is Inter, one navy accent, tonal surfaces and flat SVG icons; adopting this kit means arguing with a system that already answered every question differently, and the loser would be our brand.
- 17 stars, one author, four days old, never used in production. Importing an untested system into a production platform is a bigger risk than importing a tool, because a design system is not removable once it's in the components.
- Mobile-first shadcn with Indonesian default copy (`Simpan`, `Hapus`); the density model is consumer-app, not clinical-application. Dense schedule grids and role-gated dashboards are out of scope by design.
- Generic by construction: 51 components and 959 icons is the vocabulary of every shadcn deployment, which is the look this brief exists to leave behind.

**Should we...**
- ❌ **Skip it** — the rules, not the tokens.
**Why:** This is good work aimed at the wrong customer, and it is worth naming as a category because the brief will keep surfacing it: a design system is not an asset you install, it is a set of decisions you made, and importing someone else's replaces the most valuable thing the platform owns — the accumulated reasons behind its look. A urology platform that adopts a consumer mobile kit will read as a shadcn template with a hospital's name on it, which is precisely the outcome this brief exists to prevent. What is genuinely worth taking is three sentences: *semantic tokens only, never primitives; pair foreground and background explicitly; if nothing fits, ask instead of inventing a value.* Those belong in the `design-system.md` that Underlay's method calls for, alongside our own reasons. The kit goes in the file as evidence that the discipline exists elsewhere — not as a dependency.

## Slop Radar
- **Screenshot-verified design.** Figma stores a fallback colour behind every bound variable, and *"screenshots resolve variables"* — so a file with 858 mis-clipped frames and 112 wrong stroke weights renders perfectly. Any review where the artifact is an image is a review of the image, not the design. Ask for the file and the audit output.
- **Taste sold as an install command.** A design-style skill now ships roughly daily, and the pitch has drifted from "this preset is useful" to "install this and acquire my taste." Installation counts are being reported as evidence of ability. The test is the one Duoasa names: can you say why you chose one of the ten, or why you want none of them?
- **The smiling 3D mascot as a trust shortcut.** Friendly human-like characters have become the default route to warmth in every product category, and the default is now so uniform that it reads as a stock asset. Ester's answer — remove the face, make state carry the expression — is the tell that the category has run out of road.
- **Nested cards.** A floating card sitting inside a card, rejected by Underlay's designers as *"a box inside a box."* It is the small-scale version of the same disease as every other item here: a container added because the layout was unclear, not because the content needed one.

## Overall Assessment
The centre of gravity moved today, and it moved out of the prompt. The best artifact in this scan is not a model or a tool but a **file structure** — one markdown rule set where each line is a decision with its reason and its date, one token layer the agent cannot write hex into, one audit that runs after every batch and catches what a screenshot structurally cannot see. That is the same conclusion a motion skill reached from storyboards and a design-skill reached from state lists, now with production numbers behind it: 490 screens, 59 buttons corrected retroactively, 112 icon vectors, 858 frames. And the counterweight arrived the same week, from someone who built the tool and then argued against its category: a preset reproduces an effect, not a judgment, and the judgment is the only part a director actually owns. Put together, the position for Shareef is not "use AI less" or "use AI more" — it is **write the reasons down where the machine reads them, then make the machine prove it followed them.** The single highest-leverage move this week costs one afternoon and no software: draft `design-system.md` for the Unified Platform in the reason-plus-date format, seeded with the rules we already hold informally — 44px controls with 18px icons and 8px gaps, one navy accent and the contrast floor that darkens it rather than lightening it, Inter at the sizes we actually use, no clip without effects — and add the one audit check that matters most, tokens instead of literal hex. That page will change more output than any tool in this brief, and unlike the tools, it cannot be uninstalled.
