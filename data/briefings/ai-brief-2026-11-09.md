# AI & Hermes Brief — November 09, 2026

**The one question:** which of today's tools, repos and platforms is best for *our* system to make a major improvement?

**Short answer: Hermes Agent v0.23.0 "The Hearth."** It is not a new repo — it is the release of the agent we already run, and it fixes three defects we have been working around for weeks: cron jobs that cannot be stopped, duplicate or lost messages when several surfaces attach to the same chat, and an update path that disables the memory provider (the notes name the `mnemosyne`/`torch` case explicitly — the exact slot yesterday's brief found pointing at a broken symlink). We are on **v0.21.5 (2026.9.24)**; this is two minor releases and roughly 10,000 commits ahead.

The rest of today is the phone-agent race: **Pinky**, **Poki** and **phoneuse** all launched within four days, all trying to let an agent drive a real phone. Only one of them runs where we do, and none is production-ready yet.

### 1. Hermes Agent v0.23.0 — the release that fixes what we have been patching around

**What it is:** The November 5 release of the agent platform this brief runs on. Since v0.22.0 it carries ~10,080 commits, ~1,950 merged PRs, ~850 closed issues and 666 contributors. The structural change: **one gateway owns every conversation** — CLI, TUI, Desktop, editors, messaging bots and cron all attach to it as clients instead of each running their own copy of the agent. Alongside it: the Desktop workspace served in a browser tab (`webapp`, off by default), plugins that update themselves with a security scan, price tags and spend limits on paid MCP tools, pluggable delegation backends, and a plugin catalog that grew from ~600 to over 1,050 entries.

**Source:** https://github.com/NousResearch/hermes-agent/releases/tag/v0.23.0 · installed version here: v0.21.5 (2026.9.24), Docker install · Provenance: GitHub releases API, checked against the running binary.

**What's good about it:** The release notes read like a list of our incident reports. **Cron:** `hermes cron cancel` stops a live run from the CLI, Desktop or API; deleting a job cancels it; every job chooses its own missed-run policy (`--catch-up on|off`); a manual run no longer consumes a one-shot; and prompts now carry the fire time. **Memory:** "Updates no longer break your setup" says `hermes update` keeps your memory provider when it has to turn a plugin off, turns it back on when it fits, and — specifically — plugins whose dependencies have no wheels for our OS (`mnemosyne`, `torch`) no longer get disabled on every update. That is the failure yesterday's brief found by hand. **Sessions:** the one-gateway model removes the duplicate-write/lost-message class that comes from cron, the Telegram bot and the WebUI each holding their own agent against the same chat. **Governance:** paid MCP tools now carry price tags and spend limits before an agent can call them.

**Pros:**
- **Cron finally behaves like a scheduler.** Cancel a run, per-job catch-up policy, fire time in the prompt — our 05:30 brief and the watchdog restarts stop being fire-and-hope.
- **The memory-provider bug class is fixed at the source**, not worked around: the release names the exact plugin/dependency case that left our external-memory slot inert.
- **One session, many surfaces.** Cron, Telegram, WebUI and Desktop share one queue and one history; no more messages written twice or dropped between them.
- **Plugin lifecycle is managed:** update-all with a caution scan, auto-update switch (off by default), catalog version floors (`requires_hermes`) so an old Hermes cannot install a plugin that needs a newer one.
- **Delegation is pluggable** — `delegation.backend`, an `advanced-delegation` plugin with model-map and per-profile routing, and prompt-cache-friendly staggering for batch subagents.
- **Webapp option:** the full Desktop workspace behind a sign-in on our own gateway — useful for reviewing a cron run without SSH.
- **Scale of hardening:** 850 issues closed and seven patch releases (0.22.1–0.22.7) rolled into this one.

**Cons:**
- **Breaking change to browser tooling.** The ten `browser_*` tools (`browser_navigate`, `browser_click`, …) and agent-browser are removed; `browser_exec` is the only browser path. We adopted the agent-browser CLI on November 6 — every skill or prompt that names the old tools needs auditing first.
- **`hermes mcp serve` is now `hermes mcp-serve`** and moved into a plugin; any MCP client config pointing at the old command breaks silently until edited.
- **Upgrade mechanics are hostile on our box.** `/app` is a container layer, not a volume: a `docker recreate` wipes the watchdog hooks and any background process, so this is a maintenance window with re-install steps, not a restart.
- **Blast radius.** Ten thousand commits on a production gateway that also carries the voice agent, the M4B player and the cron fleet; a bad upgrade takes all of them down at once.
- **Webapp is off by default and unauthenticated until configured** — if we ever expose it, it needs the same Traefik/auth discipline as everything else.
- **Version gap.** We are on 0.21.5, so the upgrade skips 0.22 entirely; the 0.22 notes are part of the migration surface, not just 0.23's.

**Should we...**
- ✅ **Adopt it** — integrate into our stack (strongly recommended)  ← **our call, staged**
- 👀 **Watch it** — keep an eye on it, not ready yet but promising
- ❌ **Skip it** — not relevant, redundant, low quality, or not useful for us

**Impact on our stack:** **High — Hermes cron + gateway + memory.** Concretely: stand up v0.23.0 in a scratch container first, run `hermes doctor` and one cron job against a copy of the workspace; grep every skill and prompt for `browser_navigate`/`browser_click`/`agent-browser` and rewrite to `browser_exec`; update MCP client configs to `hermes mcp-serve`; then upgrade production in a window, re-run both watchdog installers and relaunch the background processes, and re-check `hermes memory status`.

**Why:** This is the rare day when the highest-impact item is not a new tool but the platform underneath every other tool. The three failures this brief keeps documenting — a cron job that cannot be stopped mid-run, a session split across surfaces, a memory provider silently disabled by an update — are all addressed in the release notes by name, and we are running a build from September 24 that predates all of it. The risk is real and specific: the browser tool removal collides with an adopt we made two days ago, and a Docker upgrade on this box historically costs the watchdogs. That is why the verdict is adopt-but-staged rather than adopt-and-restart: a scratch-container validation costs an afternoon, while staying on 0.21.5 means hand-patching around defects that upstream has already fixed. If the scratch run is clean, the upgrade is the single largest reliability gain available to us this week.

### 2. Pinky — let an agent use a real phone, with the approval gate outside the model

**What it is:** A native desktop app for macOS, Windows and Linux that connects a real iPhone or Android phone over MCP. The agent sees the screen and can tap and type; Pinky's own gateway — not the model's instructions — holds risky taps (payments, sends, deletions, installs, settings changes) until a human clicks Allow. Banking, wallet and password-manager apps are off-limits by default, and every run is recorded as step-by-step screenshots plus a screen recording exportable as an HTML report.

**Source:** https://github.com/DIYgod/pinky · Apache-2.0 · 1,226★, 716 commits, 126 forks, created Nov 6, pushed Nov 9 · Provenance: GitHub search API (new agent repos, sorted by stars).

**What's good about it:** The architecture is the point. Approvals are enforced in Pinky's gateway rather than by telling the agent to be careful, so a prompt-injected screen cannot talk the agent into approving itself. The phone's PIN can be stored once and each unlock confirmed with Touch ID / Windows Hello, and the agent never sees the PIN. On Android 13+ the agent works on a hidden second screen, so the phone stays usable while it runs. It supports Tailscale for reaching a phone away from home, ships as a 16–22 MB native app with no Electron, and targets every desktop OS we might use. The author is DIYgod — 16.1k GitHub followers, 106 public repos, and 702 of the 716 commits here — so this is not a weekend star-farm.

**Pros:**
- **Cross-platform, including Windows** — the one place we could actually run it, since the VPS has no USB, no Bluetooth and no desktop session.
- **Approvals cannot be overridden by the agent**, which makes it usable for actions that touch a real account.
- **Off-limits list by default** for banking, wallets and password managers; agents cannot type into password or one-time-code fields.
- **Audit trail built in:** every step in plain words, screenshots, a marked screen recording, exportable HTML.
- **Works with any MCP client**, so Hermes can drive it without a bespoke integration.
- **Real engineering volume** — 716 commits in three days, 126 forks, only four open issues.

**Cons:**
- **Pre-alpha by its own README.** It has been driven end to end by Claude Code on an Android phone over USB and an iPhone on iOS 27; several features still wait for a person to try them.
- **Requires a spare phone, a cable and a desktop session** — it cannot live on the VPS, so social posting becomes dependent on one workstation being on.
- **Windows installer is unsigned** (SmartScreen warning), and the iPhone helper needs Xcode for iOS 17.4–26.
- **Driving Instagram/TikTok through the UI is still automation of a consumer app** — the account can be flagged; use a throwaway account and a dedicated device, not the program's main handle, until proven.
- **Screen contents go to the configured model service.** With a work phone that means PHI exposure; it must be a dedicated device with no clinical apps.
- **Approvals only cover the taps Pinky recognizes** — a novel button in a novel app may not match its rules.

**Should we...**
- ✅ **Adopt it** — integrate into our stack (strongly recommended)
- 👀 **Watch it** — keep an eye on it, not ready yet but promising  ← **our call**
- ❌ **Skip it** — not relevant, redundant, low quality, or not useful for us

**Impact on our stack:** **Medium–High — social media pipeline.** Concretely: install on the Windows desktop, pair a spare Android phone with a throwaway Instagram/X account, and pilot one repeatable task — "post the approved faculty clip with this caption" — with approvals on for every send. If it holds for two weeks, it replaces the manual phone step that currently blocks the social program.

**Why:** The social program's real bottleneck is not content generation, it is the last mile: Instagram and TikTok want a logged-in phone, and nothing on the VPS can provide one without putting credentials on a datacenter IP. Pinky is the first implementation that takes that constraint seriously — the phone stays real, the credentials stay on the phone, and the risky action waits for a human click that the model cannot fake. It is not an adopt today because it is four days old and self-described pre-alpha, and because its failure mode is acting on a real account. But the shape is right, the author is credible, and the pilot is cheap: one spare Android phone and a throwaway handle. That is a watch with a concrete test, not an indefinite maybe.

### 3. Poki — the same idea, locked to macOS

**What it is:** A macOS-hosted MCP server plus an agent that operates a real, unjailbroken iPhone. Installation is itself an agent skill: tell Claude Code or Codex on the Mac to install Poki and it runs `bin/install-iphone.mjs`, leaving only the Apple Account entry, Developer Mode and Trust taps to the human. The agent can also be reached over iMessage or Telegram channels.

**Source:** https://github.com/JosssphZhou/poki · AGPL-3.0-only · 642★, 648 commits, 129 forks, created Nov 5, pushed Nov 9 · Provenance: GitHub search API; also named in ManuAGI's GitHub Trending #308 — https://www.youtube.com/watch?v=bHOG9aX08tY.

**What's good about it:** It removes the jailbreak and the extra hardware from iPhone automation, and the installer skill automates everything an installer can automate. It uses a free Apple Account rather than a paid developer program, works with any MCP client, ships READMEs in six languages, and remembers past tasks so repeats get faster. Two authors account for nearly all of the 648 commits, so the volume is real.

**Pros:**
- **No jailbreak, no extra hardware, no paid developer account.**
- **Agent-driven install** that stops and asks only at the iOS prompts a human must touch.
- **MCP plus standalone agent**, with Telegram and iMessage channels for remote use.
- **Active**: pushed today, 129 forks, community Linux and Windows ports already exist.
- **Six-language documentation** signals a maintainer expecting non-Chinese users.

**Cons:**
- **macOS 14/15+ only.** Our desktops are Windows; there is no Mac in the stack, and the VPS cannot host it. The community Linux port is explicitly maintained outside the repo and untested by the author.
- **The iPhone needs a VPN/proxy app** (Karing, Shadowrocket) configured to route `10.7.0.1` back to the Mac — a fragile network trick that will break on iOS updates.
- **Free-account signing expires every seven days** and must be renewed; the agent reports setup as unverified until a human confirms.
- **Screen contents are sent to the configured model service** — the README says so plainly, which makes it a PHI hazard on any work device.
- **AGPL-3.0** with 30 open issues in four days; the licence is fine internally but rules out embedding.
- **Same account-risk profile as any UI automation** of Instagram or TikTok.

**Should we...**
- ✅ **Adopt it** — integrate into our stack (strongly recommended)
- 👀 **Watch it** — keep an eye on it, not ready yet but promising
- ❌ **Skip it** — not relevant, redundant, low quality, or not useful for us  ← **our call**

**Impact on our stack:** **Low** — it duplicates Pinky's function with a harder platform requirement. The only reason to track it is the community Linux port; if that matures and Pinky stalls, revisit.

**Why:** Poki is a credible implementation of the same idea as Pinky, and on a Mac-only desk it might even be the better one — the install skill is genuinely nice. But the decision for us is made by the platform line in its own README: macOS 14+, with a proxy app on the iPhone and a signing certificate that expires weekly. We run Windows and Linux, and the VPS is a headless container. Adopting a tool we cannot install where we work is not an adopt; it is a bookmark. Skip it, and spend the pilot on Pinky, which supports the machine we actually have.

### 4. phoneuse — iPhone control from Linux, as a technology demo

**What it is:** A Linux tool that sees and operates an unmodified iPhone: the phone mirrors its screen over AirPlay to the PC, and the PC sends taps and keystrokes back as a Bluetooth mouse and keyboard using AssistiveTouch. It exposes a CLI and MCP for agents, and optionally uses a small ESP32 bridge left next to the phone instead of the PC's own Bluetooth adapter.

**Source:** https://github.com/lxe/phoneuse · MIT · 496★, 214 commits, 50 forks, created Nov 7, pushed Nov 9 · Provenance: GitHub search API.

**What's good about it:** No jailbreak, no developer account, no cable, no app on the phone — it uses two features every iPhone already has. The HID path means the phone sees a real mouse and keyboard rather than synthesized events, which is more robust than touch injection. The optional ESP32 bridge is a thoughtful answer to Bluetooth range, and the project is honest about its limits in a warning at the top of the README.

**Pros:**
- **Zero footprint on the phone:** Screen Mirroring plus AssistiveTouch, nothing installed.
- **Real HID input**, not a private API that iOS can patch shut.
- **MIT, CLI and MCP** — an agent can drive it without a vendor SDK.
- **214 commits from one author** in three days; the engineering is substantial, not a mockup.
- **ESP32 bridge option** decouples the phone from the PC's Bluetooth stack.

**Cons:**
- **"Under heavy construction… tested on one setup: an iPhone 17 Pro, Arch Linux, Hyprland and an NVIDIA GPU."** Everything else will need fixes.
- **Needs a graphical Linux desktop** with GTK4, GStreamer and UxPlay — our VPS is headless with no Bluetooth adapter.
- **`phoneuse install` turns off bluetoothd's input plugin**, so the PC stops accepting ordinary Bluetooth keyboards and mice. That is a system-wide side effect on a workstation.
- **Opens AirPlay ports** (TCP 7000/7001/7100, UDP 6000/6001/7011) on the same network as the phone.
- **Hyprland/Wayland-specific** in practice, despite the generic Linux claim.
- **Single author, no tests in the README**, and a demo-grade warning that should be believed.

**Should we...**
- ✅ **Adopt it** — integrate into our stack (strongly recommended)
- 👀 **Watch it** — keep an eye on it, not ready yet but promising
- ❌ **Skip it** — not relevant, redundant, low quality, or not useful for us  ← **our call**

**Impact on our stack:** **Low** — no Linux desktop exists in our stack, and the VPS cannot host a GUI AirPlay receiver. Worth remembering only if we ever stand up a Linux workstation next to a spare iPhone.

**Why:** phoneuse solves the problem elegantly — AirPlay in, HID out, no jailbreak — but it solves it for a desktop that happens to be Arch Linux with Hyprland and an NVIDIA GPU, which is not a machine we have. The install also disables Bluetooth input system-wide, a side effect no production workstation should accept for a demo. This is a skip on environment, not on quality: if the author generalizes the compositor support and we ever put a Linux box beside a phone, it becomes relevant again. Until then, Pinky is the same capability on hardware we own.

### 5. Tinker AI Skill — turn our own sessions into a model

**What it is:** An Agent Skill (one `SKILL.md`, eleven Python/shell scripts, six reference notes) that takes agent session transcripts, anonymizes and slices them into an SFT dataset, trains a LoRA on Thinking Machines' Tinker, merges it, and exports a quantized GGUF that runs in llama.cpp. It is the distilled pipeline behind the Tess-4 and Tess-4.5 open models.

**Source:** https://github.com/drost-ai/tinker-ai-skill · MIT · 272★, 6 commits, created Nov 7 · Provenance: GitHub search API (new agent repos).

**What's good about it:** The details are the value, and they are the kind you only learn by shipping: anonymous identities randomized per session (a single fake world gets memorized and asserted over the real environment), compaction context rebuilt on continuation slices, tool definitions and the system prompt on every row, thinking kept in history, token budgets measured with the model's real tokenizer, checkpoints judged by behavior rather than loss. It shows the cost before launching, ships a synthetic transcript generator for a five-minute dry run, and stops before anything that spends money.

**Pros:**
- **A complete pipeline, not advice:** collect → clean → anonymize → slice → compact → split → train → merge → GGUF.
- **Proven on real releases** (Tess-4-27B, Tess-4.5-27B) with weights and a write-up.
- **Anonymization fails closed** — the script errors if anything leaks, which is the right default for our transcripts.
- **Dry-run path costs nothing** and needs no real data.
- **Export targets llama.cpp**, so the result can run without a vendor.
- **Behaviour-based checkpoint selection** avoids the classic "loss improved, model got worse" trap.

**Cons:**
- **Six commits, one author (mtisz), two days old.** The README is stronger than the commit history.
- **Built around Claude Code transcript format.** Our sessions are Hermes SQLite/Markdown; the collection and normalization steps need a converter we would write.
- **Tinker account and spend required** — "a few dollars to a few hundred," plus a GPU for serving; our VPS is CPU-only.
- **PHI risk is structural.** Even with per-session anonymization, training on our transcripts means clinical text leaves the box; the fail-closed check helps but does not make it compliant by itself.
- **Base-model and dataset licensing** must be checked per run; the skill does not decide that for us.

**Should we...**
- ✅ **Adopt it** — integrate into our stack (strongly recommended)
- 👀 **Watch it** — keep an eye on it, not ready yet but promising  ← **our call**
- ❌ **Skip it** — not relevant, redundant, low quality, or not useful for us

**Impact on our stack:** **Medium — agentic-os / copy desk.** Concretely: if it matures and we write a Hermes-transcript collector, it could produce a small local model that drafts briefs and edits in our voice — useful for the copy desk and for offline work, not for the production gateway.

**Why:** The idea is right for us: we have months of cron runs and copy-desk sessions that encode how we want work done, and a LoRA is a cheaper way to capture that than ever-lengthening prompts. But the pipeline is written for Claude Code transcripts, and converting Hermes sessions is real work; add Tinker spend, a GPU for serving, and clinical text leaving the box, and this cannot be an adopt today. Watch it, and if the author adds a generic transcript adapter — or if we decide to build one — it becomes a serious candidate for the copy desk's local model.

### 6. vibe-shield — a security gate aimed at the code agents actually write

**What it is:** A static security scanner for AI-written code, plus an Agent Skill that makes coding agents audit before saying "done." It ships 91 detection signatures across client exposure, auth and route protection, database/RLS, AI sinks, infrastructure, dependencies, secrets and agent/MCP integrity. `audit-skills` checks skill and MCP files for poisoning and unsafe instructions.

**Source:** https://github.com/avivgerz-hue/vibe-shield · MIT · 24★, 12 commits, created Nov 7, pushed Nov 9 · npm: `@vibefoundry/vibe-shield` · Provenance: GitHub search API (MCP repos, last 3 days).

**What's good about it:** The examples are our failure mode, not a generic checklist: a `NEXT_PUBLIC_SUPABASE_SERVICE_ROLE_KEY` in a client bundle, a `DELETE` route with no session check, a `CREATE TABLE` with no Row Level Security. It is offline and read-only by default, runs in milliseconds, can gate CI with `--fail-on critical`, and `--fix-prompt` writes a machine-readable remediation file for the agent that wrote the bug. The `audit-skills` mode is the part nobody else has: it treats SKILL.md and MCP config as attack surface.

**Pros:**
- **RLS and Supabase checks map directly to the Unified Platform**, which is React + self-hosted Supabase.
- **Read-only and offline by default** — safe to run against a production repo before trusting it.
- **`--patch-prompt` closes the loop** with the agent instead of filing a PDF nobody reads.
- **CI-ready** with severity thresholds and GitHub-format output.
- **Skill/MCP integrity auditing** is a genuinely new check for a stack that installs third-party skills.
- **Zero runtime dependencies**, Node ≥18.

**Cons:**
- **24 stars, 12 commits, one author, two days old.** The README is more mature than the project's history.
- **The README admits the published npm 2.0.0 predates the universal `--agents` initializer** — it tells you to use 2.1.0+ or the `v2` git ref, which means the default `npx` path may be stale.
- **Heuristic, not proof:** the README itself says signals do not prove guards or policies work.
- **Next.js/TypeScript-centric rules**; our Unified Platform is React + Supabase, so some checks will not apply and some gaps will remain.
- **A+ self-scan is marketing**, not an independent audit.

**Should we...**
- ✅ **Adopt it** — integrate into our stack (strongly recommended)
- 👀 **Watch it** — keep an eye on it, not ready yet but promising  ← **our call**
- ❌ **Skip it** — not relevant, redundant, low quality, or not useful for us

**Impact on our stack:** **Medium — Unified Platform security.** Concretely: run it read-only against the Unified Platform repo and the agentic-os skills directory, triage the RLS and service-key findings by hand, and only then consider a CI gate. Do not let it rewrite code yet.

**Why:** Our platform is exactly the shape this scanner targets — React front end, self-hosted Supabase, agents writing endpoints — and the two failure modes it leads with (service-role key in the client, table without RLS) are the ones that would hurt us most. But a two-day-old, one-author scanner with a known stale npm artifact is not something to wire into a deploy gate. The right move is a read-only trial on a copy of the repo, with its findings treated as leads for a human review, and a decision in a week once the commit count and issue tracker show whether it is a project or a launch.

### 7. Arete-27B — Nous Research's value-alignment fine-tune of Qwen3.8-27B

**What it is:** A 27B open-weight model from Nous Research, produced by supervised fine-tuning Qwen3.8-27B on ~52.8M tokens of teacher-generated data across seven value categories (free expression, state ideology, state vs. free market, education, data privacy and surveillance, democracy, environmental policy). Apache-2.0, with 38 community quantizations already published.

**Source:** https://huggingface.co/NousResearch/Arete-27B · blog: https://nousresearch.com/arete · eval dataset: https://huggingface.co/datasets/NousResearch/Propaganda_Eval · Provenance: Hugging Face trending API.

**What's good about it:** The evaluation is unusually transparent for a model card: 803 held-out prompts, a rubric, an LLM judge (Grok 4.7) piloted against human grades, and per-category results. Fact score rose from 2.32 to 2.98 out of 5, answers containing propaganda fell from 22% to 0.9%, and the general-capability check (Hermes Bench 65.60% vs 65.77%) shows no meaningful regression; Terminal-Bench-2.1 went 67% → 70%, which the authors explicitly decline to take credit for. It is Apache-2.0 and already quantized, so it is deployable without a vendor.

**Pros:**
- **From the lab that builds Hermes**, with the training recipe and eval published.
- **Apache-2.0** and 38 community quantizations already published — no licence friction for internal use.
- **Honest reporting:** decoding settings differ across rows and the card says so; the Terminal-Bench improvement is disclaimed.
- **No capability regression claimed** on the benchmarks they ran, within noise on general capability.
- **A real option for private inference** if we ever need clinical text to stay on-prem.

**Cons:**
- **27B in bf16 is ~54GB of weights**; our VPS is CPU-only, so there is no production inference path today.
- **The eval measures political framing, not clinical or agentic quality** — it says nothing about how good this model is at our work.
- **Single SFT run, self-reported numbers**; nobody independent has reproduced the result.
- **Quantized quality is unmeasured** — the 38 community quants are not evaluated on the card.
- **Values alignment is a policy choice**, not a capability; adopting it would need a deliberate decision about what we want the model to refuse.

**Should we...**
- ✅ **Adopt it** — integrate into our stack (strongly recommended)
- 👀 **Watch it** — keep an eye on it, not ready yet but promising  ← **our call**
- ❌ **Skip it** — not relevant, redundant, low quality, or not useful for us

**Impact on our stack:** **Low–Medium — future local inference.** Concretely: none this week. If a GPU desktop or an on-prem box ever joins the stack, Arete is a credible candidate for tasks that must not leave the building; on the current VPS it cannot serve at usable speed.

**Why:** This is the most interesting model release of the week for us personally — it is the house lab's work, it is Apache-2.0, and the methodology is documented well enough to trust the direction. But the brief's question is what makes *our system* better now, and a 27B model that cannot run on a CPU-only container does not. The value is strategic: it establishes that a small, well-chosen SFT run can change a model's behavior without wrecking its capability — which is the same bet the Tinker skill above would let us make on our own data. Watch it, and revisit if we add a GPU.

## Overall assessment

The day's real signal is that the phone-agent race arrived before any of the entrants is ready: three implementations in four days, all doing real work, none installable on a headless VPS without a phone and a desktop. The single largest gain available to us is not in that race at all — it is the platform release we have been ignoring while patching around its defects.

**If we do nothing else, do these, in this order:**

1. **Stage the Hermes v0.23.0 upgrade** — validate in a scratch container, rewrite `browser_*` references to `browser_exec`, update MCP configs to `hermes mcp-serve`, then upgrade production in a window and re-run the watchdog installers.
