### Supernova's Claude Design token test
**Link:** https://www.supernova.io/blog/claude-design-design-system · published **12 November 2026** · by Nezar Mansour · test run 11–12 November 2026
**Type:** Idea (a measured test, written up by a vendor)
**What it is:** Supernova set up **the same design system in Claude Design twice** — once from screenshots, once from code and tokens — then asked each version for the same three screens and **counted what came out wrong**. The system was **Mozilla Protocol** at commit `9107746` (6 November 2026), tokens package `@mozilla-protocol/tokens` 7.0.0, about 30 components. Setup A got seven full-page captures of mozilla.org at 1280px and nothing else. Setup B got 362 files: Protocol's Sass, its component templates and the token package, no screenshots. Three fixed prompts, no follow-ups, six screens total, Claude Pro on Opus 5.5 at Medium effort. The counts: **colours not in the system, 10 vs 0. Off-scale spacing values, 18 vs 7. Off-scale spacing declarations, 55 of 193 (28%) vs 19 of 142 (13%). Components or patterns the system doesn't have, 13 vs 2.**

**What's good about it:** It replaces the argument with a table, and the table is the argument. Everyone who has spent 2026 defending design systems against generated UI has been reduced to saying "it drifts" — which is true, unfalsifiable, and ignored by whoever is shipping. This is four rows of counts, run on a public open-source system, with the commit hash and the model version printed, and it splits the claim into the part that is now proven and the part that is still broken. The proven part is worth the read: **code and tokens eliminated every off-system colour and eleven of thirteen invented components**, which means a design system handed to a model as data functions as a real constraint rather than as a described intention. The still-broken part is more interesting: **setup B wrote 2, 10, 12, 18 and 20 px, none of which are on Protocol's scale.** Colours and components travelled from tokens; spacing did not. The reading is that a model can be told what a colour *is* — a named value it must copy — while spacing arrives as a judgement it still feels entitled to make by eye, and a token file alone doesn't stop it. That is the single most useful diagnostic sentence published about agent-built UI this month, and it points at the fix: spacing has to be enforced by a checker, not by a token list.

**Pros:**
- A reproducible method — one system, two setups, three fixed prompts — with the commit hash, token version, plan tier, model and effort level all stated. You can rerun it.
- The counterintuitive result is the finding: colours and components obey tokens; spacing does not. Worth more than any "AI respects your design system" claim.
- It publishes the method's own weaknesses (files may have been selectively read, values counted in code not pixels) rather than burying them, which is rare in vendor content.
- The result is granular enough to act on — "enforce spacing with a lint" is a different job from "improve your design system."

**Cons:**
- It is **Supernova's own marketing**, and the closing section is a pitch for Supernova's token-sync product. The test is honest; the framing is not disinterested.
- **n of 6.** Three screens from three prompts, one system, one model, one shot each — no repeats, so there is no variance estimate and no way to tell a real effect from one lucky run.
- **Product in motion, and the author says so:** Anthropic is folding Claude Design into Claude and **the standalone claude.ai/design closes 14 December 2026**. Every number here may be obsolete in five weeks, which sharply limits how much weight to put on the exact counts.
- Mozilla Protocol is a rare case — 30 components, tokens shipped as data, a public site to screenshot. A department whose system lives in a Figma file and a stylesheet would not get the same clean setup.

**Should we...**
- ✅ **Adopt it** — use it now; it raises our design ceiling
**Why:** Copy the test, not the conclusion. The Unified Platform is exactly the case this experiment was built for, and the department can run the identical protocol in one afternoon: take the platform's token file and component source, import them into whichever agent is producing screens, generate the same three screens that always go wrong — the schedule table, the call-out form, a resident profile — and count four things per screen: colours outside the token set, spacing values off the scale, components the platform doesn't have, and empty/error states missing. That converts a year of "the agent keeps making it look different" into a number Shareef can put in front of a decision. The specific finding to carry is the spacing one. The platform's spacing scale is real but it is advisory — nothing stops a generated page writing 18px — whereas the accent colour is enforced because there is only one. So the fix is ordered: **enforce spacing with a checker, and keep tokens as the source.** And the structural point deserves one line in the brief forever: this article's sharpest implication is that a snapshot import is not a system, because nothing tells the tool when a token changes — which is the same drift problem the 11th and 12th briefs hit from three other directions. Where to be careful is the vendor surface: the numbers are useful, the product pitch is not, and the whole measurement expires when standalone Claude Design closes on 14 December.

### Kern by sammii
**Link:** https://hackernoon.com/building-a-typography-playground-with-variable-fonts-and-fluid-css · live tool: https://sammii.dev/projects/kern/ · published **13 November 2026** · by sammii (front-end / design engineer)
**Type:** Technique (with a working tool attached)
**What it is:** A write-up of **Kern**, a variable-font explorer with three views: a specimen sheet, a playground that exposes every axis of a font as a slider, and **a type-scale generator that emits fluid `clamp()` values**. The architectural idea is that **the axes are data**: each font is a config listing its axes, each with a tag, label, minimum, maximum, default and step — Roboto Flex carries weight, width, optical size, grade and slant; Fraunces adds softness and a wonk axis; Playfair Display has weight only. The slider panel maps over that list and renders one control per axis, so a five-axis font gets five sliders and a one-axis font gets one, with no special cases anywhere in the UI. The same list writes `font-variation-settings`. The generator takes a base size, a ratio (default a perfect fourth), a step count and a viewport range, and writes one `clamp()` per step as a `:root` custom property.

**What's good about it:** The maths is published, and it is the right maths. Large size is the base times the ratio to the exponent; the **small size uses three quarters of the exponent**, which is a gentler ratio on narrow screens so headings still step up but less steeply. Then each step becomes a straight line between two known points: **slope is (large − small) ÷ (max viewport − min viewport), intercept is small − slope × min viewport**, slope × 100 gives the vw value, intercept ÷ 16 gives rem. That is the whole of fluid type, written so it can be checked rather than copied — and "it is easier to check that way" is the author's own stated reason, which is the sentence that makes this a design-engineering document instead of a tutorial. Second, the tool is honest about what it cannot feel: the optical-size axis gets a second rendering with opsz pinned to its minimum so you can see what the axis is doing, the preview eases glyphs with a transition while the numeric readout is driven by a spring, and the page's whole state lives in the URL so a type decision can be **handed to someone** rather than described. Third, and rarest: **it publishes its own edge case.** Below the base, the exponent is negative and three quarters of a negative is closer to zero, so the narrow-screen size comes out *larger* than the wide-screen size; `clamp()` resolves a min-above-max conflict by taking the minimum, so those small steps render at one fixed size at every width — and the label beside them shows a size you never see. "A cleaner version would skip the damping below the base." A designer who documents the failure of their own heuristic is worth reading on any subject.

**Pros:**
- Slope-and-intercept explained as the underlying geometry of a `clamp()` scale — checkable, portable, and correct — rather than as a copied formula.
- The axes-as-data pattern makes the control surface emerge from the font's own metadata; adding a font is adding a config, not editing the interface.
- URL-encoded state turns a type decision into a shareable artefact, which is the thing that stops three people picking three different scales.
- It names the failure modes: the negative-exponent artifact, and the fact that `vw` follows the browser window rather than the container, so the viewport preview lies and container query units would be the fix.

**Cons:**
- **A personal project with no stated repository, licence or release** in anything I could read; the article links to a project page, not to code. Nothing to adopt as software — only as method.
- HackerNoon is a low-signal outlet and this very page carries a **GPTZero banner declaring the story AI-assisted**, which is either an honest disclosure or a credibility flag, and the reader has no way to tell which.
- Three quarters is an arbitrary damping factor — it produces plausible results and is not derived from anything, so a scale built with it is a taste decision wearing a formula.
- It solves fluid size and nothing else: no measure, no leading, no optical hierarchy, no contrast. A perfect clamp() scale on a bad type choice is still a bad page.

**Should we...**
- ✅ **Adopt it** — use it now; it raises our design ceiling
**Why:** Adopt the arithmetic, this week, because the Unified Platform's type ramp is currently a set of fixed sizes and the two places that need fluid type are the two most visible surfaces in the department. The platform's marketing-adjacent pages and the Big Reef Chapter Player both have to work from a phone to a 27-inch display, and both currently jump at breakpoints because the sizes were chosen as integers rather than as a line between two viewports. Rewriting the ramp as slope and intercept — base size, ratio, min and max viewport, one `clamp()` per step on `:root` — is a two-hour job with a checkable output, and it deletes a category of bug permanently: no step can be off-scale because the scale is generated, not typed. Do it at the ratio the brief already blesses rather than inventing one. The second adoption is the axes-as-data idea, and it applies beyond type: **any control surface should be generated from the metadata of the thing it controls**, which is how the platform's spacing and radius scales should behave too, and is the same structural insight as the token-drift argument arriving from typography's side. Third, take the URL-state habit: every type decision should leave a link. And take the edge case as a standing rule — when a formula produces a size that is never rendered, the formula is wrong even if the page looks fine. Where this stops short is the thing that matters most: a generator cannot choose the face, and the brief has spent a week arguing that the face is now the whole game.

### Fontroom
**Link:** https://fontroom.tekcify.com · repo: https://github.com/Tekcify/fontroom · created **12 November 2026** · free, open source, no sign-up
**Type:** Tool
**What it is:** A browser tool that **puts a font on a real page before you commit to it**. Pick a heading and a body face from 180 curated Google Fonts (or type any family's name), and it renders a **full landing page and a phone app side by side** in four registers — SaaS product, café, magazine, developer docs. Or paste **any live URL** and Fontroom loads the real site, desktop and mobile, with your fonts applied; links inside it stay clickable. Drop in a `.woff2`, `.woff`, `.ttf` or `.otf` to test a paid or brand face — it is read in the browser and **never uploaded**, and it detects variable fonts and the real weights of static ones. Heading and body are set separately, swappable, or randomised from a hand-picked list; the weight menu shows only weights the font actually has; the preview flips light/dark, takes an accent colour and a body size; any text in the preview is editable; pairings save to the browser; the state lives in the URL. Then it writes the setup code — HTML/CSS, Tailwind v4, Next.js `next/font`, Flutter `google_fonts`, Expo — **with only the weights you used**, and `@font-face` / `next/font/local` for your own files.

**What's good about it:** It attacks the actual failure in type selection, which is not a lack of specimens but the fact that **a specimen is the wrong test**. Google Fonts shows one sentence on a blank page; every real decision involves buttons, prices, a table, numbers in a column and a phone screen, and the reason designers cycle through three faces and forget which one worked is that they were comparing them in a context that does not exist. Fontroom's four layouts plus arbitrary-URL loading is the correct instrument: it lets you see the face doing the job. The **"your own font files, never uploaded"** detail is what makes it usable for the department's licensed faces — that is a real constraint respected rather than a feature bullet, and it means the Sub-I packet's display face can be tested against the platform's actual pages without a designer's laptop or an Adobe licence in the loop. "Real weights only" is a small, sharp piece of discipline too: designing a headline in a weight the family does not ship is a mistake people make constantly and this simply removes it from the menu.

**Pros:**
- Tests type in the context the type will live in — real layouts, real viewport widths, and any live URL — which is the only test that predicts anything.
- Own font files are read client-side and never leave the device, so licensed and unreleased faces can be trialled safely.
- Code output is per-weights-used, across five stacks, so the decision hands off without a second translation step.
- Free, no sign-up, nothing stored server-side: zero procurement friction, which matters more than any feature in an institution.

**Cons:**
- **Nine stars, created yesterday, one author.** There is no maintenance signal, no roadmap and no guarantee the domain outlives the month; treat it as a good instrument that may vanish.
- Loading an arbitrary third-party page and swapping fonts will break layouts in ways the tool cannot foresee or fix — an overridden font stack can blow up a navigation it knows nothing about.
- It answers *which face*, not *is this set properly*: no contrast check, no measure, no leading, no optical-size guidance. It is a chooser, not a typographer.
- The 180-font curated set is Google Fonts, which is precisely the pool where the comfortable, AI-adjacent sans-serifs live. A tool that makes the free pool frictionless also makes it more likely to be the answer.

**Should we...**
- ✅ **Adopt it** — use it now; it raises our design ceiling
**Why:** Adopt it because the single most consequential typographic decision the department has to make this quarter — the licensed display face for external creative argued for on the 12th — cannot be made on a specimen page. Load the platform's actual schedule screen and the Chapter Player's actual library into Fontroom, drop in the two or three candidate display faces as files, and look at them setting a real headline over a real table at 1280px and at 390px. That is a one-hour test that replaces a week of opinion, and it produces something the brief has been asking for repeatedly: a decision with a reason, made in context, that survives a committee. The second use is internal and immediate: the Sub-I welcome packet's typography has never been tested against a phone, and Fontroom renders a phone app next to every layout by default. The third is the quiet one — because it accepts any live URL, Shareef can put a candidate face on a *competitor's* recruitment page or on a peer institution's site and see instantly whether the department's material would read as a peer to it or a lesser version of it. That comparison is the whole job, and it currently costs a designer half a day. What to be careful about is the ceiling: this tool will make a mediocre face look acceptable in a real layout because the layout is doing the work. Judge the headline at 96px, alone, first — then check it in place.

### Figma 3D transform
**Link:** https://www.figma.com/release-notes/ · help: https://help.figma.com/hc/en-us/articles/44568893374999 · released **12 November 2026** · companion Motion bundle 10 November 2026
**Type:** Tool
**What it is:** A new Figma effect that puts **real 3D transforms on the canvas**. Rotate any object along the x, y and z axes with on-canvas handles and live previews; build scenes from scratch or **let the Figma agent compose them**; adjust perspective and depth to assemble a full 3D scene; then pair it with Figma Motion to animate flips, turns and perspective shifts. When it is time to build, **copy the CSS out of Dev Mode** or send the design to a coding agent through the Figma MCP. It arrives alongside the 10 November Motion bundle, which added **physics-based springs** — mass, stiffness and damping set per platform (iOS and Android), with duration derived to match, and the spring savable into a design system for reuse at scale — plus animation style previews on canvas and Lottie export previews before export.

**What's good about it:** Two decisions are right and one of them is structural. The structural one is **CSS out, in the same release**: a 3D transform that only exists as a picture would be a rendering trick, whereas perspective expressed as a CSS transform is a property a developer can build, a designer can re-open, and an agent can read — the same "recoverable structure" argument the 11th and 12th briefs made about flattened type and generated flyers, arriving now in the third dimension. The second is that the agent is a *component* of the feature rather than the feature: "let the Figma agent compose them for you" is a convenience on top of a control surface that works without it, which is the correct order and the reverse of how most 2026 AI design announcements are built. The Motion pairing is the part with the most craft in it: **springs specified by mass, stiffness and damping rather than by a duration curve** is how motion is authored in code (Framer Motion, React Spring, SwiftUI), so the design file and the implementation can now describe the same physics — and saving a spring into the design system means an institution can have *one* motion feel instead of whichever easing each designer picked.

**Pros:**
- Perspective as a real transform, with CSS out and MCP handoff — the design stays editable at both ends, which is the only reason to do it in Figma rather than in Blender.
- Physics springs with named parameters, saveable to a design system: this is the mechanism by which a department gets a consistent motion language instead of eleven different easings.
- The 3D and the motion are separable — you can use the springs and ignore the depth, which is the sane adoption path for a hospital.
- Lottie preview before export removes the format gamble that has wasted more motion-design hours than any other step.

**Cons:**
- **Perspective is the fastest route to the exact slop this brief exists to escape.** Tilted cards, faux-depth chrome and floating planes with soft shadows are the 2025–26 signature of generated creative, and this release makes them one drag away for everyone.
- A CSS transform is not a 3D render: no real lighting, no occlusion, no materials. Anything that needs those will be faked, and faked depth is precisely what reads as cheap.
- It is another effect on a tool that already carries shaders, Motion, code layers and an agent. Figma ships no opinion about **when** 3D is appropriate, so the entire discipline burden moves to whoever is holding the file.
- The 10 November Motion features and this one are landing in the same week, which means neither has a body of real production use behind it yet.

**Should we...**
- 👀 **Watch it** — promising, not proven yet
**Why:** Watch the 3D and **take the springs**, and keep the two decisions separate because they have opposite risk profiles. A single motion language is the cheapest premium upgrade the department can buy: pick one spring — one set of mass, stiffness and damping — for the whole platform and all external creative, save it, and let every hover, sheet and transition use it. That is one afternoon, it costs nothing, and it does more for how the platform *feels* than any visual change made this year, because inconsistent easing is the thing viewers register as amateur without being able to name it. The 3D is the opposite: it should be used **once, on one artefact, with a reason**, and the reason has to be better than "it looks modern." The legitimate use is a plane that has a job — a single poster where the type sits on a tilted surface to create the hierarchy a flat layout cannot, a Sub-I cover where one element breaks the picture plane. The illegitimate use is everything else, and the test is simple: if you removed the tilt, would the composition still be doing any work? If yes, the tilt is decoration and it should go. The institutional argument for restraint is the same one the brief made about every other new capability this month — the tool is now free, so the differentiation is entirely in the judgement about when not to use it. And note what this release signals about direction: Figma's roadmap is converging on "the file contains the real properties," which is good news for anyone who has been arguing that a flattened JPEG is not an asset.

### AI-ready design system by Nayara Marques
**Link:** https://github.com/nayyymarques-eng/ai-ready-design-system · created **8 November 2026**, last pushed **12 November 2026** · React + TypeScript · 10 stars
**Type:** Tool (a framework, with an eval)
**What it is:** A framework that makes a design system **readable by AI coding tools** and then **checks every screen against it**. The tokens, components and rules in the repo are an example system — the one used in its own eval; a team brings its own. The parts are explicitly separated: **`tokens.css`** as the only place raw values live, named for purpose (`--critical`, never `--red`); **components** one per contract with typed props, where a variant that doesn't exist, a `className` or a `style` **does not compile**; **templates** for whole screens (list, detail, form) each with its own contract; a **`contracts/`** folder with one file per component and template stating what it is, its markup, variants, when to use it, **never**, where it lives, and the checks that enforce it; **`rules.md`** for how components sit together on a screen and the single route in for a new part; a **decision map**; a **harness** that decides when a screen is production-ready; and **triage** for the things the harness catches. The published result: **components only passed 85% of the checks, with 0 of 9 screens production-ready and 176 class names outside the system, none labelled. The framework passed 99%, with 8 of 9 screens production-ready, one class name outside the system, and 16 new parts labelled for triage.**

**What's good about it:** It is the **"never" line** that makes this worth reading. Most design-system documentation says what a component is for; almost none says what it must not be used for, and "never" is the clause an agent needs because an agent's failure mode is not ignorance of your components, it is **confident misuse** — the modal put inside a table row, the destructive button used for a secondary action. Writing the prohibition down next to the prohibition's reason is the cheapest possible guardrail and it is almost universally skipped. Second, the compile-time constraint is the correct enforcement mechanism: a variant that does not exist **fails the build**, which converts a style preference into a type error — the same principle as the 11th's lint-on-drift and the 12th's generated agent skill, now applied to the component API itself. Third, **the triage count is the honest part**: sixteen new parts labelled for triage is not a failure statistic, it is a workflow that assumes the system is incomplete and routes the gap somewhere instead of pretending it didn't happen. Fourth, an actual eval with a percentage and a screen count, run over nine screens, three runs per condition on first build — a designer publishing a measurable claim about their own framework is still rare enough to be notable.

**Pros:**
- Contract files with an explicit **"never"** section and named checks per component — the missing clause in nearly every design system, and the one agents need most.
- Enforcement at the type level: an off-system variant, `className` or inline `style` does not compile, so drift becomes a build failure rather than a code review conversation.
- A harness that grades whether a screen is production-ready, plus triage for whatever it flags — a complete loop, not just documentation.
- Named-for-purpose tokens (`--critical`), templates as starting points, and a decision map that tells a non-designer which screen type to begin from.

**Cons:**
- **Ten stars, one author, published as a portfolio case.** The eval is nine screens of the author's own example system, graded by the author's own harness — a demonstration, not a controlled study.
- "The framework" is mostly a folder structure and a set of conventions, not an installable dependency; adopting it means adopting a React + TypeScript toolchain with no `className` escape hatch, which is a real migration.
- Nothing in the repo addresses empty, error, loading or long-content states, which are where agent-built screens actually fail and where the 12th's A2UI item also stopped short.
- The 99% figure invites the wrong reading: a harness that it wrote and that grades its own example system will converge on 99%, and the number says more about the checks than about the screens.

**Should we...**
- 👀 **Watch it** — promising, not proven yet
**Why:** Watch the framework, write the "never" column this week. The Unified Platform has component documentation that says what things are and where they live; it has almost nothing that says **what a component must not be used for**, and that is exactly the gap an agent falls into when it composes a screen at speed. Ten lines of writing — table rows never contain modals, the accent is never used for status, destructive actions never sit next to the primary without a divider, the empty state is never omitted — would prevent more bad pages than any tool released this month, and it costs an hour. The second adoption is the triage idea in its smallest form: when an agent builds something the system doesn't have, **the output is a labelled gap**, not an invented component. That reframes every agent-built screen as a request for a new part rather than a violation, which is both kinder and more useful than a rejection. Watch rather than adopt because the enforcement story requires a full TypeScript component API that compiles rather than styles, the eval is self-graded, and the repo is nine days old with one author — the *pattern* is worth taking today, the repository is not.

### Design Week: supplements that look like sweets
**Link:** https://www.designweek.co.uk/why-are-supplement-brands-starting-to-look-like-sweets/ · published **13 November 2026** · Design Week, Opinion · by Daniel Hinde, founder and creative director of Greatergood Brands
**Type:** Idea
**What it is:** A category-convergence argument. Supplements are leaving the medicine cabinet: Boots launched a Korean-inspired wellness range of chia fibre jellies, collagen cool melts and popping vitamins; **Unilever agreed in April 2026 to buy Grüns, the gummy-bear wellness brand, for a reported ~$1.2bn** — a brand launched in August 2023 that reached a $300m annualised run rate within two years. Across the aisle, "tubs are giving way to pouches, jelly sticks and sweetshop-inspired chaos packaging." Earlier arrivals: Olly renamed melatonin "Sleep" and sold it as a gummy; Lemme took its cues from vintage sweet jars; **Zooki put collagen in squeezable sachets that became the brand asset — "Made to be enjoyed, not endured" — and went from £9m to £20m in a year.** The stated drivers are a treat mentality (you actually take it), a lower barrier than swallowing tablets, and shelf presence against rows of tubs.

**What's good about it:** The mechanism generalises far past wellness, and it is the most transferable thing published this week: **when every brand in a category converges on the same visual language, differentiation migrates from the graphics to the format.** Nothing in the article's examples is a better logo — Grüns is a lowercase wordmark and a bear outline; Zooki is a sachet. What changed is the *unit* the brand is delivered in. That is a genuinely useful lens for a department whose entire category — academic medicine recruitment — looks identical: white coat, blue, smiling resident, a building. No amount of art direction on the poster escapes that, because the poster is the wrong unit. The second good thing is the honest ending, which most trend pieces skip: **playful packaging wins the trial and loses the reorder.** "Supplements are a habit-building category, and the real value is in the monthly reorder, not a one-off novelty purchase" — so the brands that last pair the playful surface with "a pack that is instantly clear and consistent." That is the correct design-director structure: novelty is a first-purchase mechanism, consistency is a retention mechanism, and they are not the same job.

**Pros:**
- Names a real structural shift — format as the differentiator when the visual language is saturated — with dated, priced examples rather than mood.
- The trial-versus-reorder split is a clean, reusable model for any communications work that has to earn a second look: novelty gets attention, clarity keeps it.
- Two concrete sales figures and a $1.2bn acquisition give the argument an economic spine most design commentary lacks.
- The examples are all *cheap* moves — a sachet, a rename, a jar — which makes the strategy legible to an organisation without a packaging budget.

**Cons:**
- **It is written by a packaging agency founder and ends by naming his agency.** The observation is sound; the advice is inventory.
- "Chaos packaging" is itself the 2026 cliché — a trend piece about category convergence that recommends the converged look.
- The prescription ("pair playful energy with a pack that is clear and consistent") is unfalsifiable; every failing brand would also claim to have done it.
- It is entirely about physical FMCG shelf presence. There is no evidence, and no argument, that format-flipping transfers to a service, a screen, or an institution.

**Should we...**
- 👀 **Watch it** — promising, not proven yet
**Why:** Watch the trend, take the lens. The department's recruitment problem is structurally identical to the supplement aisle: every urology program in the country presents the same three images and the same blue serif, so a better version of the same artefact cannot differentiate — the format has to change. That reframes the whole creative brief. Instead of another poster, the unit could be **a single printed object that arrives before the interview** (the 12th's textured-print argument, and the cheapest premium move available), or **a 40-second cut from the 28 faculty interviews that nobody has edited**, or a **one-page call schedule that a Sub-I can read in nine seconds**. Those are format moves, and each of them is defensible in a way "make the flyer look nicer" is not. The second half of the article is the discipline to attach: **novelty earns the first look, consistency earns the second**, so whatever format is chosen has to be repeatable every year with the same rules — a one-off gimmick is a worse investment than a boring template. What to leave is the aesthetics and the author's self-interest: sweetshop chaos is a packaging language for a category that has no stakes, and this one does.

## Overall Assessment
The centre of today is **measurement**, and it is the healthiest shift this brief has recorded. Supernova set up one system two ways and counted what the model got wrong — ten colours outside the system became zero when tokens replaced screenshots, while spacing barely moved, which is a diagnosis you can act on.
