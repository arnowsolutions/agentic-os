# AI & Hermes Brief — November 07, 2026

**The one question:** which of today's tools, repos and platforms is best for *our* system to make a major improvement?

**Short answer: Agent Autoloop.** Not because it is the biggest repo in the feed — it is four days old — but because it names and solves the exact hole in our cron architecture: a job that hits a decision it should not make alone can **stop, hold its place in SQLite, and resume the same conversation three days later without a process running or a token spent.** Every approval-gated thing we do — sending a department email, filing to the vault, deploying, spending money — currently ends the run and re-starts from scratch, because our cron has no way to wait. Autoloop's kernel is that wait, and it ships with a documented Hermes command: `hermes chat -Q -q {prompt}`.

It is a **watch**, not an adopt, for four concrete reasons: it needs Node 24 and we run 22.22.3; its notification channels are Feishu, DingTalk, WeCom, Slack, Discord and desktop — **Telegram is not on the list**; its CLI output and default card strings are still Chinese; and 3,839 stars in four days with 693 forks is a promotion signature, even though 24 contributors and a published crash-simulation suite say it is not vapour.

## 1. Agent Autoloop

**What it is:** A small, deterministic kernel that turns command-line agents into a background loop. Events (a cron time, a GitHub issue, an HTTP call) are dispatched by rules to any agent CLI that accepts a prompt; the agent works one round and exits; anything sensitive — deleting data, restarting a service, spending money, messaging people — is pushed to you as a card, and the run **pauses at zero cost** until you answer, then resumes the same conversation. Around the kernel everything is a plugin: event sources, agents, notification channels, and a CI/CD delivery pipeline.

**Source:** https://github.com/KKKKhazix/agent-autoloop · configuration manual: https://github.com/KKKKhazix/agent-autoloop/blob/main/skills/agent-autoloop/SKILL.md · Provenance: GitHub search API — self-hosted agent repos created since Oct 25, sorted by stars (3,839★, created Nov 3).

**What's good about it:** The **zero-cost wait** is the feature. In our stack, a job that needs a decision sends a Telegram message and *ends*; the decision arrives in a different session with none of the context, and the next run re-derives everything. Autoloop keeps the waiting state in SQLite, kills the agent process, and resumes the original conversation when you answer — the README claims answering three days later costs nothing in the meantime, and the mechanism (state on disk, process exited, session id retained) is visible in the repo rather than asserted in marketing. The second thing worth having is the **code/data split**: external text like an issue title or a webhook body is written to a local data file and never into the prompt, `rules.json` alone decides which agent runs in which folder with what access, and events that carry `cwd`, `agent` or `access` fields are rejected outright. That is a prompt-injection boundary, written down as a rule. Third, the engineering is unusually honest for a four-day-old repo: the kernel is ~1,850 lines with **zero runtime dependencies**, reads no clock and uses no randomness, all state is an append-only fact log committed in the same SQLite transaction as its indexes, and the repo ships simulations you can run yourself — 200,000 steps of dropped packets and duplicate requests from a seed, plus 1,000 process kills with no acknowledged record lost. Published numbers: 88.78 ms cold start, 59.94 MB idle RSS, 2,394 durable writes/s on an M5 Pro.

**Pros:**
- **It is the missing primitive in Hermes cron.** Scheduled job → needs a human → pause (process gone, tokens zero) → answer arrives hours or days later → the same conversation continues. We do not have this today at any price.
- **Hermes is a first-class agent in its table** — `hermes chat -Q -q {prompt}` — alongside Claude Code, Codex, ACP, DeepSeek Harness and a generic `command` plugin. No SDK, no forking an agent.
- **A prompt-injection boundary that is enforced, not suggested:** external text never enters the prompt, and events cannot set their own `cwd`, `agent` or `access`.
- **Event sourcing done properly** — append-only log, rebuild-from-log instead of migration scripts, `agent-autoloop why 1` traces any round end to end. For a system that quietly fails overnight, that trace is worth more than a dashboard.
- **Hop circuit breaker:** agent-spawned events inherit a hop count that an agent cannot reset; past 8 hops the kernel stops and tells you. That is the runaway-loop guard our own agent chains lack.
- **Zero runtime dependencies and a small footprint** — 60 MB idle, no database server, no cloud, no inbound ports. It would sit next to the gateway, not on top of it.
- **Rules are JSON, changes take effect in seconds,** `check` validates a draft without touching the running hub, and a broken rules file leaves the previous valid set running while it cards you about the mistake.

**Cons:**
- **Node 24 or newer; we run 22.22.3.** Same class of problem as agent-browser last week — it will probably run and it will be an untested configuration. Either upgrade Node in the image or pin a release and test.
- **No Telegram channel.** Built-in channels are desktop notifications (default), Feishu, DingTalk, WeCom, Slack and Discord. Our entire delivery surface is Telegram, so adoption means writing a channel plugin first — small, but it is code we own.
- **Only Feishu has been tested for real.** The README says the four webhook templates were "only checked against local mock servers". A channel that has never delivered to a real Slack or Discord is a channel we would be the first to break.
- **CLI output and default card strings are still Chinese.** The English README is complete, the protocol doc is not, and every operator-facing string needs translating before Shareef sees a card.
- **Four days old, and the star curve is a promotion signature.** 3,839 stars and 693 forks in four days is not organic; 24 contributors and the crash sims are the real evidence, and they are good, but the repo has no track record under someone else's workload.
- **It needs an agent already signed in on the same machine.** For Claude Code or Codex that is the account-on-a-server risk we keep refusing; for Hermes it is fine, because Hermes already holds its own provider keys.
- **Another scheduler next to cron.** We would be running two scheduling systems until the old one is retired, and "which one owns 9 a.m.?" is exactly the ambiguity that produces duplicate emails.

**Should we…**
- ✅ **Adopt it**
- 👀 **Watch it** — one afternoon pilot on the desktop with Hermes CLI as the agent, no credentials, Telegram plugin drafted ← *this one*
- ❌ **Skip it**

**Impact on our stack:** **High — Hermes cron.** Concretely: the daily brief could ask "file these three items as adopt, or hold?" and then actually wait for the answer instead of asking and ending; a deploy job could stop before `docker compose up` and resume when Shareef says go; the reimbursement workflow could pause on an ambiguous receipt. The change is not a new feature on top of cron — it is cron gaining a state machine.

**Why:** We have built an entire operating rhythm on jobs that run unattended and report afterwards, and the weak point is exactly the moment a job should not decide alone. Today that moment ends the run: the question goes out as a message, the process dies with all its context, and the answer comes back into a different session that has to reconstruct what happened. Autoloop's kernel is a clean, small, dependency-free answer to that, with the prompt-injection boundary and the hop breaker already thought through, and it explicitly supports Hermes as the worker. The reason it is a watch rather than an adopt is not doubt about the idea — it is that the delivery half does not exist for us yet (no Telegram channel, untested webhook paths, Chinese operator strings) and the runtime is one Node major ahead of ours. The pilot is cheap and answers the only question that matters: does a paused run actually resume with its context intact when the worker is `hermes chat`? If yes, this becomes the backbone of every approval-gated job we run.

## 2. Rerun

**What it is:** A self-hostable app of "AI coworkers". You tell it what you need done, a guide called the Foreman plans a team, and each coworker gets a job, its own memory, its own skills, its own files and its own schedules. They work in Gmail, Google Calendar, Drive, Sheets, Slack, Notion, HubSpot, Airtable, Stripe, GitHub, Linear, Figma and 200+ more (plus any MCP server and 2,000+ apps through Composio), and they ask before they send, pay or delete anything.

**Source:** https://github.com/rerun-build/rerun · self-host docs: https://docs.rerun.build/self-host · Provenance: spotted on **Github Awesome** — https://www.youtube.com/watch?v=nXxM1lrr6o4 (episode #58, 01:24).

**What's good about it:** It is the same product Rerun sells as a cloud service, under AGPL-3.0, with **no plan, no credits, no limit on coworkers or seats** — which is a better open-source posture than most "self-hostable" launches. The self-host story is documented honestly: one `docker compose` command, two containers (the Next.js app and the engine for the first workspace), Supabase for accounts and storage, an OpenRouter key only if you want their default models, and the **engine data-dir is a plain folder of files and SQLite databases** — souls, skills, memories, private database, credentials — with credentials explicitly never sent to Supabase. Each coworker runs with a Chromium browser and an Xvfb/x11vnc desktop that a human can watch. v0.11.2 shipped yesterday, so the release cadence is real, and the approval-before-acting rule is the right default for a department that cannot have an agent email a chair.

**Pros:**
- **Approval gates in the product, not bolted on** — "they ask before they send, pay or delete anything" is the behaviour we have been hand-building in prompts.
- **Per-coworker memory, skills, files and schedules**, which is a cleaner separation than one agent with one giant memory file.
- **A real integration catalogue** rather than a promise: Gmail, Calendar, Drive, Sheets, Slack, Notion, HubSpot, Airtable, Stripe, Shopify, GitHub, Linear, Jira, Figma, Webflow, X, YouTube, Instagram, plus any MCP server.
- **Self-hostable under AGPL with no seat limits** and credentials kept in the engine's data-dir instead of the shared database.
- **Two containers and a folder of SQLite** is an architecture we understand and can back up, unlike a black-box SaaS.
- **Templates that map to work we actually have** — an executive assistant that sorts an inbox and briefs you each morning, a data analyst that answers questions with charts.

**Cons:**
- **No Outlook and no Microsoft Graph.** Its email integrations are Gmail. Our department mail is Outlook/Montefiore, so the single most valuable coworker template is inert for us until something bridges it — and we know from the July incident that bridging it from this VPS is not a small thing.
- **Nine days old, two contributors, six open issues.** The release numbers are real but there is no evidence of it running under anyone else's workload.
- **The install is heavy for our box.** Building the images needs ~6 GB available to Docker, and the engine runs Chromium plus Xvfb plus x11vnc. `/workspace` is at **92% used with 18 GB free**; this is the wrong week to add two containers and a Supabase schema.
- **A second agent platform next to Hermes.** Coworkers with their own memory and schedules, sitting beside our cron jobs and our memory file, is two sources of truth about what the department's agents are doing.
- **AGPL-3.0** — fine internally, a constraint the day anything is exposed as a service.
- **It assumes a human opens a board.** Our operating model is Telegram; Rerun's is a web app.

**Should we…**
- ✅ **Adopt it**
- 👀 **Watch it** — revisit when it has Outlook/Graph or when our disk and mail path are ready ← *this one*
- ❌ **Skip it**

**Impact on our stack:** **Medium — agentic-os and email.** If it worked with Outlook, the executive-assistant template would replace a set of hand-written cron jobs with a scheduled coworker that has memory and asks before sending. Without Graph, its value to us is a reference architecture: per-coworker memory, approval gates, and an engine data-dir we can inspect.

**Why:** The interesting thing about Rerun is not that it runs agents on a schedule — we do that. It is that the *shape* of the work it encodes (a named coworker with a job description, its own memory, and a rule to ask before acting) is the shape our ops work keeps taking, and it is the first time we have seen that shape shipped as a product rather than a prompt. But two facts decide the verdict: its email path is Gmail-only, which makes the best template useless to a Montefiore department, and running it means a second platform and roughly 6 GB on a disk that is 92% full. Watch it — and take the design, not the deployment. If Rerun adds Microsoft Graph, this becomes a serious conversation, because the alternative is us hand-building approval gates one cron job at a time.

## 3. CloneGuard

**What it is:** A dependency-free Go command-line tool that scans a repository **before you run it** — reading files only, never executing, installing or importing anything from the project — and flags the tricks used in credential-stealing "take-home assignment" attacks: install hooks, auto-run editor tasks, obfuscated code, hidden network calls, and reads of SSH keys, cloud credentials, browser passwords and wallets.

**Source:** https://github.com/tharun208/cloneguard · Show HN: https://news.ycombinator.com/item?id=50397435 · Provenance: Hacker News (Show HN, Nov 6, 29 points).

**What's good about it:** It is aimed at a specific, real attack, and it is aimed at the moment that matters. The described pattern — a fake recruiter sends a "demo app", you clone it and run `npm install`, and an install hook quietly uploads your keys — is the same pattern as *this brief's own workflow*: we resolve a repo from a trending video and, within minutes, someone runs `npm install` or `curl … | sh` on the VPS. The tool is honest about its own scope: read-only, no dependencies, no claims of catching everything, `--include-deps` is off by default because it is slow, and `--json` output means a cron job could gate on it. It builds with Go 1.24 in one command and the binary is small enough to live in `~/.local/bin` next to Lightpanda.

**Pros:**
- **Scans without executing** — the only safe way to inspect an untrusted repo, and the opposite of "just try `npm install` and see".
- **Targets the actual delivery mechanism of these attacks** — install hooks and editor auto-tasks, not just suspicious source strings.
- **`--json` output** makes it scriptable: a pre-install gate in a cron job or a hook before `git clone` gets installed.
- **One static Go binary, no dependencies**, buildable from source in a container with no root.
- **A clear honest scope** — skipped dependency folders, size caps, plain-text mode — rather than a scanner that promises everything.

**Cons:**
- **16 stars, one author, four days old, v0.1.0.** There is no evidence of detection quality: no test corpus, no false-positive rate, no list of what it actually looks for.
- **Heuristics lose to a determined attacker.** A scanner that greps for patterns is a speed bump against a targeted attack, not a boundary — and it must never be treated as one.
- **Go 1.24 required to build** and no prebuilt binaries published in the release, so installing means a toolchain.
- **Narrow by design** — it protects against malicious repositories, not against a legitimate repo that later ships a compromised dependency, which is the more common supply-chain failure.
- **It does not replace the real control** — running untrusted code in a throwaway container with no credentials mounted.

**Should we…**
- ✅ **Adopt it**
- 👀 **Watch it** — build it, run it once over the next ten repos this brief surfaces, and see what it flags ← *this one*
- ❌ **Skip it**

**Impact on our stack:** **Low–Medium — Hermes cron and the VPS.** It would add a read-only gate between "this repo looks interesting" and "it is running in our container": one `cloneguard scan --json` call whose exit code a job can act on. It does not change any product surface, but it closes a habit that has a bad ending written on it.

**Why:** This brief's job is to find repos and then someone tries them, and the honest risk in that loop is that a trending repository is not the same thing as a safe one. CloneGuard is a small, correctly-scoped answer to the first look — read-only, no dependencies, JSON output — and it is cheap enough to try without changing anything. It is a watch because four days and sixteen stars is not a security tool yet: we have no idea what it misses, and treating a heuristic scanner as a boundary is worse than having none. Build it, run it against the repositories this brief named today, and compare what it flags to what we can see by hand. If it earns its keep, it becomes a one-line gate before every `npm install` that did not come from a vendor we already trust.

## 4. CLIProxyAPI

**What it is:** An open-source proxy server that sits between local coding agents and Claude, Codex, Gemini and other model APIs. It wraps consumer AI tools — Antigravity, ChatGPT Codex, Claude Code, Grok Build, Muse Code, Devin — as OpenAI/Gemini/Claude/Codex-compatible endpoints, automatically renews the session about every ten minutes so you are not logged out mid-task, and load-balances multiple accounts across several machines.

**Source:** https://github.com/router-for-me/CLIProxyAPI · docs: https://help.router-for.me/introduction/what-is-cliproxyapi · Provenance: spotted on **The Next New Thing** — https://www.youtube.com/shorts/4M-ZFI_EbEU

**What's good about it:** It is genuinely popular and genuinely maintained — 57,846 stars, MIT, created July 2025, pushed today — and the engineering problem it solves is real: coding agents lose their session in the middle of a long task, and re-authenticating by hand is tedious. The session-refresh loop and the account pooling are competently done, and it accepts OpenAI-, Gemini- and Claude-compatible clients, so any tool we already run could point at it without changes. If the goal were "keep one developer's laptop agent logged in", this would be the obvious answer.

**Pros:**
- **Automatic session renewal** about every ten minutes, before expiry, so long agent runs do not die at the login wall.
- **Protocol-compatible with everything** — OpenAI, Gemini, Claude and Codex clients work unchanged.
- **Account pooling** lets one setup serve several machines, which is the feature people actually want it for.
- **MIT, 57k stars, daily activity** — this is not an abandoned experiment.
- **Self-hosted and local** — no third-party service in the middle.

**Cons:**
- **Its core function is turning consumer subscriptions into API endpoints.** That is a terms-of-service problem, not a technical one: Anthropic's and OpenAI's terms are written around interactive personal use, and a proxy that shares one account across machines is exactly the pattern they police.
- **It requires live OAuth sessions for Claude and ChatGPT to live on the machine running it.** Put that on a datacenter IP and you have recreated the shape of the July problem — a personal account signing in from a server — which cost us a conversation with Montefiore IT we do not want to repeat.
- **Shared accounts and load balancing multiply the blast radius**: one flagged account takes every machine behind the proxy down at once.
- **A single point of failure in the middle of every agent call**, with credentials for multiple providers inside it.
- **The upstream providers change auth constantly**; a proxy that depends on reverse-engineered flows is a maintenance treadmill, and the repo's own history has a licensing caveat on at least one provider.

**Should we…**
- ✅ **Adopt it**
- 👀 **Watch it**
- ❌ **Skip it** — wrong side of the account-risk line ← *this one*

**Impact on our stack:** **Low.** Nothing we run needs it: Hermes holds its own provider keys and does not depend on a consumer subscription session, and our agents run server-side where a personal-account login is the last thing we want.

**Why:** The honest use case for CLIProxyAPI is a developer who wants their laptop agents to stop logging out, and even that is a ToS argument rather than a technical one. For us it is worse than useless: putting Claude or ChatGPT OAuth sessions on this VPS is precisely the pattern that got a Hermes script flagged in July, and "it worked" would only mean we had not been caught yet. The session-refresh idea is worth remembering when we next review how Hermes handles provider token expiry — but as a thing to build in, not a service to adopt.

## 5. Herdr

**What it is:** A desktop application for terminals and coding agents. Work lives in **spaces** (one machine, usually one repo), split into tabs and panes; an agents sidebar shows every agent as Working, Blocked, Done or Idle; a background core keeps terminals running after you close the window; and spaces can live on another machine over SSH. Layouts and panels are programmable JavaScript "mods".

**Source:** https://github.com/herdrdev/herdr-app · https://herdr.dev · Provenance: spotted on **Github Awesome** — https://www.youtube.com/watch?v=nXxM1lrr6o4 (episode #58, 00:11).

**What's good about it:** The **core/window split** is the right architecture and it is the part most terminal apps get wrong: the window arranges terminals, the core runs them, so closing the window does not kill an agent mid-task, and after a reboot kept panes come back as fresh shells in their last folders. The agent status list — Working / Blocked / Done / Idle, with "Done: finished while you were looking elsewhere" — is a better small piece of design than most agent dashboards manage, because it answers the only question you have when you come back to the machine. Remote spaces over SSH mean the same structure can point at a server. 62 contributors and 2,260 stars in three weeks is real momentum.

**Pros:**
- **Terminals survive the window** — the single most useful property for anyone running long agent tasks.
- **Agent status is legible at a glance**, including work that finished while you were away.
- **SSH machines are first-class**: a space runs its terminals on the remote host, not locally.
- **`herdr-app --skill` prints an agent guide**, so an agent can drive the window without a plugin.
- **Rust, Apache-2.0, 62 contributors** — a serious project, not a weekend toy.

**Cons:**
- **It needs a desktop session and a working Vulkan driver on Linux.** Our agents live in a headless container with neither; this is the same class of blocker as Chrome missing `libglib-2.0.so.0`.
- **It is a GUI, and Shareef is not a programmer.** The value it offers is managing many terminals — a problem he does not have, because Hermes is the interface.
- **424 open issues and no published releases** — installation is `curl … | sh` from their own release host, which is a supply-chain decision, not a convenience.
- **Telemetry is on by default** in release builds, and mods are explicitly "trusted code, not sandboxed extensions".
- **What it does for a desktop, Hermes cron already does for a server** — scheduling, background runs, and status reporting without a window.

**Should we…**
- ✅ **Adopt it**
- 👀 **Watch it**
- ❌ **Skip it** — not for our stack ← *this one*

**Impact on our stack:** **Low.** Nothing changes on the VPS or in the platform. At most it is a nicer terminal on Shareef's desktop, where Hermes already runs natively and where he works through chat rather than a terminal grid.

**Why:** Herdr is a good product solving a problem we do not have. Its whole thesis is that managing many terminal panes and agent windows by hand is painful, and that is true for a developer with six agents in six repos — not for a department whose agents run headless on a schedule and report into Telegram. The one idea worth borrowing is the status vocabulary (Working / Blocked / Done / Idle, with finished-while-away), which is a cleaner way to describe a cron run than "it either sent a message or it did not". Install it on the desktop if the terminal ever becomes the place work happens; it should not enter the architecture.

## 6. OpenAI SIP telephony — *news*

**What it is:** OpenAI's SIP trunk path for GPT-Live (and the Realtime API): a SIP trunking provider such as Twilio connects a phone number to an OpenAI project, your backend receives an incoming-call webhook and accepts or rejects it, and a sideband connection lets the backend receive session events and send commands while SIP carries the audio. Outbound calling is now available to all organizations — the change that made this generally usable.

**Source:** https://developers.openai.com/api/docs/guides/voice-sip · discussion: https://news.ycombinator.com/item?id=50399695 · Provenance: Hacker News (Nov 6, 63 points).

**What's good about it:** It removes the middle layer for phone agents. Today our call-out line speaks to a voice platform that speaks to a model; with SIP, the model's own session is on the call, with TLS signalling, SRTP for audio, and an explicit accept/reject decision per call — which is a real control we do not have in the current setup, where the provider decides what answers. The sideband model is also the right shape for our use: audio over SIP, business logic and tool calls on our backend, so the schedule lookups and the roster data stay in our systems rather than in a vendor's flow builder.

**Pros:**
- **One fewer vendor hop** between the caller and the model, and one fewer place for a transcript to be stored.
- **An explicit accept/reject webhook per inbound call** — a door we control, not a provider's routing rule.
- **Sideband connection** keeps tools, lookups and logging on our backend where our data already lives.
- **Works with the trunk we already have** — our number is on Twilio, which is the example provider in the docs.
- **TLS signalling and SRTP** rather than a proprietary transport.

**Cons:**
- **It is infrastructure, not a product.** No flow builder, no barge-in UI, no call logs, no voicemail, no transfer semantics — all of that becomes our code.
- **Requires a public webhook endpoint and signature verification**, which means exposing a route and keeping it correct; our current voice path does not require that.
- **The call-out line is staff-only by policy** and works today on Vapi; the migration buys capability we have not asked for and risks a line residents depend on.
- **Cost per minute against our current provider is unquantified** here; without a number this is curiosity, not a business case.
- **Vendor concentration** — it moves voice onto the same provider as our models, so an outage takes both.

**Should we…**
- ✅ **Adopt it**
- 👀 **Watch it** — keep as the fallback plan if Vapi pricing or terms change ← *this one*
- ❌ **Skip it**

**Impact on our stack:** **Medium — voice.** It is a genuine alternative path for the call-out line and for any inbound phone agent: audio on a trunk, decisions and data on our backend. It would replace a vendor's flow builder with our own code, which is better long-term and more work now.

**Why:** This belongs in the brief because voice is the one part of our stack where the vendor owns the conversation, and SIP is the standard way out of that. But "available to all organizations" is a capability, not a plan: adopting it means owning a webhook, an accept/reject policy, transfer handling and call logging that Vapi currently provides, for a staff-only line that is not broken. The right posture is to keep it documented as the exit and to revisit it if Vapi's pricing, terms or reliability change — at which point the migration is a known quantity instead of a scramble.

- **`kunchenguid/runner-up`** (281★, MIT, 2 contributors, 9 days, v0.1.12) — self-hosted GitHub Actions runners, one fresh container or VM per job. Real and well-built; we do not run GitHub Actions workloads, so there is nothing for it to replace.
- **`eduwxyz/tucano`** (268★, Apache-2.0, 42 open issues, 10 days) — "your team of AI agents, on your Mac, Windows or Linux", agents that talk in channels and review each other. The third entrant this week in the coworker category (with Rerun and Autoloop); desktop-first and Claude-Code-centric, so it duplicates the two above without adding a capability.
- **`Balanov/latch`** (62★, MIT, 1 contributor, 2 days) — a tiny HTTPS contract between an agent and a service: ask / quote / approve / commit / status, with SHA-256 offer digests and idempotency keys. The idea — an approval bound to a digest — is genuinely good and relevant to spend-gating, but it is a 0.1 wire spec with one author and a simulated demo. Worth re-reading when we design our own approval gate.
