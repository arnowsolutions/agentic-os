### 1. Incremental learning for `AGENTS.md` — the memory mechanism, not the app

**What it is:** A plugin in Cursor's official registry that keeps `AGENTS.md` current by learning only from transcripts that are **new or changed**. Three parts: a `stop` hook that decides when a learning pass is warranted, a `continual-learning` skill that orchestrates it, and an `agents-memory-updater` subagent that mines the transcript deltas and rewrites the matching bullet points in place. It reads the existing `AGENTS.md` first so it updates rather than regenerates, processes only files it has not already processed, and writes **plain bullet points only — no evidence or confidence metadata**. MIT licensed, v1.0.0, author Eric Zakariasson, shipped inside `cursor/plugins`.

**Source:** https://github.com/cursor/plugins/tree/main/continual-learning · manifest: https://raw.githubusercontent.com/cursor/plugins/main/continual-learning/.cursor-plugin/plugin.json · Provenance: spotted on The Next New Thing — https://www.youtube.com/shorts/bG0gy-9Fyb0 (the short names Cursor Plugins; the mechanism is inside the registry).

**What's good about it:** The design constraints are the valuable part, and they are exactly the constraints our own memory file has failed. Our `MEMORY` block is at **96% of 6,000 characters** and visibly full of things that should have replaced older lines but instead sat beside them — the same fact appears three times in slightly different words (the gateway watchdog survives restart / the hook must be re-added after a recreate / watchdogs must be external processes), and each version was appended, never merged. This plugin's three rules are the fix: (1) *read existing first, update matching bullets in place* — that is the merge we keep failing to do; (2) *only new or changed transcripts* — no re-reading the whole history and no duplicate entries, which is the same discipline this brief's dedupe step enforces by hand; (3) *plain bullets, no metadata* — the reason our memory stays readable at 6k where a JSON store would not be.

It is also the cheapest possible thing to test. The whole artefact is a hook config, one `SKILL.md` and one subagent prompt; there is no runtime, no service, no database, no API key. The Hermes side already has the inputs it needs — every cron run writes a transcript and every session leaves files under the Hermes home — so the mechanism ports with a different file path, not a rewrite.

**Pros:**
- **In-place edits, not appends.** This is the specific failure mode our memory file shows: the same lesson recorded repeatedly instead of one bullet being sharpened.
- **Delta-only processing** means the cost per run is bounded by what changed, not by total history. That is what makes it viable to run after every cron job rather than quarterly.
- **Three small text files, zero runtime, no credentials.** Nothing to install, nothing to keep alive, nothing that can hold a session.
- **It lives in a 119-plugin registry that is actively maintained** — 14.6k stars, 1,508 forks, commits landing hourly on Oct 29 — so the `stop`-hook contract it targets is not a hobbyist invention.
- **Honest about scale.** The README does not promise semantic memory or embeddings; it promises bullets in a file. That is a promise we can verify by diffing.

**Cons:**
- **It is a Cursor feature, not a general one.** The hook is invoked by Cursor's agent loop on a `stop` event; Hermes has no equivalent event, so what we adopt is the *procedure* (read → diff transcripts → edit bullets in place → plain text only), wired into the Hermes memory path ourselves.
- **No dedupe beyond file identity.** "Only new or changed transcript files" prevents re-reading, but nothing in the README prevents a *new* transcript from restating a fact already in `AGENTS.md` — the same failure at one remove. The subagent prompt is where that has to be enforced, and prompts drift.
- **Version 1.0.0, one named author, no tests in the plugin directory.** There is nothing to break (it is text), so this is survivable — but it is not engineering we can lean on.
- **"No evidence metadata" is a trade, not a free win.** Our memory lines that matter most (the Montefiore login ban, the CRM-is-source-of-truth rule) are rules *because* of a dated incident; stripping provenance makes the bullet shorter but loses the reason it exists.
- **The registry is not a trust boundary.** 111 of the plugins are `third_party/`, and the Gmail/Outlook ones are pointers at remote MCP servers run by other companies. Membership in the repo means "listed", not "reviewed by Cursor".

**Should we...**
- ✅ **Adopt it** — as `~/.hermes/skills/memory-consolidate/SKILL.md`, not as an installed plugin.

**Impact on our stack:** High — the Hermes memory file and its 96% ceiling. Concrete change: a job (or a step at the end of this one) reads the day's cron transcripts, finds memory-worthy new facts, and **edits existing bullets in place** instead of appending — which is what would take the three watchdog lines down to one and hand back the characters that got evicted this week.

**Why:** Memory is the one component of our stack that silently degrades, and it degrades in a way no watchdog can see: nothing fails, the file just fills with restatements until the useful facts start being pushed out. This plugin is the first description I have seen of the fix written down as procedure — read what is there, diff what is new, merge into the existing line, keep it plain. We do not need Cursor to run it; we need the three rules and a transcript directory, both of which Hermes already has. The adoption is a small skill file plus one dry run against a copy of the current memory to see whether it collapses the duplicate watchdog entries the way the README claims. If the dry run produces a cleaner file, we run it weekly and stop hand-pruning 6,000 characters; if it produces lossy rewrites, we keep the diff and lose nothing.

### 2. Cursor Plugins — an official registry, and a first-party mail connector we cannot use from here

**What it is:** Cursor's official plugin specification and plugin collection: a repo of standalone plugin directories, each with a `.cursor-plugin/plugin.json` manifest, an optional `mcp.json` and its own skills/agents/hooks. 119 plugins in total — about a dozen written by Cursor itself (`thermos`, `ralph-loop`, `teaching`, `pr-review-canvas`, `docs-canvas`, `orchestrate`, `cursor-sdk`), a handful from named developers (`continual-learning`, `cursor-team-kit`), and 111 in `third_party/` covering Gmail, Outlook, Google Drive/Calendar/Docs/Sheets/Slides, GitHub, Playwright, Salesforce, HubSpot, Docusign and 100-odd others. It was covered in the Oct 28 brief as a single item; what is new today is the material behind the headline — I read the manifests and the MCP wiring for the four plugins that touch us.

**Source:** https://github.com/cursor/plugins · Gmail: https://github.com/cursor/plugins/tree/main/third_party/gmail · Outlook: https://github.com/cursor/plugins/tree/main/third_party/outlook · Provenance: spotted on The Next New Thing — https://www.youtube.com/shorts/bG0gy-9Fyb0 (previously covered Oct 28 as "Cursor Plugins"; **new: the mail connectors' actual endpoints and auth**, and the plugin inventory).

**What's good about it:** The two plugins that matter for us are wired the way a bank would want, which is rare in this category. Gmail does **not** bundle a scraper: its `mcp.json` points at `https://gmailmcp.googleapis.com/mcp/v1` — **Google's own remote MCP server** — with OAuth 2.0 against Google, and the docs link to Google's published setup guide for their Workspace MCP servers. Outlook does the same with Microsoft Entra ID and Microsoft Graph. That means no password, no cookie jar, no device-code flow, no headless browser signed into a real account: the model talks to a server the vendor runs, and the token is minted by the vendor's own consent screen. After the July incident, this is the *only* mail architecture I would even consider, and it is the first time a mainstream dev tool has shipped one by default.

The rest of the inventory is useful as a map rather than as software. The registry shows which integrations reach maturity with an official MCP server (Google Workspace, Microsoft 365, GitHub, Salesforce, Docusign) and which do not. `thermos` is a real two-subagent review rubric (deep correctness/security audit plus a maintainability audit, run in parallel and synthesized). `ralph-loop` is the loop-until-done pattern as a plugin. And the manifest format itself — a JSON file pointing at skills, agents, hooks and MCP servers — is a portable description our own skill loader already understands in spirit.

**Cons:**
- **The Outlook path crosses a line we drew on purpose.** The endpoint is `https://api.cursor.com/rest-mcp/outlook/mcp` — Cursor's relay in front of Microsoft Graph, OAuth via Entra ID. Pointing a Montefiore mailbox at it from this VPS is the same shape of mistake as July's Graph device-code login, only with a third party in the middle of the medical mail. Memory rule stands: never log into `@montefiore.org` from the VPS. This one is desktop-and-throwaway-account territory or nothing.
- **Remote MCP = the vendor's availability is your availability.** If Google's or Microsoft's MCP server is down or changes its consent flow, the plugin stops. We do not get to inspect or pin that server.
- **No stated licence on the repo itself.** The GitHub sidebar and API both report `license: null` for `cursor/plugins`; individual plugin manifests declare MIT. The registry is therefore a mix, and the aggregate has no terms — a real gap if we ever wanted to vendor anything from it.
- **604 open issues** on a repo whose contribution model is "add your company's plugin". A lot of what is there is marketing surface with a logo asset.
- **Everything here is Cursor-shaped.** Skills, hooks, `run_in_background` subagents — the contracts are Cursor's, so porting a plugin to Hermes means porting its content, not its wiring.

**Should we...**
- 👀 **Watch it** — and specifically watch the Google remote MCP server as a *replacement candidate* for our current Gmail auth path on the desktop.

**Impact on our stack:** Medium — email/Outlook and the Hermes skill loader. Concrete change (if it ever happens): the desktop's Gmail access moves from our own OAuth app to Google's remote MCP server, which removes our client secret from the loop entirely. The Montefiore mailbox stays exactly where it is.

**Why:** I want to be precise about what is and is not new, because yesterday's brief already ruled on this repo. What changed is that I read the plumbing, and the plumbing is better than the headline: Gmail here is Google's server, not a third party's scraper, and that is a genuine improvement on every mail integration we have evaluated since the summer. But the honest verdict does not move, because the plugin that would actually change our week — Outlook for Montefiore — routes Entra-ID-authenticated mail through `api.cursor.com`, and putting the residency program's mail through a dev-tool relay from a datacenter IP is a worse version of the thing that got us flagged in July. So we watch, with a specific trigger: if Google ships the same remote MCP server for Microsoft Graph auth, or if Microsoft publishes one directly, the desktop Gmail/Outlook path gets rebuilt on it immediately. Until then this is a map of who has a real MCP server and who has a logo, and the answer is useful on its own.

### 3. Omnara — an open-source managed agent platform, durable across restarts

**What it is:** Apache-2.0, self-hostable agent runtime that sits between your app and a model: a REST API and TypeScript SDK to launch agents, a Postgres **event log that is the agent's state** (so any worker can pick an agent back up after a crash), stateless workers that only exist while an agent is taking a turn, a `omnarad` daemon that each machine runs to connect *outbound* to the platform (no inbound ports), approvals as a first-class event, memory stores as shared filesystem across agents, schedules, and Slack/Discord/GitHub integrations. Self-host is `docker compose -f compose.yaml --profile app up -d`. It is a live project — release 0.2.14 (omnarad and cluster) shipped Oct 29, 21 contributors, 3.3k stars, 260 forks — and it re-emerged in today's results as an Open Source release (`debughui-crypto/show-hn-omnara-open-source-0f786a`), which is what put it on the scan.

**Source:** https://github.com/omnara-ai/omnara · docs: https://docs.omnara.com/self-hosting/deployment · release: https://github.com/omnara-ai/omnara/releases/tag/omnarad-v0.2.14 · Provenance: GitHub Search API (`Show HN agent` created since Oct 24, plus a direct `omnara` query) — not from any tracked channel.

**What's good about it:** The architecture is a direct answer to the worst structural property of our cron fleet. Today, if a Hermes job dies at 11:50 of a 12-minute brief run, the work is simply gone; the state lived in the process. Omnara's core claim is the opposite — **every step of every agent is written to Postgres, and that record *is* the state**, so a restarted worker resumes an agent mid-task. That is the thing that would have saved the October rebuild pain, where the watchdogs had to be relaunched by hand because they lived in the container's process tree.

The operational shape is also right for us. Machines connect by dialing out, so nothing on the desktop needs a hole punched in it — the same constraint we already solved with `omnarad`-style reverse connections for Tailscale. Approvals are events in the stream, not a separate approval UI, which is how our own confirm-before-send logic should have been modelled. And the multi-model story is complete: OpenAI, Anthropic, OpenRouter, Bedrock, **LiteLLM, Ollama, or any compatible endpoint, including models you host**. The Oct 7 changelog (memory stores, Slack/Discord/GitHub integrations, redesigned dashboard) is the largest update since launch; 0.2.14 was a maintenance release two days ago, not a marketing drop.

**Pros:**
- **Durability is the headline and it is verifiable in the architecture, not just the copy:** Postgres event log + stateless workers + "any worker can pick an agent back up after a crash or restart".
- **Outbound-only machine daemon.** No inbound ports on the desktop or on any host we add — that removes the single riskiest part of running agents across two machines.
- **One-command self-host, and the local path needs no email provider** (the verification link prints in `docker compose logs api`), so it can be tried without touching production identity.
- **Any model, including local** — which is the property that makes it a candidate for the "run the cheap jobs on a small local model" idea we keep deferring.
- **Real project, not a launch:** Apache-2.0 in both the sidebar and the badge, 21 contributors, continuous releases (0.2.13 and 0.2.14 a day apart), 36 open issues — a maintained codebase with normal turnover.

**Cons:**
- **It is another Postgres + Redis + workers + blob storage on a VPS that already runs Supabase self-hosted, Hermes, several Django/nginx containers and a full attack-surface stack from yesterday.** RAM and disk are the binding constraint, not enthusiasm. This is the single biggest reason it is not an adopt today.
- **"Managed platform" means it wants to *own* the agent loop** — model calls, tools, machines, memory. Adopting it properly means moving cron jobs into `agent.yaml` files and giving up control of the loop Hermes already runs well. A partial adoption buys the durability without the benefit.
- **The local defaults are explicitly insecure** ("The local defaults are intentionally insecure" — README), so any real deployment needs the self-hosting guide and a public URL for sandboxes, which is a security review we have not done.
- **36 open issues and 0.2.x versioning.** The event schema and `agent.yaml` format will change; anything we build against it this month we will be rewriting in the new year.
- **The cleverness is in the platform, and the risk is in the mailbox.** Every agent it runs needs a machine plus a model plus secrets; a platform that makes it trivial to run many agents also makes it trivial to run many agents with the wrong credentials.

**Should we...**
- 👀 **Watch it** — with a specific adoption trigger (see Why).

**Impact on our stack:** High, if taken — Hermes cron durability and the whole job architecture; concretely it would replace "restart the watchdog by hand after a container recreate" with "an agent that resumes where it stopped". Medium if we only borrow the pattern.

**Why:** Our October was spent recovering from work that vanished when a process went away, and we patched it with external shell loops — which is the right short-term answer and the wrong long-term one. Omnara exists precisely to make that class of problem structural rather than patched: state outside the process, workers that come and go, machines that phone home. That is worth knowing about, and it is close enough to real that I nearly recommended it. What stops me is arithmetic, not doubt: our VPS is already running several stateful stacks, and adding a Postgres, a Redis and a worker pool to buy durability for jobs that mostly run in under a minute is a bad trade *today*. The trigger that flips it: the next time a Hermes job dies mid-run and we lose real work — or the next time we add a second machine that has to run the same jobs — we should stand Omnara up on the spare capacity rather than write another watchdog. Until then, the borrowable idea is the smallest piece of it and the most valuable: make the cron scripts write their progress to a row as they go, so a restart resumes instead of repeating.

### 4. Mistral Large 4 "Le Chonk" — the open-weight release actually landed

**What it is:** Mistral's largest model: a ~1 trillion-parameter natively multimodal mixture-of-experts with ~52 billion active parameters (128 routed experts, 4 active per token, 1 shared), **1M context**, three reasoning efforts (`low`/`medium`/`high`), native function calling with strict JSON schema, fluent in 160+ languages. The Oct 6 announcement was an API preview; **the weights were published on Oct 29** at `mistralai/Mistral-Large-4-1T-A52B` on Hugging Face, with a quantized NVFP4 checkpoint, GGUF builds, and a Mistral Ecosystem Open-Weight License (a modified MIT: free commercial and non-commercial use, but running it as a Model-as-a-Service needs a separate Mistral licence). API price is $0.70/M input, $2.10/M output.

**Source:** https://huggingface.co/mistralai/Mistral-Large-4-1T-A52B · announcement: https://mistral.ai/news/mistral-large-4 · Provenance: Google News RSS (`q=new AI model`: CNET, WIRED, ZDNET, Euronews all carrying the weight drop on Oct 29) — no tracked channel covered it.

**What's good about it:** The numbers are real and independently interesting in one specific direction. On the Artificial Analysis Coding Agent Index it scores **48% — effectively tied with the leading open-weight model (GLM-5.3) while using 47% fewer tokens per task**, and on the Cyber Index a specific test — reproduce a real vulnerability in open-source software and patch it — it scores **82%, the highest of any model**, including closed ones, because "several leading closed models, including Claude Opus 5.5 and GPT-6 Astra, score near zero on the same test because they refuse to perform the task." It solves 93% of Cybench. That refusal-delta is the interesting finding, and it is directly relevant to a project we have running: cvENGINE, adopted in yesterday's brief, exists to tell us which exploited CVEs are live on our domains.

The engineering is also unusually coherent: trained from scratch on 3,800 Grace Blackwell GPUs in Mistral's own European datacentres, the checkpoint ships with an embedded DSpark speculative-decoding head, vLLM/SGLang/llama.cpp/transformers are all supported on day one with pinned Docker images and recipes, and the vision tower is exempted from the FP8 quantisation. And the licence is honest — it says what the restriction is (MaaS) instead of hiding behind a custom name with no plain-English explanation.

**Cons:**
- **We cannot run it.** 1T parameters at FP8 is roughly half a terabyte of weights and needs a multi-GPU node; the NVFP4 checkpoint targets Blackwell. There is no machine in our stack — VPS or desktop — that hosts it, so the open weights are worth nothing to us operationally. The only usable surface is the paid API.
- **The API is not obviously better for our workloads than what we already call.** 26 on the Intelligence Index v5 (highest among *western* open-weight models, behind the Chinese ones), and the "$0.70/$2.10" pricing only pays off if the 47% token reduction holds on *our* prompts, which nobody has measured.
- **The vendor's own benchmark pages contradict each other by a point** — the blog says a "combined Coding Agent Index score of 49.8%", the model card says 48%. Small, but the brief rule is that the README wins, and here there are two READMEs disagreeing.
- **The licence is not MIT, whatever the file's first line says.** "Modified version of the MIT license" plus a MaaS restriction is a source-available licence; the HF tag is `license:other`. If we ever put it behind a product, that clause is the one that bites.
- **The cyber capability is the reason to be careful, not just the reason to want it.** A model that is explicitly good at reproducing vulnerabilities and is *less likely to refuse* is a capability that in our environment needs to sit behind a policy, not behind a cron job.

**Should we...**
- 👀 **Watch it** — value to us is in a comparison test, not a deployment.

**Impact on our stack:** Medium — the Hermes model layer (a possible second provider for the cheap jobs) and, indirectly, cvENGINE. Concrete change: one A/B of ML4 against our current model on the brief-generation prompts and on a CVE-triage prompt, and nothing else until that returns a win.

**Why:** Two releases landed within 24 hours of each other and this is the one that actually shipped open weights — Gemini 4 Carbon, which yesterday's brief covered, is still gated behind approved cyber defenders. So the news is real: a trillion-parameter western open model with a 1M context and a licence that permits commercial use. But "open weights" and "runnable by us" are different claims, and the gap here is a data centre. The version of this that would matter for our stack is much smaller: add `mistral-large-4` as a second endpoint behind the brief job, measure it against the model we already pay for on the same nine days of briefings, and keep whichever is cheaper per acceptable brief. If it wins on the CVE-triage prompt specifically — that is where its headline benchmark actually lives — it is worth wiring in front of cvENGINE's findings. That is a two-hour test, and it is the right size of commitment to a model we cannot host.

### 5. `ai-design-skills` — 12.6k stars, eight commits, one file

**What it is:** An MIT repo of design skills for AI coding tools — Claude Code, Cursor, Codex, Windsurf, or anything that reads a markdown rules file. As shipped it contains exactly **one** skill, `landing-page-design`: a 431-line `SKILL.md` in two halves — Part A (intake questions, page structure, layout selection, conversion rules, copywriting, build order, SEO/AEO, pitfalls) and Part B (a non-negotiable visual system: typography, spacing, corner radius, borders and backgrounds, hero section, icons, motion, navigation). The `design-to-motion` skill was moved out to its own repo three days ago, leaving the collection with one member. Inside `cursor/plugins` today it is the only third-party entry the episode actually pushed.

**Source:** https://github.com/elayadesign/ai-design-skills · skill file: https://github.com/elayadesign/ai-design-skills/blob/main/skills/landing-page-design/SKILL.md · Provenance: spotted on The Next New Thing — https://www.youtube.com/watch?v=vz7nLocDtEE

**What's good about it:** The structure is the right way to write a design skill and better than most: separate what the page *says* from how it *looks*, decide A before touching B, and put every design value in one editable section near the bottom so a fork can change the system without touching the method. Some of the rules are genuinely sharp — the nested-radius formula (`inner radius = outer radius − gap`) is the kind of detail that separates a polished card from a sloppy one, and the "one offer → one audience → one primary action" framing for a landing page is correct and hard to argue with.

**Cons:**
- **The numbers do not survive the honesty rule.** 12,598 stars, 916 forks, 44 watchers — on **8 commits**, **one author**, a repo 38KB in size, and a collection that currently contains a single skill. That is a promotion profile, not an adoption signal. Watchers (44) is the number that is hard to inflate, and it is 0.35% of the star count.
- **It bakes in a house look that is not our house look.** Geist (or Inter) only, one typeface per site, "never use italic fonts", `#000000` / `#181818` dark backgrounds, black-to-white gradient headings, Tailwind's type scale only. Montefiore's system is navy `#003da5` on `#f5f5f0` with real photography, and Shareef has rejected dark-background concepts four separate times. Applying this skill's Part B would produce the generic dark-gradient SaaS page he calls "not innovative".
- **It duplicates something we already hold.** The vault has **Hallmark — Anti-AI-Slop Design Skill** as an adopt, and the briefs' own `unified-no-slop-page-redesign` workflow already encodes the review standard. A second, competing visual system is how the two get blended into mush.
- **A one-skill "collection" with the second skill already moved out** is a project still deciding what it is.
- **Landing pages specifically** — long-form single-offer marketing pages — are the page type we build least. Unified is a logged-in product surface.
