## 1. ai-design-check

**What it is:** An npm package (`@enmera/ai-design-check`) that ships three things in one install: a zero-dependency checker with 95 design rules for interfaces built by AI coding agents, a pair of agent skills that repair a screen and report the count before and after, and secondary commands (`inventory`, `narrow`, `system`, `story`) for auditing components, phone breakage, type/colour systems and before/after video.

**Source:** https://github.com/enmerasoftware/ai-design-check · npm: https://www.npmjs.com/package/@enmera/ai-design-check · Provenance: GitHub API — new repos in the last 7 days, 206 stars, pushed Nov 2.

**What's good about it:** The rules were not invented in a vacuum — the README says they come from screens the authors shipped at Enmera and Searvia, "what read as generated, what broke at narrow widths, what people did not understand," then cross-checked against 16 highly rated dashboards. 57 of the 95 rules are machine-checkable; the other 38 are marked `review` and handed to the fix skill, which is an honest split rather than pretending a linter can judge a layout. It reads web projects *and* SwiftUI and Jetpack Compose, and the fix skill is explicitly constrained never to lower the finding count by deleting content and never to silence a finding without a reason. It also has a `PostToolUse` hook for Claude Code so an agent gets its own findings back on every edit it makes — that is the loop our redesign work has been missing.

**Pros:**
- 95 concrete rules across accessibility, phone browsers, type scale, copy, components, layout, motion, data and localisation — these are the categories the redesign reviews keep hammering, written down once instead of re-argued per screen.
- Zero dependencies, no API key, `npx` only — it can run on the VPS or in a cron with nothing to provision.
- `inventory` answers "how many different buttons, inputs, headings and cards do we have?" — the drift question behind the "unified" in Unified Platform.
- `narrow page.html` tests phone and long-language breakage, which is where the public schedule and the Call Out flows actually get used.
- MIT, 15 tagged releases in six days, real before/after examples committed as HTML files (266 findings to 0 on a dashboard).
- Ships a hook so the fix happens during the agent's turn, not in review three days later.

**Cons:**
- Rule-count and release-count inflation is real: 15 versions in six days and version 0.10.1 with 30 commits and 2 contributors means this is still a fast-moving beta. APIs and rule IDs will move under us.
- The rules are opinionated in ways that will fight our brand: "no tracked uppercase labels," "no cards inside cards," a hard 11 px type floor and a 4 px spacing grid. Some of those will be right for Montefiore, some will not, and suppressing a rule needs a reason written down or the next run re-flags it.
- Turkish-origin ruleset: some rules encode localisation concerns (Turkish i/İ, locale-aware casing) that simply do not apply to us, and the README is machine-translated in places, so rule intent occasionally needs the source JSON.
- It measures code and rendered HTML, not judgment — it cannot tell you a page is boring, which is the complaint that actually kills a design review.
- The fix skill is a Claude Code / Codex skill. `npx skills add` works with agents that read `SKILL.md`, but our Hermes skills use a different loader, so we would install the rules file and the checker and wire the skill by hand.

**Should we…**
- ✅ **Adopt it**
- 👀 **Watch it** — keep an eye on it, not ready yet but promising ← *this one*
- ❌ **Skip it**

**Impact on our stack:** High — **Unified Platform (and any future redesign work).** Concretely: run `npx @enmera/ai-design-check` against the built Unified Platform dist and against the standalone `unified-*-redesign-vN.html` surfaces, and get a number per page instead of a verdict paragraph. The 18 redesign surfaces plus Decision Studio are exactly the "AI-built interface that reads as generated" case this tool was written for.

**Why:** This is the highest-impact item today because it converts a recurring argument into a measurement. The redesign loop currently depends on Shareef looking at a page and saying "not good" — and per the standing rule that a "still not good" verdict means reset to the principle, not micro-tune, there is no instrument in that loop telling us *which* of the 95 things is the one that reads as generated. The checker gives that: a finding count, a file, a line, and a before/after. Two cautions keep it off "adopt today." First, the design rules are another shop's taste baked into lint, and our brand has hard constraints it will happily flag (navy #003da5, light #f5f5f0 campaign surfaces) — so it has to start as a signal, not a gate. Second, it is six days old with a moving API. The move: run it read-only against one Unified Platform page and one redesign HTML file, look at the finding list next to the page, and see whether it names anything the reviews already named. If it does, wire the `PostToolUse`-style check into the redesign workflow; if it just flags our brand tokens, we stop there for the price of one `npx`.

## 2. Kanzo

**What it is:** A self-hosted kanban board and an MCP server in a single 4.5 MB Rust binary. The board runs in a browser at `localhost:4242`; agents connect through `kanzo mcp` and take tasks, move cards and comment; the CLI handles sharing and sync. State lives in SQLite under `~/kanzo`.

**Source:** https://github.com/emanuele-em/kanzo · Provenance: spotted on **Github Awesome** — https://www.youtube.com/watch?v=l661iLW2QTA ("28 Self-Hosted Projects on Github: kanzo, traccar, suna, dossier, doska, mitra, magic, freetvarr")

**What's good about it:** This is a genuinely mature repo, not a trending blip: **177 commits, 6 contributors, 7 tagged releases**, first release Oct 25 and v0.3.0 on Nov 1 — and the commit log is unglamorous engineering ("Build a lighter Kanzo," "Share the board on the network with kanzo share, join and leave," dependabot bumps, a security policy, a code of conduct). The measured footprint is real and small: 4.5 MB binary with SQLite included, ~4.5 MB idle memory, 2 ms start, a 3,000-task board loading in 17 ms, and — the number that matters for agents — about 900 tokens of tool list once per session and **10 to 60 tokens per agent reply**. Its sharing model is the clever part for us: `kanzo share on` prints every address the machine has, and the README names **Tailscale** as a first-class way to join a board across the internet — which is exactly our VPS↔desktop setup.

**Pros:**
- An MCP server that costs agents almost nothing per call — 10–60 tokens a reply — so a cron agent can poll and update a real backlog without burning the budget that made us build TokenEconomizer.
- Agent ergonomics are designed, not bolted on: the agent finds the right project from the git remote of the repo it is working in, so it does not need to be told which board to use.
- A "Human" flag on tasks — mark a task Human and agents leave it alone — plus a Backlog column agents never touch. That is the review gate we keep re-implementing by hand.
- Tailscale is in the README as the supported way to share a board across the internet, which matches our existing VPS↔desktop mesh; `kanzo share on` just prints the 100.x address.
- `kanzo export` prints the board as Markdown or JSON, so the backlog is never trapped inside the tool.
- `kanzo service install` keeps it running across restarts — the same "survive a restart" requirement our watchdogs exist to satisfy.

**Cons:**
- **No authentication anywhere.** The README says it plainly: "There are no logins: share only on a network you trust." That is fine on a Tailscale-only interface and unacceptable if it ever gets a public hostname or a Traefik route.
- AGPL-3.0, and it says so deliberately ("Kanzo was never released under MIT"). Internal use is fine; anything we expose as a service with modifications carries the source-sharing obligation.
- It is a *board*, not a scheduler. It does not know about cron, does not trigger work, and will not replace the UGenda-adjacent scheduling logic — it would sit beside it as a task queue.
- New surface area in a department that already runs a lot of moving parts: another service, another SQLite file, another thing to back up and patch.
- Sync across machines goes through a private git repo — workable, but a second sync mechanism to reason about when we already have Tailscale.

**Should we…**
- ✅ **Adopt it**
- 👀 **Watch it** — keep an eye on it, not ready yet but promising ← *this one*
- ❌ **Skip it**

**Impact on our stack:** Medium — **Hermes cron + agentic-os.** It would replace the "what is the agent working on" that currently lives in chat history with a durable, agent-readable backlog: cron jobs that fan out work, agents that claim a card and comment as they go, and a Human-flagged lane for anything that needs Shareef before it ships.

**Why:** Watch, not adopt, for one reason and it is a security one: a kanban board with no logins must never be reachable from anything but a trusted private network, and on a VPS any mistake in a Traefik rule or a `listen = "0.0.0.0"` puts a department's task list on the open internet. The honest path is to run it bound to `127.0.0.1` (the default in the README's config sample) and reach it only over our existing Tailscale mesh on 100.87.237.45, never through a public hostname. If we do that, this is a real improvement to how agentic-os tracks work and how the daily brief and cron jobs hand off tasks — it is the first board we have seen where an agent's cost per interaction is low enough to use continuously. If Shareef wants a task board for the department's human work as well, that is a bigger scope question and should be its own decision; this tool's shape is individual-plus-agents, not department-wide.

## 3. trina-ax

**What it is:** A self-hosted workspace that puts real Claude Code and Codex agents behind a web/desktop/mobile chat for a whole team: company folders as the knowledge base, `SKILL.md` files as governed team skills, an MCP layer, and — the distinguishing feature — **per-person folder permissions enforced on every file the AI touches, as the person asking.**

**Source:** https://github.com/trina-app/trina-ax · Provenance: GitHub API — MCP-tagged repos in the last 7 days, 109 stars, 1,029 commits, 19 releases, v0.2.21 pushed Nov 2.

**What's good about it:** The commit history reads like a project that has shipped and then been QA'd: 34 branches, 1,029 commits, a design-system contrast audit with WCAG numbers checked in tests, upload-memory bounds with real measurements ("20 files now peak at 286 MB, 50 at 370 MB"), Korean register consistency enforced by unit tests, and a release-CI that refuses to publish when a read-back cannot prove the upload landed. The permission model is the real idea: the server checks every file the AI opens *as the person asking*, so a folder someone cannot see does not exist for their AI either — the README's example is a sales person asking about revenue and correctly getting "I found no revenue figures in any team file she can access." It also supports running Claude Code against DeepSeek, Kimi or GLM through an Anthropic-compatible gateway, and it runs on Debian 12/13 or Ubuntu 24.04 with systemd.

**Pros:**
- The permission model is the correct one for a hospital: AI answers are scoped to what the human asking is allowed to read, enforced server-side, and not just in the prompt.
- Real Claude Code / Codex agents on the server — up to 150 tool rounds, up to 4 sub-agents, web search and schedules — rather than a thin chat wrapper.
- Mature engineering signals: 19 tagged releases, tests that assert contrast ratios and byte-level upload integrity, an explicit security-and-permissions doc.
- Self-hostable on the Linux we already run, with an honest hardware floor: 4 GB RAM, 20 GB disk.
- Skills are plain `SKILL.md` files with folder-based access rules — conceptually compatible with how our own skills are structured.
- Speaks English, Korean, Indonesian, Japanese and Spanish, and the repo shows real work shipping non-English UI properly.

**Cons:**
- **It assumes one company AI account shared across people.** "Connect the company's Claude or OpenAI account once, or let people connect their own" — and the README itself disclaims that "this software setting does not grant permission under Anthropic's or OpenAI's terms." Putting several staff on one consumer/team subscription is a licensing question we should not answer by installing software.
- Heavy footprint for what it replaces: Bun + Go + a TypeScript monorepo, systemd with cgroup v2, a DuckDB/SQLite-ish state layer, macOS menubar app, mobile app, an AWS-hosted paid tier. This is a product, and self-hosting it is an IT project, not a pull request.
- AGPL-3.0-only — fine internally, but it constrains anything we build on top and expose.
- The team it was built for is a Korean office team (HWP document preview, Korean register tests, AWS Seoul). Our document reality is Outlook, Word and Epic-adjacent exports, so the file-reading path would need verification before we trust it on anything clinical.
- It puts a lot of institutional data into a second system with its own auth, its own audit trail and its own backups — the exact duplication the CRM-as-source-of-truth rule exists to prevent.

**Should we…**
- ✅ **Adopt it**
- 👀 **Watch it** — keep an eye on it, not ready yet but promising ← *this one*
- ❌ **Skip it**

**Impact on our stack:** Medium — **CRM / email + the agent stack behind it.** Its permission model is the design we would want if we ever gave staff a chat front-end that reads CRM contacts and program documents: the answer inherits the asker's access. It would not replace Hermes; it would be the layer nobody at Montefiore IT has to be talked into, because "the AI sees what you see" is auditable.

**Why:** This is the most interesting architecture in today's batch and the least responsible thing to install this week. The mature-engineering signals are real — 1,029 commits and releases every few hours is not a weekend promotion — and the permission design is genuinely the right model for a residency program that handles resident records. But two things keep it at watch. First, the "connect the company's Claude account once" pattern is a licensing hazard in a healthcare setting; before we would run this for staff, we would need per-user authorized accounts, not a shared subscription with usage limits. Second, it is a full second platform (Bun, Go, systemd, apps for three OSes) that would duplicate identity, permissions and audit that already have homes. What we should actually take from it is the *pattern*: enforce file access as the asking human on our own agent tools, and treat "the AI found nothing because she cannot see it" as the correct answer rather than an error. Revisit if we ever build a staff-facing assistant on the Unified Platform.

## 4. Verdict

**What it is:** A 197 KB local semantic verifier for AI agent tool calls, trained tiny model included. The premise is in the subtitle: *exit code 0 is not proof.* You give it a tool call and its result, and it judges semantically whether the call actually succeeded.

**Source:** https://github.com/Balanov/verdict · Provenance: GitHub API — new repos in the last 7 days, 217 stars on the search index, 66 stars on the repo page at read time.

**What's good about it:** The problem is real and it is the one our own tooling keeps tripping on — a script that returns 0 while silently writing nothing, a deploy that "succeeds" and serves a stale asset, a cron run that reports complete with an empty vault append. The design is disciplined: zero-dependency inference, int8 quantized weights, Apache-2.0 code and weights with a CC0 synthetic dataset, a reproducible training script, and a benchmark directory with measured metrics.

**Pros:**
- Attacks the right failure: exit status and semantic outcome are different facts and almost nothing checks the second.
- Genuinely tiny — 197 KB — so it could run inside a cron wrapper without a model server.
- Reproducible by design: `training/train.py` regenerates the corpus, retrains, quantizes and evaluates.
- Permissive licensing across code, weights and data.

**Cons:**
- **Two commits. One author. Five hours old at read time.** This is a release announcement with a repo behind it, not a validated tool.
- The 217 stars on the search index versus 66 on the repo page are inconsistent; either way, stars on a same-day repo are promotion, and the rule here is to check commits and authors, not stars.
- Trained on synthetic data with no independent evaluation — the metrics are self-reported and the corpus is generated by the same author.
- Our failures are not generic "did the tool call work" failures; they are specific (double-prefixed API paths, SW cache, 401 from rotated Supabase keys). A generic semantic verifier would not have caught any of the four silent failures we actually hit.

**Should we…**
- ❌ **Skip it** — not relevant, redundant, low quality, or not useful for us

**Impact on our stack:** Low. It would not have caught the failures that bit us, and the real fix for "exit code 0 is not proof" is the assertion-after-write discipline we already apply (read back the exact target, quote the output line).

**Why:** The thesis deserves respect and the implementation does not yet. Everything here would have to be re-derived before we trusted it on a deploy, and we already have a stronger version of the same idea: the proof rules in our own cron prompts require reading back the external target and quoting a real output line, which is deterministic and checkable, whereas a 197 KB semantic model is a judgment call we cannot audit in a hospital report. Watch the author, not the repo — if Verdict survives three months with external evaluation, it is worth a second look for the specific case of "did the agent's action actually change the world."

## 5. Shim

**What it is:** A tiny local-first terminal AI harness in Go — any model, MCP and Agent Skills, natural-language CLI, zero dependencies, MIT, 4.5 MB-ish single binary shape.

**Source:** https://github.com/Balanov/shim · Provenance: GitHub API — new repos in the last 7 days, 412 stars, v0.1.0 pushed Nov 2.

**What's good about it:** The architecture choices are exactly the ones we would defend: local-first, provider-agnostic, MCP plus Agent Skills, zero dependencies, MIT so it can be embedded and shipped, with a stated roadmap (sandbox profiles, OAuth helpers for remote MCP, context compaction) that reads like someone who has used these harnesses in anger.

**Pros:**
- Zero-dependency Go binary with MCP and Agent Skills support — the deployment shape we trust on a VPS.
- MIT and explicitly "fork it, modify it, embed it, ship it."
- A roadmap that names the right hard problems: OS-level sandbox profiles, context compaction, provider conformance tests.

**Cons:**
- **1 commit, 1 author, 15 hours old, v0.1.0.** By our own rule this is watch-at-best, and 412 stars on one commit is promotion, not adoption.
- It competes directly with Hermes — which already does MCP, skills, cron, and the delivery plumbing we depend on — so adopting it would mean replacing the agent, not adding a tool.
- No tests in the tree at read time and no security policy worth relying on for a v0.1.0 that would hold credentials.
- The roadmap items (sandboxes, context compaction) are the parts that are missing, and they are the parts that matter before an agent gets near a server.

**Should we…**
- ❌ **Skip it** — not relevant, redundant, low quality, or not useful for us

**Impact on our stack:** Low — negative, in fact. It occupies the same slot as Hermes while having none of Hermes's operational history.

**Why:** Same author, same day, same README discipline as Verdict — and the same conclusion. A one-commit Go harness that duplicates the agent runtime we already run in production is not an improvement; it is a migration risk with a demo attached. If one specific feature from it proves out (the provider conformance tests and sandbox profile design are the two worth borrowing conceptually), we take the idea into Hermes, not the binary into the VPS.

## 6. stack-diagram

**What it is:** An agent skill that turns one sentence describing a stack into an architecture diagram with official vendor logos, rendered in light and dark, exported as a self-contained HTML file plus PNG and a React component.

**Source:** https://github.com/caru-ini/stack-diagram · Provenance: GitHub API — agent-skill repos in the last 7 days, 1.1k stars, 27 commits.

**What's good about it:** The output quality is real and the packaging is smart — an HTML file with fonts and logos inlined so it renders offline anywhere, official logos pulled from svgl, devicon, gilbarbara/logos and AWS's own icon set with a stated policy of never recoloring a logo. It has a live gallery site and works across Claude Code, Codex, Cursor and skills-compatible agents.

**Pros:**
- Genuinely well-crafted output: both themes, inlined assets, one file to hand someone.
- MIT for code and docs, with third-party asset licences itemized properly.
- Real examples committed as images (monorepo tooling, AI app, AWS) rather than a claim.

**Cons:**
- **It draws what you tell it, not what you have.** There is no parser, no repo scan, no runtime discovery — you describe the stack in a sentence and it illustrates the sentence. That is a presentation tool, not an architecture tool.
- The single-author signal is weak: 27 commits, one contributor plus Claude, a star-history chart in the README and a gallery-share feature — the shape of a repo built for visibility.
- Our architecture is already documented in prose, and what we lack is a *verified* map (Project Quarry and Floorplan from previous briefs both addressed this), not a prettier rendering of an unverified description.

**Should we…**
- ❌ **Skip it** — not relevant, redundant, low quality, or not useful for us

**Impact on our stack:** Low. It would produce a diagram of the stack someone typed, which for the Unified Platform is exactly the failure mode of documenting what you believe rather than what runs.

**Why:** Wrong unit of truth. A diagram that renders a sentence is useful when you are pitching a system; it is actively harmful when you are trying to find out why the public schedule double-prefixes an API path, because it will happily draw the system as described and hide the discrepancy. The two prior briefs both landed on "we need a map of what is actually mounted and routed" — that requires reading `App.tsx`, the Traefik rules and the dist, not a logo library. The artwork is nice; the job we need done is a different job.

## If we do nothing else, do these, in this order

**1) Run ai-design-check read-only against one Unified Platform page and one `unified-*-redesign-vN.html` file.** It changes how redesign reviews happen: from a verdict after the fact to a finding count per page, naming the specific rule that makes a screen read as generated — before Shareef has to say "not good" a third time.

**2) Stand Kanzo up on the VPS bound to `127.0.0.1` and reach it only over Tailscale.** It changes what agentic-os work looks like: a durable board that cron jobs and agents claim from and comment on, at 10–60 tokens a reply, with a Human lane for anything that needs a decision — instead of work tracking that lives in chat scrollback.

**3) Take trina-ax's permission pattern, not its install.** It changes the design bar for anything staff-facing we build later: enforce file access as the asking person so the AI's answer can never exceed the human's clearance — the one property a residency program assistant cannot ship without.
