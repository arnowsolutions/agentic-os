### AI-agent GitHub malware campaign — poisoned repos that instruct the assistant

**What it is:** Bitdefender Labs documented a campaign of 22 malicious GitHub repositories whose instruction files, hooks and settings are written to persuade AI coding assistants to execute a file called `setup.js`. The payload steals developer credentials and then uses them to spread to other projects.

**Source:** https://www.bitdefender.com/en-us/blog/labs/how-ai-agents-become-new-targets-in-github-malware-campaign  ·  Provenance: Google News RSS (cybersecuritynews.com, 2026-11-18) and Hacker News front-page-adjacent discussion, 2026-11-18/19

**What's good about it:** It names the exact surface we use every day. The attack does not exploit a model bug or a package manager — it exploits the files an agent is *supposed* to read first: `SKILL.md`, `.cursor/rules`, `.claude/settings.json`, git hooks. Once an assistant reads the file, the instruction is treated as project context, not as untrusted input, and the script runs with the developer's own permissions. Bitdefender mapped the chain and tested detection against all 22 samples on Nov 10. The mitigation it implies is procedural and free: read the instruction file before you let anything execute it, and never let an install step run a blob script.

**Pros:**
- Attack surface is precisely ours — daily repo ingestion, skill installs, and cloned repos in `/workspace/agentic-os`.
- Concrete, countable evidence: 22 links, named researcher, mechanism documented end to end.
- The defensive change costs nothing and can be written into our install workflow this week — no product purchase required.
- Reinforces a rule we already half-follow (we read READMEs before adopting) and extends it to hooks and scripts, which we were not checking.

**Cons:**
- Vendor research published by a company that sells the fix (Bitdefender AI Guardian); the detection test is their own product.
- The public write-up gives the mechanism, not a usable IOC list — we cannot retro-scan against hashes from this article alone.
- Nothing in it is specific to Hermes-style skill directories, so the "does this apply to us" mapping is inference, not a documented finding.
- The recommended remedy is commercial endpoint protection, which is the least useful part for a Linux VPS.

**Should we...**
- ✅ **Adopt it** — integrate the practice into our stack: a mandatory pre-install read of `SKILL.md`, hooks, `settings.json` and `package.json` scripts before any repo is cloned into a skill path or executed, plus pinning to a reviewed commit.

**Impact on our stack:** High — the Hermes skill loader and the nightly repo/vault pipeline. Concretely: a review step in the skill install procedure and a refusal to run `setup.js`/`postinstall` blobs from unreviewed repos.

**Why:** We adopt tools faster than any team I know of — this brief alone files repos every night, and the skill directory is the load path into the VPS, the cron scheduler, and through Tailscale, the desktop. That is exactly the position the campaign is built to exploit: not a vulnerability in code we wrote, but trust in a file we asked the agent to read. No tool fixes this; a step does. Read the instruction file, read the hooks, refuse the blob script, pin the commit. It costs ten minutes per install and closes the only path in this brief that could actually hurt us.

### Stitch Loop — an always-on product agent that ships PRs

**What it is:** A Google Labs experiment: a long-running product agent that connects to your GitHub repo plus live product context (logs, behaviour, feedback — 180 integrations, custom MCP servers, or CLI uploads), runs evergreen "loops," and for each opportunity writes code in an isolated cloud sandbox and opens a pull request for approval. Three loops ship by default — cybersecurity, latency, accessibility — and you can add your own.

**Source:** https://blog.google/innovation-and-ai/models-and-research/google-labs/stitch-loop/  ·  Waitlist: https://stitch.google.com/loop/waitlist  ·  Provenance: Google News RSS (blog.google, 2026-11-18); "Early look at Loop" coverage on TestingCatalog the same day

**What's good about it:** It targets the gap nobody else does. Coding agents stop at merge; Loop starts there — it watches the metric, proposes a change with a tradeoff, writes it, opens the PR with screenshots and video of the work, and then keeps watching in case the metric slips. The security loop pairs Gemini 4 Carbon's cyber capability with DeepMind's CodeMender, which is a serious scanner under a decent front end. It exposes itself over an MCP server and a CLI, so a different agent (ours) can pull the same product context instead of duplicating it. Slack `@stitch` for digests means the human review step is one click.

**Pros:**
- The four-step shape — suggest, propose solutions with tradeoffs, build in sandbox, reflect on real metrics — is the loop we do manually in CE audits.
- Human approval gate by design: nothing merges without your review.
- Built-in accessibility loop is directly relevant to the 18 redesign surfaces and the public schedule page.
- MCP/CLI exposure means it can act as a context layer for our own agents rather than replacing them.
- PRs carry screenshots and video, which is exactly what a non-programmer reviewer needs.

**Cons:**
- Waitlist only; Google AI Ultra subscribers get priority — we have no guaranteed access.
- Requires connecting GitHub *and* product telemetry to Google infrastructure. For anything touching scheduling, residents or patient-adjacent data that is a compliance conversation, not a signup.
- No published pricing and no independent benchmarks; the announcement is marketing with a diagram.
- The "reflect" step needs live metrics we do not currently collect on the Unified Platform — without instrumentation it degrades to a code scanner.
- It is another Google-hosted dependency in a stack that already has too many.

**Should we...**
- 👀 **Watch it** — join the waitlist, and build the cheap 20% ourselves in the meantime (a scheduled check that diffs key pages and opens an issue).

**Impact on our stack:** Medium — Unified Platform maintenance. Concretely: a monitoring loop over the 18 redesign surfaces and the public schedule, replacing ad-hoc manual audits.

**Why:** The Unified Platform has 18 surfaces in permanent redesign, a weekly CE audit cycle run by hand, and no continuous check that anything still works after a deploy. Stitch Loop is the first product I've seen that names that exact problem — post-merge, metric-anchored, PR-producing — and the accessibility and latency loops map onto our real complaints. But it is closed, waitlisted, and wants our repo plus telemetry in Google's cloud, which is a decision Shareef has to make, not a config change. Watch it, take the waitlist slot if it comes, and meanwhile implement the same loop with a cron job and a Playwright check — that version needs nobody's permission.

### Gemini 4 Neon — frontier tier at a mid-tier price

**What it is:** Google DeepMind's newest Gemini 4 model, released Nov 18, aimed at fast end-to-end task completion in software engineering, knowledge work and science. 1M-token context, $3 per million input tokens ($0.15 cached), $15 per million output.

**Source:** https://blog.google/innovation-and-ai/models-and-research/gemini-models/introducing-gemini-4-neon/  ·  Provenance: spotted on Paul J Lipsky — https://www.youtube.com/watch?v=AbfheTIO2Ec and Hyperautomation Labs — https://www.youtube.com/watch?v=duPT764-chI; Google News RSS (blog.google, 2026-11-18)

**What's good about it:** It scores 61 on the Artificial Analysis Intelligence Index at its highest thinking setting — #3 overall, the blog claims ahead of the models it is priced against — and #1 on the Artificial Analysis Coding Agent Index (58.6). The 95% discount on cached input is the part that matters for us: cron jobs re-read the same vault dump, the same CRM schema, the same briefing archive on every run, and caching turns that into cents. A 1M window means an entire repo or a year of briefings fits in one call instead of a retrieval dance. Glean's early evaluation claims it matched or beat Gemini 4 Carbon at three times the speed and 60% of the cost, and Google reports its lowest fabrication rate yet in internal Antigravity testing — the failure mode that matters most for an admin assistant.

**Pros:**
- Cached-input pricing at $0.15/M is the cheapest way to keep a large standing context (vault, CRM schema, brand docs) permanently warm.
- 1M context with reported reliable context compaction over long sessions — built for tool-heavy agent runs, not chat.
- Top of the coding-agent index, which is a better proxy for our work than a chat benchmark.
- Same API family as models we already know (Carbon/Hydrogen/Argon were filed earlier this month), so an evaluation is a key and a config line.
- Steerability rank #2 on the new Agent Arena Index — mid-task corrections are a daily reality here.

**Cons:**
- $15/M output is not cheap; a runaway agent loop costs real money, and our cron jobs are exactly the runaway shape.
- The launch page is heavy on partner quotes and vendor-run benchmarks; the three tasks where it loses are named only by third-party reviewers, not by Google.
- Sending anything to a hosted API is a hard no for PHI — this can touch briefs, code and public data, nothing clinical.
- Hyperautomation Labs reports a December 1 pricing change and that Neon replaces Argon in the Gemini app; that detail is not in the blog post and needs checking before we budget on today's numbers.
- No evidence yet on our actual jobs — nobody has run it against a 40-item vault dedupe or a 12-source brief.

**Should we...**
- 👀 **Watch it** — but with a specific test: run one read-heavy cron job on Neon for a week and compare cost and output quality against DeepSeek.

**Impact on our stack:** Medium — Hermes model routing for long-context cron work (the daily brief, CE audits, repo scans).

**Why:** Our crons are context-hungry and repetitive, which is precisely the profile a 1M window with a 95% cache discount is built for — the daily brief re-reads 1,929 vault items and a week of briefings before it writes a word. But we have no measurement of what that costs today, and swapping the model under a running scheduler without a baseline is how you get a silent quality drop. The right move is unglamorous: instrument one job's token spend, run it on Neon for a week, compare. If it holds, it becomes the default for read-heavy work and DeepSeek stays for the cheap chatter.

### Claude Code "Code Mode" — one script instead of twenty tool calls

**What it is:** An experimental, opt-in mode in Claude Code (v2.1.323+) where instead of requesting each Bash, Read or Edit call and reading every result, the model writes a piece of JavaScript that chains those calls in one step, feeds one result into the next, and returns only the output it actually needs to read. Enabled with `CLAUDE_CODE_EXPERIMENTAL_CODE_MODE=1`.

**Source:** https://code.claude.com/docs/en/code-mode  ·  https://www.marktechpost.com/2026/11/17/anthropic-claude-code-code-mode-javascript-tool-calls/  ·  Provenance: Google News RSS (MarkTechPost, 2026-11-17); Anthropic's ClaudeDevs announcement Nov 17

**What's good about it:** It fixes the most expensive inefficiency in agent loops: every tool result goes back into the context window, so a ten-step shell sequence bills you ten round-trips of tokens to learn one fact. Code Mode pays for the instruction once and returns a filtered value. It is the same insight behind Anthropic's Programmatic Tool Calling and Cloudflare's Code Mode, which means it is converging across vendors rather than being one product's quirk. And it is opt-in — one env var, no migration.

**Pros:**
- Directly cuts token spend and latency on multi-step shell work, which is most of what our cron jobs do.
- Filtering at the source means the model sees the answer, not 400 lines of `ls -la`.
- The pattern is portable — nothing stops us implementing the same thing in Hermes' tool layer.
- Opt-in and reversible; no lock-in beyond a flag.

**Cons:**
- Experimental, undocumented failure modes, and the generated code is hidden by default (Ctrl+O to inspect) — bad for auditing what an agent did.
- The script runs with the session's permissions, so a bad generation is a shell script with your access.
- It is Claude Code only; Hermes gets no benefit without building the equivalent ourselves.
- No published evaluation of when it helps versus hurts — small tasks may not amortize the code-writing turn.

**Should we...**
- 👀 **Watch it** — as a design reference for our own tool layer, not as something to install.

**Impact on our stack:** Low today, potentially Medium — Hermes cron tool-calling efficiency if we copy the pattern.

**Why:** Our scheduled jobs are terminal-only by design and routinely run five to ten sequential commands where only one line matters — the dedupe step alone curls the vault, parses JSON, and greps titles. Code Mode is the cleanest statement yet of the alternative: let the model write the orchestration once and return only the answer. We can't install it, but the architectural lesson is free, and it is the kind of change that would cut token spend across every cron job at once.

### Pulsar — a message bus so agents can find each other

**What it is:** An MCP server that gives coding agents running in different harnesses a shared registry: one list, tags, multicast, and a bus so agents can discover each other and send messages rather than working blind.

**Source:** https://github.com/yocontra/pulsar  ·  Provenance: GitHub repository search, created 2026-11-17

**What's good about it:** Multi-agent setups fail at coordination, not at intelligence — two long-running agents doing overlapping work have no way to see each other. Pulsar makes the registry the MCP server itself, so any client that speaks MCP gets discovery for free, with no per-harness plugin. MIT licensed, TypeScript, and written by Eric Schoffstall, who has shipped real open source before (jspm/gulp-era tooling), which is a better signal than the star count.

**Pros:**
- Solves a real gap: cross-harness agent discovery with no vendor buy-in.
- MCP-native, so it works with clients we already run.
- MIT and small enough to read in an afternoon.
- Tagging and multicast are the right primitives for "who is working on the vault right now."

**Cons:**
- Two days old, 50 stars, 17 commits, effectively one author — the definition of too early.
- No test or CI evidence I could verify from the repo metadata.
- Adds an always-on internal messaging channel on the VPS; another daemon to secure and monitor.
- We do not currently run parallel coding agents, so the problem it solves is latent for us.
- Twenty-two MCP servers already in our config; adding another has a real cognitive cost.

**Should we...**
- 👀 **Watch it** — right idea, wrong maturity. Revisit in a month if it still has commits.

**Impact on our stack:** Low — Hermes subagent coordination, if we ever run them concurrently.

**Why:** Hermes already spawns subagents, and the moment two of them run at once — a deploy and a brief, say — they have no way to know about each other and will happily fight over the same files. Pulsar is the smallest credible answer to that, and being MCP-native means it would not require touching Hermes' internals. But 17 commits from one person in 48 hours is a prototype, not infrastructure, and our MCP surface is already crowded. Watch it for a month; if it holds up, it is a two-hour integration.

### Sellbird — cold outreach at volume (skip)

**What it is:** An open-source (AGPL-3.0) AI outreach platform, formerly called Harvey: it finds companies and decision makers, verifies emails, writes personalized cold email, sends it, and handles the replies — running on your Claude or ChatGPT plan rather than per-token API billing.

**Source:** https://github.com/ethanplusai/sellbird  ·  Provenance: spotted on The Next New Thing — https://www.youtube.com/watch?v=-rcNy4nN2lM (chapter 0:38)

**What's good about it:** As a piece of engineering it is real: 6,594 stars, active commits through Nov 18, Python, a complete pipeline from prospecting to reply handling, and a clever cost model (drive it from a consumer LLM subscription instead of API tokens). The workflow is genuinely end-to-end — most "AI sales" repos stop at list generation.

**Pros:**
- Complete pipeline: find, verify, write, send, reply — not a demo that stops halfway.
- Uses an existing LLM plan instead of metered API calls, which is a real cost trick.
- Active development and a large, engaged audience.
- Python and AGPL, so it is forkable if someone ever needed the pieces.

**Cons:**
- Unsolicited cold email at volume from a Montefiore domain is a deliverability and compliance problem, not a growth tactic.
- AGPL-3.0: run it as a network service and our modifications must be published.
- It needs a logged-in Claude/ChatGPT session — it cannot live on the VPS without putting real account credentials on a datacenter IP.
- Zero overlap with residency operations, GME compliance, scheduling or the CRM.

**Should we...**
- ❌ **Skip it** — wrong domain, wrong risk profile.

**Impact on our stack:** None.

**Why:** The one thing Sellbird does well — automated outreach at volume — is the one thing a hospital department should never point at the outside world. Faculty recruitment, resident communication and patient contact each carry legal constraints a cold-email bot has no model of, and the deliverability damage to a montefiore.org sending domain would be immediate and hard to undo. It is filed here only so it is never suggested again. The other repos named in that same episode — Chatwoot, Mautic, Plane, GrowthBook, Formbricks, Meilisearch, Novu, Papermark — are established platforms, not new this week, and none of them fills a gap we have.

## Overall assessment

If we do nothing else, do these, in this order:

1. **Write the pre-install review step into the skill/repo workflow** — reads `SKILL.md`, hooks and `settings.json` before anything executes, and refuses blob `setup.js` runs. It costs ten minutes and closes the only live security path in this brief.

3. **A/B Gemini 4 Neon on one read-heavy cron job** — baseline the tokens first, then a week on Neon. If the cached-input discount holds on our vault-sized context, it becomes the default for the brief and the audits.

Nothing else this week is worth acting on. The two model launches (Neon, MAI Code 2) mostly matter for what they do to prices, Code Mode is an idea we can copy but not install, and Pulsar is a month away from being a decision.
